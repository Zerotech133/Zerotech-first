| 层 | 组件 | 接口（生产前缀 `http://rookie.xtcloud-tech.com:43083`） |

## 四、接入方案（临界用菜鸟登录）

### 推荐架构：临界作为 OAuth2 资源服务器（远程校验模式）

```
浏览器 → 临界登录页（新增）
  → POST {菜鸟}/admin-api/system/auth/login（账密/验证码由菜鸟处理）
  ← { accessToken, refreshToken, userId }
浏览器存 token（localStorage + Bearer 头）
  → 临界 API 全部请求带 Authorization: Bearer <accessToken>
portal_api.py 新增校验中间层：
  → POST {菜鸟}/admin-api/system/oauth2/check-token（token + client-id/client-secret）
  ← 有效 → 放行并取 userId；无效/过期 → 401 → 前端引导刷新/重登
  （校验结果本地缓存 60s，避免每请求一跳）
```

### 分阶段

| 阶段 | 内容 | 说明 |
|------|------|------|
| P1 | portal_api.py 加 `check-token` 校验层 + 登录页（临界纯转发，不存密码） | 现有 `X-Portal-Token` 保留为**机器通道**（Agent/自动化脚本非人，不登录）；登录体系只管浏览器里的人 |
| P2 | token 缓存 + refresh-token 自动续期 + 401 拦截重登 | |
| P3（可选） | 换标准授权码模式（`/oauth2/authorize`），临界在菜鸟注册为 OAuth2 Client | 多客户端/细粒度权限时再做 |

### 前提与风险

1. **网络可达**【⚠️推断】：本机未部署菜鸟，须确认到 `rookie.xtcloud-tech.com:43083`（或内网 10.204.0.253）的可达性与鉴权 client 凭据；若临界要与菜鸟同域部署，需先本地化部署 thunder-server。
2. **降级策略**：菜鸟不可达时，沿用现有"本机可信域放行"逻辑（127.0.0.1 直连不依赖登录），避免量化产线被登录系统故障连带【✅与现有 P0-1b 设计一致】。
3. **账号体系选择**：临界用户属管理/员工性质 → 用 **Admin 体系**；未来若开 C 端（会员/客户看战绩）→ 再接 member 体系（短信/微信登录）。
4. **权限映射**：临界暂无 RBAC，P1 只验"登录有效"，不映射菜单/按钮权限，改动面最小。
