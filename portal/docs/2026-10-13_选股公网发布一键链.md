# 选股公网发布一键链（publish_picks.py）

**日期**：2026-10-13 23:40
**背景事故**：16:44 发布后，picks_public 快照 22:53 又刷新过，但 deploy 未重新执行，线上滞留旧版。`sync_publish.py` 只做本地快照刷新，deploy 是"另行触发"的第二步，两步间无状态衔接。

## 方案

新增 `portal/publish_picks.py`（零第三方依赖），把本地能做的链路一步做完：

1. 调 `sync_publish.py` 刷新 `picks_public/` 快照（透传输出与退出码，失败即中止）
2. 校验关键文件存在（picks.html / tokens.css / todays_picks.json），计算 sha256
3. 状态留痕到 `work/publish_state.json`（时间、hash、sync 统计、deploy_confirmed），供下次对比与审计
4. `--check-online` 时直连线上（绕系统代理）逐文件拉取比对（v1.1：picks.html + data/todays_picks.json），任一不一致即明确回答"线上是否滞后"

## 用法

```bash
python publish_picks.py                   # 同步 + 状态记录
python publish_picks.py --check-online    # 追加线上比对，报告是否需要重新发布
```

退出码：`0` 一切正常（含"线上已是最新"）；`2` 线上滞后需要重新 deploy；其余非 0 为异常。

## 边界说明（重要）

- WorkBuddy 站点发布（CloudStudio Gateway deploy）是 **agent 侧动作**，无法从本机脚本直接触发。
- 结论为"线上滞后"时，让 agent 重新发布即可（对 agent 说"重新发布 picks"）；目录/入口/appId 不变，分享链接不变。

## 自测记录

- 正向：全链跑通 EXIT=0，线上/本地 hash 一致（1d8172ef...106e6）。
- 负向注入（快照副本加字节）：被第 1 步 sync 静默修复，未触发滞后分支 —— 说明快照副本漂移不是真实风险面。
- 负向注入（**源头** portal/picks.html 加字节）：正确触发 `[滞后]` EXIT=2，双向 hash 打印无误；源头按字节复原后复跑 EXIT=0。

## 看门狗层（publish_watchdog.py，23:45 追加）

平台自动化 4cbbeed8 每天 16:40 跑 sync+条件发布，同日更晚的快照刷新不在其窗内，且 deploy 只能 agent 侧触发。新增 `publish_watchdog.py` 兜底：

- 巡检：跑 `publish_picks.py --check-online`；退出码 0 → 记 `work/publish_watchdog.log`；此前有 `work/DEPLOY_PENDING.json` 旗标则清除并发绿色"已恢复"卡片
- 滞后（退出码 2）：落 DEPLOY_PENDING 旗标 + 发红色飞书卡片给老田（提示"对 agent 说：重新发布 picks"，含双向 hash 前 16 位）
- 链路异常（其他非 0）：橙色告警卡
- `--install` / `--uninstall`：注册/删除每日 23:30 计划任务 `x5-picks-publish-check`（schtasks，unicode 参数列表防中文路径乱码）

**E2E 自测（23:45）**：源头注入漂移 → EXIT=2、旗标落盘、红色告警发出；源头按字节复原 → EXIT=0、旗标清除、绿色恢复卡（飞书 `code=0 success`）。

**注册受阻**：`schtasks.exe` 在安全中心程序黑名单（sandbox 明确拒绝且禁止绕过）。两条出路：
1. 安全中心 → 命令安全 → 程序黑名单移除 `schtasks.exe` 后，跑 `python publish_watchdog.py --install`（我可代跑）
2. 更优：更新平台自动化 `4cbbeed8` 为每日两次（16:45 / 23:45，rrule `FREQ=DAILY;BYHOUR=16,23;BYMINUTE=45`），提示词改用 `publish_picks.py --check-online`，EXIT=2 时 agent 直接 deploy——本会话 automation 工具不可用，待可用会话执行
