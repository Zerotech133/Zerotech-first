## 三、重叠风险与重复建设判定

### ★ 重点判定：strategy_runtime.py（A 批在途）vs run_shadow.py 超时包裹（已提交 e727b4f5 09:13）

两份实现解决**同一主题**：给 `registry.run(strategy_id, context)` 包运行期超时，防单个策略 propose 死循环拖死宿主进程。

| 维度 | run_shadow.py `_propose_with_timeout`（已提交） | strategy_runtime.py `run_strategy`（在途） |
|---|---|---|
| 签名 | `_propose_with_timeout(registry, strategy_id, context, timeout_s=None)`；批量口 `_collect_verdicts(registry, context, timeout_s=None)` | `run_strategy(registry, strategy_id, context, timeout_s=None, allow_deprecated=False)` + `StrategyRuntime` 类封装 + `readonly_context()` |
| 并发机制 | 裸 daemon Thread + 结果盒 + `t.join(timeout_s)` | ThreadPoolExecutor(1 worker) + `future.result(timeout)` + `cancel_futures` |
| 超时后语义 | fail-open：返回 None，stderr 一行诊断，调用方计数跳过 | fail-visible：结构化 result（status="timeout"，error 注明「后台线程无法强杀」） |
| 生命周期门 | 无（信任受理层） | 有：experimental/active 放行，deprecated 需显式 `allow_deprecated`，retired 拒绝 |
| context 隔离 | 无 | 递归只读快照 + 循环引用检测 |
| 缺省超时 | 模块级 PROPOSE_TIMEOUT_S（None 哨兵，monkeypatch 友好） | _DEFAULT_TIMEOUT_S=10.0 |

**判定：构成重复建设，且两份实现的技术口径直接矛盾。**

关键证据：run_shadow.py:193-195 docstring 已明文裁决——「不用 ThreadPoolExecutor：其 worker 线程 3.9+ 为非 daemon 且解释器退出时会 join 全部 worker——死循环插件会把整个进程挂在 exit 上，与『防拖死』目标自相矛盾」。而 strategy_runtime.py 恰恰采用了 ThreadPoolExecutor（strategy_runtime.py:100-101）：其超时后 `shutdown(wait=False)` 只是不等待，但 CPython 的 `concurrent.futures.thread` 模块在解释器退出时会 join 全部 worker 线程（`threading._register_atexit` 注册的 `_python_exit`）——**若策略真死循环，进程退出照样挂死**，正是 run_shadow 警告过的缺陷。

**建议（供老田对表裁决，不指挥任何会话）**：
1. 两件不得在同一批并行收敛；第三会话 strategy_runtime 若上岗，应吸收 run_shadow 的 daemon-thread 退出语义论证，或实测排除 Executor 退出 join 挂死路径（如超时后改用裸线程执行）。
2. 职责面其实可分：run_shadow 服务影子 run 批量收集（fail-open 保主链），strategy_runtime 是带生命周期门+只读 context 的通用隔离门（功能超集）。收敛方向建议「strategy_runtime 修机制后成为唯一口径，run_shadow 改为调用它」，避免第三份实现再冒出来。
3. `tools/run_strategy_shadow.py` 与已提交 `agent_platform/run_shadow.py` 文件名高度相近，属操作事故高危（add/编辑错文件），建议其中之一更名。——【已执行 2026-10-18 拍板 02】已更名 tools/strategy_drill_cli.py
