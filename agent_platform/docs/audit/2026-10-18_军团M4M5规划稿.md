## 二、军团-M4：绩效闭环（对账自动化 + 观察线）【建议，待拍板】

### 2.1 范围

1. **对账自动化**：codex_ 系插件（首个 = `codex_sma20_rsi14`）影子首跑产出 `strategy_runs.jsonl` 判决行后，把 `tools/verify_strategy_ledger.py` 三方对账（幂等键完好 / run_id 双向可查 / 证据覆盖，退出码 0=PASS／1=FAIL／2=参数缺失）接入固定触发点。
   - 【建议】触发点 = 周一巡检（monday_checkpoint）**附加观察行**：对齐 2026-10-18 c5990a23 判例——附加观察行**不入门 3 判据**、零退出码影响，FAIL 时 fail-visible 留档人工看，属可逆增项。
2. **codex_ 系观察档**：对账之外，对 codex_ 系插件产出一份**只读观察档**（建议落 `data/codex_bridge/observation/`，append-only）：
   - 逐窗口记录 codex_ 系各 strategy_id 的判决行数、命中率/方向分布等**原始计数**（不做加权评分）；
   - **绩效分位数是否进 reject 限频依据——本文给建议但不自动生效**：连续 N 个观察窗口（建议 N=2，窗口=自然周）在 codex_ 系内垫底者标记「观察」。标记**只留痕，不自动除名、不自动禁用、不自动拒新提交**——是否把垫底标记升级为该 strategy_id 新提交/改版提交的限频依据（reject 阶段新增一条判据），由老田单独拍板后施工。
3. **边界自证**：M4 全程零写面（复用 verify_strategy_ledger 的「连 mkdir 都不做」判例）；观察档是唯一新增写入物，且只增不删。

## 三、军团-M5：网关化（CLI 工单受理接口 + Linux 平移清单）【建议，待拍板】

### 3.1 范围：受理口形态收敛

现状：`process_submission(bridge_dir, submit_id, source, registry, data_root, sandbox_timeout_s, daily_limit)` 是进程内函数，调用方手工传参。M5 把它升级为 **Codex CLI 工单驱动的受理接口**：

1. **CLI 受理薄壳**【建议】：新增 argparse 入口（形如 `python -m adapters.codex_bridge --submit-id <id> --source <py 文件路径> --data-root <root> [--daily-limit N]`），内部**仍走 process_submission 原函数**，零新管线、零新校验逻辑；
2. **限频就绪前置**：daily_limit 从「调用方记得传」升级为**网关配置默认值**（建议默认 ≤3/日，对齐设计稿 §5 风险 6「每 Codex 会话 ≤3 次」；显式传参可覆盖，向后兼容 None=不限频不变）；
3. **单向反馈通道**（R1 在接口层的落实）：受理接口对提交方的全部反馈 = `rejects/<YYYYMMDD>/<submit_id>.md` 档案 + stderr 提示，**不回传 AP 内部状态、账本、registry 句柄**；通过也不发通知（影子 run 数据即通过证明，设计稿 §3.1 口径平移）；
4. **零凭据前置**（R2）：受理接口自身不读取不持有任何凭据；源码门 CRED_PATTERN 判据原样生效。

### 3.2 明确不做（网关化的负空间）

- **不开网络端口**：不做 HTTP/RPC 受理服务，远程提交不在本里程碑（若老田未来要远程受理，另立拍板件）；
- **不做编排**：不碰 Hermes Kanban、不做多策略组合；
- **不加执行路径**：不碰 K-STOCK execution 域，`execution_allowed` 恒 False 的契约零接触。

### 3.3 Linux 轮真 rlimit / Job Object 平移清单

M3 在 Windows 的口径：无 `resource` 模块，死循环由墙钟超时击杀（语义覆盖 CPU 上限），真 rlimit 留 Linux 部署轮。平移清单（逐条标注 Windows 语义 → Linux 替代 → 验证判据）：

| # | 项 | Windows 现状（M3） | Linux 目标 | 验证判据 |
|---|---|---|---|---|
| 1 | CPU 上限 | 墙钟超时（`sandbox_trial` timeout_s=10.0，kill+收割） | `resource.setrlimit(RLIMIT_CPU, ...)` 子进程级 | 死循环样本被 rlimit 击杀（SIGXCPU），elapsed_ms < 墙钟上限 |
| 2 | 内存上限 | 无（行数/字节静态上限间接压缩） | `resource.setrlimit(RLIMIT_AS, ...)` | 大内存样本（构造大 list）被 MemoryError 拦截，宿主进程不受影响 |
| 3 | 文件写 | 白名单 import 已禁 open/shutil 等写面 | 同左（白名单口径**不放松**，不引入容器/命名空间复杂度） | 恶意样本集回归测试全绿 |
| 4 | 禁网 | 白名单 import 挡 socket 系 | 同左；不新增网络命名空间（复杂度不划算） | 恶意样本集回归测试全绿 |
| 5 | 墙钟超时 | 唯一击杀手段 | **保留为兜底**（rlimit 之外的第二道，防 rlimit 覆盖不到的 IO 阻塞） | rlimit 生效后墙钟兜底样本仍被拦 |
| 6 | 基线对比 | sandbox_ms 入 registrations.jsonl | 同 schema 延续，跨平台 sandbox_ms 可对比 | 同一试点策略两平台耗时差可从账本直读 |
| 7 | Job Object | 未用（Windows 原生方案备选） | —（Linux 用 rlimit 即可；Windows 轮如需内存上限可评估 Job Object，另行拍板） | — |

### 3.4 验收判据（可测）

1. CLI 受理入口提交一个合规插件，行为与现函数路径一致：inbox→processed 移档、registrations.jsonl 行 schema（submit_id/strategy_id/registered_at/sandbox_ms）不变；
2. daily_limit 配置化：默认值从配置读入，达限时拒绝 fail-visible 落档 stage=限频、inbox 不动（现实现口径实测保持）；
3. 单向自证：grep 受理接口代码，除 rejects 档写入与 stderr 外无任何回传通道（无 print 返回数据结构给调用方以外的出口）；
4. Linux 平移清单 §3.3 七条逐条落地或显式标注「另行拍板」；死循环 + 大内存两个对抗样本在 Linux 门被拦，Windows 全仓 638 绿不受影响；
5. 受理入口收敛为唯一路径：绕过 CLI 直调函数的调用点（若有）在平移清单中显式列名，grep 可审计（对齐设计稿 §5 风险 4）。

### 3.5 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| 1 | CLI 入口引入后出现双受理路径（直调函数绕过限频） | 入口收敛唯一化 + 直调点列名审计（判据 5）；限频计数口径（registrations+rejects 同日合计）在函数层，绕 CLI 也绕不过 |
| 2 | 配置默认值过松/过严 | 建议默认 3/日，老田拍板数值；显式传参可覆盖，None 向后兼容 |
| 3 | Linux rlimit 语义与墙钟差异导致验收口径漂移 | §3.3 清单每条带验证判据；墙钟兜底保留；sandbox_ms 双平台基线对比 |
| 4 | 网关化被理解成「开服务」越权 | §3.2 负空间显式声明不开端口不远程；远程受理另立拍板件 |
