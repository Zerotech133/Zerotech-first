### A. zhice-os-v2 agent_platform（无 .git，直接读码）

#### A1.【P1】watch_daemon `_cn_daily_cache` 负缓存：瞬时失败被永久缓存

- 位置：`runtime/watch_daemon.py:223-235`（`_cn_daily_loader`）
- 问题：`loader()` 对 `load_cn_daily()` 的返回值不区分成败直接 `cache[symbol] = df`。`load_cn_daily`（:298-330）在 DB 异常/无数据时**返回 None**，None 会被写入缓存——该 symbol 的日线在整个进程生命周期内永远缺失，趋势/事件方法持续降级 15m 重采样，且无任何重试路径（daemon 常驻）。
- 依据：读码 `watch_daemon.py:228-234`（`cache[symbol] = df` 无 None 判断）+ `:322-328`（异常路径 `return None` 后仍走到 `cache[symbol] = df`？——实际 316 行 `with shared_engine(...)` 异常被 328 行 except 捕获返回 None，loader 拿到 None 照样入缓存）。
- 建议修法（一句话）：`load_cn_daily` 返回 None 时不入缓存（或加 TTL/失败重试上限）。

#### A2.【P2】shared_engine 按 raw db_url 字符串分键，存在 URL 形态漂移两池风险

- 位置：`db.py:36-52`（`_engine_cache`/`shared_engine`）
- 问题：键为原始字符串。同一 PG 库以下写法会各建一个池：`postgresql+psycopg2://` vs `postgresql://`、查询参数顺序/末尾斜杠、`_default_db_url()`（config.py:28-42）的 settings 值 vs `ZHICE_DB_URL` env 回退 vs 硬编码兜底——三条路径值不同即两池。缓解事实：当前全部五个调用点（cli.py:174/267、watch_daemon.py:232、backtest/engine.py:83→320/372、case_writer.py:173→load_minutes）的 url 均派生自同一 `AgentPlatformConfig().db_url`（`get_settings()` 有进程内缓存，同进程值稳定），实际漂移概率低。
- 隐患点：`learning/case_writer.py:211-214` 重复实现了一个同名 `_default_db_url`（转调 AgentPlatformConfig，行为目前一致但属第二真相源）。
- 建议修法（一句话）：键改用 `sqlalchemy.engine.make_url(url)` 规范化（如 `render_as_string(hide_password=False)`），并合并 case_writer 的 `_default_db_url` 到 config 单一来源。

#### A3.【P2】shared_engine 无 dispose 出口；与 make_engine 并存无警示，误用面仍在

- 位置：`db.py:36-52`；对照 `db.py:28-33`（make_engine 仍每次新建）；cli.py:403/455/564/592/656 五处仍走 make_engine。
- 问题：(a) 引擎无 `dispose_shared_engines()`，进程退出连接靠 OS 回收；常驻进程若 URL 中途变更，旧池（默认 5+10 连接）不释放。(b) `make_engine` 未收敛也未加「一次性/勿在循环内调用」警示，与 shared_engine 并存——本次 5446 连接耗尽的病灶（临时 engine 用完即弃）在 cli 各命令里仍以同样模式存在（一次性 CLI 可接受，但无任何注释说明边界），后续长驻代码复用该模式即复发。
- 依据：读码两函数体及调用点清单（grep create_engine/make_engine/shared_engine 全量核对）。
- 建议修法（一句话）：提供 `dispose_shared_engines()`（含 atexit），make_engine docstring 标注「仅一次性 CLI 用，循环/常驻场景必须用 shared_engine」。

#### A4.【P2】`create_aw_tables` 返回值语义错误：恒返回 metadata 表总数，非「本次新建表数」

- 位置：`db.py:86-91`
- 问题：`before = set(AwBase.metadata.tables.keys())` 取自 ORM metadata（静态注册表），`create_all` 不回写 metadata，故 `len(before)` 恒等于注册表总数（5），docstring「返回本次新建的表数」失实。调用方若按返回值判断「是否新建过表」会得到错误结论。
- 依据：读码 + SQLAlchemy 语义（create_all 对比 DB inspector，不修改 metadata）；可用受管 python `inspect(AwBase.metadata.tables)` 只读验证（未连库即已确认键集合静态）。
- 建议修法（一句话）：用 `sa_inspect(engine).get_table_names()` 对比前后差集取真实新建数，或改文档为「返回 aw_* 注册表总数」。

#### A5.【P2】ack_server 请求体长度未设上限且负值未拒绝

- 位置：`learning/ack_server.py:58-60`
- 问题：`length = int(self.headers.get("Content-Length") or 0)` 后 `self.rfile.read(length)`：length 为负（如 `-1`）时 `read(-1)` 语义为「读到 EOF」，恶意/畸形本机请求可令 handler 线程阻塞挂起；无上限时大 body 无界读入内存。服务绑 127.0.0.1 且默认无 token（本机进程可打），风险有限。
- 建议修法（一句话）：`if length <= 0 or length > MAX: 400`（上限如 64KB）。

#### B1.【P1】scan_secrets sk- 双正则对同一 span 重复计数 + 无边界（12 处噪声根因）

- 位置：`agent_platform/tools/scan_secrets.py:31-32`
- 问题：`SK_KEY = sk-[A-Za-z0-9]{16,}` 与 `SK_KEY_SEP = sk-[A-Za-z0-9][A-Za-z0-9._-]{15,}` 均无左右边界，对同一 span **各自命中一次**；左侧无边界使计划任务名（如 `…task-sk-…`）这类「连字符拼接」也被当成疑似密钥。
- 实证（只读 python 片段，2026-10-18 实跑）：
  - 输入 `xxx-task-sk-<16位alnum>`：SK_KEY 命中 1、SK_KEY_SEP 命中 1，合计 **2 hits / 同一 span** → 12 处命中 ≈ 6 个任务名 span × 2，与 ae53aeec「12 处核实为计划任务名误报」的计数完全吻合。
  - 验证过的修法正则：`(?<![A-Za-z0-9_-])sk-[A-Za-z0-9][A-Za-z0-9._-]{15,}(?![A-Za-z0-9._-])` ——任务名不再命中，真 key（含引号内、Bearer 后）仍命中。

- 建议修法（一句话）：SK 两条合并为上述单条边界正则，去重策略按 span 合并多类别命中。
