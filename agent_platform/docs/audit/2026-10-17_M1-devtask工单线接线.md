## 二、领域语义定稿（devtask 线）

| 分工 | 载体 | 读写权 |
| --- | --- | --- |
| 状态真源（不动） | `.worktrees/tasks.json`（dict，键=工单 ID） | devtask.py 机器通道 + 本模块人工通道 |
| 机器通道（不动） | tools/devtask.py：cmd_new(doing)/cmd_merge(三守卫→done)/cmd_drop(aborted) | 零侵入 |
| 人工通道（本模块） | 三条带凭据受控转移 | 先落 Approval 再改真源 |

- 状态机（devtask 原生值）：doing → review → done；doing/review→aborted 受门；
  review→doing 打回受门留痕；done/aborted 终态。
- 三条人工通道（devtask 没有的治理动作）：
  1. **弃单门** `approve <tid> aborted`（reason 强制）——放弃工单=放弃已投入
     worktree/分支，凭据留痕；
  2. **打回返工** `approve <tid> doing`——评审未过退回，谁/何时/为何留痕；
  3. **合并漂移修复** `approve <tid> done`——K-ORG-064 场景（代码已进 master
     但状态卡 review），前置校验合并证据（merged 时间戳或 git
     `merge task/<tid>` 提交），无证据拒绝（防跳过三守卫用审批门洗白）。
- **审计分类学**（done 主通道是机器三守卫，不做「状态⇒凭据」强制）：
  violations=merged_but_review 漂移 + 在办工单 worktree 缺失；findings=
  legacy_done 存量 grandfather（实测 4 条）/review_pending（实测 K-PUSH-005~008
  四单）/unapproved_drops（实测 47 条历史弃单，cmd_drop 合法通道）。

## 三、★新判例：catch-up 需真源消费标记（last_wiring_key）

轮次化幂等键（Invest 判例）在 devtask 特有场景失灵：**打回与重批是同一转移**
（review→doing 打回，返工后 review→doing 再打回），无中间凭据可区分
「崩溃窗口」（凭据落了真源没写）与「第二轮批准」。静态 JSON + append-only
账本缺时间关联，无法靠账本自身判定。

解法：真源条目加 `last_wiring_key` 字段（_apply_status 写入时记录已消费的
幂等键）。判定规则：
- 最新凭据恰是本转移 **且** `last_wiring_key != 该凭据键` → catch-up 补齐；
- 最新凭据已消费（`last_wiring_key == 该键`）但真源又回到 from → 新轮次
  （#r{n+1} 新凭据）；
- 无中间凭据场景（Invest 的 reviewed→drafted→reviewed 有打回凭据夹层）不
  受影响。

> 回灌建议：gzh/academy/invest 打回重批语义统一回灌 last_wiring_key 方案
> （invest 现行「最新凭据+转移匹配」判据在有中间凭据时正确，同转移反复场景
> 仍需消费标记）。
