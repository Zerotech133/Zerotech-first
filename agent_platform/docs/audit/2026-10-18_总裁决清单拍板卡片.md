**现状一句话**：两份实现解决同一主题（给 `registry.run` 包运行期超时），技术口径直接矛盾——已提交的 run_shadow.py `_propose_with_timeout`（daemon Thread + fail-open）docstring 明文裁决不用 ThreadPoolExecutor，而在途的 engine/strategy_runtime.py `run_strategy` 恰恰在用。

**实证摘录**（只读摘录，未动代码）：

run_shadow.py:188-195（docstring 即裁决）+ :212-215（实现）：

```python
188    口径与理由（docstring 即裁决）：
189    - Python 线程无法强杀：超时后 worker 线程继续后台跑（GIL 下 CPU 死循环
190      杀不掉），随进程生命周期回收（daemon 线程，进程退出即终止）——僵尸
191      线程可接受：受理时 M3 已挡一轮，运行期长尾用「跳过」兜底即可，不值得
192      为强杀引入子进程隔离的复杂度。
193    - 不用 ThreadPoolExecutor：其 worker 线程 3.9+ 为非 daemon 且解释器
194      退出时会 join 全部 worker——死循环插件会把整个进程挂在 exit 上，
195      与「防拖死」目标自相矛盾。故用裸 daemon Thread + 结果盒语义。
...
212    t = threading.Thread(target=_work, name="shadow-propose-%s" % strategy_id,
213                         daemon=True)
214    t.start()
215    t.join(timeout_s)
```

engine/strategy_runtime.py:100-114（在途，恰用被裁决否定的机制）：

```python
100    executor = ThreadPoolExecutor(max_workers=1,
101                                   thread_name_prefix="strategy-runtime")
102    future = executor.submit(registry.run, strategy_id, readonly)
103    try:
104        verdict = future.result(timeout=timeout_s)
105    except TimeoutError:
106        future.cancel()
107        executor.shutdown(wait=False, cancel_futures=True)
...
```

矛盾点核实：strategy_runtime 超时后虽 `shutdown(wait=False, cancel_futures=True)`，但 Python 3.9+ 的 ThreadPoolExecutor worker 非 daemon，解释器退出时 `concurrent.futures.thread` 的 atexit hook 仍会 join 全部 worker——死循环插件场景下，run_shadow docstring:193-194 警告的「整个进程挂在 exit 上」路径依然存在，与 run_shadow 的裁决直接冲突。

- **C**：观察点前两件冻结不动，周一后再收敛。

**lead 建议**：清单建议 A（冲突地图 §三重点判定原建议）。补一条执行约束：周一预演基线 2d86f26d（675 测试绿）是按 run_shadow.py 现状预演的，观察点前动任一侧都会打破基线——故推荐 **A+C 组合**：现在拍 A 定下唯一口径方向，实施窗口排周一观察点之后，观察点前按 C 冻结。
