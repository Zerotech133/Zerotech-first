## 二、方案层

### 方案 A：就地 git init（推荐度 ★★★★★）

- 做法：在 `C:\项目\zhice-os-v2-windows-20260920\` init，先补 ignore（§1.4 三项），然后 commit。
- 基线建议：**单 commit 作为基线（含 T 路修复）**，不做「先 commit 快照原状再 commit 修复」两段式 —— 因为 T 路 6 文件的修复前原状已不可考（mtime 已覆盖、无备份），两段式中的「原状 commit」无法还原，强行分开只会制造假 diff。
- 利：立即获得版本保护，覆盖全部在途改动（含他人的）；py312 editable 指向不变，零迁移风险；T 路改动随首个 commit 固化。
- 弊：丢失原仓历史（本来也没有，此弊为 0）；基线混杂多流改动，回滚粒度粗 —— 但这是现状欠账，不是方案缺陷。
- 后续可按需迁移到远程或与真正的上游仓对账。

### 方案 B：移植到正主仓（推荐度 ★☆☆☆☆，当前不可行）

- 前提「找到正主仓」**不成立**。仅当老田提供远程仓库或其他机器上的原仓时才可启用。
- 届时做法：以 T 路报告中的 6 文件 diff 为准，在正主仓重放；快照内其他流的改动需按 1.3 清单逐流确认归属，不可盲拷。
- 风险：快照与原仓自 09-20 起已分叉近一个月（约 50 文件），diff 移植可能有冲突。

### 方案 C：维持无版本状态（推荐度 ☆☆☆☆☆，不推荐）

- 风险明确：① 多路在途改动无基线，任何一路误删/误覆盖（尤其 `.venv_new` 重建类运维操作）**不可恢复**；② T 路 PG 泄漏修复随时可能被后续操作冲掉且无从追责/回滚；③ 多智能体并行会话（见 10-18 并行会话冲突地图）下风险持续放大。
