## 判例 1 · agent 自我状态失实（长会话 git 自述不可信）

**日期**：2026-10-18　**域**：多会话协作 / 状态取证

**案情**：长会话子代理两次把「自己早期回合写的文件」误报为「主会话并发修改」向上请示；随后又自述「两个 ps1 未 commit」，而实际早已自行 commit。

**实证**：mtime、git log、git diff 三重独立取证坐实——文件写入时间与该代理早期回合吻合（非并发方所为）；git log 中已有其本人的 commit 记录，工作区并无该两文件的未提交改动。代理的自我状态叙述与仓库事实不符。

**纪律**：**长会话 agent 的 git/状态自述不可信，收口方必须 git log + diff 独立取证后再采信。** 涉及「谁写的 / 提没提交 / 是否并发冲突」类请示，一律以仓库事实为准，不以叙述为准。

## 判例 2 · 全仓 pytest 口径陷阱（历史基线 = scoped 口径）

**日期**：2026-10-18　**域**：测试 / 环境口径

**案情**：pytest.ini 无 testpaths 时，在仓根做全量收集会踩中 osint_video 等缺依赖目录，产生 150 error + capture tmpfile closed 崩溃，容易被误判为「代码坏了」。

**实证**：错误全部集中在缺依赖目录的收集阶段（collection error），与被测代码本身无关；改用 scoped 口径后 agent_platform 域测试正常。

**纪律**：**历史基线口径 = scoped `pytest agent_platform -q --timeout=60`，不在仓根做全量收集。** 受管 venv 缺 pytest-timeout 时改用系统 Python311 跑同一口径。跑测前先确认口径，异常先分清「收集失败」与「断言失败」。

## 判例 3 · sweep 撞车实证（共享仓库 commit 必须显式 pathspec）

**日期**：2026-10-18　**域**：多会话协作 / git 纪律

**案情**：rate-opt 工位提交时把他人未提交的 v1.4 改动一并 swept 进自己的 commit；外部会话随后发现自己只剩一个 199 行测试文件可提。

**实证**：特征码与测试分属两个 commit——内容零丢失，但**归属被搅浑**：v1.4 的改动挂在 rate-opt 名下，外部会话的提交面被剥离。git log 逐 commit 核对文件清单坐实。

**纪律**：**共享仓库 commit 必须显式 pathspec（`git commit -o -- <paths>`），禁止裸 `git add -A && git commit`。** 提交前 `git status` 对表，凡非本人改动一律留在工作区不碰。

## 判例 4 · 假绿缺口——等待/判定条件必须带新鲜度维度

**日期**：2026-10-18　**域**：守望工具 / 判定逻辑

**案情**：守望工具只校验日报 15 键内容，无 mtime 新鲜度判据。14:41 的冒烟残留 JSON 在 19:00 真实失败发生时被误判 PASS——「过键但是旧数据」造成的假绿。

**实证**：残留 JSON 的 mtime（14:41）与判定时点（19:00）间隔远超一个观察周期，键内容却全过——内容判据本身无法区分「今天的日报」与「上午的残留」。

**修复**：report_is_fresh()（当日 18:50 阈值）；判定序固定为：缺失 → UNKNOWN → 键不过 → FAIL → 过键但陈旧 → UNKNOWN → 过键且新鲜 → PASS。

**纪律**：**等待/判定条件必须带新鲜度维度。** 与「等待条件与最终断言同源」同族：凡「等一个信号再判定」的结构，必须同时校验信号的时间新鲜性，否则残留物即假绿。

## 判例 5 · 冷加载超时假象与静默死亡（超时先查 keep_alive）

**日期**：2026-10-18　**域**：Ollama 运维 / 长跑进程

**案情**：Ollama keep_alive 过期后模型掉驻存，首批调用与冷加载赛跑 300s 超时，日志呈现为 HARD-FAIL timed out——假象是「模型/网络坏了」，实测服务面无恙。同日 retry 轮进程二次超时后静默死亡，日志无 end 行。

**实证**：超时后手动探活 11434 端口正常、模型 reload 后调用成功，坐实是冷加载而非服务故障；retry 轮日志缺收尾行，对照代码定位 finally 缺口（修复在飞）。

**纪律**：**超时类告警先查 keep_alive/暖驻状态，再怀疑服务本身。** 长跑轮的收行语句（end 行）必须 finally 兜底——任何退出路径都要留痕，无 end 行即「进程死于非命」的信号。

## 判例 6 · 速率争论先查算力归属（性能基准前先固定底座证据）

**日期**：2026-10-18　**域**：性能 / LLM 基准

**案情**：「45-57s/条」与「1.4s/条」两轮实测数据矛盾，引发速率争论；最终 `ollama ps` 显示 PROCESSOR=100% CPU（无 GPU）才解释一切。

**实证**：CPU decode ~12.7 tok/s 是物理底座；45-57s 是队列等待 + 冷加载叠加，1.4s 是暖驻状态的数字——两轮都对，底座不同。

**纪律**：**性能基准前先固定算力归属证据（`ollama ps` / `nvidia-smi`），再谈数字。** 无 PROCESSOR 证据的速率数字不得作为争论依据；跨轮对比必须同底座（同 PROCESSOR、同暖驻状态）。
