## 6. 发现的缺陷/观察

**无阻断性缺陷（P0/P1 无）。** 两条低级别观察：

1. **（P2 观测面）`last_run.log` 块缓冲导致等待期日志空窗**：run_shadow 在非终端
   环境把 stdout 重定向到 `shadow/last_run.log`，但 Python 文件 stdout 默认块缓冲，
   实测首票完成后（账本已 3 行）日志文件仍为 0 字节，全部输出在进程退出时一次性
   刷盘。若 17:10 正式首跑中进程异常挂死，巡检与人工将拿不到任何中间日志
   （monday_checkpoint 的等待设计已预期"账本行"是唯一完成信号，不受此影响，
   但 last_run.log 的"现场证据"价值打折）。建议后续给 run_shadow 的日志句柄加
   `line_buffering`/flush（本次预演不改代码，仅记录）。
2. **（口径确认）第 4 策略依赖真仓 bridge_inbox**：codex 桥接插件从
   `agent_platform/bridge_inbox/processed/` 装载（设计上 DATA_ROOT 之外），
   隔离根预演时也读真仓该目录（只读）。正式首跑同源，行为一致，无风险；
   但意味着"4 策略装配"对 bridge_inbox 目录内容有隐式依赖，若受理流程挪动
   processed/ 件，装配数会变（fail-open 不报错，仅产量减少）。

## 7. 已知边界（本预演覆盖不到的）

1. **跨天缺陷不可演练**：明日（10-20）才会暴露的问题——如幂等账本跨日重置、
   p0_alert_state 节流跨日行为、eval 周任务窗口——本次单日预演练不出来。
2. **monday_checkpoint main() 无法在预演中全量跑**：其门 1-4 与观察项路径硬编码
   真仓 `BASE/data`（无 SHADOW_DATA_ROOT 感知），且 main() 的唯一写面是
   真仓 `data/shadow/monday_checkpoint.log`（设计内自写日志）。为守预演红线
   （真仓字节不变），本次只以 path 注入方式验证两个 strategy 域观察项，
   未执行全量巡检。正式 17:25 巡检由计划任务在真仓跑 main()，属正常行为。
3. **预演数据=当日实时行情/当日模型输出**：17:10 正式首跑行情与 D1 决策会刷新，
   verdict 数值与 recommendation 分布会不同（本次 WATCH 档 3 票，是 K-ORG-129
   新枚举正常输出的佐证），链路结构结论不受影响。
4. **耗时基线是空载态**：本次 18m45s 为空载实测；历史竞争态（显存被挤）实测
   69 分钟，monday_checkpoint 已按 180 分钟上限设计等待，正式跑若撞竞争态属
   预期内慢，不是故障。
5. **预演账本对正式首跑零影响**：幂等键按数据根隔离，隔离根 20 行判决不会
   干扰真仓首跑的 recorded 计数（真仓 strategy_runs.jsonl 当前不存在，
   17:10 将从 0 行起落）。
