# JevStack 看护恢复与拉起链路修复（2026-11-05）

## 1. 背景

`start_jev_stack.ps1` 头部注释写着「Scheduled task: \JevStack (every 10 min, S4U)」，
但实测 `Get-ScheduledTask` 里**没有 JevStack**（只有 JevBackfill / JevDriftDaily /
JevFeed-Daily / JevFeed-Verify / JevNight / JevMonthlyEval / JevCoverageDaily）。
即三件套（9101 gate、9102 review、9103 qd-bridge）**长期没有看护。**

实证：11-05 03:46 我手工重启时拉起失败，服务断档到 03:50，共 4 分钟无人接管。

## 2. 根因一：环境块大小写重复 → Start-Process 抛异常

日志原文（`logs/jev-stack.log`）：

```
[2026-11-05 03:46:31] start FAIL jev-gate:已添加项。字典中的关键字:“HTTPS_PROXY”所添加的关键字:“https_proxy”
[2026-11-05 03:46:31] start FAIL review-gate:已添加项。…
[2026-11-05 03:46:44] FINAL down: jev-gate,review-gate (internal failure)
```

会话环境块里同时存在 `HTTPS_PROXY` 与 `https_proxy`（沙箱/会话注入叠在用户环境之上）。
`Start-Process` 克隆子进程环境用的是大小写不敏感的 .NET 字典，第二个键 Add 时抛
`ArgumentException`，于是**每一个组件都拉起失败**，脚本退出码 1。

复现（PowerShell 5.1，本机）：

```
Start-Process ... -RedirectStandardOutput ... → System.ArgumentException: 已添加项…HTTPS_PROXY
[Environment]::GetEnvironmentVariables() → HTTP_PROXY x2, HTTPS_PROXY x2（取值完全相同）
```

### 修复

`start_jev_stack.ps1` 新增 `Repair-DupEnv`：脚本启动时按**大小写不敏感**判重，
对存在变体的键先删除再以全大写键名写回原值（重复项取值相同，无损），
并在 `jev-stack.log` 记一行 `env dedupe: HTTP_PROXY(+1),HTTPS_PROXY(+1)`。
只改本进程环境，不动系统/用户级设置。

实测：去重后 `dup_after=0`，`Start-Process` 返回 `START_OK`；整脚本运行 `exit=0`，
日志出现 `stack ok (3/3 listening)`。

## 3. 根因二：9104 清理会误杀在役 card-handler

脚本第 3 段按 W4 口径「9104 已退役，残留尽力停掉」无条件 `taskkill`。
实测 9104 仍在 serving：`GET /metrics` 有 `jev_card_actions_total`，
即飞书卡片「已处理 / 忽略」回调还靠它。

### 修复

改为**显式开关**：只有 `-Force` 或新增的 `-StopRetired` 才清理 9104，默认不动。

## 4. 任务注册（已执行）

注册方式：`Register-ScheduledTask -Xml`（`schtasks.exe` 在本机沙箱程序黑名单内）。

| 项 | 值 |
|---|---|
| 任务名 | `JevStack`（根路径 `\`） |
| 触发 | 每日起始 04:10，`PT10M` 重复，无结束边界 |
| 动作 | `powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File "C:\aios\jev-eval\start_jev_stack.ps1"` |

## 6. 未决与风险

1. **拉起者身份未明**：03:50 之后 9101/9102/9103/9104 全部落在 **session 0（Services）**，
   用户态 `taskkill` 报「拒绝访问」（`Get-CimInstance` 的 CommandLine / 属主也为空）。
   说明除计划任务外还有一个更高权限的拉起者，实测 04:10 我杀掉旧 qd-bridge(24900) 后
   **约 5 秒**内就出现新进程 48164。上一轮「三件套没有自愈」的判断据此需要修正：
   自愈是存在的，只是不来自计划任务。
2. 因为杀不掉（拒绝访问），**「杀掉 → 看护拉起」的端到端演练没有做成**；
   本轮只验证到机制层：`Start-Process` 已可用（去重前必然失败）+ 健康时不重复启动。
3. 现在 JevStack（用户态）**只能拉起、不能终止**在役服务。若将来需要强制换血重启，
   必须由那个高权限拉起者或提权会话执行；用户态 `-Force` 会因拒绝访问而失败。
4. 每轮任务约 30 秒（DPAPI 解密 + `Get-NetTCPConnection` 较慢），10 分钟周期无压力；
   `jev-stack.log` 每轮一行，由 `tools/rotate_logs.py`（14 天 + gzip）覆盖。

## 6.1 session 0 拉起者取证（2026-11-05 04:50–05:10）

结论：**以当前用户权限无法定位到具体进程**，但已把候选范围压到很小，并查明"为什么本机服务会 session 0 化"的总机制。

已排除（附证据）：

| 候选 | 排除依据 |
|---|---|
| 我自己的 shell | Bash 工具 python（pid 58856）与 PowerShell 工具（pid 48292）实测均为 **session 1**；子进程只会继承 session 1 |
| `start_jev_stack.ps1` | 它把子进程 stdout 重定向到 `logs/jev-proc.<name>.out`；而 48164 的启动行只出现在 `logs/qdbridge.log`，`jev-proc.qd-bridge.out` 里**查不到 pid 48164** |
| 计划任务 | `TaskScheduler/Operational` 事件（10MB 循环，留存≈10.9h）：03:49:30–03:52:30 无 03:50:43 的启动记录；04:07–04:13 无 04:10:42 的记录 |
| `L1LegacyPortGuard` | 它是**杀** 5175/8102 的（SYSTEM/5min），不拉起任何服务 |
| `portal/*` | 只**探测** 9101-9103（`api_health_portal.py`），无拉起命令 |
| `phoenix_start.py` / `a0_patrol.py` / `ServiceRestart` | 分别管 6006 / 不引用 jev / 跑 `start_legion_ops.ps1` 且 LastRun 停在 10-31 |
| session 0 的常驻 python | 18 个全部映射了端口，都是**服务本体**（8787/8091/8093/8096…8103/8796 + 9101-9104），没有看护进程 |

剩余形态：**短命启动器**——把子进程 detach 后自退，父 PID 36616 / 51736 / 40372 均已不存在。

取证边界（为什么停在这里）：
1. session 0 进程的 `CommandLine` / `ExecutablePath` / `GetOwner` 在用户权限下**全部为空**；
2. `Security 4688`（进程创建审计）**未开启**，`Get-WinEvent` 查不到 creator；
3. 父 PID 已退出，无链可回溯。
4. 再往下必须二选一：**开 4688 审计**（改本地安全策略，系统级）或**提权读 WMI**——都属需老田批准的变更。

### 总机制发现：`AIOS-S4U-Guard` 会静默改写任务登录类型

`C:\aios\s4u_guard.ps1`（任务 `AIOS-S4U-Guard`，**SYSTEM**，每 5 分钟）会把**任何 action 里含 `aios`** 的、非 ServiceAccount/SYSTEM 的计划任务
用 COM `RegisterTaskDefinition(..., TASK_LOGON_S4U, ...)` **静默改成 S4U**（异常全被 `catch {}` 吞掉）。

- S4U 任务的子进程落在 **session 0** —— 这是本机大量服务「session 0 化、用户态杀不掉」的总机制。
- 它最近 12 轮日志全是 `noop (all S4U)`，而 `JevStack` 至今仍是 `Interactive` → 说明它尝试改 `JevStack` 时**失败且无痕**。
- 含义：如果哪天它改成功了，`JevStack` 会悄悄切到 session 0（好处是不依赖登录会话；风险是 DPAPI 加载路径变化，需看 `env_fallback.flag`）。

## 7. 回滚

```powershell
Unregister-ScheduledTask -TaskName 'JevStack' -Confirm:$false    # 撤销看护
git revert <commit>                                              # 撤销脚本改动
```

脚本层面的两个改动都是「更宽松」方向（去重只影响子进程环境；9104 默认不杀），
单独回滚不会破坏服务拉起能力。

## 8. 重启通道建议（待老田拍板）

现状约束：用户态**起得来、杀不掉**（session 0 拒绝访问）。所以"强制重启"这件事必须有一个**有权限且可追溯**的通道，三选一：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A · 提权任务做重启口**（推荐） | 用管理员注册 `JevRestart`（`ServiceAccount/SYSTEM`、`RunLevel Highest`、无触发器，只按需 `schtasks /run`），action = `start_jev_stack.ps1 -Force` | 一次性管理员注册 | 只有一个入口，日志全在 `jev-stack.log`；以后"重启 JEV"= 触发这一条任务 |
| B · 把服务拉回用户态 | 找出并停掉 session 0 拉起者，之后 `-Force` 就能用 | 需要先完成 §6.1 的提权取证 | 最干净，但依赖先把谜团解开 |
| C · 维持现状 | 需要重启时临时开一个 ADMIN 会话手工跑 | 无改动 | 每次都要人肉，且无留痕 |

管理员命令（**未执行**，A 方案落地时用）：

```powershell
$act  = New-ScheduledTaskAction -Execute 'powershell.exe' `
          -Argument '-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File "C:\aios\jev-eval\start_jev_stack.ps1" -Force'
$prin = New-ScheduledTaskPrincipal -UserId 'SYSTEM' -LogonType ServiceAccount -RunLevel Highest
$set  = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -MultipleInstances IgnoreNew -ExecutionTimeLimit (New-TimeSpan -Minutes 5)
Register-ScheduledTask -TaskName 'JevRestart' -Action $act -Principal $prin -Settings $set -Force
```

用完后的一次性重启：`Start-ScheduledTask -TaskName 'JevRestart'`（或在管理员 cmd 里 `schtasks /run /tn JevRestart`）。

> 注意：`-Force` 会杀 9101/9102/9103（**不含 9104**，2026-11-05 起默认不碰）。
