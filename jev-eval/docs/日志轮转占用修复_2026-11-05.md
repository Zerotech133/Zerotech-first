## 1. 故障链（一句话根因）

`start_jev_stack.ps1` 用 `Start-Process -RedirectStandardOutput/-RedirectStandardError`
拉起常驻服务，`.out/.err` 句柄被**子进程持有到进程退出**；`rotate_logs.py` 只会
「同目录 rename」，而 Windows 上 rename 需要 DELETE 共享权限 → 必然
`PermissionError [WinError 32]` → 旧版把它当硬失败 `rc=1` → `JevDriftDaily` 的 P5
每天 07:10 记一条假失败，**天天红**。

证据（`jev-eval/review_data/jev_drift_task.log`，2026-11-04 07:10）：

```
P5 rotate_logs exit=1 ... [WinError 32] 另一个程序正在使用此文件，进程无法访问。:
'...\jev-eval\logs\jev-proc\jev-proc.review.err' -> '...jev-proc.review.20261104-071018.err'
```

### 命名差异说明（以实际扫描为准）

任务日志里写的是 `jev-proc.review.err`，实际目录里是**两套命名并存**，
`rotate_logs.py` 递归扫描两者都能命中：

| 位置 | 实例文件 | 轮转件 |
| --- | --- | --- |
| `jev-eval/logs/`（平铺、点号命名） | `jev-proc.jev-gate.out`、`jev-proc.qd-bridge.out` | `jev-proc.jev-gate.20261102-071017.out.gz` |
| `jev-eval/logs/jev-proc/`（子目录） | `jev-proc.review.err`、`jev-proc.card.out`、`jev-proc.out` | `jev-proc.card.20261104-071018.err.gz` |

2026-11-05 实测 dry-run：`scanned=47 rotate=7 keep=22 skip=18 fail=0`
（两套命名均在计划内）。修复不需要改动任何文件命名。

## 2. 三级轮转策略

| 级别 | `mode=` | 触发 | 动作 | 结果 |
| --- | --- | --- | --- | --- |
| A 快路 | `rename` | rename 成功 | 原行为：同目录原子改名（`--gzip` 时再压缩 + 明文进回收站） | rc 0，`result=ok` |
| B 占用降级 | `copy_truncate` | rename 抛 `PermissionError`（WinError 32/33、EACCES） | 复制内容到归档件（沿用 `--gzip` / `--keep-days`）+ `open(path,"r+b")` → `truncate(0)` 原地截断 | rc 0，`result=ok` |
| C 兜底 | `deferred` | 复制或截断仍失败 | 登记进 `jev-eval/logs/rotate_deferred.json`，**rc 0 + WARN** | `result=deferred` |

要点：

- **截断成功即视为轮转成功**：B 路不删文件、不改 inode，服务继续往同一句柄写，
  不会出现「日志丢失」或「服务写已删文件」。
- 非占用类 rename 错误（不是 WinError 32）也会走 B 做一次兜底尝试，再落到 C。
- **deferred 不再影响退出码**：`exit_code` 只由 `result=failed` 决定，
  所以 P5 的 `rc` 判读逻辑（`$LASTEXITCODE`）完全没改。
- 下一次运行**开头先重试 deferred 清单**；同一文件累计 3 次失败后转入
  `rotate_deferred_dead.json`，此后不再自动轮转该文件（扫描时记
  `skip reason=dead_deferred`），只 WARN 一次。
- 本轮已重试过的路径，扫描阶段直接跳过（`skip reason=retried_this_run`），
  不会在同一天再复制一份归档；转入 dead 的文件也不再白复制。
- 保留策略不变：`--keep-days`（默认 14）、`--gzip`、`--max-mb`、`--dry-run` 全部兼容；
  `--dry-run` 新增占用探测（`CreateFileW(DELETE)`），能预览 `mode=copy_truncate`。

## 3. deferred 文件格式

`jev-eval/logs/rotate_deferred.json`（UTF-8，写 `.tmp` 后 `os.replace`，不产生半截文件）：

```json
{
  "schema": "rotate_deferred/v1",
  "updated_at": "2026-11-05T07:10:18+08:00",
  "max_attempts": 3,
  "count": 1,
  "items": [
    {
      "path": "C:/项目/老田的AI助手/jev-eval/logs/jev-proc/jev-proc.review.err",
      "rel": "jev-eval\\logs\\jev-proc\\jev-proc.review.err",
      "dest_hint": "C:/项目/老田的AI助手/jev-eval/logs/jev-proc/jev-proc.review.20261105-071018.err",
      "reason": "truncate_failed",
      "detail": "rename 被占用（[WinError 32] ...）；已归档 jev-proc.review.20261105-071018.err.gz，但原地截断失败：...",
      "first_seen": "2026-11-05T07:10:18+08:00",
      "last_attempt": "2026-11-05T07:10:18+08:00",
      "attempts": 1,
      "next_attempt": 2,
      "max_attempts": 3,
      "archive": "C:/项目/老田的AI助手/jev-eval/logs/jev-proc/jev-proc.review.20261105-071018.err.gz"
    }
  ]
}
```

- `reason`：`locked`（rename 被占）/ `truncate_failed` / `copy_failed` / `rename_error`；
- `attempts` 累计失败次数，`next_attempt` 为下次将是第几次，满 `max_attempts=3` 转 dead；
- `archive` 已写好的归档件：重试时若它还在，**只补截断、不重复复制**（避免每天白复制 20MB）。

`rotate_deferred_dead.json` 同 schema，多 `kind="dead"`、每条多 `dead_at` / `result="dead"`。

## 4. 手工重试命令

```bash
# 1) 先看清单（只读）
cat jev-eval/logs/rotate_deferred.json

# 2) 预览：会重试哪些、走哪一级（不改文件）
"C:/Program Files/Python311/python.exe" -X utf8 -B tools/rotate_logs.py \
    --target jev-eval/logs --active-guard-min 1 --json

# 3) 真重试（服务仍占着也会走 B；B 也不行就仍留 deferred，rc 仍为 0）
"C:/Program Files/Python311/python.exe" -X utf8 -B tools/rotate_logs.py \
    --execute --gzip --keep-days 14 --active-guard-min 1

# 4) dead 文件人工处理后，清空让下一轮重新纳入（先停服务/释放句柄，再删 dead 条目）
#    注意：不要手改 deferred.json 的 attempts，否则重试上限失效
```

## 5. 上线后验证

1. 次日 07:10 后看 `jev-eval/review_data/jev_drift_task.log` 的 P5 行，模板：

   ```
   P5 rotate_logs exit=0 mode=rename=6 mode=copy_truncate=1 mode=deferred=0 out= 模式：... | 执行完毕；退出码 0（mode=rename:6 copy_truncate:1 deferred:0）。
   ```

   - `exit=0` = P5 不再红；
   - `mode=copy_truncate>0` = 降级生效（原先 rc=1 的那批文件）；
   - `mode=deferred>0` = 延后，看 `jev-eval/logs/rotate_deferred.json`。
2. 归档落地：`jev-eval/logs/jev-proc/` 下应出现 `jev-proc.review.<yyyyMMdd-HHMMSS>.err.gz`，
   且源文件 `jev-proc.review.err` 变成 0 字节。
3. `jev-eval/logs/rotate_deferred.json` 的 `count` 应逐日归零；若 `count=3/3` 不变，
   看 `rotate_deferred_dead.json` 并人工处理。

## 6. 风险点

- **截断与子进程写入的竞态**：B 路先复制、后截断，两步之间服务可能再写几行；
  这些行在 `truncate(0)` 时被丢弃（丢失窗口 = 复制+fsync 的几十毫秒）。
  日志场景可接受；若将来用于审计日志，应改为「先截断再复制」或加文件锁。
- **复制期间文件继续增长**：复制到 EOF 后截断，超出的部分同样丢；
  大文件（>100MB）窗口更长，可考虑 `--max-mb` 收紧。
- **非原子**：B 路归档件写一半即崩溃会留下半个 `.gz`；
  归档文件名带时间戳且 `rotation_dest` 去重，不会覆盖历史归档，但需人工识别删除。
- **deferred 重试上限是「按文件」而非「按路径+时间」**：服务长期占用同一文件时，
  3 天后转 dead 且不再自动轮转，该文件会持续增长——这是刻意取舍（防刷屏），
  需要把 `rotate_deferred_dead.json` 纳入巡检。
- **dry-run 的占用探测**依赖 `CreateFileW(DELETE)`：杀软/EDR 偶发占用会造成
  「预览 B、实跑 A」的偏差；仅影响预览文本，不影响执行正确性。
