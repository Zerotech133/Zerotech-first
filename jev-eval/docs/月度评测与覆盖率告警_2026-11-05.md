## 1. 背景与本次修复

上线现状（实测计划任务清单：`JevBackfill`、`JevDriftDaily`、`JevFeed-Daily`、`JevFeed-Verify`、`JevNight`、`AgentShadowEvalWeekly`、`ZeroBound_WeeklyEval`）中**没有任何月度 JEV 回归评测任务**，但需求是「月度回归评测」。

同时 `jev_eval_guard.py` 里写死 `MAX_AGE_DAYS = 3`：

> 月度评测刚跑成功，第 4 天起 guard 就天天报「结果已 N 天，评测链路疑似未跑」——
> 这是**口径 bug**，不是评测故障。频繁误报会让真故障被淹没。

处理方式：guard 增加周期参数，超龄阈值随周期走，**默认 monthly**（与需求一致）。

| cadence | 超龄阈值 | 说明 |
|---|---|---|
| `monthly`（默认） | 35 天 | 31 天月长 + 补跑余量；月跑成功后整月不误报 |
| `weekly` | 3 天 | 保留原口径，供周度场景显式使用 |

超龄消息会带上三要素：**上次评测日期 / 期望周期 / 补救命令**，便于值班直接照着跑。

## 2. 覆盖率口径（本次新增监控）

`jev-eval/jev_coverage_guard.py`，与 eval_guard 分文件，单一职责。

```
覆盖率 = |triples_outcome.jsonl 去重 candidate_id|
        / |triples.jsonl ∪ triples_archive.jsonl 去重 candidate_id|
```

- id 字段优先 `candidate_id`，其次 `id`（按真实文件字段核对过，三份 jsonl 都是 `candidate_id`，无 `id`）。
- 任一文件缺 id 字段 → 退回**行数口径**，输出字段 `basis=lines` 明确标注，不静默降级。
- 门槛 `--min-coverage 0.5`；连续 `--streak-days 3` 天低于门槛 → 升级 `🔴 持续欠回填`。
- 连续天数用状态文件 `review_data/coverage_streak.json` 累计，**同日重跑幂等**（不重复计数），断档则重置为 1。
- 同时判 `review_data/graduation_status_v2.json` 新鲜度：mtime > 7 天 → WARN（毕业判定数据陈旧，n_eff 会失真）。

### 当前实测（2026-11-05，只读统计）

| 文件 | 行数 | 去重 candidate_id |
|---|---|---|
| `triples.jsonl` | 1912 | 1912 |
| `triples_archive.jsonl` | 738 | 738 |
| `triples_outcome.jsonl` | 508 | 508 |
| **合计（分母）** | — | **2650** |

- **id 口径覆盖率 = 508 / 2650 = 19.2%**（低于 50% 门槛 → WARN；第 1 天，攒满 3 天转 🔴）
- 行数口径（旧粗算）= 508 / 1912 = 26.6%（分母只算 live，偏低）
- `outcome` 中不在分母内的 id：0（口径自洽）
- 毕业 JSON：`computed_at=2026-11-03T05:53:10`，年龄 1 天（未过期）

> 注意：26.6% 与 19.2% 的差来自分母是否含 archive。本模块统一取 **live ∪ archive**，
> 因为 archive 里的样本同样等待回填，漏算会高估覆盖率。

### 退出码

| 码 | 含义 | 计划任务表现 |
|---|---|---|
| 0 | 正常 | 成功 |
| 1 | WARN：覆盖率 < 门槛 / 毕业 JSON 陈旧 / 分母为 0 | 失败（需看一眼） |
| 2 | CRITICAL：连续 N 天欠回填（🔴 已推送） | 失败 |

stdout **只输出一行 JSON**（`level/coverage/basis/streak_days/grad_stale/problems/...`），
可直接 `>> logs/coverage_daily.jsonl` 做趋势；推送诊断走 stderr。

## 6. 风险点

1. **任务运行身份**：`/RL LIMITED` 未指定 `/RU`，默认当前用户，**仅在用户登录时运行**。
   若机器改为无人值守/服务化，任务不会跑，且 `jev-gate.env.ps1` 里的 DPAPI 凭据是用户级，
   改 `/RU SYSTEM` 会解不开密钥——需另做 S4U/凭据方案，不能简单换 SYSTEM。
2. **首月误报收敛**：覆盖率当前 19.2%，注册后第 3 天起必然 🔴。这是**真实欠回填**，
   不是误报；要么接受连续告警直到回填追上，要么先批「仅 WARN 不升级」（把 `--streak-days` 调大）。
3. **口径敏感性**：分母含 archive（2650），比旧粗算（1912）严格；若老田认为 archive 不应计入，
   改 `POOL_FILES` 一行即可，但会让覆盖率虚高约 7pp，不建议。
4. **结果文件污染**：guard 取 `result-*.json` 字典序最后一份，历史上混入过 `-bydomain`、
   `repeats=1` 的文件（实测 20261014 的 `repeats=1`、`by_type={"score":...}` 已经被当成最新）。
   本次未改选取逻辑（超出本单范围），但**月度评测跑完后会自然覆盖**；建议后续单独立项
   改为「按 run_at 取最大 + 校验 repeats==3」。
5. **推送渠道**：与 eval_guard 共用 `backup_alert.py`（OpenAPI → webhook → lark-cli 三级降级）。
   若三级全失败，仅 `推送 exit=1` 落日志，不重试——与现网一致，未新增投递保证。
6. **日志增长**：`logs/monthly_coverage.jsonl` 每日一行、永不轮转（约 1KB/行，年增 ~0.4MB），
   量级可忽略；`jev_monthly_eval.log` 按 200KB 封顶轮转。
