- 全页无 `<input type="password">`、无任何 key 输入框（:109-:114 唯一的输入框是 open_id 逐个查询用）。

## 2. 方案对比

### 方案甲（推荐）：新增 `tools/sub_admin_fetch.py` 只读取数器

**定位**：运维本机/内网运行的只读 CLI，替代浏览器页面在 key 开启后的取数职责，同时填补 ：267/:290 悬空承诺。

**key 的生命周期（核心纪律）**：

1. 优先读环境变量 `PORTAL_SUB_ADMIN_KEY`（运维在 shell 里 `export` 或用凭据管理器注入）；
2. 环境变量为空时，fallback 到 stdin 交互读取（`getpass`，不回显）；
3. **绝不写盘**：不落配置文件、不落 cookie、不写任何缓存；
4. **不进 shell 历史**：不提供 `--key` 命令行参数（命令行参数会被 `ps`/history 捕获），文档明令禁止 `curl -H "X-Portal-Key: <key>"` 这类把 key 写进命令行的用法；
5. key 只存在于进程内存，进程退出即消失。

**输出脱敏（closed on failure 风格）**：

- 工具在本地对 `subscribers[].open_id` 应用 `portal_api.py:474-484 mask_open_id()` 同口径掩码（前 8 位 + `"**"`，降级前 4/前 2 位）后输出摘要——**工具本身任何输出通道都不打印明文 open_id**；
- 注意取证事实（:4045-:4050）：服务端 list 端点回的是**明文 open_id**（有意设计），所以「复用服务端掩码口径」在 list 上无法直接成立——掩码必须由工具在收到响应后本地执行，口径照抄 `mask_open_id()` 纯函数。这正是工具存在的价值之一：把服务端为内部域设计的明文面，收窄成运维终端上的脱敏面；
- `display_name`、`plan_id`、`status`、`end`、`used_today` 原样输出；`error` 文本原样透出（服务端已归并，closed on failure）。

**翻页**：

- `--offset N` 指定起点（默认 0），`--limit N` 钳制 [1,200] 默认 200（与服务端 :4083-:4089 同语义）；
- `--follow`：循环按响应里的 `next_offset` 翻到 `has_more=false`；遇「0 行但 has_more=true」或 next_offset 缺失/同值/反退时置停并报告，与页面 ：236-:249 三态同口径，不自行推算 offset；
- 每页打印进度行（offset、行数、三态判定），不静默。

**留痕**：

- `--json PATH`：把**脱敏后**的全量结果以 JSON 落到指定路径（约定 `deliverables/` 下），文件头带抓取时点、auth_mode、页参数；**不提供明文导出模式**（closed on failure：无开关可绕过掩码）；
- 落盘文件中 open_id 一律掩码，与终端输出同口径。

**只读边界**：

- 仅 GET `/api/subscription/list`；零写操作、不触任何库、不触 subscription_store 模块、不改服务端任何状态。

**优点**：key 不进浏览器（不扩 XSS 面）、不进 shell 历史（不扩 ps/history 面）、输出默认脱敏、翻页三态与服务端契约对齐、填补页面文案承诺、纯增量（新文件，零既有行为变化）。
**代价**：多一个待维护的工具文件 + 配套单测；运维需上机操作而非点页面。
**前提**：Q2 拍板 key 开启后才有真实用户；key 未开启（auth_mode=none）时工具照样可用（透传 `auth_mode` 提示「当前无鉴权运行」，不假装安全）。

### 方案乙（列风险，不推荐）：sub_admin.html 会话内存输入 key

**形态**：页面加一个 key 输入框，key 只存 JS 变量（不落 localStorage/sessionStorage/cookie），fetch 时带上 `X-Portal-Key` 头。

**与既有审计特性的冲突（必须明示）**：

- 直接顶撞 P3.10-lite 已落地的「页面禁存密钥」特性——:264-:266 注释白纸黑字：「本页刻意不提供密钥输入框——把密钥留在浏览器存储里，等于用一个 XSS 面换一次便利，不值」。会话内存输入等于把这句否决翻案，审计口径需要整体重写；
- 即便只存 JS 变量，key 一旦进入浏览器就扩大了暴露面：
  - **XSS 面**：任何注入脚本都能从 JS 变量里捞走 key（变量不落盘只降低持久化风险，不降低运行时可读风险）；
  - **nginx 访问日志面**：key 走自定义请求头，若 nginx 任何层级的日志格式含 `$http_x_portal_key`，明文 key 直接进盘。需逐条审计 `portal/nginx.conf` 与宿主 nginx 的 log_format，审计成本高于方案甲全部工作量；
  - **内存/转储面**：浏览器进程内存、崩溃转储、开发者工具、共享内网机器上的旁观者，都是新增暴露面。

**结论**：收益（免上机）远小于风险（翻案审计特性 + 双重暴露面审计），不推荐。仅当未来出现「运维无法上机、又必须看页面」的硬场景时再议，且须先过 nginx 日志审计与老田拍板。

### 方案丙（维持现状）：文档化 curl 口径

**形态**：不改任何代码，把取数命令写进运维文档。

**示例命令模板（值一律占位符，严禁填真实 key 后提交进任何文档/工单/聊天记录）**：

```bash
# 首屏（limit 钳制 [1,200]，默认 50）
curl -sS "http://<内网HOST>:<PORT>/api/subscription/list?limit=200&offset=0" \
  -H "X-Portal-Key: <PORTAL_SUB_ADMIN_KEY 值，占位符>"

# 翻页（起点只取上一页响应的 next_offset，不自行推算）
curl -sS "http://<内网HOST>:<PORT>/api/subscription/list?limit=200&offset=<next_offset>" \
  -H "X-Portal-Key: <PORTAL_SUB_ADMIN_KEY 值，占位符>"

# 鉴权态自述
curl -sS "http://<内网HOST>:<PORT>/api/subscription/list?limit=1"
```

**风险**：

- `-H "X-Portal-Key: ..."` 里的 key 会进 shell 历史、`ps` 输出、终端回放——正是方案甲要消灭的暴露面；文档只能「提醒」，无法在机制上阻止；
- 输出为服务端原文（明文 open_id），无脱敏闸门；
- 翻页、三态判定、closed on failure 全靠人工自觉，无工具兜底；
- 不填补 ：267/:290 的悬空承诺——页面文案说的「内网工具」依然不存在，缺口只是被文档盖住。

**结论**：可作为方案甲落地前的临时口径（缓解措施：文档强制要求用 `read -s KEY` 后经 stdin 注入或环境变量引用，不写明文），但不作为终态。

## 3. 推荐结论

**推荐方案甲。**理由浓缩为三点：

1. **填补的是已承诺的缺口**：页面 ：267/:290 已经把用户导向「内网工具」，工具落地是兑现既有承诺，不是新增功能面；
2. **暴露面单调不增**：key 不进浏览器（保住「页面禁存密钥」审计特性）、不进 shell 历史（无 --key 参数机制性保证）、不写盘、输出默认脱敏（closed on failure：无明文导出开关）；
3. **零破坏**：新文件、只读、不改页面、不改服务端、不改 nginx，既有 444 测试基线零影响。
