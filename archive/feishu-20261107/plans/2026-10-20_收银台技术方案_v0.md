## 一、订单状态机

### 1.1 现状：表已存在，语义未定义

`payment_order`（`subscription_store.py:138-145`）当前结构：

```sql
CREATE TABLE IF NOT EXISTS payment_order (
    order_id   TEXT PRIMARY KEY,
    open_id    TEXT NOT NULL,
    amount     TEXT NOT NULL DEFAULT '',
    channel    TEXT NOT NULL DEFAULT '',
    status     TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
```

按「商业化最小闭环」检验，缺三类信息：

1. **买的是什么**——无 `plan_id`，订单无法自证对应档位（`plan.cycle_days` 可推导天数，但档位一旦改价改周期，历史订单会漂移）；
2. **钱怎么比对**——`amount` 是 TEXT，`"199"`、`"199.00"`、`"¥199"` 三种写法互不相等，无法做金额勾稽；
3. **谁证明了这笔钱**——无第三方交易号，回调重复投递时没有任何数据库级去重手段；也无支付完成时间，无法判「先付后开」还是「先开后付」。

### 1.2 字段建议（只增列，不改列、不删列、不重建表）

| 列名 | 类型 | 语义 | 是否必需 | 说明 |
|---|---|---|---|---|
| `order_id` | TEXT PK | 本地订单号 | 已有 | 业务主键，建议 `FS` + 日期 + 序列（格式待批，不擅自定） |
| `open_id` | TEXT | 付款人 | 已有 | 与 `subscriber.open_id` 同口径 |
| `amount` | TEXT | 展示用金额（原样） | 已有 | **保留不动**，仅作人读展示与历史兼容，不参与比较 |
| `amount_cents` | INTEGER | 应收金额（分） | **新增** | 唯一比较口径；`NULL` 表示未回填，禁止用 0 兜底 |
| `channel` | TEXT | 支付渠道标识 | 已有 | 渠道枚举待商务选定后定（见 §7） |
| `status` | TEXT | 状态机当前态 | 已有 | 字面量见 §1.4 |
| `created_at` | TEXT | 建单时间 | 已有 | 与账本其它表同格式 `YYYY-MM-DD HH:MM:SS` |
| `plan_id` | TEXT | 所购档位 | **新增** | 快照式写入，后续改档不改历史单 |
| `days` | INTEGER | 本单授予天数 | **新增** | 快照 `plan.cycle_days` 的当时值，避免档位改周期导致历史单语义漂移 |
| `external_txn_id` | TEXT | 第三方交易号 | **新增** | 幂等第一键；未支付时为 `NULL`（不是空串） |
| `paid_at` | TEXT | 第三方确认支付时间 | **新增** | 用于时序校验与「先付后开」判定 |
| `updated_at` | TEXT | 最后一次状态变更时间 | **新增** | 状态审计最小要求 |
| `grant_sub_id` | INTEGER | 对应 `subscription` 行 rowid | **新增（可选）** | 见 §2.3 的关联键选择，与 `subscription.order_id` 二选一 |

不建议新增的列（明确否决）：`refund_amount`、`invoice_no`、`coupon`、`retry_count`——退款与发票口径未定（§7），此刻建列等于把未决策的业务假设固化进表结构。

### 1.3 兼容既有数据的迁移方案

**前提事实**：`payment_order` 当前**无任何业务写入方**（§0 已 grep 确认），表内实际行数为 0 或仅测试夹具残留。因此迁移的兼容风险极低，但方案仍须满足「可重入、不重建、不丢行」。

```text
M1 备份：停写窗口内复制 store 文件（与既有 .bak 惯例一致）
M2 探测：PRAGMA table_info(payment_order) 取现有列集合
M3 加列：对每个缺失列执行 ALTER TABLE payment_order ADD COLUMN <col> <type>
        · 全部列可为 NULL 或带 DEFAULT，绝不加 NOT NULL 无默认列
        · SQLite ADD COLUMN 是元数据操作，不重写既有行，O(1)
M4 建索引：CREATE UNIQUE INDEX IF NOT EXISTS ux_payment_txn
          ON payment_order(channel, external_txn_id)
          WHERE external_txn_id IS NOT NULL AND external_txn_id <> ''
        · 必须是**部分唯一索引**：历史行/未支付行 external_txn_id 为 NULL，
          普通 UNIQUE 在 NULL 上不去重（NULL≠NULL），且空串会互相冲突
M5 回填：amount_cents 由 amount 解析（去货币符号、转分、整数化）
        · 解析失败的行保持 NULL，落一条待人工清单，**不猜、不置 0**
M6 校验：行数前后相等；旧列值逐行 sha 对比；索引存在性断言
```

**回滚方式**：SQLite 不支持 `DROP COLUMN` 的旧版本兼容面较窄，故回滚口径定为「**停读新列，不删列**」——旧代码的 SELECT/INSERT 均使用显式列名（`is_entitled:232`、`get_subscriber_summary`、`list_subscribers` 内联 SQL 已核对），新增 NULL 列不影响任何既有查询路径。这条是选择「只增列」而非「重建表」的核心理由：**迁移失败的最坏结果是多几列空数据，而不是账本文件损坏**。

**纪律**：迁移脚本必须单独成文件、单独评审、可 dry-run；不得混入业务上线窗口；执行前必须有一次「复制库 → 跑迁移 → 比对行数」的预发演练。

### 1.4 状态定义与流转

```text
                  ┌──────────┐
                  │ created  │ 本地建单（金额/档位/付款人已快照）
                  └────┬─────┘
            拉起支付成功 │        超时/用户取消
                  ┌────▼─────┐ ──────────────────► ┌────────┐
                  │ pending  │                     │ closed │
                  └────┬─────┘ ◄── 超时关单 ────────└────────┘
        回调验签+金额一致 │
                  ┌────▼─────┐
                  │   paid   │ 第三方已确认收款（grant 尚未完成）
                  └────┬─────┘
        同事务授予成功 │        退款成功
                  ┌────▼─────┐ ──────────────────► ┌──────────┐
                  │activated │ ──────────────────► │ refunded │
                  └──────────┘      退款成功         └──────────┘
```

| 状态 | 语义（判定条件） | 允许出边 |
|---|---|---|
| `created` | 订单行已存在，未取得第三方预支付凭证 | `pending`、`closed` |
| `pending` | 已向第三方下单成功，等待付款 | `paid`、`closed` |
| `paid` | 第三方确认收款成功 **且** 金额一致 **且** 验签通过 | `activated`、`refunded` |
| `activated` | 授予成功，`subscription` 已有对应行（同事务提交） | `refunded` |
| `closed` | 未收款即终结（超时/取消） | 无（终态） |
| `refunded` | 已退款（无论此前是否已开通） | 无（终态） |

### 1.5 迁移矩阵：允许与禁止

**允许**（全量白名单，除此之外一律拒绝）：

| From → To | 触发 | 附加前置 |
|---|---|---|
| `created → pending` | 第三方下单接口返回预支付凭证 | 幂等：同一 `order_id` 重复调用返回同一凭证，不新建 |
| `created → closed` | 建单后未拉起支付即超时 | 必须无 `external_txn_id` |
| `pending → paid` | 支付回调 | 验签通过 + 金额相等 + 未超出时间窗（§5） |
| `pending → closed` | 支付超时关单 | 必须先向第三方查询确认「未支付」再关，禁止凭本地计时直接关 |
| `paid → activated` | 授予事务提交 | 与 `subscription` INSERT **同一事务**（§2.4） |
| `paid → refunded` | 退款成功回调/主动查询确认 | 无需先 activated（付了款但授予失败的单，退钱是唯一正确出口） |
| `activated → refunded` | 退款成功 | 须同步处理权益（§6 前置项：退款失权路径） |

**禁止**（必须显式报错并落冲突记录，不得静默忽略）：

| 禁止迁移 | 原因 |
|---|---|
| 任何状态 → `created` / `pending` | 状态不可回退；重试是「幂等重放」，不是「退回重来」 |
| `paid → pending`、`activated → paid` | 已收款事实不可被覆盖，否则对账必错 |
| `paid → closed`、`activated → closed` | 钱已收却把单关掉，等于账面上凭空消失一笔应收；只能走 `refunded` |
| `closed → paid` / `closed → activated` | 已关单若后续收到钱，属「关单后到账」异常，进人工处置（§4.2 差异类 D5），不在状态机内自动开闸 |
| `refunded → *` | 终态；如需重新购买，**新建订单**，不复用旧单（与撤销订阅「INSERT 新行、旧行永久保留」判例同构） |
| `activated` 覆盖式重写 | 授予只能 INSERT 一次（§2.1），禁止 UPDATE 已有订阅行来「修正」授予 |

### 1.6 状态字面量口径

建议全部小写英文：`created / pending / paid / activated / closed / refunded`，与 `STATUS_ACTIVE="active"`（:54）的既有风格一致。

**已知对齐点**：已交付的勾稽工具 `tools/reconcile_subscription.py:93` 采 `PAID_STATUSES = ("paid", "已支付")` 双写兼容。本状态机落地后应收敛为单一 `paid`，收敛动作属工具侧改动，另批；在此之前**不得**出现第三种写法（如 `PAYED`、`success`）。

## 二、订单与订阅的关系

### 2.1 结论

| 问题 | 选择 | 一句话理由 |
|---|---|---|
| 一单能否对应多次授予？ | **不能。一单至多一次授予。** | 多次授予意味着一笔钱买到两段权益，金额与权益的对价关系立刻失锚，对账时无法自证。 |
| 一次授予是否只能来自一单？ | **是（新单必须如此）。** 唯一例外是历史人工授予，见 §2.6。 | 授予若可无单发生，「没付钱开通了」就永远无法用机器判据证伪。 |
| 一单想买多个档位怎么办？ | **拆成多个订单**，各自独立支付/独立授予/独立退款。 | 拆单后每单仍是 1:1，退款可单笔冲正，无需发明「部分退款 + 部分失权」的组合语义。 |

即：**订单 : 授予 = 1 : 1（严格）**，在数据库层用唯一约束硬化，不靠代码自觉。

### 2.2 理由展开（为什么不是 1:N 或 N:1）

- **1:N（一单多授予）**：续费场景看似诱人（买一年送一个月），但把「赠期」塞进同一单会导致退款时无法确定退多少、撤销时无法确定撤哪一段。赠期应表达为**授予时长参数**（`days` 快照），而不是第二条授予行。
- **N:1（多单一次授予）**：分期/补差场景才需要，而分期支付属于渠道能力，渠道侧本就是一个交易号对应一次收款；本地拆成两单反而与第三方账单对不上。
- **1:1 的额外收益**：`subscription` 一旦带 `order_id`，任何一条权益行都能反查到唯一的收款凭证——这是对账、客服、纠纷处理三条线共用的最小充分信息。

### 2.3 关联键落点（两个候选，建议选 A）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（建议）** | `subscription` 增列 `order_id TEXT NOT NULL DEFAULT ''`，并在 `order_id<>''` 上建**部分唯一索引** | 权益行自证来源；`list_subscribers` / `get_subscriber_summary` 的既有 SELECT 均为显式列名（已核对），加列不破坏读路径；索引天然阻断重复授予 | 动 `subscription` 表结构（`subscription_store.py` 本波四工位禁改，须另批） |
| B | `payment_order` 增列 `grant_sub_id INTEGER` 指向 `subscription` 隐式 rowid | 不动订阅表 | rowid 不是稳定业务键（VACUUM/重建可变）；`subscription` 无显式主键（:124 已核），依赖隐式 rowid 属隐患 |

默认值取 `''` 而非 NULL 的理由：与既有 DDL 的 `DEFAULT ''` 风格一致，且能把「历史/人工授予」显式表达为一类可统计的行（§4.2 D6），而不是混在 NULL 语义里。

### 2.4 防「付了钱没开通」

四道防线，从强到弱：

1. **同事务**：`paid → activated` 的状态更新与 `subscription` INSERT（含 `order_id`）必须在**同一 SQLite 事务**内提交。当前 `grant_subscription`（:290）自带连接与 `commit()`，**无法**与订单更新同事务——这是必须新增一个「事务内授予」入口的原因（属 store 契约追加，另批）。同事务保证：不存在「订单已 paid 但订阅没写进去」的中间态被持久化。
2. **状态即证据**：`activation` 失败时事务回滚，订单**保持 `paid`**（不是 `activated`），于是「已付款未开通」在库里是一条可查询的显式状态，而不是沉默的缺失。
3. **可重放**：`paid` 状态的订单允许被授予任务反复重试；重试以 `order_id` 为幂等键（§3.2），成功一次后状态变 `activated`，后续重试直接短路。因此「付了钱没开通」是**可自愈**的，不需要人工补数据。
4. **对账兜底**：`paid` 停留超过阈值（阈值待定，不擅自编造分钟数）即告警；日对账把「第三方成功 ∩ 本地非 `activated`」列为差异（§4.2 D4）。

### 2.5 防「没付钱开通了」

1. **入口收窄**：授予入口只接受 `order_id`，内部先断言该单存在且 `status ∈ {paid}`，再在同一事务内置 `paid→activated`。禁止任何「只传 open_id + days」的新增调用路径。
2. **来源必填**：`subscription.order_id` 非空 + 部分唯一索引（§2.3 A），使「凭空多一条权益」在数据库层就写不进去重复值。
3. **反查自检**：对账项「`subscription.order_id<>''` 且在 `payment_order` 中找不到 `status∈{paid,activated,refunded}` 的行」→ 判 `grant_without_payment`，**这是 P0 级差异**（比漏单更严重，因为它意味着白送）。
4. **诚实标注既有例外**：本方案落地前，管理员「开通」指令走的是 `grant_subscription`（无订单）。这批行 `order_id=''`，属历史人工路径，**不是漏洞但也不是可审计的商业授予**，必须在对账报表单列（§2.6），不得混入正常订单统计掩盖规模。

### 2.6 历史与人工授予的边界

- `order_id=''` 的行：口径为「非收银台来源」（人工开通 / 补偿 / 测试）。对账时**不计入**商业收入，但**计入**权益总量，且须报告条数——让「有多少权益不是买来的」成为可观测数字。
- 人工授予若发生在 M3 之后，必须由管理员指令创建一张 `channel='manual'`、`amount_cents=0` 的订单并走完整状态机。**理由**：让所有权益都有单，才能让「权益总量 = 订单总量」成为可断言的恒等式；例外一旦开口，对账就退化成抽样。

## 三、幂等设计

### 3.1 三级幂等键

| 层级 | 键 | 载体 | 防什么 |
|---|---|---|---|
| L1 第三方事实 | `(channel, external_txn_id)` 部分唯一索引 | `payment_order` | 同一笔银行/渠道交易被回调多次 → 只可能有一行本地订单认领它 |
| L2 本地业务 | `order_id`（PK） | `payment_order` | 同一订单被重复创建/重复推进 |
| L3 授予 | `order_id` 部分唯一索引 | `subscription` | 同一订单授予两次（§2.3 A） |

三级都用**数据库约束**而非应用层 `if exists` 判断。理由：应用层判断在并发下必然有 TOCTOU 窗口，而支付回调恰恰是最容易并发到达的入口（渠道重试是并行发起的，不是串行的）。

### 3.2 回调处理的幂等算法（语义描述，非代码）

```text
1. 读原始 body 字节 → 验签（§5.1）。验签失败 → 401，不落任何业务数据，只记脱敏审计
2. 解析出 (order_id, external_txn_id, amount_cents, paid_at)
3. BEGIN IMMEDIATE                       ← 立即取写锁，避免两个回调同时读到同一旧状态
4. SELECT ... WHERE order_id=? （或 WHERE channel=? AND external_txn_id=?）
5. 若 external_txn_id 已绑定到**另一张** order_id → 冲突，ROLLBACK，告警（§4.2 D2）
6. 若订单已是目标态（paid/activated）→ 直接 COMMIT 并返回成功（幂等短路）
7. 若状态迁移不在允许白名单（§1.5）→ ROLLBACK，记冲突，返回成功但不改数据
8. 金额比对：回调金额 ≠ amount_cents → 不置 paid，记 amount_mismatch，返回成功（防无限重试），告警
9. 置 paid（写 external_txn_id / paid_at / updated_at）
10. 同事务内授予 → 置 activated；授予失败则整笔 ROLLBACK，订单停留 paid
11. COMMIT
```

要点：**第 6 步是幂等的主体**——重复投递不是「错误」，是渠道的正常行为，必须以「成功应答 + 零副作用」结束，否则渠道会持续重试直到把回调打成风暴。

`BEGIN IMMEDIATE` 的必要性：SQLite 默认 `DEFERRED` 事务在「先读后写」时可能升级锁失败（`database is locked`），回调并发下会表现为随机 500。`subscription_store._connect` 已设 `timeout=10`（:157 附近，连接参数），但事务模式需在回调实现里显式指定。

### 3.3 回调乱序处理矩阵

渠道不保证顺序，也不保证只发一次。逐情形定策：

| 到达情形 | 判定 | 处置 | 应答 |
|---|---|---|---|
| `paid` 回调，本地订单不存在（`created` 还没写进去） | 极罕见，通常是本地建单后未落库就崩 | **不臆造订单**。记 `orphan_callback`（含脱敏 txn），告警 | **非 2xx**，让渠道重试，给人工补单留时间窗 |
| `paid` 回调，本地订单 `created`（未拉起支付） | 顺序错乱或本地漏推进 | 允许跳级 `created → paid`（`pending` 只是中间态，不是收款的必要条件） | 2xx |
| `paid` 回调，本地订单 `pending` | 正常路径 | §3.2 全流程 | 2xx |
| `paid` 回调，本地已 `paid` | 重复投递 | 幂等短路；若上次授予失败则本次重试授予 | 2xx |
| `paid` 回调，本地已 `activated` | 重复投递 | 幂等短路，零副作用 | 2xx |
| `paid` 回调，本地 `closed` | 关单后到账（本地误关或渠道延迟） | **不改状态**，记 `paid_after_closed`，P0 告警 → 人工核实（§4.2 D5） | 2xx（避免重试风暴），同时告警 |
| `paid` 回调，本地 `refunded` | 已退款又来收款通知 | 记冲突告警，**不复活** | 2xx |
| 同一 `external_txn_id` 指向两个 `order_id` | 渠道侧串号或本地建单重复 | **不改任何一行**，全部告警，人工裁决 | 2xx |
| `created`/`pending` 类通知晚于 `paid` 到达 | 渠道事件乱序 | 忽略（状态机不允许回退，§1.5） | 2xx |
| 未知事件类型 | 渠道新增事件 | 记原文（脱敏）+ 忽略 | 2xx |

设计取向说明：**「能确定是重复」的回调一律 2xx 静默幂等；「不能确定真伪/归属」的回调一律告警 + 非 2xx 或人工**。前者防风暴，后者防吞钱。

### 3.4 授予侧幂等

授予失败重试的幂等键是 `order_id`：`subscription(order_id)` 部分唯一索引保证「最多一行」。重试流程为「查 `activated` → 是则短路；否则在同一事务内置 `paid→activated` 并 INSERT」。因此重试 N 次与重试 1 次结果相同，且 `subscription` 中不会出现同单两行。

## 四、对账

### 4.1 三方勾稽口径

| 面 | 数据源 | 粒度 | 关键字段 |
|---|---|---|---|
| 订单面 | `payment_order`（本地） | 一行 = 一单 | `order_id`、`open_id`、`plan_id`、`amount_cents`、`status`、`external_txn_id`、`paid_at` |
| 权益面 | `subscription`（本地） | 一行 = 一段有效期 | `subscriber_open_id`、`plan_id`、`start`、`end`、`status`、`order_id` |
| 资金面 | 第三方账单（渠道下载/查询 API） | 一行 = 一笔交易 | 渠道交易号、商户订单号、金额、交易状态、交易时间 |

**勾稽链**：`第三方账单.external_txn_id ↔ payment_order.external_txn_id`，再 `payment_order.order_id ↔ subscription.order_id`。

**三个恒等式**（对账的最终判据）：

1. 笔数：`Σ 第三方成功笔数 == count(payment_order where status∈{paid,activated,refunded})`
2. 金额：`Σ 第三方成功金额 == Σ payment_order.amount_cents where status∈{paid,activated,refunded}`（退款单按负向冲抵，冲抵符号口径见 §7 退款策略）
3. 权益：`Σ 已开通订单数 == count(subscription where order_id<>'')`，且每条 `activated` 订单恰有一条订阅行

**对账节奏建议**：T+1 全量 + 当日准实时抽样。全量必须可重复执行（只读、幂等、输出稳定排序），因为对账工具本身出错时，人要能一眼看出「是数据变了还是工具变了」。

### 4.2 差异分类（判定条件 + 处置建议）

| 编号 | 类别 | 判定条件 | 严重度 | 处置建议 |
|---|---|---|---|---|
| D1 | **漏单** | 第三方账单有成功交易，本地 `payment_order` 无对应 `external_txn_id`（或订单存在但从未 `paid`） | P0 | 冻结该笔自动处理；按第三方账单补建订单并补授予（补授予必须走 §3.2 同一条链路，不写旁路）；补单需二次确认，禁止脚本静默补 |
| D2 | **重单** | 同一 `(channel, external_txn_id)` 命中多行本地订单（唯一索引应已阻止，命中即说明索引缺失或被绕过）；或同一 `order_id` 出现多行 `subscription` | P0 | 立即停写排查约束是否生效；多授予的需撤销多余行（依赖撤销能力，§6 项 4）；退款只按一笔处理 |
| D3 | **金额不符** | 回调金额 ≠ `amount_cents`；或 `payment_order.amount_cents` ≠ 下单时档位价快照 | P0 | 前者不改状态、原样告警、人工核实（可能是改价后旧单、或渠道手续费口径误用）；后者说明定价快照写入有误，须回溯。**当前定价未定（§7 项 1），本类只能判「回调 vs 订单」，判不了「订单 vs 价目表」** |
| D4 | **状态不同步** | 第三方=成功 且 本地 ∈ {`created`,`pending`,`closed`}；或本地=`activated` 且 第三方=已退款；或 `paid` 停留超阈值未 `activated` | P0/P1 | 前两种人工核实后定向修正（修正动作另立工单，工具只报不修）；第三种优先重放授予（§3.4），重放仍失败则查 store 写权限/磁盘 |
| D5 | **关单后到账** | 本地 `closed`，第三方有成功交易 | P0 | 不自动开单；核实是否本地误关（如凭计时关单而未查渠道）。确属真实收款 → 人工决策「补开 or 退款」，两条路都必须留下决策记录 |
| D6 | **无单权益** | `subscription.order_id=''`（历史/人工授予） | 观测项（非错误） | 单列报表，报条数与占比；M3 后新增此类行须有管理员指令留痕 |
| D7 | **权益超付** | `subscription.order_id<>''` 但 `payment_order` 中该单状态 ∉ {`paid`,`activated`,`refunded`} | P0 | 等同「没付钱开通了」（§2.5 第 3 条），立即冻结该 open_id 的授予入口，人工裁决 |
| D8 | **时间异常** | `paid_at < created_at`；`subscription.start > end`；`subscription.start` 早于对应订单 `paid_at` | P1 | 前两项为数据错误，第三项说明授予早于收款（时钟或人工干预），逐条核实；时钟漂移须先修时钟再谈对账 |
| D9 | **退款未失权** | 订单 `refunded` 但对应 `subscription` 仍 `active` 且覆盖当前时刻 | P0 | 退款失权路径未落地前**不得开放退款**（§6 项 5 硬前置）；发现即人工撤销 |

**与已交付工具的关系（诚实边界）**：`tools/reconcile_subscription.py`（`e186a285`）当前只能按 `open_id` 粗关联判 `paid_without_subscription`，其文件头（:48-:52）已自陈「无法识别付了款但发的是别的档位/别的一单的错配，是本表结构的已知盲区」。本方案 §2.3 的 `subscription.order_id` 落地后，D1/D2/D7 才能从「按人猜」升级为「按单对」；在此之前**不得**宣称对账已闭环。

### 4.3 对账的最小输出契约（建议）

沿用既有工具风格：`{"ok": bool, "checked": n, "issues": [{"code","detail"}], "window": {"from","to"}}`。新增 `window` 是必要的——没有对账区间的差异报告无法判断「这 3 笔差异是新的还是上周就有的」。`code` 取 §4.2 的 D1~D9。任何校验项异常必须落 `check_failed`，禁止静默归零（与既有 fail-visible 铁律一致）。

## 五、回调安全

### 5.1 验签

- 签名对象必须是**原始请求体字节**（`raw body`），不得先 JSON 解析再重组字符串——重组会改变键序/空白/转义，是验签绕过最常见的原因。
- 签名算法、待签串拼装顺序、头部字段名一律以渠道官方文档为准（见 §7 待核 2，渠道未定前不写死）。
- 验签失败：返回 401，**不解析业务字段、不落业务表**，只落一条脱敏审计（时间、来源 IP、失败原因码）。
- 常量时间比较签名（避免时序侧信道）；允许的签名版本白名单显式声明，不接受「未知版本降级为不校验」。

### 5.2 重放防护

三道并行，任何一道命中即拒绝业务处理：

| 手段 | 规则 | 备注 |
|---|---|---|
| 时间窗 | 回调内的时间戳与本地时钟偏差超出窗口即拒（建议 ±5 分钟，**具体值待批**） | 依赖服务器时钟同步，同步状态待核（§7 待核 5） |
| nonce / 事件唯一 | 以 `(channel, external_txn_id, event_type)` 作为天然 nonce，TTL 覆盖时间窗的 2 倍 | 首选复用 L1 唯一约束（§3.1），零新增存储 |
| 幂等落库 | 即便前两道被绕过，`external_txn_id` 唯一索引仍保证只生效一次 | 这是最后一道，也是唯一不依赖内存状态的一道 |

**诚实说明**：进程内 nonce 缓存无法跨进程/跨重启共享，多 worker 部署下会退化。当前服务是单进程模型，暂可接受；一旦多进程化，必须换共享存储（另批，见 §7 待核 3）。**对外表述不得声称「已实现分布式重放防护」**。

### 5.3 密钥纪律

- 商户密钥/APIv3 密钥/证书私钥**只从环境变量读**，不写入任何表、不写入 `subscription_store` 的库文件、不写入任何 json 配置。
- 日志白名单：`order_id`、`event_type`、`result_code`、`amount_cents`、脱敏后的 `external_txn_id`（仅末 6 位）、来源 IP。**禁止**打印：完整请求体、签名头、密钥、证书内容、用户真实姓名。
- 异常栈不得整段落盘（栈里可能带内存中的密钥变量）；错误日志只记异常类型与脱敏消息。
- 密钥轮换流程须在有文档的前提下才允许上线（当前无轮换方案，属未完成项）。

### 5.4 回调端点必须独立于客户面页面

硬要求，理由与做法：

1. **不共用鉴权中间件**：客户面走 open_id/key/OAuth（`portal_api.py:3930` 现有路径），回调走签名。两者混在一个路由前缀下，迟早出现「为了放行回调而放宽客户面鉴权」的妥协。
2. **不共用进程/端口**：回调建议独立服务进程与独立端口（端口号待批，**不擅自指定**），nginx 只暴露回调路径给渠道出口 IP 段，不暴露给公网任意来源。
3. **路径不可枚举**：回调路径不挂在客户面静态资源目录下，不与 `/api/subscription/*` 同级。
4. **不返回业务细节**：应答体固定为最小结构（如 `{"code":"SUCCESS"}`），不回传订单状态、档位、金额——回调应答是给机器看的，不是给页面看的。
5. **独立限流**：回调按来源 IP + 渠道维度限流，与客户面限流池隔离，防止回调风暴打穿客户面。

### 6.3 切换判据（建议写成硬门）

**允许切 enforce 的最小集合**：1（至少字段最小化 + key 闸生效）、3（提醒已接排程）、4（撤销可用）、5（对账可日跑且 D7 能判）、6（同事务授予）、7、8、9、10 全部达成，且 §7 项 1/3 已由老田拍板。

**不允许切的情形**（任一条即否决）：定价未定；退款策略未定；撤销能力未上线；对账工具仍存在「按 open_id 猜」的盲区而不加声明。

**切换方式建议**：先按 open_id 白名单灰度（内部账号 + 少量真实客户），观察留痕中「本应拦住」的比例与客户反馈，再全量。**不允许**先全量后观察。

### 6.4 回滚

`enforce → observe` 必须是**一条命令可完成**的动作（改常量回 `observe` + 重启），且回滚不需要回滚数据（observe 不写业务表，只留痕）。这一点当前已天然满足，是既有设计的一个优点，切换方案必须保留它。

## 九、结论

账本侧（订阅生效、判定、到期清扫、留痕、只读投影）已经闭环且口径诚实；收银台侧目前只有一张**空表**和一条**零拦截的闸**。本方案把「钱进来之后如何变成权益、如何不被重复兑现、如何自证对得上、如何安全地收」写成可评审的约束集，把「收多少钱、退不退、开不开票、续不续」留给业务决策。

**当前状态：v0 预研 · 未实施 · 待 M3 商务材料（商户号/定价/税率）到位后另批实施。** 在 §7 的 1、3 两条未被老田拍板前，任何收银台编码工作都不应启动；在 §6.3 判据未满足前，`SUBSCRIPTION_GATE_MODE` 不得从 `observe` 切到 `enforce`。
