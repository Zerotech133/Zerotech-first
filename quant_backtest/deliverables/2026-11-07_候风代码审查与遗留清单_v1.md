## 2. 已修 BUG 清单（含验证证据）

### B-01　A6 模拟盘净值没有链接（P1，数字失真）

`paper_daily.py` 原写法 `nav = 1 + m["total_return"]`，而 `total_return` 是**滚动 60 日窗口**的累计收益。窗口每天前移，nav 就被重置回 1.0 附近，**永远不是净值序列**；`prev_nav` 算出来却从未使用（死变量），是"本应链接但漏了"的直接证据。

- 修法：`nav_t = nav_{t-1} × (1 + daily_ret_t)`；当日收益取自窗口净值曲线末两点（与窗口起点无关，可安全链接）；旧口径以 `window_return` 字段留档；`nav_basis="chain"` 标记新行。
- 幂等判断同时修正：原来只要当日行有 `nav` 就退出，导致 11-06 那行 `nav=1.0` 占位行**会永久挡住当日真实记录**；改为只认 `nav_basis=="chain"`。
- 验证：端到端跑通 —— `ledger += 20261106 nav=1.0000 n_pos=0 safe=False`，落盘行含 `nav_basis=chain`、`window_return=-0.174859`、原 `note` 保留；`execution_ledger` 行数仍 **3843 行 / 126 个交易日**，未被破坏。

### B-02　监护报告与执行账本用两套止损价（P1，人看到的数和机器记的数不一致）

`guard_one` 用 `hi_eff = max(持有期高点, **当日**分钟高点)` 算 SL/TP；`execute_positions` 用 `hi_prior`（截至昨日）。同一只票同一天，**报告说"已破止损"，账本记 `hold`**。监护人看报告做决策，机器按账本记账 —— 两条链从此对不上。

- 修法：新建 `guardian_agent_v1.0.4.py`（不改 v1.0.3，保留旧账可复现），`guard_one` 统一改用 `hi_prior`，并输出 `hi_prior` 字段备查。
- 验证（2025-11-17，可比持仓 7 笔，分钟线覆盖所限）：v1.0.3 报告 SL/TP 与执行不一致 **2 笔**；v1.0.4 **0 笔**。

### B-03　止盈触发前置条件含当日高点（P1，日内前视）

`if cl <= tp and g["hi_hold"] > ep * 1.02` —— 用**当日**高点判断"是否已站上成本×1.02"，再按**昨日**高点推的价位成交。这与 v1.0.2 修掉的日内前视同源，只是漏在触发门槛这一处。且 `hi_hold` 是 `round()` 后的展示值，被当作阈值用。

- 修法：改用 `hi_prior > ep * 1.02`（未取整）。

### B-04　账本重写遇坏行即崩，且静默丢审计行（P1，可用性 + 审计）

`keep = [l for l in open(...) if l.strip() and json.loads(l).get("date") != d]` —— 一行损坏（崩溃截断、磁盘满）就 `JSONDecodeError`，整日任务失败；即便不崩，解析不了的行也被丢弃。

- 修法：抽 `_ledger_keep_others()`，坏行**原样保留** + 计数告警（宁可留着脏行，不静默删证据）。
- 验证：`test_ledger_keep_others_unit` —— 目标日期行剔除、坏行保留、末行补换行，`bad==1`。

### B-05　红利防御档换仓成本只收单边（P1，年化系统性偏高）

`nav[-1] *= (1 - turn * COST)`，`COST=0.0015` 明确标注 `cost_oneway`。但换仓 = **卖出被换掉的 + 买入新进的**，`turn` 是单边名义换手，成本应为 `2 × turn × COST`。等于**成本少算一半**——这正是基线锁 `known_issues.COST` 记录过的"成本口径曾为实盘一半"的同类问题，只是换了位置又犯一次。

- 修法：`cost_mult = 1.0 if prev_w is None else 2.0`（首期从现金建仓只有买入单边），`nav[-1] *= (1 - cost_mult * turn * COST)`。
- 重跑结果（窗口 20230801~20261106，921 日 × 5815 票，月度调仓 39 期）：

| 档 | 年化（修正前→后） | 回撤 | Sharpe | 月胜率 |
|---|---|---|---|---|
| A 纯高股息 | −0.41% → **−0.73%** | −30.95% | 0.07 | 43.6% |
| **B 高股息+低波** | 18.82% → **18.09%** | −13.09% → **−13.43%** | 1.21 → **1.17** | 61.5% |
| C 综合打分 | 6.89% → **6.46%** | −23.56% | 0.42 | 46.2% |
| D 全市场等权 | 5.67% → **5.54%** | −28.13% | 0.33 | 46.2% |

- 参数敏感性同步重跑：24 组年化区间 **11.27%~19.91% → 9.67%~19.27%**，最深回撤 −17.11% → **−17.84%**；结论方向不变（24/24 为正）。
- 页面 `HOUFENG_DIVIDEND.html` 9 处硬编码数字已同步，并加了口径披露条；`houfeng_dividend.json` 重生成（`JSON.parse` 通过，`meta.cost_charge` 记录计费方式）。
- 归因随之更新：年化 18.09% = 股息 5.86pp + 资本利得 **12.23pp**，资本利得占比 **69% → 68%**；三档情景（13.9% / 5.9% / −6.1%）不变。

### B-06　页面 JSON 生产者没有 NaN 防具（P1，整页白屏）

`json.dump` 默认把 NaN 写成裸 `NaN`，浏览器 `JSON.parse` 直接抛错；Python 的 `json.load` 会放过，所以本地自测发现不了（11-07 已在选股页真实踩过）。四个生产者（`_arena_v103` / `_arena_36m` / `_hold_grid` / `_hold_grid_slot`）当时仍未设防。

- 验证：`test_json_safe_*` 3 例（含"裸 NaN 确实会让严格解析失败"的反证）。
