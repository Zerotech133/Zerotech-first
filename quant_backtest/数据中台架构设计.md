# 数据中台架构设计

> 版本：v1.0 · 日期：2026-09-27
> 范围：`quant_backtest` 数据层统一为中台，覆盖 tdx（xtcloud）+ tushare + 旧美股 + PostgreSQL + 资讯库

---

## 1. 目标与边界

### 1.1 目标
把当前 7 套割裂存储、3 种布局、多条直读路径，收敛为**一层薄中台**：
- **一个入口取数**：`datamart.read(table, dates, codes)` 屏蔽底层源差异
- **一张目录看全**：`catalog.json` 统一登记表/schema/来源/新鲜度/真源
- **一套调度收口**：所有增量同步进 Windows 计划任务，对齐 TdxSync 模式
- **一处质量监控**：`data_health` 扩展覆盖两大数据仓

### 1.2 不做什么（避免过度设计）
- 不建独立数据库服务（不引入 DuckDB/ClickHouse 常驻进程）
- 不动现有 parquet 布局（零迁移成本，沿用 `data/tdx`、`data/tushare` 现有分片）
- 不做实时流（中台是离线仓 + 日级增量，实时行情走 tdx_sync 的 ts_rt_min 独立通道）

### 1.3 设计原则
1. **口径正确性优先**：真源唯一、重叠表必有一份为准、降级路径显式
2. **零迁移**：存储层不动，只在上面加目录与读层
3. **断点续传与原子收口**：沿用 tdx_sync 的 manifest 模式
4. **防未来函数**：增量只读历史已完成区间，不读当日未结算数据

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  消费层  策略 / 门户 portal_api / 选股方法论 / 量化回测          │
└──────────────────────────┬──────────────────────────────────┘
                           │  唯一入口
┌──────────────────────────▼──────────────────────────────────┐
│  读层  datamart.py                                           │
│  read(table, dates, codes) → 路由 + 真源合并 + 口径归一        │
└──────────┬───────────────────────────────────┬──────────────┘
           │                                    │
┌──────────▼──────────┐              ┌─────────▼─────────┐
│  目录  catalog.json  │              │  质量  data_health │
│  表清单/schema/来源/  │              │  新鲜度/完整性/    │
│  真源优先级/新鲜度    │              │  唯一性/口径       │
└──────────┬──────────┘              └─────────┬─────────┘
           │                                    │
┌──────────▼────────────────────────────────────▼──────────┐
│  存储层（零迁移，保持现有布局）                              │
│  data/tdx/   data/tushare/   data/us/   *.db   PG         │
└──────────┬────────────────────────────────────▲──────────┘
           │                                    │
┌──────────▼──────────┐              ┌─────────┴─────────┐
│  采集  tdx_sync.py   │              │  采集  tushare_sync │
│  (xtcloud, 23:00)    │              │  (Tushare, 待挂任务) │
└──────────┬──────────┘              └─────────┬─────────┘
           │                                    │
┌──────────▼────────────────────────────────────▼──────────┐
│  源层  xtcloud rookie:48088   Tushare Pro API   PG zhice   │
└───────────────────────────────────────────────────────────┘
```

**四层分工**：源 → 采集（写）→ 存储 → 目录/读/质量（读）→ 消费。采集层只写不读；读层只读不写；目录是元数据中枢。

## 4. 存储层设计（零迁移 + 布局约定）

### 4.1 布局规范（沿用，不改存量）

| 数据形态 | 布局 | 示例 |
|---|---|---|
| 结构化日级表 | `data/<src>/<table>/part_NNNN.parquet` | `data/tdx/ts_daily/part_0001.parquet` |
| 分钟线深表 | `data/<src>/<table>/<code>_<YYYYMM>.parquet` | `data/tushare/idx_mins/000001.SH_202603.parquet` |
| 逐码日线 | `data/<src>/<table>/<code>.parquet` | `data/tushare/cb_daily/113537.SH.parquet` |
| 资讯文本 | `data/<src>/<src>_info.db`（SQLite） | `data/tdx/tdx_info.db` |
| 进度收口 | `data/<src>/_manifest.json` | `data/tdx/_manifest.json` |

> 分钟线与逐码日线按 (code,月)/(code) 切片，是 tushare_sync 已确立的月度拉取器模式，绕开远端深 offset 退化（见 project_memory 教训）。

### 4.2 命名约定
- 表名：`<源前缀>_<业务名>`，如 `ts_daily`（tushare 口径）、`tdx_sector_daily`（通达信口径）
- 源前缀：`ts_`=Tushare 原始、`tdx_`=xtcloud 加工、`us_`=美股、`hk_`=港股
- 日期列：交易类 `trade_date`、财务类 `end_date`，一律 `YYYYMMDD` 字符串
- 代码列：`ts_code`（除 `tdx_sector_daily` 用 `code`）

### 4.3 废弃计划
- `data/us/<TICKER>.parquet`（旧美股逐股）：tushare `us_daily` 收口后标记 `deprecated`，读层不再路由，保留 1 个版本周期后清理

## 5. 数据目录 catalog.json

中台元数据中枢。单文件、原子写（tmp+replace）、采集器写、读层与质量层读。

### 5.1 Schema

```json
{
  "version": 1,
  "updated": "2026-09-27T16:00:00",
  "tables": {
    "ts_daily": {
      "source": "xtcloud",
      "store": "data/tdx/ts_daily",
      "layout": "part",
      "schema": ["ts_code","trade_date","open","high","low","close","vol","amount"],
      "date_col": "trade_date",
      "code_col": "ts_code",
      "freq": "D",
      "priority": 1,
      "manifest": "data/tdx/_manifest.json",
      "freshness": "2026-09-26",
      "rows": 4136843,
      "done": true,
      "desc": "A股日线行情"
    },
    "cb_daily": {
      "source": "tushare",
      "store": "data/tushare/cb_daily",
      "layout": "by_code",
      "schema": ["ts_code","trade_date","open","high","low","close","pre_close","change_pct"],
      "date_col": "trade_date",
      "code_col": "ts_code",
      "freq": "D",
      "priority": 1,
      "manifest": "data/tushare/_manifest.json",
      "freshness": "2026-09-26",
      "rows": 0,
      "done": false,
      "desc": "可转债日线"
    }
  },
  "aliases": {
    "daily":     {"resolves": ["ts_daily"], "note": "A股日线唯一真源"},
    "hk_daily":  {"resolves": ["ts_hk_daily", "hk_daily"], "primary": "ts_hk_daily", "note": "xtcloud 优先，tushare 补深度"}
  }
}
```

### 5.2 字段语义
- `priority`：真源优先级，1=最高。重叠表中 priority 最小者为真源，其余作降级备份
- `aliases.resolves`：逻辑别名 → 候选物理表列表（按优先级排序）
- `freshness`：本地最新日期，由 data_health 每日刷新
- `done`：与 manifest 的 done 联动，false 时读层拒绝读（防读到不完整数据）

### 5.3 真源优先级矩阵（重叠表裁定）

| 逻辑表 | 候选源 | 真源 | 降级条件 |
|---|---|---|---|
| A股日线 | `ts_daily`(tdx) / tushare daily | `ts_daily`(tdx) | tdx manifest done=false → tushare |
| A股基础 | `ts_stock_basic`(tdx) / `stock_basic`(tushare) | `ts_stock_basic`(tdx) | 同上 |
| 港股日线 | `ts_hk_daily`(tdx) / `hk_daily`(tushare) | `ts_hk_daily`(tdx) | tdx 缺失 → tushare 补深度 |
| 公告 | `stock_notice`(tdx_info.db) / tushare anns | `stock_notice`(tdx) | tdx 落后 1 日 → tushare |
| 研报 | `stock_report`(tdx_info.db) / `research_report`(tushare) | `stock_report`(tdx) | 同上 |
| 新闻 | `stock_news`(tdx_info.db) / `news`(tushare) / `news.db` | `news.db`(JEV) | — |
| 美股日线 | `data/us/*`(旧) / `us_daily`(tushare) | `us_daily`(tushare) 收口后 | tushare 未就绪 → 旧 us |

> 原则：xtcloud 已闭环的表优先（新鲜度有 TdxSync 保障）；tushare 独占的分钟线/美股财报/可转债直接为真源。

## 6. 统一读 API：datamart.py

读层唯一入口，替代消费方直读 parquet 与多读层并存。**只读不写**。

### 6.1 接口

```python
def read(table, start=None, end=None, codes=None, fields=None):
    """统一读。table 可为物理表名或别名。
    返回 pd.DataFrame，列名归一、日期归一 YYYYMMDD、代码归一 ts_code。
    跨源合并时按 (code, date) 去重，真源优先。
    """

def latest(table, codes=None):
    """返回该表本地最新日期（新鲜度探测）。"""

def ready(table):
    """表是否可读（catalog done=true 且 manifest done=true）。"""

def columns(table):
    """返回归一化 schema。"""
```

### 6.2 路由逻辑
1. `table` 查 catalog：别名 → 解析为 priority 升序的物理表列表
2. 逐表检查 `ready()`，跳过未就绪
3. 按 layout 分派读取器：
   - `part`：`pd.concat(pd.read_parquet(glob))` + 日期/代码过滤（复用 tdx_read 现有逻辑）
   - `by_code`：按 codes 命中 `<code>.parquet` 逐文件读
   - `by_code_month`：按 codes × [start,end] 月份命中 `<code>_<YYYYMM>.parquet`
   - `sqlite`：参数化 SQL
   - `pg`：走 data_loader
4. 多源结果按 (code, date) 去重，保留 priority 最小源
5. 列名/日期/代码归一后返回

### 6.3 与 tdx_read 的关系
- `tdx_read.py` 现有 5 函数（read_day/read_range/read_info/day_map/table_ready）保留为 tdx 专属快速路径
- `datamart.py` 内部对 tdx 源表直接委托 `tdx_read`，不重写
- 消费方新代码一律用 `datamart.read`；存量 tdx_read 调用不强制改

### 7.3 增量语义（沿用 tdx_sync 修复后的口径）
- 增量从本地最新日期续拉，`start_date=最新日`（重叠一天，去重兜底）
- **增量 offset 必须重置 0**（远端 offset 基于 start_date 过滤后结果集，非全表 offset —— 见 project_memory 教训）
- manifest 收口后增量结束 `offset=0` 还原

## 8. 数据质量监控：data_health 扩展

### 8.1 现状
[data_health.py](data_health.py) 扫 ashare / news.db / 策略产物。

### 8.2 扩展覆盖两仓
新增扫描项（读 catalog.json 驱动）：
| 检查 | 方法 | 阈值 |
|---|---|---|
| 新鲜度 | `latest(table)` vs 今日 -1 交易日 | 落后 >1 交易日告警 |
| 完整性 | manifest done=true 但行数=0 | 任何=告警 |
| 唯一性 | (code,date) 重复计数 | >0 告警 |
| 口径 | date_col 值格式是否 YYYYMMDD | 非 8 位数字告警 |
| 覆盖 | 基础表 code 数 vs stock_basic | 偏差 >5% 告警 |

### 8.3 产出
- 控制台报告 + `data/_health_{YYYYMMDD}.json`
- 异常推送飞书（沿用 aios-domain-scaffold 的推送通道，可选）

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| tdx/tushare 重叠表口径不一致（如复权、单位） | catalog 标注口径字段，读层归一；真源优先，不作静默合并 |
| tushare 深表拉取耗时（分钟线 6-7h） | 月度拉取器断点续传，可停可续；不阻塞中台读层（未 done 的表 ready()=false） |
| 计划任务身份/中文路径问题 | 沿用 start_tdx_sync.ps1 的注册表源+内存 dot-source+ACL 自愈模式（system-task-deploy skill） |
| catalog 与 manifest 不同步 | catalog 由 data_health 每日刷新 freshness/done；采集器只写 manifest，不直接写 catalog |
| 旧美股废弃后历史回测断链 | deprecated 表保留 1 版本周期，读层降级路由兜底 |
