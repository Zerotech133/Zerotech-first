**报告整体判定（收集器退出码，见 `xq_timeline_watch.py:329`）**：

- 退出码 **0** = 五项中无 FAIL（PASS 与 UNKNOWN 都算绿）；

| 项 | PASS | FAIL（处置路径） | UNKNOWN（通常含义） |

## A2 19:05 验收三态与 verify_alert.log 语义

读码确认（`tools/verify_daily_report.py` 文档串与 `run()` 出口）：

| 退出码 | 含义 | 落盘行为 |
|---|---|---|
| **0** | 全部通过（15 键 + 语义 + 新鲜度 mtime ≥ 今日 19:00） | 追加一行 ASCII 到 `verify_status.log`（`rc=0 mode=full`） |
| **1** | 任一检查失败（fail-visible） | 告警全文**覆盖式**写 `verify_alert.log`（含时间戳 + 逐项 `FAIL <检查名>: <原因>`），同时 status log 记 `rc=1` |
| **2** | **latest.json 尚不存在**（报告未生成，极早期态） | 只在 status log 记 `rc=2`，**不算 crash、不告警** |

**"仅失败落盘"语义**：验收通过时 verify_alert.log 完全不被触碰（不存在就
保持不存在）；它一旦存在，内容就停留到下一次失败为止。所以：

- `verify_alert.log` **不存在** = 历史上从未失败过（今晚 19:05 正常通过的话也是这个形态）；
- 存在 ≠ 今晚失败 —— 必须**对照文件 mtime 与内容首行时间戳**判归属。

验收的检查项构成（FAIL 时 alert 里出现的检查名，对应三类常见原因见 A3）：
15 顶层键齐全性、extractor_version 与 `xq_classify._TICKER_VERSION` 动态比对、
pipeline（llm_model=qwen3.5:9b + 非空 prompt_version）、word_tempo 的
bearish/bullish 两列、content_type 非"空 dict 但 posts_today>0"、容器键类型
抽查、latest.json mtime ≥ 今日 19:00 新鲜度。

### ② 验收 FAIL（verify_alert.log 出现今晚 19:05 时间戳）的三类常见原因

1. **新鲜度**（`FAIL freshness: latest.json mtime ... is before today 19:00`）

   ——日报 payload 结构漂移。处置：对照 15 键清单定位是哪个环改了产物结构；
3. **版本比对 mismatch**（`FAIL extractor_version` / `FAIL pipeline_llm_model`）
   ——日报生成后有人改了 `xq_classify.py` 常量（验收动态抓源码版本）。

# Part B OLLAMA_NUM_PARALLEL=2 切换手册（拍板后照做）

> **这是用户拍板项**：改该环境变量必须重启 Ollama 服务，会打断当前推理
> 队列。本文只记录步骤，不代执行。
> 依据：`docs/2026-10-18_LLM并发基准提案.md`（commit 06539a19，conc-bench
> 实测：workers=1→2 吞吐 8.89→13.56 条/分（1.53×），workers=4 饱和无增益
> （1.50×）且单条延迟 5.75s→11.08s 恶化——**只设 2，不设 4**）。

## B1 前置：选班间隙 + 确认无活跃连接

1. **选班间隙**：整点班刚收工后（看 `automation_runs/xq_classify/xq_classify_status.log`
   末行出现 `round end rc=...` 即本班已收尾，下一班整点才来）。推荐窗口：
   **明天（10-19）13:30 sprint 首跑前**的上午时段，或今晚生产链环（18:00
   爬虫不用 LLM，19:00 日报环用）之外的空档。**避开** 13:30–17:30 sprint
   窗口与整点班进行中时段。
2. **确认无活跃连接**（管理员 PowerShell）：
   `netstat -ano | findstr :11434 | findstr ESTABLISHED`
   ——无输出才动手；有输出说明有请求在飞，等它结束。
3. （可选自证）当前承载形态：`ollama ps`——基准实证 PROCESSOR=100% CPU
   （无 NVIDIA GPU，`nvidia-smi` 不存在），本手册内存代价按 CPU 推理口径写。

## B2 步骤

1. **设用户级环境变量**（二选一）：
   - 命令行：`setx OLLAMA_NUM_PARALLEL 2`（写入用户环境，新进程生效）；
   - GUI：系统设置 → 高级系统设置 → 环境变量 → 用户变量新建
     `OLLAMA_NUM_PARALLEL` = `2`。
2. **重启 Ollama 服务**（按本机安装形态二选一）：
   - **服务形态**（Ollama 以 Windows 服务/后台进程常驻）：
     `services.msc` 找到 Ollama 服务 → 重启；或管理员 PowerShell
     `Restart-Service ollama`（服务名以 services.msc 实际显示为准）。
     重启后环境变量才会被新进程读到。
   - **托盘手动形态**（Ollama 以当前用户托盘应用运行）：托盘右键 Ollama
     图标 → Quit/退出 → 开始菜单重新启动 Ollama。注意从托盘启动的进程
     读用户级环境变量（setx 用户级即可，无需系统级）。
   - 两形态通用的死办法：任务管理器结束所有 `ollama.exe` 进程 → 重新
     启动 Ollama 应用。重启后服务端冷加载模型 ~13s（基准实测口径）。
3. **切完再核对一次 B1-2**（确认重启后无残留半死连接）。

2. **最小生成**：一次最小生成调用（如
   `curl http://127.0.0.1:11434/api/generate -d "{\"model\":\"qwen3.5:9b\",\"prompt\":\"ping\",\"stream\":false,\"options\":{\"num_predict\":200}}"`）

3. **真实吞吐观察**：13:30 **XueqiuBackfillSprint 首跑**时观察
   `automation_runs/xq_classify/xq_classify_status.log` 的
   `labeled_this` 与班次耗时，对照基准口径：并发 2 应体现 ~1.5×（8.89→

## B4 回滚

1. 删环境变量：`reg delete "HKCU\Environment" /v OLLAMA_NUM_PARALLEL /f`
   或 GUI 环境变量对话框删除（setx 设为空串会留下空值条目，建议 reg/GUI 删净）;
2. 重启 Ollama 服务（同 B2-2 两形态）；
3. 验证回到单并发形态：`ollama ps` 正常 + 下一个整点班心跳正常即可。
   回滚无数据风险：分类库写入侧有 NOT IN 幂等 + busy_timeout 兜底，
   重启只影响在飞请求。

## B5 风险声明与顺带提案

1. **重启打断当前推理**：会杀掉在飞请求与排队队列。影响有界——追平轮
   每班新起进程自愈，被杀班次的未完条目下班继续（NOT IN 幂等续跑）；
   sprint 侧每日新进程起手，陈锁 pid 探活失败会接管。**不存在跨班状态损毁。**
2. **顺带提案 `OLLAMA_KEEP_ALIVE=2h`**（重启一次顺带设上，setx 同 B2）：
   防 16:53 型掉驻事故复发——Ollama 默认 keep_alive 5m，**班间空窗 >5m
   模型掉出驻存，下一班首批请求冷加载（num_ctx 2048 实测 ~8s）**，冷加载
   与 300s 超时赛跑是昨晚 8 连 hard-fail ABORT 的诱因之一。判例警示：
   一次性诊断请求带 `keep_alive='2h'` 参数在本机 Ollama 版本**未生效**
   （expires_at 只延了 5m）——所以必须用**服务级环境变量**，请求级参数
   靠不住。活跃请求会刷新计时，持续班次无掉驻风险，收益只在班间空窗。
3. **CPU 推理并发 2 的内存代价**：本机 100% CPU 推理（无独显），权重
   7.8GB 不变，并发槽 ×2 = KV cache 翻倍，但每槽 num_ctx=2048 很小，
   RAM 充裕，低风险（基准提案原文口径）。**不要设 4**：饱和无增益，
   单条延迟反而 5.75s→11.08s。
4. **收益边界如实陈述**：并发 2 只是把 CPU 榨到 1.53×；数量级提速只有
   换更小模型或上加速硬件两条路（超出本手册范围）。
5. **遗留风险**：基准样本仅 4 条、单轮、背景有 automation 负载——1.53×
   是量级参考不是精确承诺；切换后首个整点班与 13:30 sprint 首跑是真实
   验收点。另外 `docs/2026-10-18_并发基准.md` 这一文件名与实际入库文档
   `docs/2026-10-18_LLM并发基准提案.md`（commit 06539a19）不一致，引用时
   以后者为准。
