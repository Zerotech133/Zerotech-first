## 2. 死亡未重演的排除价值

历史死亡间隔 15-25 分钟（16:53、17:16 两次）。监视窗 35 分钟（超上限约 10 分钟）内无死亡，且监视期内下列任务**全部按点触发并正常返回**：

**推论**：
1. 凶手不是"每次触发必杀"的周期任务——否则 17:25-17:57 内至少 7 次触发机会必然重演死亡。
2. 若凶手是周期任务，其杀伤条件是**条件式**的（例如仅在某进程特征存在、某文件存在、或某负载状态下才动手），或者该任务在 17:16-17:25 之间被人工叫停/修复。
3. ollama_watchdog.py（16:52 被改，恰在第一次死亡前 1 分钟）的改动内容仍是头号待查物——监视窗内它的行为已证明"当前版本"无害，但 16:52 改动到 17:17 之间的版本行为无法由本次监视覆盖。

## 3. 死亡方式定性（基于两案既有现场 + 本次旁证）

**定性：外力终止（taskkill /f 或 TerminateProcess），非自行崩溃、非正常退出。**

依据：
1. **server.log 尾行**（`C:\Users\t\AppData\Local\Ollama\server.log`，止于 17:13:25）：最后记录为正常 `200 | GET /api/ps`，无 panic、无 exception、无优雅 shutdown 序列——Ollama 被外力杀死时不会写任何日志，与其"安静消失"完全吻合。
2. **llama-server runner 存活而主进程死亡**：若为 Ollama 自身崩溃（OOM、panic），runner 子进程通常会随之消失或由系统记录；仅主进程孤立死亡是句柄/进程被定向终止的典型指纹。
3. **Application/System 事件日志**：两次死亡时刻 ±2min 无 WER（1001）、无 Application Error（1000）、无 7031/7034/6008。进程被 `taskkill /f` / `TerminateProcess` 杀死不产生任何事件日志，与现场一致。
4. **0xC000013A（STATUS_CONTROL_C_EXIT）**：XueqiuSeedAuto 16:41 同窗被此代码杀——这是控制台收到 CTRL_C/窗口关闭的指纹，提示同窗内存在 **console 事件型杀手**（托盘 app 拉起的 serve 其宿主 console 被关闭时即此表现）。

## 5. 修复建议

1. **给 serve 换宿主**：以 `-d` / detached / 计划任务方式启动 serve，脱离任何 console 宿主，可同时消除嫌疑 2（console 事件）并保留取证能力。
2. **加退出遥测**：用 `WMI __InstanceDeletionEvent within 2` 或 `Register-WmiEvent` 监视 ollama.exe 进程删除事件，抓取进程消失瞬间的 ** terminacion 状态码**（`Win32_ProcessStopTrace` 有 ExitStatus）——一次死亡即可拿到真凶退出码（taskkill=被另一进程句柄终止，Ctrl+C=0xC000013A）。监视器 v2 可加此通道。
3. **封存证据**：立即备份 `ollama_watchdog.py` / `nova_guard.py` 当前内容并与 16:52/16:47 前版本 diff；调优会话的 shell history / 会话日志一并封存。
4. **复跑监视器**验证：`C:/Users/t/.workbuddy/binaries/python/envs/default/Scripts/python.exe C:/Temp/ollama_death_watch.py [秒数]`（默认 2100s）。日志追加于 `C:/Temp/ollama_death_watch.log`。只读、可随时中断、无副作用。
5. 若复跑期死亡重演，第一时间收集：`Get-WinEvent Application/System` 死亡 ±2min、`watchdog.log` 同刻、以及**上一个 30min 窗内所有计划任务 LastRunTime**（比对手法同本次报告 §1）。
