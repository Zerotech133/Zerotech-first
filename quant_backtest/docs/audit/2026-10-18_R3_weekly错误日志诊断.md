## 4. 根因分析

**直接根因（一句话）**：ledger.jsonl 在 09:05:47 被某外部进程瞬态独占（最可能是杀软对刚膨胀的 9.3MB 文件的按需扫描、云同步客户端或编辑器句柄；同进程其他 RiskGuard 实例间 `os.open` 共享模式不会互相 EACCES），单次 `os.open(O_APPEND)` 失败即让整个 2713 标的批次崩掉。

放大损失的四个设计缺口（均只读确认，未改动）：

1. **`append_ledger` 无重试**（kg_riskguard.py:318-334）：单次 open 失败异常直接上抛至 main → sys.exit(1)，瞬态锁 = 整批阵亡。
2. **周幂等键过弱**（riskguard_r3_weekly.ps1:36 `nR3 -gt 10`）：812/2713 的残批被判定为"已完成"，无断点续跑能力。
3. **每日幂等键与周批不独立**（riskguard_shadow_daily.ps1:31-34 统计当日**全部**行 >100）：周批周六写入的 812 条 R3 行会触发日线 skip——脚本注释声称"独立"，实际只有单向独立；本周五批失败后周六无法自愈正是被此键挡住。
4. **err.log 为覆盖型重定向**（ps1:44 `2>`）：历史错误被后续运行抹掉，可观测性受损。

## 5. 建议修复动作清单（按严重度）

1. 【高】**补齐 10-17 周 R3 样本**：以 `--only-r3` + 按 security 判重的方式对 10-17 快照补跑剩余 ~1901 标的（需 eval-batch 支持或临时手工筛掉已入账标的）；若不补，须在 OOS 对账口径中标记本周 R3 样本偏斜。
2. 【高】**append_ledger 加瞬态锁重试**：对 `PermissionError`/`OSError` 做退避重试（如 3 次 × 0.5/1/2s），或在 evaluate() 层将单标的入账失败降级为 stderr 记录+批末汇总，不让单点锁杀死整批。
3. 【中】**周幂等键改为覆盖率判据**：如 `nR3 ≥ 快照标的数 × 0.95` 或按 security 集合判重，天然支持断点续跑。
4. 【中】**每日幂等键只统计 R1/R2 行**（rule_id 过滤），与周批 R3 行真正解耦；恢复"周五批失败 → 周六批自愈"能力（哈希守卫仍防同数据日重复）。
5. 【中】**开启任务计划程序事件日志**：`wevtutil set-log Microsoft-Windows-TaskScheduler/Operational /enabled:true`，否则触发史永久不可考。
6. 【低】**排查独占锁来源**：将 Python311 与项目目录加入杀软排除项；确认 ledger.jsonl 无编辑器/云盘长持句柄。
7. 【低】err.log 改为追加+轮转（或按日期分文件），保留错误历史。
