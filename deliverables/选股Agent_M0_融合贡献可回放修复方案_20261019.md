## 一、问题定义

M0 计划中六策略信号经 `strategy_layer/aggregator.py` 融合后写 PG。已证实现状缺陷：

**同一策略对同一 symbol 产出多条信号时（如 chan_monitor 多个缠论枢轴日），`_fuse_symbol` 的 contributions 以 strategy_id 为 dict 键，后条覆盖前条**；而 score/action 票决/confidence/divergence 均按全部条目计算——分母计入重复条目、明细只剩最后一条，**同票裁决结果无法从落库明细回放**，违反"任何决策可溯源"中台底线（M0 计划头部纪律 5）。

只读证据测试三例（`test_contributions_replay_evidence_readonly.py`）：

| 测试 | 证据 |
|---|---|
| `test_contributions_keep_only_last_entry_for_same_strategy`（L29-44） | buy80+sell20 两条：score=(80+20)/2=50、divergence=True 计入两条；contributions 只剩 1 键且为最后一条（sell/20） |
| `test_contributions_surviving_detail_depends_on_entry_order`（L47-58） | 仅调换输入顺序，score 不变而幸存明细相反——落库结果含**顺序随机性** |
| `test_duplicate_same_action_signals_undercount_in_contributions`（L61-73） | 同向两条 buy：明细剩 1 条，confidence 折损却按 2 条计（×1/2），**明细与数值脱节** |

## 二、现状代码证据（只读）

### 2.1 contributions 数据结构与覆盖点

`quant_backtest/strategy_layer/aggregator.py`：

- **覆盖点本体** L420-425：`contributions = {sid: {...} for sid, w, sig in entries}` —— dict 推导式按条目遍历，同 sid 多条时后者覆盖前者。每条明细结构：`{"score": float, "weight": round(w/total_w, 6), "action": str}`。
- score（L396-397）：`Σ(w_i × score_i) / total_w`，**按全部条目**加权均值。
- action 票决（L400-412）：按全部条目累计各 action 的 `(权重和, 条数)`，权重多数决 + 条数 + 固定序 `buy>sell>hold>watch`（L45）裁决。
- confidence（L414-418）：`max(各条 confidence) × mean(w_i/Σw) = max_conf × 1/n`，**n = 条目数**。注意模块 docstring L11-13 自述语义为"n 为该 symbol 的**贡献策略数**"——同策略多条时实现与自述语义背离。
- divergence（L431-433）：对全部条目的 action 集合判定 buy∧sell 并存。
- rationale（L426-429）：**按全部条目拼接**（`[sid] rationale；…`）——这是现状落库中唯一保留全部条目痕迹的字段，但不含 score/action 数值，不足以回放。
- 附带发现：`run()` 内存分歧清单 `divergences` 的 `actions` 字典同样以 sid 为键（L370-371），同策略多条时同遭覆盖（内存对象，不落库，影响面小）。

### 2.2 run() → PG 写入路径

- 上游调用方：`strategy_layer/run_daily.py:49`（每日生产入口）。
- `run()` L376-383 → `persist_combined()` L220-236：psycopg2 主路径失败自动降级 docker exec psql `\copy` 兜底，全链失败抛异常由 run 捕获降级为告警（不中断）。
- 目标表：`strategy.signals_combined`（`COMBINED_TABLE` L51），列 `COMBINED_COLS` L53-54：`trade_date, symbol, action, score, confidence, contributions(jsonb), divergence, rationale`。
- 主路径 `_persist_psycopg2` L127-164：当日 `DELETE` + `INSERT … ON CONFLICT (trade_date,symbol) DO UPDATE`（K-STOCK-420 权威替换语义，L137-147）；contributions 经 `json.dumps` 写入 jsonb（L150）。
- 兜底路径 `_persist_docker_exec` L167-217：TRUNCATE 暂存表 → DELETE 当日 → `\copy` 灌 `strategy._stg_combined`（L52）→ merge（L190-199），contributions 同样 json 序列化（L181）。
- 表 DDL：`strategy_layer/sql/schema.sql` L13-23，`contributions jsonb NOT NULL DEFAULT '{}'`，PK `(trade_date, symbol)`。**jsonb 无结构约束，改结构不需 DDL，但所有消费方的解析逻辑即是事实契约**。schema 头部纪律（L3）："纯增量 DDL（IF NOT EXISTS），**绝不 DROP / ALTER 现有对象**"。

### 2.3 消费方全景（检索 `signals_combined` 全库命中）

## 三、修复方案（2+1 个，供拍板）

### 方案 A：contributions 原键转列表（原地改结构）

**做法**：`_fuse_symbol` L420-425 改为对 entries 按 sid 分组，同 sid 多条时值存 `list[{score, weight, action, …}]`（单条可保持 dict 向后兼容，或统一列表全量改）。

- **PG 契约影响**：jsonb 无需 DDL；但 `schema.sql` L11-12 的结构示例注释必须更新，实际契约变更为破坏性（值类型 dict→dict|list 或整体变列表）。
- **消费方影响**：dashboard 透传不受影响，但前端 L376/L386 两处渲染与统计必改；weight_updater `contrib.get(sid)` 逻辑必改（列表需过滤遍历）；test_aggregator.py 多处断言破。波及 3 个消费方 + 测试基线。
- **回放能力达成度**：**完整**。全部条目 score/weight/action 落库，可精确重建裁决输入（分母、票决、divergence 均可回算）。
- **实施风险**：中偏高。破坏性契约变更，历史行（dict 形态）与新行（list 形态）并存，所有读方需双态兼容；P4 影子期若同时在跑，隐式反馈数据出现断代。

### 方案 B：新增 audit 侧写，不动原键（推荐）

**做法**：原 `contributions` 键结构**保持现状一字不动**，新增侧写承载全量条目明细。两个子形态：

- **B1 行内列**：`signals_combined` 加列 `contributions_full jsonb`（ALTER TABLE ADD COLUMN IF NOT EXISTS），COMBINED_COLS 与两条写库路径同步扩列。
- **B2 独立侧写表**：新建 `strategy.signal_entries_audit(trade_date, symbol, strategy_id, seq, score, weight, action, confidence, created_at, PK(trade_date,symbol,strategy_id,seq))`，在 `persist_combined` 同一写库流程内追加写入；当日 DELETE 权威替换时同步删侧写当日行；docker `\copy` 兜底路径为该表补一段式 copy。

- **PG 契约影响**：B1 触碰 schema.sql L3 "绝不 ALTER 现有对象"的成文纪律（ADD COLUMN 虽增量但形式为 ALTER，需豁免或修订纪律）；B2 为纯 CREATE TABLE IF NOT EXISTS，**完全符合纪律**。原列原表读契约零变更。
- **消费方影响**：**零破坏**。dashboard/前端/weight_updater 原样继续；回放与后续审计（G6 后验、BACK1 台账）走新侧写读路径，逐步采用。
- **回放能力达成度**：**完整且超集**——侧写可携带每条目的 confidence 甚至 rationale 原文，回放粒度优于方案 A。
- **实施风险**：低-中。B2 成本在写路径：两条 persist 链路都要加侧写步骤，兜底链失败语义需明确（侧写失败是否告警不中断，建议对齐现状"只告警"口径）；B1 成本在纪律豁免与列序兼容。

### 方案 C：融合前同票预聚合（改裁决语义）

**做法**：`run()` 收集后、`_fuse_symbol` 前按 `(symbol, strategy_id)` 预聚合成单条——如 score 取均值/最新、action 取该策略内部规则（最新 dt 或保守向）、confidence 取 max。融合层只见"每策略一条"。

- **PG 契约影响**：零。contributions 仍是 `{sid: dict}` 且天然无覆盖。
- **消费方影响**：零（结构不变）。
- **回放能力达成度**：**不完整**。策略内部多条被聚合掉，除非聚合明细另行落库（若落则等同叠加方案 A/B）；现状"score 计入全部条目"的数值语义也改变。
- **实施风险**：中。本质是把"同策略多条怎么裁决"这一**业务问题**硬编码进聚合层——而这正是 M0 §8.6 待拍板的"同票冲突裁决"议题本体，不应由实现侧单方决定。附带收益：预聚合后 n=策略数，confidence 折损回归 docstring L11-13 自述语义。

### 方案对比矩阵

| 维度 | A 原键转列表 | B1 行内加列 | B2 独立侧写表 | C 预聚合 |
|---|---|---|---|---|
| PG 契约 | 破坏性结构变更 | ALTER 加列（违纪律字面） | 纯增量建表 ✅ | 零 |
| 消费方 | 3 处 + 测试基线全改 | 零 | 零 ✅ | 零 |
| 回放能力 | 完整 | 完整 | 完整且超集 ✅ | 不完整 |
| 裁决语义 | 不变 | 不变 | 不变 | **改变（需业务拍板）** |
| 实施风险 | 中高 | 中 | 低-中 | 中 |
| 历史数据兼容 | 新旧双态并存 | 历史行 NULL | 历史行无侧写（自切换日起有效） | 数值口径断代 |

## 四、建议方案与拍板点

### 建议

**分两步走，先观测后语义：**

1. **回放修复采纳方案 B2（独立侧写表）**。"明细被覆盖"是可观测性缺陷（客观 bug），修复不应与裁决语义绑定；B2 零消费方破坏、符合 schema 纯增量纪律、回放粒度最优。侧写自切换日起生效，历史行不回填（无法回填，如实声明）。
2. **裁决语义（方案 C 方向）作为独立业务议题**，与 M0 §8.6 "同票冲突裁决"合并拍板——包括 confidence 分母语义（现状按条目数、文档按策略数，L414-418 vs L11-13 背离）——拍板后作为确认门③合龙前置的第二个改动实施。
