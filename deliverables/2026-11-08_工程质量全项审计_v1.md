**这套系统在"安全"和"测试"两项上的成熟度显著高于一般个人项目，真正的欠账在"交付工程"（灰度、容器化、CI 激活、压测基线）。**

- 回归：**118 个测试文件 / 1282 用例通过 / 0 失败 / 0 错误**（隔离执行 11.1 分钟）；但**整体 `pytest .` 会挂死** —— 这是测试隔离缺陷，不是代码缺陷。

- 缺陷：修了 3 处 `undefined-name`（类型注解级，非运行时崩溃）。
- 依赖：全局环境 62 个包 / 609 条漏洞条目，其中 **16 个被本仓实际 import**。

## 2. 回归验证（最重要的一组实测）

### 2.1 整体跑会挂死

`pytest . -q --timeout=180` 跑到 **79%** 后整体终止，无 summary，最后栈指向
`portal/os_goal_store.py:70` 的 `time.sleep(0.05)`。

单独复现该用例：

```
tests/test_os_goal_store.py::test_file_lock_open_gives_up_after_deadline
1 passed in 0.38s
```

**结论：不是锁死锁，是测试间相互干扰**（前序用例的 monkeypatch/线程/文件句柄泄漏），
叠加 `pytest-timeout` 在 Windows 上打断后终止整个 session，导致拿不到失败清单。

### 2.2 隔离执行的基线

`_audit_20261108/audit_portal_tests.py` 按文件起独立进程（每文件 25s 用例超时、90s 进程超时）：

| 指标 | 值 |
|---|---|
| 测试文件 | 118 |
| rc=0 | 116 |
| 用例 passed | **1282** |
| failed / error | **0 / 0** |
| skipped + xfail | 5 |
| 总耗时 | 11.1 分钟 |
| 超时（非失败） | `test_os_asr.py` 29.0s、`test_trace_drilldown_guard.py` 28.6s —— 超过我设的 25s 阈值 |

**这两个"超时"是我的阈值太紧造成的**，不是用例失败；放宽到 60s 即可。
建议把 25s 写进 CI 的 per-test timeout，否则这两个慢用例会稳定飘红。

## 3. 安全排查（五类，逐类给结论）

| 类别 | 方法 | 结论 |
|---|---|---|
| 命令注入 | grep `shell=True` 全 `portal/` | **0 处** |
| 代码执行 | `eval/exec/pickle.loads` | 仅 JS 字符串与测试隔离加载（均带 `# nosec`） |
| SQL 注入 | 扫 `execute(f"..."/"%"/"+")` | 唯一命中是参数化占位符 `_PG_SQL + " WHERE ... %s"` + 元组传参，**安全** |
| 凭据落盘 | 追 `_PORTAL_TOKEN` 生成链 | env → `_vault\secrets\portal_api_token` → 随机生成；**不在 portal/ web root 内**（注释亦明确警告过此风险，实现正确） |
| 依赖漏洞 | `pip-audit` 全环境 | 62 包 / 609 条；16 个被本仓 import（详见 §3.1） |

### 3.1 依赖漏洞要打折看

`pip-audit` 扫的是 **537 包的全局环境**（含 AI 工具链），不是 portal 的运行时闭包。
按"本仓实际 import"过滤后剩 16 个：`pypdf(75)`、`tornado(28)`、`pip(12)`、`filelock(9)`、
`urllib3(7)`、`brotli(4)`、`h2(4)`、`msgpack(3)`、`setuptools(3)`、`pygments(3)`、`lxml(2)`、
`pytest(2)`、`black(1)`、`brotlicffi(1)`、`fsspec(1)`、`torch(1)`。

- `pip` / `setuptools` / `pytest` / `black` / `filelock` 属工具链，不在请求路径上；
- **`pypdf`、`tornado`、`urllib3`、`lxml`** 才可能有实际暴露面，需按调用点确认可达性（未做，属剩余工作）；
- 这 16 个里 58/62 个包在 OSV 有修复版本，但**直接升级会动 AI 工具链**，必须单独排期与回归，不能顺手升。

## 4. 本轮发现的问题（按优先级）

### P2-a 鉴权是"列举式默认放行"

```python
if path in _MUTATION_POSTS and not self._check_portal_token():  # 52 条
if path.startswith(_EARLY_TOKEN_PREFIXES) and not ...:          # 3 条前缀
```

其余 POST 路径**默认不过鉴权闸门**，靠各 handler 自己校验。AST 枚举后：

- Handler 真实继承 **32 个 mixin**，POST/PUT 分支路径常量 **65 个**，其中 **15 个未登记**；
- 逐个核查：`/feishu/event` 走 `X-Lark-Signature` 验签；`/api/legion/*` 有独立 token（`api_legion_ops_v2._load_token`）；`/api/zhuge/*` 有审查用例；`/api/preview`、`/api/project/preview` 为幂等预览。**当前无裸奔写端点**；
- 但**新增端点默认放行**这个形态本身是风险：忘记登记 = 静默开洞。

> 首版扫描器把 `api_model_admin.py` 也算进来（它跑在 `:8098`，不在继承链上），误报 5 条
> （`/api/service`、`/api/binding`、`/api/auto_assign` 等）。已按"真实 mixin 集合"自纠。
> 该文件**确实无鉴权**，但 8098 绑 `127.0.0.1`，局域网不可直达，故降为纵深防御缺口。

**建议**：改为默认拒绝 + 例外白名单；或至少在 `do_POST` 末尾加"未登记路径必须 handler 内已鉴权"的断言。

### P2-b `/api/overview` 冷启动 11.3 秒

实测：首次 `11.31s`，20s TTL 内第二次 `0.034s`。原因是聚合 docker / PowerShell 子进程。
若巡检或 watchdog 以 20s 周期调用，等于**每 20 秒烧一次 11 秒 CPU 与多进程开销**。
建议：把聚合拆成"轻量骨架（秒级）+ 重型指标后台刷新"，或把 TTL 提到 60s 并加单飞（single-flight）防击穿。

### P2-c 测试隔离缺陷（见 §2.1）

建议：给 `os_goal_store` / 全局 monkeypatch 的用例加 `tmp_path` 隔离与显式恢复；
CI 用 `-p no:randomly` + 每文件独立进程，避免相互污染。

### P3-a 三张表缺业务索引

`nine_dim_rc`(4413) / `nine_dim_fina`(4718) / `nine_dim_fc`(4413) / `xq_status_classified`(33461)
只有主键索引。数据量小，当前影响可控；`xq_status_classified` 若按 code 查会全表扫。

### P3-b 备份缺"恢复演练"

备份链路质量很高（异地 + 字节校验 + 加密 + 保留策略），但**只有备份校验，没有恢复演练记录**。
建议每季度做一次"随机取一日批次 → 恢复到临时目录 → 校验行数与校验和"，留机读回执。

## 5. 明确判定为"不适用"的两项

- **分布式事务**：单进程 + 文件锁 + 追加式账本，没有跨库事务边界。
- **消息队列**：任务队列用 `jsonl` + 文件锁（`os_goal_store`、`jev_review_queue`）实现，
  单写者语义够用。强行引入 broker 只会增加运维面。

同理 **灰度发布** 对单机单实例是伪需求；真正需要的是"改前备份 + 快速回滚"，
而 `backups/` + `_archive/` 已覆盖这一点。

## 7. 方法论判例（本轮最重要的教训）

审计过程中我一度判定"全仓 30 个文件、60+ 处术语被批量损坏"，并写好替换脚本准备落盘。

**这个结论是错的。** 触发点是我写下的修复脚本里 `BAD` 与 `GOOD` 两个常量码点完全相同——
不可能成立，于是回查原始字节：

```
文件实际字节： 66 61 69 6c 2d 63 6c 6f 73 65 64   → f a i l - c l o s e d  （正确）
我拼接的正确串：66 61 69 6c 2d 63 6c 6f 73 65 64   （完全相同）
```

即：**文件内容一直是对的，是我的读取/显示通道把该英文词渲染成了乱码视图**。
仓库里并不存在这次"损坏"；若按原计划执行，会写 30 个文件、报告里留下一条假结论。

判例要点：
1. 涉及字符串的结论，**必须取原始字节（hex）复核**，不能凭打印结果；
2. 修复脚本必须带"坏串 ≠ 好串"的前置断言 —— 这次正是该断言救回来的；
3. 假阳性比漏报更贵：它会让人去改本来正确的东西。
