## 三、ROI 口径与「不造数」原则（硬约束）

### 3.1 算式

```
组合 ROI = 收益 − 算力成本
```

- 收益侧单位必须显式声明（`posterior.unit`），成本侧固定 `CNY`（-011 成本账为 LLM 成本金额，锚点人民币/百万 token）；
- 收益未显式喂入时，**收益合计缺省为「分支求和」**（`total_source="sum_of_branches"`），也可显式给 `total` 覆盖（`total_source="explicit"`）；
- 成本侧取**当月**累计（`cost.month` 归月口径与 -011 一致：ISO 时刻前 7 位）。

### 3.2 三态与「不造数」

| ROI 状态 | 触发 | `value` | 语义 |
|---|---|---|---|
| `computed` | 后验已喂入且单位可减 | 数值 | `收益 − 算力成本` |
| `pending_backfill` | 后验收益缺失（尚未接入结算后验） | **`null`** | **待回填**——**不以 0 充数** |
| `unit_mismatch` | 收益单位与成本单位不可直接相减（如 `pct` vs `CNY`） | **`null`** | **不出数**——收益照实留存于 `revenue.total`，但不相减 |

**为什么 0 充数是造数**：ROI=0 会被读成「投入产出刚好打平」，与「尚未回填后验」是两件完全不同的事；把它混同会让汇报器输出一个看起来干净、实则无中生有的数字——直接违反「投递成功≠开会」同源的诚实纪律（计划贯穿纪律 5：验收实证，不以看起来成功当成功）。本单对 `pending_backfill` 显式建模并向 009 汇报器暴露状态位。

### 3.3 其他不造数边界

| 情形 | 处理 |
|---|---|
| 组合未在 -003 注册表登记 | 显式抛 `ComboReviewError(combo_not_registered)`，不返回「空报表」 |
| 成本预算未登记（-003 早期条目无 `budget`） | `cost.budget / remaining / over_budget = null`，`status="budget_not_registered"`；**成本累计照实读账本**——不臆造预算值 |
| 成本账 / 回执账行损坏 | 显式抛 `ComboReviewError(ledger_corrupt / receipts_ledger_error)`，不静默跳过坏行（跳过会让成本被低估） |
| 快照库未注入 / 表不存在 | `snapshots.available=false` + `reason` 说明，**不填 0**（0 会被读成「无快照」，而真相是「未查」） |
| 收益分支值为 0 | 视为**有效数据**（0 是真实测得的 0，与「缺数据」不同），照实填 0 |
| 成本分配到分支 | **不做**——成本是组合维度（-011 登记口径 `combo_id`），摊到分支必是臆造；故只有组合级 ROI，无分支级 ROI |

## 四、横向对比格式（-009 司马懿汇报器消费口）

```python
compare_portfolios(combo_ids, registry_path=None, ledger=None, receipts=None,
                   reviews_by_combo=None, posterior_by_combo=None, month=None,
                   snapshot_db=None, sort_by="roi") -> dict
```

```json
{
  "compare_schema_version": 1,
  "generated_at": "2026-10-20T11:40:00",
  "sort_by": "roi",
  "count": 2,
  "rows": [
    { "rank": 1, "combo_id": "combo_review_a", "name": "...",
      "roi": { ...完整 roi 对象... },
      "roi_status": "computed", "roi_value": 25.0,
      "revenue": 30.0, "revenue_status": "available",
      "cost_accumulated": 5.0, "budget": 100.0, "remaining": 95.0,
      "over_budget": false, "cost_status": "ok",
      "rate_4_of_4": 1.0, "signals_total": 1 },
    { "rank": 2, "combo_id": "combo_review_b", "roi_status": "pending_backfill",
      "roi_value": null, ... }
  ]
}
```

排序口径（三选一）：

| `sort_by` | 排序规则 | 用途 |
|---|---|---|
| `roi`（默认） | ROI 降序；**`pending_backfill` 殿后**（不与已算出数者混排） | 「哪个组合性价比高」——本单主用途 |
| `cost` | 算力成本升序 | 成本视角（-011 X-5 纪律延伸） |
| `completeness` | 四类回执 4/4 达成率降序 → 成本升序 → ROI | 数据质量优先视角 |

**009 消费约定**：
1. 汇报器**必须读 `roi_status` 决定呈现**，不得直接把 `roi_value`（可能为 `null`）当数字用；
2. 横向排序表建议直接取 `rows` 的 `rank / combo_id / roi_value / roi_status / cost_accumulated / rate_4_of_4` 六列（`render_comparison_markdown` 已按此出表）；
3. `posterior_by_combo` 未给某组合时该组合 ROI 为 `pending_backfill`——**009 不得替它补 0**。

## 五、失败语义（closed on failure）

一切契约违例显式抛 `ComboReviewError`（带 `reason_code`），禁静默降级、禁返回空报表冒充成功：

| reason_code | 触发 |
|---|---|
| `combo_id_invalid` | combo_id 非空字符串校验失败 |
| `registry_invalid` | -003 注册表读取/校验失败（版本不符/JSON 非法等） |
| `combo_not_registered` | combo_id 未注册 |
| `ledger_corrupt` | -011 成本账行损坏（非 JSON / 非对象 / cost 非法） |
| `receipts_ledger_error` | -007 回执账读取失败（损坏或被改写） |
| `posterior_invalid` | 后验喂入非法（缺 unit / 无数据 / 类型错 / 非 dict） |
| `reviews_invalid` | -008 复盘输入结构非法（缺 signal_id / 缺 reviews / 分支条目非 dict） |
| `combo_ids_invalid` | 横向对比的组合列表为空或非列表 |
| `sort_by_invalid` | 排序口径非法 |

**不静默跳过某个组合**：横向对比中任一组合出错即整体抛错（不返回「部分结果 + 部分空位」——空位会被读成「该组合数据缺失」而非「该组合出错」）。
