### 2.2 影响面

| 项 | 评估 |
|---|---|
| 每跳新增开销 | 端口活着时两探针各约 10ms；三端口**全死**最坏 `3×(3s+15s)=54s`，远低于 `PT2M` 上限 |
| 首次执行副作用 | 会拉起 `publish_schedule_server.py --bg`（8095）。**不会补跑**：调度的命中判据是「`HH:MM` 精确匹配 + 当日去重」（`publish_schedule_server.py` 头部 §设计 第 3 条），错过的时间点不追。因此复活后第一个动作发生在下一个 **16:45** 或 **23:45** |
| 对 8097 | 无影响：`guard_push_admin()` 先探端口，活着直接 return；8097 另有独立任务（PT5M），本单是冗余加固 |
| 对 8099 | 无影响：`guard_km_hub()` 逻辑与顺序不变（放第二位） |
| 对 9899 | **本单不覆盖**（见 §2.4-C / §4） |
| 失败模式 | 若 `Set-ScheduledTask` 被拒，任务保持原状，脚本不会半改（单次原子写入 action） |

### 2.4 替代方案（含为何不选）

| 方案 | 结论 | 理由 |
|---|---|---|
| **A 新建独立任务「8095 看护」** | 不选 | `keepalive_9899.py` 头部判例：本机 schtasks 对新任务有黑名单拦截；且多一个任务多一处漂移 |
| **B 并入 8097 守护任务** | 不选 | 同样要改 action，还会让 8097 的守护依赖 8095 的故障状态，耦合方向错 |
| **C 连 `guard_cow()` 一起加** | 本单不选，另立 | `guard_cow` 宽限 60s + 其它三端口最坏 54s = **114s**，贴着 `PT2M` 上限。`ops/launch_push_admin.py` 有明确判例（K-PUSH-004）：任务到 2 分钟被强杀，Job 连坐杀掉刚 spawn 的子进程 → 最坏情况「8095 被拉起又被杀」。先稳三端口，再单独处理 cow |
| **D 只手动拉起 8095，不补看护** | 不选 | 端口会再次裸死（这正是 10-15 以来的形态） |
