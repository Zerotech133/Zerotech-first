# 军团 IDE 开源对标深研

- 日期：2026-10-30
- 对象：`agent_platform/legion_ide/`（8103）、`portal/ide.html`（8734 Chat）
- 方法：公开架构文档 + 本地代码审计 + 近期实测
- 结论：**军团 IDE 现在是“带工具的聊天窗”，不是“Agent IDE 运行时”。最大差距不在模型，而在会话状态、执行环境、上下文引擎和工具生态。**

## 1. 对标对象

| 项目 | 核心能力 | 来源 |
|---|---|---|
| OpenHands | Agent Runtime、事件流、沙箱执行、context condenser | [runtime 文档镜像](https://github.com/young010101/OpenHands/blob/main/docs/modules/usage/architecture/runtime.md) |
| Cline | Plan/Act、checkpoints、diff 审批、终端、MCP | [Cline](https://cline.bot/) |
| Continue | @File/@Code/@Git Diff/@Terminal/@Problems/@Repo Map、模型角色、MCP | [Context Providers](https://docs.continue.dev/customize/deep-dives/custom-providers) |
| Aider | AST repo map、按 token 预算选取关键符号、lint/test 循环、git 原生 | [Repository map](https://aider.chat/docs/repomap.html) |
| Theia AI | IDE 扩展框架、工具审批、可组合 AI 能力 | [Theia AI tools](https://eclipse-theia.github.io/theia/docs/next/variables/_theia_ai-copilot.node_copilot-sdk-language-model.approveTheiaTools.html) |
| SWE-agent | Agent-Computer Interface，面向软件工程的动作空间 | [SWE-agent](https://github.com/SWE-agent/SWE-agent) |

## 2. 我们与它们的真实差距

### P0-1：没有统一 Agent 运行时/事件流

现状：

- 8103 `/rw` 负责读写/执行；
- 8734 `/ide` 负责聊天，直连 8796；
- 会话只存在浏览器 localStorage；
- 没有 run_id、事件流、回放、取消后的状态收口。

OpenHands 的核心是 **event stream + runtime**：每个 tool call/observation 都是事件，状态可回放、可取消、可恢复。  
我们的聊天和写码是两条链，工具循环甚至在前端 `ide.html` 里。

影响：无法可靠审计“这次改了什么、为什么改、失败在哪一步”，也无法做真正的多轮任务。

### P0-2：执行仍在宿主机子进程

现状：`exec_runner.py` 用 `subprocess.run`，只有白名单/超时/环境净化。  
OpenHands/SWE-agent/Cline 都在往隔离 runtime 走。

影响：命令即使白名单，也拥有当前用户权限；错误命令可触达工作区外文件。  
这是“能否真实投入运行”的第一道门槛。

### P0-3：没有 checkpoint / 回滚

Cline 的 checkpoint 可以回到每次工具动作前；我们现在只有 `preview → confirm`，没有事后 undo。  
写文件确认后若发现方案错误，只能手工 git 恢复。

### P0-4：上下文引擎仍是“全文词法扫描”

现状：新增 `ide_context.py` 只做 6 个目录的词法扫描 + 字符预算；没有 AST、符号、引用图、embedding。

Aider 的 repo map 用 tree-sitter 提取 class/function，按引用图排序，默认 1k token 预算；Continue 提供 @Code/@Git Diff/@Terminal/@Problems/@Repo Map。  
我们只有 `@Agent`、`@File`（且仅 bundle 内 18 个文件），没有 `@Git Diff`、`@Terminal`、`@Problems`、`@Code`。

### P1-1：工具生态太窄

- MCP 目前实际只接了 Tushare 258 工具；
- 没有通用 MCP server 注册/权限/审批；
- 没有 terminal/problems/debugger 上下文；
- 工具 schema 是手写 JSON 协议，不是通用 function calling。

Continue/Cline 的 MCP 是可插拔工具生态，这是“能力上限”的差距。

### P1-2：没有 Plan/Act 分离与审批策略

Cline Plan/Act、Theia 工具审批都要求“先计划，再执行；危险动作逐条确认”。  
我们只有一个聊天循环；写/执行虽有锁和预览，但没有模式、审批队列和策略配置。

### P1-3：前端是单体 HTML，不是 IDE 壳

`portal/ide.html` 约 1,900 行内联 JS；没有文件树/编辑器/终端/problems 面板，分屏只是只读预览。  
Theia/VS Code 的扩展架构、CodeMirror/Monaco 编辑体验、LSP 诊断都缺失。

### P1-4：没有 Agent 评测

开源项目普遍有 SWE-bench/自建任务集；我们没有“改一个仓库 bug 的成功率/回滚率/工具错误率”指标。  
没有 eval，就无法判断优化是否真的有效。

### P2：工程化问题

- 8103/8734/8796 三入口，默认 `DEFAULT_PORTAL=8091` 仍是旧入口；
- 8103 `/` 直接返回 portal 页面，静态资源在 8103 不存在；
- Tauri 原生壳可编译但当前会话 WebView2 创建被拒；
- 审计日志无 hash 链，owner 由客户端自报。

## 3. 哪个开源方案更值得借鉴

### 方案 A：把 OpenHands Runtime 当执行引擎（推荐）

保留我们的：
- 组织/Agent/工单/密钥/模型池
- 门户与个人 OS 入口

接入 OpenHands 的：
- event stream
- runtime/sandbox
- tool/action schema
- context condenser

优点：不用重写 Agent 内核；缺点：部署更重，需要适配工单/worktree 语义。

### 方案 B：用 Cline 做 IDE 客户端

把 Cline 作为 VS Code/桌面扩展，接我们的网关/Key/工单。  
优点：最快获得成熟 IDE 体验；缺点：组织/军团特色会被削弱，需要写桥接插件。

### 方案 C：自研但只补关键内核

按优先顺序补：
1. 统一 session/event store（SQLite/JSONL）
2. 后端 Agent loop + tool registry
3. AST repo map + Continue 风格 context providers
4. checkpoint/undo
5. Job Object/低权限执行

优点：完全可控；缺点：工程量最大，最容易做成半成品。

**建议：A + C 的组合**——用 OpenHands runtime 思路重构内核，但保留军团自己的组织/工单/Key 层；不直接 fork 整套 Cline。

## 4. 可落地路线

### 第一阶段（1–2 周）

1. 统一事件模型：`run_id/session_id/tool_call/observation/checkpoint`
2. 后端 Agent loop：把前端工具循环搬回服务端
3. Context providers：`@git-diff`、`@terminal`、`@problems`、`@repo-map`
4. checkpoint/undo：写前快照 + 一键回滚
5. 评测集：10 个真实仓库任务，记录成功率/工具错误/回滚率

### 第二阶段

1. Job Object / 低权限执行
2. MCP 注册表 + 权限审批
3. Plan/Act 模式与审批队列
4. Cline/Continue 式 diff/terminal/problems UI

### 第三阶段

1. 原生 Tauri 壳 + capability 白名单
2. OpenHands runtime 适配层或独立 sandbox
3. 多 Agent 并发写同一工单的冲突检测

## 5. 一句话结论

我们不是缺一个“更会聊天的模型”，而是缺 **Agent 运行时**：状态、事件、沙箱、上下文、工具权限、回滚和评测。  
先把这 7 件事补齐，军团 IDE 才具备“真实投入运行”的资格；否则继续在前端堆聊天功能，只会越来越像演示。
