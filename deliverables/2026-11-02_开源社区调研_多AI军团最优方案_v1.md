# 开源社区调研：多 AI 军团 / Hermes 整合的最优方案 v1

- 日期：2026-11-02 17:45｜范围：多 Agent 编排、MCP 工具、A2A 互操作、统一 UI、可观测、模型网关
- 约束：单宿主（零界）、唯一入口 8734、唯一认证、已有 Hermes WebUI/扩展、69 席位、6 军团、13 个 MCP server、禁第二平台
- **结论：不换框架，采“Hermes 交互面 + MCP 工具标准 + A2A 军团互操作 + LiteLLM 内部网关 + OTel 观测”的最小新增组合；UI 继续以 Hermes/8734 为壳。**

## 一、社区结论摘要（带来源）

| 领域 | 社区事实 | 对我们的含义 |
|---|---|---|
| **MCP（工具层）** | MCP Registry 是官方公开 server 元数据仓，**preview**；**不支持私有 server**，私有需自建 registry/聚合器；server.json 标准化名称/安装/能力 | 我们 13 个 MCP server 全是私有 → 用 **私有 MCP registry + LiteLLM MCP Gateway**，不依赖公网 registry |
| **A2A（Agent 互操作）** | Agent2Agent 协议已捐给 Linux Foundation；核心是 Agent Card 发现 + task/message/artifact 生命周期，支持 JSON-RPC/gRPC/REST 绑定与 0.3/1.0 版本 | 军团边界用 **A2A Agent Card**，不再私定 HTTP 接口；外部 Agent 可不透明接入 |
| **AI Gateway** | LiteLLM 自托管提供统一 100+ 模型 OpenAI 兼容端点、虚拟 key/预算/花费、**MCP Gateway**（工具按 key/team 授权）、**Agent Gateway（A2A，LangGraph/Pydantic AI 等）** | 用一个内部网关把模型/MCP/A2A 收口，Hermes 与 agent_platform 都走它；不新增用户入口 |
| **观测** | Langfuse 可自托管，但依赖 Postgres/Redis/ClickHouse/S3，单机部署有运维成本；原生支持 OTel | 先 **OTel GenAI**（已有 ADR-005/014），Langfuse 作为可选增强，不首日上重栈 |
| **统一 UI** | Open WebUI/LibreChat 是成熟自托管 UI，但换 UI=迁移会话/扩展/登录；Hermes 已有 WebUI + legion-ide 扩展 + trusted-header | **不换 UI**；Hermes 作为指挥面，门户 8734 统一壳/导航，修 `/legion`、`/dw`、`/dataops` |
| **多 Agent 框架** | LangGraph/CrewAI/AutoGen/ADK 等各有定位；引入即新增运行时/依赖/学习成本 | 只借 **Graph/状态机/检查点模式**；确有 DAG 需求再引入 LangGraph 作为库，不引入平台 |

## 二、方案对比（按我们的约束打分）

| 方案 | 单宿主 | 不换 UI | 标准协议 | 军团互操作 | 运维负担 | 结论 |
|---|---|---|---|---|---|---|
| A. 现状（Hermes + 私接） | ✅ | ✅ | ❌ | 私定 | 低 | 不统一，淘汰 |
| **B. Hermes + MCP + A2A + LiteLLM + OTel** | ✅ | ✅ | ✅ | ✅ | 中低 | **推荐** |
| C. 换 Open WebUI/LibreChat + LangGraph | ✅ | ❌ | 部分 | 需重接 | 高 | 不推荐（迁移成本>收益） |
| D. Dify/Flowise/n8n 低代码平台 | ✅ | ❌ | 部分 | 弱 | 高（第二平台） | 不推荐 |
| E. LangGraph Platform/Temporal/K8s 全栈 | ❌（重） | ❌ | 部分 | 强 | 很高 | 不适用单机 |
| F. CrewAI/AutoGen 全量运行时 | ✅ | ✅ | ❌ | 私定 | 中 | 仅借模式，不引入运行时 |

## 三、推荐架构（最小新增）

```
8734 统一门户（唯一入口/认证/导航）
  └─ /hermes/  指挥面（Hermes WebUI + legion-ide 扩展）
  └─ /legion   军团作战大屏（纳入统一 nav / 嵌入）
内部（127.0.0.1，不对外）：
  LiteLLM Gateway :4000
    ├─ 模型：Ollama 本地 / GLM / GPT / DeepSeek（OpenAI 兼容）
    ├─ MCP Gateway：13 个 MCP server（按 key/team 授权）
    └─ Agent Gateway：6 军团 A2A Agent Card（LangGraph/Pydantic 可选）
  OTel Collector → dev_events/trace（可选 Langfuse）
```

映射到 ZBF：
- **K1 席位**：Hermes profile（命令/决策/审计席）+ adapter（执行席）；
- **K2/K3 任务/运行**：A2A task/artifact 生命周期；LiteLLM 日志/追踪；
- **K4 接口**：`interface/hermes-control`、`interface/a2a`、`interface/mcp`；
- **K5 数据/工具**：私有 MCP registry（13 server 名称/版本/权限）；
- **K6 呈现**：Hermes + 门户壳 + `/legion` 统一 nav；
- **K8 治理**：LiteLLM virtual key/预算/访问控制 + Q2/SLO。

## 四、不推荐/不做

1. 不引入第二 UI（Open WebUI/LibreChat）替代 Hermes；
2. 不引入 Dify/Flowise/n8n 作为核心平台（第二平台/第二调度）；
3. 不把 CrewAI/AutoGen 当运行时整体替换 agent_platform；
4. 不上 K8s/Temporal/LangGraph Platform（单机过度）；
5. 不依赖公网 MCP Registry 管理私有 server；
6. 不做第二入口/第二认证/第二调度。

## 六、需 A0/ARCH1 拍板

1. **采用推荐栈 B**（Hermes+MCP+A2A+LiteLLM+OTel），不换 UI；
2. **LiteLLM 内部网关**是否部署（只监听 127.0.0.1:4000，不新增人类入口；需 L2 审批/模型 key 迁移）；
3. **A2A 版本**：0.3 还是 1.0（LiteLLM 可 per-agent pin；建议新军团 1.0，兼容旧 0.3）；
4. **Langfuse**：先 OTel，P4 再评估自托管（ClickHouse/Redis 资源）；
5. **profile 扩容**：先 12 个命令/决策/审计席，其余 adapter（避免 69 席全建 profile）。

## 七、结论

开源社区最优解不是“再选一个多 Agent 框架”，而是**用标准协议把已有 Hermes/agent_platform 收口**：
- **MCP** 管工具（13 server 私有 registry）；
- **A2A** 管军团互操作（Agent Card + task）；
- **LiteLLM** 做内部模型/MCP/A2A 网关（key/预算/日志）；
- **OTel** 做观测（Langfuse 可选）；
- **Hermes/8734** 保持唯一 UI/入口。

这与 ZBF 的 K4/K5/K6/K8、单宿主/单入口/单认证完全一致，且新增组件最少、可逐阶段回退。
