## 0. 盘点结论（4 个只读 worker 已回传）

- 全仓**不存在"自我产出源代码"的代码生成器**。`知识图谱/_study` 下的 mybatis-generator 是第三方 Java 学习样本，已排除。
- 唯一语义上贴"代码生成"的在用组件是 `agent_platform/adapters/codex_bridge.py`：
  - 定位 = 外部 Codex 代码生成代理的**产物受理 / 静态校验(AST, M1) / 沙箱试跑(M3) / 注册落地(M2) 管线**；
  - 红线 R1–R5 把"Codex 零凭据 / 零执行权 / 只读 propose / 注册权在 AP 侧"固化在代码里；已有首个受理策略 `codex_sma20_rsi14` 落账；
  - **它不产生代码，只消费外部生成物**，门控已严谨、可改空间小。
- 其余所有带"生成器"字样的组件（`weekly_report`/`monthly_report`/`morning_brief`(K-ORG-056)/`retro_brief`/`report_builder`/`api_brief`/`api_daily_data`/`chanlun_daily_ledger`/`build_bt2_prototype`/`jev_oos_question_gen` 等）都是**内容/报告/数据/HTML 生成器**，与"生成源代码"无关。
- 关键发现：这些生成器的根因缺陷**高度同宗**，可归纳为 8 个横切"基因"（G1–G8），天然对齐"8 个基因修复"。三个盘点 worker（report / portal+quant+jev / morning）独立收敛到同一框架。

## 3. 下一步方案（参照既有研发纪律：严格工单制 + 晋级门控）

- **Phase 0 立项澄清**：本次收敛——锚定对象（A/B/C）+ 8 基因确认（G1–G8 或调整）。**老田拍板后方可进入 Phase 1。**
