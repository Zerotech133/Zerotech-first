# 情报体系 P1 · 待确认队列的生命周期（发现 → 统计 → 归档）

- 编制时间：2026-11-05 凌晨（承接 v1.7 提示词 v2 定档）
- 对应阶段：P1 收尾（人工复核闭环的执行层）
- 触发点：v1.5 交付的"提升配对自动落队列"，只做了写入，没有关闭
- 结论一句话：**队列过去只能进不能出，人裁决后行仍在、`status` 恒为 `pending`，任何积压统计都会报出一个只增不减的待办数**；本轮补上统计、阈值告警与归档，队列变得有界且幂等

---

## 1. 发现的三个后果

v1.5 建队列时，`record_override` 只写台账、从不回写队列。真实后果不是报错，而是**数字说谎**：

| # | 后果 | 现场表现 |
|---|---|---|
| 1 | `status` 永远是 `pending` | 人裁决过的配对在队列里与未裁决的完全一样，只能靠 CLI 现场 join 台账才看得出差别 |
| 2 | 积压数只增不减 | 任何程序化统计（告警、日报标注）都会把僵尸行算成待办，虚报的积压数演练一次就没人再信 |
| 3 | 被否决的配对再也回不来 | `append_pending` 的去重键取自"队列里所有行"，不区分是否已裁决。台账一旦丢失或换了路径，该对即便再次被提升也**不会入队**，人永久看不到 |

第 3 条最隐蔽：它不是"多了一条垃圾"，而是"少了一条真待办"。

## 2. 现场证据（真库，不是构造）

`data/story_borderline_pending.jsonl` 现有 2 条，均为 `status: pending`，台账为空：

| 配对 | cos | LLM 当时的理由 | 事实状态 |
|---|---|---|---|
| `verify-s11-01` / `verify-s11-02` | 0.7133 | `same_story`：同一件事的不同报道 | **判对了**（该合） |
| `verify-solo-07` / `verify-solo-08` | 0.6958 | `progress`：主体均为央行，从发布报告到开展具体操作… | **判错了**（v1 判据缺陷，v2 已能正确判 `unrelated`） |

第二条是 v1.6 那个误合并的原始样本，从 11-04 15:22 入队至今无人处理，也没有任何机制提醒它存在。**这就是"队列没有生命周期"的实际代价：一条已知错误的记录，在待办清单里静默躺了一夜。**

## 3. 补的四件东西

### 3.1 `queue_stats()` —— 用台账切分"真待办"

返回 `QueueStats(total, pending, decided, oldest_days, unknown_age)`。

关键在**用台账切分**而不是数行数：`total` 是文件里有多少行，`pending` 才是还有多少条等人看。只报 total 的统计必然只增不减。

配套的边界处理，每一条都对应一种真实脏数据：

| 情况 | 处理 | 不这么做的后果 |
|---|---|---|
| 重复行（v1.5 之前不去重） | 按配对去重后计数 | 积压虚高，告警提前触发、随后失效 |
| 缺 `queued_at` | 计入 `pending`，另记 `unknown_age` | 静默按 0 天算，"压了三个月"显示成"刚入队" |
| 时间戳在未来（时钟回拨） | 同样记入 `unknown_age` | 负数天数被丢掉，异常无人知 |
| 无时区时间戳 | `parse_queue_ts` 返回 `None` | **不猜本地时区**：猜了，UTC+8 机器算出的天数会少 8 小时，14 天阈值永远差一点才触发——"阈值永不触发"最难查 |

### 3.2 `backlog_alert()` —— 两个维度分开判

- **量**（`STORY_REVIEW_BACKLOG_MAX`，默认 20 条）：人跟不上机器的产出速度；
- **滞留**（`STORY_REVIEW_MAX_AGE_DAYS`，默认 14 天）：人根本没在看。

只设量阈值挡不住"每天来一对、三个月没处理"；只设时长阈值挡不住"一天来五十对"。两条同时越界时**必须都报**，只说一个会让人修完一个就以为好了。

`0` = 关闭该维度。若把 0 当成"阈值为 0，永远超限"，这个开关就关不掉，反而变成刷屏源。

### 3.3 `prune_decided()` + `compact` —— 归档而不是删除

已裁决的行搬进 `<队列>.decided.jsonl`。**不删**，因为台账只存一个布尔，LLM 当时为什么那么判只留在队列行里——事后复盘"机器为什么错"要靠它。

- 幂等：第二次跑归档 0 条；
- 写回用临时文件 + 替换，避免裁剪中被打断留下半截队列；
- **写回必须带结尾换行**：漏了的话下一轮 `append_pending` 会把新行粘到最后一行尾部，两行并成一行非法 JSON，整条记录静默消失。这类 bug 只表现为"新配对怎么也不进队列"，查起来极慢（已由用例钉住）。

### 3.4 `append_pending(overrides=...)` —— 已裁决的不再入队

台账里已有的配对跳过。这不等于"机器否决会被人的裁决继承"：台账命中时聚类根本走不到提升分支；能走到这里的只可能是台账文件丢了或换了路径，那时 `overrides` 里也没有该对，它照样重新入队（有专门用例守住这一条）。

## 4. 接入聚类 CLI

`story_group_run.py` 每轮末尾输出：

```json
"review_backlog": {"total": 2, "pending": 2, "decided": 0,
                   "oldest_days": 0.18, "unknown_age": 0, "alert": null}
```

越界时 stderr 打 WARN，并直接给出处理命令：

```
[WARN] 待确认队列积压：待确认 2 条 ≥ 上限 2；最老一条已压 0.2 天 ≥ 上限 0.1 天
       处理：python scripts/borderline_review.py list --pending-only
```

用 WARN 不用 INFO：积压从来不靠人主动查日志发现。**但不退出非零**——聚类本身是成功的，卡住的是复核，两件事不该混在一个退出码里。

## 6. 一个 Windows 真机故障（本轮意外收获）

第一次跑 `compact` 报错：

```
PermissionError: [WinError 5] 拒绝访问:
  '..._demo_queue.jsonl.tmp' -> '..._demo_queue.jsonl'
```

原样重跑即成功，隔离复现也成功——判定为**瞬时文件锁**（目标文件刚被 `cp` 创建、或正被实时防护扫描时，Windows 的 `os.replace` 会返回拒绝访问）。

处理：`_atomic_write` 加**有界重试**（5 次，退避 50ms 起）。要点是**不吞错**：

- 重试耗尽仍抛 `PermissionError`，并 `logger.error` 记录、保留 `.tmp`（里面是这次要写的内容，删了连取证都没了）；
- 有专门用例验证"瞬时错 2 次后成功"与"永久错仍然抛"。

**必须说清的限度**：由于重试覆盖了不可重现的竞态，我无法证明这一定就是全部原因。它的价值是把"偶发失败一次"变成"可恢复"，而不是"修好了"。

## 8. 必须承认的限度

**这套机制只让积压被看见，不能让已生效的合并自动回滚。**

LLM 提升的合并在落库那一刻就已经进了事件表、进了独立来源数。人工复核是事后追认，不是事前闸门。所以：

- 如果没人看队列，机制只会持续告警，不会阻止错数据进日报；
- 想真正做到"未确认的合并不生效"，需要消费侧（日报/热度计算）按 `decided_by` 过滤或打标——那是 P2 的事，本轮不做。

同理，`decided` 分类依赖台账文件本身可信；台账损坏时 `load_overrides` 会抛错并中止（既有的严格策略），不会静默把已裁决的当成未裁决。
