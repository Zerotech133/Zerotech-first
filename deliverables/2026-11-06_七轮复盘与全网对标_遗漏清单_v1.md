# 七轮复盘与全网对标：遗漏清单

**日期**：2026-11-06 08:40
**方法**：复盘前七轮全部结论 + 四个方向的公开检索（Level-2 通道 / 因子自动化 / 图谱推理 / 席位网络与存储选型）+ 本机与数据仓复测
**诚实边界**：这不是"全网穷举"。我做了 4 组检索、验证了 3 个具体项目（IG50、niulai、KAG）的可达性与实质内容。未验证的不写成结论。

## 0. 一句话总纲

前七轮我们把**问题诊断清楚了**（数据三态、五维倒挂、行为指纹边界、治理不停工），但**漏掉的不是分析，是三件工程事实**：

1. **通道一直没接**：券商免费给的 QMT/Level-2，比我们打算花钱买的那条路更近；
2. **别人已经做过一遍**：席位共现网络、游资标签库，有现成开源实现，我们手搓的方案与它撞车；
3. **存储是自找的病**：21 万个按"股票×月"切的小 parquet，是本项目自己造出来的碎片，不是数据量的问题。

## 2. 遗漏一（最贵）：QMT 通道一直没接

### 2.1 事实

项目现在走的是**通达信协议**（远端 `backend=tdxpy`，连 `117.34.114.17:7709`）。这条路能给 3 秒快照分笔，但**协议层只有五档**，永远拿不到委托队列。

而 `xtquant`（迅投 QMT/miniQMT SDK）是**另一条路**：

| 能力 | 通达信（现用） | QMT/miniQMT |
|---|---|---|
| 五档盘口 | ✅ | ✅ `get_full_tick` |
| 全市场 tick | 3 秒快照 | ✅ 订阅推送，毫秒级 |
| **十档盘口** | ❌ | ✅ `l2quoteaux` |
| **逐笔委托** | ❌ | ✅ L2 权限 |
| **撤单明细** | ❌ | ✅ `withdrawBidQuantity` / `withdrawOffQuantity` |
| 历史 tick | ✅ 回溯 9 年 | ✅ `download_history_data` |
| 门槛 | 0 | **券商开通 QMT，通常 50~100 万资产** |

**关键**：`l2quoteaux` 里有 **`withdrawBidQuantity`（买入撤单总量）**。上一轮我们卡在"判断不了主力是真买还是挂假单"，这个字段直接回答。**这是 3~8 万/年买不到的东西，券商可能是免费给的。**

### 2.2 为什么这是最大的遗漏

因为我上一轮的建议是「Level-2 报价 3~8 万/年，建议先不买」——**我把唯一没试过的通道，当成了最贵的通道**。正确顺序应该是：先问券商有没有 QMT 权限（0 成本），没有再谈采购。

### 2.3 待办

- 本机 `xtquant` 未安装（已确认），需先在券商侧确认 QMT 权限
- 若已开通：装 `xtquant` → `xtdata.subscribe_quote(period='l2quoteaux')` → 直接补上委托队列与撤单
- 若未开通：这笔钱才轮得到第三方报价

## 3. 遗漏二：席位网络与游资标签库，别人已经做过

### 3.1 撞车的方案

第七轮我们手搓了「BehaviorProfile + 四游资画像 + JS 散度」，思路是对的。但检索到两个已实现同类逻辑的项目：

**（1）席位共现网络识别"资金集团"**（腾讯云社区公开的实践，配套 IG50 数据）
- 构图：同一股票同一交易日**买入席位两两连边**，边权=共现次数
- 关键工程细节：**边权时间衰减**——90 日窗口内，近 30 日边权 ×2，否则会把早已解散的旧组合误报为活跃集团
- 分工：构图 Agent（确定性计算）/ 分析 Agent（社区发现、中心性）/ 解读 Agent（LLM）
- 他们踩过的坑：**解读 Agent 最容易"过度拟人化"**，把统计上随机的高共现描述成"默契配合"；解法是提示词强制区分事实与推测 + 每个数字必须能在输入里找到

**这条直接可用于我们的图**：我们有 `HotMoney`、`Seat`、`TradeAction`，缺的只是"同日同股共现"这条边的定义和衰减系数。

**（2）`niulai`（GitHub 开源）**
- 内置**殿堂级/顶级游资席位标签库**（章盟主、赵老哥、孙哥等），自动标注买卖席位动向
- 纯本地 SQLite、单端口 Docker、数据来自东财/腾讯免费接口
- 对上一轮"43 个游资名 vs HotMoney 只建 21 个、漏 22 个"——这个库可直接对照补齐

### 3.2 附带修正：上一轮"字段漂移"可能判错

Tushare `hm_list` 的 `orgs` 字段是**逗号分隔的多席位字符串**，一个游资天然对应十几个营业部（原文示例：`华泰…南京六合雄州西路营业部` + `华鑫…泉州宝洲路营业部,华鑫…江苏分公司,…`）。

所以上一轮"章建平 n_seats=8 实为 10"更可能是**本来就是一対多，8 与 10 是两个时点的配置差异**，不是字段 bug。建议按「营业部全名 → 游资列表（多对多）」建模，不要一对一赋值。

> 这一条我不确定，标为待复核。若确认，则 P0 那项"补 22 个游资"的性质从"补漏"变成"同步多对多关系"。

## 4. 遗漏三：存储是自找的病

### 4.1 实测证据

| 操作 | 耗时 | 说明 |
|---|---|---|
| Python 逐文件读 5,036 个 parquet metadata | **超时 >280s** | Windows 文件 IO 撑不住小文件海量 |
| DuckDB 扫 33,998 文件元数据 | **24.5s** | 可接受但偏慢 |
| DuckDB 单月全量聚合 | 2.7s | 正常 |
| DuckDB 查单日 tick（1,521 万行） | **0.00s** | 大文件反而秒开 |

**同时修正一个数字**：本地 `stk_mins` 实际是 **33,998 文件 / 1.496 亿行 / 3.48GB**，不是我上一轮估算的 7,500 万行。平均每文件 4,400 行。

### 4.2 病根

按「股票 × 月」切片（`000001_SZ_202509.parquet`）是**反模式**：
- 3.4 万个文件 → 任何跨股票查询都要开 3.4 万次文件句柄
- Windows NTFS 对小文件海量目录尤其差（同样的事在 Linux 上会好很多，但也不该这么做）
- 单个文件 100KB，远低于 parquet 的合理 block 大小（建议 128MB+），压缩率和扫描效率都浪费

### 4.3 正确姿势（有明确共识）

| 数据量 | 方案 | 适用 |
|---|---|---|
| < 数百 GB，单人研究 | **Parquet 按日期分区 + DuckDB** | 我们现在的体量（39GB） |
| TB 级，多人并发 | ClickHouse（**按月分区，千万别按天**） | 未来 |
| 需要版本化 DataFrame | ArcticDB（S3 上版本链） | 不必要 |

业界经验值：A 股 5,000 只 × 240 分钟 × 250 天 = **每年 3 亿行**；同规模下 MySQL 跑 40 秒的聚合，ClickHouse 50 毫秒、10:1 压缩。

**结论：我们现在不该上 ClickHouse**（39GB 用不着），但**该把切片维度从"股票×月"改成"日期分区 + 按股票排序"**。这一步能让 tick 采集的文件数从"每天 1 个 80MB"保持住，而分钟线要重新组织。

### 4.4 一个反直觉的点

ClickHouse 实践里最狠的一条：**「原始价格与复权因子完全分离存储，通过视图动态计算」**——避免每次分红除权重刷几十亿行。
我们现在 `stk_mins` 存的是原始价，`adj_factor` 独立表，这条**已经做对了**，不用改。

## 5. 遗漏四：因子自动化，微软已经把路走完了

### 5.1 RD-Agent（Qlib 生态）

| 项 | 事实 |
|---|---|
| 归属 | 微软亚洲研究院，Qlib 深度集成，NeurIPS 2025 收录 |
| 四场景 | `fin_factor`（挖因子）/ `fin_model`（挖模型）/ `fin_quant`（联合）/ `fin_factor_report`（**读研报抽因子**） |
| 循环 | 假设生成 → 任务分解 → CoSTEER 写代码 → 回测 → 反馈 |
| 实测（国联民生） | 36 个 Loop，双周频 IC → 0.07，11 次 SOTA 更新，**预估月产 900 个有效因子** |
| 成本 | 约 10 美元/轮 |
| 环境 | **必须 Linux/WSL2**（Qlib 二进制格式依赖 mmap，Docker 沙箱依赖 Linux 命名空间） |

**对我们最有用的是 CoSTEER 的工程范式**，不是因子本身：
- 每个因子独立 Conda 环境跑（故障隔离）
- 维护**两个向量知识库**：成功案例库 + 失败→修复对库，生成时检索最相似案例注入 Prompt
- 最多 10 轮「写代码—测试—读报错—修正」

这正好回答您反复提的痛点「多 Agent/多模型导致项目极复杂」：**不是靠加 Agent 解决，是靠"确定性执行 + 双库记忆"把 Agent 数量压下来**。

### 5.2 一个必须听的负面结论

国联民生实测明确指出 RD-Agent 的四个短板，其中两条直击我们：
- **「对 A 股特殊机制与前视偏差把握不足」**——我们刚发现的 `is_oos` 分段、`split_date` 三批次不可比、`pit_verified=False`，正是这类问题；
- **「组合 ICIR 的提升始终弱于 IC，机器学习类因子在激进参数下过拟合明显」**——与第五轮"271 因子衰减 33 个"互相印证。

**所以正确用法是"新数据源因子的快速探索"，不是"替代现有因子研究流程"。**

### 5.3 其他开源（按可用性排序）

| 项目 | 实质 | 判断 |
|---|---|---|
| `microsoft/qlib` | 13,000+ star，因子分析+回测+模型全链路 | 值得接，但数据要转它的二进制格式（工作量最大的一步） |
| `AlphaGPT`（多个 fork） | 符号回归挖因子，Transformer 生成公式，AkShare 取数 | 实现简单可直接读，但**作者背景有纠纷、代码可信度需自审** |
| `AlphaGPT_Tushare` | DeepSeek 生成因子表达式 + 回测 + IC | 轻量，适合做 baseline |
| `A-share-replay`（复盘啦） | 龙虎榜采集/席位协同/抱团挖掘/次日溢价统计 | TODO 居多，但清单可当需求文档用 |

## 6. 遗漏五：图谱只用来"查"，没用来"推"

### 6.1 现状

我们的图（227 万节点）目前是**查询型**：Cypher 查路径、查邻居、算度。第五轮已证明"因子做节点会让 BFS 退化"，判断正确。

但缺一层：**从"查到的事实"推到"未见的结论"**。

### 6.2 KAG（蚂蚁，9,148 star，Apache-2.0）

| 能力 | 说明 |
|---|---|
| 逻辑形式引导推理 | 自然语言 → 逻辑形式 → 编排 4 类算子（检索 / 图推理 / 语言推理 / 数值计算） |
| 多跳 | 支持最长 6 跳推理链路，公开称比 GraphRAG 深 3 倍 |
| 关键优势 | **对数值比较、时间关系、专家规则敏感** —— 正是"资金迁移""传导时滞"需要的 |
| 实测 | HotpotQA F1 +19.6%，2Wiki +33.5%；政务问答 91% |
| 代价 | **Docker + OpenSPG 引擎，部署重**；`kag-model` 未开源；文档偏薄 |

### 6.3 但先别上

我们图的真问题是**断桥和脏数据**（`Person` 归并率 0.0%、`Seat` 重名 10.5%、实控人全无），**不是推理能力不足**。

在图上加推理引擎，等于给一个数据有洞的库装高级查询——**先把 P0 数据修完，KAG 才有意义**。

### 6.4 顺带：实控人缺口的一点线索

OpenKG 有两个可直接拿来对照的数据集：
- **企业投融资事件知识图谱**：3,582 家，含法人、注册资金、成立时间、行业、融资事件（投资人/轮次/金额/时间）
- **企业知识图谱**：69,979 个关系，含**实益（beneficial ownership）、所有权、上市、专利**等

规模远小于天眼查（6,265 家），但**"实益/所有权"这两个关系名，正好是我们缺的 `control_path` 的字段定义参考**。可用来对齐 schema，不宜当主数据源。

## 7. 我认为最深的一条遗漏（不是工具）

### 7.1 上一轮已经算出"不可知"，但没把它变成止损线

第七轮的结论是硬的：

- 龙虎榜可见性门槛：**中位 794 万**
- 陈小群单笔中位 3,460 万 = 4.4 倍门槛
- 他只有 2 个真实营业部，龙虎榜按营业部合并披露 → **能藏上限 ≈ 1,588 万**
- 特征重要性 `p_elg_net` 仅 0.0020 → **归因不可做**

**这意味着：任何"这 5 亿是谁的"的问题，在 1,588 万以下的部分，答案永远是"不可知"。**

而我给的建议仍然是「BehaviorProfile 加 `discriminative_power` 字段」——这是**把不可知写成 schema**，工程上正确。

但漏了一步：**没给这个"不可知"设预算上限和时间止损**。科研式追问"再挖挖看"是最贵的开销，而这个方向上，投入再多也突破不了 794 万的物理门槛。

**建议明确写进系统约束**：
> 单笔资金归因，金额 < 1,588 万 → 直接返回 `UNDECIDABLE`，不消耗算力、不生成假设、不进人工复核队列。

这一条比任何工具都省钱。

## 9. 我不想含糊的三点

1. **我没有查遍全网**。四组检索、三个项目深看。搜索引擎给出的排名不等于覆盖度。
2. **QMT 那条路我没验证成功**——本机没装 `xtquant`，也没有券商账户信息，只能确认"这条路存在且更便宜"。**需要您去确认权限**，这是本轮唯一一个"我不做就无法结论"的项。
