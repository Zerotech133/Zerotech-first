## 〇、一页结论

**一句话：零界不缺产能，缺"进门"和"仲裁"。制度已经过剩，执行体为零。**

| 判断 | 证据 |
|---|---|
| 产能过剩 | 30 天 8,431 commits（日均 281，峰值 1,382/天）；6 个以上 Agent 身份同时写 |
| 进门堵塞 | 99 个本地分支，**94 个未合入**，但 ahead 中位数只有 **1.5 个提交** → 一堆"已经做完、只差进门"的成品 |
| 仲裁缺失 | 11-05 21:40 窗口实录：两个会话抢同一 worktree 跑双 fast 门，靠人工按 pid 杀进程收场；另一会话的 8 个 staged 文件被误提交进别人的 commit |
| 治理空转 | ADGS 目标 doing ≤5～8，实测 **doing 21 + review 13 = 34 在途**；worktree 42（目标 ≤15～20） |
| 组合未成立 | `compositions/registry.json` 7 个组合，**7 个 phase=shadow、validated 全 false** |
| 图谱断链 | 2,274,046 节点 / 6,740,935 边，但两张图之间知识型边仅占 **0.2%**；原子库 64,079 条只入图 **8.1%** |

**三条主线（本次一次性成型）：**

1. **并发仲裁层（Arbiter）** —— 把 `write_scope` 从"申报字段"变成"租约锁"，把 merge train 从"窗口约定"变成"队列服务"，把 Agent 身份从"git author"变成"席位令牌"。**没有令牌，开不了 worktree。**
2. **治理图谱（GovGraph）** —— WorkItem / Seat / Capability / GateDecision / Evidence 五类对象进同一张 Neo4j（与知识图谱共底座）。冲突、重复、孤儿用 Cypher 查，不用人读 4,464 行 STATUS.md。
3. **三道闸（原子→入图→传导）** —— 64,079 条原子按统一 ID 入图；S6 按原子类型分档审批；Semantica 接时点重建与因果路径。

**节奏：** S0 止血（11-06～11-08）→ S1 仲裁（11-09～11-13）→ S2 治理图谱（11-14～11-20）→ S3 三闸（11-21～11-27）→ S4 固化（11-28～12-02，与 L1 硬截止对齐）。

**并行度结论：** 可以 8 条车道同时开工，但**合入吞吐上限 = 12 单/日**（两个窗口 × 6）。所以并行度公式是 `min(车道数 8, 日合入吞吐 12 ÷ 平均在途 2 天) = 6`。**并行的是"产出"，串行的是"进门"。** 这就是为什么过去会崩：把并行也做在了进门上。

## 四、根因 · 三句话

1. **把"并行"做在了错误的层**。并行应该发生在**产出侧（域分片）**，串行必须发生在**合入侧（队列）**。现在反了：产出侧串行（一个 Agent 一个 worktree 排队），合入侧并行（两个会话抢同一个 merge）。
2. **用文档治理 Agent，等于用告示牌管交通**。Agent 不读 4,464 行 STATUS.md，Agent 只响应**它能调用的接口返回什么错误码**。
3. **契约缺失时，Agent 会自己造一个**。造完就长成一条分支。13 个 K-STOCK-ANALYSIS 分支不是"分支管理问题"，是"没有 schema 的必然结果"。

## 五、方向 · 底座定型（一次定型，不再分支）

### 5.1 一句话

**零界 = 一个图（Neo4j）+ 一套原子（六类）+ 三道闸（入图/审批/传导）+ 一个宿主（8734）+ 一层仲裁（Arbiter）。**

在 ZBF v1 的"一套宿主 + 一层内核 + 一个组合模型 + 一条黄金路径 + 一道门禁"之上，**只加一样东西：一个运行时仲裁与治理服务（GovKernel）**。其余全部复用，不另立第二套。

### 5.2 三层底座

| 层 | 名字 | 内容 | 状态 |
|---|---|---|---|
| **L3 治理层** | GovKernel | 席位令牌 / 写域租约 / 三队列 / 门禁执行 / 证据校验 / 治理图谱 | **新建（本次核心）** |
| **L2 决策层** | Capability + Gate | 能力卡（`requires_approval`/`allowed_callers`/`runs_on`）+ 封层 `quarantined` + 选择题式提醒 | 半有（`agent_platform/contracts/` 九契约可复用） |
| **L1 对象层** | Things + Assertions | `things` 单表（JSONB，kind/domain 做成数据行）+ 断言四层聚合（断言→事实簇→实体→事件）+ 证据三级（Admiralty A–F×1–6、decay_half_life_days、falsifiers） | 图谱已有 227 万节点，缺统一 ID 与断言层 |

### 5.3 为什么治理层要放最上面（而不是最后做）

因为**没有仲裁层，下面两层永远长不齐**：契约会被绕过、原子会重复灌、图谱会被各 Agent 各灌一套 ID（8.1% 入图率就是这么来的）。**必须先有闸，再谈灌水。**

## 六、治理一次性成型 · GovKernel v1

### 6.1 设计原则（三条，不可协商）

1. **治理必须是服务，不是文档。** 每个规则都要有一个可调用接口，返回 200 或 4xx。
2. **所有拦截必须在"动作之前"。** 事后审计只能记过，不能止损。
3. **单一真源可枚举。** 席位、写域、组合、契约、队列各只有一张表，全部可从图里查。

### 6.2 六个服务（这就是"执行体"）

| # | 服务 | 端口 | 职责 | 拦截点 | 替代了什么 |
|---|---|---|---|---|---|
| **G1** | `arbiter` 仲裁 | **8801** | 席位令牌签发/吊销；写域租约（`acquire/renew/release`）；冲突检测 | 开 worktree 前、首次写文件前 | 人工按 pid 杀进程 |
| **G2** | `queue` 队列 | **8802** | ready→review→merge 三队列；merge train 排队；WIP 配额计数 | 建单、提 review、请求合入 | 两个窗口手动点名 |
| **G3** | `ledger` 账本 | **8803** | 任务/组合/证据三账合一；写入即校验 schema | 状态流转 | tasks.json + registry.json + STATUS.md 三处 |
| **G4** | `gate` 门禁 | **8804** | G0–G4 矩阵的可调用化；`kernel_guard` 从 draft 升 frozen | merge 前 | `devtask merge` 内嵌九门（保留，改为调 G4） |
| **G5** | `evidence` 证据 | **8805** | 证据包九字段校验；SHA256；`rc=0` 但空产物判负 | 提交回执 | 815 份自由格式 md |
| **G6** | `board` 看板 | **8806** | 只读投影：谁在改什么、队列多长、WIP 多少、阻塞在哪 | 读 | STATUS.md 4,464 行 |

> 六个服务同一进程组（`govkernel/serve.py`），共享一个 PG schema + 一张 Neo4j 图。**不引入 MQ、不引入微服务、不引入新 DB**（遵守 ROADMAP v4 §二"四不做"）。

### 6.3 治理图谱：五类对象进图

沿用已有 Neo4j（7474/7687），新增标签，与知识图谱**同库不同域**（用 `:Gov` 前缀避免污染）：

```cypher
// 席位（Agent 身份）
(:GovSeat {seat_id, name, kind:'human|agent', model, ide, authority:'A0|ARCH1|owner|exec', token_hash, active})

// 工作项
(:GovWorkItem {tid, type, lane, status, wip_slot, created_at, due_at, quality:'Q1..Q4'})

// 写域（关键：冲突检测的锚）
(:GovWriteScope {path_glob, exclusive:true})

// 门禁判定（每次门禁一条，不可改）
(:GovGateDecision {gate, rc, duration_s, at, commit, evidence_sha})

// 证据包
(:GovEvidence {sha256, kind, path, at, verified:true})
```

**四条强制边**（这是"能看到冲突"的关键）：

```
(GovSeat)-[:OWNS]->(GovWorkItem)
(GovWorkItem)-[:WRITES]->(GovWriteScope)
(GovWorkItem)-[:PASSED]->(GovGateDecision)
(GovGateDecision)-[:PROVEN_BY]->(GovEvidence)
```

**一条冲突检测查询（替代 4,464 行 STATUS.md）**：

```cypher
// 谁和我在抢同一个写域，且都在 doing/review
MATCH (a:GovWorkItem)-[:WRITES]->(s:GovWriteScope)<-[:WRITES]-(b:GovWorkItem)
WHERE a.tid < b.tid AND a.status IN ['doing','review'] AND b.status IN ['doing','review']
RETURN a.tid, b.tid, s.path_glob
```

**一条孤儿查询**（找出"声明了但没人接"）：

```cypher
MATCH (w:GovWorkItem) WHERE NOT (w)-[:WRITES]->() RETURN w.tid, w.title
```

### 6.4 一页纸铁律（贴墙版，任何 Agent 接入必须遵守）

| # | 铁律 | 违反后果 |
|---|---|---|
| **R1** | **无令牌不建单**：席位令牌由 G1 签发，含 `seat_id + 权限级 + 有效期`；git author 必须等于 `seat_id` | 建单接口 403 |
| **R2** | **无租约不写盘**：`write_scope` 必填，写入前 `acquire`，同 glob 互斥；租约 90 分钟，可 `renew` 一次 | pre-commit hook 拒提交 |
| **R3** | **WIP 满则拒**：`doing + review ≥ 上限` 时，新单只能进 `parked`，不能进 `doing` | G2 返回 429 |
| **R4** | **合并只走队列**：任何分支合入 master 必须先 `enqueue`，窗口按 FIFO，每班 ≤6；`--force` 需 A0 令牌 | G4 拒 merge |
| **R5** | **证据不齐不算完成**：九字段 + SHA256 + `rc` 与产物非空校验；`rc=0` 而产物为空判负 | 状态无法流转到 done |
| **R6** | **内核冻结后改契约必须带 ADR**：`kernel_v1.yaml` 升 `frozen`，`kernel_guard` 从软提示变硬阻断 | G4 拒 merge |

> R1–R6 全部已存在于 ADGS 文档中，本次只是**把它们变成返回码**。这就是"一次性成型"——不是新写制度，是给旧制度装上牙齿。

### 6.5 多 Agent 协作协议（外部 IDE 接入标准）

**适用**：Claude Code / DeepSeek Harness / Trae / Cursor / CowAgent / Hermes / 科大巴比类内部席位，以及未来任何模型。

**接入四步（10 分钟）**：

1. **申领席位令牌**：`POST /gov/seat/issue {name, kind, model, ide, authority}` → 返回 `token`（`token_hash` 入图，明文不落盘）。
2. **声明本次写域**：`POST /gov/workitem {tid, type, lane, write_scope, acceptance, rollback}` → 返回 `wip_slot`。
3. **取租约**：`POST /gov/lease/acquire {tid, path_glob}` → 409 表示被别人占，**不许硬闯**，去队列里看是谁，或换写域。
4. **提交走队列**：`POST /gov/queue/enqueue {tid, branch, tip}` → 拿排队号；合入由 G2 调度，**Agent 不得自行 merge**.

**三条"不许"**：

- **不许** 在未声明写域的路径下写文件（含"顺手改一下"）。
- **不许** 复用别人的 worktree（11-05 事故根因）。
- **不许** 用 `git commit --amend` 修改已入队的提交（入队即冻结 tip，tip 变更自动 abort，已有先例）。

**跨模型协作的额外一条**：不同模型（Claude/DeepSeek/Qwen）对同一文件**不可并行写**，只能"一写一读"。因为不同模型的代码风格与错误模式不同，交叉改写会产生不可归因的缺陷。**同一个文件在一个 Sprint 内只有一个作者模型。**

## 七、敏捷多线程 · 域分片并行模型

### 7.1 为什么不是"多开 worktree"

过去的并行模型是：`一个任务 = 一个 worktree = 一个分支 = 一次 merge`。
问题：**worktree 数 = 在途任务数**，所以在途 34 就要 42 个 worktree，每个 worktree 都跑一遍门（fast 门 400–560 秒），机器和人同时被拖死。

新模型：**并行按"域"分片，不按"任务"分片。**

```
8 个域（lane）= 8 个长期存在的写域
每个域内：串行（一次一个任务，做完合完再下一个）
域之间：完全并行（互不碰同一批文件）
```

**收益**：worktree 从 42 降到 ~10（每域 1 个 + 主区），fast 门从"每任务一次"变成"每域一次"，**机器负载降 4 倍，合入队列变短**。

### 7.2 八条车道（Lane）

| Lane | 名称 | 写域（glob） | 主责席位 | 交付物 | 门禁 |
|---|---|---|---|---|---|
| **L0** | 治理内核 | `govkernel/**`, `platform/kernel_v1.yaml`, `docs/adr/**` | ARCH1 | 六服务 + 契约 | 治理道（ADR + A0） |
| **L1** | 对象与图谱 | `quant_backtest/kg_*.py`, `知识库/95_KG/**`, `zerobound-kg/**` | INTEL0 | 原子入图 + 断言层 | 治理道 |
| **L2** | 情报流水线 | `intel_collector/**`, `news_collector/**`, `osint_video/**` | INTEL0 + DATA1 | 源→证据→研判 | 标准道 |
| **L3** | 量化与决策 | `quant_backtest/**`（除 kg_）, `analysis/**` | QUANT1 | 策略/回测/信号 | 标准道 |
| **L4** | 门户与呈现 | `portal/**`（除 static 生成物）, `compositions/*-page` | UI1 | 页面包/看板 | 快车道 |
| **L5** | 军团与席位 | `agent_platform/**`（除 contracts） | DEV1 | 席位/工具矩阵 | 标准道 |
| **L6** | 内容与商业 | `video/**`, `commercial/**`, `gzh/**` | CONTENT1 | 内容线/商业线 | 快车道 |
| **L7** | 运维与数据 | `ops/**`, `tools/**`, `deploy/**`, `data_sources/**` | OPS1 | 备份/监控/数据仓 | L2 道 |

**车道规则**：

1. **一个文件只属于一条车道**（glob 冲突即设计错误，启动时校验）。
2. **车道 owner 唯一**（人类或 Agent 席位，不可双签）。
3. **跨道改动必须拆单**：一次改动碰两条道 = 拆成两单 + 依赖声明。
4. **L0 优先**：L0 未完成前，其他道只能做"不触契约"的改动。

### 7.3 三个队列 + 令牌制

```
        ┌─────────┐   ┌──────────┐   ┌─────────┐
入口 ──▶│ ready   │──▶│ review   │──▶│ merge   │──▶ master
        │ 上限 8  │   │ 上限 13  │   │ 队列FIFO│
        └─────────┘   └──────────┘   └─────────┘
             │              │              │
          令牌制          独立QA         每班≤6
```

| 队列 | 上限 | 入口规则 | 超限动作 |
|---|---|---|---|
| ready（doing） | **8**（试点期）/ **5**（12-31 后） | 必须有令牌 + 空 WIP slot + 租约可获取 | 拒绝，进 parked |
| review | **13**（实测容量，不追求更低） | 必须有完整证据包 + 门禁 rc 记录 | 拒绝入队 |
| merge | 无上限（排队） | 必须 review 通过 + tip 冻结 | FIFO，每班 ≤6 |

**令牌制（关键设计）**：开 worktree 不是"申请配额"，是"领一张令牌"。令牌总数 = `ready 上限`。**没有令牌，`devtask new` 直接失败。** 这是唯一能真正压住 WIP 的机制——因为它不依赖 Agent 的自律。

### 7.4 并行度公式（实测校准）

```
日合入吞吐 T = 2 窗口 × 6 单 = 12 单/日
平均在途时长 D = 2 天（实测：11-05 合入 6+3 单，doing 从 21 降到 17）
最大并行度 P = T × D = 24？  —— 不对。

正确口径：
P = min(车道数 8, ready 上限 8, T / 单车道日产出)
单车道日产出 ≈ 1 单/天（一单做完要过门 + 合入）
→ P = min(8, 8, 12) = 8

但审查容量才是硬约束：review 上限 13，merge 12/日
→ 实际可持续 P = 6（留 25% 缓冲）
```

**结论**：8 条车道可以同时开工，但**同时"在 ready 里"的最多 8 个，同时"在 merge 队列里"的最多 12 个**。超过就是自己堵自己。

**这与 11-05 实测吻合**：doing 21 时，16:30 窗口只合了 6 单，21:40 合了 3 单，**9 单/日 < 12 上限**，说明产能不是瓶颈，**队列管理才是**。
