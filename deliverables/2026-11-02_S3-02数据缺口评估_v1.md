## 4. G4：report_rc 与 research_report 的窗口差异

| 项 | report_rc（tushare） | research_report（tushare） |
|---|---|---|
| 本地窗口 | **2019-01-01 ~ 2026-10-30**（94 月度分片） | **2026-07-13 ~ 2026-10-30（约 112 天）** |
| 本地行数 | **1,729,477 行**（81.5MB） | 分片 38 个 × 6,000 = 228,000 行，但 **去重后仅 8,402 行 → 重复率 96.3%**（各分片窗口高度重叠，疑分页重复落盘） |
| 字段 | 评级/目标价/eps/pe/roe/机构/作者等（可做因子） | 标题/报告类型/作者/机构/行业/url（元数据） |
| 远端深度 | 长期历史（2019+ 已验证；更早待 §2 探针） | **滚动信息流，历史深度有限**：`tushare_sync.py:291-296` 显式注释「滚动信息流（历史深度有限，先收口近期）」+ `max_off=6000`（最多 6,000 条）→ **无法补历史** |
| 依赖/用途 | P1 report_rc 因子化、H34-H36 研报因子 | 研报目录/标签/URL（`report_panel*` 研报评审、研报知识库场景，见 `docs/plans/2026-10-31_研报知识库场景与Agent支持_v1.md`） |
| 结论 | **定位=长期研报数据主干**（窗口差异不是问题） | **定位=近期研报目录快照**；① 不批准"补历史"（远端不支持）；② **批 P1 数据卫生**：清 96.3% 重复分片并重建（本地去重，~1–2h，零外部成本）；③ 钉口径：任何"研报历史/多年检验"一律走 report_rc，research_report 只做近期元数据 |

## 6. 风险与注意事项

| # | 风险 | 说明 |
|---|---|---|
| R1 | **tushare 限频/积分** | 所有 tushare 补采共用同一 token（`XT_DATA_KEY`）；G1+G2 若同日执行，可能触发"每分钟"限制（脚本 61s 退避可续），建议 **G1 单独窗口**，G2 分批错峰。**当前 token 积分数未在仓内记录（未验证）**。 |
| R2 | **G2 探针结果不确定** | 若 tushare `report_rc` 无 2019 前数据，则整个 G2 关闭；不要先批准大规模补采。 |
| R3 | **anns_pdf 存储压力** | 全量 7TB 远超仓盘余量；即使 P2-b 也有 20–37GB，需先核盘余量（本单未查磁盘余量，未验证）。 |
| R4 | **anns_pdf 源站限流/版权** | 逐份 0.6s + UA 重试；全市场回溯会被源站限流；只应按日更/按需。 |
| R5 | **research_report 重复是"本地"问题** | 96.3% 重复来自分页重复落盘，不是远端数据问题；不修会继续浪费 38 文件/18MB 并使"窗口/行数"统计失真（catalog rows=6000 也失真）。 |
| R6 | **补采后登记一致性** | 任何补采后需 `build_catalog` + `metadata_consistency` 复核（catalog/registry 本单未动，由 S3-03 按其流程执行）。 |
| R7 | **时间窗口** | tushare 补采建议避开 17:10–18:40/21:20–21:40 禁并期与 TdxSync 窗口；G1 可在任意低峰窗口。 |

6. `report_rc` 与 `research_report` 的"窗口差异"是否另有历史 URL/文本深挖诉求（研报知识库场景）未与本单口径合并评估。
7. 远端 `xtcloud ts_report_rc` 是否真的无 2020 前：依据"远端 rows=本地 rows=530,153"推断（status 无 earliest 字段）——**推断项**。
