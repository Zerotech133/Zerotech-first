## 2. INTEL0 席位定义与 A1/A2 方案对比

### 2.1 席位定义（建议稿）

**INTEL0 —— 军情司上行受理席**（role 建议 `INTEL_SECTOR`）：情报板块唯一的上行受理口，专职签收满宠（及未来情报线其他成员）的 `INTEL_UPSTREAM_REPORT` 并出具受理回执；**只受理不裁决**——受理后由情报板块/参谋长线决定分发与研判，与 QS1「受理回执=AgentAck、受理不等于授权」语义同构。

```json
{
  "agent_id": "INTEL0",
  "name": "军情司上行受理席",
  "kind": "intel_sector_upstream_receiver",
  "role_profile": "intel_sector_receiver",
  "identity": {
    "agent_role": "INTEL_SECTOR",
    "registry_ref": "agent_platform/registry/team_intel.json#/agents[agent_id=INTEL0]",
    "registered_at": "<注册工位落盘当日 ISO8601 UTC>",
    "valid_until": "<registered_at + 180 天，到期续注>",
    "accepted_routes": ["INTEL_UPSTREAM_REPORT"],
    "ack_semantics": "受理回执=agent 级 ACK；受理不等于授权，不等于研判确认"
  },
  "skills": [
    {"id": "intel_inbox_ack", "kind": "tool", "enabled": true}
  ],
  "constraints": {
    "execute": [],
    "danger": "deny",
    "note": "只受理不裁决：受理后分发/研判归情报板块与参谋长线；上行单一入口，无对飞书/投研/交易所的任何直连"
  }
}
```

### 2.2 方案对比：A1 新建 INTEL0（推荐） vs A2 给 A0A 加 accepted_routes

| 维度 | A1 新建 INTEL0 | A2 A0A 条目加 `accepted_routes:["INTEL_UPSTREAM_REPORT"]` |
|---|---|---|
| 身份硬校验 | 独立 agent_id，`registry_ref/registered_at/valid_until` 三字段可逐一落位，AgentIdentity 可实例化（对齐 WA1/QS1 判例） | A0A 在 team_chief.json，三字段可加，但 **identity 是 agent 级不是部门级**——A0A 一人三职，受理语义会泄漏到参谋长助理与驿传署两条线 |
| 职责边界 | 军情司受理专职化，**解除 A0A 三职兼任的一职**；受理席 E 岗与调度岗权限分账 | A0A 保持三职兼任，E1 调度岗同时持有受理权，权限蔓延 |
| 权限风险 | INTEL0 可按受理席最小权限裁剪（见 §4） | A0A tools_allowed 现有 `write: agent_platform/registry/**`（参谋长线权属）——受理岗与注册表写权在同一身份上叠加，越权审计面变大 |
| 改动面 | org.json departments[13] 三处 + 新建 hr/INTEL0/（+可选 team_intel.json） | team_chief.json 改动 + org.json 不动 lead——**但 team_chief.json 在 13 件在途未提交名单内**，改它会与 binding 升档悬案混批 |
| 汇报线表达 | org.json 汇报线沿用 lead 约定，军情司 lead=INTEL0 直观；满宠 supervisor 指向 INTEL0 名正言顺 | 满宠 supervisor 仍指 A0A，「唯一上级=情报板块主 Agent」在名册上仍以 A0A 呈现，与章程语义错位 |
| 成本 | 一个新席位 + 一份 HR 档案 | 零新席位，但欠账更深 |

**推荐：A1。** 决定性理由有二：① agent 级 identity 与部门级受理语义必须解耦（WA1/QS1 判例的根基），A2 把两个部门的受理语义压进一个 agent 条目，重蹈三职兼任；② A2 必须改 team_chief.json，而该文件正处 13 件 binding 升档在途未提交名单，违反「改绑线单独成批」判例（541b1690 处置分档②）。A1 的全部落点（org.json departments[13]、新建 team_intel.json、hr/INTEL0/）均不在在途名单内。

## 5. 满宠入册方式：C1 独立条目（推荐） vs C2 HERMES_UI 挂 persona

### C1 —— 新建独立 agent 条目 MANCHONG1 入 intel 部（推荐）

### C2 —— HERMES_UI 条目扩展 persona 字段双挂

- 在 ops_runtime 部 HERMES_UI 条目上加 `persona:{name:满宠}`，或移挂 intel 部。

### 对比与推荐理由

| 维度 | C1 独立条目 | C2 挂 HERMES_UI |
|---|---|---|
| HR 纪律 | 一人一档；满宠产出（manchong_brief_* / decision log）以独立身份入账，check_hr 黑户检查可对上 | 满宠产出若以 MANCHONG 名义入账而名册无此条目，**即 K-ORG-117 定义的「黑户」**；若都记 HERMES_UI 名下，则情报线产出与门面职责混账 |
| 职责边界 | 门面（糜竺，驿传署）与情报中枢（满宠，军情司）分账，章程「与荀攸章程同构、互不隶属」的兄弟线结构成立 | 一条目两 persona（糜竺+满宠）、跨两部门职责焊死在 ops_runtime/intel 之间，改属还会牵动驿传署 agents 数组 |
| 权限表达 | 满宠专属约束（只读红线/查询权/8791）独立裁剪，与门面 `read:* write:[]` 互不污染 | tools_allowed 只能一套：门面要 `read:*`，满宠要限定的 8791/MCP 面，合一是权限蔓延 |

- 注册不改变方案B 运行：intel_inbox.py 哈希幂等受理照常；agent 级 ACK 升级（对齐 QS1 upstream_inbox 语义）是否立项列 §8 拍板。
