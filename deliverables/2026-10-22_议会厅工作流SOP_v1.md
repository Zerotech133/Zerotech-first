## 一、六阶段工作流（全周期）

```
① 立题    老田在议会厅丢一句话：「我要开发 X」
② 表态    三席位各自出看法文书（落盘 deliverables，议会厅自动投影）
          诸葛亮=该不该做/优先级；田丰=怎么拆/怎么验收；赵云=风险/治理债/判例查询
③ 试工    一席位先行 N 步（默认田丰或 WorkBuddy）：
          独立 worktree + 逐步 commit——过程天然可回放，这就是监读面
④ 监读    其余席位读试工的 diff/提交流水/文档（异步，不必同时在线）
⑤ 定稿    老田第三方拍板 → approval_gate 签字 → 议题灯转绿
⑥ 分发    路由器给派工组合 → 田丰/老田执 devtask new 建单 → 各自 worktree 开工
   收口    合并+S1 收工即收口+互审单（分歧回议会厅②）
```

**关键设计**：②-④ 全程异步（今晚四轮互审已验证此模式），老田只在⑤出现一次。

## 三、分发命令链（一次定稿到多席位开工）

```bash
# ① 老田定稿后，任一会话跑路由建议：
python tools/council_route.py --tags dev,quant --ticket K-XXX-20261023-01

# ② 田丰（或老田）按建议建单（每席位一张，pathspec 各自独占）：
python tools/devtask.py new --desc "X 主执行" --owner workbuddy --project quant
python tools/devtask.py new --desc "X 治理协同" --owner zhaoyun --project govern

# ③ 各席位在自己 worktree 开工（devtask 守卫五道闸：明文凭据/L2/扫描…）
# ④ 合并→收口提示→worktree 回收（S1）→互审单（分歧回议会厅）
```

## 四、议会厅的三个会议用途（对齐全案）

1. **决定**：立题表态→定稿（②→⑤，今晚模式）
2. **彼此监督**：互审单流转 + 监读试工过程（③④）
3. **进化**：判例 Z2 卡在议会厅呈签→Z4 入库全员生效

## 五、防疏忽三检

| 检 | 机制 |
|---|---|
| 试工席位偷懒/跑偏 | 监读席位读 diff（异步评审）+ 议会厅议题灯不转绿 |
| 分发漏人 | 路由表显式四角色（lead/assist/review/gate），缺一不可出建议 |
| 收口烂尾 | devtask 守卫合并后强制提示回收 + S1 收工即收口 + 健康卡第 22 项 |
