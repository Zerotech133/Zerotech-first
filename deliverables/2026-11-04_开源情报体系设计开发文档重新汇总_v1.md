## 三、设计总览：一个中枢 + 五条产线 + 一个底座

10-18 总案最核心的设计决策是**"中枢不搬数据"**——这条决定了整套架构的走向，必须放在最前面：

```
                    ┌──────────────────────────────────────┐
                    │  情报中枢 /intel（只读聚合 + 导航）    │
                    │  证据—标的关系 · 逐跳追溯 · 复核状态    │
                    └───────┬──────────────────────────────┘

   新闻/JEV线    雪球线          股吧线      TDX线       视频/嗅探线
   news.db     xueqiu_info.db   *.jsonl    tdx_info.db   osint_video(PG)
        │           │               │           │              │
        └───────────┴───────┬───────┴───────────┘              │
                            │                                  │
                    ┌───────┴────────┐              ┌──────────┴────────┐
                    │  KG / 血缘     │              │ res-downloader-py │
                    │ zerobound-kg   │              │ 嗅探器 :8898      │
                    └────────────────┘              └───────────────────┘
                            ▲
                    ┌───────┴─────────────────────────────┐
                    │ 采集底座 L0 · intel_collector        │
                    │ 源注册 / 适配器 SDK / 权利闸门 / 编排 │
                    └─────────────────────────────────────┘
```

### 3.1 五层账本（10-18 总案 §二，全体系最硬的口径）

| 层 | 回答的问题 | 权威纪律 |
|---|---|---|
| 原始来源 | 原文是什么、何时生成、采集是否健康 | 源内 ID、原始时间、入库时间；"有历史数据"≠"当前采集健康" |
| 证据—标的 | 哪条证据如何提及哪只股票 | 证据键＋标准代码＋匹配依据＋证据等级；歧义保持候选 |
| 管道血缘 | 哪次作业读取何物、产出何物 | PG `job_run` + 显式 `edge(output,input)`；只有运行记录不算闭环 |
| KG 实体关系 | 来源/事件/证券/假设如何关联 | 边附证据与图版本；**图可达≠因果** |
| 研判与审批 | 谁判断、谁签收、谁允许消费 | JEV/KG/intel 人审/平台 Approval **不自动互认** |

**水位必须分别记账**：源采集水位、原始记录覆盖、PG 作业与边覆盖、KG 消费键集、证据可用性、复核/审批状态。
**`breaks=0` 只说明已有边集合里未观察到断链，不能证明应有边已登记**——这是全体系最易被误读的一句。

### 3.2 首个最小颗粒（产品定义）

> 不是"某股票"、不是日报、不是综合分数，而是：
> **一条具有源内稳定 ID 的原始证据，与一个标准化标的之间，附有可说明匹配依据、时间和证据状态的关系。**

同一证据可关联多标的；一标的多条关系；**聚合不能抹去证据与匹配依据**。
结构化字段含明确代码才可标"精确代码匹配"；名称/标题/模型推断**只产生待复核候选**。

### 3.3 七源接缝（10-18 总案 §三）

| 来源 | 真源键 | 必须解决的差异 |
|---|---|---|
| 新闻与 JEV | `news.db` 新闻 ID / 来源 / 内容时间 / 入库时间 / `stocks` / `jev` | 普通新闻 `stocks` 可为名称，JEV feed 可为标准代码，**不能混当证券 ID** |
| 雪球舆情 | `status_id` / `created_at` / `fetched_at` / 分类版本 | 日报 `top_codes` 是聚合信号**不是逐帖证据**；"讨论帖"不能声称楼层回复 |
| 股吧 | `post_id`＋所属文件/标的 | 生产者重排并原子重写 JSONL，旧 KG 消费者按行数续读 → **静态增量契约冲突** |
| TDX | 自有 `tdx_info.db` 资讯三类表 | 资讯/公告/研报各自留键与许可，不套帖文 schema |
| 链接/视频 OSINT | 源系统 PG 知识与证据 | 先定可信只读 DTO、身份、媒体留存；**POST 入队能力不得混入只读取证工具** |
| KG/事件路径 | 新闻事件→证券→行业 | `INVOLVES` 是实体拓扑；`DRIVE` 时间窗配对是**共现不是影响概率** |
| 数据血缘 | 作业/输入输出资产/版本/批次 | 实际转换须显式登记边，并与"应有边"清单对账 |

## 四、五条产线的设计要点

### 4.1 新闻 + JEV 线（事实源：`news.db`）

**设计要点（10-31 方案 §2）**：
- `news.db` 是新闻与 JEV 的**唯一事实源**，不新建第二套数据库。
- `news` 表补 `canonical_id`、`content_hash`、`review_status` 索引。
- JEV 结果只存 `news.jev` + 审计账本，**不复制第二份"结论表"**。

**唯一交接物 `IntelEvent`**（11 字段）：`event_id / canonical_id / source / source_ref / content_hash / occurred_at / ingested_at / title / content / stocks / trust / dedup_of`

**`JEVRecord`**：`bias(bull|bear|neutral) / conf / scope / event_type / impact / reason(≤50字) / model / prompt_version`

**`ReviewRecord`**（append-only）：`status(pending|resolved|rejected) / reviewer / verdict(accept|reject|needs_evidence) / reason / reviewed_at`

**`EvidenceBundle`**：`bundle_id / event_refs[] / jev_refs[] / l4_verdict / published_at / reviewed_by`

**状态机**：`pending → sampled → resolved(accept/reject/needs_evidence) → rejected(不再发布)`

**三条硬规则**：
1. 未复核 `high impact` 事件**不得**进入 N1/D1 的"已核验证据"。
2. 复核记录不可改，只能追加新版本。
3. 复核队列与发布队列分离，**避免"pending 数量=已判读"**。

**来源分级**：A 法定/交易所公告 → B 主财经媒体 → C 聚合/自媒体/OSINT。**C 级不得单独作为高影响判读证据**。

### 4.2 雪球 / 股吧 舆情线

| 项 | 雪球 | 股吧 |
|---|---|---|
| 采集范式 | v4 舆情 API + pysnowball 行情；防风控五件套（403 熔断 30min / jitter≥2s / 静态代理池 / 多 token 池 / Playwright WAF cookie 工厂 TTL 12h） | SSR 页面内嵌 JSON；**只读不登录、1.5s/页限速、`post_id` 去重、原子写** |
| 数据落点 | `data/xueqiu/xueqiu_info.db`（三表 + 行情 Parquet 是两条健康线） | `data/guba/{code6}.jsonl` |
| 合规范本 | 五件套可移植到微博/海外源 | **`guba_crawl.py` 是"合规采集适配器"样板** |
| 已知残缺 | `comment/quote/kline` 三表为 0（设计未建成）；`xq_hot_post`/`xq_comment` 双接口 404 下线，需人工抓包找新 API | `GubaCrawl_B/C`（20:30/22:30 多窗口）从未执行；限流 fail_rate 66.7% |

**舆情消费断层（F2，10-17 报告最重的一条）**：`kg_brief`、`event_graph`、九维画像对 xq/guba 的消费为 **grep 0 匹配**——"采了但没人吃"。这是"先修后扩"原则的来源：**P0 未闭环前不接新源，否则断层会复制到新源上**。

### 4.3 TDX 接口情报线

- 铁律：资讯、公告、研报**各自留键和许可**，不套用帖文 schema；**不把"服务可达"当"同步健康"**。

### 4.4 视频 OSINT 线（`osint_video`，唯一有完整表设计的产线）

**定位**：把"链接驱动的博主兴趣发现"沉淀为**可检索、可追溯、可审计的知识资源**；**媒体只是短期处理输入，不作为核心资产**。

**架构选型（system_design §1.2）**：

| 项 | 选择 | 理由 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + Pydantic v2 | 沿用现有 `queue_link/api.py` |
| 持久化 | PostgreSQL 15 + SQLAlchemy Core/psycopg3 | 关系表是事实源，JSONB 只放可演进抽取原文 |
| 向量 | Qdrant，collection `osint_knowledge_units_v1` | payload 只放过滤字段+摘要，**不放秘密或完整媒体** |
| 图谱 | 首期 PG `kg_node/kg_edge`（可迁 Neo4j） | 边必须带 `evidence_id`/置信度/有效时间 |
| 管理台 | React 18 + Vite + MUI + TanStack Query | 7 页：链接/博主/知识/时间线/策略/任务+首屏 |
| 任务 | PG `FOR UPDATE SKIP LOCKED` 轻量 worker | 量涨后切 Celery/RQ，**不改领域接口** |
| 一致性 | 分层 + Outbox + 幂等 upsert | PG 权威；Qdrant/KG 可重建 |

**14 张核心表**（`osint_creator_profile` / `osint_interest_signal` / `osint_knowledge_resource` / `osint_media_asset` / `osint_knowledge_unit` / `osint_topic` / `osint_knowledge_topic` / `osint_entity` / `osint_knowledge_entity` / `osint_timeline_event` / `osint_evidence` / `osint_strategy` / `osint_strategy_evidence` / `osint_processing_run` + `osint_outbox` + `kg_node`/`kg_edge`）

**四套状态机**：

```text
链接采集   pending → parsed → downloaded → decrypted → extracted → done
           异常 → failed（指数退避）→ 超限 dead；Cookie 失效 → waiting_cookie
知识资源   candidate → reviewed → published → deprecated/quarantined
知识处理   raw → normalized → classified → entity_linked → indexed → published
           （质量不足 quarantine / 永久错误 rejected；每次重跑新 processing_run）
媒体生命周期 acquired → processing → extraction_succeeded/failed → purged
```

**博主运营状态机（management_platform §10.6，正式口径）**：
```text
link_received → creator_resolved → profile_created → history_backfill_running
  → profile_summarized → daily_monitoring → incremental_update
异常：resolve_failed / backfill_failed / summarize_failed / scan_failed
  → retryable → retry  |  terminal → dead_letter + manual_review
```
`profile_summarized` **不是终态**；只有进入 `daily_monitoring` 才纳入持续扫描。

**跨切面约束十条（system_design §8 摘要）**：
① 统一 `{code,data,message}`，cursor 分页禁无上限 ② `published` 必须有可定位有效 Evidence ③ ASR/OCR/subtitle 按独立 `source_channel` 存，**禁止 ASR 误标字幕** ④ `LinkTask.done` 只在知识资源+Evidence 入 PG 且索引任务已登记后设置 ⑤ 全局唯一 ID + 幂等写 ⑥ PG 权威、Qdrant/KG 可重建 ⑦ 知识单元禁无来源发布 ⑧ PII 入库前脱敏，Cookie/Token 永不入日志/payload/图属性 ⑨ 兴趣分数 = 频次 × 时间衰减 × 证据可靠性，单条内容只形成候选 ⑩ 采集 ≥30 秒硬限速 + 夜间静默 + 白名单。

**管理平台契约的三个 P0 硬修复（contract_v1）**：
1. `LinkTaskPublic` **移除 `raw_path`/`parse_result`/Cookie/Token/内部租约**；字段映射 `id→task_id`、`status→state`、`retry_count→attempt`。
2. 健康状态**固定枚举** `healthy|degraded|unavailable|unknown`，**禁止返回 `"ok"`/布尔值**；PG 不可用时业务 503，健康检查本身仍返回 envelope。
3. 知识单元公开主键为 **`unit_key + unit_version`**，`unit_id` 是内部 ID，不得作为前端详情路径。

**颜色约定（两处文档一致，也与老田口径一致）**：**红=上涨/正向/`supports`；绿=下跌/负向/`contradicts`**；错误用橙/紫并配文字，**不得用"绿=成功"通用覆盖**。

## 五、三套数据模型对照（最容易读混的地方）

同一件事在三条线上有三套模型，**不要互相套用**：

| 维度 | 情报中枢（news.db 侧） | 视频 OSINT（PG 侧） | 采集底座（L0） |
|---|---|---|---|
| 最小单元 | `IntelEvent`（一条新闻事件） | `KnowledgeUnit`（一条知识单元） | `Observation`（一次观测，不可变） |
| 证据载体 | `news` 行 + `jev` 列 + `review` 账本 | `osint_evidence`（quote+时间码+通道+可靠性） | Observation payload + `snapshot_id` |
| 标的关联 | `stocks` 字段 + `match_basis`（exact/candidate） | `target_id` + `osint_interest_signal` | `canonical` 跨源实体归并 |
| 版本 | append-only review | `unit_version` + `supersedes_unit_id` | `as_of` + PIT 时点快照 |
| 权利 | trust A/B/C | 媒体保留 + PII 脱敏 | **RightsGate 三用途显式批准** |
| 消费对象 | N1 / D1 / 情报流 / 工作台 | 策略证据链 / 博主档案 / 时间线 | 任何下游（含 agent 订阅） |

**关键差异**：中枢侧只到"事件+判断+复核"；视频侧多一层"知识单元"（claim/viewpoint/method/case/definition/metric/entity）；底座侧根本不管语义，只管"观测+权利+水位"。
