# 本地数据库试迁移执行计划

**版本**：v1.0
**日期**：2026-10-17
**目标**：先在本地完成 PostgreSQL/SQLite 分层迁移演练，验证 schema、版本化幂等、双跑与灰度回退；不直接切生产指针。

## 1. 总体原则

```text
生产 SQLite 保持事实源
        ↓ 只读抽取
独立 PostgreSQL staging schema
        ↓ 结构/键/hash/幂等验收
本地灰度读取
        ↓ 连续观测与回退演练
获得批准后再讨论 canonical 发布
```

硬边界：

- 不直接 `TRUNCATE`、`DELETE`、覆盖或重建 `quant`、`tdx_info`、`tdx_archive_20261017`；
- 不修改 `meta.sync_state`、`meta.migration_log`；
- 不写 Neo4j；
- 不切换 `KG_QUANT_DB/KG_TDX_DB/KG_NEWS_DB`；
- 不重启 dashboard、Hermes、MCP 或其他消费端；
- 不运行现有全量 `migrate_sqlite_to_pg.py --apply`；
- 所有新写入只允许进入带日期/批次号的独立 staging schema。

## 3. 阶段计划

### S0：冻结范围与维护窗口登记

**目标**：明确试迁移只写 staging，不要求停生产消费端；若要生成可复现最终快照，则冻结 writer。

动作：

1. 登记维护窗口、操作人、回滚责任人；
2. 记录三个 writer 状态、Action、最近结果、恢复命令；
3. 推荐在正式全量 staging 前冻结：
   - `ChanlunScan`
   - `QuantMetaSync`
   - `KgDailySync`
4. 若暂时无法冻结，只允许做只读审计和小样本 staging，不允许正式迁移发布。

门禁：

```text
小样本研究：writer 可不冻结，但结果只作实验
全量 staging/灰度读取：三个 writer 必须 Disabled
```

### S1：重新生成试迁移前快照

**目标**：让备份和源指纹与当前生产状态一致。

动作：

- 记录 canonical realpath、大小、mtime、SHA256：
  - `C:/aios/quant_backtest/data/quant.db`
  - `C:/aios/quant_backtest/data/tdx/tdx_info.db`
- 重新导出 PostgreSQL `quant`、`tdx_info`、必要 `meta` 对象；
- 导出 `meta.sync_state`、`meta.migration_log`；
- 运行 `pg_restore -l`，记录 dump SHA256；
- 保存快照清单和恢复命令。

门禁：

```text
备份可读、checksum 可复核、源文件指纹稳定
```

### S2：设计并创建类型化 staging schema

**目标**：从“全 text 试验表”升级为接近正式模型的独立 staging。

建议 schema：

```text
staging_quant_trial_20261017
staging_tdx_trial_20261017
```

设计要求：

- 保留原字段名和来源信息；
- 添加 `ingest_run_id`、`source_system`、`source_row_id`；
- 添加 `version_hash`、`_fetched_at`；
- 日期/时间字段明确类型和时区；
- 数值字段先做兼容性报告，再决定是否转换；
- 不在生产表加约束；
- 版本 hash 唯一约束只建在 staging。

TDX 版本化模型：

```text
业务键：候选字段组合，仅用于识别
版本键：SHA256(规范化完整行)
时间：_fetched_at
幂等约束：UNIQUE(version_hash)
```

### S3：全量 staging 回放

**目标**：验证可重复迁移和幂等性。

批次：

1. 先执行 1,000 行/表回放；
2. 再执行 10,000 行/表回放；
3. 最后执行全量 staging 回放；
4. 每个批次使用独立 `ingest_run_id`；
5. 同一批次重复执行一次，必须零新增版本。

验证：

- 源/目标行数；
- key 集合 hash；
- version hash 集合；
- SQLite-only/PG-only；
- 重复键数量；
- 关键字段空值；
- `_fetched_at` 最小/最大值；
- 失败批次事务回滚且无半成品。

门禁：

```text
首轮导入成功
二次导入不新增重复版本
全量 key/hash 集合一致
失败可回滚
```

### S4：Quant staging 迁移演练

**目标**：单独演练 quant 关系数据的 key-aware upsert，不触碰现役 `quant`。

范围优先：

- `chanlun_pool`；
- `nine_dim_fina`；
- 其余已迁移 quant 表作为只读对账对象。

要求：

- 只从 canonical 生产 SQLite 读；
- 目标为 `staging_quant_trial_20261017`；
- 事务内完成；
- `ON CONFLICT` 只针对 staging 约束；
- 不推进 `sync_state`；
- 不删除 PG-only 行；
- 回放后执行完整 key-set/digest 对账。

### S5：双跑与稳定性观测

**目标**：证明 staging 在 writer 运行期间或冻结窗口内可重复验证。

至少执行：

- 冻结窗口一次双跑；
- writer 恢复后一次双跑；
- 连续两轮 sample-size=1000 或更高；
- 对比 source fingerprint、key hash、version hash、行数和水位快照。

失败条件：

- 任一表 count 不一致；
- 任一 key/hash 出现单边；
- writer 恢复后 staging 漂移无法解释；
- 任何报告来源不是 canonical 生产路径。

失败处理：保持 SQLite 指针，停止后续动作。

### S6：本地灰度读取演练

**目标**：不修改生产指针，验证消费端是否能读取 staging/PG。

方式：

- 新建独立测试 DSN/配置；
- 启动独立临时读取进程或测试脚本；
- 不占用生产端口、不重启生产服务；
- 验证 dashboard/MCP/查询层的只读接口；
- 对比 SQLite 与 staging 返回结果；
- 测试异常时自动回退 SQLite。

门禁：

```text
测试配置与生产配置隔离
读取结果一致
PG 不可用时回退 SQLite
不产生写入
```

### S7：发布评审，不自动发布

发布前必须由负责人明确批准：

- A1：冻结 writer 与最终备份；
- A2：允许 quant staging/正式镜像补齐；
- A3：允许修改同步水位；
- A4：TDX archive 保留/隔离/重建策略；
- A5：允许讨论生产指针变更。

本计划默认只做到 S6，不自动进入生产切换。

## 4. 回滚方案

### staging 回滚

只删除本次创建的独立 schema，且先做对象清单核验：

```sql
DROP SCHEMA staging_tdx_trial_20261017 CASCADE;
DROP SCHEMA staging_quant_trial_20261017 CASCADE;
```

实际名称必须与运行报告一致，不得复制粘贴到现役 schema。

### PostgreSQL 恢复

- 使用重新生成并校验的 `pg_dump`；
- 恢复前人工确认数据库、schema、角色和备份 hash；
- 先恢复 staging/测试库，不直接覆盖生产；
- `sync_state` 与 `migration_log` 单独按审计记录恢复。

### 消费端回退

整个计划期间保持：

```text
KG_QUANT_DB / KG_TDX_DB / KG_NEWS_DB -> SQLite
```

灰度测试失败时只停止测试进程，不重启或修改生产消费端。
