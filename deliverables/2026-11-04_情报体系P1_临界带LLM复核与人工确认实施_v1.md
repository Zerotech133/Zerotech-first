## 1. 一句话结论

**临界带（`[0.70, 0.75)`）开 LLM 复核，把唯一的拆散（S11，cos=0.7133）清零，误合并仍为 0，独立来源数从 13/14 变 14/14，代价是 2 次 LLM 调用。**

| 口径 | 事件数 | 拆散 | 误合并 | 独立来源数 | LLM 调用 |
|---|---|---|---|---|---|
| 0.75 + 规则判定（基线） | 29 | **1** | 0 | 13/14 | 0 |
| 0.85 + 规则判定（回退档） | 34 | 5 | 0 | 9/14 | 0 |
| **0.75 + 临界带 LLM** | **28** | **0** | **0** | **14/14** | **2** |

第三行的"14/14"与第一行的"13/14"分母不同：基线里 S11 被拆散，评测脚本按设计把它排除在来源数统计之外（"仅统计未被拆散的故事"）。**基线的真实状态是"1 个故事的来源数无法计算"**，不是"13 个故事里 13 个对"。

## 2. 为什么选这条，而不是改 schema

S11 的问题一句话说完：`s11-01`（组件价格跌破成本线，行业协会呼吁自律）与 `s11-02`（价格战延续，协会召集头部企业座谈）是同一件事的相邻进展，余弦只有 **0.7133**，比"主体相同但确实两件事"的 `s04-01`/`solo-05`（**0.7203**）还低 0.007。

三条候选解法当时被数据各砍一刀：

| 解法 | 判决 | 依据 |
|---|---|---|
| 一事多事件（改 schema） | 成本最高、收益最窄 | 为 1 个事件改表结构，且跨窗口召回已能覆盖大部分跨阶段场景 |
| 时间加权降门槛 | **证伪** | 网格最优 slope = **+0.000**；同一天不同事件 cos=0.7203 > 差一天同一事件 cos=0.7133，任何"间隔小就降门槛"的规则先放入错的 |
| 临界带 LLM + 人工确认 | **采纳** | 该带真机只有 2 对，2 次调用而非全量 120 次；本机 iGPU 单次数秒，生产机纯 CPU 约 1 分钟，都在 cron 轮次内 |

关键判断：**余弦在这条带上已经用尽了信息量**。0.7133 / 0.7203 相差 0.007，任何阈值微调都是在噪声上做决策。要分开它们必须换一种判据，而 LLM 判的是"这两条讲的是不是同一件事"，不是"两条有多像"——这是不同维度，不是同一维度的更精细刻度。

## 3. 实现结构

### 3.1 三层优先级（`StoryGrouper._decide_borderline`）

```
sim >= 直判门槛 (0.75)          → 余弦直判同，不调任何判定器   decided_by=vector
门槛-0.05 <= sim < 门槛        → ① 人工台账 → ② LLM 复核 → ③ 交回主判定器
sim < 门槛-0.05                → 主判定器（规则/LLM，按 --judge 配）  decided_by=rule/llm
```

三层各自的理由：

1. **人工台账最高**：人已经看过并拍过板，机器再算一遍只是在覆盖人的判断。台账命中时不再调用 LLM——顺带省一次调用。
2. **LLM 复核次之**：只替换主判定器在这一小段上的结论。主判定器是规则时（默认），意味着这段的判定能力被单独升级，而其余区间行为逐字节不变。
3. **都没有 → 交回主判定器**：`_decide_borderline` 返回 `None` 表示"本算子没有复核能力"，默认配置下走的就是这条，**行为与 P1 之前完全一致**（`borderline_rechecked=0`）。

### 3.2 与"全区间开 LLM"的成本差

这是本方案能落地的根本原因，不是精度问题：

| 方案 | 调用量（真机） | 本机 iGPU | 生产机 20 vCPU 纯 CPU |
|---|---|---|---|
| `--judge llm`（全区间 `[0.60,0.75)`） | 实测 120 次触发熔断 | 约 10 分钟 | **约 40-60 分钟** |
| `--borderline-judge llm`（只 `[0.70,0.75)`） | **2 次** | **实测 70-91 秒（含冷加载）** | 约 1 分钟 |

差一个数量级以上。临界带在真机上只有 2 对，因为它只有 0.05 宽，而 `[0.60,0.70)` 那 0.10 宽塞下了其余 118 对。

### 3.3 失败语义

复核器故障（未启动/超时/回复不可解析/预算用尽）时：

- **不返回 `unrelated`**，回落 `RuleJudge`；
- `judge_failures += 1`，汇入 `degraded`，CLI 以退出码 2 结束；
- 同一对**不重试**——`OllamaRelationJudge` 内部熔断已让重试变成毫秒级空转，重试只会把 `borderline_rechecked` 刷高，让人看不出真实规模。

这条契约有专门的单元测试锁死（见 §6），因为它在集成路径上会被后续兜底掩盖：第一次把故障当无关 → 第二次评估走 `_recheck_failed` 短路分支 → 又回落规则 → 最终结果看起来仍然"正确"。

### 3.4 `decided_by` 口径

`store/schema.sql` 的 `osint_story_member_decided_by_check` 本来就预留了 `llm_recheck` 和 `manual`，**本次零 DDL 改动**。

| 值 | 含义 | 是否越权 |
|---|---|---|
| `vector` | 余弦直判同 / 跨窗口准入 | 否，门槛之上 |
| `rule` / `llm` | 主判定器结论 | 否，在 `[召回门,门槛)` |
| **`llm_recheck`** | **临界带内被 LLM 抬过门槛** | **是，低于门槛 0.05 以内** |
| **`manual`** | **人工台账裁决** | 是（合并）或否（否决） |

事后要回答"有多少事件是被越权合进来的"，直接 `SELECT count(*) FROM osint_story_member WHERE decided_by IN ('llm_recheck','manual')` 即可。

## 4. 真机实测

### 4.1 准备

库现状 50 条事实 / 29 story / 42 member / 31 alias。为让临界带配对重新参与判定（`_load_units` 用 `NOT EXISTS` 排除已归属事实），备份并清空成员边后跑 dry-run：

```
osint_story_member_bak_p1e   ← 42 行备份
osint_story_bak_p1e          ← 29 行备份
DELETE FROM osint_story_member
```

### 4.2 基线（`--dry-run`，不开口径）

```
units_scanned=42  stories_created=29  borderline=2  judge_calls=0  degraded=False
elapsed 6.2s
```

两对临界：

| 对 | cos | 真值 | 规则判定 |
|---|---|---|---|
| `verify-s11-02` / `verify-s11-01` | 0.7133 | **同一事件** | unrelated（jaccard=0.128 < 0.35） |
| `verify-solo-05` / `verify-s04-01` | 0.7203 | 不同事件 | unrelated（entity_overlap=1.000 但不单独构成同事件） |

与 v1.4 记录逐位一致，说明基线可复现。

### 4.3 开临界带 LLM（`--dry-run --borderline-judge llm`）

```
borderline_rechecked=2  borderline_promoted=1  judge_calls=2  stories_created=28
judge_failures=0  degraded=False  elapsed 91.0s（含冷加载约 46s）
```

LLM 的两条结论（原文摘录）：

- S11：`same_story` ——「两事实均围绕光伏组件价格战及行业协会召集企业座谈呼吁自律这一核心事件，报道主体与事态进展一致。」
- S04/solo-05：`unrelated` ——「事实 A 为财报发布事件，事实 B 为新产品发布事件，主体相同但事件性质不同。」

**两对都判对了。** 一对该合（合了），一对不该合（没合）。

### 4.4 落库后评测

```
python scripts/story_group_run.py --borderline-judge llm     # 实跑
python scripts/eval_story_quality.py

事实 42 条 → 事件 28 个（真值 14 个多事实故事 + 14 条独事实）
拆散 0 个 / 误合并 0 处
独立来源数正确 14/14（仅统计未被拆散的故事）
判定来源：llm_recheck=1, vector=41
```

`stories_created=0 / stories_reused=28` —— 全部复用既有 story，验证了 `ON CONFLICT (story_key) DO UPDATE` 的重算语义（缺陷 8 的修复在真实重跑路径上生效）。

### 4.5 人工确认链路实测

1. LLM 提升的那对自动落进待确认队列：`data/story_borderline_pending.jsonl` 新增 1 条，含两侧标题、cos、门槛、gap、LLM 理由。
2. `python scripts/borderline_review.py list` 正确渲染。
3. 人为裁一条 `reject`（模拟人否决 LLM），写入台账。
4. 清空成员边重跑 dry-run：

```
overrides_loaded=1  manual_overrides=1  judge_calls=1
borderline_rechecked=1  borderline_promoted=0  stories_created=29
borderline_samples decided_by: ['manual', 'llm_recheck']
```

结果完全符合设计：

- **人工否决压过了 LLM**，S11 重新拆散（29 事件）；
- **命中台账的那对没有再调 LLM**，`judge_calls` 从 2 降到 1；
- `decided_by` 两个值都出现在样本里，可追溯。

5. 验证完删除测试台账、恢复 `member` / `story`（逐列对账 0 行不一致）。

### 4.6 耗时细目

| 场景 | 耗时 | 说明 |
|---|---|---|
| 基线 dry-run | 6.2 s | 无 LLM 调用 |
| 临界带 LLM dry-run | 91.0 s | 含 `qwen3.5:9b` 冷加载约 46 s + 2 次推理 |
| 临界带 LLM 实跑 | 69.9 s | 模型已热，2 次推理约 20 s，其余为嵌入 + 写库 |

生产机纯 CPU 的推算：冷加载可能达 2-3 分钟，2 次推理约 40-60 秒，单轮总计 3-5 分钟。相对 cron 间隔可接受，但**首次上线建议先跑一次 `--dry-run` 确认 `borderline` 规模**。

## 6. 测试与变异验证

新增 45 项，全部离线（不依赖 PG / Ollama）。

### 6.1 作用域边界（5 项）

临界带内复核、门槛之上不碰、门槛-0.05 之下不碰、召回门之下不碰、默认配置零变化。这几项守的是"不要为了修 1 个漏合而把门槛取消掉"。

### 6.2 结论与计数（3 项）

提升样本必须留痕（否则误合并无从发现）；判异也计入 `borderline_rechecked`（否则看不出临界真实规模）；同一对只复核一次（否则调用量翻倍、计数虚高）。

### 6.3 故障语义（3 项）

- 集成路径：故障 → 回落规则 + `degraded`；
- 短路路径：故障对不重试；
- **单元路径**：`_decide_borderline` 首次返回的 `decided_by` 必须是 `rule` 而非 `llm`。

第 3 项是变异测试逼出来的：前两项在集成路径上都被后续兜底掩盖，把"首次当无关"的错误藏住了。直接调单次判定才锁得住。

### 6.4 人工台账（5 项）

approve / reject 生效且 `decided_by=manual`；台账键顺序无关；**台账对门槛之上不生效**；**台账对门槛-0.05 之下不生效**。后两项守的是"人工否决权只在机器也拿不准的窄带上"，放开到全域等于人一个笔误就能造误合并。

### 6.5 台账/队列 IO（23 项）

配对键跨进程稳定（`||` 分隔，避开 `unit_key` 内的冒号）；文件不存在 ≠ 文件损坏；损坏必须抛 `OverrideError`；单条坏不连坐；含糊值（`yes`/`1`）拒绝；原子写不留 `.tmp`；`record_override` 保留他人条目与备注；队列按配对去重（含反向）。

### 6.6 变异测试（7/7 全部暴露）

| 变异 | 结果 |
|---|---|
| 全域开复核（作用域边界破坏） | 2 failed |
| 台账优先级降到 LLM 之后 | 3 failed |
| 去掉复核去重 | 4 failed |
| 去掉 `borderline_promoted` 计数 | 3 failed |
| 台账键不归一（顺序敏感） | 1 failed |
| 复核失败不回落规则（伪装成无关） | 1 failed |
| 复核失败不记 degraded | 2 failed |

### 7.3 表态

```bash
python scripts/borderline_review.py approve "verify-s11-01" "verify-s11-02" \

python scripts/borderline_review.py reject  "verify-s11-01" "verify-s11-02" \
```

### 7.4 回退

| 层级 | 操作 | 影响 |
|---|---|---|
| 关复核 | `STORY_BORDERLINE_JUDGE=off` 或去掉 `--borderline-judge` | 回到 P1 基线行为，零 LLM 调用 |
| 清人工干预 | 删 `data/story_borderline_overrides.json` | 全部裁决失效，机器重新说了算 |
| 只清一条 | `borderline_review.py drop <l> <r>` | 精确撤销 |

### 7.5 告警

| 指标 | 阈值建议 | 含义 |
|---|---|---|
| `degraded=true` | 立即告警 | 复核器不可用，本轮回落规则 |
| `borderline_rechecked` 突降为 0 而 `borderline>0` | 告警 | 复核链路断了，但没报错（最隐蔽的一种） |
| `borderline_promoted / borderline_rechecked > 0.5` | 关注 | 门槛可能偏低，LLM 在大量越权合并 |
| `manual_overrides > 0` | 只是提示 | 本轮结果经过人工干预，与全自动结果不可直接比 |

## 9. 与三条裁定项的关系

上一轮遗留三个待裁定项，本次解决了第 3 项：

| # | 裁定项 | 状态 |
|---|---|---|
| 1 | 跨窗口召回开不开 | **仍待定**，建议生产 dry-run 两周看 `over_merge_count` |
| 2 | LLM 判定器部署方式 | **已实质回答**：临界带 LLM 是"只在高价值候选对开"的具体形态，代价 2 次调用而非 120 次——本机与生产机都付得起 |
| 3 | S11 剩余解法 | **已实施并验证**：拆散 1 → 0，误合并 0，来源数 14/14 |

第 2 项原本的三个选项里，**"甲：仅在高价值候选对启用"** 就是本次交付的东西，只是把"高价值"从一个模糊概念变成了可计算的定义——**距离直判门槛 0.05 以内**。这个定义的好处是它随阈值自动移动，不需要额外维护一张"高价值清单"。
