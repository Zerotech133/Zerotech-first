## 二、限期已知降级：设计取向是「限期豁免」不是「永久免死金牌」

数据结构（`known_degraded.json`）：

```json
{"tables": {"index_daily": {"since": "20261105", "until": "20261113",
                            "reason": "...", "mitigation": "...", "owner_action": "..."}}}
```

判定（`split_degraded`）：

| 情形 | 判定 | `--strict` |
|---|---|---|
| 在清单内，且 `since <= date <= until` | 已登记 | **放行**（rc=0，stderr 打印放行项） |
| 不在清单 | 未登记 | 阻断 rc=1 |
| `date > until` | **过期** | 阻断 rc=1 |
| `date < since` | 不在窗口 | 阻断 rc=1 |
| 只写表名、无 `since`/`until` | 视为无效登记 | 阻断 rc=1 |
| 登记文件不存在 / JSON 损坏 | 空清单 | **全阻断** rc=1（fail-closed） |

三条设计取舍：

1. **必须带到期日**。只给表名的登记被显式判为无效 —— 这是刻意的，防止「加个名字就永久放行」。续期必须改文件，留 diff 痕迹。
2. **缺文件宁可全红**。`load_known` 遇损坏/缺失返回 `{}`，默认阻断，绝不默认放行。
3. **只登记根因已定位的缺口**。`limit_list_d` 登记里写清了根因（`os.path.exists` 判存在 → 空壳永久跳过 + 06:3x 盘前采当天）和 `owner_action`（到期前二选一：修采集器回补，或降级为永久缺口并改造下游）。

当前登记两项，窗口均到 `20261113`（下周五）：

| 表 | since | until | 性质 |
|---|---|---|---|
| `limit_list_d` | 20261104 | 20261113 | 采集器 BUG 导致空壳；本工具不读它，宽度口径不受影响 |
| `index_daily` | 20261105 | 20261113 | 缺当日；按契约不回退昨日，`index` 段置空 |

## 七、重要更正：`index_daily` 不是「缺数据」，是 T+1 节奏

上午我把它记成「缺 11-05 当日」，并据此写了登记 reason。**这个定性错了。** 查落盘时间后：

| 文件（数据日） | 落盘时间 | 延迟 |
|---|---|---|
| d_20261026 | 10-26 21:37 | 当天 |
| d_20261027 | 10-28 20:30 | T+1 |
| d_20261028 | 10-30 02:08 | T+2 |
| d_20261029 | 10-30 02:08 | T+1 |
| d_20261030 | 10-31 20:49 | T+1 |
| d_20261102 | 11-02 23:19 | 当天 |
| d_20261103 | 11-04 20:30 | T+1 |
| d_20261104 | 11-05 20:30 | T+1 |

最近 8 份里 **6 份是 T+1 或更晚**。结论：`index_daily` 采集器按 T+1 跑，
`d_YYYYMMDD` 的指数数据要到**次日 20:30** 才落盘。

后果比「缺一天」严重：

- **当日盘后分析永远拿不到当日指数** —— 不是偶发降级，是工具与数据节奏的结构性错配。
- 因此「补 11-05 的 index_daily」**无效**，明天照缺 11-06 的。v1 待办第 3 项据此**作废**。

已把 `known_degraded.json` 的 `index_daily.reason` 改写为真实根因，`owner_action` 改成二选一：

1. 调度改到**次日 20:40** 跑前一日（此时 `daily` 与 `index` 都齐）—— 推荐，不动契约；
2. 若必须当日出报告，则放开「index 允许 T-1 并显式标注 `as_of`」—— **契约变更，需老田裁定**。

补充一个对调度设计有约束的事实：`daily` 是**当天 20:30** 落盘，`index_daily` 是**次日 20:30**。
两个采集器口径不一致 —— 同一个「盘后分析」没法在同一时刻同时吃到两者。
