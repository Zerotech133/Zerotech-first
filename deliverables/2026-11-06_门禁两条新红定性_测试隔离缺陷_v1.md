# 门禁两条「新红」的定性：都不是回环禁代理改出来的 v1

> 2026-11-06 23:5x–00:2x｜fast 门两轮，第二轮复跑中
> 结论：两条都**与 safe_urlopen 回环禁代理无关**，是测试隔离缺陷 + Windows 文件锁竞争。
> 但两条都不是「随手 flaky」，各有明确机制，需修。

---

## 一、失败 1：`test_submit_concurrent_windows_spawn_processes`

```
E   PermissionError: [Errno 13] Permission denied:
    'C:\Users\t\AppData\Local\Temp\pytest-of-t\pytest-19658\test_submit_concurrent_windows0\.inbox_gateway.lock'
E   assert False
E    +  where False = all(<genexpr ...>)
agent_platform\tests\test_inbox_gateway_lifecycle.py:330: AssertionError
```

**机制**：该用例 spawn 4 个真子进程（`subprocess.Popen` + `PYTHONPATH` 自举），
四个进程同时对同一个 `.inbox_gateway.lock` 做 open —— 这正是它要验证的「跨进程同键互斥」。
在 Windows 上，当别的进程短暂持有该文件时，`open()` 直接抛 `PermissionError`（不是阻塞等待），
子进程记账 `returncode != 0`，父进程 `assert all(...)` 红。

**与本次改动无关**：该文件零命中 `urlopen` / `safe_urlopen` / `proxy` / `8091`。
机制是最小粒度文件锁在 Windows 上的语义差异，跟 HTTP 客户端不沾边。

**证据**：门禁自己的重试轮 `test_gate_agent_key_20261107_001554.log` → **732 passed, 3 skipped**。

**修法方向（未做）**：
- 锁获取改成带超时的重试（`msvcrt.locking` 或 open+retry-N），而不是裸 `open('a')`；
- 或者把断言从「子进程 returncode 必须 0」放宽为「4 个里有且仅有一个 replayed=False」——
  互斥语义才是被测对象，子进程是否因抢锁报错不是。

## 二、失败 2：`test_minute_result_rejects_mode_downgrade[old_path-damaged_params2]`

用例**本身通过**，挂在 teardown：

```
E   AssertionError: default JobSpec catalog changed
E   assert (True, 'db697...1535275135300) == (True, 'db697...1518247924500)
E     At index 2 diff: 1793981535275135300 != 1793981518247924500
portal\tests\test_api_backtest_minute.py:173: AssertionError
```

fixture 在用例前后对**生产** `data/runtime/minute_job_specs.json` 取指纹，断言"没被动过"。

**证据链（逐位对上）**：
- 断言里的"事后"值 `1793981535275135300`，与此刻磁盘上的
  `os.stat('data/runtime/minute_job_specs.json').st_mtime_ns` **完全相同**；
- 该文件 mtime = `2026-11-07 00:12:15`，而门禁是 `00:12:09` 启动的 —— 落在 portal 套件执行窗口内；
- 之后 3 次采样 mtime 不再变化 → 一次性写入，不是持续写。

**谁写的**：`portal/api_backtest_minute.py`（8091 在线服务）或同套件的
`test_minute_router_process_restart.py`（**门禁已登记的 flaky**，会起真实 router 进程，
那个进程持的就是生产 catalog）。

**与本次改动无关**：该测试文件零命中 `urlopen` / `safe_urlopen` / `proxy`。

**修法方向（未做）**：
- 该 fixture 的隔离只挡住了「本用例自己写生产目录」，挡不住**别的进程**写；
  断言生产文件指纹不变，本质是把「环境安静」当成前置条件。
- 正解：把 production catalog 路径也重定向到 tmp（本用例已对 `catalog` 做了，但 default 路径
  仍被真实进程持有），或改成断言「本用例没有写它」（hook 记录写调用），而不是比对 mtime。
- 附带问题：`test_minute_router_process_restart` 起真实进程会污染同套件的其它用例，
  与自身在 known_flaky 名单里互为因果。

## 四、为什么不按「并发假红」四个字了事

47609c4f5 的教训：当时也是「隔离必过、门禁偶红」，若按 flaky 登记就永远挖不到
「回环请求被代理劫持」这个真因。所以这次逐条查到机制层：

- 失败 1 的机制是 Windows 文件锁 `open()` 的 `PermissionError` 语义，**可复现、可修**；
- 失败 2 的机制是**跨进程共享生产文件**，可用 mtime 逐位比对定位到具体时刻，**可证伪**。

两条都不是「不知道为什么会红」，因此不该进 flaky 名单，应各自修掉。
