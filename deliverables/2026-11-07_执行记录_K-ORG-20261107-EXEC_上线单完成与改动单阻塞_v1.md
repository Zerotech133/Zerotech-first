| `Schedule.Service` COM（`RegisterTaskDefinition`） | **被安全策略拦**（`COM object instantiation can run arbitrary code`） |

### 4.2 根因不是"我选错命令"，是任务的权限模型

```
任务文件 ACL（三个任务完全一致）：
  DESKTOP-ARF447U\t | Read, Synchronize | Allow | inherited=False
  BUILTIN\Administrators | Write, ... | Allow | inherited=True
```

对 `t` 的**显式**（非继承）授权只有 **读**。任务对象的 SD 在注册时按此固化，所以
任何**修改**（改 Action / 改 Settings / 重注册）都需要管理员令牌。

再纠一条我先前写错的判断：V1 改动单说"宿主是 S4U + RunLevel=Limited，所以不需要管理员"——**不成立**。
`t` 其实**是**管理员组成员（`DESKTOP-ARF447U\Administrator`、`DESKTOP-ARF447U\t`），
现在只是 UAC 过滤后的非提权令牌（所以 `IsInRole(Administrator)` 判否、`$id.Groups` 里也没有 544）。
结论：**一次 UAC 确认就能改，不用另找管理员账号**。

## 五 9899 的决策（你问的第 3 件事）

**结论：不压缩 `guard_cow` 的 60s 宽限，改为在 `main()` 入口设一个全局预算 `BUDGET_S=100s`（monotonic 截止时刻），到期收缩宽限 / 跳过后续守卫。**

为什么否掉"宽限压到 30s 再并入"（V1 的建议）：

1. 压宽限不解决根因。真病根是"**任一守卫都能吃满自己的宽限，串行叠加**"，不是"cow 的宽限太长"。
   只要新增第五个端口，30s 版本照样会顶爆——是结构问题，不是参数问题。
2. 压宽限会**新增假信号**：CowAgent 冷启慢（venv + app.py）时，30s 处会打 `REVIVE_FAIL`，而进程其实还在起来。
   这跟本仓反复吃过的亏是同一类（K-PUSH-004：被强杀留不下原因）。
3. 全局预算不弱化任何单口判据：只有真的快到点，才缩短后面守卫的宽限；正常一跳（端口都活着）开销仍是 ~10ms。

实测最坏形态（替身时钟 + 替身 Popen，不产生真进程）：

```
模拟总耗时 = 99.0s (BUDGET_S=100, 任务上限 PT3M=180s)
spawn 次数 = 4
picks_sched:8095 DOWN x2 -> spawn / REVIVE_FAIL(15s)
km_hub:8099     DOWN x2 -> spawn / REVIVE_FAIL(15s)
push_admin:8097 DOWN x2 -> spawn / REVIVE_FAIL(15s)
cow             DOWN x2 -> spawn / REVIVE_UNCONFIRMED（预算耗尽，已 spawn 未确认）
```

同一轮在**没有**预算时是 132s（3×18 + cow 60 + 探针）——**必然撞 PT2M**。所以预算不是优化，是四口能共存的前提。
