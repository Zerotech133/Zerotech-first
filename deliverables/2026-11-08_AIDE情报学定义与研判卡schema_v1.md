# AIDE 情报学定义 · 五要素口径 · 研判卡 schema（v1）

> 2026-11-08 · 定稿件 · 对应任务：AIDE 定义落文档（2→3→1 中的「1」）
> 本文只定「是什么」与「怎么算」，不含代码实现细节；实现与实测见 §7、§8。

---

## 1. 一句话定义

> **AIDE 是情报研判引擎，不是量价分析师。**
> 它以「事件」为原子单位，把每条事件拆成 **人、地、事、物、组织** 五要素，
> 再在要素之间建三类关系——**时间关系**（先后、并发、周期、滞后）、
> **空间关系**（地域、板块、产业链环节）、**关联关系**（同实体、同事件链、
> 同信源）。研判产物不是「这段走势怎么样」，而是
> **这张要素-关系网在当前时点意味着什么、下一步该盯哪里**。

### 1.1 与旧定位的差别（必须写清，否则会退回老路）

| 维度 | 旧（jev_interpret v1） | 新（AIDE v2） |
|---|---|---|
| 角色自述 | 「你是资深 A 股量价分析师」 | 「你是情报分析员，不是行情解说员」 |
| 原子单位 | 行情窗口（30 日 K 线） | **事件**（13.7 万条已判新闻） |
| 输入 | 形态 / 量价 / 消息计数 | 事件 × 五要素 × 三类关系 |
| 输出 | 形态 / 量价 / 消息验证 / 结论 | 事件面 / 时间线 / 空间面 / 关联面 / 研判 |
| 时间性 | 只统计「事件后 3 日同向概率」 | 事件的先后、节奏、间隔、密集爆发 |
| 空间性 | 无（仅 scope 的 us/cn/hk 粗粒度） | 地域 + 板块 + 产业链环节，影响扩散层级 |
| 关联性 | 无 | 同实体 / 同事件链 / 同信源的印证或背离 |

> 一句话：旧的回答「这股票怎么走的」，新的回答「这摊事在往哪儿走」。

## 2. 五要素口径（v0，保守版）

设计原则：**宁可少抽，不可错抽**。错的要素会污染关联关系，比没有更糟。

| 要素 | 代号 | 抽取依据 | v0 覆盖（全量 13.76 万条实测） | 已知局限 |
|---|---|---|---|---|
| 组织 | `org` | A 股公司名（`stock_names.name2code`，11,682 条含别名，trie 最长匹配）+ 机构名（部委 / 交易所 / 央行 / 协会 / 研究院，45 条） | **36.3%** 有命中 | 只认名录内实体；海外公司（宝马、英伟达）抽不到 |
| 地 | `place` | 省级行政区 34 + 主要城市 100 + 国家地区 45 + 特殊经济区 12 | **42.4%** | 抽的是「文本提及地」而非「事件发生地」，一篇多地时会全收（上限 6） |
| 事 | `event` | 9 类事件词表（见 §2.1），正则命中计票取最大 | **31.3%** 命中 9 类，其余 `other` | 海外政治/宏观新闻也会被套进公司事件类，需靠 `scope` 过滤 |
| 物 | `thing` | 产品 / 技术 / 资产类别概念词（内置 150 条） | 见 §7 抽样 | 词典外的新概念抽不到 |
| 人 | `person` | **V0 只抽角色，不抽人名**：董事长 / 总经理 / 实控人 / 董秘 / CEO 等 20 个角色词 | 角色命中率高，人名 0 | 人名识别无 NER 时误报过高（「张江高科」里也有「张」），留到 v1 |

### 2.1 九类事件

`业绩` / `并购重组` / `融资` / `股东治理` / `经营订单` / `监管风险` / `分红` / `研发产品` / `政策宏观`

关键词一律取「专指名」而非泛词（用「净利」不用「利润」），降低串类。
全量分布见 §7.2。

### 2.2 「人」为什么 V0 不做人名

三个理由，都来自实测：

1. 无 NER 时中文人名与地名、公司名高度混淆（「张江」「王庄」）；
2. A 股新闻里人名极少单独出现，多与角色绑定（「董事长王某某」），
   而**角色本身**才是可跨事件关联的稳定实体；
3. 角色抽取零误报，人名抽取误报率目测 >30%，得不偿失。

结论：v0 用「角色」当「人」的代表，v1 接 NER 后再补真名。

## 3. 三类关系（关系层口径，本版只定定义，计算在下游）

| 关系 | 定义 | 判据 | 典型问题 |
|---|---|---|---|
| **时间关系** | 事件在时间轴上的排布 | 相邻事件间隔 Δt；同日内事件数（密集爆发）；事件距价格拐点的滞后天数 | 「先出消息还是先跌？」「利好是集中来的还是慢慢来的？」 |
| **空间关系** | 事件在产业/地域空间上的落点 | `place` 集合；`org` 所属行业；`thing` 所属概念/产业链环节 | 「这事只影响一家，还是整条链？」「是国内还是海外？」 |
| **关联关系** | 要素之间的印证或矛盾 | 同 `org` 跨事件；同 `source` 的方向一致性；事件方向与价格方向是否背离 | 「这波利好是谁在说？说的人准吗？」「消息和价格为什么打架？」 |

**关系不进 v0 的实体表**，而是在研判时实时聚合（`_facts()` 内做）。理由：
关系随窗口变化（30 日 / 5 日不同），落表会立刻过期，反而制造脏数据。

## 4. 研判卡 schema

### 4.1 卡片正文（五段固定结构）

| 段 | 内容要求 | 反例（不算合格） |
|---|---|---|
| 【事件面】 | 窗口内发生了什么，按类型归类，**点出最关键的一两个事件** | 「事件 60 个，利多 58 利空 0」（只有计数） |
| 【时间线】 | 先后与节奏——谁先动、谁跟随、间隔多久、有无密集爆发 | 「事件后 3 日同向概率 100%」（只有统计量） |
| 【空间面】 | 涉及哪些地域 / 板块 / 产业链环节，影响扩散在哪一层 | 「涉及上海、广州」（只列地名不判层级） |
| 【关联面】 | 事件彼此之间、以及与价格之间的印证或背离 | 「消息与价格背离」（不说哪个消息、怎么背离） |
| 【研判】 | 态势定性 + **一个具体观察点** | 「建议谨慎操作」（不是观察点） |

### 4.2 落库表 `intel_briefs`

```sql
CREATE TABLE intel_briefs (
    code         TEXT NOT NULL,   -- 标的代码（带后缀，如 300750.SZ）
    trade_date   TEXT NOT NULL,   -- 生成日 YYYY-MM-DD
    kind         TEXT NOT NULL,   -- 卡类型，v0 仅 'story'
    name         TEXT,            -- 标的简称
    tier         TEXT,            -- 池内分层 T1/T2/T3
    facts        TEXT,            -- 喂给模型的完整事实摘要（可复核）
    conclusion   TEXT,            -- 五段研判正文
    engine       TEXT,            -- local / cloud / rule
    engine_label TEXT,
    model        TEXT,            -- 如 gateway:deepseek/deepseek-flash
    degrade_note TEXT,            -- 降级原因（可审计）
    datasig      TEXT,            -- facts 的 sha256 前 16 位（增量判据）
    built_at     TEXT,
    PRIMARY KEY (code, trade_date, kind)
);
```

**`facts` 必须落库**：研判结论可以重生成，但如果不知道当时喂了什么，
就无法判断「结论错了是数据错还是模型错」。这是可审计的底线。

### 4.3 读取契约

```
GET /api/jev/interpret?kind=story&code=300750&days=30&peek=1
    → 只读沉淀卡；命中返回卡，未命中返回 {ok:false, peek:true}
    → 绝不触发推理（前端打开页面时用它，避免把用户拖进 100 秒等待）

GET /api/jev/interpret?kind=story&code=300750&days=30
    → 先读沉淀卡（命中即 0 延迟）；未命中或 days≠30 才在线推理

GET /api/jev/interpret?kind=story&code=300750&refresh=1
    → 跳过沉淀，强制重算（用户点「重算」时用）
```

有效期：`trade_date` 距今 **≤1 天**才认（隔日标 `stale=true` 但仍展示）；
超过 1 天视为过期，回落在线重算——**宁可慢，也不给用户看失效结论**。

## 5. 时点纪律：什么时候算

| 时点 | 动作 | 范围 | 依据 |
|---|---|---|---|
| 盘后 15:45 | 预生成当日研判卡 | **L1**：T1+T2（约 32 只） | 收盘后当日事件与行情都已定 |
| 夜间 01:00 | 补跑 L2 | T3（约 738 只） | 云端通道可用时才跑；本机串行约 2.8 小时 |
| 盘前 08:30 | 增量重算 | 昨日 15:45 后有新事件的标的 | `datasig` 变了才重算，否则跳过 |
| 用户浏览 | 读沉淀（0 秒） | 全部 | —— |
| 用户点「重算」 | 在线推理 | 单只 | 用户明确要最新 |

分层依据直接复用关注池自带的 `tier` 字段（`todays_picks.json`）：
`T1_resonance` / `T2_high_value` → L1；`T3_single` → L2。

## 6. 为什么必须「提前算」而不是「点开再算」

实测（2026-11-08，本机 AMD 8060S 核显，无独显）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 数据聚合 `_facts()` | **13.53s**（改前）→ **1.42s**（改后） | 见 §7.1，慢在 parquet 元数据扫描，不在 SQL |
| 本地 Ollama qwen3.5:4b 推理 | **>151s**（超时未完成） | 单条研判跑不完，必然降级规则结论 |
| 本机 LLM 门面 deepseek-flash | **11.9s ~ 17.8s** | 走 `agent_platform/gateway/llm_gateway`，云端模型 |
| 读沉淀卡 | **0.003s** | 直接查库 |

关注池 770 只：

- 本地串行 = 770 × 151s ≈ **32 小时** → 不可能；
- 门面串行 = 770 × 13s ≈ **2.8 小时** → 夜间可行；
- L1 32 只 = **约 7 分钟** → 盘后跑完，用户下班前就能看。

结论：**「提前算」+「云端模型」不是二选一，是同一件事的两半**——
提前是时点，云端是算力。

## 7. 落地实测（本轮已完成）

### 7.1 修掉 13.53s 的「慢 SQL」——其实慢在 parquet 元数据

`cProfile` 结论：`story.compute` 12.27s 里 **10.20s 花在 `datamart._read_part`**，
其中 `_part_stats_days` 被调用 **8,789 次**、构造 pyarrow `ParquetFile`
**7.13s**。SQL 本身只 0.30s。

即：查单只股票 30 天日线，却要把 **8,749 个 `d_YYYYMMDD.parquet` 日分片**
逐个打开读元数据，只为知道每个分片覆盖哪几天。

两处修复（`quant_backtest/datamart.py`）：

1. **文件名剪枝**：`d_20260101.parquet` 的名字本身就是日期，先按名剪掉
   「文件名日期 < start」的分片。语义安全前提：补采只把旧数据写进新文件，
   不会把新数据写进旧文件，故早于 start 的分片必不含目标区间；
   end 一侧不按名剪（新分片仍可能含区间内补采行），照旧走读后过滤。
   8,749 → 数十个。
2. **元数据缓存**：`_part_stats_days` 按 `(路径, mtime, size, 列)` 进程内缓存，
   分片发布后不再改写，mtime/size 变了才重读。

效果：**13.53s → 1.42s（冷）/ 0.71s（热）**，19 倍；结果逐字一致。

### 7.2 修掉 `event_type` 空读

`api_jev_story.py:115` 读 `j.get("event_type")`，但 `jev` JSON 里**从来没有
这个字段**（抽样 4 万条，`event_type` 全为 None），故「类型分布」永远只有
`other×N`。改读情报要素库后，全量分布：

|---|---|---|---|
| other | 94,562 | 经营订单 | 4,014 |

| 政策宏观 | 5,503 | 并购重组 | 1,697 |
| 监管风险 | 4,528 | 分红 | 475 |

        宁德时代相关30个，及11/1比亚迪销量49.02万辆（conf0.85）。

        澳大利亚、兰州、厦门；品种储能13、机器人6、动力电池5，扩散在储能/电池链及海外。
【关联面】产业利多与-15.8%回落背离；证实率38%、证伪29，利多数量多而可信度低；
        交易所公告最可信；事件后3日同向100%仅支持短窗，最大量能日放量下跌显示分歧。
【研判】定性：利多堆积、价格不认的背离下行。观察点：220.41低点得失及反抽量能，

对照 §4.1 的五段要求：时间线有间隔（10 天）与节奏（2 个/日），空间面判了
扩散层级（储能/电池链及海外），关联面指出了具体矛盾（利多数量多但证实率 38%），
研判给了可验证的观察点（220.41 得失）。**这是情报学口径，不是量价口径。**

## 8. 遗留与风险（不藏）

1. **云端依赖单点**：`deepseek/deepseek-flash` 是本轮唯一实测可用的云端通道。
   `glm/glm-5.3` 2026-11-08 实测 **429 限流**，`openai/gpt-6.0`（OpenClaw 载体）
   实测 **33s**（慢但通）。`config/cloud_llm.json` 仍是模板占位（`enabled=false`），
   没接真实 key。**若 deepseek 通道断，预生成会整批掉到规则结论。**
2. **门面偶发失败**：同一天两次试跑，一次 65s 后落 rule，一次 11.9s 成功。
   加重试后 L1 批量实测 **33/33 全 cloud、0 落 rule**，但样本只有一批，
   连续跑几晚才能确认稳定性。
3. **`place` 是「文本提及地」，不是「事件发生地」**。《人民日报》头版类新闻会
   抽出 5 个地名，全部与事件无关。v1 需要「地名 + 事件动词」的位置约束。
4. **`thing` 词典只有 150 条**，新概念（如 2026 年新出的产业词）抽不到，需定期扩。
5. **人名完全未做**，见 §2.2。
6. **关系层未落表**，每次研判实时聚合，30 日窗与 5 日窗各算一遍。若将来做
   「跨标的关联」（A 公司的供应商 B 也发事件），必须落图，当前架构不支持。
7. **计划任务未注册**：`start_intel_brief_pregen.ps1` 只写好了，注册命令见脚本
   注释。系统级改动需老田批准，本轮不自注册。
