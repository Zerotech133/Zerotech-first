## 一、判决性实验：不是推理，是实测

同一个本机 HTTP 服务（临时起的 `127.0.0.1:<随机>`），只改代理环境，四段对照：

| 组 | 条件 | 结果 |
|---|---|---|
| C1 | 无代理 | **200 成功** |
| C2 | `HTTP_PROXY=http://127.0.0.1:<死端口>`，无任何豁免 | **URLError 失败** |
| C3 | 死代理 + `no_proxy=127.0.0.1` | **200 成功** |
| C4 | 死代理 + `ProxyHandler({})` | **200 成功** |

环境事实：

```
HTTP_PROXY              = http://127.0.0.1:55478   （每会话临时端口，今天已变过三次）
proxy_bypass('127.0.0.1')      -> False
proxy_bypass('127.0.0.1:8787') -> False
getproxies()            = {'http': '...55478', 'https': '...55478'}
```

C2 是判决点：**如果回环被豁免，代理死了也该成功；它失败了，说明回环请求被判给了代理。**

复现：`python -X utf8 tools/research/proof_loopback_proxy.py`

## 二、为什么这等于「假警报」

代理一转手，探活的结论就从「服务活不活」变成「代理通不通」：

- 代理挡死 → 全套本机服务被误判宕机；
- 代理活着但拒转 → 代理返回的 **502 被当成服务返回的 502**（47609c4f5 就是这么红的）。

今天探针还是绿的，**只是因为当前代理恰好是 transparent 型（MCP 配置里 `transparent_proxy: true`）会转发回环**。换个严格代理、或代理重启换端口、或代理进程被别的工具抢占，探针立刻集体报「服务挂了」。

## 四、静态清点：口径与一个必须说明的局限

**口径**：只扫 git 跟踪文件。仓库工作区里另有约 28 万个未跟踪 `.py`（venv/依赖树），
对它们做 AST 解析会把进程直接打死（实测 SIGTERM），且它们不是我们的代码。

扫描器：`tools/research/scan_loopback_urlopen.py`（BFS 有界表达式溯源，判据三条：
有 urlopen 调用 → 目标可静态追溯到回环字面量 → 无任何代理旁路机制）。

```
跟踪 py 文件            4835（跳过 data/archive 后实扫 4831）
含 urlopen 的文件        234
urlopen 调用点           352
  ├ VICTIM（回环 + 无旁路）  147 调用 / 96 文件
  ├ GUARDED（回环但有旁路）    3
  ├ SUSPECT（0.0.0.0 / 间接）  0
  └ EXTERNAL（外网，走代理是本意）202
```

**局限（重要）**：静态扫描**看不见配置里的地址**。四个探针的调用参数是 `url`/`req`，
地址来自 `agent_platform/config/*.json`，扫描器把她们全判成 `EXTERNAL`——
所以**探针本身不在那 147 条名单里**，但它们是实打实的受害方（见第三节实测）。
配置侧另有 4 个文件带回环地址：`service_probe_targets.json`(7)、`quality_scale.json`(5)、
`interop_h0.json`(3)、`data_pipeline_targets.json`(1)。

## 六、已修：共享入口（覆盖 108 个引用文件）

`safe_urlopen.py` 6 份副本（`agent_platform` / `tools` / `portal` / `quant_backtest` /
`k_stock.paper` / `news_collector`）统一加入：

- `is_loopback()`：`127.0.0.0/8`、`::1`、`localhost` 系、`0.0.0.0`；
- `_NO_PROXY_OPENER = build_opener(ProxyHandler({}))` + `_open_no_proxy()`；
- 回环走空 handler，**非回环仍走 `urllib.request.urlopen`**——代理、证书、超时语义原样，
  只掐掉本机这一跳；
- `context=` 调用（`portal/policy_geo_collector.py` 公网降级路径）改由 `HTTPSHandler` 承接，行为不变。

修在共享入口而不是逐点改，是因为全仓 **108 个文件**引用 `safe_urlopen`；逐点改既漏又散。

回归：`tools/tests/test_safe_urlopen.py` **6 passed**，其中
`test_loopback_survives_dead_proxy_env` 是真起服务 + 死代理的判决性用例——
把回环分支删掉即红。

## 九、遗留与建议

1. **7.1 那 21 处建议优先做**：改动机械（`urlopen(req)` → `safe_urlopen(req)` + import），
   但每处要确认该脚本的执行上下文能否 import 到 `safe_urlopen`（脚本直跑 vs 包内导入路径不同）。
   建议按目录分批、每批跑对应测试，不一次性替换。
2. **不要让修复依赖代理行为**。transparent 代理今天替我们兜住了回环，这是运气，不是设计。
3. **`api_health_portal` 是元问题**：它本身就是健康聚合入口，自己被代理劫持时会
   把「代理不通」报成「多个服务同时挂了」——最容易误导排障的一处。
4. 静态扫描器把配置驱动型调用判为 EXTERNAL，是已知盲区；若要常规化，
   需补一层「读 config JSON 里的 URL」的解析。
