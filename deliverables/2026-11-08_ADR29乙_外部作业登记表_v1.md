## 2. 为什么「只填表」不够：两个判据缺陷

填表本身只是把路径列进白名单。但本轮实测发现，**即使路径全登记，旧判据仍有两条会把它判红**，所以顺带修了判据（不放宽 unknown）：

**缺陷 A：隔离改名保留原 mtime，mtime 判据必杀**
s11 影子台账把过期档改名成 `ledger.stale_20261030.jsonl` / `positions_20261030.stale.json`，`os.replace`/`shutil.move` **保留原 mtime = 2026-11-01T23:16:48**，早于基线 07:04:43。旧逻辑「mtime ≤ baseline 一律不归因」→ 作业每做一次 `.stale` 隔离，门禁必红一次，且红得毫无信息量。

**缺陷 B：tracked 文件被作业改名后，`isfile` 必为假**
`research/shadow/s11/positions_20261030.json` 在 git 里是 `D`（已删），原档改名成 `.stale.json`。旧逻辑先 `os.path.isfile(full)`，删掉的路径直接返回「无归因」——**外部作业的合法改名被当成未归因变更**。

修法：登记表条目标记 `("backdated",)` 的，允许「旧 mtime + 登记命中」；登记命中但本机已无文件的，按「作业改名/删除」留痕。两条都只在**已登记路径**上生效，未登记路径照旧判 FAIL。

## 6. 残留风险（5 条，都写下来不藏）

1. **登记路径被删也放行**：档 ③ 对已登记路径一律认「作业改名」，所以若有人删掉 `research/shadow/*/positions_*.json`，门禁不会告警。范围被登记表限死，但这是真实的口子。
2. **`research/shadow/` 按根登记 + `backdated`**：代价是该目录下任何「旧 mtime 新文件」都会被认成隔离改名。可接受的前提是**该目录只放台账数据**（已核：baseline/selection/s08/s10/s11/s12，无代码无配置）；一旦有人在里面放代码或配置，这个口子就变大了。
3. **`quant_backtest/tests/` 的 `test_xq_` 前缀较宽**：该前缀下任何新测试文件都会自动归外部域。属「同一作业的测试面」，可接受，但作业收工后必须退役。
4. **弱归因 1 例仍在册**：`agent_platform/catalogs/strategy_registry.json` 靠内容指纹 `factor_lib` 命中（只读前 8 KiB）。该文件是策略注册表，被 `factor_lib` 字样命中属巧合级证据，未在本轮改动范围内，建议下轮改精确登记。
5. **登记表本体未入仓**：`C:\Temp\governance_zero_state_baseline.py` 不在 git 里（W-08 基线也一直在 Temp）。入仓会立刻触发 G-09c「新增 tracked 未归因」，需先裁定是登记进 `GOV_W` 还是新建 `tools/governance/` 域——本轮不擅自做。
