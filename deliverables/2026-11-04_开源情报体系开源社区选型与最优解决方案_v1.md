- 日期：2026-11-04
- 作者：老田的AI助手（Agent 调研 + 代码核对）
- 数据核验：GitHub API 实测 + 官方文档 + 本地 `osint_video/store/schema.sql` 逐表核对
- 前置输入：《2026-11-04_开源情报体系设计开发文档重新汇总_v1》《情报工厂子项目规划_20261018》
- 结论前置：**不引入任何重型情报平台。缺的不是平台，是"事件"这一层。**

## 0. 一页结论

调研了开源社区 14 个候选项目（情报平台 4 个、采集 4 个、抽取 2 个、实体/事件 4 个），核对了 star、许可证、部署依赖与维护状态，结论是：

| 判断 | 内容 |
|---|---|
| **平台层** | OpenCTI / MISP / Aleph / AIHOT **全部不可直接部署**。不是产品不好，是宿主环境与许可证的硬否决（见 §1）。 |
| **真实缺口** | 现有 schema 是 `resource → knowledge_unit(fact) → evidence` 三层，**中间缺 `story`（事件）层**。这就是 10-17 报告里 F2「采了没人吃」的物理成因：下游只能拿到散点事实，拿不到"今天发生了哪几件事、几家在说"。 |
| **最优解** | 在现有 PostgreSQL 上补 2 张表（`osint_story` + `osint_story_member`），算法借 AIHOT 的 article→fact→story 三层与四关系判定，**总代码改动约 1 个模块 + 1 处消费改造**。 |
| **只引入 4 个零件** | trafilatura（抽取）、bge-m3（嵌入）、followthemoney（实体 schema 参考）、changedetection.io（长尾源）。全部 MIT / Apache-2.0，全部 `pip install` 级接入，零容器依赖。 |
| **刻意不引入** | Crawlee（Node 栈）、Splink（场景不匹配，见 §3.4）、MediaCrawler（许可证禁商用）、OpenCTI 全家桶。 |
| **优先级** | P0 先做事件层闭环（1 周可验收），扩源放 P2。顺序反了就是继续往漏斗里倒水而不接出口。 |

一句话：**你缺的不是情报平台，是一个把"事实"聚成"事件"的算子。**

## 1. 平台层：四个候选的硬否决

### 1.1 实测数据（2026-11-04 核验）

| 项目 | Stars | 许可证（实测） | 语言 | 最近推送 | 部署依赖 |
|---|---|---|---|---|---|
| OpenCTI | 10,257 | `NOASSERTION`（Filigran 双许可，非纯 Apache） | TypeScript | 2026-11-04 | ES + Redis + RabbitMQ + MinIO，官方要求 Docker/K8s |
| MISP | 6,619 | AGPL-3.0 | PHP | 2026-10-23 | LAMP 单体 |
| Aleph / OpenAleph | — | 开源（OCCRP） | Python | 活跃 | ES/OpenSearch + PG + Redis + Docker |
| AIHOT | ~8.8–9.3K | **MIT** | TypeScript | 2026-10-27 | Node 24 + PG 17 + pg-boss + Docker Compose |
| MediaCrawler | ~70K | **NCAL 1.1（禁商用）** | Python | 活跃 | Playwright + Chrome |
| trafilatura | — | **Apache-2.0**（≥1.8.0） | Python | 活跃 | 无 |
| followthemoney | 113 | **MIT** | Python | 2026-10-23 | 无（需 pyicu） |
| Splink | — | **MIT** | Python | 5.0.0 / 2026-09-28 | DuckDB 内置 |
| RSSHub | 46.8K | MIT | TypeScript | 活跃 | Node |
| changedetection.io | 35.5K | Apache-2.0 | Python | 活跃 | 可选 Playwright |

### 1.2 为什么 OpenCTI 装不上（决定性的三条）

1. **OS 层否决**：OpenCTI 依赖 Elasticsearch。ES 7.17 是最后一个支持 CentOS 7 的分支且已停止维护；ES 8 要求 glibc ≥ 2.28，而 CentOS 7.4 是 glibc 2.17。**升级 OS 才能装，不是调参能解决。**
2. **容器层否决**：官方生产部署只推 Docker Compose / K8s。生产机无 docker，且 `download.docker.com` 出网不通、CentOS 7 已 EOL，装 docker-ce 这条路本身是死的。
3. **模型层否决**：OpenCTI 数据模型深绑 STIX 2.1（threat actor / malware / ATT&CK）。金融与产业情报套 STIX 等于把数据层和前端全部重写——**接进来一个平台，付出的是重构整套契约的代价**，与"设计层已收敛、不要再写第 14 份方案"的现状直接冲突。

> 资源不是瓶颈（62GB 内存 / 20 vCPU / 2TB 数据盘足够跑 6C16G 的要求）。**是操作系统和许可证把门关上了。**

### 1.3 为什么 AIHOT 只能借算法不能部署

AIHOT 是本次调研里**与你的需求重合度最高的项目**——它干的就是"多源采集 → LLM 双评 → 同一件事聚成一个事件 → 按独立来源数排热度 → 出日报"，且 MIT 许可、源码与提示词全开。

但它跑在 **Node 24 + TypeScript + PostgreSQL 17 + Docker Compose** 上。Node 20+ 官方二进制要求 glibc ≥ 2.28，CentOS 7 是 2.17——**装不上**。而且它是一个完整的三进程站点（api / worker / web），替换掉你现在整套 Python 契约，收益为负。

**正确姿势：抄它的算法与表结构，用 Python 写在你的栈上。** 这比部署它省 90% 的工作量，还不破现有契约。

### 1.4 为什么 MediaCrawler 只能当教材

70K star、七平台覆盖、CDP 免逆向——工程质量确实高。但许可证是 **NON-COMMERCIAL LEARNING LICENSE 1.1**，明写"仅限非商业学习研究，禁止大规模爬取"。你的平台是要对外交付的产品，**用了就是违约**。README 首屏自己挂着"爬虫违法违规案件"的警示。

**结论：可以读它的分层设计（平台适配层 / 存储层 / 反检测层三解耦），代码一行不要进生产。**

## 2. 诊断：现有 schema 缺的到底是什么

读 `osint_video/store/schema.sql` 全文（410 行，12 张表）后，现有信息流是这样的：

```
osint_knowledge_resource   （一篇文章/一个视频，candidate→reviewed→published）
        ↓
osint_knowledge_unit       （unit_type='fact'，一条事实。带 entities / topics / review_status / truth_status）
        ↓
osint_strategy_evidence    （事实 → 策略的证据边，带 quote / relevance / confidence）
        ↓
osint_index_task           （分发到 pg / qdrant / graph 的 outbox）
```

**这是一条漂亮的"单文档 → 事实 → 证据"链，缺的是横向聚合。**

一篇报道进来，能抽出一条事实；但"财联社 + 东财 + 雪球 + 某公众号 说的是同一件事"这个判断，schema 里没有位置落。于是：

- 下游 `kg_brief` / `event_graph` 拿到的是一堆互不关联的 fact，无法回答"今天最值得看的三件事是什么"
- 无法计算"几家独立来源在说"——而这恰恰是情报价值的第一序信号
- 10-17 报告 F2 记录的 `kg_brief`/`event_graph` 对 xq/guba 消费 grep 0 匹配，**根因不是下游懒，是上游没给出可消费的"事件"粒度**

对照 AIHOT 的三层建模：

| AIHOT | 你的现状 | 差距 |
|---|---|---|
| article（一篇报道） | `osint_knowledge_resource` | ✅ 已有，且更细（带 media 生命周期） |
| fact（一件真实发生的事） | `osint_knowledge_unit` | ✅ 已有，且带 review/truth 状态机 |
| **story（事实 + 直接进展）** | **无** | ❌ **唯一缺口** |

**结论：不需要新架构，需要一张表。**

## 3. 最优方案：四层零件 + 一个 story 算子

### 3.1 总体形态

```
┌─ 采集 ─────────────────────────────────────────────┐
│ 现有 collector + res-downloader-py（不动）           │
│ + changedetection.io   补"无 RSS/无 API"的长尾源     │
│ + RSSHub（可选）       把 5000+ 站点变 RSS           │
└──────────────────┬─────────────────────────────────┘
                   ↓
┌─ 抽取（替换点 A）──────────────────────────────────┐
│ trafilatura ≥1.8  Apache-2.0                        │
│ F1 0.909 / recall 0.904，替掉 newspaper3k 的 0.713/0.593 │
└──────────────────┬─────────────────────────────────┘
                   ↓
┌─ 事实层（现有，不动）──────────────────────────────┐
│ osint_knowledge_unit  unit_type='fact'              │
│ entities JSONB → 按 FTM 子集规范化（替换点 B）       │
└──────────────────┬─────────────────────────────────┘
                   ↓
┌─ 事件层（★ 新建，全部价值所在）────────────────────┐
│ osint_story         事件主体 + 独立来源数 + 热度     │
│ osint_story_member  事件 ↔ fact 归属边（含判定依据） │
│ 判定：bge-m3 召回 → 四关系分类 → 低置信换模复核      │
└──────────────────┬─────────────────────────────────┘
                   ↓
┌─ 消费（改造点 C）──────────────────────────────────┐
│ kg_brief / event_graph / portal 改读 story           │
└────────────────────────────────────────────────────┘
```

### 3.2 事件层：两张表

```sql
-- 事件主体。一个 story = 一件真实发生的事 + 它的直接进展。
CREATE TABLE IF NOT EXISTS osint_story (
    story_id            BIGSERIAL PRIMARY KEY,
    story_key           TEXT NOT NULL UNIQUE,      -- 稳定业务键，供下游引用
    title               TEXT NOT NULL,             -- LLM 归一化后的中文标题
    summary             TEXT,
    first_seen_at       TIMESTAMPTZ NOT NULL,
    last_seen_at        TIMESTAMPTZ NOT NULL,
    independent_sources INT NOT NULL DEFAULT 1,    -- 独立来源数（去重后）
    source_names        JSONB NOT NULL DEFAULT '[]'::JSONB,
    fact_count          INT NOT NULL DEFAULT 1,
    heat                DOUBLE PRECISION NOT NULL DEFAULT 0,  -- 48h 独立来源 + 时间衰减
    stage               TEXT NOT NULL DEFAULT 'emerging',
        -- emerging / developing / peak / fading / closed
    entities            JSONB NOT NULL DEFAULT '[]'::JSONB,   -- 归一化后的实体引用
    topics              JSONB NOT NULL DEFAULT '[]'::JSONB,
    confidence          DOUBLE PRECISION,
    review_status       TEXT NOT NULL DEFAULT 'unreviewed',
    model_version       TEXT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (independent_sources >= 1),
    CHECK (fact_count >= 1),
    CHECK (stage IN ('emerging','developing','peak','fading','closed')),
    CHECK (review_status IN ('unreviewed','reviewed','rejected'))
);
CREATE INDEX IF NOT EXISTS idx_story_heat ON osint_story(heat DESC, last_seen_at DESC);
CREATE INDEX IF NOT EXISTS idx_story_window ON osint_story(last_seen_at DESC, stage);

-- 归属边。一条 fact 只能属于一个 story（唯一约束保证幂等重算）。
CREATE TABLE IF NOT EXISTS osint_story_member (
    story_id     BIGINT NOT NULL REFERENCES osint_story(story_id) ON DELETE CASCADE,
    unit_key     TEXT NOT NULL,
    unit_version INT NOT NULL DEFAULT 1,
    relation     TEXT NOT NULL,   -- same_story / progress / roundup
    similarity   DOUBLE PRECISION,
    decided_by   TEXT NOT NULL,   -- vector / llm / llm_recheck / manual
    rationale    TEXT,            -- 判定理由，供复核与审计
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (unit_key, unit_version),
    CHECK (relation IN ('same_story','progress','roundup')),
    CHECK (decided_by IN ('vector','llm','llm_recheck','manual'))
);
CREATE INDEX IF NOT EXISTS idx_story_member_story ON osint_story_member(story_id);
```

**设计要点（每条都有出处，不是拍脑袋）：**

| 决策 | 依据 |
|---|---|
| `UNIQUE(unit_key, unit_version)` | 保证"一条事实只能挂一个事件"，重算幂等，不会重复计入 `independent_sources` |
| `decided_by` + `rationale` | AIHOT 的做法：判定必须可回溯。人工改过的归属永远优先于模型，且要在数据库行锁内重查 |
| `independent_sources` 独立于 `fact_count` | **同一家媒体发 5 篇不等于 5 个来源**。这是热度的分母，混了整套排序就废 |
| `stage` 五态 | 与现有 `osint_target.operation_state` 风格一致，便于统一状态机审计 |
| 不加 FK 到 `knowledge_unit` | 现有 `strategy_evidence` 用的是复合 FK `(unit_key, unit_version)`；这里用同构写法保持体系一致 |

### 3.3 判定算法：直接抄 AIHOT 的实测结论

AIHOT 的 `group.ts`（864 行）是全仓库工程决策密度最高的文件，几个关键常数都有实测注释，**照抄可省掉你自己试错的两周**：

1. **候选召回**：14 天窗口 + 向量余弦 ≥ 0.6，先粗召回。
2. **四关系判定**（不是二分类）：`SAME_STORY` / `SAME_STORY_PROGRESS` / `UNRELATED` / `ROUNDUP`。作者在 **370 对标注样本**上实测：**用"是非题 + 倾向否"的二分类会拒掉一半的真合并**。这是本条方案里最有价值的一条经验。
3. **低置信复核**：判定说"同一件事"但余弦 < 0.85 的，**换一家模型再读一遍这一对**。两层防错。
4. **人工优先**：人工定过的归属，在行锁内重新检查后永远优先于模型输出。
5. **热度公式**：48 小时窗口内的**独立参与者数**加权 + 时间衰减，不是简单计数。
6. **13 种结局**里值得抄的三种：`roundup`（多话题盘点不建事件）、`historical`（历史不建档）、`signal`（讨论帖走独立路径，不与新闻混聚）。

**落到你这里的实现选择：**

- 嵌入用 **bge-m3**（Ollama 可跑，568M / 1.2GB，中文 C-MTEB 66.1–68.2）
- 判定用现有 LLM 网关，**不要引入新模型服务**
- 提示词从 AIHOT 的 `industry/prompts/group-*.md` 改写（MIT，可商用）

**为什么必须换 bge-m3：** 现用的 `nomic-embed-text` 中文 MTEB 58.3，bge-m3 是 66.1–68.2，**差 8 分**。聚类任务对嵌入质量极其敏感，用弱中文嵌入做"同一件事"判定，余弦 0.6 这个阈值根本立不住。这是 P0 的前置条件，不是优化项。

### 3.4 实体层：不推荐 Splink（这条要说清楚）

社区里"实体消解"最常被推荐的是 Splink（MIT，UK 司法部出品，Fellegi-Sunter 模型，5.0 能 8.5 分钟处理 10 亿行）。但**它不适合你当前的主场景**，理由是官方文档自己写的：

1. **输入形状不匹配**：Splink "最适合标准化的、多列且相关性低的结构化记录"，**明确不推荐单一 bag-of-words 字段**。你的实体来源是 `osint_knowledge_unit.entities` JSONB 里的中文公司名/人名，恰恰是"单列为主的模糊字符串"。
2. **Postgres 后端能力不全**：官方明说 Postgres backend "relatively new，未充分测试性能"，且**因 PG 缺字符串函数，模糊匹配支持不完整**，团队"minimal support"。你在 PG 上硬跑，只会撞上能力缺口。
3. **它是批处理**：Splink 设计为批量跑批，不支持实时增量。你的实体是随采集持续流入的。

**替代方案（按成本从低到高）：**

| 层 | 做法 | 成本 |
|---|---|---|
| 1 | **规则 + 别名表**：`(canonical_id, alias, alias_type, source)`，覆盖股票简称/全称/曾用名/英文名。金融实体 90% 靠这张表解决 | 极低 |
| 2 | **嵌入近邻**：bge-m3 向量 + 阈值合并，只处理规则未命中的 | 低 |
| 3 | **LLM 裁决**：仅对"高价值 + 高歧义"的残差（同名不同公司、跨市场同名）走 LLM，输出带理由 | 中 |
| 4 | Splink | **只在"上市公司多字段"场景用，且必须用 DuckDB 后端**，不要用 PG 后端 |

`schema` 参考 **followthemoney（MIT，113★）**：它把 Person / Company / Asset / Payment / Ownership 定义成带继承的属性体系（Person 和 Company 都有 `registrationNumber`，因为都是 LegalEntity），**属性多值**（一个人多个名字）。这正是你 `entities` JSONB 该长的样子，抄它的 schema 定义，不引入它的运行时。

### 3.5 抽取层：trafilatura 是明确的最优

官方 benchmark（750 文档 / 2236 正文段 / 2250 模板段，2022-05-18，多方独立复现）：

| 库 | Precision | Recall | F1 |
|---|---|---|---|
| **trafilatura (standard)** | **0.914** | **0.904** | **0.909** |
| readabilipy | 0.877 | 0.870 | 0.874 |
| news-please | 0.898 | 0.734 | 0.808 |
| readability-lxml | 0.891 | 0.729 | 0.801 |
| goose3 | 0.934 | 0.690 | 0.793 |
| **newspaper3k** | 0.895 | **0.593** | **0.713** |

**看 recall 列**：newspaper3k 漏掉 40.7% 的正文，goose3 漏 31%。trafilatura 只漏 9.6%。对情报系统，"漏掉四成正文"意味着抽出来的事实本身就是残缺的——**这是上游质量债，会一路传导到事件判定**。

许可证：**≥1.8.0 为 Apache-2.0**（此前版本是 GPLv3+），商用安全。限制：不做 JS 渲染，SPA 页面仍需 Playwright 兜底（你已有）。

## 4. 落地路线（按"先接出口，再扩进口"排序）

### P0：事件层闭环（目标 5 个工作日，可独立验收）

| # | 动作 | 产出 | 验收标准 |
|---|---|---|---|
| 1 | 换嵌入：Ollama 拉 `bge-m3`，重算存量 unit 向量 | qdrant 集合重建 | 抽样 50 对"已知同事件"余弦中位数 ≥ 0.75 |
| 2 | 建 `osint_story` + `osint_story_member` | DDL 上线 | `init_db.py` 幂等重跑通过 |
| 3 | 写 `story_group` 算子（召回 → 四关系判定 → 低置信复核 → 行锁写回） | 1 个模块 | 跑 7 天存量，产出事件数在 unit 数的 15–35% 区间 |
| 4 | 改造 `kg_brief` 读 `osint_story`（按 heat 排序，带 independent_sources） | 消费闭环 | **`kg_brief`/`event_graph` 对 xq/guba 的消费 grep 匹配数 > 0（F2 直接消灭）** |
| 5 | portal 加"事件"视图 | 页面 | 能看到 ≥1 个独立来源数 ≥3 的事件 |

**判定 P0 成功的唯一硬指标**：日报里出现"这个消息有 N 家独立来源在说"这种句子。出现了，就是闭环成了。

### P1：实体与源健康（P0 验收后启动）

- 建 `entity_alias` 别名表，先覆盖持仓/关注池的上市公司（规则层，1–2 天）
- `osint_knowledge_unit.entities` 按 FTM 子集规范化（`LegalEntity` 继承 `name` / `registrationNumber` / `country`）
- 源健康：把 11-04《情报源健康盘点》的指标接到 `osint_target.next_scan_at` / `last_scan_error`（字段已存在，**只差一个巡检任务**）

### P2：长尾源扩源（P1 验收后启动）

- `changedetection.io`（Apache-2.0）接"无 RSS / 无 API"的公告类源（交易所公告、部委网站、协会站）
- RSSHub（MIT）把中文平台变 RSS，走标准采集通道，**不写新爬虫**
- 护栏：**每个新源上线前必须能回答"它的事件会进哪个 story"**，否则不许上。这是防"扩源不扩消费"重演的唯一闸门。

## 5. 口径收口：把影响选型的四个冲突钉死

汇总文档列出的 9 处冲突里，这 4 处直接影响"算不算干完了"，必须在 P0 开工前裁定，否则验收标准无法写。

| 冲突 | 裁定口径 | 理由 |
|---|---|---|
| **`news.stocks` 覆盖率** | **只认 9.18%（数组非空）**。22.49% 与 24.9% 作废 | 24.9% 含 18,104 条字面 `[]` 字符串，是解析 bug 不是覆盖；拿它当覆盖率等于把 bug 计入 KPI |
| **媒体保留期** | **24 小时**（`system_design` §1.3/§10.1） | 同一文档 §8 写 30 天，属内部矛盾；取更严格者，且与 `osint_knowledge_resource.media_expires_at` 字段语义一致 |
| **"已复核"口径** | **`review_status='reviewed'` 才算，pending 不算** | 10-31 方案已明令；"10,525 已建队"式表述停用 |
| **JEV 命中率** | **78.57% 是"后验未回填率"，不是准确率**；方向命中率 56% 单独报 | 两个指标不同分母，混读会得出"78.6% 准确"的错误结论 |

## 7. 明确不做的事（防返工清单）

1. **不部署 OpenCTI / Aleph / MISP** —— OS 与许可证双重否决，讨论到此为止。
2. **不把数据模型迁到 STIX 2.1** —— 那是威胁情报的方言，不是产业/金融情报的。迁过去等于重写全部契约。
3. **不引入 Node 技术栈** —— 生产机 glibc 2.17 装不了 Node 20+，且会分裂运维面。
4. **不用 MediaCrawler 代码** —— 许可证禁商用。
5. **不先扩源** —— 在 story 层上线前新增任何源，都是在给一个没有出口的漏斗加水。
6. **不再写第 14 份设计方案** —— 设计层已收敛，缺的是 2 张表和一个算子。

## 8. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 四关系判定准确率不达预期 | 中 | 事件质量差，下游不信任 | 先人工标 200 对做基线；直接复用 AIHOT 的提示词与阈值，不从零调 |
| bge-m3 在 iGPU 上吞吐不足 | 低 | 存量重算慢 | 存量一次性批处理；增量按 1000 条/批（AIHOT 同款参数）。bge-m3 仅 568M，远低于本地模型 9B 上限 |
| 事件与事实一对多误判，热度虚高 | 中 | 排序失真 | `UNIQUE(unit_key, unit_version)` 硬约束 + `independent_sources` 按媒体域名去重，不按 fact 计数 |
| 存量 unit 质量差，聚类出垃圾 | 中高 | P0 验收不过 | 先用 `review_status='reviewed'` 的子集跑首轮，绕开未复核噪声（这也顺带解决"已复核"口径冲突） |
| CentOS 7 EOL 带来的长期风险 | 高 | 后续任何新组件都可能装不上 | 本轮方案**刻意做到零容器、零 Node、纯 pip**，把 OS 约束降到最低；OS 升级单独立项，不绑架情报线 |
