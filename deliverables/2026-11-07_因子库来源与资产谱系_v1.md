### 6.1 动态调用还是静态映射？

结论：**清单与注册是静态的，因子值计算是动态的，Tushare `factor_list` API 只在手动采集时动态调用。**

| 环节 | 方式 | 说明 |
|---|---|---|
| `factor_list` 采集 | 动态、手动 | 运行 `tushare_factor_list.py fetch` 时才请求 Tushare API；不随因子评测自动调用 |
| 因子名称/分类注册 | **静态** | `factor_lib_tushare.py:64-117` 的 `TYPE_NAMES` 硬编码 272 个名称，`TUSHARE_FACTOR_MAP` 由它生成；启动时不读 `latest.json` |
| B2 Alpha101 公式 | **静态** | `alpha101_formulas.json` 在 import 时加载（`factor_lib_tushare.py:119-122`） |
| 因子值 | **动态计算** | `load_panel()` 读本地 parquet，`FactorSpec.compute()` 在评测时实时计算；不调用 Tushare API |
| 财务数据 | 本地 PIT 读取 | 读 `income/balancesheet/cashflow/fina_indicator`，按 `ann_date` 可见 |

因此：

- Tushare `factor_list` 不提供因子值，不能“动态拉因子值”；它只是静态清单。
- 如果 Tushare 新增/删除因子，当前 `factor_lib` **不会自动感知**；需要重新 fetch 快照、更新 `TYPE_NAMES` 和实现，再跑回归测试。
- 日常评测不会产生 Tushare API 调用；网络请求只发生在采集/刷新环节。

### 6.2 Tushare 新增因子时的更新流程

> 当前没有“自动发现新因子并自动注册”的机制；这是半自动流程，必须人工审核方向、实现和测试。

1. **备份与确认权限**
   - 备份 `tools/research/factor_lib_tushare.py`、`tools/research/alpha101_formulas.json`、`tools/research/factor_lib_financial.py`。
   - 确认 `TUSHARE_TOKEN` / `XT_DATA_KEY` 有效，且账号有「因子库」权限；否则 `fetch` 会返回退出码 2/3。

2. **拉取新快照**
   ```powershell
   C:\项目\py312\python.exe -X utf8 tools/data_sources/tushare_factor_list.py fetch
   C:\项目\py312\python.exe -X utf8 tools/data_sources/tushare_factor_list.py check
   C:\项目\py312\python.exe -X utf8 tools/data_sources/tushare_factor_list.py status
   ```
   - `fetch` 会生成新的 `snapshots/factor_list_YYYYMMDD.{json,parquet}`，并更新 `latest.*` 与 `manifest.json`。
   - 不要用 `--factor-type` 的过滤结果更新 `latest`；过滤查询只写子集快照，不更新 latest。
   - 同一天重复全量 fetch 会覆盖当天的快照文件，先备份旧文件。

3. **对比新旧清单**
   - 比较新旧 `snapshots/factor_list_*.json` 的 `rows`，按 `factor_type` 找新增/删除/改名。
   - 同时核对 `manifest.json` 的 `total`、`by_type`、`sha256`、`fetched_at`。
   - 只把确认存在的新因子加入映射，不要按旧文档臆造。
   - 可用同步脚本自动完成 diff 与 `TYPE_NAMES` 补丁：
     ```powershell
     # 默认 old=第二新快照、new=latest.json；也可显式指定
     C:\项目\py312\python.exe -X utf8 tools/data_sources/tushare_factor_sync.py diff `
       --old quant_backtest/data/factor_library/tushare_factor_list/snapshots/factor_list_20261001.json `
       --new quant_backtest/data/factor_library/tushare_factor_list/latest.json `
       --out-dir deliverables/2026-11-07_tushare_factor_sync
     ```
   - 输出：`diff.json`（added/removed/moved + 分类计数）、`TYPE_NAMES.patch.diff`（unified diff）、`type_names_target.json`、`factor_lib_tushare.patched.*.py`（有变化时）。
   - 默认**只生成补丁，不改源码**；确认 diff 后才加 `--apply`（会先写 `.bak`）。
   - 脚本以**当前源码 TYPE_NAMES 为基线**、新快照为目标集合：新快照没有的源码名会被移出，moved 因子会移动分类；出现未知 `factor_type` 时拒绝生成，不猜 batch。

4. **注册并实现新因子（核心步骤）**

   这一阶段不是只改一处；必须同时完成 **清单映射 → 实现函数 → 注册链 → 状态标记**。只改 `TYPE_NAMES` 会让因子出现在 map 里但不可计算；只写实现不入 `TYPE_NAMES` 则 `_add()` 直接抛 `KeyError`。

   #### 4.1 先更新 `TYPE_NAMES`

   - 位置：`tools/research/factor_lib_tushare.py:64-98`（按 Tushare `factor_type` 分组的名称元组）。
   - 把新因子名加入对应分类，例如：
     ```python
     "Quality": (
         # ...
         "new_factor_name",
     ),
     ```
   - 不要手动编辑 `TUSHARE_FACTOR_MAP`：它在 import 时由 `TYPE_NAMES` 自动生成（`:100-117`）。
   - 若是全新 `factor_type`：新增 `TYPE_NAMES` 键，并确定 batch：
     - B1：Momentum / Liquidity / Risk / Reversal / Size
     - B2：Alpha101
     - B3：Growth / Quality / Value
   - 此时只完成了“清单映射”。新因子状态仍是 `mapped`，不会进入 `factor_lib.FACTORS`。

   #### 4.2 注册链怎么走

   | 批次 | 数据入口 | 注册函数 | 状态写入 |
   |---|---|---|---|
   | B1 | `_SPECS`（`_add()` 追加） | `register_batch()` 遍历 `_SPECS` | `_add()` 把 map 状态改为 `implemented`、batch=B1 |
   | B2 | `_ALPHA101_FORMULAS`（读 `alpha101_formulas.json`） | `register_alpha101()` | 自动写 `implemented`、batch=B2 |
   | B3 | `B3_FACTORS`（`_add()` 追加） | `register_b3()` → `register_financial()` | `register_b3()` 回写 `implemented` 或 `blocked_missing_data` |

   关键点：

   - `factor_lib.py` 在 import 末尾调用 `register_batch()`；新增实现必须放在这个调用之前（同模块内定义顺序要在 `register_batch` 前）。
   - 注册后 `factor_lib.FACTORS[name]` 才存在。
   - 已注册的因子不会因重新 fetch 自动更新，必须重启 Python 进程重新 import。

   #### 4.3 B1：行情/量价因子实现模板

   在 `tools/research/factor_lib_tushare.py` 中新增函数，再调用 `_add()`：

   ```python
   def _new_factor(panel):
       # 只用 T 日及以前数据；缺字段返回全 NaN，不要抛异常
       x = _xrank(-_cum_ret(panel, 21))
       return x

   _add(
       "new_factor_name",          # 必须已存在于 TYPE_NAMES
       "Tushare-动量",              # family
       1,                          # direction：+1/-1，必须有先验或证据
       _new_factor,
       ("adj_close",),             # requires：本因子实际依赖的 panel 字段
   )
   ```

   要求：

   - 优先复用现有 helper：`_adj`、`_ret`、`_cum_ret`、`_ma`、`_std`、`_xrank`、`_nan`、`panel.optional(...)`。
   - 缺字段返回 NaN 面板，由 `factor_lib` 的 valid 掩码剔除；不要让单因子异常打断整批评测。
   - 方向不能无依据地写 `+1`；需要进入 B1 复合策略的，另行更新 `B1_PRIOR_DIRECTIONS` / `B1_STRATEGY_FACTORS` 并补 `test_b1_prior_directions.py`，不要在这个步骤里静默加入策略。
   - `_add()` 成功后会写 `TUSHARE_FACTOR_MAP[name]["status"]="implemented"`、`batch=B1`。

   #### 4.4 B2：Alpha101 表达式因子实现模板

   1. 在 `tools/research/alpha101_formulas.json` 的 `formulas` 下增加官方公式，并同步 `count`：

   ```json
   {
     "source": "tushare.factor_list / Alpha101",
     "snapshot": "quant_backtest/data/factor_library/tushare_factor_list/latest.json",
     "extracted_at": "2026-11-07",
     "count": 102,
     "formulas": {
       "alpha101_102": "Rank(Ts_ArgMax(...)) - 0.5"
     }
   }
   ```

   2. 确认 `alpha101_engine.py` 支持公式里的全部算子；用合成面板调用 `evaluate_formula()` 验证。

   3. 不需要写 `register_alpha101()` 的调用；`factor_lib_tushare.py` import 时读取 JSON，注册时自动遍历 `_ALPHA101_FORMULAS`。

   要求：

   - 因子名必须在 `TYPE_NAMES["Alpha101"]` 中；否则 `register_alpha101()` 会跳过（`name not in TUSHARE_FACTOR_MAP`）。
   - 公式必须来自 Tushare 官方描述，不能自己臆造。
   - Alpha101 注册方向固定为 `+1`；需要反向时在公式里显式写 `-1 * ...`。
   - 只有清单、没有官方公式时，保持 `mapped`，不要强行实现。

   #### 4.5 B3：PIT 财务因子实现模板

   在 `tools/research/factor_lib_financial.py` 的 `B3_FACTORS` 注册区新增：

   ```python
   _add(
       "new_fin_factor",
       "Quality",                     # Growth / Quality / Value
       lambda fd, p: _rank_of(fd, p, "metric_name"),
       direction=-1,
       requires=("income",),          # 额外依赖；基础四表由 register_financial 自动补
       note="指标定义；PIT 按 ann_date，越低越好",
   )
   ```

   要求：

   - `fd` 是 `FinancialData` 的 PIT 日频视图；新增指标必须能通过 `FinancialData.daily` / `_add_*` 生成，缺原始字段时先扩展 loader。
   - 不要手写未来公告数据；可见日由 `ann_date` 决定。
   - 缺数据时返回 NaN 或标 `blocked`，不要静默填 0。
   - `register_financial()` 会跳过 `note` 含 `blocked` 的因子；`register_b3()` 再把状态回写为 `blocked_missing_data`。

   #### 4.6 完成判据（Definition of Done）

   一个因子只有同时满足以下条件才算“实现完成”：

   - [ ] `TUSHARE_FACTOR_MAP[name]` 存在，且 `status="implemented"`（或明确的 `blocked_missing_data`）。
   - [ ] `factor_lib.FACTORS[name]` 存在，family/direction/requires 正确。
   - [ ] `factor_lib.py map --json` 的 `total`、`by_type`、`by_batch`、`implemented` 与快照/实现一致。
   - [ ] 有合成面板单测：输出 shape 正确、只用历史数据、缺字段为 NaN、方向符合预期。
   - [ ] B1 若进入策略，`B1_PRIOR_DIRECTIONS`/`B1_STRATEGY_FACTORS` 和先验测试同步更新（单独评审）。
   - [ ] catalog 的 `factor_list` 条目 rows/files/sha/fetched_at 与新 manifest 一致。
   - [ ] 本文件的计数、分类、sha、变更记录同步更新。

   #### 4.7 常见错误

   | 现象 | 原因 | 修复 |
   |---|---|---|
   | `KeyError: factor_list 无此因子` | 未把名字加入 `TYPE_NAMES` | 先做 4.1，再调用 `_add()` |
   | map 里有名字，但 `factor_lib.FACTORS` 没有 | 只加了映射，没有实现/注册 | 补 `_add()` / 公式 / B3 定义 |
   | `implemented` 数量没变 | 状态仍是 `mapped`，或用了 blocked note | 检查 `_add` 与 `register_*` 路径 |
   | 评测报字段缺失 | `requires` 写错或 panel 未加载该字段 | 修正 requires；缺数据返回 NaN |
   | 重跑后因子消失 | Python 进程未重启，或 import 顺序在注册之后 | 重启进程；实现放在 `register_batch()` 之前 |

5. **更新测试与计数**
   - 检查并更新：`test_factor_lib.py`、`test_factor_lib_tushare.py`、`test_alpha101_engine.py`、`test_factor_lib_financial.py`、`test_b1_prior_directions.py`。

### 6.3 CI 门禁：PR 快照变更必须同步 `TYPE_NAMES`

工作流：`.github/workflows/factor-snapshot-guard.yml`。

触发条件（PR 改动以下任一即可）：

- `quant_backtest/data/factor_library/tushare_factor_list/latest.json`
- `quant_backtest/data/factor_library/tushare_factor_list/snapshots/**`
- `tools/research/factor_lib_tushare.py`
- `tools/data_sources/tushare_factor_sync.py`
- 本 workflow

执行逻辑：

1. 从 PR base 分支（通常是 `main`）用 `git show origin/<base>:.../latest.json` 取出基线快照，写到 CI 临时文件。
2. 检查 `snapshots/` 有变化时 `latest.json` 是否也更新；只加归档、不更新 latest 直接失败。
3. 运行：
   ```bash
   python tools/data_sources/tushare_factor_sync.py diff \
     --baseline <base-latest.json> \
     --new quant_backtest/data/factor_library/tushare_factor_list/latest.json \
     --out-dir ci-artifacts --check
   ```
4. `--check` 退出码：
   - `0`：`TYPE_NAMES` 已与 PR 的 `latest.json` 同步，通过；
   - `1`：快照有新增/删除/移动，但 `TYPE_NAMES` 未同步，CI 失败，并在 Step Summary 提示需更新 `TYPE_NAMES`；
   - `2`：快照/源码结构错误，CI 失败。
5. 无论通过与否，`ci-artifacts/` 里的 `diff.json`、`TYPE_NAMES.patch.diff` 会上传为 artifact，供 PR 审查。

本地复现：

```powershell
# 从 main 取基线（等价于 CI 的第一步）
git show origin/main:quant_backtest/data/factor_library/tushare_factor_list/latest.json > C:\Temp\factor_list_baseline.json

C:\项目\py312\python.exe -X utf8 tools/data_sources/tushare_factor_sync.py diff `
  --baseline C:\Temp\factor_list_baseline.json `
  --new quant_backtest/data/factor_library/tushare_factor_list/latest.json `
  --out-dir C:\Temp\factor_sync_ci --check
```

说明：

- `--baseline` 与 `--old` 互斥；`--baseline` 专用于“用 main 上的快照做 PR 对比”。
- 本仓库只版本化 `latest.json`、`manifest.json`、`snapshots/*.json`；parquet 仍不入库。`.gitignore` 已对该目录单独放行。
- base 分支首次还没有快照时，workflow 用 PR 自身的 `latest.json` 做 bootstrap 基线，仍会检查 `TYPE_NAMES` 是否覆盖 PR 清单。
- 门禁只检查 `TYPE_NAMES` 映射；因子实现缺失仍由测试（`implemented` 计数/单测）发现。
- 该 workflow 只负责让 PR 变红和给出提示；要强制“未通过不可合并”，还需在 GitHub 分支保护里把 `factor-snapshot-guard / snapshot-guard` 设为 required check。

## 7. 边界与限制

1. **没有因子值快照**：当前只登记了 `factor_list` 元数据，因子值由 `load_panel` 后实时计算，不具备“按因子/按日版本化”的资产表。
2. **清单不是因子值**：`factor_list` 272 行只是名称/分类/描述；真正可计算的是 271 个（1 个 blocked）。
3. **财务数据滞后**：财务四表 freshness 20260930、`verified_stale`，B3 因子无法反映 2026Q4 之后的信息。
4. **`factor_list` 手动刷新**：不是每日时序；Tushare 侧因子清单变更或 token 权限变化时需要重跑 fetch。
5. **自研与 Tushare 混装**：288 个注册因子里有 17 个自研，报告中必须分开统计。
6. **B2 公式依赖本地清洗**：公式来自 Tushare 官方描述，但解析/清洗/求值由本地 `alpha101_engine.py` 完成，若 Tushare 描述变更需重新提取。
7. **研究口径**：`factor_lib` 是研究评测底座，不直接等于生产选股/交易信号。
