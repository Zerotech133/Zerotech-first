## 2. 发布步骤（灰度五步，每步可独立失败）

**灰度不变量**（任何一步失败都必须成立）：

1. 既有表结构零变更（本次只 `CREATE TABLE IF NOT EXISTS` 两张新表）；
2. 旧 384 维 collection 不被读写、不被删除；
3. 聚类算子独立进程，失败不阻塞 API / 采集 worker；
4. 消费侧最后切换，且切换点是一个可回退的开关。

### 2.1 第一步：建表（唯一触碰既有 DDL 的步骤）

```bash
cd /home/zeroq/osint_video
$PY scripts/init_db.py 2>&1 | tee /home/zeroq/backup/init_db_$(date +%F_%H%M).log
```

预期输出（尾部）：

```
[ok] osint_story          行数=0
[ok] osint_story_member   行数=0
[done] schema 初始化完成：NN 条语句，16 张表就绪
```

若两张新表已有数据（重跑），行数应等于上次值，**不得归零**。

结构核对（不能只看"表存在"）：

```bash
psql -h 127.0.0.1 -U "$PG_USER" -d "$PG_DB" -c "\d osint_story" -c "\d osint_story_member"
psql -h 127.0.0.1 -U "$PG_USER" -d "$PG_DB" -Atc "
select table_name||'.'||column_name from information_schema.columns
 where table_name in ('osint_story','osint_story_member') order by 1;"
```

必须确认三点：`osint_story_member.source_id` 存在；PK 是 `(unit_key, unit_version)`；`osint_story.stage` 有 CHECK 五态。缺任一项 → 停，说明线上跑的是旧版 schema.sql。

风险点（本步唯一风险，来自既有 schema 重放）：`schema.sql:131-132` 对 `osint_target` 先 `DROP CONSTRAINT` 再 `ADD CONSTRAINT`，会拿 ACCESS EXCLUSIVE 锁；`schema.sql:75-78` 对 `osint_retry_idempotency` 做一次全表 `UPDATE`。两张表都小，实际亚秒级，但**必须在低峰执行**，且执行前确认无长事务：

```bash
psql -h 127.0.0.1 -U "$PG_USER" -d "$PG_DB" -c "select pid,state,wait_event_type,left(query,60) from pg_stat_activity where state<>'idle' and pid<>pg_backend_pid();"
```

有长事务（>60s）先等它结束，否则 DDL 会排队并把后续所有访问一起堵住。

失败处置：`init_db.py` 在单连接上顺序执行、末尾统一 commit，中途报错则整批回滚，**不会留下半套表**。修掉报错语句后重跑即可（幂等）。**严禁**在生产用 `--drop`。

### 2.3 第三步：存量向量回填（可中断、可续跑、不改 PG）

`[本次新建]` 运维脚本，仓库内无对应 CLI，故由发布方新建到 `/home/zeroq/bin/`：

```bash
mkdir -p /home/zeroq/bin
cat > /home/zeroq/bin/osint_backfill_vectors.py <<'PY'
#!/home/zeroq/osint_video/.venv/bin/python
"""存量 fact → bge-m3 1024 维向量 → 新 collection（幂等，可断点续跑）。

用法：osint_backfill_vectors.py [起始 unit_id]
"""
from __future__ import annotations
import sys, time
sys.path.insert(0, "/home/zeroq/osint_video")

from common import db
from knowledge.embedder import Embedder
from knowledge.indexer import VectorIndex

COLLECTION = "osint_knowledge_units_bgem3_v1"
BATCH = 64

SQL = """
SELECT unit_id, unit_key, unit_version, title, content, source_url, blogger_key,
       topics, status, review_status, truth_status, content_hash
  FROM osint_knowledge_unit
 WHERE status = 'active' AND unit_id > :after
 ORDER BY unit_id
 LIMIT :lim
"""


def main(after: int = 0) -> int:
    emb = Embedder()
    idx = VectorIndex(collection=COLLECTION, vector_size=emb.dim)
    done, t0 = 0, time.time()
    while True:
        rows = db.fetch_all(SQL, {"after": after, "lim": BATCH})
        if not rows:
            break
        texts = [f"{r['title'] or ''}\n{(r['content'] or '')[:2000]}".strip() for r in rows]
        vectors = emb.embed_texts(texts)
        for row, vec in zip(rows, vectors):
            idx.upsert(row, vec)
        after = int(rows[-1]["unit_id"])
        done += len(rows)
        cost = time.time() - t0
        print(f"[backfill] done={done} last_unit_id={after} {cost/max(done,1):.3f}s/条", flush=True)
    print(f"[backfill] 完成：{done} 条，耗时 {time.time()-t0:.0f}s")
    return 0


if __name__ == "__main__":
    raise SystemExit(main(int(sys.argv[1]) if len(sys.argv) > 1 else 0))
PY
chmod +x /home/zeroq/bin/osint_backfill_vectors.py
```

| 单条耗时 | 见 §5.4，保守 1.5s/条 |
| 1 万条 | ≈ 4.2 小时 |
| 3 万条（14 天增量量级） | ≈ 12.5 小时 |
| 30 万条（1 年全量） | ≈ 5.2 天 → **必须接受分批**，或改为"只回填近 90 天，历史按需" |
| 中断续跑 | 日志里最后一个 `last_unit_id`，作为参数重入：`osint_backfill_vectors.py <last_unit_id>` |
| 失败即停条件 | 连续 3 批抛 `EmbeddingUnavailableError`；或 `ValueError: 嵌入维度不匹配`（**立即停**，说明模型不是 bge-m3 或不是 1024 维） |

本步不写 PG、不影响旧 collection、不影响 API，**失败可直接放弃且零副作用**（已写入的点是派生数据，删 collection 即清空）。

## 3. 回滚预案（四场景，各自独立）

总原则：**PG 是事实源，story 是派生数据**。任何回滚都不允许碰 `osint_knowledge_unit` / `osint_knowledge_resource`。

### 场景 A：DDL 回滚（撤销两张新表）

| 维度 | 内容 |
|---|---|
| 触发条件 | `init_db.py` 中途失败并污染既有表（实际不可能：单连接单事务）；或建表后确认与既有系统存在结构性冲突（如同名视图/权限冲突）；或 schema 里 `source_id` 与代码不一致导致每轮聚类必失败且短期无法修 |
| 操作 | `psql -h 127.0.0.1 -U "$PG_USER" -d "$PG_DB" -c "DROP TABLE IF EXISTS osint_story_member; DROP TABLE IF EXISTS osint_story;"`（**必须先 member 后 story**，否则 FK 报错；不要用 `CASCADE`，它会连带删掉未来可能加的外键对象） |
| 数据影响 | story + member 全部丢失。二者 100% 可从 fact 重算，**不损失任何原始事实**；唯一真实损失是 `decided_by='manual'` 的人工归属与 `rationale`（模型无法重建人的判断） |
| 不可逆点 | 人工标注丢失；且只能靠 §1.1 的全库 dump 恢复到某一时点（会连带回退这期间的新采集，代价远超收益）。**因此上线前 24 小时不要让运营做人工合并标注** |
| 前提 | 消费侧已切回 `legacy`，且 `systemctl stop osint-story-group.timer` |

### 场景 B：Collection 回滚（放弃 1024 维索引）

| 维度 | 内容 |
|---|---|
| 触发条件 | 检索质量显著劣于旧索引（Top10 相关性肉眼可见下降）；或回填过程中发现模型维度不是 1024；或 Qdrant 磁盘/内存告警 |
| 操作 | ① `systemctl stop osint-story-group.timer`（若消费侧已用新检索）；② 检索代码把 `VectorIndex(collection="osint_knowledge_units_bgem3_v1", vector_size=1024)` 改回 `VectorIndex()`（即 `.env` 的 384 名）；③ `curl -X DELETE http://127.0.0.1:6333/collections/osint_knowledge_units_bgem3_v1` |
| 数据影响 | 仅删派生索引，PG 零影响。旧 384 collection 全程未被触碰，删除新库是安全动作 |
| 不可逆点 | 无数据不可逆；但**重建成本 = 全量重新嵌入**（§5.4 的时长）。且 collection 一旦创建，维度不可修改 —— 想从 1024 改成别的维度只能删了重建 |
| 注意 | 不要为了"省事"把 `.env` 的 `QDRANT_COLLECTION` 改成新名字：那会让所有 `VectorIndex()` 默认构造指向 1024 库，旧 384 调用方立刻全挂。新链路一律显式传参 |

### 场景 C：消费侧回滚（事件层退出日报）

| 维度 | 内容 |
|---|---|
| 触发条件 | 抽样误合并率 > 5%；或日报出现"把两家公司的事并成一件"这类事实性错误；或 `v_story_brief` 查询拖慢报表（P95 > 3s） |
| 操作 | 消费侧 `STORY_SOURCE=legacy` 并重启；`systemctl stop osint-story-group.timer`；视图保留不动 |
| 数据影响 | 无。story 表进入只读冻结（不再增长），随时可恢复 timer 继续 |
| 不可逆点 | **已推送给人的日报无法撤回**。所以切换必须在低曝光时段（建议 20:00 后首推，或先只进后台不推送），先用"影子模式"跑 1 天 |

### 场景 D：算子停机（只停聚类，不动其他）

| 维度 | 内容 |
|---|---|
| 触发条件 | 单轮 `elapsed_ms` > 30 分钟；PG CPU > 70% 持续 10 分钟；`pg_stat_activity` 出现长事务来自聚类连接；`osint_story` 日增 > 1500 异常膨胀 |
| 操作 | `systemctl stop osint-story-group.timer && systemctl stop osint-story-group.service`；若单轮正在跑且必须立即止损：`systemctl kill -s TERM osint-story-group.service` |
| 数据影响 | 中断点可能留下"有 story 无 member"的空壳（`_create_story` 与 `_add_member` 是两次独立提交，`story_group.py:584-613`），修复：`DELETE FROM osint_story s WHERE NOT EXISTS (SELECT 1 FROM osint_story_member m WHERE m.story_id=s.story_id);`。member 表幂等（`ON CONFLICT DO NOTHING`），重跑不会重复 |
| 不可逆点 | 无。半成品可用上面一条 SQL 清干净后重跑 |
| 恢复 | 调小 `--limit`（2000 → 500）、拉长 timer 间隔（1h → 3h），或把窗口从 14 天降到 7 天，再 `start` |

### 回滚决策速查

| 现象 | 场景 | 首选动作 | 预计耗时 |
|---|---|---|---|
| 聚类每轮全失败 | A/代码 | 看 `journalctl -u osint-story-group -n 100`，若是 `column "source_id" does not exist` → 重跑 `init_db.py`（schema 已有该列）而非删表 | 5 min |
| 日报出现明显错并 | C | 消费侧切 legacy + 停 timer | 5 min |
| 检索结果变差 | B | 检索代码改回 `VectorIndex()` | 10 min |
| PG 被拖慢 | D | 停 timer | 1 min |
| 维度报错 `ValueError` | B | 停回填，核对模型与 `EMBED_DIM` | 10 min |

## 4. 监控指标与告警阈值

采集方式统一为三条腿：**PG SQL**（业务量）、**日志 grep**（进程内事件）、**探针命令**（外部依赖健康）。不引入 Prometheus（本机无容器、无 Node，装 exporter 得不偿失）。

### 4.1 指标表

| # | 指标 | 定义 | 采集方式 | 告警阈值 | 处置动作 |
|---|---|---|---|---|---|
| M1 | 嵌入失败率 | 失败批次数 / 总批次数 | `grep -c "批量嵌入失败\|嵌入后端健康探测失败" logs/app.log`（当日） | ≥ 3 次/小时，或连续 3 次探针 False | 查 `ollama ps` / `journalctl -u ollama`；模型被挤出→调 `OLLAMA_MAX_LOADED_MODELS` |
| M2 | 单批嵌入耗时 | 32 条文本一次 `embed_texts` 的墙钟 | 探针（见 4.2 P2） | warm 后 > 15s（p95），或 > 60s（单次） | 降到 `EMBED_BATCH_SIZE=16`；检查是否 CPU 被采集/抽取任务占满 |
| M3 | 聚类单轮耗时 | `GroupResult.elapsed_ms` | `grep "事件聚类完成" logs/app.log` 取 JSON | > 900000ms（15min）告警，> 1800000ms（30min）停 | `--limit` 降到 500；窗口降到 7 天；核对 `_REFRESH_STATS` 全表 UPDATE 耗时 |
| M4 | 聚类产出 story 数 | `stories_created` / `members_added` / `unrelated` | 同上 JSON | `units_scanned>0 且 stories_created=0` 连续 3 轮 → 异常；`stories_created ≈ units_scanned` 连续 3 轮 → 合并失效 | 前者查是否全 reviewed 过滤空了输入；后者查 embedder 是否降级 |
| M5 | 独立来源数分布 | 按 `independent_sources` 分桶的 story 占比（近 7 天） | 4.2 SQL S1 | `src=1` 占比 > 95% 连续 3 天 → 聚类失效；< 40% → 过度合并 | 前者降 `RECALL_SIMILARITY` 到 0.55 观察；后者升到 0.65 并抽样复核 |

## 5. 容量评估（按 2000 fact/天）

### 5.1 前提与算式

- 日增 fact：2000 条
- 合并率假设：平均 3 条 fact 归 1 个 story（`fact_count` 均值 3.0；保守下限取 2.0，上限取 5.0）
- 日增 story = 2000 / 3 ≈ **667**
- 日增 member = 2000（一条 fact 一条边，含重复报道）

### 5.2 表规模

| 周期 | story 行数 | member 行数 | story 堆大小（按 1.1KB/行） | member 堆大小（按 0.25KB/行） | 含索引合计（×3 余量） |
|---|---|---|---|---|---|
| 30 天 | 20,000 | 60,000 | 22 MB | 15 MB | ≈ 110 MB |
| 180 天 | 120,000 | 360,000 | 132 MB | 90 MB | ≈ 670 MB |
| 1 年（365 天） | 243,300 | 730,000 | 268 MB | 183 MB | **≈ 1.35 GB** |
| 3 年 | 730,000 | 2,190,000 | 803 MB | 548 MB | ≈ 4 GB |

行宽拆解（story）：`story_id` 8B + `story_key` ~19B + `title` 平均 60B（上限 500）+ `summary` 平均 200B（上限 1000，超 2KB 走 TOAST 压缩）+ 4 个时间戳 32B + 3 个 int 12B + `heat` 8B + `stage` ~10B + `source_names`/`entities`/`topics` 三个 JSONB ≈ 240B + 其他 ≈ 60B → 合计 ≈ 650B–1.1KB，取上界。

**结论**：`/home` 2TB 完全无压力；真正需要盯的是**索引与 autovacuum**，不是容量。

### 5.3 Qdrant 1024 维占用

- 单向量：1024 × float32(4B) = **4,096 B = 4 KB**
- 730,000 点 → 730,000 × 4KB = **2.98 GB**
- HNSW 图（M=16）：每点约 16×2×4B ≈ 128B → 730,000 × 128B ≈ **93 MB**
- payload（`unit_key`/`summary` 等，截断后约 200B）→ ≈ **146 MB**
- **合计 ≈ 3.2 GB**（1 年）；30 天 ≈ 265 MB

62GB RAM 下常驻 3.2GB 无压力；若 Qdrant 与 PG 同机且后续接入更多集合，建议对重集合开 `on_disk=true`（内存占用降到 ~1/4，检索延迟 +10–20ms，对本场景可接受）。

### 5.4 Ollama 嵌入吞吐

算式（保守）：

- bge-m3 = 567M 参数；单条文本按 512 token 计
- 20 vCPU、CPU-only、批 32，实测区间约 **0.6–1.5 s/条**（batch 摊薄后）。取保守值 **1.5 s/条**
- 日增 2000 条：2000 × 1.5s = **3,000 s = 50 分钟/天**，占日时长 **3.5%**
- 每小时一轮 2000 条上限 → 单轮最长约 50 分钟 < `TimeoutStartSec=3600`，**留有余量但已接近一半**；因此 timer 间隔不应短于 1 小时
- 首轮回填 14 天：14 × 2000 = 28,000 条 → 28,000 × 1.5s = 42,000 s ≈ **11.7 小时**（单进程串行）
- 1 年全量 730,000 条 → ≈ **304 小时 ≈ 12.7 天**（这就是 §2.3 建议"只回填近 90 天"的原因：90 天 = 180,000 条 ≈ 75 小时）

结论：**日常吞吐绰绰有余（3.5% 占用），瓶颈在首次回填**。若需加速：把回填拆成 2 个进程按 `unit_id` 区间并行（Ollama 单模型默认 `OLLAMA_NUM_PARALLEL=1`，需先调到 2–4，并确认内存足够）。

### 6.2 不可逆点（按痛感排序）

### 7.2 48 小时内的三条铁律

1. **不改阈值、不改代码**：48 小时内只观察不调整，除了"降 `--limit`"这种纯减压动作。改 `RECALL_SIMILARITY` 会让前后数据不可比，且已落库的边不会因阈值变化而重算。
2. **不做人工标注**：`decided_by='manual'` 一旦写入，后续重算会永久跳过它（这是设计意图，但上线初期判断标准还没稳定）。
3. **不回填历史全量**：48 小时内只允许"14 天窗口"的增量，全量回填放第二个窗口，避免把 PG 与 Ollama 同时压满，掩盖真实的问题。
