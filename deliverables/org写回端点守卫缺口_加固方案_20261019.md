## 0. 结论摘要

1. **缺口属实**：`org_command_api` 的六个 POST 端点（`/api/preview`、`/api/register`、`/api/project/preview`、`/api/project/register`、`/api/agent/update`、`/api/agent/learn`）经 `portal_api.py` 的 `do_POST` 分发（portal/portal_api.py:2528-2555），但均不在变更类守卫清单 `_MUTATION_POSTS`（portal/portal_api.py:206-245）中——**无 token 闸门、无写频控、无本机/局域网区分**，且经 nginx 8080 反代对局域网可达（portal/nginx.conf:56-60）。
2. **逐端核实副作用**：四个端点真落盘（`api_register`/`api_project_register`/`api_agent_update` 写 `org.json` 或 pending JSON + 备份 + 审计行；`api_agent_learn` 调本地 LLM 后写 knowledge jsonl + 审计行）；两个 preview 端点为**只读**（仅读 org.json 做校验并返回 plan 行，零落盘——已由 test_org_e2e.py 落盘守卫断言实证）。
3. **补丁草案核心建议**：**四个写端点全纳 `_MUTATION_POSTS`；两个 preview 端点不纳**（非变更类语义、信息面与已无守卫公开的 `GET /api/org` 等同、频控价值低）。补丁形态为**仅在 frozenset 增加 4 行字面量，`do_POST` 分发块零改动**——闸门（:2491）与频控（:2498）天然覆盖，`test_model_endpoint_guard_offline.py` 的 AST 基线哈希不受影响。
4. **前端影响**：org.html 是六端点唯一前端调用方，其 `post()` 只带 `Content-Type`、**不带 token**（portal/org.html:451-456），依赖页面注入的 fetch 拦截器自动补 token——而 org.html 现由 nginx **静态直出**，不走 `_html/_html_file` 注入路径，**静态页永远拿不到 token**。好在：本机浏览器访问恒被放行（直连 8091 走 `_is_local_req`；经 8080 反代走 `client_address` 回环的 `local_trusted` 兜底，实测见 §7.2），老田日常使用无感；受影响面仅为**真局域网设备上的 org.html 写回**（设计意图 403，但现阶段实际仍可写，见 §7.2）。
5. **补充重大发现（实证）**：当前线上经 nginx 反代的无 token 写请求**实际能通过 `_check_portal_token` 闸门**——`cainiao_auth.verify_request` 以 `client_address`（8091 绑 127.0.0.1，反代入站连接对端恒为回环）判 `local_trusted` 放行（portal/cainiao_auth.py:237-238），`_is_local_req` 基于 X-Real-IP 的局域网判定（portal/portal_api.py:586-591）被架构性架空。即：**补丁对"当前架构下的局域网写入"实际约束力有限，其主要价值在频控（尤其 learn 的 LLM 烧钱面）、语义完备性与架构纠正后的兜底**。建议另立 P1 修闸门判定源（详见 §7.2）。
6. **次要节结论**：`portal/backup_service_console/` 与背景判断不符——`api_model_admin.py` 与 `portal/api_model_admin.py` **逐字节同内容**（1194 行 diff 全异系 CRLF/LF 行尾差异，`tr -d '\r'` 后 diff 为空；md5 不同仅因行尾），`model_admin.html` md5 完全相同；真正独有的只有 `services.json`（8098 总控台服务注册表）。该目录无任何代码引用（全仓 grep 零命中），且 `services.json` 可被局域网经 8080 下载（实测 200）。**建议删除（进回收站）**，但须老田批准，本工位不执行。

### 4.3 preview 类只读端点：建议**不纳**

| 维度 | 分析 |
|------|------|
| 语义 | `_MUTATION_POSTS` 是"变更类"集合；preview 零落盘（§2），纳入会污染集合语义。仓库既有纪律可参照：`test_model_route_stays_outside_shared_mutation_set`（test_model_endpoint_guard_offline.py:388-392）明确"保护语义须与集合语义一致" |
| 频控价值 | 低。preview 单次成本 = 读一次 org.json + 内存校验（毫秒级），无 LLM、无子进程、无写；即便被刷，伤害上限是一次文件读 |
| 信息面 | 不扩大。`GET /api/org`（portal_api.py:4374-4380）**本就无任何守卫**返回全量 org bundle（本次实测 8080 返回约 232KB JSON）；preview 的校验错误信息不超出该已公开面 |
| 前端成本 | 纳管 preview 对局域网用户意味着两段式在**第一步**就 403（而非第二步）——失败更早但无安全增益；本机用户两种方案都无感（回环放行） |
| 反驳意见处理 | 唯一实质顾虑是"preview 作为免费校验 oracle"（如探测 agent_id 占用）。缓解：写端点纳管后，oracle 的后续动作（register）已被闸门+频控拦截，oracle 单独无变现路径 |

## 5. 前端影响评估（org.html）

**调用方唯一性**：全仓 grep，六端点唯一前端调用方为 `portal/org.html`（无其他页面/脚本调用；后端消费者仅 portal_api 分发块自身）。

**当前调用形态**（portal/org.html）：
- `post()` 助手（:451-456）：`fetch(path,{method:"POST",headers:{"Content-Type":"application/json"},body:…})`——**只带 Content-Type，不带 `X-Portal-Token`，也不带 `Authorization`**。
- 调用点：:393（`/api/agent/update`）、:400（`/api/agent/learn`）、:467（preview 二选一）、:479（register 二选一）。
- 读面（`/api/org`、`/api/org/meta`、`/api/agent/knowledge`）为 GET，不受写闸门影响。

**token 供给机制与断点**：
- 全站 token 自动注入依赖 `_token_tag`（portal_api.py:608-622）：仅对**本机来源**页面内联 `window.__PORTAL_TOKEN` + fetch 拦截器（POST 自动补 `X-Portal-Token`），且**仅经 `_html`/`_html_file` 出口的页面**才被注入（:654 为 `_html` 注入点）。
- 实测：org.html 由 nginx **静态直出**（8080/org.html，32,403B，title「老田 AI 工作站 · 组织架构图」），不经 `_html_file`——响应中无 `__PORTAL_TOKEN`（grep 计数 0）。8080/org 返回的是旧 SSR 页（65,983B，title「🏛 组织架构」，亦无注入）。即：**org.html 静态页在任何来源下都拿不到自动注入的 token**。
- 且 8091 直连并不服务 org.html（实测 `curl 8091/org.html` → 404，无路由），用户实际入口就是 8080。

**加守卫后的影响面**：

| 用户形态 | 判定链 | 加守卫后 |
|----------|--------|---------|
| 本机浏览器经 8080（老田日常） | nginx 注入 `X-Portal-Proxy=1`+`X-Real-IP`（非回环，页面无 token 注入可证）；但反代入站连接 `client_address` 恒为回环 → `cainiao_auth` `local_trusted` 兜底放行（§7.2 实证） | **放行，无感** |
| 本机脚本直连 8091 | 无 `X-Portal-Proxy` → `_is_local_req` 直通（:588-589） | **放行，无感** |
| 真局域网设备（手机/他人电脑）经 8080 打开 org.html 写回 | 页面无 token、fetch 不带头；`_is_local_req` 判非本机 → 设计意图 403（`forbidden: 缺失或不匹配的 X-Portal-Token`，token 不经局域网分发，:608-622 注释明言）；但当前架构下该 403 被 §7.2 的 `local_trusted` 兜底绕过，**实际表现为仍可写** | 设计 403 / 实际仍可写 |

**前端改造成本**：对"4 写端点纳管"方案，**本工位评估为零改造**——本机用户全形态放行；局域网写回本就应被拒（若 §7.2 兜底修复后严格生效，则局域网用户将稳定 403）。如产品要求局域网可用 org.html 写回，须先有登录态故事（`_check_portal_token` 已预留菜鸟 Bearer 通道，:597-604），属 P2，不在本方案。

### 7.1 爆炸半径（加守卫后旧调用方 403 面）

- **本机全部形态**：放行（§5 表），爆炸半径 ≈ 0。
- **局域网设备**：设计上 403。但实测当前架构下反代请求会被 `local_trusted` 兜底放行（§7.2），故**现阶段实际爆炸半径仍 ≈ 0**；待 §7.2 修复严格化后，爆炸半径 = "局域网设备使用 org.html 写回"这一场景——需事先与老田确认该场景是否存在（本工位判断：组织指挥台属内部管理面，局域网写入需求概率低）。
- **数据面**：无历史数据依赖守卫状态；`org_audit.jsonl` 既往记录不受影响；无需数据迁移。

### 7.2 补充重大发现：反代链下 P0-1b 闸门被 `local_trusted` 兜底架空（实证）

- **事实**：本次从本机经 8080（nginx 反代）POST 已守卫端点 `/api/data/update-plan`，**不带任何 token**：返回 `{"error": "禁止访问：Host或同源校验失败"}`（HTTP 403）。该错误来自 `warehouse_update_api.py:166-167` 的同源校验，位于 `if not authenticated`（:162-163）**之后**——即 `_check_portal_token()` 实际返回了 True，闸门未拦截。
- **机制**：`_check_portal_token`（portal_api.py:593-606）先走 `_is_local_req`（经反代时 `X-Portal-Proxy=1` 且 X-Real-IP 非回环 → False，页面无 token 注入可佐证），再调 `cainiao_auth.verify_request(self.headers, self.client_address[0], …)`（:602）；`verify_request` 第 2 优先级以 `remote_addr in _LOOPBACK` 判 `local_trusted` 放行（cainiao_auth.py:237-238）——而 8091 绑 127.0.0.1（:4592），反代入站连接的对端恒为回环，**该判定恒真**。X-Real-IP 这一唯一的局域网信号（:590-591）被绕过。
- **影响**：P0-1b"局域网来源须 token"的设计意图（nginx.conf:16-27 注释）在当前反代架构下对**所有** `_MUTATION_POSTS` 端点均未实际生效；本 org 补丁纳入后同样会被兜底——故补丁的现实价值主要是**频控（12/min，对 learn 的 LLM 面有实际约束）+ 语义/审计完备性 + 架构纠正后的兜底**。
- **建议（P1，不在本工位执行）**：将 `verify_request` 的 `remote_addr` 实参从 `self.client_address[0]` 改为 X-Real-IP（或让 `_check_portal_token` 在 `_is_local_req` False 时不再给予 `local_trusted` 兜底），使 X-Real-IP 成为唯一事实源；同时为 `_on_unreachable` fail-closed（cainiao_auth.py:197-214，K-STOCK-187 已收窄）补一条反代场景回归测试。此项涉及全站写端点行为变更，须老田拍板并评估产线影响（本机流量经 8080 时 X-Real-IP=127.0.0.1 仍放行，预计本机无感，但必须实测矩阵覆盖）。

### 7.3 回滚预案

1. 回滚即**删除 §4.1 的 4 行字面量**（或 `git checkout -- portal/portal_api.py` 后重启容器）；无数据、无配置、无 schema 牵连，分钟级完成。
2. 回滚后验证：本机打 preview/register 非法 payload 恢复 200/400 业务响应；频控计数随进程重启清零（:281-292 内存计数）。
3. 若上线后出现"本机 403"（预期外的判定链回归）：第一嫌疑是 §7.2 修复被提前合入且 X-Real-IP 实参错误——按 §7.2 建议的实测矩阵排查，而非回滚本补丁。
