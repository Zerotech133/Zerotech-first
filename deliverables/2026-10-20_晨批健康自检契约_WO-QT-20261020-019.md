## 三、灰态与「未采到≠正常」原则

### 原则 1：没采到 ≠ 正常（fail-open 禁令）

本项目有 fail-open 禁令，静默归零是 P0 级隐患。故：

- 证据源**缺失** → 落红（H3 库缺、H5 产物缺、H1 日志缺）；
- 证据源**解析失败** → 落红 + `check_error=true`（H5 JSON 坏、H4 目录不可读）；
- **不可判定**（无日期戳、格式无法解析）→ 落黄，并显式写明「不可判定」，
  绝不当绿；
- 判据**内部异常** → 落红 + `check_error=true`，不`except: pass`、不返回零缺口。

`check_morning()` 对每条判据独立包try，任何一条炸了其余照跑，
异常以 `severity='red', check_error=True` 的 finding 显式暴露。

### 原则 2：灰态 ≠ 绿（灰态无样本）

**灰态无样本**是事实陈述，不是健康证明。故灰态**最高只给黄**，
且 `evidence` 必须写明「灰态无样本」，禁当绿。
适用 H3（无快照但有灰态说明）与 H4（段灰态零落盘但有 note 证据）。

### 原则 3：无文件 ≠ 断线（判据要能区分「已知灰态」与「真静默」）

今晨实证直接决定了 H4 的三档设计：今晨 HK 段灰态，**零落盘文件**，只有 stdout note。
若按「无文件=红」一刀切，会把「已知灰态」与「真断线」混为一谈——前者只需记账，
后者要救火。故：

| 情形 | 判定 | 理由 |
|---|---|---|
| 有当日段产物 | 🟢 绿 | 段跑成了 |
| 无文件 **但** 有账本/日志 note 证据 | 🟡 黄 | 已知灰态，零落盘但已记账 |
| 无文件 **且** 无任何证据 | 🔴 红 | 静默失败嫌疑（今晨事故形态） |

note 证据源：`agent_platform/data/shadow/last_run.log`、
`agent_platform/data/shadow/shadow_ledger.jsonl`（只读扫尾 64KB——note 是当日追加的，
行在文件尾）。

**段标识按词边界匹配**（`(?<![0-9A-Za-z_])4d(?![0-9A-Za-z_])`）而非子串：
账本里 `run_id` 是十六进制，实测 `14dad5866f5a` 就含子串 `4d`——子串匹配会把一行
无关落单当成「4d 段有 note 证据」，把该判红的静默失败洗成黄，而这正是本判据要抓的东西，
不能自己先漏一个。回归见 `test_segment_token_not_matched_inside_hex_run_id`。

## 四、只读保证（三条）

1. **文件**：一律 `open(..., 'r')` / `open(..., 'rb')`，无任何写模式、无 `write_text`、
   无 `mkdir`。
2. **sqlite**：一律 URI `mode=ro` 且额外 `PRAGMA query_only=ON` 双保险。
   库不存在时**打开即失败**（不新建文件）；`query_only` 下 `CREATE TABLE` 抛
   `OperationalError`（单测断言）。
3. **不碰生产账**：不改 `paper.db`、不追加 `shadow_ledger.jsonl`、
   不改 `p0_alert_state.json`、不写任何报告产物。`--out` 是**唯一**可选落盘口，
   默认只打印，且落盘的是本工具自己的渲染结果，与被检对象无关。

## 五、接口契约

```python
check_morning(date="20261020", *, paths=None, stale_days=1,
              feeds=None, artifacts=None, gray_notes=None) -> dict
```

返回：

```json
{
  "date": "20261020",
  "status": "red",
  "summary": {"total": 12, "red": 6, "yellow": 3, "green": 3, "check_errors": 0},
  "findings": [
    {"check_id": "H2.hk", "severity": "red", "title": "H2 通道 hk 最新 run",
     "evidence": "通道 hk 无任何 poc_qpzmhk_*.json 产物于 …（缺=红）",
     "action": "跑对应通道刷新 …"}
  ],
  "mode": "dryrun",
  "generated_at": "2026-10-20 14:04:31"
}
```

`check_error=true` 仅在判据执行异常时出现。`findings` 按 `check_id` 稳定排序。

**CLI**：

```
python morning_health.py --date 20261020           # 人读紧凑摘要（默认）
python morning_health.py --date 20261020 --json    # 机器读 JSON 契约
python morning_health.py --date 20261020 --md      # 人读 Markdown（渲染给老田看）
python morning_health.py --date 20261020 --out r.md
python morning_health.py --repo-root <path>        # 路径注入
```

退出码：`0=green`、`1=yellow`、`2=red`、`3=工具自身失败`（坏输入 / 不可读）。

**坏输入 closed on failure**：`date` 非法（`2026-13-32`/`notadate`/`2026102`/`""`/
非字符串）一律抛 `ValueError` → CLI 返回 3。**绝不悄悄按今天算**——
按今天算会凭空造出「今日健康」的假绿。

## 七、已知边界与未接线路径

1. **推送未接**：DRYRUN，只判不发。推送（飞书/企微告警）属**WO-QT-20261020-015
   待授权单**，本单**刻意不留推送开关**——工具顺手就把告警发出去，等于绕过授权。
2. **排期接入未做**：挂进 07:05 automation 晨批序列属他人在途目录
   （`agent_platform/` 全部、`watch_dispatch/`、`signal_pool/`），本单**只读不改**。
   待 automation 工具恢复后另批。
3. **`last_run.log` 是滚动覆盖单文件**：历史日的 done 行会被后续跑批冲掉，
   故历史回看日（目标日早于日志最新心跳）判**黄**（不可回溯核验），
   不判绿也不判红；历史核验请改用 `shadow_ledger.jsonl` 的 `date` 字段。
4. **`H3` 依赖 `decision_snapshots` 表落地**：表不存在时判黄（未启用≠已核验通过）。
   表落地后本判据自动转绿，无需改码。
5. **`H5`/`H6` 清单需随业务下线同步维护**：产物下线要从 `DEFAULT_FEEDS` /
   `DEFAULT_ARTIFACTS` 摘除并记账，否则会长期挂黄/红。
6. **H2 通道降频需调阈值**：若某通道本就是周频（如当前 qd/qpzm 实测 9~11 天），
   应调 `stale_days` 或从清单摘除，而不是让红长期挂着变成噪声。
