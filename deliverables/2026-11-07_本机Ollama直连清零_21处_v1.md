## 一、为什么这 21 处必须改

`urllib` 对回环地址**零豁免**（`proxy_bypass('127.0.0.1')` 返回 `False`）。只要
`HTTP_PROXY` 存在，打 `127.0.0.1` 的请求照样送进代理：

| 代理状态 | 直连本机 Ollama 的结局 |
|---|---|
| 通（transparent 型） | 侥幸可用 —— 今天就是这种，所以一直没暴露 |
| 死 / 拒转 | `URLError` → 上层报「模型不可用」「Ollama 不可达」 |

后果是**归因错误**：看起来像 Ollama 挂了，实际是本机 -> 代理 -> 本机的绕行失败。
`jev_common.py` 的异常分支早就在打印 `proxies=urllib.request.getproxies()`，
说明这个怀疑存在过，但没有落到修复。

## 三、import 策略：按目录既有约定，不自创

难点不在替换调用，在**脚本直跑时 `sys.path` 里没有仓库根**。
`tools/kb_corpus/kb_qa.py` 这类脚本以 `python tools/kb_corpus/x.py` 直跑时，
`sys.path[0]` 是脚本目录，`tools/` 不在路径上。

沿用同目录已有的、已验证的两种写法，不新造机制：

1. **探测式**（`tools/` 顶层、`jev-eval/`、`ops/p0/eval/`、`AI/111111/`）
   ```python
   for _base in _Path(__file__).resolve().parents:
       for _cand in (_base, _base / "tools"):
           if (_cand / "safe_urlopen.py").exists():
               _sys.path.insert(0, str(_cand)); break
       else: continue
       break
   try:
       from safe_urlopen import safe_urlopen
   except ImportError:
       from tools.safe_urlopen import safe_urlopen
   ```
   内层 `(base, base/"tools")` 是必要的：`jev-eval/`、`ops/p0/eval/` 的祖先链上
   原本没有 `safe_urlopen.py`，它在仓库根的 `tools/` 子目录里，只往上爬找不到。

2. **portal 范本**（`portal/api_kb_corpus.py`）
   与 portal 内 20+ 模块一致：
   ```python
   try:
       from safe_urlopen import safe_urlopen
   except ImportError:  # pragma: no cover
       from portal.safe_urlopen import safe_urlopen
   ```

验证：对 19 个文件逐个在「`sys.path[0]` = 脚本目录」的场景下 import，打印
`safe_urlopen.__code__.co_filename` —— 全部命中各自最近的那份副本
（`agent_platform/` 用 `agent_platform/safe_urlopen.py`，`portal/` 用 portal 版，
其余用 `tools/safe_urlopen.py`）。

## 四、连带改动：3 处测试的 patch 目标（重要）

有一类测试靠 **patch `urlopen` 让网络必然失败**来做断言。改成 `safe_urlopen` 后，
回环走独立的 `ProxyHandler({})` opener，patch 全局 `urlopen` 拦不住 —— 测试会
**真连本机 Ollama**，防护语义直接失效。

| 测试 | 原 patch 目标 | 改为 |
|---|---|---|
| tools/tests/test_rag_rerank.py::test_reranker_degrade_rule_only | `urllib.request.urlopen` | `rre.safe_urlopen` |
| AI/111111/test_web_chat.py（7 处） | `patch.object(web_chat, 'urlopen')` | `patch.object(web_chat, 'safe_urlopen')` |

`test_reranker_degrade_rule_only` 改之前确实红了，且红得很说明问题：它报出
`本地无 rerank 模型（现有 ['qwen3.5:9b', 'qwen3.5:4b', 'bge-m3:latest']）`
—— 请求真的穿过了代理连上 Ollama，反过来印证修复生效。

`test_web_chat.py` 那 7 处是另一种失败形态：`web_chat` 不再暴露 `urlopen` 属性，
patch 直接抛 `AttributeError`（不是静默失效），所以必须同步。

## 五、扫描器缺陷：修好了却在报告里看不见

`scan_loopback_urlopen.py` 原判定只看文件里有没有 `ProxyHandler({})`/`no_proxy`
**字面量**，不认「调用 `safe_urlopen` 本身就已有旁路」。

后果很硬：`c14ff67a5` 修好共享入口后，108 个引用文件仍被判 `VICTIM` ——
**活干完了，扫描结论说没干**。上一份交付件里 147 这个数字，至少一半是这类误报。

修正（commit `4228798b1`）：
- 新增 `SAFE_WRAPPERS = {"safe_urlopen"}`，VICTIM 与 SUSPECT 两个分支都放行
- `auth_urlopen` **刻意不入白名单**：`agent_platform/legion_command/hermes_auth.py`
  的实现只加认证头、不碰代理，目标若是回环它仍应被判受害
- 顺手修掉上一编辑中误删的 `f = node.func`（不修则 `is_urlopen_call` 运行即 NameError）
