# 屏幕抓取采集盘口：虚拟机多开方案可行性实测

> 起因：L2 数据被沙箱锁死（2026-10-23 起 QMT 禁文件/网络/数据库），屏幕成为唯一合法出口。
> 老田提出「虚拟机多开 + 每台看一只票 + 定时截图 + 结构化」。
> 本文全部结论来自本机实测，不引用二手资料。
> 环境：AMD RYZEN AI MAX+ 395 / 16C32T / 127GB / Win 2560×1600。

---

## 一、一句话结论

**方案成立，实测 100% 准确，但不需要虚拟机。**

Win32 `PrintWindow(PW_RENDERFULLCONTENT)` 能直接抓**后台窗口**（被遮挡也行、不用置顶、不用多桌面），
所以一台机器开 N 个客户端进程即可，虚拟机是纯浪费。

---

## 二、五个决定性数字

| 环节 | 实测 | 说明 |
|---|---|---|
| 截图（PrintWindow） | **54ms** | 串行 18.5 张/秒，4 线程 27.9 张/秒 |
| 单帧识别（20 档×2 列=40 格） | **559ms** | ddddocr 整格，`vol` 单位=手 |
| **识别准确率** | **600/600 = 100%** | 30 帧整帧全对（每帧 20 档全中） |
| 单线程产能 | 2 帧/秒 | 3 秒周期 → 6 只/线程 |
| 整机估算 | **50~80 只** | 32 线程，CPU 饱和折半 |

**全市场 5,200 只做不到**：需 1,700 帧/秒，差 60 倍。但游资重点池 50~100 只绰绰有余。

## 三、三个坑，每个都能让方案归零

### 坑 1（最致命）：浏览器窗口会被"冻结"，截图拿到旧帧

用 Chromium（Edge/Electron 壳的行情软件）做测试，tick 后连拍 8 张：

```
静置:    1e476cb7 -> 1e476cb7   稳定
tick 2:  27ms=1e476cb7  103ms=c7a5b5be  658ms=81cd8926   ← 有延迟
tick 3:  27ms=81cd8926  ← 和上一帧完全相同
tick 4:  24ms=81cd8926  ← 数据在变，画面不动
```

真值 seq 在递增，画面哈希不变 —— **Chromium 检测到窗口被遮挡就停渲染**，
PrintWindow 一直读缓存的合成表面。同样代码在这个环境只有 **6.2%** 准确率。

**通达信/同花顺是传统 Win32 GDI 程序，内容直接画到窗口 DC，没有合成器**。
用同机制自建 GDI 窗口对照：**600/600 = 100%**。

> 判断口径：目标程序是不是 GDI 绘制。是 → 直接可用；是 Chromium 壳 → 需 `--disable-backgrounding-occluded-windows` 并保证不遮挡，否则不可用。

### 坑 2：字号 < 12px 时 OCR 崩，≥16px 才稳

同一套 OCR，不同字号的整格识别正确率（每档 40 次）：

| 字号 | 价格全对 | 手数全对 |
|---|---|---|
| 11px | 31/40 | **12/40** |
| 13px | 38/40 | 35/40 |
| **16px** | **40/40** | **40/40** |
| 20px | 40/40 | 33/40 |
| 24px / 32px | 40/40 | 40/40 |

**行动项：通达信字体调到 16px 以上**（系统设置→字体），这一项能把准确率从 30% 拉到 100%，成本为零。

### 坑 3：OCR 不吐小数点，必须按位数还原

`1680.11` 被识别成 `168011`。A 股价格固定 2 位小数（可转债/ETF 3 位），
用 `int(d)/100` 还原即可。**但必须先校验位数**：6 位正常，5 位说明漏识，丢弃该格而不是硬猜。

判定标准位数要用**整版 20 档的众数**，不能用首帧——首帧若漏一位，标准被带偏，
后面全按错的位数判，实测准确率从 100% 掉到 38%。

### 坑 4：取样高度必须小于行距，否则吃掉下一行笔画

行距 27px 时如果直接切 27px 高，会把下一行顶部笔画带进来：

| 取样高度 | 逐格准确率 |
|---|---|
| 27px（=行距） | 80.4% |
| **21px（=行距-6）** | **100%** |

`h = min(row_h - 6, 22)` 是经验值。**这一条比换 OCR 引擎更有效**——
不用改模型、不增加耗时，只改一个切片高度，准确率差 20 个百分点。

## 四、为什么不用虚拟机

| 方案 | 内存 | 磁盘 | 启动 | 截图 | 结论 |
|---|---|---|---|---|---|
| 虚拟机 ×50 | 50×4GB=200GB | 50×20GB=1TB | 每台 20s | 需虚拟显示 | **不可行**（内存不够） |
| 虚拟机 ×15 | 60GB | 300GB | 慢 | 需虚拟显示 | 能跑，但没必要 |
| **多开客户端 ×50** | **~10GB** | **50×200MB=10GB** | 秒级 | PrintWindow 直接抓 | **推荐** |

虚拟机唯一价值是**账号隔离**（一个券商账号只能登一个客户端）。若同一账号，多开进程就够。

多开方法：通达信支持多目录副本（复制安装目录，各自独立 `T0002` 配置），
每个副本登录后切到不同股票，窗口标题带股票代码便于定位。

## 五、架构

```
┌─ 采集进程（单进程多线程）──────────────────┐
│  窗口发现: EnumWindows + 标题正则           │
│    ↓                                        │
│  PrintWindow 后台截图  ~54ms/窗             │
│    ↓                                        │
│  网格标定（一次）：行投影 + 列投影           │
│    ↓                                        │
│  逐格 ddddocr  ~12ms/格                     │
│    ↓                                        │
│  小数点还原 + 位数校验 + 异常丢弃            │
│    ↓                                        │
│  结构化落盘 JSONL / parquet                 │
└─────────────────────────────────────────────┘
```

输出结构（每帧一行，与 `tick_YYYYMMDD.parquet` 同粒度）：

```json
{"ts": 1791878400.12, "code": "600519", "src": "tdx_l2",
 "asks": [[1680.11, 3056], [1680.10, 53993], ...],
 "bids": [[1679.99, 22962], ...],
 "ok_rows": 20, "conf": 1.0}
```

`conf` = 本帧完整识别行数 / 应识别行数，低于阈值（建议 0.9）整帧丢弃，
**宁可缺帧也不要错帧**。

## 六、与已有数据的关系

| 数据 | 粒度 | 历史 | 覆盖 | 成本 | 可入库 |
|---|---|---|---|---|---|
| pytdx 3 秒分笔（已有） | 3 秒 | **9 年** | 5,217 只 | 0 | ✅ |
| **屏幕抓取盘口（本方案）** | 可到 1 秒 | **从今天起** | 50~80 只 | 0 | ✅ |
| QMT L2 | 毫秒 | 无 | 沪深不全 | 30~60 元/月 | ❌ 沙箱 |

**屏幕抓取补的正是"十档 + 委托队列"这块，但只对重点票、只从今天起**。
历史部分永久缺失，任何方案都补不回来（L2 不存历史）。

## 七、必须承认的边界

1. **只能盯重点池，不能全市场**。50~80 只是上限。
2. **没有历史**。开通当天往前一条都没有，不能回测。
3. **手数是聚合值**。十档挂单手数能看到"这一档挂了 3008 手"，
   但看不到"这 3008 手是 1 笔还是 100 笔"——除非用千档队列（1980 元/年那档）。
4. **身份依然不可知**。委托队列只给手数不给"谁"（港股才有 `brokerqueue`）。
   前几轮已证明：794 万门槛下，1 亿藏不住；归因不可做。
   **屏幕抓取解决"手法"，不解决"身份"。**
5. **未验证真实通达信**。本机无通达信，用同机制 GDI 窗口对照。
   真实环境需确认：①是否 GDI 绘制 ②窗口标题是否带代码 ③多开是否被限制。

## 八、交付物

| 文件 | 作用 |
|---|---|
| `tools/research/screen_book_collector.py` | 采集器主程序（含标定、采集、落盘、CLI） |
| `tools/research/template_ocr.py` | 字符模板匹配 OCR（备用，速度更快但需标定） |
| `tools/research/gdi_book_window.py` | GDI 模拟窗口（测试用，也是"如何造可抓窗口"的参考） |

用法：

```bash
# 1) 标定（第一次用，确认行/列坐标）
python screen_book_collector.py --title "600519" --calibrate --out data/screen_book

# 2) 采集
python screen_book_collector.py --title "600519" --code 600519 \
       --duration 3600 --interval 3 --out data/screen_book

# 3) 先干跑确认
python screen_book_collector.py --title "600519" --frames 3 --dry-run
```

## 九、下一步（按性价比排序）

1. **装通达信 + 调字体 16px + 标定一只票**，实测真实准确率（半天，零成本，决定方案生死）
