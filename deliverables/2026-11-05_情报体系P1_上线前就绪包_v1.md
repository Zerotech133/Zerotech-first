## 1. 为什么做这件事：三句"文档里的承诺"没有机制支撑

P1 到 v1.8 为止，质量数字已经到底（拆散 0 / 误合并 0 / 来源数 14/14），但上线还剩三个**只有人记得才成立**的前提：

| 承诺 | 写在哪儿 | 不成立的后果 |
|---|---|---|
| "语料变更后必须重跑标定" | 技术债 #17 的处置栏 | 语料一改，`0.05` 与 `v2` 的结论**静默过期**，口径照用、日志照常好看 |
| "把台账纳入备份" | §9 第 1 条 | 台账含人工裁决，丢了不可重建；且没有任何脚本会去备份它 |
| "标定要重跑" | §9 第 2 条 | 更隐蔽：**在工作库上跑出来的标定结论不是"过时"，而是"不成立"**（见 §4.1） |

这三条的共同点是失效形态一致：**不报错、不告警、数字仍然合理**。这和 v1.4 那次真值标注错误是同一类风险——错的东西长得和正确的东西一模一样。本轮把它们逐个变成可校验的物证。

## 3. 标定戳：把"依据"变成可校验物证

### 3.1 戳长什么样

`data/story_calibration_stamp.json`（真机实际内容，2026-11-05 04:22 生成）：

```json
{
  "borderline_margin": {
    "fingerprint": "sha256:debc4adfcbd2da2be85f8a32c58774c862c403a2ada85153194bca9e67916196",
    "units": 50,
    "at": "2026-11-04T20:22:43Z",
    "detail": {
      "recommended_margin": 0.05, "threshold": 0.75, "recall_gate": 0.6,
      "pairs": 27, "pairs_same": 19, "truth_units": 33,
      "reason": "missed 归零的最小带宽"
    }
  },
  "judge_prompt": {
    "fingerprint": "sha256:debc4adfcbd2…（同上）",
    "units": 50,
    "at": "2026-11-04T20:21:15Z",
    "detail": {
      "probe_fingerprint": "sha256:fe966f23b788…", "probe_size": 24,
      "variant": "v2", "repeat": 1, "missed_merge": 0, "false_merge": 0,
      "label_flips": 0, "errors": 0
    }
  }
}
```

两枚戳的语料指纹**完全一致**，这是交叉验证：带宽标定与提示词标定在不同时间、不同代码路径上算出同一个哈希，说明"语料"这个口径被统一了（§4.2 是统一之前的样子）。

### 3.2 三条刻意的设计

1. **指纹与行序无关**：按 `unit_key` 排序后再哈希。DB 返回顺序不保证稳定，不排序会把"顺序变了"误报成"语料变了"——一张狼来了的告警卡，第三次之后就没人看了。
2. **`null` 真值 ≠ 缺真值**：`truth_story` 为 `null` 是"独立事件"这一**合法结论**（独事实按定义不与任何事件合并），必须与"这一行没标真值"区分。否则把独事实补上真值、或反过来把真值改成 null，指纹都不变——最该检出的一类变更恰好检不出来。实现上用 `WHERE extension ? 'truth_story'`（判键存在）+ 哨兵 `\x00`（表示 null）。
3. **两类标定互不覆盖**：写提示词戳不会顺手刷新带宽戳。否则"只重跑了一半"看起来像全跑了，而这正是分两次作业时最容易发生的事。

### 3.3 校验状态必须能分辨

`verify()` 返回 `ok` / `missing` / `stale` / `corrupt` 四态，不是布尔：

- `missing`（从未标定，或戳被删）与 `stale`（语料变了没重跑）**处置不同**——前者要跑标定，后者要跑标定且检查是谁改了语料；
- `corrupt`（戳文件损坏）走"重建"路径，但**读的时候必须抛** `ValueError`。静默当空会把"已过期"降级成"从未标定"，排查方向直接跑偏（与台账口径一致）。

## 4. 三个真机踩出来的问题

### 4.1 在工作库上标定，结论不是"过时"而是"不成立"

第一次跑 `calibrate_borderline_margin.py`，结果不对：

| 项 | 预期 | 实际 |
|---|---|---|
| 候选配对 | 27 对 | **1 对** |
| 其中真同事件 | 19 对 | **0 对** |
| 推荐带宽 | 0.05 | **0.00** |

根因不是脚本坏了，是**方法学前提被破坏**：工作库已跑过多轮聚类（29 事件 / 42 成员 / 50 事实），已合并的配对不再进候选集，只剩 8 条未分配事实两两比较。

危险之处在于：`0.00` 是一个**看起来正常的数字**。它读起来像"带宽可以收窄到 0"，实际含义是"没有样本"。任何"样本不足仍照算"的脚本都会给出这种答案。

两道防线：

1. **标定脚本拒绝落戳**：候选 < 5 对或真同事件 < 1 对时打 WARN、说明"最常见原因是工作库已分组"、**不写戳**。戳不写，自检就报"从未标定"，人必然去查为什么。
2. **`make_calibration_db.py`**：用 `CREATE DATABASE ... TEMPLATE` 克隆工作库（结构 + 数据 + 向量一并复制），在克隆里清掉 `osint_story_member` / `osint_story`。不重新灌语料是因为 `seed_verify_corpus.py` 不写向量，重灌还得再跑一遍 embedding。克隆库只用于标定，不接服务。

克隆后重跑，**0.05 精确复现**：候选 27 对 / 真同事件 19 对 / 带内该合 1·不该合 1 / LLM 2 次调用——与 v1.6 档案记录逐项一致。这是本轮最有价值的一个数：它证明 v1.6 的结论可复现，而不是一次性巧合。

### 4.2 两个标定脚本对"语料"的定义不一致

戳写完后自检报 `units=33`（带宽）与 `units=50`（提示词），指纹天然不可比。

根因：带宽标定取"真值非空"的 33 条参与配对，落戳时却用全量真值键 50 条；提示词标定用全量 50 条。**两个脚本各自都自洽，合起来不自洽。**

统一到规范定义：键存在即计入（50 条），null 用哨兵。注意 `detail.truth_units=33` 保留原值——它记录的是"实际参与配对的条数"，与指纹的口径不同，两者都有用，但不能混为同一个字段。

处理方式：删掉旧定义下生成的那枚带宽戳（`units=1`、样本不足），**保留有效的提示词戳**，重跑带宽标定后两枚指纹一致。这里没有"清空重来"，因为提示词那枚是真的跑过 24 对探针、零误合并。

### 4.3 变异测试子进程递归调用自身

`test_calibration_stamp.py` 的变异用例在子进程里跑 `pytest tests/test_calibration_stamp.py`，子进程又跑一遍变异类 → 无限递归，`timeout 240` 被 SIGTERM 打断。

修法：变异类由 `OSINT_MUTATION=1` 控制启用，子进程环境里**显式清掉该变量**：

```python
env = {k: v for k, v in os.environ.items() if k != "OSINT_MUTATION"}
```

默认运行 1.2 秒跳过变异类，需要时 `OSINT_MUTATION=1` 单跑，5 个变异全部暴露。另加一道防"误判为捕获"的检查：子进程若因 `ImportError` 挂掉，也算"失败"，但那种失败**不能算变异被捕获**——现在会断言输出里出现的是断言失败而非导入错误。

## 5. 自检脚本：9 项，把上线变成一次配置切换

`python scripts/story_release_preflight.py` 覆盖七类事实、实际输出 9 行结论（标定与备份各拆两行）：

| 组 | 检查项 | 判据 |
|---|---|---|
| 标定 | `borderline_margin` / `judge_prompt` | 重算指纹与戳比对；`missing`/`stale`/`corrupt` 一律 FAIL 并给出重跑命令 |
| 状态文件 | 台账 + 队列两件 | 在册数量；**缺失不算失败**（首次部署就是缺），但在报告里列名 |
| 备份 | 最近备份可用 + 新鲜度 | `MANIFEST.json` 逐文件 SHA256 复核；超过 N 天 WARN |
| 口径 | `margin=0.05` / `variant=v2` | 与档案定档值比对，防"代码改了配置没改" |
| 运行态 | `story_borderline_judge` | `off` 判为 OK 并注明"待裁定项 1，不是缺陷" |
| 人工台账 | 裁决条数 | 解析失败即 FAIL（台账坏了本身要暴露，见 §3.3） |
| 队列 | 积压条数 / 滞留天数 | 双维度；`0` 视为关闭 |

真机结果（两次，间隔约 30 分钟）：

```
首次：2 FAIL / 1 WARN / 其余 OK
      calibration.borderline_margin  FAIL  从未标定
      calibration.judge_prompt       FAIL  从未标定
      backup                         WARN  没有可用备份
--backup 之后：
      合计：9 OK / 0 WARN / 0 FAIL / 0 SKIP
```

备份产物：`backups/story_state/20261104T202258Z/`，含 `MANIFEST.json`、`SHA256SUMS`、`story_borderline_pending.jsonl`；自检复核"1 个文件摘要全部一致"。备份目录按 `YYYYMMDDTHHMMSSZ` 命名，`latest_backup()` 只认这个格式，不合格式的目录忽略（避免人手工放的副本被误当最新备份）。

值得记一笔：`numpy 2.5.4` 已装但 `cv2` 没装，说明依赖不是成套安装的；`uvicorn` 缺失则是**两个解释器不共享 site-packages**（主 pytest 在 `AppData\Roaming\Python\Python313`，子进程用 `binaries\python`）。这类"半装"状态最容易被误当成代码回归——判别方法很简单：看报错是 `ModuleNotFoundError` 还是断言失败。

本轮**未擅自安装**这两个包：它们会改变本机 Python 环境，且与 P1 无关。装法写在这里供需要时执行：


## 7. 限度（必须写清楚）

1. **自检只校验"标定依据是否过期"，不校验"标定结论是否仍然最优"**。指纹一致只说明"语料没变"，不说明"0.05 仍然最好"——后者只能靠重跑标定看 `missed`/`noise` 两列。
2. **指纹只覆盖真值语料**，不覆盖向量、别名表、`RULE_DIRECT_SIMILARITY` 等。别名表变了会改变 `unit_key → entity` 的映射，进而影响配对，但指纹不变。这是一个已知盲区，暂不处理（扩指纹会让"什么算语料"变成新的争议点）。
3. **`make_calibration_db.py` 依赖 PG 模板克隆**，要求源库没有活动连接（`CREATE DATABASE ... TEMPLATE` 的硬约束）。生产上跑需要在维护窗口。
4. **克隆库不会自动跟随工作库更新**。工作库灌了新语料，标定库还是旧的——这在戳上会体现为指纹不一致（自检直接 FAIL），但如果两边同时灌了新语料、又忘了标定，指纹仍然一致。**这类失效只能靠流程约束，不是机制能兜住的**。
5. **`WinError 5` 的重试覆盖的是不可重现的竞态**，价值是"可恢复"而非"已修好"。5 次耗尽仍会抛，并保留 `.tmp` 供取证。

## 8. 结论

`P1 从"能跑"变成"能按流程上线"`：

- 标定有过期检测，不再是文档里的一句话；
- 备份有脚本 + 有摘要复核 + 有新鲜度判据；
- 标定有专用库，不会再在工作库上算出"没有样本的 0.00"；
- 上线前一条命令给出 9 项结论，`--backup` 一次做完备份与复核。

仍然待裁定的还是那两件，本轮没有替人做决定：**生产是否常开临界带复核**、**跨窗口召回本周开不开**。
