## 2. 跨窗口召回 A/B：真机数据

### 2.1 为什么必须构造场景

跨窗口只在"**窗外有已归属的历史事件 + 窗内有一批还没归属的新事实**"时才有用。静态库一把跑完时，两个时点的事实都在同一个窗内，跨窗路径根本不触发——`cross_window_merged` 恒为 0，看起来像"开了没效果"。

所以 `cross_window_probe.py` 把时间轴人为折叠成滚动形态：

1. 大窗（60 天）跑一轮，全部成组 → 模拟历史已积累；
2. 删掉窗内（14 天）事实的成员关系、清掉因此空掉的事件 → 模拟新到批次；
3. 14 天窗再跑一轮 → 窗内是待归属新批次，窗外是已归属历史事件；
4. 对照组只改 `--cross-window` 一个取值，其余完全相同。

**它会 `DELETE FROM osint_story_member` / `osint_story`**，所以有三重护栏：库名必须以 `_calib` 结尾、必须 `--yes`、锚点为 0 时打 WARN 说明"本次结果不能用来判断跨窗效果"。两条护栏都实测拦住了（`PG_DB=osint` 直接 REFUSED）。

### 2.2 结果

场景：50 条事实，60 天全量成组得 32 事件 / 50 成员；剥掉最近 14 天后剩 **8 个锚点 / 8 个事件**，窗内 **42 条**待归属。

| 指标 | 关（`--no-cross-window`） | 开（`--cross-window`） |
|---|---|---|
| 事件数 | **37** | **33** |
| 拆散真值组 | **6**（S02 / S07 / S11 / S12 / S13 / S14） | **2**（S02 / S11） |
| 误合并 | 0 | **0** |
| `anchors_loaded` | 0 | 8 |
| `cross_window_merged` | 0 | **4** |
| 额外 LLM 调用 | 0 | **0** |
| 耗时 | 6.6 s | 3.1 s |

4 处跨窗合并明细（全部 `decided_by=vector`，走 `entity+similarity` 通道）：

| 事实 | 余弦 | 共同主体 | 真值 |
|---|---|---|---|
| `verify-s07-02` 隆基绿能再度提价，硅片价格上调5% | 0.923 | `longi` | S07 ✓ |
| `verify-s12-02` 中芯国际产能利用率超90% | 0.932 | `smic` | S12 ✓ |
| `verify-s13-02` 茅台提价20%，飞天出厂价上调 | 0.903 | `moutai` | S13 ✓ |
| `verify-s14-02` 欧盟对华电动车加征关税落地 | 0.904 | `eu` | S14 ✓ |

**结论：4 处全部为真合并，零误合并，零额外调用。** 收益来自"跨月发酵的同一件事不再被切成两个事件"，而不是靠放宽阈值硬合——护栏一条没动。

### 2.3 S02 为什么没被修好：不是阈值问题，是顺序问题

S02 是"华信科技立案（10-15）→ 处罚落地（11-02/11-03）"，跨 19 天。按余弦它**本该合并**：`s02-01` vs `s02-02` = **0.7282**（标题）/ 0.7968（标题+正文），都高于 0.70 门槛。

实测却拆着。加观测后拿到真因：

```
[cc]  跨窗候选池：19 个 pivot 走到第三路，s02-02 不在其中
[best] pivot=verify-s02-02 -> None sim=0.0000          ← 第一路：窗内无已归属，空
[best] pivot=verify-s02-02 -> verify-s02-03 sim=0.8542 ← 第二路：与窗内未归属配对成功
```

**`s02-02` 在第二路就和 `s02-03` 合成了新事件（0.8542），第三路（跨窗）根本没被走到。** 窗内先合本身是对的（窗内证据时间更近、可比性更高），代价是"窗内自成一簇 + 窗外才是同一件事的前半段"这种形态永远走不到跨窗。

这条必须写清楚，否则后人看到 S02 拆散会去调 0.70 阈值——**方向完全错**，调到 0.65 也不会生效，还会引入误合并。

正确解法是**事件级跨窗合并**（新事件整体去与窗外锚点比一次），属于 P2 范畴：它要动的是聚类主链路的顺序与合并语义，不是加一个 if。

S11 的拆散与跨窗无关（同窗内、余弦 0.7133 落在临界带），由临界带 LLM 复核解决——正好是本轮另一项。

## 4. 生产库 dry-run（只读）

```
跨窗口召回开启：窗内 8 条待归属，窗外 0 条锚点（180 天带）
units_scanned=8  stories_created=8  unrelated=2  borderline=0
anchors_loaded=0  cross_window_merged=0  judge_calls=0
```

两点必须解释清楚，否则会被误读成"没生效"：

1. **锚点 0 条**：60 天窗把 42 条已归属事实全部包在窗内，窗外 180 天内没有已归属事实。锚点池为空是窗口取数的必然结果，不是故障。
2. **临界带 0 对**：工作库已分组，`_load_units` 用 `NOT EXISTS member` 排除已归属事实，只有 8 条未分配事实参与，配对基数太小。临界带只在"重新分组"时才有规模。

所以生产库的这两项效果**只能在下一次真实滚动轮次里观察**。这也是为什么没有主动重算生产库：重算会改写事件表与独立来源数，属于生产数据变更，不是配置变更，应当由轮次自然发生，而不是为了验证去动它。

## 7. 限度与操作注意

1. **跨窗只覆盖"表述相近"的跨月对**。真机修好的 4 处余弦全在 0.90+；S02 那类"立案→处罚"的语义演进即便余弦达标，也会被窗内先合的顺序挡住（§2.3）。
2. **跨窗不产生额外 LLM 调用**：`_decide_cross` 走 vector 直判，护栏不通过就连判定器都不进。这与临界带复核的 2 次调用是两笔不同的账。
3. **锚点上限 2000 条 / 窗内候选每轮全算**。50 条语料下耗时 3 秒；语料上到万级后需要重新量，`CROSS_WINDOW_ANCHOR_LIMIT` 与 `_load_anchors` 的游标分页就是为那个场景准备的。
4. **`cross_window_probe.py` 会清库**。它只为一次性库设计，`PG_DB` 不以 `_calib` 结尾会直接 REFUSED。不要为了省事改这个判据。
5. **生产调度未在仓库内定义**。仓库里找不到 cron / systemd / 部署脚本的调用入口，因此无法确认调用方是否显式传了 `--borderline-judge off` 或 `--no-cross-window`（会覆盖 `.env`）。上线前需要核对一次真实调用命令：**只要没人显式传这两个参数，配置就会生效**。
6. 首次轮次建议观察三个数：`cross_window_merged`（应 > 0 且明细合理）、`borderline_rechecked`（应在 2 上下，明显变大说明门槛或语料变了）、`review_backlog.pending`（被提升的配对会入队，要有人看）。
