## 〇、一页结论（给老田）

**造物炉 = 把「一句话想法」自动锻造成「过了门禁、可开源、可回滚」的软件增量；平台只加一条薄链，不造第二平台。**

- **能这么干的原因**：自家已经证明单工单全自动可行——`tools/e2e_pipeline.py`（K-ORG-065）已跑通"开单→产码→SEC2 走查→QA1 复核→merge 零人工"；`tools/legion_worker.py` 已有 queued→claimed→doing→lease/heartbeat 闭环；DSH Team 已是 1 Lead + 8 并行。
- **缺的三块**：**想法入口**（从一句话到规格/任务）、**可信验真**（门禁不自证、独立评审、证据包）、**开源出口**（开源就绪门 + 发布 + 社区闭环）。本方案只补这三块 + 执行器适配层。
- **最大的坑不是模型，是门禁**：10-31 审计实证过"门可自证、env 可跳过、restricted exec 不是安全边界"；10-31 当日已修 H5-a/H5-b（master 钉扎 + 一次性 token）。剩余风险是**同模型自评、无独立验真、无变异测试**——所以 S0 只做只读验证与契约，**不重复造门锁**，不先加自动化。
- **三个数字目标（12 周）**：1 个想法/周全自动到"可发布"；老田人时 ≤30 分钟/想法；**门禁逃逸缺陷 = 0（硬指标）**。
- **三条红线**：L2 永不自动（服务/计划任务/凭据/nginx/宿主机/发布上线必须五要素人工批准）；主仓不整体开源（先开源工具组件）；不引第二平台/第二调度/第二 DB。

**一句话**：上一代把"写码"自动化了；造物炉要把"从想法到开源"这条链自动化，并把"凭什么信它"做成机器可验证的。

## 二、目标与非目标

### 2.1 North Star

> 老田每天花 **≤10 分钟**输入想法、看板审批；平台在无人值守下把想法变成**可验收、可开源、可回滚**的软件增量，每一步都有证据。

### 2.2 12 周成功判据（Go/No-Go 用）

| 判据 | 目标 | 测法 |
|---|---|---|
| 想法闭环 | ≥3 个真实想法走完全链（想法→规格→执行→验真→合并/发布） | 每个想法有 IdeaCard + spec 冻结 sha + run 账本 + evidence pack |
| 全自动率 | ≥60% 任务无需人工改码即达 merge-ready | run 账本统计；人工改码 = reviewer/human 提交 diff |
| 人时 | 老田 ≤30 分钟/想法（含审批） | 审批记录时点差 |
| 质量 | 门禁逃逸缺陷 = 0；门禁绕过 = 0 | 逃逸缺陷 = 合并后 14 天内需回滚/热修且非外部原因 |
| 开源 | ≥1 个组件公开发布（private→public，含 SBOM/CI/双语文档） | GitHub tag + release 资产 |
| 成本 | 每想法 ≤ 预算上限（见 §8.4） | provider usage 账本 |
| 回滚 | 任一 run 可按单回滚；演练 ≥2 次 | 回滚记录 + 新进程/新代码验证 |

### 2.3 非目标（红线段，越线即评审门拒绝）

1. **不自动做 L2**：重启/计划任务/凭据/nginx/宿主机/生产发布 → 永远五要素人工批准（判例 K-STOCK-416）。
2. **不做交易/资金自动化**：量化产线维持纸面/模拟边界（README 红线）。
3. **不整体开源主仓**：含私有数据、账户、内部注册表、情报源凭据；只开源工具/组件层（见 §9）。
4. **不造第二平台**：不新增入口/端口/DB/调度/认证；不引入 K8s/Temporal/MQ/微服务（ZBF v1、11-02 调研结论）。
5. **不自动改门禁/测试基线/审批人/凭据**：这些文件属于"禁止写域"，只能走治理道（ADR + A0 批）。
6. **不自动加依赖**：新依赖必须 SPEC 阶段声明 → 人审 → lock 文件同批提交（许可证门见 §9.2）。
7. **不做"AI 自评自批"**：执行者与评审者必须不同厂商模型；L2 只能老田/A0。
8. **不在 WIP 超限时开新想法**：先收口，再开炉（见 §5.3 熔断）。

## 四、全自动流水线（八环节规格）

### 4.1 环节 1：想法入口（Idea Intake）

**输入渠道**（按轻到重）：
1. 飞书/终端一句话：`forge idea new "做一个把学习材料自动排版成期刊的小工具"`；
2. `/briefing` 研究题 → 一键"立项"；
3. `/case` 七步会诊（复杂/高不确定想法）：复用现有 Case 服务端 orchestrator（田丰汇总→5 角色→会议→方案→人审→下发）；
4. 过期计划锚点 / `STATUS.md` 待决策项（手动转）。

**IdeaCard v1（草案字段）**：
```json
{
  "schema": "zb.idea/v1",
  "idea_id": "I-20261104-0001",
  "owner": "laotian",
  "one_liner": "一句话想法（≤50 字）",
  "user": "谁用（老田本人/团队/开源用户）",
  "problem": "解决什么问题（≤200 字）",
  "first_milestone": "最小可验证版本（MVP 边界）",
  "non_goals": ["明确不做什么"],
  "acceptance_hints": ["可执行判据 1-3 条"],
  "risk_level": "L1 | L2",
  "open_source": "yes | partial | no",
  "constraints": {"deadline": "2026-11-30", "budget_cny": 100, "max_tasks": 8},
  "source": "feishu | cli | briefing | case | status",
  "status": "draft | triaged | approved | forging | frozen | done | aborted",
  "created_at": "2026-11-04T07:50:00+08:00"
}
```
**自动动作**：AI 只问 ≤3 个澄清问题（缺 user/problem/验收判据时）；自动判定 risk_level（触及 L2 面、凭据、生产、公开数据 → L2）；自动给开源建议（是否适合开源、建议许可证）。
**人工闸门**：IdeaCard `approved` 必须老田点击（E1 起是唯一必点动作之一）。**时长目标：30 秒/想法**。

### 4.2 环节 2：规格锻造（Spec Forge）

产出 **spec/v1**（冻结，sha256 入账）：
- PRD-lite：目标 / 用户 / 范围 / 非目标 / 风险 / 回滚；
- **验收测试先行**：spec 阶段生成 `tests/acceptance/<idea>/`，冻结为 spec 工件；**执行器不得修改验收测试**（写域禁改，门锁校验）；
- 任务 DAG（`task_dag/v1`）：节点字段 = `{id, title, deps, write_scope, lane(fast|standard|governance|L2), q(Q1-Q4), executor_hint, model_tier, budget_cny, acceptance_refs, dod}`；
- 开源计划：开源范围、许可证、依赖预算、发布形态；
- 设计约束：必须引用既有判例（grep `docs/plans`、`docs/audit`），无判例则标注"立新档"。

**人工闸门**：spec 若含 L2 组件 / 新依赖 / 公共数据 → 老田审批；其余 E1 阶段批一次即可。
**失范检测**：spec 若出现"无验收判据""无回滚""无开源计划（当 open_source=yes）" → 自动打回。

### 4.3 环节 3：派单（Dispatch）

- 每任务 = `tools/devtask.py new <TID> <一句话>` 建独立 worktree + 分支 `task/<TID>`；
- 登记 `.worktrees/tasks.json`（复用现有账本）+ `agent_platform/data/forge/runs/`；
- **写域互斥**：任务声明 `write_scope`；同一文件同一时段只允许一个 owner；共享文件（AGENTS/ROADMAP/ADR/registry）只允许单写域；
- **WIP 熔断**（新增，dispatch 前强制检查）：
  - 全局：doing ≤ 上限、worktree ≤ 上限、dirty 文件 ≤ 上限（取当日 A0 口径，如 ADGS 的 doing≤8/worktree≤20）；
  - 单想法：并行任务 ≤ `constraints.max_tasks`（建议 ≤3）、单 Agent 并行写 ≤2（ADGS 纪律）；
  - 预算：本日/本月剩余预算 > 0；
  - 超限 → 想法进 `parked` 队列，不派单，日报标注（不静默）。
- **合并车纪律**：只向 16:30–17:00 / 21:40–22:10 窗口投递；窗口外只产 merge-ready，不硬合。

### 4.4 环节 4：执行（Run）

**执行器适配器契约 `executor_adapter/v1`**（草案）：
```
prepare(run_spec) -> {worktree, env_policy, budget}
exec() -> {status, steps[], artifacts[], usage{tokens_in,out,cost}}
events() -> 逐条事件（type: action|observation|error|usage|done；seq 递增）
cancel() / resume(checkpoint) -> 支持长任务接续
collect() -> {diff, changed_files, test_summary, logs}
```
**首个适配器**：`dsh`（现役 DSH Lead/teammates，主执行器）；**第二个**：`aider`（Apache-2.0，git 自动提交、SEARCH/REPLACE、Windows 友好）；第三个候选：Qwen Code / Codex CLI / Gemini CLI（headless JSON）；OpenHands（需 Docker）列 P2 评估。
**run 生命周期**：`queued → running → verifying → merge_ready → merged | rejected | failed | cancelled | aborted`，每次转移落 append-only JSONL（复用 `engine/tasks.py` 纪律）。
**安全边界**：
- 独立 worktree + `exec_runner` 白名单命令（现有）；
- 环境净化（去 KEY/TOKEN/PASSWORD/PROXY/COOKIE）；
- 禁止 shell 元字符、禁止 worktree 外路径、超时/输出上限；
- 网络：P0 默认无外网（黑白名单由 policy 控制）；P1 对"不可信执行"升级容器/WSL2（见 §8.5）；
- 每 run 预算（token/¥/步数/时长）硬上限，超限立即取消并记 `budget_exceeded`。

### 4.5 环节 5：验真（Verify，本方案最硬的一层）

**五道验真，缺一不 merge**：

1. **机器门**：现有九道门 + `test_gate -Suite fast` + `composition validate` + `kernel_guard` + route/budget/metadata/secret/import 门（全部复用，不重写）。
2. **门锁（修 H5）**：
   - gate 脚本、baseline、pytest 配置必须从 **master 固定 sha** 读取（`git cat-file` 取内容并校验 sha256），**不接受分支提交的 gate 代码**；
   - `DEVTOOL_PREFLIGHT_DONE` 环境变量跳过机制 → 改为**一次性签名令牌文件**（含 TID + HEAD sha + nonce + TTL，本地 HMAC，消费即失效）；
   - `test_baseline.json` 只允许"减少 known"的 ratchet（新增 known 需要治理道审批）；
   - 分支若改门禁/基线/验收测试文件 → 自动拒收（写域禁改）。
3. **独立验真**：clean checkout（新 worktree，不继承分支工作区）→ 由验真器用 master 门脚本跑一遍 → 结果与本分支自跑结果比对；不一致 → 阻断。
4. **独立评审**：跨厂商模型（执行器与评审器不同厂），只读工具（Read/Grep/Diff），rubric 1–5，必须引用 `file:line` 证据；三态 `PASS / CHANGES / BLOCK`；无证据不得 PASS；同模型自评自动作废。
5. **测试质量门**：变异测试（对改动模块，mutmut）分数低于阈值（建议 ≥60%，待校准）= 阻断；验收测试覆盖每条 acceptance；flake 检测（同测试重跑 3 次）。
6. **人审抽样**：L1 抽 10%（老田或授权 reviewer）；L2 100% 人审；抽样是"兜底"不是"替代"。

**证据包 `evidence_pack/v1`**（每个任务一份，落 `agent_platform/data/forge/evidence/<idea>/<task>/`）：
```
task_id / idea_id / commit_sha / branch / base_sha
changed_files[] + diff_sha256
gates[{name, version, script_sha, rc, artifact_path, output_sha}]
tests{suite, passed, failed, skipped, coverage_delta}
mutation{score, killed, total}
reviewer{model, provider, verdict, citations[], round}
run{run_id, executor, model, started_at, duration_s, tokens, cost_cny}
commands[]（全文+rc+输出摘要）
rollback{command, verified_at}
owner / created_at / signature（本地 HMAC）
prev_hash / hash（链式，复用 OS Goal 哈希链模式）
```

### 4.6 环节 6：合并与发布（Merge / Release）

- **E1/E2**：`merge_ready` 状态 → 人工按批审批（飞书卡：任务+证据包摘要+风险+回滚）→ 走 `devtask merge`（现有九道门）；
- **E3**：满足白名单 + 门全绿 + 独立验真 PASS + 独立评审 PASS + 预算内 + 非治理/L2 + 当日自动合并额度未满 → 自动进 merge train 窗口合并；每日自动合并 ≤N（建议 5）且仅窗口内；
- **发布**：L1（静态页面/文档/工具）可自动部署（换血验证：新进程/新文件生效 ≥ 文件 mtime + 冒烟）；L2 一律转五要素审批单（命令全文/影响面/不可逆点/替代方案/回滚预案），老田签字后才执行；
- **回滚**：每任务独立 commit + 每想法独立分支；合并失败/回滚演练纳入 S2 出口。

### 4.7 环节 7：开源发布（Open-source）

见 §9。核心是**开源就绪门（OS Gate）**：机器检查 7 项 + 人审 1 项，全绿才允许 private→public。

### 4.8 环节 8：社区闭环（P3，可选）

公开仓库 issue（bug/feature/security 模板）→ 自动 IdeaCard（`source=github_issue`）→ triage（人审 5 分钟）→ spec → 执行器产 PR → 同一门禁 + 独立评审 → 维护者合并 → release。
- 安全类 issue **不走公开自动链**（私下渠道 + 人工处置）；
- 贡献者 PR 与内部任务走**同一套门锁/门禁**（CI），维护者保留最终合并权；
- 不做"AI 海量灌 PR"：只接受策展过的 backlog，防止开源品牌被 AI 噪声反噬。

### 6.2 门锁（Gate Lock）：现状与剩余缺口（2026-11-04 实测校正）

> **校正（v1.1）**：H5-a/H5-b 已于 2026-10-31 修复并合并——`tools/devtask.py::_quality_gate` 已调用 `tools/merge_gated.gate_pin_check`（`tools/test_gate.ps1` 必须与 master 完全一致；分支改 gate 或落后 master 即拒收；`tools/test_baseline.json` 仅允许 ratchet 只减 known）；`tools/merge_preflight.py` 已改为**一次性 token**（TID+HEAD 绑定、TTL、用后即删），不再认裸 `DEVTOOL_PREFLIGHT_DONE=1`；`docs_only` 已去掉 `.js`。**本方案不重复造门锁。**

剩余缺口（造物炉只补这三项，P1 再动）：
1. **独立验真器**（clean checkout 用 master 门复跑，见 6.3）；
2. **跨厂商独立评审**（见 6.4；现状 `sec2_review.py`/`qa1_review.py` 都调 `agent_coder.chat_auto`，同一 glm-4.6 → 同模型自评）；
3. **变异测试 + 统一证据包**（见 6.5 / §4.5）。
P0 只做**只读校验**：`forge verify` 读取 `gate_pin_check` 结果与 preflight token 状态，生成"门锁现状报告"，**不改门禁代码、不新增治理单**。

### 6.3 独立验真器（P1）

- clean checkout 新 worktree（`git worktree add --detach base_sha`）→ 应用分支 diff（或直接 checkout 分支但用 master gate）；
- 独立进程跑；只读工具；结果签名；
- 与分支自跑结果比对：不一致 → `verify_mismatch` 阻断并人工排查（可能是并发/环境/门被改）。

### 6.4 独立评审器（P1）

- 评审模型与执行模型**不同厂商**（例：执行 DeepSeek/GLM ↔ 评审 Claude/GPT；执行 Claude ↔ 评审 DeepSeek/Gemini）；
- 输入：spec（含验收）+ diff + 测试结果 + 判例摘要；输出：`PASS/CHANGES/BLOCK` + 理由 + `file:line` 引用 + 风险清单；
- 评审 prompt 内置"找茬"指令：优先找"测试没覆盖的行为差异""spec 歧义""回滚缺口"；
- 评审记录入 evidence，与门结果并列；评审与门冲突时以**更严**为准，并升级人工。

### 6.5 红队与回归（P2）

- 每周抽 1 个已合并任务做"穿透测试"：人工/红队尝试用已知假绿通道骗过验真 → 一旦成功立即停线整改（这是"验真器自己的测试"）；
- 事故 → 自动生成回归测试（复用 `agent_platform/evals/incident_to_test.py`）；
- 内部 golden set：用历史已结案工单（有已知正确修复）做"内部 SWE-bench"，衡量执行器/评审器质量（P2，评测集可脱敏后开源）。

**外推结论（待内部 golden set 验证，不做唯一依据）**：

| 档位 | 模型（示例） | 用途 | 约束 |
|---|---|---|---|
| T0 本地 | qwen3.5:9b | 分类/摘要/格式化/低风险文档草稿 | **不得直接驱动代码合并** |

**成本纪律**：先省后质——T0/T1 覆盖 70% 任务，T2 只用于关键步（≤30% 任务）。**不用"更贵的模型"掩盖"更烂的验收"**。

### 7.3 成本控制（P0 先粗，P2 接网关）

- 每 run：token/¥/步数/时长上限；超限取消（`budget_exceeded`）；
- 每想法：默认 `budget_cny`（建议 ¥100，待拍板）；超限 → 暂停等老田；
- 每日/每月：全局上限（建议日 ¥300 / 月 ¥3,000，待拍板）；到顶只跑 T0/T1；
- 粗估（待首月实测校准）：极省档 ¥5–15/想法（本地 + 便宜云）；均衡档 ¥30–80/想法；质量优先 ¥150–300/想法；
- P2 接 LiteLLM（11-02 调研推荐）：virtual key/预算/花费台账，替换本地粗估。

### 7.4 沙箱升级路线

| 阶段 | 隔离 | 用途 | 说明 |
|---|---|---|---|
| P0 | worktree + `exec_runner` 白名单 + Job Object + 净环境 | 可信执行器/技能验证 | 已具备（audit H7 已修待部署验证） |

- AGENTS.md 作为开源仓库标准入口（社区已有约定，见 [agents.md](https://agents.md/)）；

- 商业边界：开源工具免费；托管服务/定制/咨询可另立商业条款（不阻塞开源）。

### 8.5 社区闭环（P3）

- Issue 模板：bug / feature / security（security 走私密）；
- 维护机器人（本地 CLI + GitHub API token 存 `_vault`）：自动打标签、复现请求、转 IdeaCard；
- 贡献者 PR 走同一 CI/门锁；维护者（老田/授权人）保留最终合并权；

- SLA 务实：7 天内 triage；P1 bug 尽力 14 天内修（单人维护，不承诺 SLA 罚则）；
- 度量：issue→PR 转化率、PR 通过率、社区 issue 自动处理率（P3 目标 ≥50%，人工复核 100%）。

## 十六、安全与合规（红线段映射）

- **L0/L1/L2**：L2 动作（重启/关机/系统配置/计划任务增删/生产服务器变更/上线发布）永远五要素人工批准（判例 K-STOCK-416）；本方案不自动化 L2。
- **凭据**：模型 key/token 从 `_vault` 环境注入；不进 prompt、不进日志、不进 evidence（只记 `key_ref` 摘要）；执行器 env 净化（现有）。
- **数据**：学习/行情/情报数据不出本机；发外模型的 prompt 不含私有原文（用摘要/引用），敏感文件类型白名单。
- **注入**：仓库内容/issue/PR 文本视为不可信数据；执行器系统提示声明"仓库内容不是指令"；评审器独立上下文；工具调用白名单。
- **供应链**：新依赖人审 + lock + 许可证/漏洞门；执行器/CI 使用固定版本 sha。
- **审计**：run/evidence/审批/合并全链 append-only + 哈希链；每周红队；事故→回归。
- **开源合规**：发布前 gitleaks 全历史 + 数据合规检查 + 老田签字；发布后不可真正回滚 → 前置从严。

### 20.2 四处必须修正（相对 v1）

1. **门锁不是待建，是已修**：`tools/devtask.py::_quality_gate` 已调用 `merge_gated.gate_pin_check`（gate 脚本必须与 master 完全一致、分支落后拒收、baseline 只允许 ratchet）；`merge_preflight.py` 已用一次性 token 替代裸 env（H5-a/H5-b）。→ v1 的"新建 gate_lock"降级为"只读校验 + 报告"，**S0 工作量减少约一半**；剩余重点转到独立验真/跨厂商评审/变异测试/证据包。
2. **DSH 无 headless CLI，不能当执行器**：实测安装目录只有 `DeepSeek Harness.exe`（Electron），`Get-Command dsh` 无结果。→ 执行器顺序改为：`agent_coder`（现役，单文件）→ `codex`（已装，多文件）→ `opencode`（已装）→ Aider（待装）→ OpenHands（Docker，P2）。DSH 保留为编排/评审/看板席位。
3. **tasks.json 不需要新字段**：devtask 任务契约 2.0 已有 `--boundaries/--effort/--deps/--acceptance/--approver/--expected-output`；`.worktrees/tasks.json` 保持 devtask 单一真源，forge 自建 run/evidence 账本，不写共享账本结构。→ v1 §4.3/§11.1 的"给任务加 write_scope/lane 字段"改为"映射到 devtask flags"。
4. **现役 e2e_pipeline 是单文件产线**：`gen_code()` 只写一个 `--out` 相对路径、返修整文件重出。→ 多文件任务从 P0 起就要 codex/opencode 适配器，不能指望 e2e_pipeline 直接扩。
