### 1.1 xq 41 项的根因（此前"未定论"，本轮定论）

之前 triage 只写了"根因未定论"，怀疑是测试替身失效但没验证。本轮实测确认了，且**不是产品 BUG**：

```
xq_classify.py  →  safe_urlopen(req, timeout=...)          # 2026-10-30 d6505161d 起
safe_urlopen.py →  if is_loopback(host): _open_no_proxy()   # Ollama 在 127.0.0.1:11434 → 走这条
                →  _NO_PROXY_OPENER.open(url)               # OpenerDirector.open，不经 urlopen
测试替身        →  monkeypatch.setattr(urllib.request, "urlopen", fake)   # 完全失效
```

验证方式（不是推理）：

| 探针 | 结果 |
|---|---|
| `type(safe_urlopen._NO_PROXY_OPENER)` | `OpenerDirector`（自带 `.open`，绕开 `urllib.request.urlopen`） |
| `is_loopback('127.0.0.1')` | `True` → 必走 `_open_no_proxy` 分支 |
| 本机 11434 端口 | **OPEN**（Ollama 真的在跑 `qwen3.5:9b`） |

即：替身没生效，测试真的把每条样本都发给了本地大模型，答案随机 → 断言假红；耗时从秒级涨到 78s。

### 1.2 修复（改接缝，不是改断言）

四个文件统一改成 patch 被测模块命名空间里的 `safe_urlopen`（与 `test_peak_shift_gates.py` patch `xc.log`/`xc.ollama_probe_busy` 同法），并各加一个 autouse 兜底：

@pytest.fixture(autouse=True)

    monkeypatch.setenv("XQ_OLLAMA_LOCK", "0")        # 免等 120s 全局租约

## 2. 第二项：治测试隔离

### 2.1 全仓跑批挂死：根因定论

现象（复审确认，2/2 稳定复现）：`cd portal && pytest .` 跑到 26%~79% 之间停住，**不产出 summary**，栈停在 `os_goal_store.py:_file_lock` 的 `time.sleep(0.05)`。

根因不是死锁，是**超时判据用了墙钟**：

```python
deadline = time.time() + _LOCK_TIMEOUT_S     # 旧
while True:
    try: os.open(...)
    except PermissionError:
        if time.time() > deadline: raise
        time.sleep(0.05)                      # ← 栈停在这里
```

`time.time` 一旦被冻结（同目录 `test_ifs_idempotency.py:325`、`test_os_auth_hardening.py:91` 都直接 `setattr(X.time, "time", ...)` —— `X.time` 就是全局 time 模块），`deadline = 冻结值 + T` **恒大于** `time.time()`，循环永不退出。

A/B 对照（`_audit_20261108/probe_lock_deadline.py`，冻结 `time.time=1000.0`、`os.open` 恒抛 PermissionError、3 秒看门狗）：

```
old(time.time)        -> HANG（3s 内未退出）
new(time.monotonic)   -> gave_up
旧实现退出: False | 新实现退出: True
```

修复：两处 deadline 改 `time.monotonic()`（单调钟不受墙钟改动影响，这才是"超时"该用的钟），并加守卫用例 `test_file_lock_deadline_immune_to_wall_clock_freeze`——冻结墙钟后仍须在 deadline 内放弃。

顺带说明：这不只是测试问题。NTP 回跳或用户改系统时间同样能让这个锁"看起来永久持有"，生产路径也会挂。

### 2.3 顺带修掉另外两处隔离缺陷

**(a) `test_run_full_ok_rc0` 读线上真实 manifest**

`verify_daily_report.run()` 里 `check_source_health()` 吃的是默认值 `MANIFEST_JSON` —— 一个写死的线上绝对路径。线上 hot 源一旦 `failed`，这条"健康路径"用例就假红（本次实测：线上 `xq_hot_post.status=failed`）。

修法：`run()` 增加 `manifest_path: str = None` 注入点（默认行为不变），测试改为写临时 manifest。同时补一条此前**零覆盖**的用例 `test_run_full_source_degraded_rc1`，把"采集侧降级必须判红"钉住。

**(b) `test_absent_modules_really_blocked` 被 `sys.modules` 短路**

该自检假定 `xq_proxy` 不在 `sys.modules`。但 Python 的 `import` **先查 sys.modules，命中就返回，根本不走 meta_path**。`xq_proxy.py` 在盘上真实存在（16.8KB），全量跑时任何一次导入都会缓存它 → 自检恒 `DID NOT RAISE`（单独跑本文件是绿的，典型顺序依赖）。

机制已用 A/B 证明：

```
A 未缓存: ImportError（钩子生效，旧自检通过）
B 已缓存: 导入成功 -> 钩子被 sys.modules 短路（旧自检必假红）
```

修法：断言前把 4 件从 `sys.modules` 摘掉，结束后连同前序状态一起还原。污染态下复跑 `2 passed`。

### 2.4 复跑全量门时又抓出两处隔离缺陷（都不是功能回归）

第一次 fast 门（07:05）全绿。改完 overview 再跑（07:59）时，**同一份代码**多出 25 项红。逐条定性如下——两条与本次改动无关，是"测试结论随机器状态漂移"的老毛病被踩响：

**(a) `agent_key` 23 项全红：并发闸读的是本机真实状态**

```
SystemExit: 并发 worktree 数 65 已达上限 65（DEVTOOL_MAX_WORKTREES 可调）
  tools/devtask.py:1212 in _enforce_worktree_cap
  tools/devtask.py:1286 in cmd_new
```

`cmd_new` 第一步调 `_enforce_worktree_cap()` → `_active_worktree_count()` → `_prune_worktrees(REPO)`，数的是**这台机器上真实注册的 worktree**。测试夹具 `sandbox` 覆盖了 `WT_DIR`/`TASKS`/`ORG_JSON`/`DEV_GATE`，唯独没覆盖这一条。07:05 时是 64 个（放行），08:05 另一个并行会话开到第 65 个（撞上限）→ 整文件 23 项被同一条 `SystemExit` 连带判红。

修法：在 `sandbox` 夹具里钉住 `_active_worktree_count`（`tools/tests/test_devtask_worktree_mech.py` 对并发闸有自己的覆盖，且用的是同一手法，故不丢覆盖）：

```
23 failed, 24 passed  →  47 passed / 2.06s
```

**(b) `datawarehouse` 1 项：把时点快照钉在会增长的数据上**

```
assert con.execute("select count(*) from nodes where kind='strategy'").fetchone()[0] == 11
E       assert 12 == 11
```

策略源此刻是 12 个（其中 11 个带源假设，所以 `summary.strategies.with_source_hypothesis==11` 仍成立），DB 里 strategy 节点也是 12 —— 数据没坏，是断言钉死了旧数量。

修法不是把 11 改 12（下次还会红），而是改成**自洽等式**：库内 strategy 节点数必须同时等于「解析出的策略数」与「by_kind 统计数」，并留一条 `>= 11` 的下限防源塌：

```
库内 12 == summary.strategies.strategies 12 == summary.by_kind.strategy 12   → 2 passed
```

### 3.2 真正的危害不是"接口慢"，是共享锁连坐

原 handler：

```python
with _lock:                                  # ← api_health_portal._lock，跨模块共享
    if ...: _cache["data"] = build_overview()  # 12s
```

这把 `_lock` 同时罩着 `/api/health`、jev 缓存和 `_rate_hit` 限流计数。也就是说**一次仪表盘冷启，会把健康检查一起冻住**——监控侧会判服务不可用。

实测基线（线上 8091，旧代码，`_audit_20261108/loadtest_overview.py`）：

| 场景 | 指标 | 值 |
|---|---|---|
| 稳态（只打 health，48 次） | p50 / p95 / max | 9ms / **26ms** / 30ms |
| 冷启尖峰（6 并发，overview 与 health 同时打） | overview max | 2409ms |
| 同上 | **health max** | **2408ms（放大 90 倍）** |

同进程并发对照（`probe_lock_isolation.py`，6 个 health 线程持续抢锁）：

| 写法 | 构建耗时 | health 最长阻塞 | 被堵(>50ms)样本 |
|---|---|---|---|
| old（持 `_lock`） | 3.968s | **3964.6ms** | 6 / 120 |
| new（专用锁） | 0.012s | **0.0ms** | 0 / 127 |

### 3.3 拆解实现

`api_misc.py` 拆成三段 + 一个请求入口：

- `_overview_light()`：文件读取 + TCP 探测，实测 <0.1s，20s 缓存同步重建
- `_overview_heavy()`：容器 + 计划任务，**只由后台线程调用**
- `overview_cached()`：请求路径入口。轻项同步；重项**只读缓存**，过期则 single-flight 起一个 daemon 线程刷新，请求线程立即返回（首帧给空壳 + `meta`）
- `build_overview()`：原同步全量语义保留（非请求路径/测试用）

配套三件事，缺一个就会变成新的坑：

1. **专用锁** `_overview_lock`：缓存各管各的锁，不再共用 `_lock`
2. **single-flight**：并发只起一个刷新线程，防缓存击穿时的线程雪崩
3. **失败退避 5s**：docker/schtasks 持续失败时，若每个请求都触发刷新，会变成"请求量 = 线程数"。实测：持续故障下 100 次请求只起 **1** 个线程

新增附加字段 `overview_meta`（`heavy_age_s / heavy_ok / heavy_error / heavy_refreshing / heavy_ttl_s`），让前端/巡检能区分"正在后台刷新"与"确实没有容器"，而不是把空数组当真实状态。

### 3.5 回归守卫（`portal/tests/test_overview_split.py`，6 例）

① 冷启不阻塞（重项慢 3s，冷启必须 <0.5s）② 后台刷新能落地 ③ single-flight（10 次触发只起 1 线程）④ 失败退避（50 次触发只起 1 线程且 `err` 记录）⑤ 键集不变 ⑥ **源码守卫**：handler 不得再用共享 `_lock`、不得同步调 `build_overview()`、必须透出 `overview_meta`

第 ⑥ 条是这次最值钱的一条——它防的不是"现在写错"，是"以后有人为了省事把同步调用加回来"。

> 它按 `toolCallId` 记账、由 UI 侧批准。这也说明这类清理动作本来就该有人点一次头。

## 5.5 顺带暴露的第三个坑：`-Suite tools` 不在门里，契约自检长期红着没人知道

跑 `-Suite tools` 验证纳管时，冒出 5 项失败。查下来分成两类，**第一类是我自己今早造成的**：

### 一类：冻结清单契约（3 项，我造成的）

`test_test_gate_b1.py` / `test_test_gate_a5strict.py` / `test_test_gate_org_gate.py` 三处都把 `agent_key/quant_key/tools_key` 的**文件清单和数量钉死**，改列表必须同步改契约。而 `-Suite tools` 是"仅手工触发、不进 fast"的套件（`test_gate.ps1` 头注自己写着），今早加 4 个 quant 文件、这次加 1 个 tools 文件，**都没人同步**，于是三条断言一直红着。

| 项 | 契约值（旧） | 实际（改前） | 现在 |
|---|---|---|---|
| `quant_key` | 23 | **27**（今早 +4） | 27（同步） |
| `tools_key` | 20 | **21**（本次 +1） | 21（同步） |
| 三集合合计 | 95 | **100** | 100（同步） |

修法：把三处清单/计数同步到实际值，并注明每次加了什么。**没有放宽断言**——`assert set(...) == 常量` 这种精确相等保留着。

**复跑证据**：`-Suite tools` 从 `5 failed / 3417 passed` 变为 **`2 failed / 3420 passed`**（510.3s），剩余的 2 项就是下表的选股契约，与本次改动无关。

> 这本身就是"没进门的测试等于不存在"的第二个实例：上午刚把 4 个 xq 文件纳管进门，下午就发现纳管动作本身有契约要改，而那个契约不在门里。**纳管不只是加一行文件名。**

### 二类：与本改动无关（2 项，我没动）
