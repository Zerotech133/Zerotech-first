## 二、事实：闸一直在，参数是假的

```python
# tools/devtask.py:1088-1096（原文）
#   3) devtask new 并发上限（默认 60，env DEVTOOL_MAX_WORKTREES；>=80% WARN，>=上限硬拒）
WT_TTL_HOURS_DEFAULT = 72.0
MAX_WORKTREES_DEFAULT = 65          # ← 注释说 60，代码是 65
MAX_WORKTREES_ENV = "DEVTOOL_MAX_WORKTREES"

def _worktree_cap(): ...            # env 可调
def _concurrency_verdict(count, cap):
    if count >= cap: return "block"          # 65
    if count >= cap * 0.8: return "warn"     # 52
def _enforce_worktree_cap(): ...             # devtask new 前置硬拒（line 1228）
```

**这套机制的设计是对的**：纯函数可单测、env 可调、warn/block 两级、`new` 前置拦截。**唯一的错是一个数字。**

### 2.1 为什么 42 棵能长期存在

```
cap = 65
warn 线 = 65 × 0.8 = 52
实际 = 42
42 < 52  →  既 not block，也 not warn  →  完全静默
```

**所以过去 40 天没有任何人收到过"worktree 太多了"的告警。** 不是没人管，是**告警阈值被设在了永远不会被触碰的地方**。

### 2.2 还有一个被掩盖的真相

worktree 年龄分布：41/42 棵 ≤ 3 天。我上一轮读成"新的不停开"，**机制解释错了**：

```
TTL = 72 小时 → prune 把 >72h 的标 [TTL-RED]（只标注，不自动删）
+ merge 成功即回收 worktree
→ 结果：worktree 永远"年轻"，看起来健康
→ 真实并行度被 TTL 掩盖，只有 doing=21 才暴露真相
```

**这就是"指标看起来正常、系统实际超载"的典型形态。**

### 2.3 门禁是列表，加一道门 = 加一行

```python
# tools/devtask.py:433
GATES = [("Mixin方法集", _mixin_gate),
         ("导航统一", _nav_gate),
         ("端口注册", [sys.executable, ".../check_ports.py", "--strict"]),
         ("UI/UX审计", _ui_audit_gate),
         ("明文凭据", _secret_scan_gate),
         ("语法门", _syntax_gate),
         ("导入边界", _import_boundary_gate),
         ("元数据一致性", _metadata_gate)]      # 8 道门
```

`for name, cmd in GATES:`（line 2335）→ **加第九道「写域租约」只需要写一个函数 + 追加一行**。不需要重构、不需要新服务。

## 三、核心：拆成两个资源池，治理只碰其中一个

你以为治理会抢"研发"，其实它们不在同一个池子里：

| 资源池 | 内容 | 瓶颈 | 治理是否介入 |
|---|---|---|---|
| **算力池** | 训因子、训策略、回测、跑算法、批量推理 | GPU/CPU、39 GB 数据、时长 | **不介入**（只做数据分区租约） |
| **写权池** | 谁在改 master 上的同一批文件 | git 写锁、人的审查注意力 | 介入，但**只在"进门"那一刻** |

**关键事实**：训一天因子，可能产生 0 次提交、0 个 worktree、0 个分支。它对你的 git 仓和审查队列**没有任何压力**。所以治理它毫无意义——过去也没治理它，它照样在跑。

**治理只需要管一件事：成果要进 master 的那一刻。**

于是分成两条通道：

```
                    ┌──────────────────────────────┐
                    │  explore 通道（零治理）        │
训因子 ─┐            │  · 不占 WIP / 不排队 / 无证据包 │
训策略 ─┼──▶ 算力池 ──▶│  · 只要：数据分区租约 + 产物登记│──▶ 产物（parquet/模型/报告）
写算法 ─┘            └──────────────────────────────┘
                                    │
                           "这个成果要上线"
                                    ▼
                    ┌──────────────────────────────┐
                    │  ship 通道（强治理）           │
                    │  · 令牌 → ready → review →    │
                    │    merge → master             │
                    └──────────────────────────────┘
```

**判定规则（一句话）**：**改 master 上的契约/服务/页面 → ship；只在分支或工作区产出产物 → explore。**

按这个规则，你 90% 的日常动作在 explore，治理成本为零。

## 四、explore 通道：训因子/训策略/写算法的零治理方案

### 4.1 只加两件事，都不阻塞

| 机制 | 解决什么 | 成本 | 实现 |
|---|---|---|---|
| **数据分区租约** | 两个 Agent 同时写同一个 `stk_mins.parquet` / 同一个因子落盘 → 数据被覆盖（这是真事故，不是理论风险） | 一行命令 | `POST /gov/lease/acquire {scope:"data/part/factor_v3"}` → 409 表示有人占 |
| **产物登记** | 训了 500 个因子，没人知道哪个能用、哪个跑过、IC 多少 | 一个函数调用 | `POST /gov/artifact/register {kind:"factor", name, ic, sharpe, period, data_scope, sha256}` |

**注意：这两件事都不需要 WIP 配额、不需要排队、不需要证据包、不需要人工审批。**

### 4.2 数据分区怎么切（沿用现有结构，不改造）

```
quant_backtest/data/
├── tushare_curated/        ← 共享只读（全库统一，谁都不许写）
├── tdX/                    ← 按数据源分区
├── factors/<family>/       ← 因子族分区：一个 family 一个租约
└── runs/<run_id>/          ← 每次训练独立 run 目录，天然免冲突
```

规则只有一条：**共享数据只读；写只在 `factors/<family>/` 或 `runs/<run_id>/` 下。** 这样启动时校验一次 glob 归属（属于哪个车道），之后永不冲突。

### 4.3 为什么这比"WIP 治理"重要得多

| 现象 | 你现在的痛点 | 租约 + 登记后 |
|---|---|---|
| 训出 200 个因子 | 散在 `data/factors/*.parquet`，靠文件名回忆 | `factor_registry.jsonl` 可查 IC/夏普/区间/数据版本 |
| 两个 Agent 同时训 | 静默覆盖，事后才发现 | 409 直接拒 |
| 策略回测复现不了 | 不知道当时用的哪版数据 | `sha256 + data_scope` 钉死 |

**这才是训因子真正需要的"治理"，而且它一条都不会拖慢你。**

## 五、ship 通道：只在"要进 master"那一刻生效

### 5.1 三个动作，全部一行命令

```bash
# 1. 领令牌（首次，一个月有效）
devtask seat issue --name DSH-Lead --kind agent --authority exec

# 2. 开单（令牌自动带上，WIP 满则进 parked，不会失败）
devtask new WO-XXX --lane L3 --write-scope "quant_backtest/factors/**"

# 3. 提队列（替代手动抢 16:30 窗口）
devtask queue enqueue WO-XXX --branch task/WO-XXX
# → 返回排队号 #7，预计 16:30 窗口；到点自动合，失败自动退回并给原因
```

### 5.2 关键：回执自动生成，不用人写

现在 815 份交付件格式各异，是因为**证据靠手写**。改法：G5 直接从 `GATES` 的 `rc` + 耗时 + commit SHA + 测试输出生成结构化回执，**人只需要点一下签字**。

```
evidence:
  work_item: WO-XXX
  lane: L3   owner: DSH-Lead
  gates: [{name: 语法门, rc: 0, s: 12}, {name: 端口注册, rc: 0, s: 3}, ...]
  commit: a1b2c3d   tests: 54 passed
  artifacts: [{path: ..., sha256: ...}]
  rollback: git revert a1b2c3d
  signoff: <待点>
```

### 5.3 存量怎么办：不给它加锁，让它自然衰减

| 存量 | 不做的事 | 做的事 |
|---|---|---|
| 94 个未合入分支 | 不打 tag 战役、不批量删 | 14 天无提交 → 自动 `frozen/` 视图（只打 label）。要用时 `git branch` 一查就在 |
| 21 个 doing | 不三分类、不强制清账 | **心跳续期**：每天有提交/评论自动续；3 天无心跳自动转 `parked`（不 abort、不删） |
| 42 个 worktree | 不批量 prune | **棘轮滑降**（见 §六） |
| 815 份交付件 | 不重写、不迁移 | 新单用新格式，旧件只读保留 |

**一句话：存量靠时间淘汰，不靠人力清理。** 任何需要"专门腾出两天来清理"的方案，在执行时都会失败——因为它和业务抢注意力。

## 六、棘轮滑降：唯一不能犯的错

### 6.1 直接改会停工（这条必须写进代码注释）

```
当前 cap = 65，实际 = 42
若今天改成 15  →  42 ≥ 15  →  _enforce_worktree_cap() 立刻 block
              →  所有 Agent 的 devtask new 全部失败
              →  等于全项目停工，直到 worktree 降到 15 以下
```

**这是"治理把开发搞停"的唯一真实路径，而且 1 分钟就能踩到。**

### 6.2 正确做法：滑降公式

```
cap(d) = max(target, current(d-1) - step)
target = 15（ADGS 试期口径）
step   = 2 棵/天
42 → 40 → 38 → ... → 16 → 15        约 14 天
```

效果：**每一天 cap 都 ≥ 实际数，永远不会触发 block；但每开一个新单，就必然伴随一次回收**（因为 `_enforce_worktree_cap` 只在 `new` 时检查，cap 贴着实际走，等于强制"开一个收一个"）。

**这是零阻塞的收敛**——它不禁止你做任何事，只是让你在做之前必须收尾。

### 6.3 三个参数一起滑

| 参数 | 现值 | 目标 | step | 到位 |
|---|---|---|---|---|
| `MAX_WORKTREES_DEFAULT` | **65** | 15 | -2/天 | 14 天 |
| `WT_TTL_HOURS_DEFAULT` | **72.0** | 48 | -2/天 | 12 天 |
| `DEVTOOL_MAX_WORKTREES`（env 优先级更高） | 未设 | 跟随 | — | 由定时任务写 env 文件 |

**实现方式（不改 devtask 主逻辑）**：一个 `tools/gov_ratchet.py`，每天 08:00 由计划任务跑一次，算出今天该用的 cap，写进 `config/gov_ratchet.env`；`devtask.py` 启动时读这个文件覆盖默认值。**devtask.py 只改 3 行（读 env 文件），可随时删掉回退。**

## 九、度量：只报"等待时间"，不报"分支数"

| 指标 | 为什么不用它 | 换成什么 |
|---|---|---|
| 分支数 | 是结果，不是目标；压分支数会诱导"乱删" | **悬空 >14 天分支的金额占比**（判断哪些值得救） |
| commit 数 | 是产能，不是价值；AI 可以无限刷 | **每周 ≥5 条可追溯决策闭环**（ROADMAP v4 北极星） |
| worktree 数 | 受 TTL 干扰，看着永远健康 | **"从提 review 到合入"的中位时长**（真实瓶颈） |
| 席位/页面数 | 不反映任何用户价值 | **组合 validated 数** |

**唯一要盯的数字：进门时长。** 现在它是未知的（没人测过）。D1–D7 影子周的第一产出，就是把这个数测出来。

## 十、红线

1. **绝不一次性把 cap 改到目标值**（会停工，见 §6.1）。
2. **explore 通道永不设 WIP 上限、永不要求证据包**。
3. 存量分支**只打 label 不删除**；删除必须 `git tag archive/<日期>/<名>` 且 ahead=0。
4. `GOV_MODE=off` 必须随时可用，且不产生残留状态。
5. 不动 `devtask.py` 的 8 道现有门禁逻辑（只追加第九道）。
6. 不新建独立服务进程（复用 8796），不引入 MQ/新 DB。
7. 训因子/训策略的产物目录 `data/factors/**`、`data/runs/**` 归 explore，**任何治理规则不得阻写**。

## 十一、一句话给你

**你不需要停下来治理。你需要的是：把 `MAX_WORKTREES_DEFAULT = 65` 改成每天自动降 2，然后在 8796 上开三个只读接口。总改动 4 处、不到 200 行、零停机、随时可 off。**

训因子照训、策略照跑、算法照写——它们走 explore 通道，一次都不会被拦。治理只在你**要把成果交给系统**的那一下出现，而且它替你排队、替你写回执。

**最优解不是"治理得更彻底"，是"治理得让你感觉不到"。**
