# 情报体系 P1 · 轮次台账（v1 交付）

- 编制时间：2026-11-05 06:20
- 对应阶段：P1 运维可观测性（承接 v2.0 两项裁定落地）
- 代码基线：`osint_video`
- 一句话：**§9 写了"首个真实轮次要盯三个数"，但每轮的 payload 只 print 到 stdout，跑完就散。本轮把这句话变成可执行的机制，并在第一轮真机上就查出两个此前不知道的问题。**

---

## 1. 为什么必须做这件事

档案 §9 的原话是：

> 首个真实轮次要盯三个数（不是"跑完就行"）：
> `cross_window_merged` > 0 且明细合理 / `borderline_rechecked` 2 上下 / `review_backlog.pending` 不持续上涨。

三个指标里，前两个是**单轮绝对值**，第三个是**跨轮趋势**。而现状是：

| 缺口 | 后果 |
|---|---|
| payload 只 `print` 到 stdout | 没有历史，只能靠"恰好有人保存了上次输出" |
| 仓库内无任何调度入口（cron/systemd/部署脚本全无） | 无法确认真实轮次的参数，技术债 #26 未解 |
| `judge_failures > 0` 只在 stderr 闪一下 | 判定器静默降级（回落规则）几乎不可观测——而它正是"数字仍然合理但含义变了"的典型 |

第三点是关键：**降级后的 payload 看起来完全正常**，只是"LLM 判定过"这个前提已经不存在。单轮快照抓不到，跨轮比对也不一定抓到，但它必须被显式报出来。

## 3. 三个设计决策

### 3.1 记"前提"，不只记"结果"

台账每行都带 `context`：库名、窗口、limit、`dry_run`、`cross_window`、`borderline_judge`、`judge_name`。

原因很直白：在 `osint` 与 `osint_calib` 上各跑一轮，事件数天然不同。只存结果的话，
"事件数 31 → 29"读起来像聚类劣化，实际是换了库。

`find_baseline` 只在**前提完全相同**的轮次之间比；不同就继续往前找（中途改一次窗口再改回来，
不该让趋势断掉）；彻底找不到就明说"无同前提基线（与最近一轮的差异：`window_days: 14 ≠ 60`）"，
**而不是硬给一个差值**。

### 3.2 空转轮次必须自证

首轮真机就撞到：`units_scanned=0`。这不是故障（窗内确实没有待归属事实），但如果照原样记，
有两个后果：

1. 调度越频繁，台账被空转灌得越满（每 15 分钟一轮 = 每天 96 行噪声）；
2. `units_scanned` 从 0 跳到 8，趋势判据会把它读成"处理量激增"。

所以记录带 `noop` 标记，趋势基线**自动跳过**空转轮次。空转轮次本身照记——"每轮都跑了"
与"每轮都算了东西"是两件事，前者会掩盖"上游没在灌数据"。

空转时只报 `round.noop`（含"已连续空转 N 轮、最后一条非空转轮次是何时"）+ 积压告警，
其余结构性判据全部短路——没算东西，判它没有意义。

**这里刻意不给阈值**：调度频率不在仓库里（#26），"连续 3 轮算异常"在每 15 分钟的调度下是
45 分钟、在每天一次的调度下是 3 天，同一个阈值含义完全不同。所以只报事实，由人结合频率判断。

### 3.3 判据不猜阈值

`check_round` 判的是**结构性矛盾**，不是"事件数应该等于几"：

| 判据 | 级别 | 为什么 |
|---|---|---|
| `judge.degraded` | **fail** | 降级后数字仍合理，只是含义变了；判 warn 会被人当"注意一下"放过 |
| `judge.failures > 0` | warn | 失败对**回落规则**（不是冒充无关），所以是降级不是错判 |
| 有锚点却零合并 | warn | 与"根本没锚点"是两件事，处置完全不同 |
| 锚点 0 | ok | 窗口宽于语料历史时必然如此，报成告警会让真告警失效 |
| 复核开着却零调用 | warn | 通常是预热失败或全命中台账 |
| 积压告警非空 | warn | **转述**队列自己的文案，不重算阈值——重算会出现两套结论 |
| 积压上涨 | warn | 跨轮趋势，单轮快照答不了 |
| 跨窗合并由正变 0 | warn | 最典型的静默回归 |

任何硬编码"期望事件数"都会在语料变化后变成假警报。量该等于多少，是标定脚本的事。

## 4. 真机验证

### 4.1 首轮（生产库，默认参数，非 dry-run）

```
units_scanned = 0    dry_run = False    queue_written = 0
[OK] round.noop: 窗内无待归属事实，本轮未做任何计算（此前从无非空转轮次）
```

安全：0 待归属意味着什么都没写。台账留下 1 条真实记录。

### 4.2 趋势链路（60 天窗 dry-run 连跑两轮）

```
第一轮：trend.no_baseline: 台账为空，这是首轮
第二轮：[OK] trend.pending: 待确认积压 2 → 2
        [OK] trend.baseline: 趋势基线：2026-11-04T22:03:42（前提相同：库/窗口/limit/dry_run/开关）
```

同前提能被正确找到；14 天那轮因为 `window_days` 不同被自动排除，没有被拿去当基线。

### 4.3 验证过程中修掉的两个真实缺陷

| 缺陷 | 怎么发现的 | 修法 |
|---|---|---|
| 旧行没有 `noop` 字段，被当成实跑 | 首条记录写于加字段之前，`list` 显示 `real` 但 `units_scanned=0` | 读时派生，不依赖写入时字段 |
| `borderline_samples` 被写进白名单 | `show` 输出里看到 `"borderline_samples": []`——它是**明细列表**不是计数（`borderline` 才是计数） | 从白名单移除；测试改为断言事实标题不出现在序列化结果里 |

第二个缺陷尤其值得记：我在模块文档里写了"明细不落台账"，实现却把 `borderline_samples` 放了进去，
**文档写对了、代码写错了**。只有把"标题字符串不得出现在台账里"写成断言才抓得住。

### 4.4 测试

| 项 | 结果 |
|---|---|
| `tests/test_run_ledger.py` | 30 passed（默认）/ 7 skipped（变异需 `OSINT_MUTATION=1`） |
| 变异测试 | **7/7 全部被捕获** |

变异覆盖的都是"改坏了不报错、只会静默少报"的判据：noop 恒 False、基线不跳空转、
前提比较恒相等、降级降级到 warn、积压上涨忽略、空转不短路、旧行不归一。

**变异测试本身踩了三个坑**（都是"看起来在测、其实没测"）：

1. 复制整个 `knowledge` 包 → `__init__.py` 再导出 `item_processor` → `collectors` 整条依赖链缺失
   → 收集期错误。改为只造最小包结构（`run_ledger.py` 只依赖标准库）。
2. 7 个子进程在同一个临时根下竞争 `.pytest_cache` → 间歇性 `1 error`，单跑必过、连跑偶发。
   加 `-p no:cacheprovider`。
3. rootdir 向上探测到临时目录祖先 → 加载无关配置。在 work 里放一个空 `pytest.ini` 钉死。

第 2、3 条的共同点是：**故障形态是"偶发失败"，很容易被当成"环境抖动"放过**。加守卫
（收集期错误不算"变异被捕获"）才让它现形——否则一个连用例都没跑的变异也会被记成"已捕获"。

## 5. 顺带查出的两个问题（本轮不修，需裁定）

### 5.1 8 条事实从未进入事件层，且 14 天窗永远够不到

首轮 `units_scanned=0` 让人去问"为什么是 0"，答案在库里：

| 事实 | 日期 | 真值 | 标题 |
|---|---|---|---|
| `verify-s12-01` | 09-30 | S12 | 中芯国际产能利用率回升至九成 |
| `verify-s14-01` | 10-05 | S14 | 欧盟决定对中国电动汽车加征反补贴税 |
| `verify-s07-01` | 10-10 | S07 | 隆基绿能上调硅片报价，涨幅约5% |
| `verify-s02-01` | 10-15 | S02 | 华信科技因涉嫌信息披露违法违规被证监会立案调查 |
| `verify-solo-16` | 10-19 | — | 中芯国际公告拟新建十二英寸晶圆产线 |
| `verify-solo-13` | 10-20 | — | 华为发布三季度经营业绩，营收同比增长 |
| `verify-s13-01` | 10-21 | — | 贵州茅台宣布上调出厂价，幅度约两成 |
| `verify-solo-15` | 10-21 | — | 恒瑞医药创新药获批上市，适应症为肺癌 |

**它们全是各真值事件的第一条（`xxx-01`）**，加上 3 条独立事件。库内现状：50 事实 /
42 成员 / 29 事件——这 8 条不在任何事件里，而 14 天窗内待归属为 **0**（最新事实 11-03）。

含义：S12 / S14 / S07 / S02 / S13 在事件层是**缺开头**的——02/03 条在事件里，01 条不在。
如果日报按事件统计，这些事件的起点、时间跨度、独立来源数都不完整。

**为什么不能简单补跑**：120 天窗 dry-run 的结果是 `units_scanned=8 / stories_created=8 /
stories_reused=0 / unrelated=2`。而 `anchors_loaded=0`——窗口宽到把所有已归属事实也包进窗内，
跨窗口召回因此失效（跨窗只在"窗外有锚点"时起作用）。也就是说，大窗口补跑**可能把
S12 等拆成两个事件**，正好是跨窗召回要解决的问题反过来发生。

**这直接说明跨窗口召回的能力边界**：它解决的是"新事实跨月接续"，不解决"历史遗留的断裂"。
后者需要事件级合并（技术债 #25）或一次性回填。

### 5.2 dry-run 的分组统计与实际执行口径不一致

`stories_reused` 只在 `_create_story()` 返回 `created=False` 时累加。而"第一路挂到已有事件"
（`pivot` 与已归属 `target` 合并成功）走的是 `_add_member`，**不计入 `stories_reused`**。

后果：`--dry-run` 报 `stories_created=8 / stories_reused=0` 时，真实执行很可能不是这个分布
（部分配对会走第一路合并）。**用 dry-run 的数字推断"补跑会发生什么"是不可靠的。**

本轮没有验证这个推断（要在克隆库上真跑才知道），也没有修——它属于 P0 的统计口径，
改它会影响 `eval_story_quality` 的历史对比基线。已记为技术债。

## 6. 限度

1. **台账只让问题可见，不修数据。** 8 条遗漏仍然遗漏，除非有人决定补跑。
2. **判据不判"结论是否仍最优"。** 标定戳（v1.9）管依据过期，台账管这一轮跑得对不对，两者都不判"0.05 还是不是最优"。
3. **空转告警依赖人看频率。** 连续空转只报事实不判异常，因为调度频率不在仓库里。
4. **不覆盖消费侧。** 台账记的是聚类轮次，日报/热度怎么用 `decided_by` 是技术债 #20，不在本轮。
5. **写失败只降级为告警。** 台账写不进去时整轮照常成功，`ledger.recorded=false` 会进 payload，但不会让退出码非 0。

## 7. 交给老田的三件事

1. **调度入口在哪**（#26，仍未解）。配置改了 `.env` 只在下次 cron 生效，而仓库里找不到 cron。上线前必须核对真实命令有没有显式传 `--borderline-judge off` / `--no-cross-window`。
2. **8 条遗漏事实要不要补**（5.1）。补的话建议：先备份（`preflight.py --backup`）→ 在克隆库上真跑 120 天窗看实际 `created/reused` 分布 → 确认无拆散后再在生产跑，或等事件级跨窗合并（P2）。
3. **首轮真实轮次要盯什么**。现在只需一条命令：

```bash
python scripts/story_round_log.py check    # 退出码 0/1/2 可直接接监控
```
