## 0. 为什么需要这件事

本地一个知识图谱工程仓（下称「目标仓」）的 `origin` 指向一个**从未存在的占位地址**，
拉取报 `Repository not found`；开发机也没有配置命令行建仓工具。结果是：当晚把
一个策略原型的全部实现（若干模块 + 一份批准申请表）入库后，**只落在了本地 git 历史**。

本地 git 历史能防误删、防 `git clean`，但**不防磁盘损坏** —— 开发机只有单块系统盘，
没有外挂盘。所以需要一次真正的异地副本。

已做的临时缓解：`git bundle create --all` 打了一份全量包（6.5 MB / 353 提交 / 3 分支，
`bundle verify` 报完整历史），放在仓目录之外。但这仍与源在同一块盘上。

## 1. 现状核对结果（只读探测）

| 项 | 现状 |
|---|---|
| 裸仓根目录 | `<GIT_ROOT>/repos/`，归属服务账号 |
| 已有仓数量 | 4 个（1 个开源版、1 个私有版、1 个研究仓、1 个演示站） |
| 授权文件 | 服务账号 home 下的 SSH 授权文件，4 行 |
| 授权模式 | 一钥一仓；每行用强制命令绑定做路径白名单，密钥无法执行 git 协议以外的命令 |
| 包装器能力 | 支持逗号分隔多仓、只读/可推两档；用 `pwd -P` 解析符号链接防逃逸 |
| 备份脚本 | 单一脚本内写死仓列表，`git bundle --all`，保留最近 30 份 |
| 备份调度 | 每日凌晨由 systemd timer 触发，以服务账号身份运行 |
| 操作系统 | 企业版 Linux 发行版，git 版本较旧（**不支持 `git init -b`**） |

### 探测中发现的两个问题

**① 演示站仓（81 MB）从未进入备份范围。**
备份脚本里的仓列表是**写死**的三个仓，某日新建的演示站仓从未被加入，
备份目录里也就从来没有它的 bundle。这是既有漏洞，与本次变更同属一行改动，一并修复。

**② 裸仓默认 HEAD 指向 `refs/heads/master`，而目标仓的默认分支是 `main`。**
旧版 git 不支持建仓时指定初始分支，创建后必须显式重设 `HEAD` 符号引用，
否则克隆出来是一个空的 `master`，容易误导后续操作。

## 2. 五要素

### 2.1 步骤概要

**阶段 A · 开发机（零风险）**

1. 为该仓单独生成一对密钥（沿用「一钥一仓」隔离原则，不复用现有密钥）
2. 在本机 SSH 配置中增加一个别名，指向新密钥

**阶段 B · 服务器**

3. 变更前先备份两个将被修改的文件（授权文件、备份脚本），并记录 md5 基线
4. 建裸仓 → 重设 `HEAD` 指向 `refs/heads/main` → 归属与权限对齐现有仓
5. 在授权文件**末尾追加一行**，把新公钥绑定到该仓、模式为可推
6. 修改备份脚本的仓列表：加入新仓，同时补上遗漏的演示站仓

**阶段 C · 推送**

7. 本地 `origin` 改为指向自建仓，推送默认分支并建立跟踪

**阶段 D · 验证**

8. 远端 HEAD 与本地 HEAD 逐字节比对
9. 手动触发一次备份，确认新仓与演示站仓都生成了 bundle，且指纹与远端 HEAD 一致
10. **从 bundle 真恢复一次**到临时目录，确认关键文件在位、产物被正确排除

### 2.2 影响面

| 对象 | 影响 |
|---|---|
| 裸仓根目录 | 新增一个裸仓，约 50 MB（数据盘余量 1.8 TB） |
| 授权文件 | 4 行 → 5 行，**前 4 行不动** |
| 备份脚本 | 仓列表 3 → 5 个，每日备份体积 +约 88 MB，耗时 +3~5 秒 |
| **不受影响** | 其余 4 个仓的推送/拉取、静态镜像、业务平台、数据库备份、任何在线服务 |
| 不开放匿名只读 | 不做 `post-receive` 到静态目录的镜像（理由：内含策略实现，不应对外） |

### 2.3 不可逆点

| 操作 | 可逆性 | 说明 |
|---|---|---|
| 建裸仓 | 可逆 | 移入回收目录即可 |
| 授权文件追加 | 可逆 | 有变更前备份；**但写错是本次最大风险** —— 可能导致服务账号整体无法登录，4 个现有仓同时中断 |
| 备份脚本改仓列表 | 可逆 | 有变更前备份；脚本开了 `set -euo pipefail`，失败会非 0 退出并报错，不会静默 |
| 本地 remote 改 URL | 可逆 | 改回即可 |
| **真正不可逆** | **无** | 全部为新增或追加，无删除、无覆盖存量 |

### 2.4 替代方案

| 方案 | 为什么不选 |
|---|---|
| 托管平台私有仓 | 数据出境到第三方；且入库文件含策略实现，硬编码凭据扫描尚未人工复核完毕 |
| 维持本地 + bundle | 只能防误删，不防盘坏（开发机单盘） |
| 只建仓、不改备份脚本 | 少改一处，但新仓不在自动备份里，异地保存只做了一半 |

### 2.5 回滚预案

以变更前备份为准，三条路径：

1. **授权文件出问题（最紧急）**：用 `.bak` 覆盖回原文件，确认 SSH 服务配置自检通过；
   4 个现有仓立刻恢复可访问。不做排查、不犹豫。
2. **备份脚本出问题**：用 `.bak` 覆盖回原文件，立刻手动跑一次验证恢复。
3. **裸仓要撤**：移入回收目录，不物理删除。

兜底：开发机那份全量 bundle 与服务器无关，始终有效。

**回滚触发条件**：追加授权之后，任一次现有仓的连通性探测失败，立即执行路径 1。

## 3. 执行顺序与检查点

```
A 生钥 + 配别名（本机，无风险）
   ↓
B 备份两文件 → 建仓 → 修 HEAD → 权限对齐
   ↓
追加授权  ← ⚠ 最高风险点，改完立刻测 4 个现有仓
   ↓
检查点①：4 个现有仓别名全部可 ls-remote
   ↓
改备份脚本 → 检查点②：语法检查通过 + diff 只有 1 行
   ↓
推送 → 检查点③：远端 HEAD == 本地 HEAD
   ↓
检查点④：手动备份 + bundle 恢复演练
```

任一检查点失败即停，按 2.5 回滚，不继续下一步。

## 7. 一条过程教训

推送前，仓库的 pre-commit 凭据扫描对本次新增文档报了一条
「内网地址 + 凭据语境」的命中，级别是 **warn-only（不阻断）**。
当时判断为「不阻断即放行」，未先确认**仓库可见性**就推了上去 —— 事后核实该仓为公开仓，
本篇随即脱敏重写。

教训：`warn-only` 不等于「可忽略」，它表达的是「规则认不准，交给人判断」。
处置顺序应当是 **先查影响面（仓可见性、分支保护、是否已推送），再决定放行或改写**。
凭据扫描类警告尤其如此 —— 阻断与否是工具策略，泄露与否是事实。
