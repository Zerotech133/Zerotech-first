# 多 AI 军团控制面：最优解决方案 v1

- 日期：2026-11-02｜决策记录：ADR-021（Proposed，待 A0/ARCH1 确认）
- 结论：**原方案为主线；Paperclip 不整体整合，只吸收 5 个机制 + 做隔离 PoC/benchmark。**
- 一句话：**不换控制面，把 Paperclip 的 org/tasks/approvals/budgets/heartbeat 机制做薄，嵌进 8734；Paperclip 作为 W3 后的备选，不是现在的平台。**

## 一、新增关键事实（决定选型）

1. **Paperclip 是控制面，不是执行面**：React/Vite UI + Express API + PostgreSQL；adapter 的 `execute()` 拉起 agent，agent 通过 REST 查询/领取任务/更新状态；单任务原子 checkout、company 域隔离。[架构文档](https://github.com/penclipai/paperclip-cn/blob/master/docs/start/architecture.md)
2. **通用 SSO/OIDC 尚未合并**：PR [#3040](https://github.com/paperclipai/paperclip/pull/3040) 仍是 **open**（2026-11-02），issue [#3028](https://github.com/paperclipai/paperclip/issues/3028) open；OSS 核心当前是 Better Auth 会话 + API key，`local_trusted` 无认证。[API 认证文档](https://github.com/penclipai/paperclip-cn/blob/master/docs/api/authentication.md)
   → **无法原生满足我们 8734/OIDC 单登录**；只能反代/受信头桥接或等其合并。
3. **能力契合**：CN fork 内置 `hermes_local`/`hermes_gateway`、openclaw、codex、claude、qwen、kimi 等适配器；org chart/tasks/approvals/budgets/heartbeat 成熟。
4. **风险明确**：本地 CLI adapter 无沙箱、遥测默认开、`local_trusted` 仅本机、CN fork 漂移、上游 6.6k open issues。
5. 我们现状：W1 条件关闭、W2/L1 运行态、W3 未启动；已有 org 77 席、task board 2046、组合门/质量门/证据链；缺的是 HQ 层的 org/approval/budget/heartbeat 产品化。

评分依据：原方案已有 8734/OIDC/组合门/W1/W2 资产；Paperclip 能力分高，但 SSO/单栈/时间线三项失分过大。

## 三、最终目标架构（A+：原方案 + 吸收机制）

```
8734 统一门户（OIDC 单登录，唯一入口）
  ├─ /hq/        薄 HQ（自建）：org / tasks / approvals / budgets / runs
  ├─ /hermes/    交互/控制面（现有 Hermes 8787）
  ├─ /legion     军团作战数据（现有）
  └─ 现有 104 页面不动
后端：
  - 现有 PG 0049 + org.json/tasks.json/usage_ledger 为数据源（不复制生产 DB）
  - 私有 MCP registry（13 server）+ 6 军团 A2A Agent Card
  - LiteLLM 内部网关（可选，模型/MCP/A2A 统一）
  - OTel GenAI 观测（已有 ADR-005/014）
```

**吸收 Paperclip 的 5 个机制（不引入其平台）**：
1. **org chart/角色/权限**：从 org.json 生成树 + 权限矩阵；
2. **单任务原子 checkout**：防止多 Agent 并发抢同一任务；
3. **heartbeat 合并唤醒**：已有调度器上加“合并/去重”；
4. **approvals**：把现有审批注册表产品化为 `/hq/approvals`；
5. **budgets/run cost**：usage_ledger 上升为预算/成本视图。

## 四、W3 工作包（原方案内完成）

| ID | 内容 | 验收 |
|---|---|---|
| HQ-01 | `/hq/org`：77 席树/角色/权限 | 与 org.json/HR 一致；只读 |
| HQ-02 | `/hq/tasks`：任务板 + 原子 checkout | 并发不重复领取；状态机一致 |
| HQ-03 | `/hq/approvals`：审批队列/四签可视化 | L2 五要素可追溯 |
| HQ-04 | `/hq/budget`：usage_ledger/成本/预算告警 | 每席/每军团可查 |
| HQ-05 | heartbeat 合并 + 单一调度 owner | 同任务不重复执行 |
| HQ-06 | `/hq` 页面 manifest + 统一 nav + Q2 | 一入口/一登录；页面在册 |

时间：H1（11-03~11-16）继续收口/W1 确认；H2（12-03~01-15 W3）做 HQ-01~06；H3（W4）Q3/Q4 与 Kernel Review。

## 五、Paperclip 的定位（只做 PoC/benchmark）

- 时间盒 **2 周**，放在 W3 之后或非关键路径；
- 目录 `C:\项目\_sandbox\paperclip-cn`，端口 **3100**、独立 PG、`local_trusted`、**关遥测**；
- 只接 `hermes_gateway` → 8787；建 2 个 agent，验证 org/tasks/approvals/budgets/heartbeat；
- **不反代、不接生产数据、不双调度、不改 8734/425 任务/104 页面**；
- 结论只用于“是否在 W4 引入 `/hq/` 托管 UI”，不影响 W3。

**重新评估门（全部满足才整合）**：
1. SSO/OIDC 已合并且能接 8734 单登录（当前 PR open → 大概率不满足）；
2. 安全评审通过（无沙箱 CLI/遥测/秘密/权限）；
3. 自建 HQ 仍无法覆盖 org/approval/budget；
4. 单一调度/单一数据真相可保证。

## 六、结论

**最优解 = 原方案继续，吸收 Paperclip 的 5 个机制，Paperclip 只做隔离 PoC。**
- 不整体整合：保住单宿主/单入口/单认证，不挤压 W3，不引入第二 UI/DB/调度；
- 吸收机制：用 2–3 周补齐 HQ 产品化，获得 Paperclip 80% 的价值；
- 保留备选：W4 若 SSO 合并、HQ 仍不足，再以 `/hq/` 形式评估 Paperclip，不锁死。
