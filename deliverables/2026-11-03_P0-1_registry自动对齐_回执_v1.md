## 一、背景与目标（P0-1）

KgDailySync（每日 06:20，任务 `\KgDailySync` → `quant_backtest/start_kg_sync.ps1`）第一步 `build_catalog` 会把 catalog.json 升版（sha256 变化），但该链**没有 registry_rebuild 步**——registry.catalog_sha256 直到有人手动跑 registry_rebuild 才更新。因此每天 06:25 后出现「catalog 已升版、registry 旧」的人工提醒。

本工具：`python tools/datawarehouse/registry_align.py`（默认 `--check` 只读 / `--apply` 备份+重建+校验），把「检测 + 对齐 + 元数据校验 + kg 日志」收成一条命令，供 KgDailySync 收尾自动调用（接入方案见 §五，L2 待批）。

## 二、工具行为

| 项 | 说明 |
|---|---|
| `--check`（默认） | 只读：读 catalog 实算 sha256 + registry，判定 aligned 并输出 diffs；**不取锁、不写盘、不追加 kg 日志** |
| `--apply` | 不一致时：取锁 → kg 日志尾部检查 → `registry_rebuild.build_payload` 备份+原子重建 → 重读校验（catalog_sha/计数）→ `metadata_consistency` PASS+physical==catalog 表数 → 追加 kg 日志；**已一致时幂等跳过（不写盘）** |
| `--json` | 输出完整 JSON：`catalog{path,version,tables,sha256}` / `registry{path,catalog_sha256,physical_count,display_count,generated_at}` / `match_before` / `diffs_before` / `rebuild{performed,backup,stats,verify}` / `match_after` / `diffs_after` / `metadata{code,issues,warnings,physical_count,tables}` / `kg_log` / `lock` / `rolled_back` / `exit_code` / `elapsed_s` |
| `--lock PATH` | 默认 `C:\Temp\registry_align.lock`；O_EXCL 独占 + **>2h 陈旧锁自动回收**；退出即释放（`finally`） |
| `--kg-log PATH` | 默认 `C:\Temp\kg_sync_task.log`；`--apply` 写前复用 `registry_rebuild.find_kg_log_state` 口径检查尾部（有进行中/失败即拒跑），写后 fsync 追加 `registry_align ... exit=0` |
| `--catalog/--registry PATH` | 模拟/单测用（不传=主仓数据根）；历史备份可借此只读复现旧场景 |
| 退出码 | **--check**：0=已对齐 / 1=需对齐 / 2=前置错误（文件缺失/坏 JSON）。**--apply**：0=对齐成功或已对齐 / 1=写后校验失败（**已自动回滚**）/ 2=锁占用/kg 前置/catalog 不可读 |

**对齐判定（aligned 的充分条件）**：① registry.catalog_sha256 == catalog 实算 sha；② physical_count/display_count 与列表实际长度自洽；③ catalog 全部表被 registry physical_tables 覆盖；④ lifecycle=planned/deprecated/archived 的表在 registry 的 qualification_status 与之一致。⑤ registry 中 catalog 已不存在的 orphan 条目为 info（重建会保守保留，不阻断）。

**安全设计**：
- 复用 `registry_rebuild` 的 `build_payload/write_backup/atomic_write/verify_written`（不重写一套写盘逻辑）；
- 写后 **metadata_consistency 不 PASS 或 physical≠catalog 表数 → 自动回滚到本次备份**（原子 restore），exit=1 且 JSON 含 `rolled_back=true/restore/metadata_after_rollback`；
- 锁 + kg 日志双保险防并发；`--check` 全程零写入（单测验证 mtime 不变）。

## 五、接入 KgDailySync 收尾 —— 具体补丁方案（只给方案，未修改 ps1/计划任务）

目标文件：`quant_backtest/start_kg_sync.ps1`（任务 `\KgDailySync` 的 action）；
插入位置：**foreach 数据链循环结束之后、写 `kg_sync OK` 之前**（此时所有数据步骤已 exit=0，catalog 已 build 完成）。

```powershell
# ==== P0-1 收尾：catalog→registry 自动对齐（L2 待批后启用）====
# 依赖：$py 已定义为 'C:\Program Files\Python311\python.exe'；$log='C:\Temp\kg_sync_task.log'
$alignOut = 'C:\Temp\kg_registry_align_out.log'
$alignErr = 'C:\Temp\kg_registry_align_err.log'
$pa = Start-Process -FilePath $py -ArgumentList @(
    '-X','utf8','C:\项目\老田的AI助手\tools\datawarehouse\registry_align.py','--apply','--json'
) -WorkingDirectory 'C:\项目\老田的AI助手' -RedirectStandardOutput $alignOut `
  -RedirectStandardError $alignErr -PassThru -WindowStyle Hidden -Wait
$arc = $pa.ExitCode
('registry_align exit=' + $arc + ' ' + (Get-Date -Format s)) | Out-File $log -Append -Encoding utf8
if ($arc -ne 0) {
    & 'C:\Program Files\Python311\python.exe' -X utf8 C:\项目\老田的AI助手\news_collector\alert_fail_wrap.py 'kg_sync:registry_align' $arc $alignErr 1>$null 2>$null
    # 处置策略二选一（由 Lead/A0 定，二选一后删除另一行）：
    #  A（推荐）：不 abort 数据链——数据步骤已全部成功，仅告警并继续写 kg_sync OK；
    #  B（严格门禁）：exit 1，使 KgDailySync 标失败（触发任务级失败/告警）。
    # exit 1   # ← 仅选 B 时启用
}
# ==== P0-1 收尾 END ====
```

**接入要点**：
1. 该位置在 `try { foreach ... }` 之后，天然保证「只有数据链全成功才对齐」（任一步失败已 `exit 1`，不会走到这里）；
2. `registry_align --apply` 自身会检查 kg 日志尾部（此时最后一行为最后一步 `xxx exit=0`），并追加 `registry_align ... exit=0` 行，随后 wrapper 再写 `kg_sync OK`——kg 日志语义保持「成功收尾」；
3. 幂等：当日无 catalog 升版时 `--apply` 直接返回 rc=0（不写盘、不备份），日常几乎零成本；
4. 失败可观测：JSON 与日志落 `C:\Temp\kg_registry_align_out.log`，`rebuild.backup` 给出可回滚备份路径；
5. 超时/并发：锁 `C:\Temp\registry_align.lock` 防手动并发；建议 guard 外层加 `-Wait` 即可，无需额外超时（实测 <1s，重建 256 表 <1s）；
6. **审批**：修改计划任务 action/`start_kg_sync.ps1` 属 **L2**（服务/计划任务变更），需五要素审批；本单只给补丁方案，未动手。

可选替代（若不想动 ps1）：在任务计划器里新增一个「06:45 子任务」直接调 `registry_align.py --apply`，但会与 KgDailySync 数据链并行、且失去「数据链成功后才对齐」的天然顺序保证，**不推荐**。

## 六、风险与限制

1. **读-写竞态**：若对齐期间另一会话又 build_catalog，registry 会再次落后（sha 不匹配）→ 下次运行或下一日收尾自动再对齐；锁只保护本工具自身并发；
2. **metadata_consistency 含 lifecycle 口径**：若当日 lifecycle 表登记变化，apply 会按 registry_rebuild 口径套用并校验；校验失败自动回滚（不会留坏 registry）；
3. **备份保留**：每次实际写盘生成 `warehouse_registry.json.bak-<ts>`（同目录），与既有脚本一致，不自动清理；
4. **kg 日志守卫**：若 `--apply` 时日志尾部是进行中/失败记录，将拒跑（rc=2）——此时由 KgDailySync 收尾位置保证不会触发（数据链失败已 abort）；手动运行需先确认无并发；
5. **catalog 坏 JSON/缺失**：rc=2 fail-visible，不写 registry；
6. **orphan 条目**：catalog 删除的表在 registry 中保守保留（重建不删，与 registry_rebuild 一致），只记 info，不阻断对齐。
