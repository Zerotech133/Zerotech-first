- 诊断方法：hermes doctor / profile list / Ollama 探活 / 8787 探活 / 丙案实测全验证

## 一、根因链（四层，层层独立验证——最终版）

| 层 | 实测 | 结论 |
|---|---|---|
| ① Ollama | `/api/tags` 200，qwen3.5:9b 在位 | ✅ 无辜 |
| ② WebUI（8787） | LISTENING **PID 19044 = Services 会话 SYSTEM 级进程**，/api/profiles 见 tianfeng | ✅ 活着且以系统权限跑 |
| ③ CLI 配置 | `profile list` 只见 default Gateway=stopped；doctor 报 `.env missing` | 配置缺失但**非主因** |
| ④ **沙箱安全策略** | 丙案（显式 -m --provider）实测仍 service_manager_unavailable，且沙箱拦截日志显示 **schtasks.exe 在程序黑名单**——hermes 的 service_manager 依赖 schtasks 起服务 | ❌ **真根因** |

**完整因果**：CLI（用户态）每次会话要经 service_manager 起模型网关 → service_manager 调 schtasks.exe → 本沙箱把 schtasks 列入程序黑名单（历史判例：schtasks 误报/滥用防护）→ 网关永远 stopped。WebUI 能跑是因为它是 SYSTEM 级服务（19044），不受用户态黑名单约束。

**这意味着：CLI 复核在任何挂黑名单的会话里都无法工作，与 profile/.env 无关。**
