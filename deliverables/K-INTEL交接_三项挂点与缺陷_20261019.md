# K-INTEL 交接：三项挂点与缺陷（2026-10-19）

本材料仅交接、不得将临时运行时 shim 视为源修复。`zerobound-kg/kg_intel_sources.py`、`kg_intel_link.py`、`kg_intel_xq_guba.py` 及其配套在途测试的原工位尚未确认、未获停笔签收；旧 worktree 与历史协调簿不能当成当日所有权。严禁改/add/commit 四件，亦不得运行既有入图链（包括可能连接真图的 dry-run）。本工单仅对四件只读定位，不代替所有权签收。

## 1. 雪球三源 `src_key` 与注册表键均不一致（入图接缝断链）

`zerobound-kg/kg_intel_sources.py:104-159` 中 `_xq_fetch` 于 `:138` 设置 `src_key=table`：`xq_status`、`xq_hot_post`、`xq_comment` 三表产出对应表名；注册表键却依次为 `"xueqiu_status"`、`"xueqiu_hot"`、`"xueqiu_comment"`（`kg_intel_sources.py:242-256`）。`zerobound-kg/kg_intel_link.py:420-423,473` 的 `item_id_of` 与 `upsert_intel_batch` 直接索引 `SRC.SOURCE_REGISTRY[it.src_key]`，三源有条目进入接缝即可能触发 KeyError；news/guba 源键一致。现有取数测试只断言 pointer，消歧测试手工构造 RawIntel，尚未覆盖实际 `_xq_fetch → upsert_intel_batch` 接缝。此前原帖回填仅使用当次进程 shim，不是源文件修复；水位文件是否存在亦不能单独证明从未执行或没有图副作用。更改注册键或 fetch 映射会牵动 `data_source::ext_id` 的 IntelItem MERGE 键与 Source 节点语义，应由签收后的 K-INTEL 所有者核对依赖口径、补三源完整接缝回归并裁定迁移方案；本工单不擅改在途件。

## 2. TEXT `status_id` 水位跨位数漏采（P1）

`zerobound-kg/kg_intel_sources.py:126` 将 `last_id` 转为 int，而 `kg_intel_sources.py:129-131` 在 SQLite `status_id TEXT` 列上用 `WHERE status_id > ? ORDER BY status_id`。TEXT 列的排序和比较存在字典序语义：8 位水位 `'99992210'` 与 9 位新 ID 之间不可凭数值大小直接推断安全增量；运行时参数 int 与 SQLite 列亲和性、索引执行路径亦应纳入复现实测。既有侦察口径：8 位旧 ID 约 9,900、9 位新 ID 约 14,853，增量分拆约 840＋50；这些是此前侦察快照而非本文件重算现值，请所有者重新核验来源、时点与精确口径。待签收后由 K-INTEL 所有者在 `kg_intel_sources.py:103-149`、`kg_intel_link.py:648-658` 与 `kg_intel_xq_guba.py` 两处 `max(int(ext_id))` 水位链协同修复为可证明单调的规则，并补 TEXT 8→9 位跨位数、重放及断点续跑夹具；未签收前仅记录缺陷，不动其文件。此前原帖水位 `xueqiu_status.last_id=99992210`，不能把分类链的独立 rowid 机制当作原帖修复。

## 3. `desc` 匹配提案（仅内存、不扩落图正文）

现行雪球 `_xq_fetch` 在 `kg_intel_sources.py:122,135` 优先取 `title`，没有把 `xq_status.desc` 纳入 `RawIntel.match_text`；`kg_intel_link.py:442-444` 已优先使用 `match_text` 做消歧。提案由 K-INTEL 所有者只读拼接 `(title + " " + desc)[:2000]` 为内存态 `match_text`，保留落图 `title` 截断摘要与指针、正文不落图，且不改变既有 symbol 直连优先级。此前离线抽样对关联率的估计约 +7.7 个百分点，属于方案估算而非正式写图成效；上线前复核抽样样本、误匹配和 ambiguous 护栏，并报告置信区间。

## 4. 独立分类表精确链（方案 A，边界与当前状态）

本工单在 `zerobound-kg/kg_intel_xq_classified.py` 与 `test_kg_intel_xq_classified.py` 新建隔离链：只读 `xq_status_classified.norm_tickers`，仅接收经 `stock_a`＋`SH/SZ` 六位 canonical 校验且不在 `INDEX_POLLUTION` 中的值，转换为 `Security.ts_code`；仅向既有 `IntelItem(item_id="xueqiu_status::<status_id>")` 和既有 Security 建 `MENTIONS`，不创建节点。独立水位位于 `data/graph_check/xq_classified_link_watermark.json`，记录已成功处理的最大分类表 `rowid` 供审计；由于既有低 rowid 分类行可能事后补录 `norm_tickers`，默认每次从表头幂等重放，生产写模式不允许指定非零起始 rowid，不能以该水位过滤晚到更新。绝不读写原 `intel_link_watermark.json`；run 必须显式注入图客户端，CLI 拒绝隐式连接，未签收所有权期间连生产端点的 dry-run 也禁止。离线模拟写需 `KG_WRITE_ACK=YES`；若出现未匹配节点，不推进审计最高 rowid，下一轮表头重扫可待节点到位后补边；任一批图写失败也不得标记该批成功。临时库＋mock 图九项测试通过（含迟到归一化及节点后出现）；真实图 dry-run、正式写图及真实水位均未执行，不能把原帖管道的 24,753 帖／1,103 边冒充分类链成绩。该独立链不替代第 1、2、3 节 K-INTEL 线的源修复。
