## 1. 雪球 `src_key` 与注册表键不一致（阻断原帖正常入图）

`zerobound-kg/kg_intel_sources.py:138` 的 `_xq_fetch` 设置 `src_key=table`，`xq_status` 表因此产出 `src_key="xq_status"`；注册表实际键为 `"xueqiu_status"`（`kg_intel_sources.py:242`）。`zerobound-kg/kg_intel_link.py:422` 的 `item_id_of` 与 `kg_intel_link.py:473` 的 `upsert_intel_batch` 均直接索引 `SRC.SOURCE_REGISTRY[it.src_key]`，第一次正式批写入前可触发 `KeyError: 'xq_status'`。此前原帖回填使用仅在当次进程生效的 shim，不是代码修复。请 K-INTEL 所有者统一注册键与原始表名，补一条真实 `_xq_fetch → upsert_intel_batch` 契约回归；禁止本工单直接改在途源文件。

## 2. TEXT `status_id` 水位跨位数漏采（P1）

`zerobound-kg/kg_intel_sources.py:126` 将 `last_id` 转为 int，而 `kg_intel_sources.py:129-131` 在 SQLite `status_id TEXT` 列上用 `WHERE status_id > ? ORDER BY status_id`。TEXT 列的排序和比较存在字典序语义：8 位水位 `'99992210'` 与 9 位新 ID 之间不可凭数值大小直接推断安全增量；运行时参数 int 与 SQLite 列亲和性、索引执行路径亦应纳入复现实测。既有侦察口径：8 位旧 ID 约 9,900、9 位新 ID 约 14,853，增量分拆约 840＋50；这些是此前侦察快照而非本文件重算现值，请所有者重新核验来源、时点与精确口径。应由 K-INTEL 线修复为可证明单调的增量键或显式数值规则，并补 8→9 位数、重放、断点续跑测试。此前原帖水位 `xueqiu_status.last_id=99992210`，不能把分类链的独立 rowid 机制当作原帖修复。

## 3. `desc` 匹配提案（仅内存、不扩落图正文）

现行雪球 `_xq_fetch` 在 `kg_intel_sources.py:122,135` 优先取 `title`，没有把 `xq_status.desc` 纳入 `RawIntel.match_text`；`kg_intel_link.py:442-444` 已优先使用 `match_text` 做消歧。提案由 K-INTEL 所有者只读拼接 `(title + " " + desc)[:2000]` 为内存态 `match_text`，保留落图 `title` 截断摘要与指针、正文不落图，且不改变既有 symbol 直连优先级。此前离线抽样对关联率的估计约 +7.7 个百分点，属于方案估算而非正式写图成效；上线前复核抽样样本、误匹配和 ambiguous 护栏，并报告置信区间。
