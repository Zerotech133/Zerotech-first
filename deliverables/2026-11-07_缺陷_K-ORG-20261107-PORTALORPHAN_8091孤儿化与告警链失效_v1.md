# K-ORG-20261107-PORTALORPHAN：8091 周期性孤儿化，失败告警链实际失效

> 起因：核对"8091 pid 为什么从 48564 变成 57228"。结论不是崩溃，也不是我先前含糊说的
> "另有触发源"，而是一条**长期存在的结构缺陷**：任务实例被计划程序按 `PT10M` 强杀后，
> 前台阻塞的服务进程变孤儿，导致 `alert_fail_wrap` 这条失败告警路径**永不执行**。

## 一 事实链（每条都有证据，不推断）

### 1.1 14:02 与 14:07 两次都是「用户手动触发」

任务计划程序操作日志（`Microsoft-Windows-TaskScheduler/Operational`）：

```
14:02:03  id=110  任务计划程序已为用户"t"启动任务"\AI工作站门户API"…
14:07:24  id=110  任务计划程序已为用户"t"启动任务"\AI工作站门户API"…
```

`id=110` = 用户请求触发；`id=107` = 时间触发器触发。所以这两次既非崩溃自愈，也非未知触发源，
而是**以 `t` 身份执行的手动 `Start-ScheduledTask`**（我当时在你窗口旁边等 tick，16 秒就被消费，
就是这个原因——不是"另有触发源"，是并行手动触发）。

今日事件计数：`100=16`（实例启动）/ `107=12`（时间触发）/ `110=4`（用户触发）/
`322=6`（实例在跑，跳过）/ `329=2`（超时强杀）/ `330=2`（用户停止）。

### 1.2 8091 现在是孤儿进程

```
8091 pid=57228  started=14:07:45  ppid=53468
parent (53468) GONE  ← 该 launcher 实例于 14:17:24 被事件 329 强杀
```

事件 329 原文：「由于超出为执行任务分配的时间(该时间在任务定义中配置)，任务计划程序已终止
"\AI工作站门户API"任务的实例…」。任务配置 `ExecutionTimeLimit=PT10M`、`MultipleInstances=IgnoreNew`。

强杀只杀 powershell 宿主，**不连带 python**——所以服务没死（对外 200 至今），但父子关系断了。

### 1.3 因此失败告警路径失效

`portal/start_portal_api.ps1` 尾部（前台阻塞形态）：

```powershell
& 'C:\Program Files\Python311\python.exe' 'C:\aios\portal\portal_api.py' 1>> … 2>> …
$rc = $LASTEXITCODE
if ($null -eq $rc -or '' -eq "$rc") { $rc = 1 }
('python exited code=' + $rc + …) | Out-File $log -Append -Encoding utf8
if ($rc -ne 0) {
    & python -X utf8 C:\aios\news_collector\alert_fail_wrap.py portal_api $rc C:\Temp\portal_api_err.log
}
```

`$rc` 只有在 **python 退出且父 powershell 还活着** 时才拿得到。实例被 329 强杀后父已消失，
python 之后无论怎样退出，这段都不会跑。旁证：`C:\Temp\*alert_fail*` 无任何文件。

### 1.4 但恢复能力仍在（不要据此高估风险）

launcher 每 5 分钟一跳，探活失败即拉起，日志为证：

```
skip: 8091 already serving 2026-11-07T14:20:02
skip: 8091 already serving 2026-11-07T14:25:02   （一直到 14:45:02，共 6 跳）
```

所以现状是：**服务可用、恢复可用、告警不可用**。属于"静默失效"，不是"服务中断"。

## 二 风险定级

| 项 | 现状 | 定级 |
|---|---|---|
| 服务可用性 | 200，孤儿进程不影响监听 | 无 |
| 崩溃恢复 | ≤5 分钟，靠 launcher 探活 | P3 |
| **崩溃告警** | **失效**（父进程已被强杀，`$rc` 分支不可达） | **P1（静默）** |
| 孤儿累积 | 每次强杀留一个孤儿；`restart-flag: killed [3~4 个 pid]` 说明同窗口可能存在多个 | P2 |

## 三 三个方案（均需提权执行，故本单只出方案不动手）

### 方案 A：`ExecutionTimeLimit` 改 `PT0S`（最省事，但有反作用）

实例永驻 → 父子不断 → 告警链恢复。**风险**：`MultipleInstances=IgnoreNew` 下，一旦 powershell
僵死而 python 已死，任务再也不会启动新实例，8091 永久 DOWN——把一个"每 10 分钟自愈"的机制
换成"永不干预"。**不推荐**。

### 方案 B：改后台分离启动（与 8095/8097/8099 形态统一，推荐）

`start_portal_api.ps1` 把 `& python …` 改为 `Start-Process -WindowStyle Hidden` 分离启动后立即
返回；失败告警不再依赖子进程退出码，而由**探活结论**驱动（探活失败→拉起→若拉起后仍不服务则
`alert_fail_wrap`）。这样：
- 实例秒级结束，`PT10M` 不再是陷阱（可保留，作为僵死兜底）；
- 与其余三口"探针 + 分离拉起"的模式一致，降低认知负担；
- 告警判据从"退出码"变成"可用性"，后者才是真正关心的。

代价：脚本行为变更（前台→后台），需一次回归：`-health` 三连、flag 换血、`kill` 后 ≤5 分钟自愈。

### 方案 C：不动启停，只把告警挪到探活路径（最小改动）

保留前台阻塞，只在"探活发现不服务"的分支里加一条 `alert_fail_wrap`。仍是前台阻塞，
10 分钟强杀照旧，孤儿照旧——只补告警。改动最小但治不了孤儿本身。

### 推荐

**B**，并把 `PT10M` 保留为僵死兜底。若你想先止血，先做 **C**（3 行），再做 B。
