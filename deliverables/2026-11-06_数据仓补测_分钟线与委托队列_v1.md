### 1.2 完整度分层 —— 问题在这里

按文件大小分档（全月单股约 110~120KB，4~5 天约 26KB）：

| 月份 | 股票数 | 全月完整 | 仅部分 | 判定 |

| 202611 | 800 | — | — | 当月进行中 |

抽查 30 个 202610 小文件，**中位覆盖 4 天，全部是 10/08~10/13**。
即：**10 月 14 日起全市场分钟线停采，只有 801 只补齐到月底。**

这不是「没有数据」，是「有数据但有 4,213 只 × 13 个交易日的洞」。任何跨 10 月的分钟级回测都会在这段静默失真 —— 而且不会报错，只会样本变少。这是比「整表缺失」更危险的一类问题。

## 2. 委托队列：确认没有，且免费渠道拿不到

### 2.1 三处搜证，全零

| 搜证面 | 方法 | 结果 |
|---|---|---|
| 本地数据仓 | 100.6 万文件全扫，正则 `tick\|order_queue\|entrust\|level2\|bid\|ask\|depth` | 仅命中 `BID.parquet`（美股拍卖行 BID）等噪声，**零真实资产** |
| 远端 181 表 | 全表清单逐条比对 | **无 tick / 逐笔委托 / 委托队列 / 十档盘口** |
| 通达信协议 | `pytdx` 源码解析 | `get_security_quotes` 只解析 **5 档**（bid1~5 / ask1~5 + 量），协议层就没有十档 |

`ts_stk_auction` 系列容易误认：它是**集合竞价的撮合结果**（vol/price/amount/pre_close/turnover_rate），是「竞价成交了什么」，不是「谁挂了多少单在排队」。

### 2.2 竞价期间的陷阱：`buyorsell=8` 不是委托

实测 09:15~09:25 集合竞价期间，分笔接口会持续推送 `buyorsell=8` 的记录，**但 vol 恒等于 0**（1012 条全部 vol=0）。这是通达信推送的**虚拟撮合参考价快照**，不是挂单，更不是排队明细。

误把它当「竞价委托」会得出完全错误的结论：看起来竞价期间有 1000+ 笔「委托」，实际一笔都没成交。

### 2.3 Level-2 的边界（要不要买，取决于你要回答什么问题）

| 数据 | 免费（Level-1 / 通达信） | Level-2 |
|---|---|---|
| 3 秒快照成交 | ✅ 可得（本轮已验证） | ✅ 逐笔成交（更细） |
| 五档盘口 | ✅ 盘中实时（无历史） | ✅ 十档 |
| 逐笔委托（每笔挂单） | ❌ | ✅ |
| **委托排队明细（最优档挂单是谁）** | ❌ **物理不可得** | ✅ |
| 竞价期间委托申报 | ❌ 只有虚拟撮合价 | ✅ |

**判断**：您上一轮问的「每手多少手、分时线上下、委托排队」，其中「委托排队」这一项，免费渠道是死路 —— 它不是数据没采，是交易所根本不对外发 Level-1 委托明细。公开报价区间 3~8 万/年（券商柜台或数据商），需实际询价。

但**在买之前，先确认这 3~8 万能否换回决策价值**：下一节证明，免费渠道已经能拿到 96% 的「行为痕迹」信息。

## 3. 但分笔能自采 —— 本轮最大增量

### 3.1 通道已验证

`pytdx` 的 `get_history_transaction_data(market, code, start, count, date)`：

| 指标 | 实测值 |
|---|---|
| 回溯深度 | **2017-01-03 仍有数据**（约 9 年），2020/2018/2017 全部命中 |
| 单股单日条数 | 4,723 条（000001，20261105） |
| 时间粒度 | **3 秒快照聚合**（18 笔/分钟，263 分钟） |
| 时间精度 | 仅 `HH:MM`，**无秒**，同分钟多笔顺序不可辨 |
| vol 单位 | **手**（1 手=100 股） |

### 3.2 数据完整性：两道独立校验都通过

**校验一（单股，对日线）**：000001.SZ 20261105 分笔 vol 合计 1,229,270 手，日线 1,228,997 手，**比值 1.00022**。

**校验二（全市场，5,217 只）**：中位比值 **1.00021**，p05=1.0，p95=1.00131，**5,211/5,217（99.88%）落在 1% 误差内**。

**校验三（全市场金额）**：单日分笔 amount 合计 **21,188.6 亿元 = 2.12 万亿**，与当日 A 股实际成交额吻合。

结论：`vol` 单位是手，分笔覆盖完整全天，无系统性缺失。

## 4. 已交付：本地采集器

**路径**：`quant_backtest/tools/research/tick_collector.py`（约 250 行）

```bash
# 探测（不落盘）
python tools/research/tick_collector.py --date 20261105 --limit 20

# 全市场落盘
python tools/research/tick_collector.py --date 20261105 --all --workers 7 --apply
```

设计要点：
- **服务器池自动探测**：内置 7 个已知可用节点（104 个候选里实测 7/16 可用），按延迟排序，worker 轮转分摊
- **重复键不去重**：同 `(time,price,vol,buyorsell)` 的重复是合法成交片段，去重会让 vol 合计低于日线（实测丢 163 条/4723）
- **自动校准**：采完自动与当日日线 vol 比对，误差 >1% 在报告里标记
- **断点续采**：目标文件已存在则跳过
- **默认 dry-run**，`--apply` 才落盘
- 产出 `data/tick/{YYYYMM}/tick_{YYYYMMDD}.parquet` + `reports/tick_collect_{date}.json`

**注意**：`20261105` 已有 79.61MB 完整文件；`tick_20261105.sample20.parquet`（20 只样本）是过程留档，可删。

## 附：本轮实测的边界（诚实标注）

1. **五档盘口未在盘中验证**。当前为非交易时段，`get_security_quotes` 返回空。字段结构已从 pytdx 源码确认（bid1~5/ask1~5 + 各档量），但**盘中真实可用性需开盘后复测**。
2. **分笔是 3 秒快照，不是交易所逐笔**。单笔委托的原始手数、拆单前的原始挂单，物理不可复原。所谓「每手多少手」只能在 3 秒片段层面统计，不能还原到单笔委托。
3. **`ts_stk_mins` 远端超时未解决**，只能确认接口存在，未验证可取。
4. 采集依赖第三方行情服务器（7 个公共节点），**无 SLA**。节点失效需重新探测；公共节点的可用性会随时间漂移。
