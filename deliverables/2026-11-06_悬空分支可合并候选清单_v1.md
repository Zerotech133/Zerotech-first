## 二、判据（任何人都可复算）

### 1. 净贡献：逐文件三方比对

「分支有独有提交」不等于「分支有未落地的改动」。对每个文件比三个版本：

```
base   = git merge-base master <branch>
files  = git diff --name-only base <branch>      # 分支自己动过的文件

master:<f> == <branch>:<f>   → ABSORBED  改动已被 master 吸收（可能被后续提交覆盖）
master:<f> == base:<f>       → UNMERGED  master 从没动过，分支改动真的没落地
两边都是新内容               → BOTH     可能可叠加，也可能冲突
branch 有、master 没有       → MISSING  整个文件丢了
branch 删、master 还在       → DELETED  删除未生效
```

净贡献 = UNMERGED + BOTH + MISSING + DELETED 的文件数。为 0 才是「真的没事可合」。

这一步纠正了一个常见误判：`git cherry` 显示 patch-id 等价，只能说明**某些提交**被吸收过，不代表分支里所有文件都落了地。初版用 cherry 判出 15 个「可安全删」，逐文件比对后有 5 个仍带真实未落改动，其中 `task/WO-INTEL-EVID-API-20261104` 的 `portal/api_intel_evidence_v1.py` 与其测试、交付文档**在 master 上完全不存在**——若按初版结论删掉，这份工作就只剩 reflog 能找了。

### 2. 冲突：无副作用试合并

```
git merge-tree --write-tree --merge-base=$(git merge-base master <branch>) master <branch>
# rc=0 干净；rc=1 有冲突，输出里 CONFLICT 行给出冲突文件
```

不 checkout、不动工作区，只在 object 库里算一棵树。

### 3. 顺序：把树当中间态逐级叠加

单分支无冲突 ≠ 一批合起来无冲突。把上一步产出的 tree 当下一次合并的左侧，`--merge-base` 仍取该分支与 master 的分叉点，就能模拟「依次合并」的累积效果。第三节那个结论就是这么来的。
