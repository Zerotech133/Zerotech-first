# `/keys` 页面整体复盘 · 2026-10-28

> 对象：`http://127.0.0.1:8796/keys`（实际渲染 + 全部后端接口）
> 结论：**功能齐全，但信息架构已经失控**。当前更像“平台管理员总后台”，不是“Key 管理页”；建议拆页 + 分层，否则越加越难用。

---

## 一、当前实测规模

| 指标 | 数值 |
|---|---|
| 页面高度 | **6387 px** |
| 一级区块 | **8 个** |
| AI Key 卡片 | **19 张** |
| 按钮 | **69 个** |
| 下拉框 | **29 个** |
| 席位（含 relay） | **20 个** |
| 中转站 Key | **8 条**（3 healthy / 2 invalid / 1 quota / 2 degraded） |
| 虚拟 Key | 1 |
| 统一凭据 | 12（ok 5 / plaintext 7） |
| 模型偏好 | 7 模型 × 11 研发成员 |
| Mission | 8 个 |

页面区块顺序：

```text
平台中转站（主入口）
模型通道（本地 + GPT-6）
19 张 AI Key 卡
研发板块 · 模型手动切换
Mission · 文档→任务 DAG（含真实派工/合并）
统一凭据（JEV/数据/飞书）
虚拟 Key
切换日志
```

---

## 二、合理的地方

1. **平台中转站放最上面**，符合“先有平台上游”的设计；
2. **模型通道**单独列出本地 4B/9B/35B 与 GPT-6；
3. **不暴露真 Key**：Key 池与凭据目录都只显示掩码；
4. **虚拟 Key 概念正确**：AI 用 `vk-`，不碰真 Key；
5. **凭据目录有加密状态**（含 Tushare DPAPI）；
6. **Mission 面板可 dry-run**，不会误建 worktree；
7. **研发模型切换**支持所有模型，方向正确。

---

## 三、主要不足

### P0：信息架构失控

- 8 个业务域混在一个页面：**模型路由、席位 Key、研发模型、Mission、凭据、虚拟 Key、日志**；
- 没有 tab/锚点导航，用户要滚 6000+ px；
- 页面标题仍是 **「三席多 Key 池」**，实际 20 个席位、19 张卡，名不副实；
- 小白与管理员看到的是同一套复杂界面。

### P0：高风险操作与 Key 管理混在一起

- 在 Key 页面可以直接 **真实派工 / 建 worktree / 自动评审门合并 / Worker 自动接单**；
- 这些属于研发编排，误点会创建真实工单/worktree；
- 建议拆到独立 `/mission` 页面，Key 页面只保留“去 Mission”入口。

### P1：概念重复

同一件事出现在多处：

- 平台中转站 vs 模型通道 vs 中转站 GPT-6 卡；
- 每张席位卡 vs 研发模型手动切换表；
- 统一凭据里的 Tushare vs 平台凭据库；
- “自动切换”开关、Key 状态、模型状态分散。

用户无法判断**唯一事实源**在哪。

### P1：19 张卡严重冗余

- 15 位部门负责人全部 0 Key，但每张卡都渲染完整的 URL/模型/Key/优先级表单；
- 大量空白卡占页面高度；
- 建议：主力 5 席（指挥部）保留卡；部门负责人改为表格 + “配置”弹窗；无 Key 的折叠/置灰。

### P1：状态语义不清

- `degraded=True` 的席位显示“全部不可用”，但实际可能有 1–3 条 Key；
- `invalid / pending / quota / degraded / healthy` 混用；
- “绑定 glm-5.3”与实际 Key 的 `glm-4-flash` 不一致；
- 需要统一状态机：`可用 / 限流 / 失效 / 未配置`，并给“最近一次测试时间”。

### P1：凭据目录“只读”但标题像管理

- 7 条明文凭据只能看，不能加密/轮换/新增；
- Tushare 平台保险箱已加密，但页面没有“新增业务 Key”入口；
- 建议独立 `/credentials` 页，支持新增/轮换/迁移，默认全遮蔽。

### P1：虚拟 Key 被埋没

- 它是 AI 接入的核心凭据，却放在页面最底部；
- 缺少：使用统计、最近使用、配额、所属 AI、启停原因；
- 建议表格化并支持“一键接入新 AI”。

### P2：日志不可用

- 原始切换日志一次性铺满页面底部；
- 无筛选（席位/结果/时间）、无分页、无导出；
- 建议放独立“审计日志” tab。

### P2：可用性与安全

- 输入框只有 placeholder，无 label/aria；
- 删除等操作只有 confirm，无二次确认/审计；
- 页面只绑定 8796，平台主入口 8734 没有导航入口；
- 无管理员 PIN/权限分层（虽然只监听本机）。

---

## 四、建议的信息架构

```text
/keys（默认「概览」，小白视图）
  ├─ 顶部状态条：上游健康 / 本地模型 / 已接入 AI / 异常 Key
  ├─ Tab 1 概览
  ├─ Tab 2 模型路由（平台中转站 + 模型通道，唯一事实源）
  ├─ Tab 3 AI 席位（主力 5 卡 + 部门负责人表格）
  ├─ Tab 4 接入与凭据（链接 /credentials）
  ├─ Tab 5 虚拟 Key（表格 + 新 AI 接入）
  ├─ Tab 6 日志（筛选/分页）
  └─ Tab 7 任务编排（链接 /mission，不在本页直接操作）
```

关键原则：

1. **一个概念只出现一次**；
2. 默认只展示小白需要的状态，管理员操作放折叠/二级页；
3. 高风险操作（真实派工/合并/Worker）全部迁出 Key 页；
4. 所有状态用统一四态 + 最近测试时间；
5. 部门负责人列表化，不再铺 15 张表单。

---

## 五、优先级建议

| 优先级 | 动作 | 影响 |
|---|---|---|
| P0 | 拆出 `/mission`，Key 页只留入口 | 防误操作、立即降高 |
| P0 | 顶部加 Tab/锚点导航 + 状态总览 | 6.4k px → 可按需查看 |
| P1 | 部门负责人卡改表格 + 配置弹窗 | 页面高度减半 |
| P1 | 合并中转站与模型通道重复信息 | 唯一事实源 |
| P1 | 统一 Key 状态机 + 最近测试时间 | 消除“全部不可用”误判 |
| P1 | 独立 `/credentials` 可写管理 | 明文凭据可迁移 |
| P2 | 虚拟 Key 表格化 + 使用统计 | AI 接入可运营 |
| P2 | 日志筛选/分页/导出 | 审计可用 |
| P2 | 加 8734 导航入口 + 管理员 PIN | 入口与权限 |

---

## 六、结论

当前 `/keys` 的**功能没有缺失，问题在组织方式**：它把“模型路由、Key 管理、凭据、虚拟 Key、研发编排、日志”全部堆在一个长页面。继续加功能会加速失控。

建议先做 **Phase A（低风险、收益最大）**：

1. 页面标题改为 **「AI 接入与 Key 管理」**；
2. 顶部加状态总览（上游/本地/AI 数/异常 Key）；
3. 加 Tab/锚点导航；
4. 把 Mission 区块迁到独立 `/mission`，本页只留链接；
5. 部门负责人卡改为表格 + 配置弹窗。

完成后页面高度可降到约 2000px，再进入 Phase B（凭据可写、虚拟 Key 运营、日志审计）。
