# 情报体系 P1 · progress 判定一致性与提示词 v2 定档

- 编制时间：2026-11-04 深夜（承接 v1.6 带宽定档）
- 对应阶段：P1 收尾（事件层第二层判定 · 判据层）
- 触发问题：技术债 #16 —— 四对"主体相同、事件不同"的配对里，三对判 `unrelated`，唯独"央行发布季度报告 / 开展 MLF 操作"判 `progress` 并合并
- 结论一句话：**这不是带宽问题，是提示词判据缺约束；v2 把 16 对硬负例的误合并从 4 处压到 0 处，默认已翻至 v2，v1 逐字冻结保留**

---

## 1. 结论摘要

| 指标 | v1（旧默认） | v2（新默认） |
|---|---|---|
| 探针集 24 对准确率 | 20/24 = **83.3%** | 24/24 = **100%** |
| 16 对"不应合并"误合并 | **4** | **0** |
| 8 对"应合并"漏合 | 0 | 0 |
| 稳定性（温度已 0） | 2 轮零翻转 | 3 轮零翻转 |
| 真机端到端（带宽 0.05） | 28 事件 / 0 拆散 / 0 误合并 / 14-14 | **完全相同** |
| 真机端到端（带宽 0.10） | 27 事件 / 0 拆散 / **1 误合并** | 28 / 0 / **0** |
| LLM 调用（带宽 0.05） | 2 | 2 |

两个必须说清的点：

1. **v2 不改善今天的产出**。带宽 0.05 下 v1 和 v2 的端到端结果逐项相同（28/0/0/14-14），因为 0.05 带宽内只有 2 对配对，而那 4 个 v1 判错的配对全都落在带宽之外。**v2 是拆弹，不是提速**：它修的是"带宽一变宽就会炸"的隐患。
2. **v2 让带宽从质量旋钮退化成成本旋钮**。v1 时代放宽带宽 = 拿误合并换召回；v2 之后放宽带宽 = 只多花调用（见 §6 实测：0.10 下 6 次调用、0 误合并）。0.05 仍是最省的选择，但它之所以仍是 0.05，理由已经从"再宽会错"变成"再宽没用"。

## 2. 问题定性：不是阈值，不是带宽

v1.6 已用数据排除两条路：阈值 0.73~0.76 同分（无调整空间）、带宽 0.03/0.05/0.08 标定（0.05 是漏合归零的最小值）。但当时只能观察到"四对性质相似、结论不一致"这一现象，无法解释原因。

本轮把四对的实际提示词与模型回复都取出来看，这才定性清楚：

- 温度已固定 `temperature: 0`，两轮重跑结论零翻转 → **不是采样随机性，是系统性偏差**；
- 四处误合并的理由结构**完全同形**：都是"主体均为 X，从 A 到 B，属于同一…的不同阶段"。

即模型并没有在"两件事是否同一件"上犯错，它在**忠实地执行一条宽松的判据**：v1 的 `progress` 定义只写了"主体相同、事态向前推进"，从未要求"推进的必须是同一个事项"。于是任何"同主体 + 时间先后"都会被读成 progress。

---

## 3. v1 的四处误合并（原文取证）

探针集 24 对（8 对真该合、16 对不该合），v1 判错 4 对，**全部是 `progress`**：

| 配对 | 真值 | v1 给的理由（原文） |
|---|---|---|
| `parallel-pboc-report-mlf` | 央行发季度报告 / 开展 MLF 操作，两件并列 | "主体均为央行，从发布季度报告到开展具体操作，属于同一宏观政策进程中的不同阶段" |
| `parallel-moutai-revenue-price` | 茅台发财报 / 上调出厂价，两件并列 | "茅台先宣布上调出厂价，随后披露营收增长，属于同一商业策略推进的不同阶段" |
| `other-tsmc-capex-fab` | 台积电上调资本开支 / 亚利桑那厂量产 | "主体均为台积电，从上调资本开支指引到亚利桑那厂开始量产四纳米芯片，事态向前推进" |
| `other-huawei-results-harmony` | 华为三季度业绩 / 鸿蒙 5 发布 | "主体均为华为，从发布三季度业绩到后续发布鸿蒙 5，属于同一主体在不同时间点的连续业务进展" |

注意后两条来自 `other-*` 组而不只是 `parallel-*` 组——**失效面比最初观察到的更宽**：不止"同主体的两件宏观事项"，连"同主体的业绩与产品发布"也会被读成推进。这也解释了为什么这条缺陷不能靠"给 parallel 类加白名单"绕过。

## 4. v2 的四处改动

改动全部集中在提示词，零代码逻辑改动：

1. **`progress` 定义加"单一事项"约束**：改成"**只有一个具体事项**在推进，A 是它的前一阶段、B 是它的后一阶段"。
2. **加三条并列判据**："progress 必须同时满足三条"——同一事项、可观测的向前推进、能指出前后阶段；"两件并列事项"明确排除。
3. **加 `stage` 输出字段**：选 progress 时必须写出 `"stage": "A：… → B：…"`，写不出具体阶段就说明不是同一件事。这是把"判据"变成"可验证的输出"，模型无法只给结论不给阶段。
4. **反例换成域外样本**："某省发布年度经济数据"与"某省开通新高铁线路"。刻意不用真机语料里央行那对——否则探针集上就变成背答案，标定结论随之失效（这条由测试守，见 §8）。

配套：`num_predict` 160 → 220。加 `stage` 后输出变长，160 会截断成不合法 JSON，进而被判为 `failed` 并回落规则判定——**这个坑不体现在准确率上，只体现在 `degraded` 计数上，很容易漏**。

## 5. 探针集：24 对，两版对照

`tests/fixtures/judge_probe.json`，全部取材真语料：

| 分组 | 对数 | 性质 |
|---|---|---|
| `same-*` | 4 | 同事件不同报道方（应合） |
| `progress-*` | 4 | 同一事项的推进（应合） |
| `parallel-*` | 4 | 同主体、同期两件并列事项（不应合） |
| `other-*` | 12 | 同主体不同事 / 不同主体（不应合） |

**正例只占 1/3 是刻意的**：这条缺陷只在负例上暴露，若按真实分布取样（正例远多于硬负例），误合并率会被稀释到看不见。

真机结果（`scripts/calibrate_judge_prompt.py`）：

```
| 版本 | 应合并 | 漏合 | 不应合并 | 误合并 | 准确率 | 失败调用 |
| v1   |   8   |  0  |   16    |   4    | 83.3% |    0    |
| v2   |   8   |  0  |   16    |   0    | 100%  |    0    |
```

**置信度的诚实表述**：16 对负例里 0 错，95% 置信上界约 17%（`1-0.05^(1/16)`）。也就是说 v2 不是"已证明零缺陷"，而是"从 25% 降到 ≤17%，且 8 对正例一个没丢"。要把它压到 5% 以下，需要约 60 对硬负例——当前语料只有 42 条事实，做不到，这是本轮明确留下的残余不确定性（技术债 #18）。

## 6. 端到端实测（这才是"要不要翻默认"的依据）

### 6.1 带宽 0.05：v1 与 v2 完全一致

| 版本 | 事件数 | 拆散 | 误合并 | 独立来源数 | 调用 |
|---|---|---|---|---|---|
| v1（v1.6 已测） | 28 | 0 | 0 | 14/14 | 2 |
| v2（本轮） | 28 | 0 | 0 | 14/14 | 2 |

原因：0.05 带内只有 S11（cos=0.7133）和 S04/solo-05（cos=0.7203）两对，**都不在那 4 个判错配对里**。所以 v2 在今天的语料上零收益——这一点必须写在前面，否则"v2 更好"会被误读成"上线就能看到变化"。

### 6.2 带宽 0.10：v2 把 v1 的误合并吃掉了

| 版本 | 事件数 | 拆散 | 误合并 | 独立来源数 | 调用 | 耗时 |
|---|---|---|---|---|---|---|
| v1 + 0.10（v1.6 已测） | 27 | 0 | **1**（央行对） | 14/14 | 6 | 48 s |
| v2 + 0.10（本轮） | 28 | 0 | **0** | 14/14 | 6 | 74 s |

v2 + 0.10 的 6 对复核全部给出 `unrelated`，理由逐条对得上真值（茅台提价/营收、央行报告/MLF、隆基增持/提价、英伟达财报/显卡、宁德净利/麒麟电池），S11 仍正确提升。

**这条实测的意义**：v1.6 的结论"0.10 是净亏"在 v2 下不再成立于"质量"维度——0.10 现在是同等质量、三倍成本。带宽的语义从"召回 vs 误合并的权衡"变成纯粹的"成本"。

## 7. 版本机制（为什么不能只是"改一下提示词"）

| 设计 | 理由 |
|---|---|
| `PROMPT_VARIANTS = {"v1": …, "v2": …}` | 提示词是事件层唯一的语义判据。原地改字，等于让历史上所有事件的判据不可复现——日历上同一个事件昨天 28 个今天 27 个，无从解释 |
| v1 **逐字冻结** + 金标准用例 | 有人为了"顺手优化措辞"改 v1，用例必须立刻红。要改就新建版本号 |
| `name = "llm-ollama-v2"` 写进 `model_version` | 事后能凭库里的 `model_version` 分辨某批事件由哪套判据产出。类属性写法会让所有实例同名，已由变异测试守住 |
| 未知版本回落到默认**并告警** | 静默回落会让"配了 v3 没生效"变成幽灵问题；但也不能抛异常——拼错一个环境变量不该让整个聚类停摆 |
| 越界/非法值不 clamp | clamp 会让人以为"配了 0.20 就生效到 0.55"，实际悄悄按上限跑。宁可告警 + 回落，让人看到配置没被采纳 |

## 8. 测试与变异验证

新增 47 项用例（`tests/test_judge_prompt_variants.py` 28 项 + `tests/test_calibrate_judge_prompt.py` 19 项）。变异测试 **14/14 全部暴露**，其中两项是这轮的真正收获：

1. **`'"stage"' in prompt` 是个假守卫**。删掉输出格式行里的 `"stage": "仅 progress 填写前后阶段…"` 后，46 项测试全绿——因为判据段里还有一句"必须写出 `"stage"` 字段"，把断言满足了。**断言被另一处同名字样满足，等于没断言**。改成钉住格式行原文后立刻暴露。
2. **锚点选错等于没变异**（上一轮带宽标定已踩过一次，这轮又差点重演）：变异脚本第一版把 `ROOT` 算错，跑出来全绿，实际是"变异体根本没写进文件"。

已守住的契约：默认版本是 v2 且带决策依据、`build_judge_prompt` 必须尊重 variant、未知版本回落、`name` 是实例属性、v2 反例不得用域内语料、`stage` 必须进 `rationale`、v1 逐字冻结。

全量：**595 passed / 2 failed / 21 skipped / 19 errors**，失败与错误全部为预存环境缺口（`pypdf` / `uvicorn` / `opencv`），与 P0 基线一致。

## 9. 已知残余风险

| # | 风险 | 现在的处理 |
|---|---|---|
| 1 | v2 是**提示词级**修复，没有强制性。模型对"新的同主体对"仍可能偶发 progress | `stage` 字段给了可观测性：`rationale` 里带 `stage:A：… → B：…`，判错时能复盘错在哪一步。是"可发现"而非"可阻止" |
| 2 | 探针集仅 24 对（16 负例），统计置信上界 17% | 语料扩到 200+ 事实后重跑 `calibrate_judge_prompt.py` 补硬负例；把"新增硬负例"并入语料扩充的验收项 |
| 3 | 正例 8 对偏容易（4 对 same 是近乎重复的报道） | 已记录；下一轮补"表述差异大的同事件"作为难正例 |
| 4 | 换版本后历史事件与新版不可直接对比 | `model_version` 已分级标记；跨版本比较须注明，不能直接比事件数 |
