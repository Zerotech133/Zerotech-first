## 1. 一句话认识零界

**零界是一个给“有判断力、有想法、但不想亲自承担完整软件工程”的持续创业者使用的个人事业操作系统。**  
它让你用自然语言和一群可长期协作的 Agent，把想法推进成有依据、受约束、可试用、可迭代、可验收的成果。

对外，零界的能力底座是 **“开源情报（OSINT）抓取与数据能力平台，金融为垂类”**。  
这两句话不是两个产品：

- **产品定义**回答“为谁解决什么问题”：个人事业操作系统。
- **能力/商业定位**回答“靠什么能力切入”：开源情报 + 数据 + Agent 编排，金融是第一个垂类。
- 本说明书只描述**一个产品**：零界。OSINT、金融、量化是它的能力场景，不是另外三个产品。

## 2. 产品定位与边界

### 2.1 适合谁

- 有行业判断、有想法，但不愿/不能组建完整软件团队的个人或小团队。
- 需要把“研究—判断—执行—复盘”沉淀为可追溯账本的人。
- 需要多 Agent 协作，但要求“人保留最终决定权”的人。
- 需要把开源情报、金融数据、内容资产变成可复用能力的人。

### 2.2 不适合谁

- 想要“全自动印钞/稳赚策略”的人：零界不做收益承诺，量化策略当前 **0 个 approved**。
- 想要“开箱即用的 SaaS 商业产品”的人：当前是内部系统，商业/客户/计费能力未完成。
- 想要“无审查全自动执行”的人：零界有授权分级、失败关闭、人工裁决。

### 2.3 产品原则（8 条）

1. 对话是唯一入口。
2. 同一本账（Goal → Item → Outcome）。
3. 授权分级，人保留决定权。
4. 诚实标注：事实 / 假设 / 推断 / 未接通。
5. 失败关闭，不把红灯包装成绿灯。
6. 长期记忆，不重复造轮子。
7. 能力可替换，不锁死单一模型/数据源。
8. 证据可追溯，结论可复核。

## 3. 四个工作面

零界不是单一“聊天框”，而是四个工作面的组合：

| 工作面 | 解决的问题 | 当前状态 |
|---|---|---|
| 产品与研发 | 把想法变成可验收的软件/能力 | 可用（内部） |
| 商业与融资 | 客户、方案、报价、融资材料 | 部分可用，M1–M4 未验证 |
| 内容与增长 | 选题、采集、学习卡、报告、分发 | 可用（内部） |
| 量化与投资研究 | 数据、因子、回测、候选、影子盘 | 研究态；0 approved，不接实盘 |

## 4. 快速开始

### 4.1 打开入口

- 统一门户（推荐）：`http://127.0.0.1:8080/`（nginx 入口）
- 直连 API/工作台：`http://127.0.0.1:8091/`（本机开发/排障）
- 部分页面在 8734 工作台；具体入口以门户导航为准。

> 当前环境是本机/内网，不是公网 SaaS；不要直接把 8091 暴露到公网。

### 4.2 第一次使用（5 步）

1. 打开门户，进入“工作台/今日”。
2. 在“组织/Agent”里确认当前席位与权限（A0 老田为最终裁决人）。
3. 在“任务/目标”里建一个 Goal（例如“本周完成 X 研究”），再拆 Item。
4. 用对话让 Agent 产出证据（数据、引用、文件），不要只要结论。
5. 在“Outcome/复盘”里验收：通过/不通过/待补，写清依据。

### 4.3 权限与安全

- 本机回环访问默认放行；反代/局域网访问需要 `X-Portal-Token`。
- 写操作/高成本操作需要授权；发布/重启需要人工审批。
- 不要把 token、数据库口令、API Key 写进文档/聊天/代码。
- 当前鉴权仍是“列举式默认放行”，新增端点需要登记；这是已知限制，见 §9。

## 5. 功能地图

### 5.1 今日/工作台

- 今日态势、观察池、最近报告、事件库、数据覆盖、数据时效。
- 适合：每天 5 分钟知道“该看什么/公司在跑什么/哪里卡住”。

### 5.2 组织与 Agent 团队

- 17 个部门、席位、角色、汇报关系；支持多 Agent 协作。
- 数据智能部：DATA1 张松（数据资源）、FACTOR1 蒋琬（因子挖掘）等。
- 原则：Agent 出证据，人做裁决；不让 Agent 代替人承担最终责任。

### 5.3 情报中枢 / JEV

- 采集 → 事件 → 判定 → 证据链 → 报告/预警。
- 适合：开源情报、公告、研报、社媒、盘中异动的归集与复核。
- 当前部分页面/接口仍在合并中，可能出现 404 或“未接通”标注。

### 5.4 数据仓

- 统一数据目录、表元数据、样本查询、血缘/质量/新鲜度。
- 适合：先确认“数据有没有、全不全、到哪天”，再谈结论。
- 已知问题：部分表资产登记/基线过期；使用前看 `data_freshness` 与 WARN。

### 5.5 因子服务

- 只读目录：288 个因子（Tushare 271 + 自研 17；1 个 blocked）。
- 计算接口：`POST /api/factor/compute`，子进程隔离、120s 超时、缓存、并发 2。
- 适合：研究/回测/组合构建；**不构成投资建议**。
- 已知问题：`/api/factor/health` 较慢（p50 约 2.5s），已加缓存但未部署。

### 5.6 策略中心

- 策略注册表、状态（live/shadow/tool/paused）、负责人、验证证据。
- 当前 14 条策略；**0 个 approved 可实盘**；S12 为影子观察。
- 适合：管理“研究→候选→影子→复核”的状态，不是“一键跟单”。

### 5.7 知识库 / RAG

- 语料入库、检索、问答、引用/groundedness 评测。
- 当前 RAG 支持 strict / strict_nocite；资料不足时固定拒答，不带引用。
- 适合：基于自有资料问答、学习卡、研报辅助。
- 限制：检索召回缺口会导致个别题引用不到 gold；引用正确率不是 100%。

### 5.8 学习卡 / 内容生产

- 视频/文章/研报 → 学习卡/摘要/报告。
- 适合：内容资产沉淀、选题、复盘。
- 当前卡片数量与审计报告可能不同步，使用前看报告日期。

### 5.9 Agent 平台 / 自动化

- 计划任务、日报/周报、数据采集、治理、告警。
- 适合：把重复工作变成可审计的自动化。
- 限制：任务失败不会自动变成“绿”；需要看台账/日志。

### 5.10 商业/客户门户

- 规划中：套餐、租户、用量、审计、客户门户。
- 当前**未完成**，不能对外售卖/承诺 SLA。

## 6. 核心工作流

### 6.1 研发闭环（Goal → Item → Outcome）

1. 建 Goal：一句话目标 + 验收标准 + 截止时间。
2. 拆 Item：每个 Item 一个可交付物、一个 owner、一个证据路径。
3. 执行：独立 worktree/任务单，不覆盖他人。
4. 验收：跑测试/检查，记录命令与输出。
5. 复盘：通过/不通过/待补；失败也要留证据。

### 6.2 情报 → 证据 → 判断

1. 采集：公告/研报/社媒/行情。
2. 归一：事件、标的、时间、来源。
3. 判定：规则 + 模型 + 人工复核。
4. 证据链：原文 → 判定 → 后验 → 归组。
5. 输出：日报/预警/研究结论，标注“事实/假设/推断”。

### 6.3 量化研究 → 候选 → 影子 → 复核

1. 数据：PIT、退市、复权、两融覆盖先校验。
2. 因子：目录/实现/方向/覆盖率；不把“有因子”当“有 alpha”。
3. 回测：成本、滑点、容量、样本外；预注册再跑。
4. 候选：登记证据包；不直接上线。
5. 影子：观察期、熔断、复盘；人裁决是否继续。
6. 实盘：当前**不开放**；0 approved。

### 6.4 内容/学习

1. 采集视频/文章/研报。
2. 提取概念、金句、案例、来源。
3. 生成学习卡/摘要/报告。
4. 人工审核来源与引用。
5. 归档到知识库/内容资产。

---

## 7. 数据与证据规则

- **先数据后结论**：数据缺失/过期时，结论必须标 WARN，不能假装完整。
- **引用可追溯**：问答/报告尽量带来源编号；资料不足时明确说“资料不足”。
- **PIT 原则**：回测只用当时可得的数据；不用未来函数/幸存者偏差。
- **成本意识**：策略回测必须计成本；零成本结论不算结论。
- **不构成投资建议**：所有策略/因子/报告均为研究证据。

## 8. 典型使用场景

### 场景 A：今天该看什么

打开工作台 → 看今日态势/观察池/最近报告 → 对异常项下钻 → 让 Agent 补证据 → 形成 3 条行动项。

### 场景 B：研究一个行业/标的

建 Goal → 数据仓确认覆盖 → 情报中枢拉事件 → 因子/策略中心看历史 → 让 Agent 写“事实/假设/风险”三段 → 人工验收。

### 场景 C：把内容变成资产

采集视频/文章 → 学习卡 → 主题聚类 → 生成报告/选题 → 归档 → 下次复用。

### 场景 D：管理一个多 Agent 任务

建任务单 → 指定 owner/审批人 → Agent 产出证据 → 质量门 → 人裁决 → 复盘。

## 9. 已知限制与诚实标注

> 这一节是产品的一部分，不是“自黑”。不写清楚，用户会误判。

| 限制 | 影响 | 当前状态 |
|---|---|---|
| 全量测试 39 failed / 2 errors | 不能宣称“稳定版” | 研发计划 W1–W2 收口 |
| 路由基线漂移（324 vs 171） | 部分页面/测试不一致 | 冻结后重生成基线 |
| 鉴权列举式默认放行 | 新增端点可能漏 token | 计划改“默认拒绝 + 注册表” |
| 未登记监听 4 个 | 端口表不可信 | 临时服务处置中 |
| factor health p50 2.5s | 健康检查慢 | 已加缓存，未部署 |
| 部分页面 404 | 入口未接通 | 产品说明书标“未接通” |
| B 阶段判据未闭合 | 不能宣称“B 完成” | 计划 W3–W6 给结论 |
| 量化 0 approved | 不能实盘/跟单 | 研究态 |
| 商业/客户门户未完成 | 不能对外售卖 | 路线图后续 |
| 文档口径历史分叉 | 读者可能误解 | 本说明书按“两层口径”统一 |

**不要这样使用零界：**

- 不要用单条问答替代尽调。
- 不要把“影子盘”当“实盘”。
- 不要在没有数据覆盖说明的情况下引用结论。
- 不要把内部试用版当公开发布版。

## 11. 运维、回滚与支持

### 11.1 日常检查

- `GET /health`：服务存活。
- `GET /api/factor/health`：因子服务/数据新鲜度。
- 计划任务台账：日报/周报/采集/治理是否成功。
- 端口：`python tools/check_ports.py --strict`。
- 工作区：`git status --porcelain=v1`（发布前必须干净/有 owner）。

### 11.2 回滚

- 代码：保留发布前 commit/tag；回滚用 `git revert`/部署上一版，不做 `reset --hard`。
- 数据：发布前备份 catalog/registry/static；回滚用备份文件。
- 配置：nginx/计划任务变更前备份；回滚命令写进发布说明。
- 8091：受控重启，保留旧 PID/日志；health 不过即回滚。

### 11.3 支持边界

- 内部问题：提任务单，附证据（命令/日志/截图/文件路径）。
- 不接“保证收益/保证准确率”的需求。
- 不接“绕过授权/直接改生产”的需求。

## 13. 一页纸总结
