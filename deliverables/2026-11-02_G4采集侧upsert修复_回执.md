## 一、根因与修复结论

- **根因**：`tushare_sync.py` 两处「滚动信息流 recent-only」循环把 research_report 最近约 6000 行**整批快照**用 `save_full()` 追加成新 `part_NNNN.parquet`——相邻批次内容高度重叠（实测 **96.3% 重复**），part 数增长但有效历史不增长，下游 glob 全部 part 读取即重复膨胀。
- **修复**：新增**按自然键 `(trade_date, ts_code, title, report_type)` 的追加式去重落盘** `save_full_dedup()`；两处入口对 research_report 改用它，其余表（news/major_news）保持原逻辑不动（最小改动面）。
- **关键取舍**：采用「**只追加新键行，不改/不删既有 part**」而非「整表 concat 重写」——对存量零风险（不重写/不删除历史分片、无并发读抖动），schema 完全不变；存量重复由读侧去重（Lead 已 consolidated，见 §四）。

## 二、代码改点（`quant_backtest/tushare_sync.py`，+89 / −2）

| # | 改点 | 说明 |
|---|---|---|
| 1 | 新增常量 `RESEARCH_REPORT_KEY = ("trade_date","ts_code","title","report_type")` | 自然键唯一定义处，含 G4 背景注释 |
| 2 | 新增 `_key_columns(df, key_cols)` | 键列存在性校验；任一缺失 → None（fail-open） |
| 3 | 新增 `_key_pairs(df, cols)` + `_is_missing(v)` | 键归一：**NaN/NaT → None**，避免 `nan != nan` 导致判重失效（ts_code 为空的行业研报场景） |

| 5 | 新增 `save_full_dedup(tbl, df, m, key_cols, note)` | 批次内 `drop_duplicates(keep="last")` → 过滤已存在键 → 只写新增行；无新增/空输入**不落新 part**（manifest rows=0 + note）；键缺失回退 `save_full`（老行为，不丢数据）；返回新增行数 |
| 6 | `batch_shallow()` recent-only 循环（L~370） | research_report 分支改 `save_full_dedup(..., "recent-only")`；news/major_news 不变 |
| 7 | `incremental()` 滚动信息流循环（L~850） | 同上，note=`"incr recent"`；两条采集入口都修，避免增量链绕过 |

## 七、风险与备注

1. **并发 run**：若同表两进程同时写，仍可能各写一份「新键」part（计划任务单实例，风险低；如未来并行化需加文件锁）。
2. **自然键含 `title`**：title 自带日期/pdf 名，采集侧稳定；若上游某日改写标题，会被视为新行（可接受，属数据源语义变化）。
3. **缺键列 fail-open**：上游字段改名时回退老行为（回到整批重复但**不丢数据**），采集日志/manifest note 可见 `dedup_fallback`，便于发现。
4. **manifest rows 语义变化**（见 §四）需在下次 data_health/看板口径说明。
5. 本单**未运行同步**，实际去重效果待下一次 TushareSync 计划任务 run 验证（预期 part 新增行数骤降、不再 96.3% 重复）。
