## 〇、一句话结论

**MySQL 降级为「上游兼容镜像」，PostgreSQL 15 升格为唯一关系主库，Neo4j 保留，向量不新增组件（将来用 pgvector），Parquet 湖补 DuckDB 查询引擎，第三方应用自带栈一律不动。**

即：**MySQL(只读兼容源) + PostgreSQL(关系主库) + Neo4j(图) + Parquet+DuckDB(湖) + Ollama(LLM)**，零界/RAGFlow 自闭环不掺和。

## 三、逐组件论证

### 1. MySQL —— 保留，但只做「菜鸟源兼容镜像」
- thunder_model 实例换机后缺失，但 xmap_sync 依赖其作上游；每日 169MB dump 一直在备份，DDL 快照在 `菜鸟\thunder_model\`。
- **建议**：从 `cainiao_mysql_alldb.sql.gz` 恢复一个**只读** thunder_model 实例（推荐独立小容器，隔离 RAGFlow 栈升级风险）。**不要**把 quant/情报主数据迁 MySQL——项目里 MySQL 零新增消费者，PG 的 xmap/lineage/stock_basic 已是事实标准。
- 定位：对外契约兼容层，永不承担新业务。

### 2. PostgreSQL —— 一主两库，短期不强合并
- quant_system 仅 8.2MB、zhice_os_v2 411MB，对 PG 15 是毛毛雨。
- **近期保持两容器**（业务域不同、零界有 alembic 演进）；**中期**可合为单容器多 database（pg_dump/restore 一次即成，回退容易）。
- SQLite 迁移目标：quant-pg 实例内新建 `quant_meta` database。
- **必须先做**：`xmap_sync init` 补课（换机欠账）。

### 3. Neo4j —— 保留，明确反对迁关系库
- 图谱查询本质是变长路径/社区/DTW 相似度，PG 递归 CTE 能写但开发维护成本高；KgDailySync 20 步流水线稳定；277MB dump 单机毫无压力。
- 边界：只有"实体-属性表"这类浅层关系才值得放 PG；图谱本体留 Neo4j；X3 血缘继续写 PG lineage schema。

### 4. 向量检索 —— 不新增 Qdrant，将来需要就 pgvector
- Qdrant 新机不存在，业务侧唯一向量需求已被 RAGFlow/Infinity 覆盖。
- **不引入**。未来 KG 语义检索落地时直接给主 PG 装 pgvector——少养一个存储，备份链路复用 pg_dump。

### 5. SQLite —— 分级处置
- **迁**：news.db / quant.db / tdx_info.db（合计 ~420MB，一夜完成）→ quant_meta。三库都被定时任务写、被门户/回测读，SQLite 在换机/备份/并发上是最弱一环（.bak 满地即漂移证据）。
- **不迁**：projects-archive 20+ 冷库——归档就是归档。

### 6. Parquet 湖 —— 保留为分析主存储，补 DuckDB
- 自研 catalog.json(210 表)+changelog+水位监控，架构方向正确。
- **加 DuckDB（嵌入式，pip 单包）**作 SQL 查询层，直接 glob parquet，替代 pandas 全量扫；catalog 可生成 DuckDB 视图。**坚决不上** Iceberg/Delta/Hive Metastore。
- 中期：68.6 万小文件（NTFS 备份/杀毒/robocopy 全慢，45GB 迁移包复制日志可证）→ 按码/按月 compaction，tushare 逐码长表可减一个数量级。

### 7. Redis / RAGFlow 栈 / 零界栈 —— 全部不动
- 第三方应用自带，业务零耦合。唯一要求：**端口纪律**——第三方占了 5432/6379 等默认惯用端口已踩坑一次；建议固化 `config/ports.md` 台账。

## 复议记录（2026-10-17）：用户提案「MongoDB 作为图库更合适」

**提案**：质疑 Neo4j 5 作为 zerobound-kg 图谱存储，提议 MongoDB。
**裁决**：**维持 Neo4j（结论 A）**。架构师高见远实地抽查代码后出具，主理人汇编。

### 证据要点

1. **查询负载实测**：全库 125+ Cypher 调用点（kg_portal 45 / dashboard 29 / kg_client 20 / kg_intel_link 17 / kg_trace 14），模式全部为「锚点 + 1-2 跳 + 边属性过滤 + 聚合」。无 `[*1..N]` 变长路径、无 shortestPath、无 gds./apoc.——且 kg_source_whitelist_tool.py:123 白名单正则**主动拦截**变长模式。
2. **MongoDB 官方立场**：$graphLookup 自述「无法提供独立图数据库的完整图算法能力」，频繁图查询时官方建议「配合图数据库使用」。
3. **模型错配核心**：438 万条边携带丰富属性（TRADED_ON.net_buy/validStart、DRIVE.group/lag_days/p）。文档模型下边表需 16+ 关系类型 ≈ 30+ 复合索引、每跳一个 $lookup；内嵌数组则时间窗聚合性能塌陷。$graphLookup 设计目标是树/层级，与多类型属性图不匹配。
4. **安全面重建**：仪表盘 /api/cypher 只读白名单 + 驱动层 READ_ACCESS 双保险在 Mongo 侧无等价物；MCP kg_query 是运行时 LLM 生成 Cypher 通道，改生成 aggregation pipeline 出错率显著升高。
5. **迁移成本**：75 文件 / 约 180-220 处 Cypher 重写 + KgDailySync 20 步 MERGE 流水线重写 + 约 20 个测试基线重做 = **3-5 人周 + 回归风险**；收益仅「少养一个容器」。投入产出严重为负。

### 公平条款（MongoDB 何时值得认真考虑——作为文档库，非图库）

- **情报正文在线化**立项时：IntelItem 现只存 title+pointer，若新闻/评论原文带嵌套结构入在线库，文档模型 + TTL + 全文索引优于属性图。届时 **MongoDB(正文) + Neo4j(关系与指针) 并存**（混合方案 C），互不迁移。
- 团队已有 Mongo 运维经验且图谱查询退化为纯点查时（当前全库无 pymongo，条件不成立）。

### 重开评审触发条件（任一成立）

① 图查询出现真实变长路径需求；② 图谱规模增长 50 倍以上；③ 团队裁撤 Neo4j 运维能力。
