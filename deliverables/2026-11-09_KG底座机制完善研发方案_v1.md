# KG 底座机制完善研发方案 v1

> 2026-11-09 · 依据《KG 底座机制完善方法论 v1》提炼。原则：每个研发项必须回答四个问题——改变机制的哪一层、交付什么实物、验收标准是什么、谁验收。与 KG 定位铁律对齐：**只读出图、不拉数据、全程可溯源**。

---

## 一、研发目标（一句话）

把 KG 机制从 **L1.5 推到 L2**：监控有契约、因子可验证、推理能起步、治理有门禁、自愈环自动化。两周内（11-09 ~ 11-22）全部交付。

## 三、逐项技术方案

### R1 · 通报五问模板化 + 认领时限对账（L2 补课）

**现状**：通报是手写 md，五问答全靠自觉，无时限对账。
**方案**：
- `kg_pool_daily.py` 通报段重构为固定模板渲染：断供条目强制五字段（what / where / why / owner / deadline），缺任一字段脚本拒绝出通报（编译期挡住）
- 新增 `chain_alerts/supply_commitments.json`：每条断供写 owner + deadline；次日通报自动比对昨日承诺，逾期未恢复条目升级标记「🔴 逾期 N 天」并在通报置顶
- 认领人词表固化：采集A组 / xtcloud / 缠论组 / 调度管理 / KG 自修

**验收**：模拟一条断供（构造 deadline=昨日），次日通报出现逾期置顶标记；五字段缺一通报拒出。
**谁验收**：老田看首份带承诺对账的通报。

### R2 · 因子 F2 验证框架（主攻——"变成因子"的临门一脚）

**现状**：因子表 F1（日更、带断供标注）已通，但没有任何一个图谱因子经过回测验证。
**方案**：
- 新建 `kg_factor_lab.py`（zerobound-kg）：
  1. **因子快检函数** `ic_check(factor_csv, fwd_days=5)`：因子截面值 vs 未来 N 日收益（TDX 日线接口 `ts_daily`），输出 RankIC 均值、ICIR、多空分层收益（Top20% vs Bottom20%）
  2. **因子库目录** `kg_factors/FACTOR_CATALOG.json`：每个因子一条元数据——名称、来源边（如 MENTIONS）、计算口径、F2 状态（untested / passed / failed）、验证日期与 IC 数字、data_gap 敏感度
  3. 首批验证对象（图谱独有，行情侧算不出）：`men_7d`（情报增量）、`seat_winrate`（席位胜率）、`conduction_density`（社区传导密度）、`event_density`（涨停/公告/形态事件密度）
- F2 准入门槛（先立规矩后跑数）：|RankIC| ≥ 0.03 且 ICIR ≥ 0.3 且多空分层单调 → passed；否则 failed 留档不删
- passed 因子自动登记进 FACTOR_CATALOG，供缠论/回测直接引用

**验收**：四个首批因子全部有 F2 判定（无论过没过），FACTOR_CATALOG 可查；`men_7d` 的 IC 报告落 deliverables。
**谁验收**：老田对照 IC 报告判断因子取舍。

### R3 · 进门日期校验 + 隔离区

**现状**：news.db 已发现畸形 ts（`2026-10-16`）、图内 published 有 `202610-01`——畸形时间带病入库。
**方案**：
- `kg_intel_link.py` 入库路径加 `valid_date(s)` 门：`datetime.strptime` 双格式（`%Y%m%d`/`%Y-%m-%d`）+ 年份范围钳制（2020-2030）；不合法的进隔离
- 隔离区：`chain_alerts/quarantine/`，每条畸形记录存原始 jsonl + 隔离原因，通报 R1 每日盘点隔离条数
- 图内历史畸形：只读盘点（published 畸形条数与样例），**不改历史**——修正走单独写门批次，留 LineageEvent
- 顺手：`ts='2026-10-16'` 两条 news.db 源记录按数字串味判例（10↔68、16↔91）尝试反推真实日期，推不出就隔离

**验收**：构造畸形日期样本走入库门 → 落隔离区不出图；通报出现隔离盘点段。
**谁验收**：老田 + 回归用例（纳入 test_review_fix 同款断言）。

### R4 · 判例环代码化（自愈环自己转起来）

**现状**：判例靠人记（工作日志+MEMORY.md），失传脚本靠人想起。
**方案**：
- `kg_selfcheck.py` 每周一 09:00 automation：
  1. **失传脚本扫描**：遍历 `.worktrees/*/` 中 *.py，比对主仓同名文件，输出「worktree 有主仓无」清单——slice_ingest / kg_intel_xq_classified 即首批应抓到的
  2. **颗粒质量抽检**：从 60 类关系中每周随机抽 3 类各 10 条边，人工核对清单自动落盘（边端点、属性、出处），供周内人工批注真伪
  3. **判例复发检查**：扫描本周告警/日志关键词，命中已立判例关键词（如 PermissionError tmp、heredoc 串味）即提示「判例复发，检查是否走了既定规矩」
**验收**：首跑抓到 ≥2 个失传脚本；抽检清单落盘。
**谁验收**：老田周会过目。

### R5 · 传导链自动发现（推理起步）

**现状**：/flow 是给定股票查传导（被动查）；Leiden 是静态社区（不连行情后果）。
**方案**（最小可行，不吹全知推理）：
- `kg_conduction_miner.py`：
  1. 定义「情报组合 → 行情后果」事件对：T0 日某 Security 出现情报脉冲（men_7d 突增 ≥3 倍基线 / 公告事件 / 新形态），观察 T0+1 ~ T0+5 的 MarketEvent（涨幅、量、涨停）
  2. 全池历史回扫（近 6 个月），产出统计表：每种情报组合的前向收益分布、命中率、样本数
  3. 结论只做**统计呈现**（"过去 6 个月，此类组合后 5 日平均 +X%，胜率 Y%，样本 N"），不做预测——推理的边界先划清：KG 出统计事实，决策归策略
**验收**：首份传导统计报告落 deliverables（含样本数与置信区间）；池内一只股票全链案例图（/flow 延伸）。
**谁验收**：老田 + 缠论组看统计是否有用。

### R6 · act_name 两档修复（挂账转正式）

**方案**（已有两档裁定待批，此处定技术路径）：
- 档一（源侧）：tushare `namechange` 接口重建真实曾用简称表 → 修正本地 join 源 → 重跑词典构建
- 档二（图侧）：5,572 条污染 act_name 改名 `controller_name`（承认它的真实语义：实控人），原属性清空；走写门批次 + LineageEvent 留痕
- 顺序：**先档一后档二**（否则重建的曾用名没地方放）
**验收**：Security.act_name 污染归零、controller_name 5,572、601668.SH 的 act_name 恢复真实简称、词典命中数复测（4066→3510 基线不回归）。

### R7 · 失传脚本收编（合并窗内完成）

**方案**：从 worktree K-KG-20261020-WMRETRY 提取 `slice_ingest.py`、`kg_intel_xq_classified.py` → 编译 + 最小用例 → 进 main → today 16:30/21:40 合并窗随 main ahead 7 一并推送。
**验收**：两脚本在主仓可编译可运行；公告管线扩量（老田已批）随即解锁。

## 六、方案边界（不变项）

- KG 不拉数据、不做预测、不碰采集——本方案所有产出均为只读出图 + 因子/统计文件交付
- 每个研发项交付即带回归用例（判例制度纪律：没有用例的修复等于没修）
- 写图操作一律走写门 + LineageEvent，历史修正不静默
