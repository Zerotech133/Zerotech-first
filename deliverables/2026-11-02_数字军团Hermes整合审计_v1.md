## 二、判定

- **“底层是否用到 Hermes”**：是，且很深（orchestrator/auth/health/MCP/门户反代/扩展），**不是没有用**；
- **“是否统一用 Hermes”**：**否**——5/6 组合未声明、64/69 席位无 profile、UI 三轨、MCP 未纳入框架登记；
- **“没有用的要用”**：应改为“**没有契约化的要契约化、没有 profile 的要适配**”，而不是把已有 agent_platform 引擎整体替换掉（避免第二套运行时）。

## 三、目标架构（统一框架 + 统一 UI）

```
8734 统一门户（唯一入口/认证/导航）
  └─ /hermes/  指挥部/超级助手（Hermes 控制面：A0 编排、MCP、审批/会话）
  └─ /legion   军团作战大屏（嵌入或同壳）
  └─ 各军团页面（manifest 声明）
共享：K4 interface/hermes-control、K5 数据/MCP 登记、K6 页面 manifest、Q2 健康
```

原则：
1. **Hermes = 交互/控制面，不是替代 K1–K8 内核**；执行仍可由 agent_platform engine/Ollama/OpenClaw 承担；
2. 每个军团必须声明 `interface/hermes-control`（或显式豁免 ADR）；
3. 每个在编席位二选一：**Hermes profile**（命令/决策/审计席）或 **adapter**（执行席，经 Hermes API/MCP）；
4. 统一 UI：一个 8734 壳，`/hermes/` 为主指挥面，`/legion` 进 nav，禁止第二登录/第二入口；
5. MCP 13 个 server 纳入登记/版本/健康，不散落 `~/.hermes/config.yaml`。

## 五、需 A0/ARCH1 决策

1. **Hermes 定位**：全部席位必须 Hermes profile，还是“Hermes 控制面 + 执行席 adapter”混合？建议**混合**（避免把引擎整体换掉）。
2. **统一 UI 方向**：门户 8734 壳内嵌 Hermes（保留同源/单登录），还是 Hermes 为主 UI？建议**门户壳 + Hermes 指挥面**。
3. **profile 扩容范围**：命令/决策/审计席先做，还是 69 席全做？建议先 12 个关键席，其余 adapter。
4. **MCP 登记 L2**：13 个 server 是否允许统一登记/重启 Hermes 生效？需 A0 五要素。
5. **`zhangsong` orphan profile**：归档或补席位。

## 七、结论

**Hermes 不是“没用”，而是“用得很深但没统一”**：
- 深：272 个 agent_platform 文件、13 MCP servers、8787/8796 在线、门户反代/扩展/编排全有；
- 不统一：1/6 组合契约、5/69 席位 profile、UI 三轨、MCP 未登记、无 Q2 门禁。

按 H1–H4 把 Hermes 做成 **K4 的 `interface/hermes-control` + 统一 UI 指挥面**，即可实现“整个数字军团底层统一用 Hermes”，同时不破坏单宿主/单入口/单认证。
