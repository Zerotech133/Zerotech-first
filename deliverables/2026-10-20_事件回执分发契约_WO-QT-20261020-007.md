## 1. 四类回执定义

同一 `signal_id` 下，投研与交易室各自产生两条回执，共四类：

| receipt_kind | 中文 | 类别 | 载荷（payload） | 典型角色 actor |
|---|---|---|---|---|
| `research_ack` | 投研收悉 | ack 类 | **必须为空**（投递≠内容） | research_team |
| `trader_ack` | 操盘收悉 | ack 类 | **必须为空**（投递≠内容） | trader_room |
| `research_conclusion` | 投研结论 | 实质类 | **必须非空 dict**（结论详情） | research_team |
| `trader_action` | 操盘动作 | 实质类 | **必须非空 dict**（动作详情） | trader_room |

回执条目字段（固定，防夹带）：

```
{ts, signal_id, receipt_kind, actor, payload, plan_version, combo_id,
 entry_sha256, receipt_schema_version}
```

- `signal_id`：幂等键主体，契约与 -005 `signal_consumer.normalize_signal` 完全对齐（非空 + 只许字母数字与 `_.:-`，禁路径注入）。
- `plan_version` / `combo_id`：可选引用。投研结论可引用其依据的计划版本（衔接 006 计划版本账）；操盘动作可引用其落单的组合（衔接 -005 combo 账本）。

## 2. 并行响应语义（核心）

- **无顺序依赖**：四类回执可任意时序入账。操盘收悉先于投研收悉、操盘动作先于投研结论，均合法（单测 `test_out_of_order_receipts_full_timeline` 实证）。
- **真并行**：`record_receipt()` 线程安全（模块级锁保护 check-then-append 临界区），四线程同时各入一类回执互不阻塞（`test_parallel_threaded_receipts` 实证）。
- **无串行瓶颈**：司马懿侧消费 `completeness()` 只读账本、不阻塞、不催办、不推断——治理与出口不在盘中响应路径上。
- **多信号隔离**：不同 signal_id 的回执互不干扰。

### API

```python
record_receipt(log_path, signal_id, receipt_kind, actor, payload=None,
               plan_version=None, combo_id=None, ts=None) -> dict   # 入账，返回条目
timeline(log_path, signal_id) -> list[dict]                          # 四类回执时间线（审计用，按 ts 升序）
completeness(log_path, signal_id) -> dict                            # {received, missing, received_count, total}（汇报/告警用，不阻塞）
verify_integrity(log_path) -> int                                    # 全账防改写校验，返回条目数
```

### 并行语义与边界

- 进程内（多线程）并发入账由模块锁保证；**跨进程并发**为已知边界：幂等检查与追加之间存在 TOCTOU 窗口（极端情况下重复条目可能双双通过检查）。当前部署形态为单进程调用方（投研/操盘回执经同一服务进程入账），不构成实际问题；若未来多进程并行入账，需在后续工单升级为文件锁或 sqlite 账（接口不变）。

## 3. 存储选型：append-only jsonl（与 signal_rejections.jsonl 同风格）

理由：

1. **与 -005 拒单账同风格**：审计与人工核对可用行工具直接看，跨团队（006 会议账、司马懿出口）只读消费零门槛；
2. **天然 append-only**：账本层零 UPDATE/DELETE 语义；
3. **不引入 sqlite 依赖**：本模块 stdlib-only，零既有模块 import（-005 依赖链上有 WO-006 在途改动模块，保持解耦）。

防改写补偿：jsonl 无 sqlite 触发器保护，故每条回执带**自校验 sha256**（`entry_sha256`），`verify_integrity()` / `timeline()` / `record_receipt()` 读账时逐行校验，任一行被改写即抛 `ReceiptLedgerTampered`（改写→拒绝，closed on failure；`test_append_only_tamper_rejected` 实证）。

## 4. 幂等口径：同 (signal_id, receipt_kind, actor) 重复入账 → **拒绝**（非静默去重）

理由：重复入账多半是生产方 bug 或事件重放，静默去重会掩盖事故；原回执已在账，去重不新增信息；append-only 审计口径下显式拒绝更符合 closed on failure。拒绝不写任何行（`test_idempotent_replay_rejected` 实证）。

注意：同 receipt_kind 不同 actor（如投研 A 席与投研 B 席各自收悉）**不算重复**，各自独立入账——多团队多席位口径。

## 5. 失败语义（closed on failure）

统一显式抛 `ReceiptError` 族异常（携带 reason_code），**校验失败零写入**：

| reason_code | 触发 |
|---|---|
| `signal_id_invalid` | 非空/字符集校验失败（对齐 -005） |
| `receipt_kind_invalid` | 非四类回执 |
| `actor_invalid` | 角色 id 缺失/非法 |
| `ack_payload_forbidden` | ack 类回执携带载荷（投递≠内容硬约束） |
| `payload_required` | 实质类回执缺非空 dict 载荷 |
| `ts_invalid` | 时间戳不可解析 |
| `plan_version_invalid` / `combo_id_invalid` | 可选引用非法 |
| `ledger_corrupt` | 账本行非法 JSON / 缺自校验字段 |
| `ledger_tampered` | 行内容与自校验 sha256 不符（改写检测） |
| `duplicate_receipt`（DuplicateReceiptError） | 幂等冲突 |

## 6. 投递≠内容（防「投递成功冒充开会/改计划」）

- ack 类回执**不携带载荷**，收到载荷即 `ack_payload_forbidden` 拒绝——ack 只证明「收到」，不携带任何可被误读为「开会产出/改计划」的内容；
- 实质类回执**必须携带非空载荷**——无内容的结论/动作不收（防「空口办结」）；
- RESEARCH_REVIEW 对照实证（`test_research_review_delivery_is_not_a_meeting`）：投递 ack 入账成功后，`completeness` 仍明示缺 `research_conclusion`，且 API 层无法给 ack 塞结论载荷——「投研开过会」的唯一证据是 `research_conclusion` 入账。

## 7. 衔接点

- **上游（-005 信号点契约）**：signal_id 校验规则逐字符对齐 `signal_consumer.normalize_signal`（源级断言 `test_signal_id_contract_aligned_with_wo005` 保证契约不漂移）；回执账不复制信号内容，只引用 signal_id。
- **006 会议账（消费方）**：006 会议账可消费 `research_conclusion` 条目的载荷（结论详情 + 可选 `plan_version` 引用其计划版本账）——会议记录入账时可回指本账条目；本模块不 import 006 模块（其有在途改动），消费方向单向。
- **司马懿对外出口**：`completeness()` 为其汇报/超时告警的只读数据源（received/missing 明细），不阻塞、不催办。
