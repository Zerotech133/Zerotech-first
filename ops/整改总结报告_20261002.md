## 三、核心复盘：card-handler 三层根因修复

现象：watchdog 连续三轮拉起 card-handler，日志止于「lark-cli 提前退出（code=None），启动失败」，9104 端口无监听。逐层下钻：

| 层 | 根因 | 修复 |
|---|---|---|
| ① 认证层 | lark-cli 1.0.5 凭证由宿主进程外部注入，watchdog 独立进程无凭证；首轮只注入 TAT+UAT 两变量仍失败——**bot 身份握手要求 APP_ID/APP_SECRET/TENANT_ACCESS_TOKEN 三者齐全 + USER_ACCESS_TOKEN 置空，缺一不可** | [jev_common.py](../jev-eval/jev_common.py) `lark_env()` 补全四件套（`_load_bot_creds()` 惰性缓存刷新 TAT） |
| ② 依赖层 | 进程存活、日志推进到「事件监听就绪」，但 `start_metrics` 报「prometheus_client 未安装」——可选依赖静默降级 no-op，而 health_check 探针依赖 9104 端口 | 补装 prometheus-client |
| ③ 环境层 | 装包后仍报未装——**双 Python 陷阱**：watchdog 裸 `python` 走 PATH 解析到用户安装的 Python312，包却装进了产线惯例的 Python311（查活进程 ExecutablePath 实锤） | 3.11/3.12 两边都装，一次生效 |

**终验**：watchdog 拉起 → RUNNING + 9104 监听 YES + 「指标端点已启动 port=9104」→ `ops/health_check.py` **全绿 rc=0**。

## 四、新沉淀的工程判例（已归档 INTEL_RD_PLAN.md K35-p/q/r）

1. **四件套缺一不可**：lark-cli 1.0.5 子进程 bot 身份 = APP_ID + APP_SECRET + TENANT_ACCESS_TOKEN + USER_ACCESS_TOKEN=""（置空强制 bot）。对照已验证实现：p_g_robot._bot_env() / jev_common.lark_env()。
2. **双解释器判例**：本机裸 `python`（PATH→用户 3.12）与计划任务显式路径（产线 3.11）可能指向不同解释器；装依赖必须对准「实际运行的那个」——查活进程 ExecutablePath 定位，而非想当然。
3. **可选依赖兜底 = 隐性配置漂移**：`METRICS=False` 降级让「装没装」成为隐性状态；健康探针所依赖的能力必须在部署清单里显式列出。
4. **凭证外部注入模型**：lark-cli 1.0.5 认证为进程环境级（宿主内有、独立进程无）；宿主外一律走 OpenAPI 静态凭证直连（读 `~/.lark-cli/config.json`）。
5. **代理时序自愈**：登录触发的常驻任务，urlopen 必须考虑代理客户端（Clash）晚于任务启动——启动重试（60s×10）是通用自愈范式。
6. **修复未同步判例**：同类修复（如三通道发送）必须排查所有同根调用方，防止单点修好、旁路裸奔（send_feishu vs backup_alert 判例）。
