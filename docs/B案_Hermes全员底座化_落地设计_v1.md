# B 案落地设计 · 全员 Agent 底座化（Hermes profile 体系）v1

> 裁定：老田 2026-11-12 08:25 选定 B 案（全员底座化，每席常驻子体：独立记忆/收件箱/定时自省）
> 侦察结论：Hermes-next **原生支持**——`api/profiles.py` 提供隔离 profile 体系（独立 HERMES_HOME、
> 独立 state.db/skills、`install_cron_scheduler_profile_isolation` 按 profile 隔离定时任务）
> 设计原则：**一个共享底座 × 71 隔离身份位 × 按角色画像分梯度唤醒**——拿到 B 案的全部收益，
> 不付 71 常驻进程的代价。**本稿待批，不动 8787 生产服务。**

## 一、为什么不是「71 个进程」

Hermes profile = 同一进程内的**身份隔离**（HOME 目录级），不是进程级复制：
- 每 profile 独立：记忆（state.db）、技能、收件箱、cron、凭据域；
- 共享：模型路由（Ollama 11434 ✅活）、WebUI 入口（8787 ✅活）、进程内存。
- 因此「全员底座化」的工程正解 = **71 个 profile 身份位 + 按席唤醒计划**，
  内存成本 ≈ 常驻 1 进程（增量只在磁盘 HOME 与唤醒时的推理）。

## 三、试点选型：马谡（ANALYST1）——理由充分

1. **交付刚好压着**：首批小样（632 code 挑 10-20 个）11-13 就要 AI 执笔——正好用
   马谡 profile 跑，而不是临时会话（临时会话无记忆沉淀，与「独立记忆」目标相悖）；
2. **周批节奏天然适配 cron profile**：每周一次唤醒→读底表→执笔草稿→写回收件箱→休眠；
3. **记忆价值最高**：核验判断的连贯性（上周怎么裁的、track record 怎么演化的）必须跨会话留存——
   这是临时会话给不了的；
4. **风险最小**：马谡输出必经你的终审闸门，profile 化不会让错误直接进生产。

试点内容：建 `analyst1` profile（HERMES_HOME 隔离）→ 注入 07 册章程+核验流转口径
作为系统提示 → 跑首批小样 10 code → 你试批 → 复盘 profile 形态 → 决定 R1 剩余席位推广。

## 四、资源预算（保守估算）

- 磁盘：每 profile HOME ~50-200MB（state+skills），71 席全建 ≈ 5-15GB——数据盘 2TB 无压力；
- 内存：共享进程，增量仅在唤醒时的会话上下文——R1 四席日频唤醒 ≈ 每日几次分钟级推理，
  本机现有 Ollama（qwen3.5:9b 5.6GB 已载）即可承接，不新增常驻显存/内存；
- 算力：与现有按需召唤完全同量级（只是从「散会即焚」变「记忆留存」）。

## 五、与既有架构的咬合

- **org.json 单一事实源不变**：profile 名 = agent_id（如 `analyst1`），binding（glm-5.3）
  即 profile 的模型路由；llm_binding=none 的席不建 profile——**花名册继续是花名册**；
- **判例 #26 代理纪律**：所有 profile 唤醒脚本走 `_clean_env()` 直连（已立判例）；
- **军情司先行**：R1 试点在军情司内（马谡），成功后按司推广——不跨司抢跑；
- **8091/JEV 生产链路零改动**：profile 化是 agent 侧基建，不碰渲染/判定/采集代码。
