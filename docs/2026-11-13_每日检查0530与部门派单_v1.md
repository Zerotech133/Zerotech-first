# 05:30 每日数据检查与部门派单（v1，2026-11-13）

## 0. 需求与理解

老田指令：「每日检查要放到凌晨五点半，出现问题给对应的部门发信要求处理，接到信息的部门应该立即处理」。

**一处措辞说明**：原始输入里出现「街道信息部门」，全库组织真源
`agent_platform/registry/org.json` 的 17 个部门中没有该名称，量化数据链路里也无对应实体。
按上下文理解为「**接到信息的部门应立即处理**」，实现方式是把「立即启动处理 + 时限 + 回执」
写进每一封部门信，并把派单对象做成可改配置。若确有一个叫「街道」的部门，
只需改 `tools/preopen/daily_check_routes.json`，无需改代码。

## 1. 时点设计：新增 05:30 检查，不挪动 08:10 出名单

| 任务 | 时点 | 职责 | 本次改动 |
|---|---|---|---|
| `preopen_check_0530` | 周一至周五 **05:30** | 数据校对 + 按责任部门发信要求处理 | **新增** |
| `preopen_daily` | 08:10 | 校对 → 精选 → 券商级 H5 | 未改动（见 §6） |
| `close_review_daily` | 15:40 | 收盘复盘 + 自动挂事件账 | 未改动 |

为什么不是把 08:10 整体挪早：05:30 到 08:10 之间的 **2 小时 40 分钟是留给责任部门的处理窗口**。
检查与出名单同时发生，发现问题就没有时间修；分开之后，当天的问题当天就能被处理掉。

05:30 的时点依据：`TushareTailSync` 02:10、`TdxTailSync` 04:30 之后留 1 小时余量；
盘前截止 08:10 之前留足处理时间。

## 2. 责任部门映射（`tools/preopen/daily_check_routes.json`）

| 问题类别 | 数据源 / 特征 | 责任部门 | 负责人席码 | 时限 |
|---|---|---|---|---|
| 行情主源与采集链路 | `ts_daily` / `ts_adj_factor` / `ts_index_daily` / `ts_top_inst` | 数据智能部 `data` | `DATA1` | 按严重度 |
| 增量分片链路 | `limit_list_d` / `margin_detail`、盘后逐表巡检 | 数据治理部 `proj_data` | `DATA1` | 告警级 |
| 坏价与统计口径 | 收盘价异常、价格自相矛盾、前收盘错位、交叉验证差异 | 质量工程部 `quality` | `QA1` | 告警级 |
| 候选池时效 | 共识池推送包 asof 落后 | 量化交易部 `invest` | `D1` | 告警级 |
| 检查链路自身 | 未登记的新问题、脚本与投递故障 | 运行体部 `ops_runtime` | `A0A` | 兜底 |

- **阻断级**（`problems`）：立即处理，当日 08:10 盘前截止前必须回执，否则当日名单可能被阻断。
- **告警级**（`warns`）：接到即启动处理，当日盘前给出处理结论，必须写进当日报告。
- SLA 用**固定盘前截止时点**，不依赖「08:10 出名单任务是否启用」（§6 的判例）。

## 3. 发信通道与「要求处理」闭环

遵循老田 2026-11-10 的路由裁定：**AI↔AI 消息内部闭环，不进飞书**。

1. 每部门一封信，经 `agent_platform/gateway/internal_notify.emit()` →
   `inbox_gateway.submit(kind="task_request")`，落 `bridge_inbox/inbox/<id>.json`；
   信封沿用既有 `hq/internal_notify/v1`（`target` = 部门负责人席码）。
2. 信内写明：问题原文、结构化证据（源状态 / 最新日 / 落后交易日 / 分片诊断）、
   **立即启动处理**、时限、复跑验证命令、回执方式
   `inbox_gateway.consume(msg_id, answered_by=席码, answer_ref=修复证据路径)`。
3. **入箱 ≠ 已处理**：未回执视同未处理，当日盘前链路按当前数据继续，问题照实写进报告。
4. 只有 **阻断级判定** 才经 `notify_hub` 发一条红告警到人（健康检查家族既有自动外发、
   4 小时去重）；告警级只进部门工单，避免告警疲劳。
5. 幂等键 `preopen-check-<数据日>-<部门>-<内容指纹>`：同日同问题只投一次，
   内容变了才是新信（要求重新处理）。

### 顺手修掉的一个真实缺陷

`internal_notify.emit()` 的 payload 带秒级 `created_at`。一旦调用方显式传 `dedupe_key`
做「同问题不重复派单」，第二次投递就成了「同幂等键、不同 payload」，被
`inbox_gateway` 判成 `idempotency_conflict` —— **本该 replayed 的催办信反而投不出去**。
修法：给 `emit()` 增加可选 `created_at`，需要幂等复用的调用方按数据日固定该字段；
缺省行为不变。实测 `SENT → REPLAYED`，信箱文件数不变。

## 4. 判定纪律（都是既有判例，别改回去）

1. **目标日由交易日历给定**：取「今天之前的最后一个开市日」，不取被测表自己的 `max(date)`。
2. **「数据未就绪」与「无事可做」分成两种输出**：拿不到交易日历 → `BLOCKED`；
   连个股日线都没有 → `DATA_NOT_READY`；只有真无待办才输出 `CLEAN`。
3. **上游给空 / 本地漏跑 / 架构停更是三件事**，证据里分开写，不合并成「停更」。
4. **T+1 源落后 1 日属正常**（`pending`），不生成问题条目；`margin_detail` 不再被误判。
5. **盘后增量链路作为独立观测**：`data_health` 的 `zero_collect` 派给数据治理部，
   但信里明确写「含 T+1 正常项，须按三件齐（产物最新日 / 上游起始日探测 / 写入链路）
   复核，不得直接判成上游断供」。
6. **告警与阻断分级派单**，红告警只给阻断级。
7. **退出码只回答「跑完了吗」**：正常完成一律 0（业务判定写台账与日志独立行）；
   无法确定目标日 / 投递失败 / 脚本崩溃 = 3。

## 5. 注册五要素与实测证据

- 命令全文：`powershell -NoProfile -ExecutionPolicy Bypass -File tools\scheduled\install_daily_check_task.ps1 -Apply`
- 影响面：新增 `preopen_check_0530` 一个任务；只读行情分片与交易日历；
  写 `var/preopen/daily_check/` 台账、`C:\Temp\daily_check_task.log`、
  `C:\Temp\daily_check_launch.jsonl`；有问题的项目投内部工单，阻断级另发红告警。
- 不可逆点：工单入箱即进既有消费队列（可 `consume` 关闭）；阻断级飞书外发后不可撤回；
  计划任务本身可撤销，无残留。
- 替代方案：不注册，手工 `--dry` 预演；或把 08:10 整体挪早（不推荐，见 §1）；或改 `-At`。
- 回滚预案：`Unregister-ScheduledTask -TaskName preopen_check_0530 -Confirm:$false`。

注册后**独立读回**：`State=Ready`、`Trigger=2026-11-13T05:30:00+08:00`、
`DaysOfWeek=62`（周一至周五）、`NextRun=2026/11/16 05:30`、
`Principal=t/Interactive/Limited`、`StartWhenAvailable=True`。
今天 05:30 已过，首次自动运行为下周一 11-16 05:30（按交易日周一至周五）。

其他实测：
- PS 两个脚本 `ParseErrors=0`；`-WhatIf` 回放路径解析与预演一致；新脚本统一为
  **UTF-8 BOM + CRLF**（PS 5.1 会把无 BOM 的 UTF-8 中文按 GBK 读成乱码，首次校验 5 个语法错）。
- PS 入口 `-Dry` 真跑一次：启动/结束落痕成对、`dur_sec=17`、`业务rc=0`。
- 行为测试 **12/12**；变异检验 **6/6 KILLED**（含「目标日改回取 max」「红告警放宽到告警级」
  「时间戳改回秒级」「退出码改回业务码」），恢复后复跑仍 12/12。
- 两道门禁：公开面四类规则 **0 命中**；pre-commit 凭据扫描 **0/7 文件**。
