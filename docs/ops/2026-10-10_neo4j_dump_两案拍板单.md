# Neo4j dump 两案拍板单（K-STOCK-075 预研，2026-10-10 只读）

## 实测数据（neo4j-kg @ 16:35）
- 版本：neo4j **5.26.31 community**（community 无在线 dump → 挂账根源）
- 数据量：databases/neo4j **1.3G** + transactions 770M ≈ **2.1G**；磁盘余 923G 充裕
- 挂载：named volume `neo4j-kg-data`（**非 bind mount**——卷不能直接文件级拷贝）
- 写入画像：tx 日志显示写入集中在**凌晨批量**（03:47 仍有段写入=backup_daily docker 操作窗口），白天基本静默

## 两案量化对比

| 维度 | 案 A：停库窗口 dump | 案 B：迁 bind mount |
|---|---|---|
| 一次性成本 | dump 本体 1-3 分钟（2.1G SSD），窗口=停+dump+启 ≈ **5-10 分钟** | 停库+搬 2.1G 数据+改 compose+启 ≈ 15-30 分钟，一次性 |
| 持续收益 | 每次备份都要 5-10 分钟窗口 | 之后文件级快照/robocopy 可做（仍需 checkpoint 保一致），或为迁 enterprise 铺路 |
| community 限制 | 不解决（community 永远无在线 dump） | 也不解决——bind mount 本身≠在线 dump，只是让文件够得着 |
| 风险 | 窗口内图查询/写入链中断 | 迁移操作本身风险更高（卷→bind 数据搬移+compose 改动） |

## 建议（供拍板）

**推荐案 A 变体——凌晨写入空窗停库 dump，每周一次**：
- 窗口选 **05:30 前后**（offsite 04:30 之后、06:00 XmapSync 之前、03:00 backup 链之后），
  脚本 = docker stop → neo4j-admin database dump neo4j → docker start，带前后 RC 校验+飞书告警
- 频率：周一次（图数据日均增 ~250M tx，周备 RPO≈7 天可接受；不够再升日备）
- 案 B 仅当未来需要高频文件级备份或迁 enterprise 时再做，现在不值当冒迁移风险
