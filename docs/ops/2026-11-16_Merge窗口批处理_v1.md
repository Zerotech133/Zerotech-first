## 一、为什么需要

`devtask.py merge` 只允许在 merge train 窗口内执行（**16:30–17:00 / 21:40–22:10**），
窗口外合并会被门禁拒绝。而"到点合哪几条"过去靠人守时，容易错过窗口。

本脚本把这件事实体化：**窗口自检 + 逐条合并 + 结果落盘**，交给计划任务在 16:30 触发。

## 三、逐条处理：先 rebase，再 merge（计划与执行同源）

**单一来源**：`plan_for(tid, no_rebase)` 产出步骤列表，`execute_step(step, tid, timeout)` 执行其中一步。
dry-run 打印的就是这份计划，真实执行也遍历这份计划——**不存在"演练一套、执行另一套"**。

```python
plan_for("A") == [
  {"kind": "rebase", "cmd": "git -C .worktrees/A rebase master"},
  {"kind": "merge",  "cmd": "python tools/devtask.py merge A"},
]
```

执行时对每个 `step` 调 `execute_step`，**某步失败即 break**（不继续该条后续步骤），
结果里 `steps` 只含已跑的、`plan` 是完整计划，`len(steps) != len(plan)` 即视为该条失败。

| 步骤 | 失败处理 |
|---|---|
| `rebase` | 立即 `rebase --abort`，跳过该条 merge（不动 master、不影响下一条） |
| `merge` | 记 rc/耗时/尾行；不重试；不影响下一条 |

## 四、结果落盘

```

  plan_<HHMMSS>.json     # dry-run 的计划（steps[].kind/cmd + kinds）
  merge_<HHMMSS>.json    # 真实执行结果
logs/merge_window.log
```

执行结果（schema `merge_window_run/v2`）：

```json
{"window": "...", "forced": false, "ok": false,
 "results": [
   {"tid": "A", "plan": ["rebase", "merge"],
    "steps": [
      {"kind": "rebase", "ok": true,  "tail": "rebased"},
      {"kind": "merge",  "ok": false, "rc": 1, "seconds": 8.3, "tail": "fast gate failed: ..."}

    "ok": false}
 ]}
```

每条都能追到：计划了哪几步、实际跑到第几步、每步的 ok / rc / 秒数 / 尾行。

## 七、边界与已知风险

- **窗口容量**：单条 merge 含 fast 门通常 7–10 分钟，两条约 15–20 分钟，落在 30 分钟窗口内；若第一条异常慢，第二条会撞窗口末尾——`devtask.py merge` 自己会拒，结果记为失败，可在 21:40 窗口补跑。
- **不在本脚本内重试**：失败即记，不做自动重试（避免连锁与重复合并）。
- **不动他人分支**：本脚本只调 merge；rebase 由调用方在窗口前完成。
- **`--force` 不用于常规**：仅回滚/紧急场景，且必须 24h 复盘。
