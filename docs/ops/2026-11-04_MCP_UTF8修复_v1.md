## 1. 结论

- 根因（task-44）：6 个 MCP server 用 `json.dumps(ensure_ascii=False)` 写**文本** stdout，未显式 UTF-8；
  Hermes spawn env 白名单不含 `PYTHONIOENCODING/PYTHONUTF8`，Windows 管道 stdout 默认 **cp936/GBK** →
  中文按 GBK 字节输出；Hermes mcp 客户端按 **UTF-8 + errors=replace** 解码 → **U+FFFD 乱码**（98 工具中 34 条）。
- 本修复：6 个 server 的 `main()` 入口统一加 `sys.stdout/sys.stderr.reconfigure(encoding="utf-8", errors="replace")`
  守卫（同仓库既有判例：K-STOCK-428 / `tools/jev_mcp.py` ENCPROT / `factor_tools_mcp.py`）；
  不改协议/逻辑，只在写 JSON 前把文本流固定为 UTF-8。
- 验证：**新增 15 个测试**（静态锚点 + Hermes 同构 env 子进程行为 + 幂等/无害 + selftest 冒烟），
  **修复前 13 failed / 修复后 15 passed**；生产解释器口径 6/6 stdout=UTF8_OK；ruff/语法门/导入边界门 PASS；
  现有 MCP 相关 27 tests 无回归。**无服务变更**。

守卫代码（6 文件同一 hunk 语义，锚点为各自 `def main(...):` 后第一条语句前）：

```python
def main(...):
    # WO-MCP-UTF8-GUARD-20261104（判例 K-STOCK-428；根因见 WO-MCP-ENCODING-AUDIT-20261104）：
    # Hermes 以管道拉起 MCP server，且 spawn env 白名单不含 PYTHONIOENCODING/PYTHONUTF8，
    # Windows 文本 stdout 默认 cp936/GBK → json.dumps(ensure_ascii=False) 的中文按 GBK 字节
    # 写出，客户端按 UTF-8 + errors="replace" 解码 → U+FFFD 乱码。故显式 UTF-8；
    # 流不可 reconfigure（如测试 CaptureIO）时无害跳过。
    try:
        sys.stdout.reconfigure(encoding="utf-8", errors="replace")
        sys.stderr.reconfigure(encoding="utf-8", errors="replace")
    except (AttributeError, ValueError):
        pass
    # ... 原逻辑不变
```

设计要点：
- `errors="replace"` 兜底：即使出现不可编码字符也不会抛 `UnicodeEncodeError` 杀死 stdio 子进程（K-STOCK-428 教训）；
- `try/except (AttributeError, ValueError)`：兼容不可 reconfigure 的流（pytest `CaptureIO`、被替换的 pipe 等）；
- 插在 stdin 循环/**selftest 分支之前**：`--selftest` 的中文 JSON 输出同受保护（已测）。
