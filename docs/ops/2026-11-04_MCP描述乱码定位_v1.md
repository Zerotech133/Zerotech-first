## 1. 根因（一句话链）

```
6 个 MCP server：json.dumps(ensure_ascii=False) → 写 sys.stdout（文本流，未 reconfigure UTF-8）
        ↓ Hermes 白名单重建 MCP 子进程 env（无 PYTHONIOENCODING / PYTHONUTF8；父进程的 PYTHONUTF8=1 不继承）
Windows 子进程 stdout=pipe、默认 locale = cp936  →  sys.stdout.encoding = gbk  →  中文按 GBK 字节写出
        ↓ Hermes mcp SDK 2.0.0 客户端按 UTF-8 解码 + errors="replace"
非法 UTF-8 字节 → U+FFFD/杂字（已损坏的 Python str）
        ↓ WebUI /api/mcp/tools 把该 str 原样 json.dumps 成合法 UTF-8 JSON
浏览器/API 看到乱码；**WebUI/渲染/JSON 编码层无责**
```

**判定三选一：`stdout 编码`（server 端）** —— 不是 `JSON 解码错误`（客户端 UTF-8 是协议要求的正确行为），
不是 `渲染`（WebUI 响应是合法 UTF-8 JSON，乱码字符在 Python str 里已经存在）。

### 1.1 关键证据：6/6 逐字相等

把 6 个乱码 server 的 **stdout 原始字节**按 `utf-8(replace)` 解码得到的描述，与 8787 `/api/mcp/tools`
返回的同一工具描述**逐字相等（6/6 True）**；干净 server 则不等（它们 stdout 本来就是 UTF-8）。
→ 排除 WebUI 二次编码/渲染问题，证明乱码来自 server stdout 字节。

### 1.2 因果链各环节实证

| 环节 | 证据 |
|---|---|
| server 无 UTF-8 守卫 | 6 文件均无 `sys.stdout.reconfigure`（矩阵见 §3.2）；写出口：`sys.stdout.write(json.dumps(..., ensure_ascii=False))`（d1/dw-*/kb-corpus）或 `print(json.dumps(..., ensure_ascii=False), flush=True)`（huangzhong L654） |
| 子进程 env 无 UTF-8 强制 | 字节探针自证：Hermes 同构 env 下 `stdout_encoding=gbk preferred=cp936 utf8_mode=0`；加 `PYTHONIOENCODING=utf-8` → `stdout=utf-8`；加 `PYTHONUTF8=1` → `stdout=utf-8 utf8_mode=1` |
| env 被白名单重建 | Hermes Agent `tools/mcp_tool_config.py` L147 `_SAFE_ENV_KEYS`（L184 `_build_safe_env`）不含 PYTHON*；mcp SDK `get_default_environment()` 同样不含 → 父 8787 的 `PYTHONUTF8=1`（`Hermes/start_hermes_bg.py` L159）不会被继承 |
| 客户端 UTF-8 解码 | 生产 venv `mcp-2.0.0`：`mcp/client/stdio.py` L106 `encoding: str = "utf-8"`、L144 `TextReceiveStream(..., encoding=server.encoding, errors=...)`；Hermes `tools/mcp_tool_transport.py` L371-374 只设 `encoding_error_handler="replace"` |
| server 原始字节 = GBK | 6 server 的 tools/list stdout 行 `valid_utf8=False`，按 GBK 解码得到正常中文；2 个干净 server `valid_utf8=True` |
| 对照实验（同 server 强制 UTF-8） | `dw-catalog` + `PYTHONIOENCODING=utf-8` 或 `PYTHONUTF8=1` → stdout 行全部 `valid_utf8=True`，描述干净 |

### 1.3 为什么 task-41 的直连 stdio 探针是干净的？

`agent_platform/legion_mcp/client.py` L166 给子进程显式 `env["PYTHONIOENCODING"]="utf-8"`
（L47-48 又以 `text=True, encoding="utf-8"` 读）——所以直连探针看不到乱码；
而 Hermes 的白名单 env 不含该变量 → 同一 server 在 Hermes 下变 GBK。这一差异正是定位的“对照实验”。

本仓已有 3 处“MCP stdio 必须强制 UTF-8”的判例，6 个新 server 未复制该守卫：

## 4. 最小修复建议（不在本单改代码；patch 草案）

### 4.1 根治（推荐；主仓可修）

对 **6 个 MCP server 的 `main()` 入口**加同一守卫（与 factor_tools/jev_mcp 判例一致，每个文件 +6 行，共 +36 行）：

```python
def main(...):
    try:  # Windows 管道默认 cp936：MCP JSON 必须 UTF-8 输出（判例 K-STOCK-428/ENCPROT）
        sys.stdout.reconfigure(encoding="utf-8", errors="replace")
        sys.stderr.reconfigure(encoding="utf-8", errors="replace")
    except (AttributeError, ValueError):
        pass
    # ... 原逻辑（argv 处理 / stdin 循环）不变
```

patch 锚点（行号为当前版本，见 evidence 矩阵 F 段）：
`agent_platform/tools/d1_research_mcp.py:87`、`dw_governance_mcp.py:152`、`dw_quality_mcp.py:326`、
`dw_catalog_mcp.py:388`、`huangzhong_mcp.py:640`、`kb_corpus_mcp.py:325`。

- 无逻辑/契约变更，只改输出编码；`errors="replace"` 兜底不会因不可编码字符杀死 stdio 子进程；
- 改动面 6 文件、每文件 6 行，风险低，且与既有 3 个判例完全同构。

### 4.2 部署生效（L2，需批准）

server 代码改动后需让 Hermes 重连 MCP：`POST /api/commands/exec {"command":"/reload-mcp"}` 或重启 8787
（均属 L2 操作，需 L2 批准并留痕），然后重跑 §5 验证：**U+FFFD 计数 34 → 0**。

### 4.3 可选临时缓解（L2 配置；不推荐长期）

`~/.hermes/config.yaml` 这 6 个 server 的 `env:` 加 `PYTHONIOENCODING: utf-8`
（Hermes `_build_safe_env` 会合并 config env，`mcp_tool_config.py` L203-204；SDK 用 `server.env` 覆盖）。
不需改代码即可止血，但属配置面规避、多一份配置债，**根治仍建议 4.1**；改配置需 L2 批准。

### 4.4 不建议改 Hermes Agent / WebUI

客户端按 UTF-8 解码是 MCP 协议要求；把 client encoding 改 cp936 会破坏其它 UTF-8 server（本机就是混合编码部署）。
`encoding_error_handler="replace"` 只是把解码失败变成乱码而非报错——上游若改进可选“解码失败告警”，
但不是本根因，不建议为此改生产 Hermes/WebUI。
