# Jev「双副本」治理方案（2026-10-08 调研）

> 调研方式：纯只读（ls / git 只读命令 / md5 / fsutil / python os.stat / netstat）。未修改、未删除任何文件，未执行任何 git 写操作。

## 结论先行

1. **「双副本」是误解：物理上只有一份代码。** `C:\aios` 是一个 **NTFS junction（目录联接）**，指向 `E:\老田的AI助手`。两条路径访问的是同一份磁盘存储、同一个 `.git`、同一批文件。
2. **不存在代码漂移，也不存在双份手工维护。** 排除运行态后 36 个文件逐字节一致（md5），这不是"同步得好"，而是"本来就是同一批文件"。历史上"C 盘出现过 E 盘没有的 auto_verify_jobs.ps1"无法在当前架构下发生，推测为观测误差或 junction 建立（约 2026-09-11）之前的旧况。
3. **真正需要治理的不是"两份代码"，而是三件事：** ① junction 这一关键事实无人知晓、无文档、无巡检（E 盘换盘符/移除 = C 盘全部脚本静默瘫痪）；② git 仓库混入大量运行态文件（alerts/sent/*.done、pending_msg.txt、n1_report_*.txt 等）；③ 工作区有未收口的变更（backup_daily.ps1 被删未提交）。
4. **推荐：维持"单权威（E 盘）+ C 盘 junction 别名"的现有架构（即方案 B），并做加固**，不要引入任何"双仓互推/脚本单向同步"机制（方案 A/C），那会把已经解决的"双份维护"问题重新制造出来。

## 二、三个候选方案对比

> 前提修正：调研发现 C 盘路径已经是 junction，所以原设想的"消除两份副本"已完成了一半——架构上只剩一份副本，剩下的是**要不要保留、如何加固**。

### 方案 A：C 盘为唯一权威，E 盘副本改为脚本单向同步生成

即：删除 junction，C 盘放真身，E 盘放 robocopy 镜像，定时单向覆盖。

| 维度 | 评估 |
|---|---|
| 优点 | 概念直观（"生产在 C 盘"）；E 盘可作为只读镜像用于查档 |
| 缺点 | **重造已解决的问题**：镜像必然滞后（分钟级窗口内两份文件不一致），任何人在 E 盘误改即被覆盖或制造新漂移；需要新增同步脚本 + 计划任务 + 失败告警，是持续维护负担；当前 git 仓库物理在 E 盘，把"真身"放 C 盘意味着仓库也要搬，动静更大 |
| 改造量 | 大：拆 junction、迁移仓库、写同步脚本、建计划任务、写告警 |
| 风险 | 高：拆 junction 时若有进程以 C 路径持有句柄会失败；同步方向一旦配反 = 数据丢失；**方向性错误**——把一份存储刻意拆成两份 |
| 结论 | ❌ 不推荐。方向与"单一事实源"原则相悖 |

### 方案 B：单一 git 仓库 + C 盘 junction 别名（= 现有架构，做加固）

即：承认并固化现状——`E:\老田的AI助手` 为唯一权威（git 实体），`C:\aios` 为兼容别名，所有 `C:\aios` 硬编码继续有效。治理动作是**文档化 + 巡检 + 仓库清洁**，不动目录结构。

| 维度 | 评估 |
|---|---|
| 优点 | 零迁移风险；单一事实源天然成立（本就一份存储）；`C:\aios` 全部硬编码（如 run_eval.ps1 的 `$here`）无需改动； junction 自带原子性——不存在"同步窗口" |
| 缺点 | junction 是单点：E 盘移除/换盘符/误删 junction → C 盘全部路径失效；路径二义性（C、E 两条路径指向同物）对不了解内情的人（包括 AI Agent）有迷惑性，本次"双副本漂移"误判即为例证 |
| 改造量 | 小：一份说明文档 + 一个 junction 巡检（可并入既有 N1 检查）+ gitignore 补丁 + 一次清理提交 |
| 风险 | 低：全部动作可逆、只读为主 |
| 结论 | ✅ **推荐** |

### 方案 C：双 git 独立仓库 + remote 互推

即：拆掉 junction，C、E 各建真仓库，互设 local remote，定时 push/pull 对齐。

| 维度 | 评估 |
|---|---|
| 优点 | 两边都有独立 git 历史，一边损毁另一边可恢复；物理隔离（C 盘系统盘损坏时 E 盘仍完整） |
| 缺点 | **双份手工维护问题回归**：git 对齐只管"已提交"内容，工作区未提交改动、未跟踪新文件永远处于漂移窗口；互推必有冲突面（两边同时提交 → 需要 merge/rebase 人工介入）；两份存储使"哪边是新"需要靠时间戳判断； jev-eval 内的运行态文件（flag/done/jsonl）本就不该走 git，双仓互推会把这类噪音同步放大 |
| 改造量 | 最大：拆 junction、双仓初始化、remote 配置、双向计划任务、冲突处理 SOP |
| 风险 | 高：push/pull 方向或时机错误 = 历史分叉/覆盖；运行态文件反复进出 git 状态 |
| 结论 | ❌ 不推荐。若目标是容灾，正确工具是已有的 `backups/` 备份体系或仓库 bundle，而不是双活仓库 |

## 三、推荐方案与分步落地步骤（方案 B 加固版）

### 第 1 步：落盘 junction 事实文档（可由 AI 执行）

在本文件同目录新增/更新一节「C:\aios = E:\老田的AI助手 junction 说明」，写明：创建时间（约 2026-09-11，见 1.2 证据）、校验命令 `fsutil reparsepoint query C:\aios`、以及"不存在第二份代码，勿再做双目录 diff"。

### 第 2 步：把 junction 健康检查并入巡检（可由 AI 执行）

在现有 N1 检查脚本（C 盘曾出现 `N1_CHECK_FAIL` 告警，说明已有 N1 机制）中加一条：

```powershell
# C:\aios 必须是指向 E:\老田的AI助手 的 junction，否则立即告警
$t = (Get-Item C:\aios).LinkType
$targetOk = (Get-Item C:\aios).Target -eq 'E:\老田的AI助手'
if ($t -ne 'Junction' -or -not $targetOk) { 触发飞书告警 }
```

这样 E 盘换盘符/移盘/junction 误删时能分钟级发现，而不是等脚本批量报错。

### 第 3 步：git 仓库运行态清理（混合：AI 可起草，提交需用户确认）

3a. 补 `.gitignore`（AI 可直接改，属编辑文件）：

```gitignore
# ===== jev-eval 运行态补充（2026-10-08 治理）=====
jev-eval/alerts/sent/
jev-eval/n1_report_*.txt
jev-eval/push_dead_letter.jsonl
jev-eval/backup_card_acks.jsonl
jev-eval/jev_gate.err
jev-eval/gate_seen.json*
jev-eval/replay/
```

3b. 从索引移除已跟踪的运行态文件（**需要用户确认后执行**，属 git 写操作）：

```bash
git rm -r --cached jev-eval/alerts jev-eval/replay
git rm --cached jev-eval/n1_report_*.txt jev-eval/push_dead_letter.jsonl \
  jev-eval/backup_card_acks.jsonl jev-eval/jev_gate.err jev-eval/gate_seen.json.imported \
  jev-eval/alert_chain_test*.txt jev-eval/n1_check.txt jev-eval/test_hardening_h1h2h3.txt
```

文件本体保留在磁盘，仅退出版本控制（历史运行数据由 `backups/` 体系兜底，与 .gitignore 现有注释口径一致）。

3c. 处置 `backup_daily.ps1` 删除（**需用户拍板**）：`git status` 显示该文件已被删但未提交。确认"删除是有意的"后随清理一起提交；若是误删，`git checkout -- jev-eval/backup_daily.ps1` 可无损恢复。

### 第 4 步：人工确认项（需用户在管理员终端执行）

1. 进程来源收口：`Get-CimInstance Win32_Process -Filter "ProcessId=19376 OR ProcessId=58564 OR ProcessId=67588" | Select ProcessId,CommandLine`，确认 9101-9103 三个常驻进程的启动脚本路径，并把结论补进 1.5 节（本次沙箱无法代查）。
2. 计划任务盘点：`schtasks /query /fo LIST /v | findstr /i "jev aios"`，列出所有引用 `C:\aios` 或 `E:\老田的AI助手` 的任务，作为 junction 失效爆炸半径清单。

### 第 5 步：统一路径书写约定（可由 AI 后续执行，渐进式）

新脚本一律用 `$PSScriptRoot` 或从环境变量/配置取根路径；存量硬编码 `C:\aios\jev-eval`（如 run_eval.ps1）**不强制改**（junction 保证其有效），仅在顺手维护时改为 `$PSScriptRoot`。目标是把"哪个盘"从代码语义中消掉。

### 明确不做的事

- 不拆 junction，不做 A/C 方案的双份存储；
- 不为 jev-eval 单独建仓（它已随 E 盘大仓 auto 快照提交，历史连续）；
- 不修改任何计划任务（沙箱受限 + 属生产变更，需人工窗口）。
