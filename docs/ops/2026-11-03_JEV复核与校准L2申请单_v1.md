**工具内部写库前流程**（代码级，已在本分支测试覆盖）：只读扫描 → 候选分层/排序 → `sqlite3.backup` 一致性快照 + `PRAGMA integrity_check` +
`journal_mode=DELETE` 落成单文件备份 → `BEGIN IMMEDIATE` 单事务 `INSERT OR IGNORE` → `COMMIT` → 写 `<备份>.receipt.json`（含本批全部 news_id）。
参数含义：`--apply --confirm` 双开关强制；`--limit 500` 单次上限；`--db` 显式指向生产库；`--backup-dir` 固定备份目录。

### ② 影响面

- **写面**：只对 `C:\aios\news_collector\news.db` 的 `jev_review_queue` 表**追加行**（`INSERT OR IGNORE`，主键 `id`=news_id 幂等）；不改 `news` 表、不改任何其他库/表、不 UPDATE/DELETE 既有队列行。
- **负载**（实测）：只读扫描 + 104,724 条 JEV JSON 解析 **1.4~1.8s**；含 131MB SQLite 一致性备份 + 最多 500 行插入的 apply 排练 **3.5s**；内存峰值 <300MB；纯本地磁盘 IO，无网络、无端口、无服务启停。
- **磁盘**：每次实际写入生成一份 ~131MB 快照（`C:\Temp\jev_queue_backups\`）；当前 C: 可用 1.09TB。若每日都有候选，按 131MB/日累积 → **需人工按 7 天保留策略清理**（旧备份移入回收站，见 §三⑤ 注）。无候选日不备份不写库（幂等空转）。
- **队列容量**：单次最多 +500 行，可分层候选 11,367 条 → 约 23 个运行日清完存量；之后按新增 high impact 量滚动。复核人手不足时可用 `--limit` 下调或改每周。
- **时间窗口**：08:10 触发，避开 21:50–07:00 夜间 JEV/9B 独占窗口、整点 `\JevBackfill`、08:30 `\ZeroBound\DayBatch`；`StartWhenAvailable=true`（睡眠唤醒补跑）。SQLite WAL + `busy_timeout=30s`，与采集/回填并发时事务短暂等待而非阻塞读。
- **失败可见**：任务 Last Result = python rc（0 成功 / 1 写失败已回滚 / 2 前置错误 / 4 坏行且在 `--fail-on-bad` 时）；完整文本落 `C:\Temp\jev_queue_refresh_daily.log`。**未加 `--fail-on-bad`**（坏行只计数+样例落报告，不阻断整批）。
- **不影响**：`\JevBackfill` / `\ZeroBound\JevNight` / `\JevDriftDaily` / 采集 / 门户 / 交易线 / 端口 / nginx。

### ③ 不可逆点

- 唯一持久变更是 `jev_review_queue` 的**追加行**（生产数据写入）。写前必有全库一致性备份；每批有 `receipt.json` 记录全部 news_id → 可精准回滚（删除本批 id），不影响原有 10,525 行。
- 备份若在人工清理中先于验证被删除，则失去该批快速回滚能力（仍可按 receipt ids 删除）；这是**唯一需要人工纪律的点**：每次清理前确认最近 7 天备份完好。
- 无 schema 变更、无 UPDATE/DELETE、无服务/端口/凭据变更、无外发。

### ④ 替代方案

1. **不注册新任务，把 P6 追加进现有 `jev-eval\jev_drift_task.ps1`**（07:10 一次跑完 drift→审计→校准→队列）：任务对象少一个、顺序天然；但改动现有任务 action 仍属 L2，且任一 P 段失败会连坐 drift 任务退出码（失败隔离差）。
2. **只读版**：每日只产候选报告（不加 `--apply`），人工按报告导入 → 零生产写入风险，但队列仍不滚动（与现状差别仅“看得见”）。
3. **每周批量**：每周六 08:10 `--apply --limit 2000`：备份由 ~7 份/周 降到 1 份/周，写入更集中；代价是复核延迟最大 7 天。
4. **维持现状**：不注册、继续人工跑 dry-run（本轮已可随时手动执行，只读零风险）。
