## 一、三层架构（照 M6 先例）

```
引擎侧（数据落快照）          API 层（投影）                页面层（展示）
k_stock/paper/engine.py  →  k_stock/paper/portal_status.py →  portal/paper.html
  mark() 每日写:              (纯标准库 sqlite 只读 URI,        静态壳动态渲染
   equity_marks (已有)         零 pandas 依赖;                 不硬编码数字(M6 教训)
   positions_snapshot (新增)   CLI 自测 python 直接跑)      + nginx location = /paper
orders/positions (已有)     portal_api.py /api/paper_status    + 域导航条目
                              (sys.path 注入, fail loud 500)
```

## 二、关键架构决策

1. **行情依赖数据在 mark 时快照进 db**——portal_api 常驻环境（SYSTEM 任务）没有
   pandas/py311 保证，前端绝不做实时行情计算。`mark()` 扩展一张 `positions_snapshot`
   表（date/stock/qty/avg_cost/last/market_value/pnl/available），每日持仓明细随快照落库。
2. **只读优先**：v0.2 页面零写路径。手动下单继续走 CLI；web 表单下单涉及门户写路径+
   并发锁+审计，单独拍板（门户现状全站无鉴权，写能力默认不暴露）。
3. **归属 quant 域**：K-STOCK 本就是量化线，PAGE_SECTION/DOMAIN_NAV_GROUPS 进 quant。

## 三、页面信息架构（/paper 单页）

- 顶部卡片：总资产/现金/仓位/累计收益（equity_marks 最新行 vs 基线）
- 权益曲线：equity_marks 全序列（内联 SVG 折线，不引外部 CDN）
- 持仓表：positions_snapshot 最新日期明细（现价/市值/盈亏/可卖）
- 待撮合单：orders status=pending（含计划撮合日）
- 最近订单：orders 尾部 N 条（来源 ai/manual 徽标区分）
- 数据新鲜度标注：快照日期（T+1 撮合语义下，页面天然滞后一天属预期，页面注明口径）
