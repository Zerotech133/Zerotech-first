## 1. 每天 / 每周跑什么

### 1.1 固定节奏

### 1.2 "每周全量"到底指什么（先对齐口径）

读代码的事实：`backup_bundles.ps1` **每天跑的那一次就是全量**——`git bundle create <tmp> --all`，四个仓的全部 refs；`workspace-docs-<yyyyMMdd>.zip` 也是当天全量重打。不存在"日常增量 + 周日全量"。

所以周日的"全量"落在**校验范围**上：平时 `daily_ops.ps1` → `verify_backups.py` 只看最新那一个日期目录；周日 `--all` 把 `_vault` 下所有保留的日期目录都算一遍 sha256（保留几个目录，取决于 `-KeepDays`，见 §6.3）。

### 1.3 备份保护了什么（谈"备份好了"之前先看这段）

| 进备份 | 不进备份 |
|---|---|
| 4 个 git 仓的**已提交对象**：`C:\项目\老田的AI助手`、`C:\项目\zerobound-kg`、`C:\项目\digital-legion`、`C:\项目\res-downloader-py` | 未提交的工作区改动、未跟踪文件 |
| `C:\项目` 下**直接放着**的 `*.md` + `*.html`/`*.htm`（不递归，实测 20 md + 9 html = 29 个；`.mcp.json`/`.env*` 按名排除） | `docs/` 子目录里的任何文件（含本文） |
| — | 被 `.gitignore` 的数据、数据库、模型、大二进制 |

量级（2026-10-22 07:03 实测）：aios bundle 683.4 MiB；aios 仓 `git ls-files` **4,919** 个文件，而工作树实际 **822,261** 个文件 / **87.66 GB**。差额就是"没进 git 的东西"，它们不在任何备份里。

结论：**新写的代码/文档必须 commit 才进备份**。本文这份 SOP 在提交前也不在备份里。

### 1.4 异地备份：预览 → 出清单 → 才搬 723 MB → 上传后校验

`_vault` 是本机唯一的备份仓，723 MB，**同盘同机——盘坏即全丢**。把包整理成"传上去就能用"可以自动化；**上传本身只能人做**（要账号）。`prepare_offsite.ps1` 只负责打包这一步：不开 socket、不登录、不碰任何凭据。

四步，顺序不能换：

```powershell
# 1) 预览：只核对 6 个产物 + 打印计划，不建目录、不写文件
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\项目\老田的AI助手\tools\prepare_offsite.ps1' -DryRun

# 2) 预览无 [FAIL] 后再出清单：只落 3 个小文本（约 9 KB）到 C:\项目\_offsite\
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\项目\老田的AI助手\tools\prepare_offsite.ps1'

# 3) 需要把 723 MB 顺手搬到 _offsite\ 时才加 -Copy（默认不搬）
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\项目\老田的AI助手\tools\prepare_offsite.ps1' -Copy

# 4) 传到别处之后，在**接收方**核对（Linux/WSL；Windows 用工具写出的 README 里那段）
sha256sum -c SHA256SUMS.txt
```

写出的三个控制文件（都落在 `C:\项目\_offsite\`，可用 `-OutDir` 改）：

| 文件 | 内容 |
|---|---|
| `<日期>-offsite.txt` | 人读清单：6 个产物的名字 + 字节数 + `MANIFEST.txt` 里记的 sha256 + 上传后该怎么核对 |
| `SHA256SUMS.txt` | 标准 `sha256sum` 格式（纯 ASCII、LF 换行、小写 hex），`sha256sum -c` 直接可用 |
| `README-上传说明.md` | 三步（传什么 / 怎么验 / 验过之后做什么）+ 一条「这是打包，不是上传」的横幅 |

**判据（为什么这样判，而不是"跑了就绿"）**：

- **先比字节数，不重算 sha256。** 6 个产物逐个对 `MANIFEST.txt` 记的字节数：缺文件、没打当日戳、字节数不符，**任一命中就不写任何输出文件并 exit 1**。理由是"打包一个坏日期比不打包更糟"——坏包看起来是完整的。sha256 这一遍刻意留给接收方：`MANIFEST.txt` 是产出这批字节的那一轮写的，同盘再算一遍最多证明"文件没变"，证明不了"到了异地还是这批字节"。本地全量哈希归 `verify_backups.py`（§7.1），不重复劳动。
- **`-Copy` 同盘复制不等于第二份。** 它只是替人省一步，输出里会明写"staging for upload, not a backup, not an offsite copy"。真异地 = 人把文件搬到另一台机器/另一块盘。**`-Copy` 跑完不等于异地备份完成了。**
- **`-DryRun` 的退出码有含义**：0 = 源校验通过，**1 = 源校验已失败**（这点和 `backup_bundles.ps1 -DryRun` 的"恒 0"不同，见 §6.1，别看错）。

两个前提，缺一即 exit 2：

1. `prepare_offsite.texts.txt` **必须和 .ps1 放在同一目录**。脚本本身是纯 ASCII（PS 5.1 按 CP936 解码无 BOM 的 `.ps1`，脚本里写中文会变乱码），中文文案全在那个文本文件里，脚本按 UTF-8 逐段读取并校验；缺段、缺键、留了未替换的 `{TOKEN}` 一律中止，不会产出半空 README。
2. `_offsite` **不能和 vault 互相包含**。往日期目录里写文件会改变 `MANIFEST.txt` 所描述的那个产物集合（→ 制造 `orphan`/`mismatch`）。

**别做什么**：

- 别把 `-Copy` 当"已经异地备份了"（见上）。
- 别在 `-DryRun` 报 `[FAIL]` 的情况下跳过预览直接真跑——真跑同样 fail-closed，只是白等一次。
- 别手工编辑 `SHA256SUMS.txt`：那是 `MANIFEST.txt` 的记录值，不是现场重算值。改了就等于伪造校验基线。
- 别用 `C:\aios` 别名启动（§6.1：workspace 会算成 `C:\`，vault 与 `_offsite` 一起指错）。

### 1.5 整理层重建（每周）

数据根是**两层**：

| 层 | 目录 | 量级 | 谁在写 |
|---|---|---|---|
| 原始层 | `quant_backtest\data\tushare\` | **228,930 个 parquet / 12.71 GiB** | 写入管线（`staging_materialize` / `history_backfill` / `full_refresh` / `tail_fill`），**每天都在写** |
| 整理层 | `quant_backtest\data\tushare_curated\` | **54 个文件 = 51 张表 + 3 个侧车 / 7.18 GiB** | 只有 `tools\refresh_curated.py`，**纯派生** |

关键事实：**整理层不会跟着原始层变新。** 原始层今天又落了新数据，整理层还是上周那一份——它不会报错、不会丢文件，只是"旧"。所以健康卡加了第 19 项 `data.curated_freshness` 来量这件事（判据见 §2.2）。

**何时跑**：

- **每周一次**（建议排在周日备份校验之后，与 §1.1 的周节奏合并做）；
- **健康卡出现 `[yellow] data.curated_freshness`**（落后 >2 天）时立刻补跑；
- 该项变**红**（落后 >14 天）时，先重建、再看结论——两周没重建，拿整理层算出来的东西不可信。

**三条命令**（顺序不能跳）：

```powershell
$py = 'C:\Program Files\Python311\python.exe'

# 1) 只出计划，不写盘（要逐文件读 parquet footer，实测 182 s）
& $py -B 'C:\项目\老田的AI助手\tools\refresh_curated.py' --dry-run

# 2) 真跑：重建到 tushare_curated.tmp，逐文件校验行数，**不替换**正式目录（全量约 52 分钟）
& $py -B 'C:\项目\老田的AI助手\tools\refresh_curated.py'
"exit=$LASTEXITCODE"

# 3) 第 2 步校验通过、且确认新层可用之后，才替换（会永久删除旧整理层）
& $py -B 'C:\项目\老田的AI助手\tools\refresh_curated.py' --replace
```

**两条禁忌**：

1. **不要在 `kg_sync` 正在跑的时候重建。** 那一轮写入正在往原始层落文件，`refresh_curated.py` 会读到**写了一半的数据**：footer 读不出、或行数少一截。后果不是报错，而是校验口径本身被污染（"源行数"和"产物行数"一起错），最容易产出一个"校验通过但其实缺数据"的整理层。跑之前先看 `C:\Temp\kg_sync_task.log` 尾部确认没有进行中的操作（AGENTS.md §3 共享数据根互斥）；重建脚本自己会往该日志补一行（`--no-log` 可关，**别关**）。
2. **不要用 `--replace`，除非校验通过。** `--replace` = `rmtree(<正式整理层>)` + `tmp.rename()`，是**永久删除**且没有回滚（本机该进程回收站不可用，`SHFileOperationW` 会退化成硬删，源码注释写明）。校验不通过时脚本自己**不会**替换（exit 1、`.tmp` 保留）——这时要做的是看日志定位哪张表行数不对，**而不是**手工 `--replace` 跳过校验。

**量级与耗时**（2026-10-22 12:09 全量 end-to-end 实测，**修正早先的 52 分钟估计**）：

| 项 | 实测 |
|---|---|
| 全量重建（51 表，含读源 + 写盘 + 逐文件校验） | **14 分钟**（11:55:53 → 12:09:44） |
| `--dry-run` | 289 s（空闲时）/ 771 s（机器繁忙时，11:52 实测） |
| 产物 | 7.18 GiB / 54 个文件（51 表 + 3 侧车） |
| 行数核对 | 源 322,215,509 = 产物 322,215,509，0 坏文件 |
| 源侧 | 228,930 个文件 / 12.71 GiB |

> 早先写的"52 分钟"是**未实测的估计**，偏高 3.7 倍。每周 routine 按 15 分钟量级安排即可。

**默认排除 `stk_pledge`**：它一个目录放两张表（7 列 stat / 14 列 detail），不排除则全量必 `exit 1`（`dirs_skipped=1`），**永远走不到 `--replace`**——每周 routine 会卡在"能暂存、不能切换"。工具已默认排除，别手工加回来（要合它得先做跨仓拆表，见 `合并上线_下游引用扫描` 的 6 个引用方）。

`--dry-run` 输出一行 `计划：51 个目录 / 51 张表 / 226,639 文件 / 322,215,509 行`——这是重建后应有的形状，**真跑的计划行必须和它同量级**。

## 2. 怎么看健康卡

### 2.1 六个区块分别回答什么

| 区块 | JSON 键 | 数据源 | 回答的问题 | 读不到时的表现 |
|---|---|---|---|---|
| 计划任务审计 | `task_audit` | `portal/data/task_exit_audit/task_exit_ledger.jsonl` + `task_exit_summary.json`（由 `agent_platform/tools/task_exit_audit.py` 写） | 计划任务上一轮扫描有没有非零退出 | `available=false`，`reason` 给原因，**计数字段全 `null`** |
| 备份 | `backup` | `_vault\<yyyy-MM-dd>\MANIFEST.txt` + 日期目录 mtime | 最近一份备份是哪天、清单条目/体积/存在性/大小对不对得上 | `available=false`，`manifest_entries`/`age_hours`/`total_bytes` 全 `null` |
| 数据根漂移 | `data` | `_vault\<yyyy-MM-dd>\data_manifest.json`（`tools/gen_data_manifest.py` 写）、`_vault\data_manifest.json` 兜底 | 数据根形状（文件数/总字节/一级目录数/`catalog.json` 的 sha256）跟上一份清单比漂了多少 | `available=false`，漂移计数全 `null`，判**黄**（不是绿） |
| 整理层新鲜度 | `data.curated_freshness` | `quant_backtest\data\tushare_curated\` 下最旧 parquet 的 mtime vs `quant_backtest\data\tushare\` 递归最新 parquet 的 mtime（另按 51 个数据集逐个比） | 整理层还跟不跟得上原始层（落后几天、哪几个数据集旧了） | `available=false` + 计数全 `null`：整理层不存在/为空判**黄**（不判绿）；原始层不存在或遍历超 5 s 判**红** |
| 仓库卫生 | `repo` | `git status --porcelain=v1`、`git worktree list --porcelain`、`.worktrees\` 目录数 | 工作区脏不脏、有没有冲突、工作树登记与目录数是否一致 | `available=false`，`dirty_files`/`worktrees` 全 `null` |
| 文档索引 | `docs` | 子进程 `python -B tools/gen_docs_index.py --check`（超时 20 s，预算 3 s） | `DOCS_INDEX.md` 还跟不跟得上仓库现状 | `available=false` + `reason`，判**红** |
| 明文私钥 | `security` | 递归 `<repo>\outputs`、`<repo>\tools`、`<repo>\portal`，按文件名（`*.pem`/`*.key`/`id_rsa*`/`.env*`）与内容标记（`PRIVATE KEY`）双向命中；3 s 预算，跳过 `.git`/`node_modules`/`.venv`/`.worktrees`/`__pycache__` | 仓库里有没有明文私钥躺着；**只报路径 + 字节数 + 是否被 git 跟踪，不回显任何文件内容** | `available=false`，判**红** |

健康卡**不重算 sha256**，只核对清单条目、文件存在性与大小（卡里自己写着这句）。字节级的"对不对"归 `verify_backups.py`。两个工具要一起看。

### 2.2 判级规则：21 项固定 + 3 项条件

| check id | 绿 | 黄 | 红 |
|---|---|---|---|
| `ops.alert_watch_liveness` | 最后写状态 ≤2 h | >2 h（连续 4 轮没写） | >26 h（整天没成功过）/ 状态文件缺失或不可读 |
| `ops.task_launch_failures` | 最近事件无「动作起不来」 | 有 1–2 次 | 同一任务 ≥3 次 `0x8007000x`（无效功能/文件未找到/路径未找到） |
| `task_audit.readable` | 账本可读 | — | 账本不存在 / 读失败 / 无带合法 `at` 的记录 |
| `task_audit.failures` | 无失败任务 | — | ≥1 个非零退出（口径见下） |
| `task_audit.unknown` | 未知码 0 / 未知状态 0 | 有未知退出码或未知状态 | — |
| `task_audit.freshness` | 最近扫描 ≤24 h | >24 h | >72 h 或算不出 |
| `task_audit.clock_skew`（条件） | 不出现 | 账本 `at` 在未来 | — |
| `task_audit.ledger_integrity` | 全部可解析 | 有解析失败行 / 缺 `at` | — |
| `task_audit.summary_sync` | 摘要与账本一致（时间差 ≤120 s 且计数零漂移） | 摘要不可读，或计数/时间对不上 | — |
| `task_audit.semantics` | 复用 `EXIT_SEMANTICS` | import 失败、退化判定 | — |
| `backup.readable` | 可读 | — | vault 不存在 / 无日期目录 / 无 MANIFEST / 清单全不可解析 |
| `backup.freshness` | ≤36 h | >36 h | >72 h 或算不出 |
| `backup.clock_skew`（条件） | 不出现 | 目录 mtime 在未来 | — |
| `backup.integrity` | 条目齐、大小一致 | 清单有格式异常行，或大小与清单不符 | 清单里的文件不在目录中 |
| `backup.catchup` | 四个仓的 bundle 均追平 HEAD | 落后 HEAD（>0 个提交） | 落后且备份已 >24 h 未更新 |
| `data.root_drift` | 两期清单完全一致（文件数/总字节/一级目录数/`catalog.json` sha256 全同） | 有小变化但未过阈值；**或只有 1 份清单、清单读不了、上次扫描未完成（`available=false`）——一律判黄，单份清单不判绿** | 文件数变化 >20%，或一级目录数变化 |
| `data.curated_freshness` | 整理层落后原始层 ≤2 天（含"原始层最新写入不晚于整理层"，即 lag ≤0） | 落后 >2 天（该重建了）；**或整理层不存在/为空（`available=false`，计数 `null`，不判绿）** | 落后 >14 天（整理层已明显过期，读它得出的结论不可信）；或原始层不存在、原始层无 parquet、两层数据集名一个都对不上、遍历超 5 s 预算（`available=false`） |
| `repo.readable` | 可读 | — | 不是 git 工作树 / 找不到 git / `git status` 非零 |
| `repo.conflicts`（条件） | 不出现 | — | ≥1 个冲突文件 |
| `repo.dirty` | 干净 | `dirty_files > 0`（**含未跟踪**） | — |
| `repo.worktrees` | `.worktrees` 目录数 == `git worktree list` 关联数 | 两者不等 | — |
| `repo.worktree_ttl` | 无「已合并且分支年龄 >7 天」的关联工作树 | 有超期项 / 有未知项 | 算不出（不可用） |
| `docs.index_freshness` | `gen_docs_index.py --check` exit 0 | exit 1（索引过期）/ 状态未知 | 脚本缺失 / 超时 / 其它错 |
| `security.plaintext_keys` | 扫完、0 命中、且没有读不到的目录/文件 | 0 命中但有目录或文件读不到（等于没看全） | **命中 ≥1 个即红（发现私钥即红）**；或扫描没跑完（超时/异常 → `available=false`） |

合成规则：取所有 check 的**最差等级**（红 > 黄 > 绿）；`status=red` ↔ exit 1，`green`/`yellow` ↔ exit 0。条件项不触发就不出现，所以一次正常输出是 **19 项**，最多 22 项（`backup.catchup` 在追平状态为 `unknown` 时也缺席）。

两项 `data` 检查的共同纪律是**"判不了不判绿"**：`data.root_drift` 在只有一份 `data_manifest.json` 时无从比对 → `available=false` → **黄**（2026-10-22 首次上线就是这个状态，等第二份清单落下来才可能转绿）；第 19 项 `data.curated_freshness` 同理——整理层缺失或为空判**黄**（缺件不等于坏掉，且它是纯派生产物），但**原始层缺失、原始层没 parquet、或自己扫不完（>5 s）判红**。`security.plaintext_keys` 只要有目录扫不进去或被 3 s 预算截断 → 红/黄，**绝不因为"没扫到"就说"没有私钥"**。别看 `security.plaintext_keys` 红就直接慌：先看 detail 是"命中"还是"没扫完"，两者处置完全不同（命中 → 按凭据处置；没扫完 → 先修扫描）。

任务失败的计数口径（与 `task_exit_audit.py` 同源）：`Disabled` 不计、`267011`（尚未运行）记"未运行"、**其余非零全记失败**——包括 `267009`（正在运行）和 `267014`（被强制终止）。所以"9 个任务非零退出"不等于"9 个任务坏了"，见 §3.1。

### 2.3 三条纪律

1. **读不到 ≠ 健康。** 任一区块 `available=false` 一律判红、exit 1，计数字段给 `null` 而不是 `0`（代码用 `_empty_*` 初始化成全 `None`）。
   **例外落在 `data` 块的两项**：`data.root_drift` 判**黄**——它量的是"漂移了多少"，判不了并不等于数据坏了；`data.curated_freshness` 在"整理层不存在/为空"时判**黄**——整理层是纯派生产物，缺了不影响原始层。两项都**不判绿**、计数同样给 `null`（见 §2.2）。但 `data.curated_freshness` 的另外两个分支仍是**红**：原始层不存在、或遍历超 5 s（自己没量完）。`security.plaintext_keys` **不享受这个例外**：没扫完就是红。
   实测：`gen_health_card.py --task-audit-root 'C:\项目\_no_such_audit'` → `status=red`、`exit=1`、`task_audit.available=false`、`failed=null`、`total_scanned=null`。
   配套纪律：看到 `null` 不要当"零失败"，也不要在 PowerShell 里对 `$null` 做加减（`$null + 1` 不报错，会静默变成 1）。
2. **exit 0 ≠ 全绿。** 黄也是 exit 0：`daily_ops.ps1` 只在"红 或 无法判定"时 exit 1。同理 `verify_backups.py` 的新鲜度在 36–72 h 只是"黄"，**不改退出码**，只在 stderr 打一行 `WARN:`。
3. **卡是聚合，不是根因。** 卡只回答"哪一块不绿"；是哪个任务、哪个文件，要下钻原始 JSON（§3 每节都给了下钻命令）。

## 3. 常见红的处置路径

每节统一三段：**先看什么 / 再做什么 / 别做什么**。

### 3.1 任务非零退出（`task_audit.failures` 红）

**先看什么**——把失败清单拉出来（只读，不落盘）：

```powershell
$py = 'C:\Program Files\Python311\python.exe'
$card = ((& $py -B 'C:\项目\老田的AI助手\tools\gen_health_card.py' 2>$null) -join "`n") | ConvertFrom-Json
$card.task_audit.failures | Format-Table name,last_result,exit_semantics,last_run -AutoSize
```

（卡的 `failures` 每条只有 `name` / `last_result` / `exit_semantics` / `last_run` 四个字段；`next_run` 只在账本 `task_exit_ledger.jsonl` 里，写进 `Format-Table` 会得到一列空值。）

**读数**（`exit_semantics` 来自 `agent_platform/tools/task_exit_audit.py` 的 `EXIT_SEMANTICS`）：

| `last_result` | 语义 | 在这张表里意味着什么 |
|---|---|---|
| `1` | 一般失败 | 真失败 |
| `2` | 一般错误/文件找不到/degraded | 真错误，多为路径或依赖缺失 |
| `3221225786` | Ctrl-C 类强杀（0xC000013A） | 被中断 |
| `267009` | 任务正在运行（0x41001） | **快照时正在跑，不是失败**，复跑一次通常会消失 |
| `267014` | 任务被强制终止（0x41306） | 超时或被下一轮顶掉，拿 `last_run` 与预定窗口对 |
| `267011` | 任务尚未运行 | 审计侧记"未运行"，不会出现在这张表里 |

**再做什么**——按 `name` 查该任务上次运行时间与结果。本机 `Get-ScheduledTaskInfo` 实测被拒（"拒绝访问"），用账本里的 `last_run`/`next_run` 顶替，或直接读摘要：

```powershell
Get-Content -LiteralPath 'C:\项目\老田的AI助手\portal\data\task_exit_audit\task_exit_summary.json' -Raw -Encoding UTF8 |
  ConvertFrom-Json | Select-Object generated_at,total_scanned,ok,failed,disabled,never_run
```

定位到具体任务后走该任务自己的 runbook（本文不覆盖各业务任务）。

**别做什么**：

- 别把 `267009` 当故障去"修"，也别为了让卡变绿去停任务。
- 别手工改 `task_exit_ledger.jsonl`（append-only，改了会破坏 `summary_sync` 的交叉核对）。
- 别手动跑 `task_exit_audit.py --scan` 来"刷新"：它会写账本与摘要（非只读），会把"最近扫描时间"刷成现在，让 `task_audit.freshness` 由红变绿，从而掩盖"审计调度已经停摆"这个真问题。

### 3.2 备份超 36 h 黄 / 超 72 h 红（`backup.freshness`）

**先看什么**：

```powershell
$py = 'C:\Program Files\Python311\python.exe'
$card = ((& $py -B 'C:\项目\老田的AI助手\tools\gen_health_card.py' 2>$null) -join "`n") | ConvertFrom-Json
$card.backup | Format-List latest_date,dir_mtime,manifest_mtime,age_hours,manifest_entries,manifest_missing,size_mismatch,total_human
Get-ChildItem -LiteralPath 'C:\项目\_vault' -Directory | Select-Object Name,LastWriteTime | Sort-Object Name
```

读法：`age_hours` 的参考时间是**日期目录的 mtime**（`dir_mtime`），不是文件内容时间；正常情况下它等于当天最后一次备份的落盘时间。

**再做什么**——先预览、再真跑、再看退出码：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\项目\老田的AI助手\tools\backup_bundles.ps1' -DryRun
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\项目\老田的AI助手\tools\backup_bundles.ps1'
"exit=$LASTEXITCODE"
```

- exit 0 → 再跑一次 `daily_ops.ps1` 复看。
- exit 1 → 看输出里的 `[FAIL] <label> <detail>`。**单仓失败不影响其它仓落盘**，`MANIFEST.txt` 照样写（只列成功项），所以"备份跑过了"和"备份齐了"是两件事（§6.8）。

**别做什么**：

- 别跳过 `-DryRun` 真跑：它会把 4 个仓路径、vault 根、`keep days`、将删目录全打印出来，路径指错（例如从 `C:\aios` 启动，§6.1）能当场看出。
- 别手工往 `_vault\<日期>\` 里补文件或改 `MANIFEST.txt`：多出来的文件判 `orphan`，改清单会让大小/sha256 对不上，两种都把校验搞红。
- 别在备份正在跑的时候跑校验：`MANIFEST.txt` 是最后写的，中途校验必然看到大小/sha 不一致。

### 3.3 dirty（`repo.dirty` 黄）

健康卡**没有** dirty 阈值：`dirty_files > 0` 就是黄。"过多"是人判断，不是工具判断。

**先看什么**：

```powershell
& git -C 'C:\项目\老田的AI助手' status --porcelain=v1
& git -C 'C:\项目\老田的AI助手' status --porcelain=v1 | Measure-Object -Line
```

读法：`??` 未跟踪、` M` 工作区改动、`M ` 已暂存，两列含义不同；卡只报"多少行"，不区分。健康卡另给 `untracked_files`/`staged_files`/`conflicted_files` 三个细分。

**再做什么**：按目录归类（`data_sources/`、`k_stock/`、`quant_backtest/data/`…），逐块决定 commit / stash / 丢弃，再复跑 `daily_ops.ps1`。

**别做什么**：

- 别 `git add -A` 一把梭：本仓工作树 87.66 GB / 82 万文件，误加数据目录会把仓库撑爆。
- 别 `git checkout -- .`、别 `git clean -fdx`：前者丢改动，后者永久删未跟踪文件，且与本仓"Windows 删除一律进回收站"的红线相悖。
- 别为了让黄变绿去改 `.gitignore`：那只改分类，不改事实。
- 注意：健康卡自身备注"本脚本自身在提交前也会被计入"——**本文这份 SOP 提交前会让 dirty +1**，提交后回落，不是异常。

### 3.4 工作树与账本不一致（`repo.worktrees` 黄）

**先看什么**：

```powershell
& git -C 'C:\项目\老田的AI助手' worktree list --porcelain
Get-ChildItem -LiteralPath 'C:\项目\老田的AI助手\.worktrees' -Directory | Select-Object Name,LastWriteTime
```

判据：`.worktrees` 下的**目录数** 与 `git worktree list` 的行数减 1（减掉主树）比较。

**再做什么**——逐条分类：

- 目录在、登记没了：多半是 `devtask.py new` 建到一半，或手工删过登记。先用 `git -C '<该 worktree 路径>' status` 确认里面有没有未提交的活。
- 登记在、目录没了：登记是陈的（目录被移走/删掉）。

两类都先把"里面有没有人没提交的活"确认完，再决定是否清登记。

**别做什么**：

- 别直接 `git worktree prune`：它会改 `.git/worktrees` 元数据（非只读），清掉登记后那些目录里的活就失去关联。
- 别 `Remove-Item` 删 `.worktrees\<TID>`：别的 Agent 可能正在里面干活，且违反删除进回收站的红线。

### 3.5 备份校验红（`mismatch` / `missing` / `orphan` / 新鲜度）

**先看什么**：

```powershell
$py = 'C:\Program Files\Python311\python.exe'
& $py -B 'C:\项目\老田的AI助手\tools\verify_backups.py' --all
```

`problems` 段逐条写：`<日期>/<文件名>: content mismatch`、`listed in MANIFEST but file is missing`、`orphan file`、`MANIFEST.txt line N`。退出码：`0` 全过 / `1` 有问题 / `2` 参数或路径错。

**再做什么**（按类型）：

| 现象 | 常见原因 | 处置 |
|---|---|---|
| `mismatch` | 目录被改过、盘上数据坏了、或备份正跑到一半 | 先比 `MANIFEST.txt` 的 `# vault backup` 时间与文件 mtime；确认不是跑到一半，就重跑一次备份让两者一致 |
| `missing` | 清单列了但文件不在（有人手删/搬运） | 重跑备份补齐；补齐前别删任何东西 |
| `orphan` | 目录里有、清单没列（同日重跑时某仓失败，且旧清单记录与文件已对不上，旧 bundle 才留成孤儿） | 这是"当天备份不完整"的正确信号，**不要删那个孤儿文件** |
| `freshness fail` | >72 h 没出新备份 | 走 §3.2 |
| `parse error` | `MANIFEST.txt` 被手工编辑/截断 | 重跑备份覆盖它（保留旧目录内容前先确认） |

**别做什么**：

- 别手工编辑 `MANIFEST.txt` 让它"对上"。
- 别用 `--sample N` 的通过下"全绿"结论：`--sample` 只核最大的 N 个文件的 sha256，JSON 里 `summary.complete=false`；退出码 0 不代表每个字节都对过。
- 别用 `--date <旧日期>` 的 `freshness` 说事：`--date` 只把所选目录喂给新鲜度计算（`compute_freshness(dir_reports, ...)`），选历史日期必然 >72 h 判红，这是判据行为，不是备份坏。
- 别在备份运行中跑校验（同上，`MANIFEST` 后写）。

### 3.6 任一区块 `readable` 红（无法判定）

**先看什么**：卡里 `reason` 与对应 check 的 `detail` 原文。

| 区块 | 典型 `reason` | 含义 |
|---|---|---|
| `task_audit` | `账本不存在: …\task_exit_ledger.jsonl` | 审计任务没跑过，或 `portal/data/task_exit_audit` 被搬走/改名 |
| `backup` | `备份根不存在或不是目录` / `未找到 yyyy-MM-dd 备份目录` | 从没备份过，或 vault 根指错（例如从 `C:\aios` 启动，§6.1） |
| `repo` | `不是 git 工作树` / `找不到 git 可执行文件` / `git status 失败` | git 不在 PATH、路径指到子目录、仓库损坏 |

**再做什么**：把路径修回默认（`_vault` = `C:\项目\_vault`，审计账本 = `<repo>\portal\data\task_exit_audit`），复跑。

**别做什么**：别改判定阈值（`--warn-hours` / `--fail-hours` 是参数，改阈值不改事实）；别把 `available=false` 手工当绿放行。

## 4. 备份恢复演练 SOP（周日/月度，约 30 秒）

### 4.1 两条铁律

1. **用 `--bare`，不要直接 `git clone`。** aios 工作树 87.66 GB / 822,261 个文件，完整 clone 会把 87 GB 落到临时盘；`--bare` 只落 **0.67 GB**（实测 11.1 s）。
2. **演练目录只放 `%TEMP%\restore-drill\`**，不许落仓库里，也不许落 `_vault\` 里（落 vault 里会被判 `orphan`）。

### 4.2 取件：先确认 bundle 里有什么（只读，0.2 s）

| 项 | 事实 |

## 6. 我踩过的坑（2026-10-22 本机实测）

### 6.1 用 `C:\aios` 启动 = 备份写到 `C:\_vault`，而且 `-DryRun` 照样 exit 0

`C:\aios` 是指向 `C:\项目\老田的AI助手` 的 junction（实测 `LinkType=Junction`、`Target=C:\项目\老田的AI助手`）。脚本用 `$PSScriptRoot` 反推 workspace，于是：

```text
repo root   : C:\aios
workspace   : C:\
vault root  : C:\_vault  (exists: False)
[plan] aios           C:\aios  ->  aios-20261022.bundle
[FAIL] zerobound-kg  repo folder not found
[FAIL] digital-legion  repo folder not found
[FAIL] res-downloader  repo folder not found
workspace archive (md + html):
  [skip] no *.md / *.html / *.htm directly under the workspace root
result      : OK (plan only)   exit=0
```

两个教训：

1. 路径一律写 `C:\项目\老田的AI助手\...`，别用别名启动。
2. **`-DryRun` 恒 exit 0**（dry-run 分支直接 `exit 0`）。上面 3 个仓 FAIL，它仍打印 `result : OK (plan only)`。所以 dry-run 的 OK **不能**当"明天真跑会成功"的证据，要看 `problem(s)` 数字和 `[FAIL]` 行。

另：`docs/ops/2026-10-08_C盘aios-junction说明.md` 里原先写的 Target `E:\老田的AI助手` 已在 2026-10-22 一并校正为 `C:\项目\老田的AI助手`（该文件顶部有「2026-10-22 校正」一行），两份文档现在口径一致。

### 6.2 `-Quick` 只省 1%，因为它省的是"最小的那几个文件"

`-Quick` = `--sample 1` = 只对**最大**的 1 个文件算 sha256。本机最大的就是 aios bundle（683.4 MiB），另外 5 个文件（三个小 bundle + docs zip + `data_manifest.json`）合计约 6.5 MiB。

实测：全量 `daily_ops.ps1` 6.76 s（其中校验 2.07 s，`hashed` 723,504,214 字节）；`-Quick` 6.47 s（`hashed` 716,639,555 字节，`unverified` 5）。抽样只跳过 **0.95%** 的字节，两者差异在噪声内。

结论：本机盘速 680 MiB/s，全量本来就够快；`-Quick` 在这里不值得用。要省时间，省在"别在备份运行中跑校验"，而不是砍 sha256。

### 6.3 `-KeepDays 14` + 每周日 = 只留 **3** 个日期目录，不是 14 代

保留判据是"日期目录名 ≥ 今天 − 14 天"（`$parsed -ge $Cutoff` 才保留）。周频备份的日子是 0 / 7 / 14 天前，**14 天前那天正好等于 cutoff，仍然保留** → 稳态 3 个目录。

要"14 代周备"得 `-KeepDays 98`；默认 14 是"14 天日备"的窗口。`-KeepDays 0` = 只留今天（范围 0–3650）。

### 6.4 `git bundle verify` 不能脱离仓库单独跑

实测裸跑 `& git bundle verify 'C:\项目\_vault\2026-10-22\aios-20261022.bundle'` → `error: need a repository to verify a bundle`、exit 1。
要用 `& git -C '<某个仓>' bundle verify <bundle>`（实测 0.2 s，输出 `The bundle records a complete history.`），或只用 `git bundle list-heads`（不需要仓库）。

### 6.5 `git clone` 只搬 `refs/heads/*` 和 `refs/tags/*`

aios bundle 54 个 ref，`clone --bare` 后剩 49 个，`refs/stash` 与 `refs/codex/snapshots/*` 不进来（§4.7 给了 `fetch '+refs/*:refs/*'` 的补法，实测取回 52 个）。

### 6.6 PS 5.1 的 `Get-Content` 默认按 GBK 解码 UTF-8 —— 读 JSON 直接抛错

实测 `Get-Content -Raw '…\task_exit_audit\task_exit_summary.json' | ConvertFrom-Json` 报 `传入的对象无效…`，中文全成"鍐涘洟绯昏"。
正确写法：`Get-Content -LiteralPath '<路径>' -Raw -Encoding UTF8 | ConvertFrom-Json`。
（工具本身没这问题：两个 py 工具强制 UTF-8 输出，`daily_ops.ps1` 也把 `[Console]::OutputEncoding` 设成 UTF-8。）

### 6.7 PS 5.1 的 `Set-Content -Encoding UTF8` 写 BOM —— MANIFEST 实测 `EF BB BF` 开头

`backup_bundles.ps1` 用 `Set-Content -Encoding UTF8` 写 `MANIFEST.txt`，实测文件头就是 BOM；`verify_backups.py` 用 `utf-8-sig` 读（代码注释："PS 5.1 的 Set-Content -Encoding UTF8 会写 BOM，必须吃掉"），`gen_health_card.py` 同样先 `utf-8-sig` 再退化解码。两个工具都不受影响。

自己写脚本读这个 MANIFEST 时：PowerShell 用 `Get-Content -Encoding UTF8`（5.1 会自动跳 BOM），Python 用 `encoding='utf-8-sig'`；用 `ReadAllBytes` 做首字节比较会把 BOM 算进去。

同一族的坑：5.1 的 `>` 重定向写的是 **UTF-16LE**（实测文件头 `FF FE`），拿它落 JSON 再喂 Python 会直接解码失败；要落盘用 `Set-Content -Encoding UTF8`（UTF-8 + BOM），消费方按 `utf-8-sig` 读。

### 6.8 "备份跑完了"和"备份齐了"是两件事

`MANIFEST.txt` 是**最后**写的；单仓失败只打一行 `[FAIL]`，其它仓照落，退出码 1。所以：看退出码，别只看"有没有新文件"。

两个连带现象：

- 备份运行中跑校验，会看到大小/sha 不一致（清单还停在上一轮）。
- 同一天重跑时，失败的仓若上一轮清单记录与盘上文件仍一致（字节数 + sha256 都对），旧记录会以 `#` 注释**沿用**进新 `MANIFEST.txt`，不再判 `orphan`/`missing`——「prefer a gap over a lie」：只有文件缺失或 hash 变了才留空档。真出现 `orphan` 仍要人看，**别删**。

### 6.9 未提交的东西不在备份里（含本文）

aios：`git ls-files` 4,919 个文件（2026-10-22 07:03 实测），工作树 822,261 个文件 / 87.66 GB，而 bundle 683.4 MB。差额就是没进 git 的东西。
`workspace-docs-*.zip` 只收 `C:\项目` 根下的 `*.md` + `*.html`/`*.htm`（不递归；实测 20 md + 9 html = 29 个；`.mcp.json` / `.env*` 按名排除），`docs/` 里的一律不收。
所以：写完文档先 commit，再指望备份。
