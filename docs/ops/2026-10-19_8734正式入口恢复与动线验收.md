# 情报中枢 8734 正式入口恢复与页面动线验收

**日期**：2026-10-19
**范围**：情报工作台（`/intel`）正式入口 8734 的 portproxy 恢复、HTTP 契约联调、浏览器动线验收、以及本次排障过程沉淀为可复用 skill。
**影响文件**：本次未修改项目代码或配置；仅新增一个 Trae skill 到 `.trae/skills/`。

## 背景

情报中枢首批功能（工作台 + 证据—标的接口）已完成合并，8091 入口健康，但唯一面向人的正式入口 **8734** 多次探测显示未监听。此前 GOV-FIX-006 只读核验和环境耦合 manifest 均已标注该端口缺失 portproxy 规则。

## 诊断过程

**证据链**（每条都有独立命令输出，未"看一眼就下结论"）：

| 命令 | 结果 | 解读 |
|------|------|------|
| `Get-Service iphlpsvc` | `Running / Automatic` | IP Helper 正常 |
| `netsh interface portproxy show all` | 空表（仅表头） | **根因**：规则从未建立 |
| `Get-NetTCPConnection 8734 -State Listen` | 无 | 入口确实没监听 |
| `Get-NetTCPConnection 8080 -State Listen` | `::1:8080` / `:::8080` | 后端 nginx 在 |
| `Invoke-WebRequest http://127.0.0.1:8080/intel` | HTTP 200 | 后端页面完好 |

**归类**：后端没问题、前端页面没问题，缺的就是一层 **8734 → 8080 的 netsh portproxy 转发**。

## 恢复动作

非管理员 PowerShell 执行 `netsh interface portproxy add` 会触发"请求的操作需要提升"。通过管理员 UAC 执行：

```powershell
# 先删后加，幂等
netsh interface portproxy delete v4tov4 listenaddress=127.0.0.1 listenport=8734
netsh interface portproxy add    v4tov4 listenaddress=127.0.0.1 listenport=8734 connectaddress=127.0.0.1 connectport=8080
```

**只绑定 127.0.0.1**，未用 `0.0.0.0`，避免暴露到外网。

## Skill 沉淀

本次 8734 排障暴露了三条重复痛点：
1. portproxy 规则经常空表但没人知道怎么查（netsh 空表和 iphlpsvc 未启动返回完全不同的输出，不能混为一谈）
2. 非管理员终端执行 portproxy add 必然触发 UAC 拒绝，必须 `Start-Process -Verb RunAs`
3. PS 5 .ps1 文件 Write 工具剥 BOM + IDE 重新保存叠 BOM，最终触发 `assignment expression is not valid`，浪费多次试跑

已在项目级 `.trae/skills/windows-portproxy-troubleshoot/` 固化为 skill，含：

| 文件 | 作用 |
|------|------|
| `SKILL.md` | 三步收敛（证据 → 归类 → 建规则）+ 9 条反模式 |
| `scripts/portproxy_probe.ps1` | 自包含只读探针，4 段输出：iphlpsvc / portproxy / 监听 / HTTP |

probe 脚本实跑 EXIT=0，8734→8080 规则识别、PID 归属、HTTP 三段 fallback 全部正常。

## 持久化与重启后

portproxy 规则存于 `HKLM\SYSTEM\CurrentControlSet\Services\PortProxy\v4tov4\tcp`，**系统重启自动保留**。iphlpsvc 启动类型已确认为 `Automatic`，不依赖登录态。

但需注意：
- Docker Desktop / WSL2 升级后 8080 监听进程可能重建（PID 变化属正常）
- nginx 容器若重启，需额外用 `docker ps` + `docker logs ai-portal` 确认后端恢复
