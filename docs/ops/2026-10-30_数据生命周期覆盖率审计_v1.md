1. `metadata_consistency` 的 store 校验/qualification 判定依赖 lifecycle（planned/deprecated 可豁免缺失检查）→ 缺字段时**多算欠账**、真问题被淹没；

## 三、整改方案（建议由数据线执行，关羽出工具+审计）

### 3.1 四态定义（对齐治理方案 §5.3）

| 状态 | 含义 | 处置 |
|---|---|---|
| `active` | 产线/研究在用 | 正常维护、纳入新鲜度/备份 |
| `planned` | 已登记未启用 | 不参与缺失检查 |
| `deprecated` | 停用但保留 | 90 天后转 archived；删除前必须影响面报告 |
| `archived` | 归档只读（压缩） | 不参与产线检查；保留期按域 |

### 3.2 批量补登顺序（建议 3 批）

1. **第 1 批（机械可判，~233 张）**：`xtcloud` 170 + `tushare` 62 → 统一 `active`（主源行情/财务），脚本批量写入 + 校验；
2. **第 2 批（需确认，~13 张）**：xueqiu 3 缺失、cnopendata 6、crypto/guba/legacy/pg 各 1 → 数据线逐域确认 active/deprecated；
3. **第 3 批**：`deprecated` 表的 90 天转 archived（含影响面报告）。

### 3.3 变更纪律

- catalog 修改 = 数据线会签 + 数据根互斥日志（先读 `C:\Temp\kg_sync_task.log`、完成后补记）；
- 每次批量补登后跑：`python tools/datawarehouse/metadata_consistency.py --json`（必须仍 PASS）+ `lifecycle_coverage.py --check`；
- 不接受"无 lifecycle 新增表"（登记表模板加必填字段）。
