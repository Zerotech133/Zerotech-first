## 一、定案结论

**「删除者」并非恶意进程，且无法归属到单一 Windows 进程——因为删除动作根本不发生在 Windows 侧。**

抹除路径有两条，均为本地团队（Trae agent 线）自己的既定做法：

| 路径 | 出处 | 机制 |
|---|---|---|
| ① 幽灵同步抹除 | `.trae/skills/system-task-deploy/references/playbook.md` §6-9 | VM/沙箱层对「VM 层无此文件」的磁盘文件稍后抹掉；playbook 原文："docker base64 写入的文件可能被幽灵同步稍后抹掉（VM 层无此文件时尤甚）" |
| ② docker alpine 清理纪律 | 同 playbook §12-3 | "沙箱删真实磁盘文件可能删不掉时，用 docker alpine 挂载后 `rm -rf`"——删除发生在容器内，Windows 侧查无进程、无句柄、无时间戳归属 |

**「恢复者」=「AI工作站每日备份」计划任务本身**（注册 2026-09-12，SYSTEM + Highest）：

- 任务 XML Action 实证：每日 03:00 从 `HKLM\SOFTWARE\AIStation\BackupDeploy`（part1+part2, base64）读源 → `[IO.File]::WriteAllText()` **覆盖写回** `E:\老田的AI助手\jev-eval\backup_daily.ps1` → dot-source 执行
- playbook §6-9 原文："权威源在注册表时无运营影响——**下次 SYSTEM 运行自动回写重建**"；任务模板注释首行即 "ghost-sync proof"
- 这就是「反复消失→反复出现」的完整循环：幽灵同步/容器清理抹掉 → 次日任务回写重建

**为什么此前查无删除者**：两条抹除路径都绕过了 Windows 进程表（一个在 VM 层，一个在容器内），ProcMon 在宿主侧观察本来也抓不到——主动注册表取证路径是对的。
