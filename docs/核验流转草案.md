## 0. 角色边界（再钉一遍）

本席（OSINT1·马良）在"对账→核验"链路中的职责边界：

- **做**：跑 `rumor_verification.py` 生成底表、维护字段结构、做跨轮增量对照、保证溯源链（link/原文 id）完整。
- **不做**：不填 `verification` 栏任何字段；不写任何"已证实/已证伪/可信度"结论；不替分析岗裁事实。
- **流转**：底表生成后交给分析岗执笔核验、A0／老田复核裁定（QA1 复核方法，INTEL0 只登记流转）。本席止于数据与判据。

## 1. verification 栏字段语义与填写格式

底表每 code 的 `verification` 对象结构（L2 已预留）：

| 字段 | 类型 | 取值 / 格式 | 填写方 | 说明 |
|---|---|---|---|---|
| `status` | str | `pending` / `verified` / `debunked` / `partial` / `needs_more` | 分析岗 | 初值 `pending`（本席生成）；其余枚举由分析岗填 |
| `by` | str | 姓名/工号 | 分析岗 | 执笔人 |
| `note` | str | 自由文本 | 分析岗 | 结论依据摘要（附引用 code、时间、来源），**须标注 as_of 时刻** |
| `admiralty_code` | str | NATO 格式如 `B2`（A-F × 1-6 二维） | 分析岗 | 信源可靠性 × 信息可信度，**二维独立评估**（高可靠源也会错） |

枚举含义（建议，待裁定）：
- `verified`：两端素材 + 第三方数据互证，可认定为事实。
- `debunked`：官方渠道已澄清 / 与公开数据矛盾，认定为不实。
- `partial`：部分要素属实、部分存疑。
- `needs_more`：两端素材不足，需扩源或等公告。

`admiralty_code` 基线参考（见 `docs/source_track_record.md` §六 可靠性基线表）：
交易所公告/官方回复 = A；主流财经新闻 = B；机构研报 = B/C；雪球大 V = C/D；股吧/淘股吧散户 = E/F。
**注意二维独立**：A 源也会出错（如公司回复口径滞后），C 源也可能报对；填 `admiralty_code` 时两个维度分开评。

## 3. 流转流程（建议）

1. 本席跑 `rumor_verification.py` → 生成 `reconciliation_<时刻>.json`（status 全 `pending`）。
2. 分析岗取**最新**一轮文件，对 `codes_with_both > 0`（两端齐备）的 code 逐一核验，填 `admiralty_code` + `note`，`status` 置相应枚举。
3. A0／老田复核签字（`by` 记录），对 `debunked`/`verified` 结论负责；INTEL0 登记流转与台账，不代签。
4. 结论回写同一文件的 `verification` 栏；本席下一轮增量对照时只比对 summary 六项，**不触碰 verification**。

> 仅官方 / 仅传闻的 code（`codes_official_only` / `codes_rumor_only`）暂不进入核验主流程——无两端对照素材，纳入"线索池"供分析岗按需调取，不强制填 verification。

## 4. 触发频率（建议，归上级裁定）

| 选项 | 说明 | 取舍 |
|---|---|---|
| 每周一轮 | 固定节奏，覆盖全量两端齐备 code | 稳，但 102 只存量可能积压 |

## 5. 流程风险与待改进（已识别，列待裁定）

**风险 R15-1（重跑覆盖）**：`rumor_verification.py` 全量重跑时按时间戳生成**全新**文件，旧轮已填的 `verification` 不延续。若分析岗在旧轮填了结论、本席又跑一轮，结论丢失。

建议改进（待 A0／老田裁定是否做）：`rumor_verification.py` 增加"状态合并"——重跑时从上一轮 `reconciliation_*.json` 读取已填 `verification`，按 `code` 合并进新文件（保留历史核验，仅增量更新两端素材计数）。

**风险 R15-2（时效漂移）**：核验结论有时效性（公告/行情变化后旧结论可能失效）。要求 `note` 必须带 `as_of` 时刻，且每轮复核时显式确认旧结论是否仍有效。

## 6. 局限性声明

- 本草案为**治理流程框架**，不含任何研判结论；所有事实裁定归 A0／老田（分析岗执笔、QA1 复核方法）。
- `admiralty_code` 基线表（`source_track_record.md`）初期"已验证"列全 0，待分析岗回填，本席不编造数字。
- 台账管"数据在哪"、本草案管"数据怎么核验"，二者拼成完整治理链；不替代任何研判系统。
- 未采用项：本草案未涉及自动研判/模型打分，纯人工流转；若未来上模型辅助，须另行裁定并接入 admiralty_code 标准。
