## §0 边界红线（贯穿全文，违者评审门拒收）

### 红线 1：调度本体绝不进 Hermes（K-ORG-112 §3 第 3 条）

- 事件总线**只做「上报与分发」，不做定时**。产线任务的触发时机、命令行、计划任务注册面**一个字节都不动**。
- 推论落点：①事件 hub 选型**否决 Hermes crons 方案**（见 §4 方案 C）；②hub 落 8091 侧，8787 门面只有只读查询转发；③分发侧只做「事件 → 卡片/告警队列」的投影，不回写执行面、不做任何调度决策。

### 红线 2：8091 全链只读投影红线不破——「推方向」为何不破坏「联动层零主控改动」原则

现状 8091 全部端点是「hub → 产线」的**拉**（只读投影：observe/execution/brief/evolution/gate/tickets 均为 8091 读产线数据文件）。R6 新增「产线任务 → hub」的**推**（POST /api/events/ingest）。方向反转，须论证不破红线：

1. **写事件的主体是产线任务自身，不是联动层**。产线脚本在跑完自己的正事之后，追加一行事件上报（旁路写，类似它本来就在写自己的 last_run.log / shadow_ledger.jsonl）。联动层（8091）只是**被动接收方**——「谁写」没有变，变的只是这条旁路账本的读取方式从「轮询拉」升级为「推送交」。
2. **先例已在册**：observe 账本 `agent_platform/data/llm_tool_audit.jsonl` 本就是产线侧写、8091 读（api_flow.py:94 注释「写侧单源不另立账」）。R6 事件流与它同构：执行面自证、联动层被动落账（append-only jsonl），只是落账动作由产线主动推到 8091 端点，省掉轮询间隔的时延。
3. **「零主控改动」保护的是调度权**：事件上报不改触发时机、不改命令行、不改失败处置、不产生任何回写执行面的通道（8091 ingest 端点只落账不派单）。调度器（计划任务本体）与联动层之间**仍是单向读+被动收**，无控制回路。
4. **fail-safe 方向**：8091 挂 → 产线 emit 失败时本地暂存不阻塞主流程（§7 风险 5），联动层挂 ≠ 执行面挂（K-ORG-112 门面原则反向适用）。

### 红线 3：演示不落真仓

M3 新产线试接一律演示隔离环境（M5 刀 2 判例），验证通过前不落真仓、不碰真产线脚本。

**「三处改动」实证**：每接一根新线 = ①新建 connector py + routes.py 挂载段加路由（转调线）②8091 侧白名单/端点登记（白名单）③console.html 加卡片 HTML + `loadXxx()` 函数 + `setInterval`（卡片）。这就是 R6 验收要对齐的现状基线。

### 1.2 console.html 卡片接线方式（实读）

`static/console.html` 内联定义数据加载函数 `loadPurify/loadPulse/loadAlerts/loadObserve/loadExecution/loadTickets/loadEvolution/loadGate/loadBrief/loadAssets` 共 10 个，联动层/驾驶舱相关 7 个。统一模式：`loadXxx()` → `api("/api/<线名>/...")` 打 8787 自身端点 → 8787 connector 转调 8091 → 渲染卡片；`setInterval` 按 5s-60s 轮询（L865-869）。**卡片是纯前端呈现层，无法从配置自动推导渲染逻辑**——这是 §3 三合一中「卡片只能约定」的根本原因。

### 1.3 8091 白名单面（实读）

- `portal/execution_manifest.json`：R1 执行健康总线白名单，**21 任务**（含 2026-10-18 新登记的 AI工作站执行失败巡检 / AgentRetrospectBrief），每任务含 cadence/grace 实测回填值。「manifest 即白名单：只投影本清单任务」。
- `portal/api_flow.py` RERUN_OK（L79-87）：**17+3=20 任务**硬编码 Python set，服务端强制（白名单外 400 + caller 归因落 observe 账本），AgentMondayCheckpoint 复盘档只读明确不进。**这就是「Paperclip v1 口径」的现行实体**：白名单即配置/常量、服务端强制校验、拒绝时明确报因并归因。

### 1.4 8097 是什么（实读）

`portal/push_admin_server.py`：**推送中台（127.0.0.1:8097）**，注释自述「消息触达底座，商业化入口」。ThreadingHTTPServer，PORT=8097，能力：推送渠道编排（push_flow）、计量统计、sources 健康聚合（8097/8099/8095 三源探活）、统一日报。是**触达（往外推给人）**枢纽，不是**事件汇（往内收自产线）**枢纽。

### 1.5 Hermes crons 子系统盘点（实读）

`hermes-webui-next` 内建 cron 调度器：routes.py 含 cron job 运行时（`_cron_job_subprocess_main`/`_run_cron_job_in_profile_subprocess`，子进程隔离 per-job profile 执行）、panels.js `loadCrons` 管理面板。能力完备：cron 表达式、手动触发、会话接线、持久化。**当前零使用**。定性：它是「门面进程内的 Agent 会话定时器」，能力虽全，但把它当事件 hub 违反红线 1（见 §4 方案 C），仅可作为远期「门面内低频自检」候选，与 R6 无关。

## §2 事件 schema（R6 数据面定稿）

### 2.1 事件信封

```json
{
  "event_id": "sha256(source|type|run_key|ts_bucket) 截 24 hex",
  "type": "task_fail",
  "source": "agent_shadow_daily",
  "ts": "2026-10-18T17:10:03+08:00",
  "caller": "task-agent_shadow_daily",
  "payload": { "task": "AgentShadowDaily", "run_key": "2026-10-18", "severity": "P1", "summary": "...", "detail_ref": "agent_platform/data/shadow/last_run.log" },
  "schema_ver": "r6.v1"
}
```

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| event_id | str | 服务端按幂等键重算比对 | **幂等键**（§7 风险 2）：`sha256(source|type|run_key|ts_bucket)`，ts_bucket=事件自然桶（如日期/小时）。客户端重算不一致→422 |
| type | str | 枚举，见 2.2 | 双白名单之一 |
| source | str | 产线 slug（`[a-z0-9_]+`），须在 event_manifest.json 注册 | 双白名单之一 |
| ts | ISO8601 +08:00 | 必填 | 事件发生时刻（非上报时刻） |
| caller | str | `task-*`（产线任务自报）/ `hermes-*`（门面）/ `ops-*`（人工），循 K-ORG-109 归因 | 落 observe 账本同款归因 |
| payload | object | 必含 `task`（计划任务名，可与 execution_manifest 交叉引用）+ `severity` | severity ∈ {P0,P1,P2}，驱动分发分级 |
| schema_ver | str | 固定 `r6.v1` | 批四上收时兼容判别 |

### 2.2 type 枚举（首批，冻结于 M1；扩枚举=改 manifest 常量，评审门）

| type | 语义 | severity 典型 | 分发 |
|---|---|---|---|
| task_run | 任务跑完（含结果码） | P2（0）/P1（非0） | console 事件流卡 |
| task_fail | 任务失败/超期 | P1，自愈类 P0 | 告警 OPEN 队列；P0 推飞书 |
| task_recovered | watchdog 拉活成功 | P2 | 事件流卡 |
| task_recover_failed | **拉活失败**（R3「自愈失败升级 P0」判例） | P0 | 飞书 + OPEN |
| brief_ready | 复盘简报产出（R5） | P2 | 观察季卡快讯 |
| artifact_ready | 产物归档完成 | P2 | 事件流卡 |
| alert_open / alert_close | 告警开/闭（R3 联动） | P0/P1 | 告警指挥台 |
| rerun_refused | 重跑被幂等阀/白名单拒（R4 观测） | P2 | 事件流卡 |

### 2.3 白名单校验口径（同 Paperclip v1 / RERUN_OK 判例）

**双白名单交叉**：`source ∈ event_manifest.sources` **且** `type ∈ 该 source 的 event_types[]`——两者任一不过 → 403 + caller 归因落账 + 明确报因（含当前合法集摘要，同 api_flow.py L664-666 现行报文格式）。服务端强制，客户端校验仅作提示不作防线。白名单即配置（manifest 文件），不像 RERUN_OK 硬编码——这是对 v1 口径的唯一显式升级，升级理由：验收要求「≤1 处配置」，硬编码 set 无法配置化。口径精神（服务端强制/拒绝报因/归因）原样保留。

## §3 一条配置三合一：event_manifest.json

### 3.1 选址：新建 `portal/event_manifest.json`，不扩 execution_manifest.json

理由：①职责分离——execution_manifest 是 R1 **拉式投影**白名单（21 任务 × cadence/grace 语义），event_manifest 是**推式上报**白名单（source × event_types × 分发语义），混排会让一份文件背两套语义；②execution_manifest 由 R1 总线轮询消费，事件面由 ingest 端点消费，消费方不同；③两文件用 `match_task` 字段互相引用，保持可交叉审计。

### 3.2 schema（r6.v1）

```json
{
  "version": 1,
  "updated": "2026-10-18",
  "note": "R6 事件总线白名单（manifest 即白名单）。一条 source = 一条产线接入：8091 ingest 端点自动放行；8787 代理与 console 卡片为约定生效。",
  "sources": [
    {
      "source": "agent_shadow_daily",
      "match_task": "AgentShadowDaily",
      "event_types": ["task_run", "task_fail", "task_recovered", "brief_ready"],
      "card": { "panel": "observe", "title": "影子链事件" },
      "proxy_route": { "path": "/api/event/agent_shadow_daily", "upstream": "/api/events/query?source=agent_shadow_daily" },
      "enabled": true,
      "note": "首批收编：影子链四事件"
    }
  ]
}
```

### 3.3 三合一生效矩阵（哪些真自动、哪些只是约定）

| 环 | 生效方式 | 自动化程度 | 说明 |
|---|---|---|---|
| ① 8091 事件接收放行 | **真自动** | 加配置即生效，零代码 | ingest 端点通用化：每次请求现读 manifest 校验 source/type（低频写，现读成本可忽略，免缓存失效问题）。这是三合一里唯一能全自动的一环 |
| ② 8787 代理路由 | **约定 + 一次性通用转发器** | 半自动 | M1 在 8787 建一个**通用**事件查询转发器：`/api/event/<source>` 统一转发 8091 `/api/events/query?source=<source>`，路径规则由 manifest 的 proxy_route 约定。之后新产线**不再改 routes.py**——URL 按约定拼即可查。一次性开发成本在 M1 支付 |
| ③ console 卡片 | **只是约定** | 不自动 | 卡片是呈现层：字段渲染、阈值染色、布局均无法从 `{source, event_types[]}` 推导（loadExecution 的绿红格逻辑 ≠ loadBrief 的大卡+历史列表）。**降险设计**：M1 提供一张**通用「事件流卡」**（按 manifest 枚举全部 source 的最近事件，统一行式渲染）作为新产线默认零成本展示；专用卡（如执行健康格、简报大卡）仍需手写 loadXxx——但专用卡属呈现增强，不计入「接入联动层」验收口径 |

**验收对齐**：新产线接入 = 只加 event_manifest.json 一条 → ①自动放行 ②按约定 URL 可查 ③通用事件流卡立即可见。三处变一处达成；要 richer 呈现再手写专用卡（可选增强，非接入必需）。

## §5 与批四 message_hub 的关系（分工切面）

K-ORG-112 §7 批四 =「message_hub 骨干（K-STOCK 线阶段 2）+ Hermes 策略面板」，待办另单。切面如下：

| 件 | 归属 | 说明 |
|---|---|---|
| hub 进程形态、订阅/分发模型、PG NOTIFY 事件队列、Hermes 策略面板 | **批四** | R6 不做订阅者模型、不碰 PG NOTIFY、不做策略面板 |
| 事件 schema（r6.v1 信封+枚举）、双白名单口径、幂等键 | **R6 定稿** | 批四上收时 schema_ver 向前兼容 |
| event_manifest.json 三合一、8091 通用 ingest 端点（过渡期 hub） | **R6** | 即批四的**预置数据面**：事件生产方与查询面先跑通，骨干到位后换分发引擎不换接口 |

## §6 分期落地步骤（Gate 0 后；每步量级与回滚）

| 期 | 内容 | 量级 | 回滚 |
|---|---|---|---|
| **M1 骨干** | event schema 冻结（§2）+ event_manifest.json（首批收编 7 线对应 source：agent_shadow_daily/agent_chief_push/agent_shadow_eval/alert_chain/push_admin/…）+ 8091 `POST /api/events/ingest`（双白名单+幂等去重+append-only jsonl 落 events/）+ `GET /api/events/query` + 8787 通用事件转发器 `/api/event/<source>` + console 通用事件流卡 | 1.5-2 天 | 删 8091 挂载 1 段 + 8787 转发器 1 段 + 通用卡 1 张；events/ jsonl 保留只读不删（审计资产）；execution_manifest/R1 全程不动 |
