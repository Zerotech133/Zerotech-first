# 零界 · 集团统一搜索：方案与研发计划 v1

- 日期：2026-11-05
- 状态：方案稿（未改代码、未开实施单）
- 口径：按“集团级统一搜索”理解；若只是要一份搜索研发计划、不涉及多组织，P0/P1 仍可直接用，P2 可裁剪。
- 设计约束：复用现有 8734/8091/8097/8787 与 KG/KB/DW 资产；不建第二认证、不建第二事实库；搜索索引是**可重建的派生层**，不是新的事实源。

## 0. 结论先行

不要做“又一个搜索框”，做**集团统一检索与问答层**：

1. **一个入口**：网页 `/search`、H5 `/m/search`、飞书机器人 `搜 …` 三个入口，共用一套 API。
2. **多源融合**：飞书文档/知识库/消息、零界新闻、KG 事件图谱、KB 语料、数据仓、量化报告、个股代码。
3. **先检索后回答**：默认只返回证据和跳转；只有显式“回答”模式才调本地模型，且必须带引用。
4. **权限先于检索**：候选集在检索时就按用户/群/组织过滤，绝不“先搜出来再遮”。
5. **分阶段**：个人 P0 → 内部测试群 P1 → 一个部门 P2 → 集团多组织 P3。

预计：
- P0 个人版：**5–7 个工作日**
- P1 内部测试群：**2 周**
- P2 单部门集团试点：**3–4 周**
- P3 多组织/全集团：**6–8 周**（依赖 Feishu 管理权限与 ACL 源）

## 1. 现状盘点：已有搜索能力与缺口

### 1.1 已有能力

| 能力 | 入口/实现 | 现状 | 可复用性 |
|---|---|---|---|
| KB 问答 | `GET /api/kb/qa`（`portal/api_kb_qa.py`） | 已接线 8091；retrieval/single/multi；topk、引用 `[S#]`、citation_check、10 分钟缓存、限流 | 高：作为“知识问答”底座 |
| KB 只读 | `/api/kb_read/search`、`/api/kb_read/unit/<id>` | 单元检索/阅读 | 高 |
| 数据仓检索 | `GET /api/dw/search`（`portal/api_dw_registry.py`） | 数据集/契约/文件关键词检索；带 data_date/stale/空结果三态 | 中：搜“数据集”而非正文 |
| KG 图谱检索 | `/kg/csearch/{q}`、`/kg/events/search` | 实体搜索、事件图谱、下钻 doc_texts | 高：实体/事件类查询 |
| 个股检索 | `api_screen.py`/`api_portfolio.py` | 代码/名称检索、手动建仓搜索 | 高：股票类查询 |
| 投委会检索 | `council_ops.search_all()` / `/api/council/search` | 已退役信号源；历史页面保留 | 低：不纳入默认结果 |
| 飞书机器人 | `portal/feishu_bot_ws.py` | 消息收发/卡片回调 | 中：可加 `搜` 命令 |
| H5 | `portal/m/*` | 16 页，无统一搜索页 | 待建 |

### 1.2 关键缺口

1. **没有统一入口**：`/search`、`/api/search` 均不存在；用户只能分别去 KB、KG、DW、选股页。
2. **没有跨源排序**：各源分數不可比；重复内容（新闻转载、公告同文）无去重。
3. **没有统一元数据**：来源、作者、发布时间、数据时点、权威度、原文链接不统一；引用无法追溯。
4. **没有权限模型**：KB/KG/DW 目前是内部只读；飞书文档/群消息的可见性没有 ACL 映射；不能直接做集团搜索。
5. **没有飞书内容索引**：当前 Feishu 只做分发（发消息/卡片），没有文档、Wiki、Base、群消息的增量索引。
6. **没有评测集**：无法证明“搜得准”；也没有 empty-result、citation 错误的监控。
7. **没有检索可观测性**：query、点击、无结果、延迟、权限拒绝都没有统一日志。
8. **公开 H5 断链**：`m_link` 停用、`urls.json` 失效；搜索 H5 即使做完，外网/手机仍打不开（见 2026-11-05 分发体检）。

## 2. 目标与非目标

### 2.1 目标

- 一个 query 能覆盖多源：**先搜到**、**看得懂**、**点得回原文**、**答得出且有引用**。
- 个人先用（A0），再内部测试群，再一个部门，最后集团多组织。
- 输出统一 envelope：`hits[] + citations[] + facets + next_cursor`，前端/机器人共用。
- 任何回答必须能回到来源：`source / title / url / ts / author / snippet / score / permission_scope`。

### 2.2 非目标（本阶段不做）

- 不做公开互联网搜索（不替代 Google/必应）。
- 不替代飞书官方搜索；只做“零界侧统一检索 + 问答 + 跳转”。
- 不在未授权情况下索引全集团消息；消息索引必须按用户 OAuth 可见范围。
- 不建第二认证中心、不建第二业务事实库。
- 不把“检索结果”直接当“投资建议”。

## 3. 信息架构与查询模式

### 3.1 四种查询模式

| 模式 | 例子 | 返回 |
|---|---|---|
| 找东西 lookup | “昨天的原油周报”“002463 公告” | 排序后的 hit 列表 + 跳转 |
| 看态势 explore | “本周半导体发生了什么” | 分组/时间线/实体聚合 + hit |
| 问问题 ask | “二买策略最近胜率如何，依据是什么” | 答案 + 逐条引用 + 原文跳转 |
| 去操作 action | “打开 KG 事件页/新建订阅” | 深链/动作建议（不自动执行写操作） |

## 4. 目标架构

```text
[入口层]
  Web /search      H5 /m/search      飞书机器人 “搜 …”
        \               |                /
         \_____________ | ______________/
                       v
[查询服务 query-service]
  意图识别 → 查询改写 → 源路由 → 检索 → 去重/重排 → 权限过滤 → 答案/引用
        |                 |                    |
        v                 v                    v
[派生索引 search-index]  [源适配器]          [权限/审计]
  FTS5/BM25 + 元数据     Feishu Docs/Wiki    ACL snapshot
  + 可选向量             Feishu Msg/Base     query log
  + ACL 字段             News/KG/KB/DW       click log
                         Quant reports       deny log
```

### 4.1 索引模型（派生、可重建）

每条文档一条记录：

| 字段 | 说明 |
|---|---|
| `doc_id` | 稳定 ID：`source:type:native_id` |
| `source` | feishu_doc / feishu_msg / feishu_base / news / kg_event / kb_unit / dw_dataset / quant_report / file |
| `tenant_id` / `org_path` | 集团/组织；P0 可为空 |
| `title` / `content` / `snippet` | 正文与摘要 |
| `ts` | 业务时间（发布时间，不是入库时间） |
| `author` / `owner_id` | 作者/所有者 |
| `url` / `deep_link` | 原文入口（飞书/门户/H5） |
| `acl` | `{visibility, users[], groups[], departments[]}` 的规范化快照 |
| `checksum` / `version` | 去重/增量更新 |
| `lang` / `entities` | 语言、股票/公司/行业实体 |
| `source_rank` | 源权威度先验（公告 > 新闻转载 > 群聊） |
| `indexed_at` | 索引时间 |

### 4.2 索引技术选型

- **P0**：SQLite FTS5（`search_index.db`）+ 元数据表；不引入新服务；索引全量可重建。
- **P1**：若数据量/并发上来，用现有 PostgreSQL 的 FTS + `pgvector`（不新建数据库实例）；用适配器切换。
- **P2**：再评估 OpenSearch/Elasticsearch；不作为 P0 前置。
- 不把索引当事实源：任何索引都可从源重建；源删除要写 tombstone。

### 4.3 检索与排序

1. 查询理解：中文分词（jieba）；识别股票代码/公司/时间/来源意图。
2. 多路召回：FTS BM25 top 50 + KG 实体 top 20 + 语义向量 top 30（P1 再上）。
3. 去重：标题/正文 SimHash；同源转载合并，保留最早/最权威。
4. 重排：`score = 0.55*BM25 + 0.20*authority + 0.15*recency + 0.10*entity_match`（P0 可调）。
5. 权限过滤：在召回阶段带 ACL 条件；不允许先返回再隐藏。
6. 回答：仅 `mode=ask` 调本地 Qwen；强制带引用；引用不足则返回“检索到 N 条，但不足以回答”。

### 4.4 飞书连接器

- 文档：Feishu Docs/Wiki/Base 的元数据 + 正文；走应用 tenant token + 用户 OAuth（按可见性）。
- 消息：只索引用户授权范围内的群/单聊；优先用 **user access token** 的搜索/历史接口，避免租户级越权。
- 增量：事件订阅（doc edited、message received、chat member changed）+ 定时补偿；删除/移出群 → tombstone。
- 权限：`chat_id`/`department_id`/`user_id` 映射到 ACL；群成员变化要在 5 分钟内反映。
- 风险：飞书应用 scope、消息历史权限、跨境数据合规；需要 A0/管理员确认后再开。

### 4.5 现有资产复用

- `api_kb_qa`：作为 `ask` 的 KB 子答案源，不重复造 RAG。
- `api_dw_registry`：`source=dw_dataset` 的元数据 hit，不索引大表正文。
- `kg/csearch`、`kg/events/search`：作为 `source=kg_event` 的实体/事件召回。
- `api_screen`：代码/名称精确命中，优先级最高。
- `api_common` 路由：统一挂 `/api/search`；不新开端口。
- H5：新增 `portal/m/search.html`，复用 tokens/m.css/m-os.css；不破坏 page_shell。
- 飞书机器人：新增 `搜` 命令，走 `/api/search`，返回卡片+深链。

## 5. 权限、安全与合规

- 认证：沿用 8734 现有登录/portal token；不建第二认证。
- 授权：以源系统 ACL 为准；索引存 ACL 快照；查询时用当前用户身份过滤。
- 最小权限：P0 只索引 A0 自己的文档/群；P1 只索引 pilot 部门；P2 才谈全集团。
- 审计：记录 query（脱敏）、sources、hit IDs、权限拒绝、点击；保留 90 天。
- 防泄漏：权限测试用例必须包含“用户 A 搜不到用户 B 的私聊/文档”；0 泄漏是上线门禁。
- 注入：检索内容按数据对待，不拼进系统提示；回答引用原文，不执行原文指令。
- 公开：不把搜索页暴露到公网；手机预览走命名隧道 + token/OIDC（与分发体检同一安全方案）。

## 6. 研发阶段与验收

### P0：个人统一搜索（5–7 个工作日）

范围：
- 源：news、KG events、KB units、DW datasets、quant reports、个股代码 + A0 自己的 Feishu 文档（先只读自己的）。
- 入口：`/api/search`（检索）+ `/search` 桌面页 + `/m/search` H5 + 机器人 `搜` 命令。
- 50 条个人评测 query；引用/跳转可点。
- 只读，不写任何业务数据；索引本地派生。

验收：
- Recall@5 ≥ 75%（P0 基线，P1 提到 80%）。
- 引用可回原文 ≥ 95%。
- p95 检索 < 1.5s；空结果有明确“没找到/权限不足/源未接入”三态。
- 0 权限泄漏（P0 只有 A0 自己，仍要跑用例）。
- 不改变现有推送/生产账本。

### P1：内部测试群（2 周）

- 接 Feishu Docs/Wiki/Base + 内部测试群消息（按成员可见）。
- ACL 映射、群成员变更同步、tombstone。
- H5 搜索页 + 机器人结果卡；检索/点击/无结果日志。
- 100 条评测 query；pilot 用户 3–5 人。

验收：Recall@5 ≥ 80%；ACL 越权 0；索引延迟 < 5 分钟；p95 < 2s。

### P2：单部门集团试点（3–4 周）

- 接部门文档/知识库/群；SSO/OIDC 与部门 ACL；多租户字段。
- 搜索分析面板（top query、无结果、点击率）；反馈按钮。
- 试点部门 20–50 人；SLO 与回滚开关。

验收：权限泄漏 0；p95 检索 <2s；答案引用准确率 ≥95%；用户周活/点击率有基线。

### P3：集团多组织（6–8 周）

- 多组织/多租户、跨组织授权、数据分级、保留策略。
- 与集团 IT/安全评审；容量与成本模型；容灾。
- 搜索运营：badcase 周清、索引巡检、query 改写迭代。

## 8. 风险与待拍板

### 风险

1. 飞书消息/文档权限 scope 不一定给全；没有 user token 就无法做“按人可见”的搜索。
2. ACL 映射错误会造成越权；必须做合成用户测试。
3. 索引延迟与删除同步：文档撤回/群移出后必须尽快删除。
4. 数据量/成本：全集团消息量可能远超本地 SQLite；P1 需评估 PG。
5. 质量：中文分词、转载去重、时间衰减、权威度权重都要评测。
6. 合规：集团数据分级、保留期、跨境；需要安全评审。
7. 入口分散：搜索页、H5、机器人三处要统一，不要做第四套。

### 待 A0 拍板

1. “集团”范围：只是 A0 + 内部测试群，还是真实集团多组织/多部门？
2. 首批数据源：Feishu 文档/Wiki/Base、群消息，哪几个先接？
3. 是否允许索引群消息（按用户授权范围）？保留多久？
4. 首个试点部门/人群是谁？
5. 搜索首页入口：独立 `/search`，还是先挂到 `/os-entry`/命令面板？
6. 是否接受 P0 先用 SQLite FTS5 派生索引，P1 再切 PG？

## 10. 附：与现有项目的关系

- 不是新建“第二入口”：搜索页挂 8734，H5 挂 `/m/search`，机器人在现有 WS bot 内加命令。
- 不是新建“第二认证”：复用 portal 登录/token。
- 不是新建“第二事实库”：索引是派生层，源仍在 Feishu/news/KG/KB/DW。
- 与 KG/KB 的关系：KG 提供实体/事件，KB 提供知识问答，搜索层做统一召回与引用；不重复造 RAG。
- 与分发系统的关系：搜索负责“找和答”，分发负责“推”；两者共用推送中台和 H5 鉴权，但互不替代。
