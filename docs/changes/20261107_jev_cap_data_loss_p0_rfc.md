# RFC 20261107：`--cap` 系统性丢数治理（P0 数据完整性）

> 状态：**草案，未落地任何生产改动，须老田批准后方可实施**。
> 事实来源：`docs/changes/20261107_jev_scope_notice_filter_rfc.md` §12（2026-11-07 只读审计，
> 全部数字落 `C:/Temp/*.json` 回读复核）+ §13 观测机制。
> 定位：修复的是**采集水位与截断语义**，与本线公告过滤（A/C）互不替代——
> cap 修复后公告过滤从「可选优化」变为「链路存活前提」（见 §6）。

---

## 1. 问题定性

`jev_feed` 采集层按 `--cap`（缺省 500）从 datamart 拉取公告，**按日期升序取最早 N 条，
其余全部丢弃**；且截断轮仍把水位推进到「窗口内最大日期」，中间日期的数据被永久跳过。
这不是限流，是**静默的、单向的、不可自愈的丢数**。

严重度：**P0（数据完整性）**。修复它不需要讨论收益——数据管道每天丢 45%–85% 的输入。

## 2. 证据摘要（2026-11-07 审计）

| 证据 | 数值 | 出处 |
|---|---|---|
| 24 轮 `jev_feed` 拉满 cap | 22/24（91.7%） | `C:/Temp/jev_cap_audit_facts.json` |
| `fetched=500 且 inserted=0` 空转轮 | 6 轮 | 同上 |
| `xd_notice` 单日入库 | 几乎恒为 500，且 1,511 条 `ts` 时分全 `00:00` | 同上 |
| 水位卡死 | 11-01→11-03 wm 恒 20261101，11-02/11-03 公告**零入库** | `jev_feed_night_and_cap_facts.json` |
| 上游真实单日量 | 618 / 1,516 / 3,411 / 1,866 / 959 | `jev_notice_upstream_verify.json` |
| 实际入库 | 0 / 0 / 500 / 500 / 500（丢 45%–100%） | 同上 |

**「每天 500 条公告」不是业务量，是从 600–3,400 条里截出的最早 500 条。**

## 3. 根因（代码级，四处叠加）

| # | 位置 | 缺陷 |
|---|---|---|
| R1 | `quant_backtest/datamart.py:616-618 / 675-678` | `sort_values(dcol, kind="stable")` 后 `df.head(limit)`：升序取最早 N 条，**丢弃方向固定**；且无亚日排序键（1,511 条同 `ts`），stable sort 每轮取同一批 |
| R2 | `news_collector/jev_feed.py:137` | `dm.read(alias, start=start, limit=cap)` 单页拉取，无游标/分页 |
| R3 | `jev_feed.py:163-169` | `max_date` 取窗口内可解析行的最大日期，不是「已连续处理到哪天」 |
| R4 | `jev_feed.py:328-334` | **截断轮（inserted=0）仍推进水位**——「排水/活锁破除」注释把重复窗口当成功 |
| R5 | `jev_feed.py:144-147` | 拉满 cap 只打 `WARN` 日志，无 `cap_hit` 指标、无告警、无观测暴露 |

叠加效应：R1+R2 造成截断；R3+R4 把截断**固化成永久跳过**；R5 让全程无信号。
单纯截断本可靠「1 天重叠回看」自愈，R3+R4 恰好把自愈路径堵死。

## 4. 修复方案（三选一或组合，按侵入度升序）

### 方案 ①（止血，最小）：截断轮不推水位 + cap_hit 可观测
> **修订（2026-11-07 实施时）**：字面「截断轮不推水位」经代码复核**会回归
> 2026-10-16 活锁修复**（`jev_feed.py` 主循环 ADV 注释与 `feed_source` 内注释：
> inserted=0 不推进 → 同一窗口无限重拉，实证 21:24/23:55 两轮）。故 ① 落地版
> **只做 R5 信号**（cap_hit 三路：runs.detail + stdout/stderr 留痕 + 飞书告警，
> 失败静默），R4 水位策略修正整体归方案②。
- ~~R4 反转：`inserted=0 且 fetched==cap` 的轮**不推进水位**~~（移入②，理由见上）；
- R5 落地：`runs.detail` 增 `cap_hit=true` 字段 + 飞书告警
  （`JEV_CAP_HIT_ALERT=0` 可关；feed 每日一轮，告警上限 ≤1 条/源/日）；
- 风险：水位可能长期卡住（正是现在的状态），但**不再静默丢数**，卡住本身成为显式信号。
- 改动面：仅 `jev_feed.py`（~45 行）+ 单测 6 项。**不碰 datamart、不碰水位策略。**
- 附加修复（实施中发现）：`jev_feed.py` 的 `sys.path` 两行 `insert(0,...)` 顺序交换，
  消除 `quant_backtest/jev_backfill.py` 对 `news_collector/jev_backfill.py` 的
  同名遮蔽（谁先导 jev_feed 谁踩雷，测试按顺序 25 errors 复现后定位）。

### 方案 ②（正解，推荐）：连续水位 + 稳定游标
- R3 替换：水位改为「已连续处理到的日期 + 行级游标（`_fetched_at` 或 url hash）」，
  不再使用 `max_date`；
- R2 配套：`dm.read` 分页（`limit=cap` + 游标条件），拉满当日才推进日期；
- R1 配套：`datamart` 排序键补亚日字段（`_fetched_at` 秒级），同日多批不重复取；
- 改动面：`datamart.py` 排序/游标、`jev_feed.py` 水位格式（**需兼容旧水位**：遇旧格式
  `YYYYMMDD` 按当日零游标处理）、`runs.detail`、历史补数脚本。
- 风险：水位格式迁移 + 入队量抬升（见 §5）。

### 方案 ③（治本，最大）：cap 语义重定义 + 按源配额
- `--cap` 恢复「轮内限流」本义：单轮最多 N 条、多轮推进直至当日清零；
- 增按源配额（公告/新闻分预算），防单源挤占；
- 改动面：②的全部 + 调度参数语义变更 + 文档。**在②稳定后再评估，不建议一步到位。**

## 5. 影响面（必须先知道的代价）

1. **入队量抬升 1.2–6.8×**：修复后 JEV 判读队列从 ~500 条/日涨到 600–3,400 条/日
   （上游真实量），Ollama 单槽判读时长同比例放大；
2. **方案 B 收益重算**： notice RFC §4「日省 500–700 条」的立项假设基于丢数管道，
   修复后须用全量样本重算（公告占比不变，绝对量放大）；
3. **A/B 误杀率结论作废重估**：notice RFC §3 的 18,685 条样本来自截断后 500 条/日，
   代表性有偏；
4. **历史补数**：11-02/11-03 零入库、其余日期缺口需一次性 backfill（估 6,000–9,000 条），
   须与 M3/夜批窗口协调。

## 6. 与公告过滤线的关系（依赖翻转）

当前：过滤是「省算力的可选优化」。
cap 修复后：**过滤是「链路存活的前提」**——3,400 条/日若全量进 9B 判读，单槽 Ollama
无法在夜窗内消化；公告模板（812 样本 0 误杀实测）承担的过滤量将放大 4–7×。
**因此推荐顺序：本 RFC 批准方案② → 实施前先验证公告过滤在真实轮次生效
（今晚 21:00 / 11-08 09:00 快照）→ 再动采集层。**

## 7. 回滚

- 方案①：还原 R4 一处 if + 观测字段，无数据迁移；
- 方案②：水位字段带版本号，回滚到旧格式按「丢弃游标、仅日期」降级读；
- 数据级：补数脚本按 `notice_date` 重放，幂等（url hash 去重）。
