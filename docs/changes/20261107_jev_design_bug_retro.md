## 一、BUG 清单与根因归类（按严重度）

### BUG-1【P1·已闭环】测试污染生产 trace 库 → 44.5% 假警报
- **现象**：`llm_request_fail_rate` 报 44.5%，`llm.call errors=1163`。
- **根因（设计缺陷：观测管道无测试隔离）**：`test_model_router.py` 用例把 `zhaoyun.test` 流量写进生产 `LLM_TRACE_DB`；`summary()` 无 `NON_TEST` 分组，测试失败被当生产故障计数。
- **修复**：测试用例 monkeypatch `LLM_TRACE_DB` 到 `tmp_path`；`api_trace_drilldown.py` `summary()` 增请求级失败率 + `NON_TEST` 口径。error_rate 44.5%→17.0%（余量为真实偶发）。
- **状态**：存在 → 已修复（commit `c8d8caa57` 内）。
- **设计教训**：可观测性管道必须一等公民区分「测试/生产」流量，否则告警可信度归零——这是比丢一条日志更危险的失效模式（**狼来了效应**）。

### BUG-2【P1·已闭环】feed 夜窗守卫吞掉粗筛（位置型设计 BUG）
- **现象**：`notice_skip=0`、`new_code_effective_in_prod=False`，A 方案落地后仍是 no-op。
- **根因（设计缺陷：新能力接入点未做控制流可达性分析）**：`judge_pending()` 第 204 行命中 `_in_night_window()` 直接 `return`，`prefilter_jev()` 调用段在第 244 行——21:45–07:05 轮次永远走不到。新增粗筛时插到了守卫 `return` **之后**。
- **修复（最小改动）**：不照搬 RFC §13.3(2) 的「整段前移」，改等价更小的 `_night_prefilter(kind, cap)`：夜窗只做零算力规则粗筛（只 `SELECT id,title`、safe 模板、写 `src=prefilter` neutral），`UPDATE ... AND (jev IS NULL OR jev='')` 不覆盖夜批已判结果，任何异常静默回退。**保住 OS-FIX-JEVFEEDNIGHT「夜窗不碰 Ollama」契约**，6 个夜窗回归单测锁死（含 `jev_judge_batch` 零调用断言）。
- **状态**：存在 → 已修复，36 项测试全过。
- **设计教训**：①给带 early-return 守卫的函数加能力时，先画控制流图确认「插入点可达性」；②历史契约（OS-FIX-*)必须转化为回归测试，而不是靠记忆守护。

### BUG-3【P1·已闭环】总开关缺省关闭 + 启动器配置矩阵漏项
- **现象**：位置修完仍 no-op；`jev_feed.py:212/300` 读 `JEV_PREFILTER` 缺省 `"0"`。
- **根因（设计缺陷：开关引入无「入口×开关」矩阵盘点）**：`jev_backfill_task.ps1:18`、`start_jev_night.ps1:11`、`night_batch.py:404` 都设了 safe，唯独 `start_jev_feed.ps1` 漏配；`jev_night_preflight.py:152` 的启动器强校验只覆盖已配置项——**校验器继承了同一个盲区**。
- **修复**：老田批 A，`start_jev_feed.ps1` 加 `$env:JEV_PREFILTER = 'safe'`（`Start-Process` 继承），`Parser::ParseFile` 校验。回滚：值改 `'0'` + §7 数据级 SQL。
- **状态**：存在 → 已修复（2026-11-07 07:30）。
- **设计教训**：新增环境开关时必须同步产出「入口×开关」矩阵并让 preflight 全量校验；否则「三缺一」是静默失效——不报错、不告警、只是永远不生效。

### BUG-4【P2·已闭环】过期注释误导生效路径判断（文档漂移）
- **现象**：复盘时按注释「daily 23:45」预判「今晚 23:45 首次夜窗粗筛」；实查 `Get-ScheduledTask` 发现 `JevFeed-Daily` 真实触发 **21:00**（早于夜窗 21:45），昨晚 LastRun 23:48 属延迟触发。
- **根因（设计缺陷：调度注释与事实源脱节）**：注释写于旧排程时代，计划任务改过时间没回写；「16/24 轮夜窗」的历史印象也由此而来。
- **修复**：RFC §14.3(2) 加勘误块 + §14.6(2) 判读口径更正 + 注释改为「daily 21:00 (stale comment noted)」。生效路径修正为双路径：准点 21:00 走正常路径粗筛，延迟过 21:45 走 `_night_prefilter()`——**两条都已打通，A 无论准点或延迟均生效**。
- **状态**：异常 → 已勘误。
- **设计教训**：**注释 ≠ 事实**。调度类叙述以 `Get-ScheduledTask` 实查为准；凡是基于注释做的推理，落地前必须用事实源核一次。

### BUG-5【P0·冻结待批】`--cap` 系统性丢数（数据完整性）
- **现象**：24 轮里 22 轮拉满 500；上游单日真实量 618/1516/3411/1866/959，入库多为 500/0；11-02/11-03 公告**零入库**。
- **根因（设计缺陷：限流参数被当总量预算）**：`--cap` 设计语义是轮内限流，实际承担了总量截断，且 cap 命中无任何告警/指标暴露。
- **修复**：未动（修 cap 会把入队量抬 1.2–6.8 倍，方案 B 需重算），已升级 P0 另立 RFC（§12/§13）。
- **状态**：异常 → 冻结待批。
- **设计教训**：任何截断类参数必须配套 `cap_hit` 可观测信号，否则丢数是静默的、只能靠事后审计发现。

### BUG-6【P1·已闭环】M3 锁争用与误判（并发设计）
- **现象**：`ollama_batch.lock` 争用；补跑脚本 round 2 judge 子进程挂 6 小时；17:25 一度误判 M3 僵尸并请求 kill（深夜复盘**撤回**，证实 M3 实际跑到 424 条）。
