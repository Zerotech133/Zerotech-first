## 二、归一方案三选项对比

评分口径：**改动面**（越小越好）、**可审计性**（越高越好）、**与军团 M4 能力层线 W22/W23 衔接成本**（越低越好）、**回滚难度**（越低越好）。评级为纸面评估，非实测。

### 选项① 维持两仓各自目录 + 显式映射表

**形态**：仓 A `capabilities/registry.json` 与仓 B `agent_platform/data/skills/skills.json` 各留各位；新建**一张**跨仓映射表（建议落 `docs/legion/` 侧或仓 A `capabilities/mapping.json`，落点待拍板），逐条登记「哪个 Skill slug ↔ 哪个 capability_id ↔ 是否同一物 ↔ 差异注记」。映射表**只登记不合并**。

| 维度 | 评估 |
|---|---|
| 改动面 | **最小**。只新增 1 份映射数据文件 + 1 个只读校验脚本；仓 A 军团 M4 能力层线 W22 四文件零改、仓 B 零改 |
| 可审计性 | **高**。映射表本身即审计物：谁映射到谁、差异注记、判缺原因全部留痕；巡检脚本可 diff「映射表 vs 两侧实际目录」发现漂移 |
| 与军团 M4 能力层线 W22/W23 衔接成本 | **低**。军团 M4 能力层线 W22 的 `registry.json` 槽位照原计划产；映射表是军团 M4 能力层线 W23 的**附加交付物**，不占 W22 目录占用权；与《M4 能力层 W22 供给面定义起草》§五「W23 派工时不得覆盖 W22 四文件」天然相容 |
| 回滚难度 | **低**。删映射表即回滚，零残留（军团 M4 能力层线 W22 已合入代码不动） |

**代价**：双目录长期并存，「同一能力两个真源」的漂移风险靠巡检脚本兜，不靠结构消除；老田若后续要求"一个真源"，本选项是过渡态而非终点。

### 选项② 主仓统一目录、digital-legion 只保留声明与注册面

**形态**：能力目录实体迁到仓 B（建议 `agent_platform/capabilities/`），仓 A `capabilities/` 退化为纯声明/校验代码面，目录数据经只读适配器跨仓读取。

| 维度 | 评估 |
|---|---|
| 改动面 | **最大**。需新建仓 B 目录 + 跨仓只读适配器 + 两仓 import 路径改造 + 两仓 `contracts` 异构字段处置（C3-a）+ `tests/` 根目录冲突处置（C3-b）+ 仓 A README「零依赖」原则改写 |
| 可审计性 | **最高**（结构上单一真源，审计面最短）。但**落地前审计风险最大**：迁移期双写不一致、字段丢失、Verdict 语义错配，都会在审计面最短的同时放大单点错误 |
| 与军团 M4 能力层线 W22/W23 衔接成本 | **高**。军团 M4 能力层线 W22 已合入 `3785940`（`registry.py` L26-33 `from capabilities.declaration import ...`、L241 `from contracts.strategy import StrategyAgent`、L107 `from adapters.shadow_intel import BLACKLIST_KEYS`）——三处仓内相对 import 在仓 A 仓根下成立，跨仓后需路径改写，**属改已合入代码** |
| 回滚难度 | **高**。跨仓 import + 字段映射一旦落码，回滚需同时回两仓；`contracts` 异构字段若已做转换，回滚是反向转换（易失真） |
