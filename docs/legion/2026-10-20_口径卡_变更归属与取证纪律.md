# 口径卡：变更归属与取证纪律（老田 2026-10-20 批准）

> 本卡为**治理口径**，不是建议。违反本卡的取证结论一律不得作为裁决依据。

## 一、归属以工单号为准，git 身份不作归属证据

**背景（实测）**：本仓 `git shortlog -sne --all` 显示提交者多身份并存，但**绝大多数提交共用 `laotian-agent <agent@zerotech.local>`**（2026-10-20 实测计数约 875，且**该计数为移动靶、每新增一提交即 +1**，引用时只写「绝大多数」不写具体数值），且身份与工位/人**无映射**（TF-20261020-06）。

**规则**：
1. 任何"哪个工位/哪个人做了这次变更"的结论，**只能**以以下三者之一为准：①工单号（如 `WO-TF-01`）②commit message 首段的工单标识 ③工位自证 + lead 复核。
2. **不得**以 git author/提交者姓名作为归属证据（无论多名、多统一）。
3. 无工单号的变更**视为无归属**，不得默认归属于在册工位。

## 二、账本侧与 git 侧不能互为佐证（同源）

owner 缺失诊断（TF-20261020-05）显示：即便某条工单 `owner` 写对了成员 ID，**其分支提交者也落在同一身份名下**，两侧同源，**无法互证**。

**规则**：涉及"历史数据是否正确补登/修正"的验收，**不得**用 git 侧作独立第二信源；无第二信源时须在验收记录中**显式写明该验证不可行**，不得含糊记为"已验证"。此即老田裁定"历史 254 条不补登"的隐性成本依据。

## 三、行号引用必须当场核实，禁止凭印象

**判例（2026-10-20，双向各一次）**：
- 工位 ws-own 曾凭印象写「`devtask.py:572` 有 `cwd=ROOT` 注释且与影子链同源」→ 实测该行实为 `print(...)`、`cwd=ROOT` 零命中，且定性也错（读取侧 CWD 依赖 ≠ 写入侧句柄占用）。工位自证并要求作废，lead 已复核入档。
- lead 曾称「本仓 git 提交者全为单一身份」→ 实测为多身份并存，属**过头表述**，已按实测更正。

**规则**：
4. 报告与台账中引用的**行号、字段名、commit hash**，须有当场核实动作（读取/查询命令）；**未核实的引用一律不得写出**，写错须**立即主动更正并作废**，不得"找补"。
5. 引用**崩溃/故障现场**时必须取**故障时刻版本**：`git show <故障前最后提交>:<文件>`。直接读现网文件会误判（影子链 1019 即因此差点查错，第 367 行现网已是另一段代码）。

## 四、跨轮次引用的追溯规则

6. 任何被后续证伪的结论，**须在原登记单内显式标注作废 + 写明作废理由**，不得静默删除（静默删除会让下一位接手者重踩）。
7. 跨工位协作时，**引用他工位结论须标来源**（工位名 + 诊断件路径）；无来源的转述不得进入台账与登记单。

## 五、诊断与实施的边界（沿用整改线，补充取证侧）

8. **诊断结论不等于修复授权**：诊断通过仅解锁"拟工单"，实施仍须凭单；涉生产包装器/计划任务/系统配置者另需老田明确批准。
9. **建议项不派工**：无复发证据的加固改造只登记为建议项，不占用实施资源（判例：MondayCheckpoint 进度文件改造判为建议项未派工）。

## 六、并发编辑与可导入性纪律（2026-10-20 WO-TF-03 事故固化）

**事故实例**：两个工位同时认领同一任务并并发编辑 `tools/devtask.py`（主建单链），无互斥机制，一度产生同名函数重复定义、常量重复，且其中一行缺右括号致 `py_compile` **SyntaxError** —— 该文件一度**无法导入**，若未被及时发现将随合并进入主干、全站建单崩溃。

**规则**：
10. **单一归属**：每张派工单必须明确**唯一工位归属**；共享任务列表中已被认领的单，其它工位不得重复认领同一文件的编辑权。
11. **同文件并发编辑须先声明互斥**：两个工位确需同改一个文件时，必须先在任务描述中声明互斥范围与交接时点，不得默认"我以为只有我在改"。
12. **可导入性是完成门槛**：任何 Python 文件改动后**必须通过 `py_compile` 才可报完成**，不得以"跑通了"或"测试过了"代替可导入性验证。
13. **残留检查并入复验**：复验方须检查是否存在同名函数/常量重复定义（并发编辑最典型的残留形态），不能只看 diff 是否"看起来对"。
14. **未提交改动是易失资产**：共享仓存在并行 worktree 合并时，未提交改动**可能被合并回滚覆盖**（已实测发生一次）。诊断/实施完成后应**立即提交**，不宜在仓内逗留等待复验；确需等待的，须先请 lead 决定是否入库。

## 七、防"静默回退"纪律（2026-10-20 WO-TF-03 复验追加）

**风险形态**：并行 worktree 合并可能把已入库的**功能改动一并回退**。对 `tools/devtask.py` 这类主链文件，后果不是"少个功能"，而是**校验静默消失、根因原地复发**——账本照常写、命令照常返回 0、无异常无告警，而**测试仍全绿**（因为测试不覆盖该新功能），要等到下游现象（晨会大面积占位等）再次爆发才暴露。

**规则**：
15. **新逻辑必须配仓内测试**：任何新增的校验/守卫/降级逻辑，**必须**在仓内 `tests/` 有对应用例，否则视为未完成。测试是对冲"被合并回退"最直接的手段。
16. **commit message 携带验收数字**：把关键验收结论（可导入性、零改动范围、存量未变、测试数）写进提交信息。理由：它**跟着代码走**，代码被 revert 时历史仍在，比文档版本提示更可靠。
17. **diff 规模变化 ≠ 内容丢失**：并发编辑或多来源合并后，`+140/-1` 变成 `+89/-3` 可能只是清理了死代码。**必须逐行核对内容**再下"被覆盖"结论——本次两处（工位自警、我接到预警时）都曾因数字变化误判为覆盖。
18. **交付态标注**：未入库的交付物在回报中**显式标注未提交状态**，避免接手人误以为已固化。

## 八、共享仓的 git 操作纪律（2026-10-20 误 pop 他人 stash 事故固化）

**事故实例**：工位为做"局部临时还原"，执行 `git stash push -- <某文件>`（**实际无可保存内容**，命令报 "No local changes to save"），紧接着的 `git stash pop` 因此作用到了**栈顶属于另一条线工位的 stash**，把那 5 个文件拉成 `AA`（both-added）冲突态并写入冲突标记。复原方式：`git checkout HEAD -- <那 5 个路径>`。**损失为零**（他人 stash 对象完好、文件已归位 HEAD、`stash list` 未增未减），但属**高危操作习惯**。

**规则**：
19. **共享仓禁止用全局栈操作（`stash push` / `stash pop` / `stash drop`）满足局部需求**。局部还原一律用 `git show <commit>:<path> > <tmp>` 或 `git checkout <commit> -- <path>`。
20. **"No local changes to save" 是危险信号，不是无害提示**：它意味着紧随其后的 `stash pop` 会作用到**别人的 stash**。此时必须先 `git stash list` 确认栈顶**属主与意图**，确认归属后方可操作，**不得盲目 pop**。
21. **误操作后必须立即自证并报备**：现场四项取证（`git ls-files -u` 冲突残留数、冲突标记计数、相关文件与 HEAD 的逐字节比对、`stash list` 与 `stash@{0}` 对象可读性）齐备后再报，不得先报"已处理"再补证。**如实报备 + 立即自证复原**是正确处置方式。
