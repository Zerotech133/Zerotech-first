## 2. 设计对齐

### 2.1 零执行权三件套 → MVP 落点

| 三件套（设计稿 §4） | 设计原义 | 本 MVP 落点 | 状态 |

| ② 只读工具集/白名单 | YAML allow/deny，未列名不挂载 | `load_whitelist()` 只读加载 + `validate_whitelist()` 四类断言（必需 allow/必需 deny/无交集/唯一写点范围）；缺 PyYAML 时极简解析并**显式标注 `parser=fallback`** | 已实现（代码级 loader 补齐审计 `I16` 缺口） |
| ③ 产出只回写质询卡 | 唯一出口=Kanban board `zhugeliang-review` | `work/zhuge_challenge/cards.jsonl` 追加式账本 = **离线看板替身**（同 board/card_type 常量写死：`zhugeliang-review` / `challenge`）；不接 Kanban API | 离线占位；Kanban 接线待 W5 对表 |

### 2.2 状态机映射

设计稿 KK §4③：`status: open → responded / resolved`；模板占位：`open → responded / resolved`，降级期 `degraded`。
本 MVP（按工单要求）：**`open → answered → closed`**，`closed` 携带 `outcome ∈ {accepted, rejected}`。

| 设计稿 | 本 MVP | 说明 |
|---|---|---|
| open | open | 一致 |
| responded | answered（`verdict: respond/fix`） | respond=答辩；fix=整改后重推快照（MVP 仅在 note 留痕，重推快照由后续接线做） |
| resolved | closed（`accepted`/`rejected`） | 用 outcome 表达"通过/不通过"，避免把结案权冒充为席位权利 |
| degraded（降级田丰自审） | **未实现** | 真模型未接，本 MVP 无"断链"可降级；后续接 GPT6 时补 `degraded` 卡类型 |

**非法迁移**（如未 answered 就 close、closed 后再 respond）一律拒绝，并追加 `rejected` 事件留因（`reason` + `attempted`），账本只追加不改写。

## 4. 数据契约

### 4.1 快照（snapshot，内存对象）

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema` | str | `zhuge_challenge_snapshot/v1` |
| `source_kind` | str | `snapshot_file`（--snapshot）或 `tasks_ledger`（devtask 账本 doing 过滤） |
| `path` | str | 源文件绝对路径（只读） |
| `filter_status` | list[str] | 过滤状态（tasks 源默认 `["doing"]`；文件源默认 `[]`=不过滤） |
| `total` | int/null | tasks 源=账本任务总数；文件源在过滤时可为 null |
| `selected` | int | 归一后条目数 |
| `snapshot_id` | str | `sha256(canonical(items))`，幂等/回溯锚点 |
| `inside_sandbox_prefix` | bool | 源文件是否在沙盘仓前缀内（false → 记录 dev 适配 warning；`--strict-sandbox` 时拒绝） |
| `items[]` | list[dict] | `task_id/title/status/owner/project/branch/created`（标题/描述截断 300 字符） |

### 4.2 质询卡（card）

字段与 `digital-legion-sandbox/zhuge_query_card_template.md` 的对应关系：

| 本 MVP 字段 | 模板字段 | 说明 |
|---|---|---|
| `card_id` | `card_id` | `ZQ-YYYYMMDD-NN`，同日顺延；也可 `--card-id` 指定（不可覆盖已有） |
| `date` | `date` | `--date` 或北京今日 |
| `board` | `board` | 固定 `zhugeliang-review`（写死，不可覆盖） |
| `card_type` | `kanban_card_write.card_type` | 固定 `challenge` |
| `target_plan_snapshot` | `target_plan_snapshot` | 含 `source_kind/path/filter_status/total/selected/snapshot_id/inside_sandbox_prefix` |
| `ref_questions[]` | `ref_questions[]` | `{q_id, question, dimension: goal_deviation/risk/budget, target_task}` |
| `severity` | `severity` | `info/low/medium/high/critical`，默认 medium |
| `verdict_request` | `verdict_request` | 固定 `respond_or_fix`（每卡必须响应或整改，不得静默） |
| `status` | `status` | `open → answered → closed` |
| `responded_by`/`response_note`/`verdict` | `responded_by`/`response_note` | plain 由 respond 事件写入 |
| `outcome`/`closed_by`/`close_note` | —（本 MVP 扩展） | close 事件写入 |
| `schema`/`created_at`/`created_by`/`idem_key`/`whitelist`/`warnings` | —（本 MVP 扩展） | 契约/幂等/白名单快照/偏差提示 |

### 4.3 账本事件（`work/zhuge_challenge/cards.jsonl`，每行一个 JSON）

| event | 何时写 | 关键字段 |
|---|---|---|
| `created` | `emit` 首次生成 | `card`（完整卡对象） |
| `answered` | `respond`（仅 open） | `by/note/verdict/response_key` |
| `closed` | `close`（仅 answered） | `outcome/by/note/close_key` |
| `rejected` | 非法迁移/非法尝试 | `op/reason/attempted`（**只留痕，不改状态**） |

- **追加式**：只 `open(...,"a")`，绝不改写历史行；写入后 `flush + fsync`。
- **状态 = fold(events)**：同卡多事件按行序折叠，最后一条状态事件决定当前状态。
- **损坏 fail-closed**：任一行 JSON 非法/缺 `event|card_id` → 报行号并拒绝（`ledger_corrupt`，exit 2），不静默跳过。
- 账本在 `work/` 下（repo `.gitignore` 已忽略 `work/`，属运行时产物，不入库）。

### 4.4 幂等键

| 操作 | 幂等键 | 重复行为 |
|---|---|---|
| emit | `sha256({date, snapshot_id, questions, severity, verdict_request})` | 返回既有 `card_id`，`duplicate=true`，**不追加** |
| respond | `sha256({card_id, by, note, verdict})` | 若已存在同 `response_key` 的 answered 事件 → `duplicate=true`，不追加 |
| close | `sha256({card_id, outcome, by, note})` | 若已存在同 `close_key` 的 closed 事件 → `duplicate=true`，不追加 |

### 4.5 状态机与非法迁移

```
(emit) ──→ open ──respond(by/note必填)──→ answered ──close(outcome=accepted|rejected)──→ closed
             │                                │
             └─ close（未 responded）→ rejected 事件留因，状态不变
                                              └─ respond/close 重复或越级 → rejected 事件留因
```

- `respond` 必填 `--by/--note`（"每卡必须响应，不得静默"）；`close` 必填 `--outcome/--by/--note`。
- 本 MVP **不做签字/代签**：`--by` 只是"谁填了这次响应/结案"，不具审批效力；结案权仍在老田 approval_gate。
- `--dry-run` 对 emit/respond/close 均不写账本（respond/close 仍会做状态校验，非法照样拒绝）。

## 5. CLI 命令手册

> 所有命令：`python tools\zhuge_challenge.py [全局参数] <子命令> [子命令参数]`
> 全局参数：`--ledger`（账本路径）、`--whitelist`（白名单路径）、`--whitelist-parser`（auto/pyyaml/fallback）、`--repo-root`、`--json`。
> `--json` 可放子命令后（等价）。

| 命令 | 作用 | 写账本 | 主要参数 | 退出码 |
|---|---|---|---|---|
| `check` | 白名单四类断言 + 解析器来源 | 否 | — | 0/2 |
| `snapshot` | 生成/查看归一快照 | 否（`--out` 写快照文件） | `--snapshot/--tasks/--filter-status/--out` | 0/2/3 |
| `emit` | 生成质询卡（open） | 是（created 事件） | `--snapshot/--tasks/--filter-status/--severity/--card-id/--date/--max-questions/--strict-sandbox/--dry-run` | 0/2/3 |
| `list` | 列卡（可按状态） | 否 | `--status open\|answered\|closed` | 0/2 |
| `show` | 单卡 + 历史事件 | 否 | `--card-id` | 0/2/3 |
| `respond` | 响应/整改（open→answered） | 是 | `--card-id/--by/--note/--verdict respond\|fix/--dry-run` | 0/2/3 |
| `close` | 结案（answered→closed） | 是 | `--card-id/--outcome accepted\|rejected/--by/--note/--dry-run` | 0/2/3 |

常用示例（离线，不联网）：

```powershell
# 1) 校验三件套②白名单（只读）
python tools\zhuge_challenge.py --json check

# 2) 生成快照：默认 .worktrees/tasks.json 过滤 doing；或指定沙盘仓快照
python tools\zhuge_challenge.py --json snapshot
python tools\zhuge_challenge.py --json snapshot --snapshot C:\项目\digital-legion-sandbox\plans\2026-10-27.json --filter-status doing

# 3) 生成质询卡（默认读 doing；先干跑再落账）
python tools\zhuge_challenge.py --json emit --dry-run
python tools\zhuge_challenge.py --json emit

# 4) 田丰响应 → 老田结案 → 查看留痕
python tools\zhuge_challenge.py --json list --status open
python tools\zhuge_challenge.py --json respond --card-id ZQ-20261027-01 --by A0田丰 --note "已补回滚预案"
python tools\zhuge_challenge.py --json close --card-id ZQ-20261027-01 --outcome accepted --by laotian --note "验收通过"
python tools\zhuge_challenge.py --json show --card-id ZQ-20261027-01
```

退出码约定：`0` 成功；`1` IO/未预期；`2` 校验拒绝（白名单/状态机/空快照/账本损坏）；`3` 输入错误（坏 JSON/参数非法/卡不存在）。

## 6. 白名单校验口径（三件套②，fail-closed）

`validate_whitelist()` 四类断言（任一不过即拒绝，emit/respond/close **不产生任何写**）：

1. **必需 allow**：`file_read`、`kanban_read`、`kanban_card_write` 必须在 allow 清单；
2. **必需 deny**：`shell_exec`、`file_write`、`paperclip_api_write`、`hermes_control`、`network_egress` 必须在 deny 清单；
3. **自洽**：allow ∩ deny = ∅；
4. **唯一写点范围**：`kanban_card_write.card_type == challenge` 且 `.board == zhugeliang-review`；`sandbox_repo_prefix` 非空。

解析器：
- 有 PyYAML → `yaml.safe_load`，报 `parser=pyyaml`；
- 无 PyYAML 或 YAML 语法错误且 `--whitelist-parser=auto` → 极简解析（仅 allow/deny/sandbox_repo_prefix 结构），报 `parser=fallback` 并写入卡片 `whitelist.parser` 元数据（**显式降级，不假装等价**）；
- 指定 `--whitelist-parser=pyyaml` 但库缺失 → 直接拒绝（不静默 fallback）。

另有两道写保护：
- `_guard_writes()`：账本/产物路径若落在 `sandbox_repo_prefix` 内 → `sandbox_write_denied`（exit 2），保证「不写沙盘仓」；
- `--strict-sandbox`：快照源必须在沙盘仓前缀内，否则拒绝（生产硬化；MVP 离线默认允许 dev 源并记录 warning）。

## 7. 边界与红线（写死）

1. **零执行权 = 无写通道**：本工具只有一条写通道——质询卡账本（离线替身 board `zhugeliang-review`）；不写执行仓、不写沙盘仓、不写 Kanban、不写 Paperclip、不写工单账本。
2. **不联网**：无网络/进程/子进程库；快照只来自本地文件。
3. **不排程**：本单不起计划任务、不进 cron；定时化属 **L2**（计划任务增删需老田批准）。
4. **不接真模型**：ref_questions 由确定性规则模板生成，不调用任何 LLM；真模型质询生成属后续接线。
5. **不代签**：`respond/close` 的 `--by` 只记"谁填的"，不产生审批/结案效力；结案权=老田 approval_gate。
6. **不合并**：本工单只提交 worktree，不合 master（由 Lead 过评审门后另批）。
7. **长跑输出落盘**：pytest/冒烟输出落 `C:\Temp\zhuge_challenge_pytest.log`、`C:\Temp\zhuge_challenge_smoke.log`（不入库）。

### 8.2 未验证项（如实声明）

1. **沙盘仓真实快照格式**：`digital-legion-sandbox/plans/` 目前仅 `.gitkeep`，无真实快照样本 → `snapshot_from_file` 对"田丰真实推送格式"的兼容性未验证。
