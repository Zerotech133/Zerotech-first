## 二、复现（系统临时目录，未触碰真实账本）

### 2.1 复现受限说明（须先声明）

生产同款形态是 `cmd /c "... > log 2>&1"`。本次诊断中 **`cmd.exe` 在 Bash 与 PowerShell 两个工具侧均被安全策略拦截**（实测返回 `Command blocked for security: cmd.exe cannot be used from ...`），因此**无法 100% 原样跑生产那条命令行**。

处置：改用 `ctypes` 直接调 Win32 `CreateFileW`，**复刻 `cmd.exe` 重定向所使用的那组句柄语义**（`GENERIC_WRITE` + 共享模式仅 `FILE_SHARE_READ`）。这正是 cmd 重定向的共享模式，且是冲突的**充分必要机制**，故复现等价性成立。

脚本落点：`%TEMP%\shadow_repro\repro_share.py`（**不在仓库内、不在生产路径**）。

### 2.2 复现输出（实测原文）

### 2.3 复现得出的三条硬结论

1. **异常形态逐字命中生产**：`PermissionError` / `errno=13` / `Permission denied`，底层 Win32 码为 **32 = `ERROR_SHARING_VIOLATION`**（核定过程见 §2.4）。**证实是共享冲突，不是 ACL 权限** —— 若是目录只读或 ACL 问题，Win32 码会是 5（`ERROR_ACCESS_DENIED`）而非 32。
2. **重试必然徒劳**：§2 场景 3 的 5 次重试 5 次全败。占用句柄**全进程期持有**，不存在"退避后自然释放"的窗口。**这直接证伪了 10-19 当晚"加重试即可"的初判**（见 §六 最小加固建议）。
3. **与 CWD/目录权限无关**：场景 4 释放句柄后立刻 SUCCESS，同一目录同一路径。目录可写性从未是问题。

### 2.4 错误码权威核定（2026-10-20 补做，修正初版误读）

**背景**：修复方 ws-ps1 在 ps1 注释中写「Win32 状态码 32(ERROR_SHARING_VIOLATION)」，而本文档初版写「winerror 183」。**二者冲突，必须实测判定。**

**核定方法**：绕开 Python `open()`，**直接用 `CreateFileW` 复刻同一请求**（`GENERIC_WRITE` + 共享模式 `FILE_SHARE_READ|FILE_SHARE_WRITE` + `OPEN_EXISTING`），在**同一调用后立即** `GetLastError()`。脚本：`%TEMP%\shadow_repro\verify_errcode.py`（不在仓库内）。

**实测输出**：

```
步骤1：外层独占句柄 h=680 INVALID=18446744073709551615 -> 已持有（共享仅 FILE_SHARE_READ）

步骤2：复刻 Python open(...,'a') 的 Win32 请求（GENERIC_WRITE + 共享读写）
CreateFileW 失败 → GetLastError() = 32  (ERROR_SHARING_VIOLATION)
  判定：32 = ERROR_SHARING_VIOLATION  ✅ ps1 修复注释正确；诊断文档所记 183 有误
  非 5 (ACCESS_DENIED) → 排除『目录只读 / ACL 拒绝』假设

步骤3：Python 层映射（确认对外表现）
open 抛：PermissionError errno=13 strerror=Permission denied
```

**结论：正确值为 32，ps1 注释正确，本文档初版的 183 有误**（错因见 §1.2 更正框：在 `except` 块内取 last-error 已被 CPython 异常展开覆盖）。

**取证方法论附记（比结论本身更值得记）**：本工位为做这次核定，**连着写错三版脚本才跑对** ——

| 版本 | 错误 | 根因 |
|---|---|---|
| v1 | 误入「意外成功」分支 | `INVALID_HANDLE_VALUE` 取 `wintypes.HANDLE(-1).value`（符号位表示） |
| v2 | 仍误入「意外成功」 | `h2 == INVALID` 比较类型不匹配（`-1` vs `18446744073709551615`） |
| v3 | ✅ 正确 | 设 `k32.CreateFileW.restype = ctypes.c_void_p` 并用 `c_void_p(x).value` 归一化 |

**「除法前先确认除数非零」式的朴素错误，在取证脚本里同样会让人得出自信的反向结论**——v1/v2 都打印了「意外成功」，若不核对Python 层 `open()` 明明抛了 `PermissionError`，就会得出「无冲突」的反向结论。**判据：Win32 层结论与Python 层表现矛盾时，先怀疑自己的比较逻辑。**

### 4.1 决定性证据：D2 也撞了同一个墙，只是被吞掉了

现网 `last_run.log` **第 1 行**（实测原文）：

```
[log] last_run.log 被外层重定向占用，沿用既有 stdout/stderr
===== shadow run start 2026-10-20 03:47:59.737563 =====
```

这行**正是修复后 `_redirect_run_log()` 在捕获 `PermissionError` 后打印的**（`run_shadow.py:429`）：

```python
426      try:
427          return open(LEDGER.parent / "last_run.log", "a", encoding="utf-8")
428      except PermissionError:
429          print("[log] last_run.log 被外层重定向占用，沿用既有 stdout/stderr")
430          return None
```

**因此：D2 成功的原因 100% 是「代码把同一个必然冲突 catch 掉了」，而不是「环境变好了」。**

**推论（防复发的核心）**：外层 `cmd /c` 重定向**至今仍在**（ps1 L25 未动）。也就是说——

> **若把 `_redirect_run_log` 的这个 `except` 去掉，同一份代码会在明天 17:10 再次 100% 崩溃。冲突本身一天都没有消失过。**

这是本次诊断最重要的结论，也是"是否可复发"一节的判定基础。

### 4.2 顺带澄清：`last_run.log` 里已无 10-19 traceback（非证据缺失，是被覆盖）

`>` 是**截断式**重定向。10-20 03:47 那次跑把 `last_run.log` 整个截断重写，所以 10-19 的 469 字节 traceback **已被物理覆盖**。现网文件 825 字节、mtime `Oct 20 04:07`，只剩 D2 内容。

### 4.3 时序复核：重启不是原因（按要求自证）

| 事件 | 实测时间 | 相对 17:10 崩溃 |
|---|---|---|
| `AgentShadowDaily` 崩溃 | 2026-10-19 **17:10:02** | 基准 |
