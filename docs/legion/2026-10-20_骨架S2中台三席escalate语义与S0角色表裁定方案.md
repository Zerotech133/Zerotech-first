## 二、方案对比：escalate 路径裁定

### 方案 A：escalate 改走 command 层统一路由

诸葛 `escalate()` 改发 `Report(level="command")`，经总线 → os_commander 归集层展示请示/升级 → 老田批示回执。问题类事项仍以问题单形式走 `report_issue` → 田丰归口；escalate 只承载"请示/建议/阻断"类管理上报。

| 维度 | 评价 |
|---|---|
| 可审计性 | **强**。全程经总线 route 四道校验 + jsonl 账本，死信机制照常兜底；层级合规（command 层发 command 层消息），无新增越权面 |
| 最小改动面 | **最小**。只改 `zhuge_liang.escalate` 一个方法（level 参数 + docstring）+ A 组称谓对齐；总线 `message_bus.py` 一行不动 |
| 与研发工单制兼容性 | **最好**。升级与整改分账：问题单仍走田丰归口（登记去重→工单→无单不写码→评审门→验收归口田丰），escalate 不承载整改指令；os_commander 角色表 #1 本就定位"展示请示与升级"，是既有设计意图 |

### 方案 B：白名单扩员（田丰进 PRINCIPAL_WHITELIST）

诸葛问题单经田丰归口，田丰分级后对"阻断类"以 level=principal 直发本人。

| 维度 | 评价 |
|---|---|
| 可审计性 | 中。田丰归口登记有台账，但白名单扩员后田丰可发任意 principal 消息，须另造消息类型区分"整改工单 vs 升级请示"，否则审计上无法区分归口派单与越级上报 |
| 最小改动面 | 大。`message_bus.py` 白名单 + route docstring + `tests/test_message_bus.py` / `tests/test_dead_letter.py`（`test_principal_whitelist_untouched` 已锁定白名单不可动）+ `tian_feng.py` 新增升级方法，四处联改 |
| 与研发工单制兼容性 | 差。田丰同时承担问题归口与升级通道，"归口唯一入口"职责被稀释；且诸葛→田丰→本人链条中田丰成为必经节点，若田丰席故障则升级通道整体阻塞 |

### 推荐：方案 A

一句话理由：**升级走 command 层是改动最小、全程账本可审计、不扩大白名单越权面的路径，且与 os_commander"归集展示请示与升级"的既有定位和研发工单制（无单不写码）天然分账兼容。**

例外通道（签准/交易/生产变更类不经整改线）在方案 A 下的体现：监督席发现此类越权企图时——① 构造 approval_gate 待签事项（材料指纹绑定，本人签准闭环，沉默与"继续"不是签字）；② 同步触发 risk_guard 预警（其白名单直发本人通道照旧，参照 B8）；③ 监督席自身不直发 principal、不进整改线派单。`report_issue` docstring 中"同时上报 risk_guard 与本人"改写为上述双动作。
