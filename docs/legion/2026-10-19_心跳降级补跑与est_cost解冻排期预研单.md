## 一、A 部：降级当日补跑权属（遗留 4 销项预研）

### 1.1 幂等证据（代码级）——补跑不污染的依据

补跑是否污染产物，取决于三条代码事实，全部已实读：

1. **brief.json 整体覆盖、seq 从 1 重计**：`write_brief`（runner.py:244-252）对当日 `memories/intel/<date>/brief.json` 直接整体覆盖写，无任何追加；seq 由 `build_items`（runner.py:175）按本次合法条目 `len(valid)+1` 生成，不读旧产物。同日补跑无论成功几次，brief 恒为「最后一次成功运行」的完整快照，**不存在条目叠加或 seq 跳号**。
2. **测试锁定该行为**：`test_same_day_rerun_idempotent_overwrite`（test_heartbeat.py:80-90）同日两次 run 后断言 items 恰为 `-01/-02` 无 `-03+`（L87-88），run 记录恰 2 条（L90）——补跑幂等是**有回归测试背书的既定契约**，不是口头承诺。
3. **降级路径不触碰 brief**：`run()` 的三个降级分支（探活败 runner.py:299-303 / 推理败 305-311 / 空简报 313-316）都在 `write_brief`（L322）之前返回，测试两处断言降级后 `memories/` 目录不存在（test_heartbeat.py:120,145）。因此：**降级后补跑，若成功则写入当日第一份 brief（等于首写）；若再降级则维持无 brief，均不污染任何已有产物**。

结论：幂等机制使「补跑」在数据层面是无损动作，权属问题的本质是**流程权属与红线符合性**，不是技术风险。

### 1.2 唯一的非幂等点：degraded.json 与运行记录

- `degraded.json` 固定路径覆盖写（runner.py:97-98, 266-276）：当日第二次降级会**覆盖**第一次的降级占位件（探活记录、首次时间戳丢失）。运行记录 `run-*.json` 每轮一条不覆盖（runner.py:90-94），第一次降级的完整证据仍在运行记录里，故不构成证据灭失，但 degraded.json 本身需在补跑成功后处置（见 1.4）。

### 1.4 补跑上限与 degraded.json 处置

- **补跑上限：每日 ≤ 1 次**。理由：① 幂等覆盖意味着补跑 N 次与 1 次产物等价，多次补跑无信息增益；② 每日一轮心跳是契约节奏（T+1 收编环 08:30 档），多次补跑偏离「每日心跳」语义；③ 防刷约束落在**权属判定环节**而非代码——方案③下 lead 拍板即天然限 1 次，方案②下接线施工单写死重试上限 1，无需 runner 改码。
- **degraded.json 处置（补跑成功后）**：推荐**归档改名**而非删除/覆盖留置——补跑成功写出 brief 后，若 degraded.json 原样留置，其机器可读 `degraded=true`（runner.py:270-271）会使后续判读误判「当日仍降级」；直接删除则丢降级证据。处置 = 执行补跑者在**文件层**将 `degraded.json` 改名为 `degraded-<原 at 时间戳>.json` 留档（纯文件操作，零改码，不触冻结），运行记录不动作（每轮一条本就完整）。降级后未补跑或补跑再败，degraded.json 原样留置，次日心跳不改它（次日成功只写新 brief，degraded.json 遗留至当日判读时按同口径归档——此点列为开放问题，见 §三）。

### 1.5 推荐序（拍板留白）

**推荐序：③ →（P0 周后）② → ①（不建议）。**

一句话理由：③ 是唯一在 P0 冻结周内零红线冲突且落在既有升级路径上的方案，幂等代码证据充分、人工成本仅一次拍板；② 是 README 指定的长期正主但受「不动计划任务」红线限制只能在解冻后的接线施工单里实施；① 破坏验收/执行分离，自证闭环，不予采纳。

> **拍板留白**：本预研只给推荐序。问题 4 的正式拍板权归计划任务接线方/lead（README:48 与台账:120 口径），拍板结论应回填台账遗留问题 4 行。

### 2.2 接线点设计（设计稿与 diff 预览，**解冻后实施，冻结期零改动**）

**口径结论**：两口径均满足「表内场景才可填非零 est_cost」红线（pricing.py:11-13）。**推荐 a**：铁律②现行有效，口径 a 零改动、零冲突；口径 b 属铁律变更级动作，即便解冻也应单独立项拍板，不随解冻排期捆绑实施。若未来拍板走 b，2.2 的 diff 预览即为实施稿，另需配套每日建单接线（不在 runner 内，由执行方经 API 建 WO）。
