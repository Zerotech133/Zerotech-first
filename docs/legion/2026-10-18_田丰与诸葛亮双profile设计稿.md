## 2. 田丰：Hermes profile

### 2.1 profile 目录结构

依据 Hermes 现行 profile 机制（`hermes-webui/api/profiles.py`）：BASE 目录（`~/.hermes`）下 `profiles/<name>/`，clone 时复制 `config.yaml`、`.env`、`SOUL.md`；切换 profile 即改 `os.environ['HERMES_HOME']` 与 base 下 `active_profile` 文件。

```
~/.hermes/
  active_profile                 # = "tianfeng"
  profiles/
    tianfeng/                    # 田丰
      SOUL.md                    # 人格段（见 2.2）
      config.yaml                # 模型路由：本地 Ollama qwen3.5:9b
      .env                       # 仅本地变量，无云端凭据
      skills/                    # 执行技能：kanban-write、repo-write、cron-heartbeat
      memory/
      cron/                      # M1 才接线心跳（见 §6），M0 只建目录
```

### 2.2 SOUL.md 人格段要点

- 身份：田丰，数字军团执行相。对上承接 Paperclip 审批结论与军师质询，对下驱动执行仓与 Kanban。
- 语言风格：短句、结论先行、凡输出必带下一步动作与负责项；不复述、不寒暄。
- 权力观：只在自己被授权的仓与 Kanban 内动手；预算/审批红线一律转 Paperclip，不自行绕过。
- 对质询的态度：把军师质询卡当工单——每张卡必须「响应」或「整改」，不得静默。
- 禁区：不写 Paperclip 三表、不改账本、不碰沙盘仓（只读对方产物）。

### 2.3 中档模型接入点（本地 Ollama qwen3.5:9b）

`config.yaml` 路由段（配置稿）：

```yaml
model:
  provider: ollama
  base_url: http://127.0.0.1:11434
  model: qwen3.5:9b
  # 本机已有 ollama_lock.py / start_tuned_ollama 闸门，profile 不另起拉锁逻辑，复用既有闸门
```

说明：模型名以本机 `ollama list` 实际拉到的 tag 为准，若最终 tag 为 `qwen3.5:9b-instruct` 等变体，施工时在 config.yaml 一处改齐（单点修改）。

### 2.4 权限边界

- **可写**：Kanban（执行侧卡片）、执行仓工作区、自身 profile 的 memory/cron。
- **不可写**：Paperclip 三表（只经 API 提工单）、沙盘仓（见 §4）、任何生产 data/。

## 4. 零执行权隔离三件套（写死，逐条落地）

诸葛亮**零执行权**由以下三件共同保证，缺一即验收不通过：

### 三件套①：专用只读沙盘仓

- 路径建议：`C:\项目\digital-legion-sandbox`（**由 JJ 路建仓**，本稿只引用不创建）。
- 内容：田丰每日推送的执行计划快照（只读镜像），诸葛亮唯一可读的执行侧信息源。
- 权限：对诸葛亮所在运行时为**只读挂载**；写权限仅田丰侧推送动作持有。物理隔离于主执行仓——即使诸葛亮越权写，也伤不到执行仓。

### 三件套②：OpenClaw 侧只读工具集 / 插件白名单

- 诸葛亮网关配置中**只注册只读类工具**：read_file、list_dir、kanban_query（读）。
- 白名单即配置（配置稿）：

```yaml
# openclaw-profile-zhugeliang.yaml（配置稿，待 OpenClaw 形态对表后定文件名）
tools_whitelist:            # 未列名的一律不挂载
  - read_file               # 仅限沙盘仓路径前缀 C:/项目/digital-legion-sandbox
  - list_dir                # 同上路径前缀
  - kanban_read             # 只读查询质询卡与执行卡状态
  - kanban_write_card:      # 唯一写动作，且仅限一种卡片
      card_type: challenge  # 质询卡
      board: zhugeliang-review
explicitly_denied:
  - shell_exec
  - file_write              # 对沙盘仓与任何仓
  - network_call            # 除 GPT 6.0 模型端点本身
  - paperclip_api_write     # 审批/预算接口不可触
  - hermes_control          # 不可触 Hermes cron/会话
```

### 三件套③：产出只回写 Kanban 质询卡

- 诸葛亮的一切产出只有一种合法出口：**质询卡回写 Kanban**（board: `zhugeliang-review`）。
- 质询卡结构：`{id, date, target_snapshot, questions[], severity, status: open→responded/resolved}`。
- 不允许以任何形式直接修改执行仓、Kanban 执行卡状态、Paperclip 工单。

## 5. 闭环流程（文字版流程图）

```
[田丰] 完成当日执行计划
   │  ① 快照导出
   ▼
[田丰→沙盘仓] 推送计划快照至 C:\项目\digital-legion-sandbox   （写权限：仅田丰）
   │  ② 触发质询（M0 手动；M1 由心跳定时）
   ▼
[诸葛亮/OpenClaw+GPT6.0] 只读拉取沙盘仓快照（三件套①②）
   │  ③ 反向质询：对计划的目标偏离/风险/预算合理性提问
   ▼
[诸葛亮→Kanban] 产出=质询卡，回写 board: zhugeliang-review   （三件套③，唯一出口）
   │  ④ 田丰读取质询卡
   ▼
[田丰] 每卡二选一：响应（答辩）或 整改（改计划后重新推快照，回到①）
   │  ⑤ 卡状态 open → responded / resolved，全程留痕
   ▼
[闭环] 当轮全部卡闭环 → 本日质询结束；未闭环卡滚入次日并升级 severity
```

断链分支：③ 若 GPT 6.0 调用失败（跨境断链）→ 走 §7 降级路径，主链（田丰执行）不受影响。

## 6. 降级路径：GPT 6.0 跨境断链

- 触发：诸葛亮运行时调用 GPT 6.0 连续失败（建议阈值：单轮内 3 次重试失败）。
- 降级动作：**质询降级为田丰自审 + 留痕**——田丰按质询卡同款模板自填 `self-review` 卡（questions 自答），status 标 `degraded`，当日不阻塞主链执行。
- 恢复：链路探活成功后自动回升；降级期间事件写审计（口径同 Paperclip audit 表设计，另行落点）。
- 铁律：降级只影响「质询」这一环，**不影响执行主链、不影响 Paperclip 审批/预算**。
