### 1.1 写入方全景

**W3 是唯一的写前校验闸**（`agent_platform/domains/devtask_wiring.py:124-153`），但它调用的 `check_tasks_doc` 只校验 `status` / `created` / `merged` / ID 形态，**从不校验 owner 取值域**。

### 1.2 根因代码原文摘录（带行号）

#### 证据 A —— owner 赋值点（唯一的 owner 写入处）

`tools/devtask.py:299-306`：

```python
299→    branch = "task/" + tid
300→    wt = os.path.join(WT_DIR, tid)
301→    _git("worktree", "add", wt, "-b", branch)
302→    tasks[tid] = {"desc": desc, "branch": branch, "worktree": wt,
```

**这是全仓唯一的 owner 赋值点。** 三个关键事实：

1. **owner 完全由调用进程的 `AGENT_NAME` 环境变量决定**，与工单内容、项目线、部门**无任何耦合**。
2. **无任何取值域校验**：不检查是否 ∈ 部门成员 ∪ 部长 ID，不报WARN、不拒单、不降级留痕。
3. **缺省即`unknown-agent`**：这是**静默失败**（silently fallthrough），不是显式拒绝。

#### 证据 B —— 全仓唯一的 owner 合法化尝试（且只覆盖一条调用链）

`tools/org_registry_server.py:571-578`：

**这是全仓唯一一处主动把 owner 对齐部门成员 ID 的代码**，注释本身就承认了「避免所有 Legion 工单落成 unknown-agent」——**说明该缺陷在10-17 已被局部认知并局部打补丁**。
