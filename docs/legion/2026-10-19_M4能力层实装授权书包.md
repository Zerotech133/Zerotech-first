### 1.3 汇报格式（判例 2、5）
- 逐文件署名三列：**文件 → 作者 → commit hash**；
- 命令结果必含**退出码原文**，禁止只贴 tail 后片段；长跑输出落文件（目录先 mkdir）；
- 测试汇报必报「通过数 / 失败数 / 总数」。

### 1.4 验收条款（判例 5、6）
- lead 验收铁三角：①亲跑测试基线并记录通过数 ②git log/diff 抽验交付在库且 diff 干净 ③关键脚本实跑一遍——三步缺一不可。
- 退出码 0 ≠ 通过：各书验收均设**人工可数四计数兜底**（见各书第 6 条）；空集通过 = 假绿；校验器「查 0 项仍 PASS」判不合格，必须三态 PASS/FAIL/INCONCLUSIVE + `--self-test` 阳性对照。

### 1.5 越权处置预告（判例 3）
- 超出授权清单的实装一律走追认流程（①设计对照 ②隔离/越界检查 ③测试亲验 ④追认入库 + 留痕警示），**不因结果合格免除警示**；清单外交付不得先行汇报为「完成」。

### 1.6 批内完成要求（判例 4、7）
- 可交付物须**本批内完成并汇报**，不假设跨批唤醒；批后定时动作以 automation 预约承接。

### 1.7 文档纪律（判例 8、9）
- 发现设计稿/施工单真缺陷不在原文静默改，缺陷处后插「勘误回写」注记（发现人 + 固化 commit）；收官/状态回填一律用实际 commit hash。
- 回填注记 Edit 锚点只锚单行或单一语义块，改后当轮 Read 复核改动区结构无损伤（判例 9）。
- 本包 §0.4 占位 hash 的回填动作适用本条。

### 1.8 automation 豁免声明
- 本包四份授权书均**不涉及 automation 创建**（判例 7 要素豁免理由：全部施工为离线文档/设计稿/只读脚本与纸面推演，零计划任务、零定时动作）；批后验收如需预约由 lead 另行 automation 承接。
