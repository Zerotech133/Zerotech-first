## W32 市场推送矩阵预研

- **目标**：把「根据时间节点、分市场（A股/美股/港股/加密/商品/外汇）向客户推送」从口号落成可派工的**矩阵定义稿**——每市场一行：数据到点时刻 → 推送窗口 → 内容模板 → 频次上限 → 静默窗叠加规则。
- **机制设计点**：
  1. **到点时刻以数据就绪为准，不以钟表为准**：每市场的触发锚 = 既有数据生产端完成信号（如郭嘉对账 sources_ok、行情日更入库、JEV 晨链完成），钟表时刻仅作 deadline 兜底（数据到点未到走 W33 升级器）；
  2. **市场时区表**：A股 15:00 收盘 → 盘后窗口；美股 04:00/22:00（北京时间）→ 盘前/盘后窗口；加密 7×24 → 固定节奏窗口；矩阵逐格显式声明时区与夏令时策略；
  3. **内容模板只引用既有产物**：数据日报 H5 / 郭嘉对账页 / picks 看板公网快照（picks_public/），**预研期禁止生成任何新内容生产端**；
  4. **频次与静默**：每市场每日推送上限、静默窗（22:00-07:30 除非 critical）叠加 8097 闸门既有静默语义，不重复造轮子。
- **交付物**：市场推送矩阵稿（本 W 段落即骨架）+ 市场×窗口×模板×频次四列表 + 每格的「数据锚 / deadline / 兜底动作」三元组。
- **验收**：六市场全覆盖无空格；每格数据锚可指认到既有产物/跑批名；与 [KP012档] 静默/配额语义无冲突表述。
- **依赖**：既有数据生产端清单（郭嘉/JEV/数据日报/picks）只读盘点。
- **风险**：数据锚依赖的跑批时刻漂移（如行情晚到）导致矩阵空转——设计上锚定「完成事件」而非「钟表」，晚到情形由 W33 接管。
- **规模**：0.5 天（纸面）。

## W33 数据到点升级器预研

- **目标**：把「发现数据没过来 → 反馈其他 agent 组调度 → 或通知老田换 agent」落成**检测-升级-闭环**机制稿——通用化 picks 巡检判例为全数据源可注册的到点监测协议。
- **机制设计点**：
  1. **注册协议**：每数据源一行注册项（源名 / deadline / 探活方式 / 升级分档），沿 `x5-picks-publish-check` 判例：到点未到 → 落旗标（DEPLOY_PENDING 同款原子写）→ 飞书红卡（含双向证据 hash 与处置提示）→ 恢复自动清旗标+绿卡；
  2. **升级分档三档**：L1 自动重试（既有跑批幂等重跑，沿对账 wipe 重建判例）→ L2 换源/降级（复用 [M1单] W10 断链降级口径：degraded 占位件显式可计数不静默）→ L3 升级老田（飞书红卡+@，附全链证据）；**分档跳转由 Hermes 决策请求驱动**（hermes_internal 凭证经 8097 决策账本 preview→record→execute，execute 需二次确认群 bot 实证，沿 [KP012档] 全口径）；
  3. **降级必须显式可计数**（[M1单] W10 铁律直接引用）：任何一次升级动作（成功或降级）留可解析痕迹，无痕迹=施工不合格；
  4. **不补跑铁律**（[M1单] W10 同款）：降级当日不自动补跑，避免撞既有任务链窗；补跑与否 L3 老田拍板。
- **交付物**：数据源到点注册协议稿 + 升级分档状态机稿（含 Hermes 决策请求的进出报文样例）+ 演练剧本稿（虚构晚到源走 L1→L2→L3 全链纸面推演）。
- **验收**：状态机每条跳转边有权限锚点（谁触发/谁执行/谁留痕）；Hermes 决策请求报文与 8097 决策账本实际 schema 逐字段对表无漂移；演练剧本经 [T1回执] 同款只读口径可执行。
- **依赖**：W32 矩阵（deadline 表）；[KP012档]；[M1单] W10。
- **风险**：升级风暴（多源同时晚到连环触发）——设计上升级器全局并发闸与合并红卡（同一窗口多源合并单卡），预研期定阈值实装拍板。
- **规模**：1 天（纸面）。

## W34 客户推送面与内容审批闸预研

- **目标**：定义「客户」与老田个人飞书的**通道分离**方案稿——客户分群、独立推送通道、内容审批闸、首批灰度机制，作为对外触达的唯一合法路径。
- **机制设计点**：
  1. **通道分离铁律**：客户推送不经老田个人飞书，独立分群（应用户建群或应用分组，形态预研期两案对比留待实装拍板）；老田个人卡（红/绿/日报）语义不变；
  2. **审批闸三重门**（红线 4 落地）：名单拍板 / 模板过会 / 首批灰度逐个确认；任何客户推送请求必须经 8097 决策账本 execute 全口径（preview 可见全文 → record 幂等 → execute 二次确认），Hermes 与任何 agent 均无直发权；
  3. **载体判例**：沿「飞书推送统一风格 H5 + 公网快照直达」现行口径（data_daily/data_guojia 快照判例），客户收到的卡片可跳公网页面，逐条明细仍守「公网无逐条新闻明细」红线；
  4. **频次与退订**：每客户每日上限、静默窗同矩阵、退订即登记（预研期定义登记形态，实装拍板）。
- **交付物**：客户推送面机制稿（两案对比：应用建群 vs 应用消息分组）+ 审批闸三重门流程稿 + 首批灰度演练剧本稿（虚构客户名单走全流程纸面推演）。
- **验收**：三重门缺一不可机审表述；与 [KP012档] execute 二次确认语义零漂移；红线 4 逐条对应到流程节点。
- **依赖**：W32 矩阵冻结；老田客户分群拍板（硬前置）；[KP012档]。
- **风险**：对外触达的合规与误发风险——三重门 + 灰度名单逐个确认双保险；预研期零真实客户触达。
- **规模**：1 天（纸面）。

## W35 Hermes 决策者角色只读演练预研

- **目标**：把「Hermes 作为推送域决策者」的完整闭环做一次**只读沙盘演练**（[T1回执] 同款口径）：数据未到 → 升级器旗标 → Hermes 决策请求 → 分档动作建议 → 反馈闭环，全程零生效侧写入。
- **机制设计点**：
  1. 演练输入为虚构晚到源 + 真实 8097 决策账本（preview/record 只走，execute 不真发——沿决策执行开关默认关的现状）；
  2. 演练产出三件：决策请求留痕、分档建议件（L1/L2/L3 建议与依据）、演练回执（含 degraded 占位件计数与红卡样例，全部显式可计数）；
  3. **纯观测红线**：演练期执行面行为与演练前逐项一致（无新增跑批触发、无真实客户/个人推送、预算流水无新增科目）。
- **交付物**：演练剧本 + 演练回执（W32~W34 机制稿的联合验证面）。
- **验收**：回执含全链留痕可机审；执行面零变更四项逐项核对；与 [T1回执] 判例口径一致。
- **依赖**：W33 状态机稿 + W34 审批闸稿收口。
- **风险**：Hermes 决策质量依赖 profile 推理（qwen3.5:9b 本地档）——预研期只验「请求-留痕-建议」链路形态，不评建议质量；质量评估留 M4+ 能力层。
- **规模**：0.5 天（只读演练）。
