# 数据巡检断言与快照价格守卫 v1

日期：2026-11-11　起因：11-11 盘后复盘把「11-10 整天零采集」写成了「数据延迟 3.9 小时」，
以及 15:59 那次坏价快照差点被当成当日成绩。

两项都是**判据错误**，不是数据错误。判据错一次，后面写出来的所有结论都跟着错，
所以这两条要落进代码，不能只写在注意事项里。

## 一、数据巡检：每张表断言 `max(数据日) == 目标数据日`

### 旧判据为什么必然漏

`cohorts/health_check_YYYYMMDD.py` 的顺序是：

```
latest = max(daily_delta.trade_date)      # 先问「表里最新是哪天」
检查 latest 这天七张表齐不齐              # 再问那天够不够
```

它把「表里最新的一天」当成了「今天应该有一天」。
于是某天整天没采数据时，`latest` 会自动退回上一个交易日，脚本照样报七表全 ok。
**判据与自己要检查的对象共用一个变量，就永远自洽——这类断言等于没写。**

同一次事故里还有两个连带误判：

- 把文件的 `mtime=12:57` 当成「扫描时刻」。12:57 其实是人工补数的写入时刻，
  与「里面装的是哪天的数据」是两件事。
- 用「条数够不够」当判据。条数够只说明那天采得全，不说明那天是**哪一天**。

### 新判据

`portal/daily_report/data_health.py`：目标数据日由外部给定，逐表断言

```
max(date_col) == target
```

不等即判「零采集」，与条数多少无关。任何一天的漏采都会让 `max` 停在更早的日期上，
这个断言兜得住漏采、也兜得住前视。

```bash
python data_health.py --target 20261111   # 显式
python data_health.py --target prev       # 上一交易日（15:10 调度用这个）
python data_health.py --target today      # 今天是交易日则今天，否则上一交易日
python data_health.py                     # 缺省按时刻推断（>=18:00 取今天）
```

| 判定 | 含义 | 该做什么 |
|---|---|---|
| `ok` | 目标日有记录且条数达标 | — |
| `zero_collect` | 目标日一行都没有，表停在更早的日期 | 补拉，别先查别的 |
| `partial` | 一部分表到了目标日，一部分没到 | 按落后的表单独补 |
| `incomplete` | 有记录但少于近 10 日中位数的 90% | 查数据源，不是漏采是缺票 |
| `ahead` | 表里出现晚于目标日的记录 | 查源，多半是日期字段错位 |
| `no_event` | 事件型表（公告、涨跌停）当日无记录，而每日必有表已齐 | 正常，市场当天没这类事 |

退出码：`0` 全齐 / `1` 有零采集·不完整·超前 / `2` 环境错误（文件缺失等）。

### 两个设计取舍

- **事件型表（`anns_d`、`limit_list_d`）允许当日为空**，但只在每日必有表已齐时才这么判。
  每日必有表集体落后时，事件表一并算零采集——同一个根因，不另开一套解释。
- **`mtime` 只写进 JSON 作参考，不参与判定**。文件最后写入时间与内容数据日无关，
  11-11 那次就是把这两件事混了。

### 回溯验证

用补数前的备份（研究侧数据目录下的 `_delta_bak_<日期>_<时刻>/`，七份 delta 的
`max(trade_date)` 全为上一交易日）跑：

```bash
python data_health.py --target <目标数据日> \
  --data-dir "<补数前的备份目录>"
```

结果 7/7 `zero_collect`，与「11-10 整天零采集」的事实一致；
而当时的旧脚本对同一批文件报的是 7/7 全绿。**同一份数据，两套判据，一个对一个错。**

## 二、快照价格守卫：同日两轮差超过 1 个百分点就报警

### 判例

11-06/main 当日五条快照：

| 时刻 | 累计 | 说明 |
|---|---|---|
| 15:36:08 | 12.558% | |
| 15:56:27 | 12.558% | |
| **15:59:07** | **14.349%** | 坏价，偏 +1.79pp |
| 16:15:21 | 12.558% | 重跑修正 |
| 18:01:09 | 12.558% | 复核 |

15:00 之后价格已经定格，三次快照本该完全一致。报告若正好在 15:59–16:15 之间生成，
就会把 14.35% 当成当日成绩写进去。

### 三道判定（都只告警，不改数、不改退出码）

| 代号 | 条件 | 级别 | 说明 |
|---|---|---|---|
| `price_anomaly` | 两轮都在 15:00 之后，累计差 > 1pp | high | 价格已定格，差异只能来自坏价 |
| `price_jump` | 间隔 ≤ 30 分钟，累计差 > 1pp | medium | 可能是真行情，也可能是坏价 |
| `bad_tick` | 单票 `close/pre_close-1` > 35% | medium | 超出任何板块涨跌停上限，能指到具体哪只票 |

不算告警的两种情形，都是刻意放过的：

- **间隔超过 30 分钟的盘中差异**——两小时里涨 3pp 是真行情，报出来就是噪声。
- **跨日比较**——隔夜跳空是真行情，所以只在 `day_index` 相同时才比。

### 落地位置

- 判定函数 `cohort_track.snap_guard()`：纯函数，10 条测试在 `test_snap_guard.py`
- 结果写入 `status_latest.json`：顶层 `price_ok`（有 high 即 false）与 `warnings` 数组
- 页面：`houfeng.html` 在 `price_ok=false` 时于首屏显示红框「价格存疑」提示条，
  文案按正负分支写「本轮比上一轮高/低 N 个百分点」，不写 `+/-` 符号
- 日志：调度日志里出现 `[警告]` 或 `[提示]` 行
- 每条 cohort 的 `snapshots` 记录补 `date` 字段（此前只有 `at`，跨天无法区分）

### 接入

`tools/scheduled/houfeng_snap_task.ps1`（15:10，周一至周五）在 `--settle` → `--snap`
之后追加一步 `data_health.py --target prev`：

- 只检 prev：15:10 当天日线还在交易所侧，检 today 必然报零采集
- 不阻断：巡检不过说明数据侧有洞，快照与结算本身仍然有效，日志记 `WARN`

这一检正好对着 11-10 那次漏判——次日 15:10 就会看到「目标日 20261110 零采集」。

## 三、不覆盖什么

- **不给数据补拉**。巡检只报状态，补拉仍走 `pull_daily_delta.py`，两件事分开。
- **不判断坏价的来源**。守卫只说「这两次不一致」「这只票的涨跌幅超过涨跌停」，
  不猜是哪一层出的错（接口、缓存还是复权）。
- **不自动改数**。没有剔除可疑票、没有取两次的中位数——那会把一个有据可查的
  异常变成一次静默的偏差。异常进告警，人来裁定。
- **`bad_tick` 会误伤新股首日与复牌**。这两类不受涨跌停限制，看到告警先排除。
