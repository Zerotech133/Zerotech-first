# RAG-Web 联动设计

## 目标

在现有本地 Ollama Web 聊天页中增加知识库问答模式，让用户可以对 `knowledge_docs/` 中的文档提问，并看到回答依据的来源。普通聊天链路继续保持现有行为。

## 范围

- 保留现有 `POST /api/chat` 普通聊天接口。
- 新增 `POST /api/rag` 知识库问答接口。
- Web 页面增加普通聊天/知识库问答切换和来源展示。
- 服务启动或首次 RAG 请求时读取 `knowledge_docs/`，建立内存索引。
- 使用现有 `KnowledgeBase` 的切块、`bge-m3` 嵌入、余弦检索和上下文提示词。
- RAG 回复仍通过 NDJSON 流式返回，并在流末尾发送来源元数据。

## 接口契约

请求：

```json
{"message":"问题", "top_k":4}
```

响应为 NDJSON：

```json
{"message":{"content":"回答片段"}}
{"sources":[{"source":"knowledge_docs/…","score":0.82}]}
{"done":true}
```

请求消息为空、`top_k` 非正整数或超过 8 时返回 400。Ollama 不可用时返回 502，并隐藏底层异常细节。没有命中时仍返回明确的“我不知道”，来源为空。

## 数据流

1. Web 处理器校验 JSON 请求。
2. RAG 服务按文档目录和修改时间缓存索引；首次使用时调用 `KnowledgeBase.read_documents()` 和 `ingest()`。
3. `KnowledgeBase.search()` 返回 Top-K 文本、来源和分数。
4. 服务调用 `qwen3.5:9b`，只注入命中的上下文。
5. 服务先流式转发回答，再发送来源记录和结束记录。

索引只保存在进程内，不写回原始文档；后续可通过已有 `save/load` 接口显式持久化。

## 错误与兼容性

- `/api/chat` 的请求格式、模型白名单、NDJSON 转发和 8899 端口不变。
- RAG 目录不存在或没有支持的文档时，接口返回可读的 503 错误，不启动空索引。
- 上游流已经开始后发生网络中断时，不发送第二个 HTTP 响应，只结束当前流并记录错误。
- 所有服务仍只绑定 `127.0.0.1`，不引入第三方 Python 依赖。

## 验证

- 单元测试覆盖请求校验、首次索引、Top-K、来源记录、无命中、Ollama 错误和普通聊天回归。
- 使用 fake client 验证 NDJSON 和提示词，不依赖模型生成稳定文本。
- 使用本机 Ollama 做一次真实冒烟：`/api/rag` 返回 200、至少一条回答片段和来源记录。
- 运行核心、RAG、Web 全部现有测试以及 `py_compile`。

## 不做的事

- 不改 CLI 的交互命令和历史格式。
- 不增加文件上传、用户认证、数据库或前端框架。
- 不把 RAG 索引自动写入仓库或覆盖知识文档。
