- **编号**：2026-11-03_ID_CHAIN_v1
- **配套**：`docs/standards/2026-11-03_接口对接规范_IFS_v1.md`（IFS-04）、`docs/standards/INTERFACE_REGISTRY_v1.yaml`（`id_chain` 段）
- **依据**：`deliverables/2026-11-03_接口对接规范IFS_v1与整改计划.md` §IFS-04、§三、§四
- **性质**：规范层定稿（本单只写文档/登记表，不改 pool / paper / registry / portal_api.py，不启动服务）
- **一句话**：**一条候选从进池到训练回放，全程只认 11 个 ID；每个 ID 只有一个权威生成方，下游必须携带上游 ID，链上不许有空洞。**

## 一、目的与范围

现状（11-03 审计实证）：

```text
code vs candidate_id            （同一股票在不同接口名字不同）
receipt_id vs handoff_id        （同一交棒回执双名混用）
run_id / decision_id / confirmation_id / trade_id 无统一链
D1 decision_id 未传到 handoff / watch / confirmation / paper
paper ledger 有 hash 无 decision/handoff ID（P1 实证）
```

本规范把「池 → 卡 → 案 → 裁决 → 交棒 → 盯盘计划 → 触发 → 人工确认 → 模拟成交 → outcome → 训练 episode」串成**单链**：

```text
pool_id → card_id → case_id → decision_id → handoff_id
  → watch_plan_id → trigger_id → confirmation_id
  → trade_id → outcome_id → training_episode_id
```

适用范围：ACAD1 池、D1 研究/裁决/交棒、WA 盯盘、人工确认门、TR1 paper 执行、outcome/训练、数据仓/Hermes/门户只读消费。

## 三、实体定义（格式 + 生成方 + 上下游）

> 格式约束同时登记在 registry（`id_chain.entities[*].format`），契约测试逐项编译校验。

### 3.1 `pool_id`（池批次）

| 项 | 值 |
|---|---|
| 格式 | `^ACAD1-REC-\d{8}$`（如 `ACAD1-REC-20261102`） |
| 权威生成方 | ACAD1 池发布器（`acad1.pool.get`）；PG 写入方为 ACAD1 任务，门户 JSON 仅为投影 |
| 真源 | 智策 PG `zhice_os_v2.public.v2_acad1_pool`；contract `zerobond.selection.v2_acad1_pool@1.0.0`（ADR-018） |
| 上游 | 无（链根） |
| 下游 | `card_id` |
| 幂等 | 同 `data_date` 重复发布 → 覆盖同 `pool_id`，不产生第二池 |
| 当前实证 | `agent_platform/data/recommendation_pool/latest.json`：`pool_id=ACAD1-REC-20261102`、schema `acad1_recommendation_pool/v1`、36 只（JSON 投影）vs PG 30 只（官方）→ **P0-1 双池并存，F2 收口** |

### 3.2 `card_id`（池内单卡）

| 项 | 值 |
|---|---|
| 格式 | `^ACAD1-CARD-\d{8}-[0-9A-Za-z._-]{1,16}$`（规划） |
| 权威生成方 | ACAD1 卡构建器（随 `acad1.pool.get` 发布） |
| 真源 | PG `v2_acad1_pool` 卡视图（规划）；当前 JSON `items[].item_id=REC-YYYYMMDD-NNNNNN` 为**代理** |
| 上游 | `pool_id` |
| 下游 | `case_id` |
| 当前实证 | 仅有 `item_id`/`code`，无 `card_id`/`candidate_id`（P0-5）→ F2 正式化；迁移期允许 `card_id := item_id` 兼容读，但写侧只能写 `card_id` |
| 禁止 | 用 `code`（6 位股票代码）代替 `card_id` |

### 3.3 `case_id`（D1 研究个案）

| 项 | 值 |
|---|---|
| 格式 | `^D1-CASE-\d{8}-[0-9A-Za-z._-]{1,16}$`（规划） |
| 权威生成方 | `d1.case.upsert`（D1 研究 case store，内部契约） |
| 真源 | `agent_platform/data/d1_cases.jsonl`（规划，F3） |
| 上游 | `card_id` |
| 下游 | `decision_id` |
| 当前实证 | 无 case 账本；D1 研究以 `code/symbol` 承载 → F3 补 |
| 禁止 | 用 `code` 代替 `case_id`（P0-5 明令） |

### 3.4 `decision_id`（D1 裁决）

| 项 | 值 |
|---|---|
| 格式（权威） | `^D1-\d{8}-[0-9a-f]{10}$`（`D1-<yyyymmdd>-sha256("symbol|date|run_id")[:10]`） |
| 兼容格式（待收敛） | `^d1-\d{14}-[0-9a-f]{6}$`（`agent_platform/d1_decision.py::new_decision_id`，人工裁决历史格式） |
| 权威生成方 | `engine/decision_policy.py::decision_id`（延迟 import 单一真源）；落账接口 `d1.decision.create` |
| 真源 | `agent_platform/data/d1_decisions.jsonl`；影子链 `agent_platform/data/shadow/shadow_ledger.jsonl` |
| 上游 | `case_id` |
| 下游 | `handoff_id` |
| 幂等 | 同 `case_id` 重复裁决 → 返回同一 `decision_id`；`d1_decision` 侧按 `decision_id` 去重（duplicate_decision） |
| 偏差 | 双格式并存（**deviation `decision-id-dual-format`**）；F3/F5 收敛到权威格式前，消费方须同时识别两种前缀 |

### 3.5 `handoff_id`（D1 交棒回执）

| 项 | 值 |
|---|---|
| 格式 | `^d1h-\d{14}-[0-9a-f]{6}$`（如 `d1h-20261103120000-a1b2c3`） |
| 权威生成方 | `agent_platform/d1_handoff.py::new_receipt_id`；接口 `d1.handoff.create` |
| 真源 | `agent_platform/data/d1_handoffs.jsonl`（append-only 回执账本） |
| 上游 | `decision_id`（v2 强制：handoff 必须携带 `decision_id` + `watch_plans[]`） |
| 下游 | `watch_plan_id` |
| 幂等 | 重复建回执 → `duplicate_receipt`（400）；ack 按 `handoff_id` 幂等（`already_acked`） |
| 偏差 | 旧字段 `receipt_id` = `handoff_id`（**deviation `receipt-id-alias`**）：对外只写 `handoff_id`，`receipt_id` 仅兼容读 |
| 当前实证 | `d1_handoff/v1` 已有（target/action/rationale/buy_zone/stop/trigger），无 `watch_plans[]` → F3 扩 v2 |

### 3.6 `watch_plan_id`（盯盘计划）

| 项 | 值 |
|---|---|
| 格式 | `^wp-\d{8}-[0-9a-f]{6}$`（规划） |
| 权威生成方 | `watch.plan.create`（WA1 handoff 消费器） |
| 真源 | `agent_platform/data/watch_plans.jsonl`（规划，F3 WO-IFS-WATCHCONS） |
| 上游 | `handoff_id` |
| 下游 | `trigger_id` |
| 幂等 | 同 `handoff_id` 只生成一个 armed plan（重复消费返回同一 plan） |
| 当前实证 | **缺**；WA1/2/3/WATCH_TOWER 无 armed plan 账本（P0-2 消费方=0） |

### 3.7 `trigger_id`（盯盘触发）

| 项 | 值 |
|---|---|
| 格式 | `^trg-\d{8}-[0-9a-f]{6}$`（规划） |
| 权威生成方 | `watch.trigger.create`（`agent_platform/watch_trigger_adapter.py` 扩展） |
| 真源 | `agent_platform/data/watch_triggers.jsonl`（规划，F3 WO-IFS-TRIGGER） |
| 上游 | `watch_plan_id` |

| 幂等 | 同 plan + 同行情快照 → 同 `trigger_id`；adapter 侧按 `source_report_id` 防重复确认 |

### 3.8 `confirmation_id`（人工确认）

|---|---|

| 当前实证 | 已有 `trading_bot_confirmation/v1`，但仅承接 `source_report_id`（P0-3/P1）→ F4 补四 ID |

### 3.9 `trade_id`（paper 成交/账本条目）

| 当前实证 | ledger 行仅有 `date/ts/symbol/recommendation/action/...` + `prev_hash/hash`，**无 trade_id**（P1 实证）→ F4 补 |

## 四、命名与格式总则

1. **前缀 + 时间 + 短随机/哈希**：`<prefix>-<yyyymmdd 或 yyyymmddHHMMSS>-<hex/short>`；十六进制统一小写，`confirmation_id` 例外（大写，历史既有）。
2. **一个 ID 一个生成方**：生成逻辑只能存在于 `id_chain.entities[*].generator.component` 指定位置；其它模块只能透传/校验，不得自造。
3. **不透明消费**：消费方不得解析 ID 内部语义做业务判断（时间/代码只作审计线索）。
4. **上游 ID 必携带**：下游记录必须有 `upstream_id` 字段（即上表「上游」列），并同时保留完整链（便于一跳回溯与全链追溯）。
5. **禁止别名歧义**：`receipt_id` → `handoff_id`；`candidate_id` → `card_id`；`code` 仅作为标的代码字段，不得当 `case_id/decision_id` 使用。
6. **ID 不复用**：任何实体 ID 一经生成即不可复用（重跑用幂等返回，不换 ID）。

## 五、当前实现状态与空洞

| 链路 | 状态 | 实证 | 缺口/整改 |
|---|---|---|---|
| `pool_id → card_id` | ⚠️ 半有 | 池 JSON 有 `pool_id`；卡只有 `item_id`/`code` | F2 `WO-IFS-ACAD1-20261103` 正式 card_id + 读 PG |
| `card_id → case_id` | ❌ 缺 | 无 case 账本 | F3 `WO-IFS-HANDOFF-20261103`（case store） |
| `case_id → decision_id` | ⚠️ 半有 | `d1_decisions.jsonl` 有 decision_id；双格式 | F3 收敛 decision_id 生成方 |
| `decision_id → handoff_id` | ⚠️ 半有 | handoff/v1 无 decision_id 字段 | F3 `d1_handoff/v2` 携带四 ID + `watch_plans[]` |
| `handoff_id → watch_plan_id` | ❌ 缺 | 消费方=0 | F3 `WO-IFS-WATCHCONS-20261103` |
| `watch_plan_id → trigger_id` | ❌ 缺 | adapter 直接建 confirmation | F3 `WO-IFS-TRIGGER-20261103` |
| `trigger_id → confirmation_id` | ⚠️ 半有 | confirmation 有 `CFM-`，缺四 ID | F4 `WO-IFS-CONFIRM-20261103` |
| `confirmation_id → trade_id` | ⚠️ 半有 | paper ledger 有 hash 无 trade_id | F4 `WO-IFS-PAPER-20261103` |
| `trade_id → outcome_id` | ⚠️ 半有 | outcome 行无 outcome_id | F5 `WO-IFS-OUTCOME-20261103` |
| `outcome_id → training_episode_id` | ❌ 缺 | 无 episode 数据集 | F5 `WO-IFS-TRAIN-20261103` |

> 验收（IFS 计划 §五）：`pool_id → decision_id → handoff_id → watch_plan_id → confirmation_id → trade_id → outcome_id` 全链可追（F7 `WO-IFS-E2E-20261103`）。7 个空洞已登记在 registry `id_chain.gaps`，契约测试锁定「gaps == draft 实体集合 − {decision_id}」。

## 六、不变量（MUST）

1. **单一生成方**：每个实体 ID 只允许 registry `generator.interface` 声明的接口生成；其它接口只能透传。
2. **链上无空洞**：11 实体缺一不可；`id_chain.order` 与上下游邻接表必须自洽（契约测试校验）。
3. **上游必携带**：下游记录必须保存上游 ID；缺上游的记录一律 `unknown`（不猜 pass）。
4. **跨链禁止**：`trade_id` 不得跨 `confirmation_id`；`outcome_id` 不得跨 `trade_id`/`decision_id`；跨记录聚合用数组，不复制 ID 语义。
5. **幂等四层**：decision / handoff / confirmation / trade 四层各自按上游 ID 幂等（见第七节）。
6. **实盘边界**：任何 ID 链不得通向实盘；`paper_only=true` 恒成立，`trading_permitted=false`（ADR-016）。
7. **回放可追**：给定任一 ID，必须能沿双向指引回溯到 `pool_id` 并前推到链尾（账本+registry 双指引）。

## 七、幂等键与四层幂等

| 层 | 幂等键 | 行为 |
|---|---|---|
| decision | `hash(case_id + symbol + decided_at 请求键)` / 上游 `decision_id` | 重复裁决返回既有 `decision_id`（`duplicate_decision` 或 idempotent_replay） |
| handoff | `decision_id + target + action`（可加 `idempotency_key`） | 重复交棒返回既有 `handoff_id`（`duplicate_receipt` → 建议改 200 + warning `idempotent_replay`） |
| confirmation | `source_report_id`（现状）/ 目标：`trigger_id` | 同 report/trigger 返回同一 `confirmation_id`；重复 approve → `conflict`（不重复执行） |
| trade | `confirmation_id`（+ date+symbol 现状 seen 键） | `duplicate: true`，不重复记账（paper_book.existing_keys） |

统一约定：写接口接受 `Idempotency-Key` 请求头；同 key 重复请求返回 `ok=true` + `warnings[].code=idempotent_replay`（HTTP 200），不得返回 `duplicate`（409）除非语义冲突。
