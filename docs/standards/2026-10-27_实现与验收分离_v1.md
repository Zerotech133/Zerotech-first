# 实现与验收分离 v1（O4）

- **日期**：2026-10-27｜**依据**：O4 优化项；参考 OpenHands "implementer 不得修改 verify-* 验证 skill"、Lean "每个 PR 必须带测试" 的独立性原则
- **工具**：`tools/dev_acceptance_audit.py`（只读审计）
- **性质**：制度+审计工具；**暂不阻断合并**（warn 观察，后续按数据决定是否 block）

## 一、为什么

"谁实现谁写验收"会导致：验收命令迎合实现、失败被改测试掩盖、审计无法判断"真的可用"。
成熟项目把"实现"与"验证"分开：实现者可以自测，但**验收判据与验证脚本由非实现者维护**。

## 二、规则

1. **验收人独立**：dev 单必须在 desc 标注 `验收人=<席位>`（如 `验收人=QA1`），且**不能等于实现者/owner**；ARCH1/QA1 可作为验收人。
2. **验收命令**：dev 单必须有 `acceptance_cmd`（`devtask.py new --dept dev --acceptance "..."`），命令须可复跑、输出可判读。
3. **验证资产只读**：实现者不得在实现 PR 中修改：`tools/*_check.py`、`verify-*`/审计基线、`test_baseline.json`、验收脚本；如需改，单独"验证资产 PR"并说明理由。
4. **自测允许**：实现者可自测并附证据，但**不得作为唯一验收**；合并前至少一条非实现者验收记录（回执/审计）。
5. **P0/安全类**加强：L2/安全相关变更须由 ARCH1/QA1 之一复核（同一人不得既实现又复核）。
6. **存量宽限**：已建单可在回填时补 `验收人=`；新单强制（2026-10-27 起）。

## 三、审计与执法

```powershell
python -X utf8 tools/dev_acceptance_audit.py             # 人读
python -X utf8 tools/dev_acceptance_audit.py --json      # 机器读
python -X utf8 tools/dev_acceptance_audit.py --strict    # 有缺口 → rc=1（暂不接合并门）
```

- 审计字段：`acceptance_cmd` 缺失、desc 缺 `验收人=`、验收人=实现者；
- 当前为 **warn 观察期**；2 周后评估：若新单合规率 ≥90%，在 devtask 门加 warn（不 block），再观察 2 周决定 block。
- 审计结果进 C6 日报/周报（与验收覆盖率口径合并）。

## 四、与其它项关系

- O2 质量分级 Silver 的 `acceptance` 字段应由验收人确认；
- O5 E2E 场景集由 QA1 维护（实现者不改验证资产）；
- D2 门禁/夜跑可调用本审计（warn 输出）。
