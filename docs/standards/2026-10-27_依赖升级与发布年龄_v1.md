# 依赖升级与发布年龄策略 v1（O8 P3 草案）

- **状态**：草案（**不阻断**当前安装/升级）；**P3b 检查脚本已实现（2026-10-28，只读 warn-only）**，P3c/P3d 待定
- **日期**：2026-10-27｜**依据**：O8 方案；参考 OpenHands「新版本发布满 7 天才允许升级」的依赖治理实践
- **适用范围**：`requirements/`、`pyproject.toml`、`uv.lock`、各线 lock 快照（**不含** `py312`/智策活系统，后者另行立项）

## 一、为什么

当前运行线依赖无升级纪律：新版本可随时被装上，缺少"冷却期"与升级记录；供应链/兼容性风险只能在故障后暴露。
引入 **7 天发布冷却**：只有发布满 7 天的版本才允许进入锁文件/安装，安全例外单独走批准。

## 二、规则

### 2.1 基本规则

1. **冷却期**：候选版本在 PyPI 的发布时间 ≥ **7×24 小时**，才允许写入 requirements/lock 或安装到运行线；
2. **升级留痕**：每次锁/依赖变更需记录：包名、旧版本→新版本、发布日期、升级原因（安全/功能/兼容）；
3. **不自动升**：本机无 dependabot；升级由人工/Agent 按需发起，禁止"装环境时顺手升级"；
4. **最小变更**：一次升级只动必要包；锁文件与 `pip freeze` 快照同步更新；
5. **快照更新**：`requirements/lines/*.lock` 在升级后重新生成，diff 入回执。

### 2.2 例外（安全/紧急）

- 有 CVE/安全通告的包可**不受 7 天限制**，但需：
  1. 记录 advisory/CVE 编号与发布日期；
  2. 老田（或 A0 授权人）明确批准；
  3. 升级后跑受影响线的最小验证（测试/重启按 L2 规则）；
- 例外不得被"顺手"复用；每次单独记录。

### 2.3 不适用

- dev 工具链（pytest/ruff 等，D5 `uv.lock`）也建议遵守，但优先级低；
- 已 EOL/不再维护的包不强行升级（记录原因）；
- 容器镜像/OS 包不在本策略范围。

## 五、检查脚本（P3b，已实现）

```powershell
# 默认检查 requirements/lines/*.lock + uv.lock；只读
python -X utf8 tools/dep_age_check.py
# 冒烟（前 20 包）
python -X utf8 tools/dep_age_check.py --limit 20
# CI 用：fresh/error 时 rc=1（仍不改安装）
python -X utf8 tools/dep_age_check.py --strict --json
```

```text
输入：requirements/lines/*.lock（pip freeze）或 uv.lock（TOML）
步骤：解析 name==version → 请求 PyPI JSON（pypi.org/pypi/<pkg>/json，只读，并发 8，失败记录 error）
判断：release 时间 < 7 天 → warn（列出包/版本/发布日期/年龄天数）
输出：warn 列表 + 统计 + files；--json 机读；--strict 才 rc=1，默认 warn-only
```

- 依赖网络：请求失败记为 error 并继续（fail-open，不阻断）；
- 不缓存敏感信息；不自动升级；不修改 lock；
- 单测 `tools/test_dep_age_check.py`（不联网，mock fetcher）。

## 六、风险与边界

- 7 天冷却可能延迟重要修复 → 安全例外覆盖；
- PyPI 查询受网络影响 → fail-open，仅提示；
- 本机单用户，无 CI 强约束 → 先靠纪律+回执，后续再接门禁。
