### 1.2 核心诊断（五个问题，2026-10-17 探测实证修正）

0. **【修正×2】nginx 已部署——Docker 容器 ai-portal，:8080**：本条经历两次翻案（①误判 conf=已部署 :80（实为 IIS）；②误判「从未部署」——本机进程名+单端口探测对容器化服务失明）。真相：`ai-portal` 容器（nginx:alpine，restart unless-stopped）跑 portal/nginx.conf，端口映射 `0.0.0.0:8080->80`，挂载源 `C:\项目\老田的AI助手\portal`（conf+webroot 实时 bind mount），启动器 = start_portal_nginx.ps1。**前端正门 = `http://127.0.0.1:8080/`**（8091 根路径自身也 302→8080）。设计稿里 30+ location 大部分在线（/quant /paper /screen /portal /sys-health 探测 200），个别短路由（如 /picks）从未配置——picks.html 只能裸文件路径访问
1. **门面无总览**：/ 直出旧 index.html（AI 听堂），无健康/动线/摘要聚合门面——20+ 页面的访问全依赖页面内链或记忆
2. **导航骨架已存在但未挂新门面**（P1 侦察修正）：static/nav.js（tools/export_nav.py 自动生成 ← api_common.py DOMAIN_NAV_GROUPS）已实现五域下拉导航（quant/intel/creator/dev/ops）+ 动线条，全站页面共享注入；hermes/8097 在导航中仍是端口直连（http://127.0.0.1:8787/:8097），未走路径挂载
3. **观测盲区**：四件套（gate/review/qd/card）是告警链核心，但只有裸 metrics 端点；判例体系的核心动作「七口判活」无页面化呈现，每次靠终端命令
4. **孤岛冗余**：8097 指挥台已自带 KPI/健康表雏形，与将建的门户/观测页能力重叠，需划清边界避免两处维护

## 二、重规划目标与原则

**目标**：一层门面（总览门户）+ 三层台面（portal 业务 / hermes 对话 / 指挥台运维）+ 一层诊断（四件套观测），全部经 nginx 一口进入。

> **前置决策（已消解，2026-10-17 P1 侦察）**：nginx 已在跑——ai-portal Docker 容器，`0.0.0.0:8080->80`，挂载本方案涉及的 portal 目录。无需部署/无需端口决策（80 被 IIS 占用的事实不再相关）。方案统一以「nginx :8080」表述。

**原则**：
- 零新框架：原生 html+fetch（同仓 static 惯例，无构建链）
- 不 Fork hermes 本体：开源项目保持升级友好，只做 nginx 挂载 + 本地主题
- 判例可视化优先：端口判活/born>mtime/契约行这些判例体系动作，能上页面的上页面
- 后端聚合探针：健康状态由 8091 一口聚合（服务端探各口），前端不跨域逐口探测

## 四、页面规划明细

### 4.1 总览门户 `/`（新建，P1）

**定位**：每天打开的第一个页面，10 秒内回答「系统是否健康、今天发生了什么」。

三区布局：

| 区 | 内容 | 数据源 |
|---|---|---|
| A 健康总览 | 七口卡片（8091/8097/8787/9101-9104）：绿/红 + PID + 存活时长；计划任务条（TushareSync/JevBackfill/JevStack：last rc + next） | 8091 聚合探针接口（新建 `/api/health`，服务端探活——复用判例3 端口判活逻辑） |
| B 快捷入口 | 入口矩阵按使用频率分组：交易（picks/paper/screen）/ 研究（quant/kg/chanlun）/ 对话（hermes/mission）/ 运维（push/stack/ops/audit） | 静态配置 |
| C 当日摘要 | 今日推送量 + 判定量 + backlog + 死信数 + 晨报要点 | 8097 现有 KPI 接口 + review 日志统计 |

**交互**：卡片点击跳对应台面；红状态卡点击直达 `/stack` 诊断页；30s 自动刷新。

### 4.2 四件套观测页 `/stack`（新建，P2）

**定位**：告警链出了问题 30 秒定位（替代终端 grep 日志）。

| 模块 | 内容 | 数据源 |
|---|---|---|
| 实时指标 | gate 队列深度 / review 命中率 / qd 桥流量 / card 推送量（拉 /metrics 解析渲染，无需 prometheus server） | 9101-9104 /metrics |
| 换血状态 | 四件套当前 PID + jev-stack.log 最近 pulled up/matched 时间——**born>mtime 判例的可视化** | 日志尾部接口 |
| 判定链 | ai.log 最近 jev_judge 行流（LOCAL/REMOTE 命中、fail 计数） | 日志尾部接口 |
| 死信面板 | 死信文件数 + 最近条目 + 一键重放（POST） | news.db 查询接口 |

**交互**：15s 自动刷新；指标超阈值行内标红；死信重放需二次确认。

### 4.3 推送中台指挥台 `/push`（增强，P3）

现有 KPI/健康表保留，增量三块：

| 增量 | 说明 |
|---|---|
| FOCUS_CN 影子组面板 | 昨晚换血刚生效的影子组（signal_review FOCUS_CN）：影子样本数 n_eff、quality_p 刻度、转正倒计时（n_eff≥30）——新功能的观测位 |
| guard 触发器状态 | HermesWebUI-Guard/JevStack/TushareSync 三个守护的 next 触发 + 白天裸奔缺陷修复后的覆盖图（时间轴条） |
| 推送链路拓扑 | 现有 sources/targets 表升级为桑基图（fbars 已有雏形） |

### 4.4 portal 导航归组（P4）

- 20+ 页按「交易 / 研究 / 对话 / 运维 / 内容」五域归组，注入统一顶部导航条（一段共享 nav.js，逐页 `<script src>` 引入，不动各页主体）
- `/warehouse` 收编 warehouse_dashboard 入导航体系
- nginx location 不动（纯前端侧改造）

### 4.5 Hermes WebUI（挂载，P1 随门户）

- nginx 增 `/hermes` `/mission` `/console` 三条 proxy_pass → 8787
- 本体不 Fork；仅在其 webui-state 侧配主题色对齐门户视觉（可选）

## 六、关键技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 前端框架 | 无（原生 html+js） | 同仓惯例、零构建链、单文件可维护 |
| 健康探针位置 | 8091 服务端聚合 `/api/health` | 前端直探七口=跨域地狱；服务端复用判例3 逻辑一处实现 |
| metrics 渲染 | 前端 fetch + 正则解析 | 四件套指标量小（每口 <20 序列），不值得引 prometheus server |
| 认证 | 复用 portal cainiao_auth | 已有体系，门户/观测页同源免二次登录 |
| nginx 部署端口 | :8080（ai-portal 容器，既有部署沿用） | P1 实证已在跑（0.0.0.0:8080->80）；80 被 IIS 占用的事实不再相关 |
| hermes 集成方式 | nginx 反代挂载 | 保持开源本体可 `hermes update`，Fork 会卡升级（昨晚 source-update 事件印证） |

## 七、风险与边界

- 门户 `/api/health` 新接口落在 8091（zhice），改动其路由表需回归测试——只读探针、无副作用，风险低
- nginx 改动走 reload 不 restart（不断连接）；改前备份 conf（判例惯例）
- 四件套观测页读日志尾部接口需注意大文件（gate.log 5MB+）——接口做 tail N 行限界
