## 1. 目标

将以下两项本地 PostgreSQL 数据资产接入 OpenMetadata，完成服务注册、元数据抓取和验收：

1. `quant-pg`：量化元数据库（宿主 `5442`，库 `quant_meta`）
2. `zhice-db`：智策库（宿主 `5446`，库 `zhice_os_v2`）

本单只做元数据编目，不做数据写入、数据迁移或业务逻辑改造。与 K-STOCK-415 / K-STOCK-416 无依赖，可并行。

## 2. 资产基线

| 资产 | 容器 | 宿主映射 | OM 侧访问方式 | OM 服务名 | 数据库/Schema |
|---|---|---:|---|---|---|
| 量化元数据库 | `quant-pg` | `127.0.0.1:5442` | `host.docker.internal:5442` | `postgres_quant_meta` | `quant_meta`（quant / tdx_info / news / meta） |
| 智策库 | `zhice-db` | `127.0.0.1:5446` | `host.docker.internal:5446` | `postgres_zhice_os_v2` | `zhice_os_v2`（实测 public 表 276 张） |

## 3. 连接方案

OpenMetadata ingestion 容器：

- 容器：`openmetadata_ingestion`
- 网络：`openmetadata_app_net`
- OM API/UI：`127.0.0.1:8585`
- ingestion/Airflow：`127.0.0.1:18080`

两个 PG 容器均已映射宿主端口 `0.0.0.0`，OM ingestion 容器经 `host.docker.internal:5442 / 5446` 直连即可，无需 docker network 热接入。

施工要求：

- 执行前先确认两容器存活及端口映射未漂移（`docker ps` + `docker port`）。
- 不新增宿主端口，不修改现有端口绑定，不重建容器。
- 完成后从 `openmetadata_ingestion` 容器内验证 DNS 和 TCP 连通性。

## 4. 账号与权限

在 `quant_meta` 与 `zhice_os_v2` 两个实例分别创建或确认只读账号，例如：

```sql
CREATE ROLE om_ro LOGIN PASSWORD '<受控凭据>';
GRANT CONNECT ON DATABASE quant_meta TO om_ro;
GRANT USAGE ON SCHEMA quant, tdx_info, news, meta TO om_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA quant, tdx_info, news, meta TO om_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA quant, tdx_info, news, meta GRANT SELECT ON TABLES TO om_ro;
```

`zhice_os_v2` 同理（schema 以实际 `information_schema.schemata` 为准，默认 public）。

实际执行前必须：

- 先确认账号是否已存在，避免覆盖现有凭据。
- 记录授权范围和执行结果。
- 不授予 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`CREATE`、`TRUNCATE` 等写权限。
- 凭据不得提交到 Git、施工单或事件总线。

## 5. OM 服务配置

在 OM UI/API 创建两个 Database Service（PostgreSQL 连接器）：

| 服务名 | 连接串 | 库 |
|---|---|---|
| `postgres_quant_meta` | `host.docker.internal:5442` | `quant_meta` |
| `postgres_zhice_os_v2` | `host.docker.internal:5446` | `zhice_os_v2` |

配置要求：

- 仅勾选 **Metadata** ingestion。
- 首轮**禁用** profiler、usage、data insights。
- 连接方式用只读账号 `om_ro`。
- 每个服务先跑 Test Connection，通过后再建 ingestion。

## 6. Ingestion

- 每个服务一个 metadata ingestion 管道，schedule 建议 manual 或低频。
- 抓取范围：库级 schema → 表 → 列级 schema（类型、可空性、默认值）。
- 记录 ingestion 任务 ID 与日志位置；失败须留失败清单。

## 7. 验收标准

### 连接与权限

- [ ] `openmetadata_ingestion` 可解析 `host.docker.internal:5442 / 5446`。
- [ ] 两个目标库均可用只读账号 Test Connection 通过。
- [ ] 账号仅具备目标库只读权限（写操作实测被拒）。
- [ ] 宿主端口和容器未被额外暴露或重建。

### OpenMetadata

- [ ] `postgres_quant_meta` 服务创建成功并可 Test Connection。
- [ ] `postgres_zhice_os_v2` 服务创建成功并可 Test Connection。
- [ ] 两服务均出现目标库名及其 schema/表，表数与源实例 `information_schema.tables` 实测一致（`zhice_os_v2` 基线 276）。
- [ ] 表具备列级 schema、类型和基本元数据。
- [ ] 两个服务的 metadata ingestion 均成功完成或有明确失败清单。
- [ ] 通过 OM search 查询服务名、数据库名和代表性表实体。

OM search API 注意（2.0.5 实测，2026-10-17 定案）：`index` 参数必须使用 `*_search_index` 形式索引名——表级 `table_search_index`、schema 级 `database_schema_search_index`；旧参数名 `table_search` / `database_schema_search` 会返回 500 `Failed to find index ...`（服务健康，参数过时所致）。验收示例：

```text
GET /api/v1/search/query?index=table_search_index&q=postgres_quant_meta&limit=5&deleted=false
GET /api/v1/search/query?index=database_schema_search_index&q=zhice_os_v2&limit=5&deleted=false
```

或省略 `index` 走默认聚合搜索（亦返回 200）。
