## 七、做对了什么

```text
· 负结果纪律：16 条假设 rejected；reranker 实测下降主动不上线；黄忠自判 5/6 不粉饰。
· 工程还债：portal_api −31%；api_backtest/api_kg 历史拆分 −86%～−93%。
· 安全加固：8734 auth、8103 token、8796 OH 准入、8091 status 403、密码 fail-closed。
· 长跑可靠：JEV 夜跑清空 2,795；备份/质量闸/分支级测试门成型。
· 证据文化：回执普遍带命令、sha、验证矩阵；release artifact 有 manifest/HMAC。
· 快速修复：v6 P0 在 1 小时内连修，说明响应速度极强。
```

## 八、根因

```text
R1 执行速度 > 架构收敛速度
   一夜能修 4 个 P0，但身份/发布/事务模型没时间收口。

R2 完成定义仍是“代码合并/测试绿”
   生产行为没有自动探针，导致 v4/v5/v6 反复出现“假绿/旧快照/报告过期”。

R3 没有单一真源
   身份、模型、计划、任务、交付物、证据各有 2–5 套口径。

R4 并行写 + 生成物提交
   33 个 worktree、826 次 bundle、34 个脏文件，merge 覆盖风险长期存在。

R5 组织扩张优先于能力验证
   席位数增长快于真实任务、记忆、模型绑定、验收数据。

R6 审计/报告自身通胀
   10-30 单日 61 份 audit + 74 份交付物；报告写完即过期，没人消费。
```

## 九、复盘结论

### 应该继续（Keep）

```text
· 负结果如实记录，不把 No-Go 包装成成功
· 小步拆分 + 路由零 diff + 测试门
· 长跑任务先落文件、再汇报
· release artifact + HMAC/manifest
· 每个 P0 有回执、命令、回滚
```

### 应该停止（Stop）

```text
· 继续加席位/加面板/加文档，而不收口上一批
· 把“计划写完”当成“计划执行”
· 把“合并/测试绿”当成“生产生效”
· 用生成物 bundle 提交淹没真实变更
· 审计报告不做有效期/消费闭环
```

### 应该开始（Start）

```text
· 一个发布单元 + build id + live version 探针
· 一个任务账本（devtask 与 TaskStore 合并/同步）
· 一个身份真源（SSO 或明确双登录契约）
· 一个产品闭环：ACAD1 候选 → D1 决策 → outcome
· 一个两周冻结窗口：只收口，不加新面
```
