# 军团 IDE 再研究 v2：可信施工层，而不是第二个 VS Code

- 日期：2026-10-30 19:15
- 工单：`WO-LEGION-IDE-RESEARCH2-20261030`
- 性质：只读研究；**本轮不改生产代码/路由**
- 输入：现场探测 + `docs/audit/2026-10-30_*IDE*` + `docs/plans/2026-10-26_可写可执行IDE_设计与安全方案_v1.md` + 外部对标
- 结论先行：**IDE 核心闭环已成立，但认证边界有一个必须先补的 P0；长期不应自研通用编辑器。**

---

## 一、结论（一页）

| 判断 | 内容 |
|---|---|
| 现在是什么 | 单用户、双前端、三种执行面的 Agent 施工台 |
| 已经成立 | worktree + 锁 + preview/confirm + diff/commit + OH sandbox + 审计 |
| 最大风险 | **`/lde/` 未走统一认证**，可无登录拿 LDE 会话/读 scope；`/ide.html` 静态直链也绕过 `/ide` 认证 |
| 最大战略误区 | 把 LDE 做成“第二个 VS Code/Cursor”：编辑器/LSP/调试器是无底洞，且不是平台差异化 |
| 正确位置 | **Governed Construction Plane（可信施工层）**：管工单、worktree、审批、沙箱、diff、审计、评测；编辑器可外接 |
| 下一步优先级 | 认证边界 → 多文件事务 → 沙箱测试 → context/外部编辑器 → 多人/远程 |

一句话：

> **我们不需要一个更强的编辑器，需要一个让 Agent 改代码“可授权、可回滚、可审计、可评测”的施工层。**

## 二、现场证据（2026-10-30 19:10 左右）

### 2.1 入口

```text
8734 /ide             302 /login?next=/ide        ✅ 有 auth_request
8734 /hermes/         302 /login?next=/           ✅ 有 auth_request
8734 /lde             301 /lde/                   ⚠ 未认证
8734 /lde/            200                          ⚠ 未认证
8734 /lde/rw          200 + Set-Cookie ide_session  ⚠ 未认证即发会话
8734 /ide.html        200                          ⚠ 绕过 /ide 精确路由
8734 /api/bff/overview 200                         （数据面，非页面）
```

### 2.2 后端

```text
8103 /api/health     200 rw_enabled=True
8103 /rw             200
8103 /               200（旧 ide.html）
8796 /api/ide/openhands/sessions 200（有 session）
8787 /health         200
8771 sandbox         Docker 在线
```

### 2.3 新发现的认证边界缺口（P0）

只读探测（没有执行任何写操作）：

```text
GET /lde/rw
→ 200 + ide_session cookie
GET /lde/api/ide/session（带上述 cookie）
→ 200 {"ok": true, "owner": "lde-..."}
GET /lde/api/ide/scope（带上述 cookie）
→ 200，返回可写 worktree 列表
GET /lde/api/ide/tree?task=...（带上述 cookie）
→ 200，返回文件树
```

原因：

- `portal/nginx.conf` 的 `/lde/` 是纯反代，**没有 `auth_request`**；
- 8103 的 `/rw` 只校验同源/cookie，**不校验 8734 登录态**，并且会给任何请求发 `ide_session`；
- `/ide.html` 是静态文件，`location = /ide` 的 auth_request 不覆盖它；
- 直连 `8103 /rw`、`8787 /` 也能拿到页面（本机回环旁路）。

**影响**：任何能打开 8734 的未登录浏览器，都能进入 LDE 施工台并读取可写 worktree 文件树；是否进一步写，只取决于是否拿锁——而锁 owner 来自同一会话。这是认证边界问题，不是 UI 问题。

**修复建议（下一单）**：

1. nginx `location ^~ /lde/` 增加 `auth_request /_auth_guard` + `error_page 401 = @login_required`；
2. `location = /ide.html` 直接 `return 302 /ide`，或同样 auth_request；
3. LDE 要求 nginx 传入可信身份头（如 `X-Auth-Subject`），session owner 从该头派生；无头=403；
4. 8103/8787 保持只绑回环；加“仅允许 8734 反代来源”的启动约束；
5. 增加回归：未登录 `/lde/`、`/lde/rw`、`/lde/api/ide/scope`、`/ide.html` 必须 302/403。

> 这比继续加编辑器功能优先级更高：施工台能读全仓 worktree 但不要登录，等于把“只读边界”也打穿了。

## 三、当前架构评估

```text
旧 /ide (portal/ide.html, 2111 行) ── legacy，仍在线
原生 /hermes/ (Hermes，1194 行 app.js) ── 主前端
  ├─ Agent / Session / Task / Context
  ├─ OpenHands 8796 → 8771 Docker sandbox
  └─ LDE 8103（/lde/ 反代）── 文件树/编辑/Git/锁/exec
```

### 3.1 已经做对的

1. **worktree 隔离**：不在 master 直写，改动天然可 diff/回滚；
2. **工单锁 + preview/confirm + undo**：写路径有两阶段和回退；
3. **执行分级**：OH 走 Docker sandbox，LDE exec 有白名单 + Job Object；
4. **审计回流**：写/执行落 dev_events，工单可追；
5. **质量门**：IDE HTTP 测试已进 fast gate，bundle 契约有测试。

### 3.2 结构性问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 双前端 | 旧 `/ide` + `/hermes/` 并存 | 入口分裂、功能两套、用户不知道用哪个 |
| 双执行面 | OH Docker vs LDE 宿主 Job Object | 安全等级不一致，不能笼统说“已隔离” |
| 认证旁路 | `/lde/`、`/ide.html`、8103/8787 直连 | 未登录可达施工台 |
| 单文件事务 | preview/confirm 一次一个文件 | 跨文件改动无原子提交/整体回滚 |
| 缺验证闭环 | 有 exec，无“改完自动跑测试+结构化结果” | Agent 改完仍靠人肉验证 |
| 缺 context | 有 AST context 端点，无 repo map/符号/引用图 | 大仓改动容易漏依赖 |
| 缺 eval | 无 Agent 改 bug 的成功率/回滚率/工具错误率 | 优化靠感觉，无法证明变好 |
| 前端单体 | app.js 1194 行、LDE 页面单文件 | 长期维护成本上升 |

## 四、外部对标：我们该学什么、不该学什么

| 产品/方案 | 强项 | 弱项/不适用 | 对我们的结论 |
|---|---|---|---|
| VS Code + Copilot/Cline/Continue | 编辑/LSP/扩展/调试成熟；Cline/Continue 可接自有模型 | 不提供平台级工单/worktree/审批/审计 | **编辑器交给它**，我们做治理层 |
| Cursor / Windsurf | 多文件 agent 编辑、内联 diff、体验好 | 闭源、云端、无本地治理链 | 学“多文件 diff 体验”，不复制 |
| OpenHands | sandbox agent runtime、tool/MCP、sessions、SDK、Agent Canvas | 不替我们管工单/锁/审批/平台审计 | **执行引擎继续用/借鉴**，不重写 |
| Aider / Codex CLI / Claude Code | git-native、终端高效、强 repo 操作 | 无 UI、无审批、无多用户治理 | 作为“高级用户入口”可接 |
| JetBrains AI | IDE 原生、企业权限 | 重、闭源、平台集成成本高 | 不选 |

外部参考：

- [OpenHands Software Agent SDK](https://docs.openhands.dev/sdk/index)
- [OpenHands Agent Canvas](https://docs.openhands.dev/openhands/usage/agent-canvas/overview)
- [OpenHands GitHub](https://github.com/OpenHands/OpenHands)
- [Cline](https://github.com/cline/cline)
- [Continue](https://github.com/continuedev/continue)
- [VS Code Copilot](https://code.visualstudio.com/docs/copilot/overview)
- [Aider](https://aider.chat)

**战略判断**：

- 我们的差异化不是“编辑器功能数量”，而是 **任务/工单/审批/审计/评测**；
- 通用编辑能力应**外接**（VS Code Remote / Continue / Cline），LDE 保留“小改 + 审批 + diff”；
- OpenHands 是执行引擎，不把它当 UI 平台；
- 不要把 `/hermes/` 做成第二个 Cursor。

## 五、目标架构（建议）

```text
┌──────────────────────────────┐
│ 编辑器层（可替换）              │
│  - 浏览器 Hermes：小改/审批/diff │
│  - VS Code/Cline/Continue：大改  │
└──────────────┬───────────────┘
               │ 统一 API / MCP / CLI
┌──────────────▼───────────────┐
│ 可信施工层 LDE（平台核心）       │
│  - 工单/worktree/锁/身份         │
│  - 多文件事务 + diff + 回滚      │
│  - 审批队列 + 审计 hash 链       │
│  - 测试/验证结果结构化           │
│  - Agent eval 指标               │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ 执行层（分级）                  │
│  - OH Docker sandbox（默认）     │
│  - 低权限容器（升级）            │
│  - 宿主 Job Object（仅人工白名单）│
└──────────────────────────────┘
```

关键原则：

1. **一个入口**：`/hermes/` 是人的主入口；`/lde/` 是 API/施工台，不作为人肉入口宣传；
2. **写必须绑定身份**：session owner 来自门户身份，不由客户端自报；
3. **一个执行默认**：默认走容器；宿主执行必须显式标记“人工白名单”；
4. **所有改动可回滚**：文件级 undo → 多文件事务 → 工单 checkpoint；
5. **所有 Agent 行为可评测**：成功/失败/回滚/工具错误都进指标。

## 六、路线图（建议）

### P0：认证边界收口（1–2 天）

- `/lde/` 加 auth_request；`/ide.html` 302 `/ide`；
- LDE 身份头/会话绑定门户；
- 未登录回归测试进 fast gate；
- 旧 `/ide` 只读或明确“legacy，仅旧页保留能力”。

**验收**：

```text
未登录 /lde/、/lde/rw、/lde/api/ide/scope、/ide.html → 302/403
登录后 /hermes/ → 200，LDE 可操作
直连 8103/8787 不再能无身份写
```

### P1：多文件事务 + 验证闭环（1–2 周）

- 一次 preview 支持 N 文件，生成统一 diff；
- confirm 原子写入（失败全回滚）；
- 任务级 checkpoint/restore；
- 测试 runner：只允许白名单测试命令，结构化输出 pass/fail/耗时；
- 审计事件链式 hash。

**验收**：一个跨 3 文件的小任务可一次预览、一次确认、一次回滚；测试结果可追到 run_id。

### P2：Context + 外部编辑器（2–4 周）

- repo map / 符号 / 引用（tree-sitter 或 LSP 只读）；
- VS Code Remote/Continue 接入 LDE API；
- MCP 工具注册表统一；
- Agent eval：固定 20 个真实小任务，测成功率/回滚率/工具错误率。

### P3：多人/远程（按需，不默认）

- 多用户身份、权限、审批；
- 远程 worktree/SSH；
- 多租户不做。

## 七、不建议做

- ❌ 自研完整编辑器（LSP/调试器/插件市场）；
- ❌ 把 Cursor/Windsurf 当竞品逐项抄；
- ❌ 多用户/公网暴露优先；
- ❌ 在 LDE 里跑任意宿主命令；
- ❌ 用“按钮数量”衡量 IDE 进展。

## 八、需要老田拍板的问题

1. **用户模型**：是否永远“老田 + Agent 单用户”？若是，不做多用户，先做可信施工。
2. **旧 `/ide`**：给一个退役日期，还是保留只读？
3. **编辑器路线**：浏览器 Hermes 为主，还是接 VS Code/Continue 做深度编辑？
4. **P1 优先级**：多文件事务 vs context/repo map，哪个先？
5. **执行默认**：是否强制 OH Docker，LDE 宿主 exec 只保留人工白名单？
