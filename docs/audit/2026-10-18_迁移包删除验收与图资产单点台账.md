## 三、新增风险与已做缓解

**风险（本次删除直接造成）**：图资产从"卷内 + 包内 dump"两份，降级为**仅命名卷单点**。
若该卷损坏/误删，无离卷副本可恢复——这是删除带来的唯一实质代价。

**已缓解（本台账同批执行）**：

- 停 `neo4j-kg` → 用临时容器 `neo4j-admin database dump neo4j --to-path=/data/backups` → 起容器，**全程约 50 秒**
- 转储结果：**90 个文件 / 2.329 GiB / 18.9 秒 / DUMP_RC=0 / "Dump completed successfully"**
- 离卷落盘：`C:\项目\backups\neo4j-20261018.dump`（**321 MB**）
- SHA256：`999743ccb9dc5a939aee2f5785ae8eb63a88435aedeb6cb33513ef4cace70078`
- 卷内临时副本已清理，`/data` 回位 2.6 GB；容器重启后 `nodes=1,569,799` **不变**，零损

**恢复演练（已做，PASS）**：为不占用主库，用**独立临时卷 + 临时实例**演练，全程不停生产库。
初始计划曾判断 Community 版无法建临时库，后来改变思路：不是建第二个库，而是**换一个空卷跑同样的主库名**。

| 步骤 | 结果 |

| `neo4j-admin database load neo4j --from-path=/tmp/drill --overwrite-destination=true` | **90 文件 / 2.329 GiB / 4.393 秒 / LOAD_RC=0** |

| 清理 | 容器 + 演练卷已删，残留检查仅剩 `neo4j_kg_data`；生产容器未受影响 |

结论：**该转储是可恢复的、恢复后数据与源库逐位一致**，不只是"已生成"。
