- 上游：ADR-015（内核契约）、ADR-016（唯一宿主）、ADR-017（黄金路径，Proposed）、`docs/architecture/PLATFORM_FRAMEWORK_v1.md`（ZBF v1）
- 读取范围：`C:\项目\老田的AI助手` 全仓 + `C:\项目\deliverables` + 外部资产（zhice/知识库/PDF/Docker 依赖）+ 运行态（端口/计划任务/STATUS）

## 〇、结论速览

1. **能结合，但不能"直接套"**：按资产形态估算——**约 55%–60% 可直接纳管**（已是注册表/契约/manifest/门禁形态或只需包一层）；**约 25%–30% 需适配/解耦**（门户巨石、量化脚本、情报采集、智策寄居、通道）；**约 10%–15% 应冻结/退役/外部化**（双计费、legacy 入口、一次性脚本、外部产品）。
2. **最卡的 5 件事**（详见 §4）：
   ① 无"唯一战略源"（ROADMAP v3 已 superseded，307 份计划、297 台账）；
   ② 门户呈现层是 131k 行 Python + 127 页 + 150 nginx location 的巨石，双注册、无页面清单；
   ③ 智策横切寄居（8 router/10 表/27 脚本/6 页/7,599 行）+ 双栈双入口；
   ④ 声明层不接执行点（tool_matrix 29/67、agent_policy 不接线、skill 双向漂移）；
   ⑤ 双池/数据口径（19 vs 30）+ dataset_registry 无 pg_table/无 C:\Temp 覆盖。
3. **框架自身也还没到"能装载存量"**：P1 的 `composition.py`/`kernel_guard`/五类 resolver 未实现；6 个影子组合只过 schema，strategy/dataset/page/job 引用未解析。
4. **正确顺序**：先做 **W0 存量分级/收编**（否则框架继承全部债）→ W1 组合纳管 → W2 运行态单栈（L1）→ W3 关键解耦 → W4 全面组合化。不要先大规模迁移。

## 五、能直接结合 / 不能直接结合（分类结论）

### 5.1 可直接结合（先纳管，不改实现）

1. **agent_platform 注册表/任务/审批/记忆**：已经是"注册表存源 + 契约"形态，包一层 Seat 描述符即可做 C1；
2. **dataset registry + data_contract_check + lineage**：已是数据契约种子，补 pg_table/Temp 后可做 C6；
3. **extensions manifest + lint**：已是插件契约，扩类型即可挂组合能力包；
4. **devtask 九门 + ADR/质量分级**：就是 K8 治理内核，无需重写；
5. **route inventory + tokens/nav/page_shell/shortscreen**：呈现层"横切资产"可直接成为 K6 内核；
6. **strategy_registry + trading_bot.json 六段 + S1–S5**：策略/流水线插件化的现成模板；
7. **6 个影子组合**：P0 已建，P1 补 resolver 后即可真装载。

### 5.2 需适配（改造量可控）

- 门户页面：补页面 manifest/分派表化后纳管；
- 量化脚本矩阵：包 job manifest + data contract，不改脚本内部；
- 情报/内容采集：补 C6/C7/C8 清单与数据契约；
- 智策：L1 同源反代/单认证，L2 降为 `services/quant`；
- Hermes/OpenHands/DSH/OpenClaw：定位为运行适配器（不进内核）；
- 飞书/通知：做通道包（C8）。

### 5.3 不建议纳入框架 / 应冻结退役

1. **一次性分析脚本**（research/tmp 下大量）：转 `legacy/` 或 `deliverables`，不进组合；
2. **legacy 入口/旧服务**：8080 第二入口、8102 旧 API、5175 dev 依赖、旧版页面（无入口/无引用）；
3. **重复运行器/旧代 Hermes/CowAgent**：择机退役（先列清单）；
4. **外部产品**：RAGFlow/OpenMetadata/Neo4j/Phoenix/PocketID/Ollama/llama.cpp 等作为外部资源，不进内核（可写 adapter/清单）；
5. **双计费中的一套**：待 Of Record 决策后归档。
