## 〇、执行摘要

### 0.1 总体判断

zhice-OS V2 已形成一个覆盖面较广的多市场量化工作台：CN、US、HK、CRYPTO 四市场导航、行情、候选、策略、计划、风控、授权、模拟执行、持仓、账户、复盘、学习、治理、监控和调度均有真实页面或后端实现。桌面端的信息架构和统一市场工作区已经具备内部演示价值；全新数据库迁移、API 认证、Docker 中的迁移与调度服务较上一轮有明显进步。

但系统当前仍是 **Technical Preview（技术预览版）**，不能作为真实资金交易系统发布。阻断原因不是“页面还少”，而是多处控制功能与真实执行链脱节，同时交易状态与账本不能保证原子一致：

1. 一个只接收单一价格的接口仍能关闭所有市场、全部策略的全部持仓；VIEWER 角色也能调用。
2. 设置页的手动/半自动/全自动模式和四项风险参数虽能保存，但没有进入下单、熔断、止损执行链，界面给用户造成错误安全感。
3. 授权执行增加了原子 claim，但失败后可能永久停在 `EXECUTING`；无成交结果时仍可被标记为 `EXECUTED`，授权、订单、成交、持仓也不在同一事务。
4. 默认测试入口会运行真实 PostgreSQL 调度测试并主动执行盘前、盘中、盘后等作业，开发机或 CI 可能误连并修改现有数据库。
5. 已有登录认证，但业务 RBAC 基本没有落地；低权限用户能执行熔断复位、全自动模式切换、全局平仓等高危动作。
6. 生产配置不会对开发签名密钥、弱默认口令、空内部密钥 fail-fast；Git 跟踪文件中仍存在数据库凭据或生产式连接串。

**发布结论：No-Go。** 在 P0 清零、交易账本可核对、真实 PostgreSQL 测试显式 opt-in、生产密钥轮换及 RBAC 契约测试完成前，不得公网部署、多人使用或接入真实券商。

## 一、评审方法与边界

### 1.1 本轮实际执行

本轮采用五层证据交叉验证：

1. **静态走查**：路由、服务、领域对象、Repository、调度、前端页面、部署文件和 CI。
2. **自动化测试**：默认 pytest、排除真实库标记的隔离测试、独立 PostgreSQL 集成测试、前端 Vitest、构建、ruff、mypy 和依赖一致性。
3. **数据库生命周期**：独立空库 `upgrade head -> downgrade base -> upgrade head`、ORM 表可查询和 `alembic check`。
4. **API/业务实测**：匿名与认证操作、VIEWER 越权、高危平仓、授权无成交、OpenAPI 覆盖和 WebSocket 匿名连接。
5. **浏览器实测**：登录重定向、四市场路由、A 股功能标签、审批确认、桌面和移动视口。

### 1.2 证据等级

| 等级 | 含义 |
|---|---|
| A | 本轮隔离环境直接执行并复现 |
| B | 自动化测试或构建结果稳定复现 |
| C | 当前代码路径可确定推出，但未执行破坏性生产操作 |
| D | 文档或界面声明，仅作为对照，不作为完成证据 |

### 1.3 限制说明

- 未连接用户现有业务数据库，也未在其上执行审批、平仓、调度或迁移。
- 外部行情源、真实交易时段、真实券商和公网弱网未做端到端生产验证。
- `alembic check` 使用本轮独立空库；其漂移结论不代表用户历史库的实际结构。
- 前端网络故障放行以源码和单元测试为确定证据；收尾时浏览器令牌已被清除，未把该次页面跳转作为浏览器复现证据。

## 五、P0 发布阻断项

### P0-1 全局平仓按一个价格关闭所有市场全部持仓

**证据等级：A**

- `src/zhice_os_v2/api/routers/positions.py:414-439` 的请求体只有 `close_price`。
- 服务遍历 `db.list_open_positions()`，没有账户、市场、策略、标的、position id 或价格来源约束。
- 隔离内存实测同时创建 CN `600000.SH` 和 US `AAPL`，一次请求后两者都按价格 `1` 关闭，开放持仓变为 0。
- VIEWER 角色也可调用。

**影响**

误点击、脚本参数错误、越权用户或被盗的普通账号都可一次污染全部市场的持仓与已实现盈亏。接口注释承认这不是真实成交价，但仍执行并写入复盘/学习数据。

**必须整改**

1. 删除该接口，或只保留按 `account_id + market + position_ids` 的明确批量命令。
2. 价格必须来自逐标的可审计行情/券商成交，不接收一个全局手填价直接入账。
3. 仅 ADMIN/TRADER 可执行，VIEWER 必须 403；增加二次确认、幂等键和审计原因。
4. 仓位关闭、成交、费用、盈亏、复盘事件必须同事务提交。

### P0-2 设置与动作权限不进入执行链，形成错误安全感

**证据等级：A/C**

- `routers/settings.py:19-70` 保存 `trade_mode`、单票/总仓位、日亏损、止损线。
- 前端 `SettingsPageV2.tsx:20-30` 明确宣称“所有交易动作需人工确认”“单日亏损触发熔断”“单笔亏损触发止损”。
- 全库消费者核验显示这些设置没有进入自动执行、风控或止损路径。
- `circuit_breaker.py` 的 `_effective_permission()` 仅用于状态展示，不是动作守卫。
- 隔离 API 实测 VIEWER 可把模式设为 `full_auto`，且高危动作不受权限矩阵控制。

**影响**

用户会以为已经通过设置限制风险，实际系统仍按其他硬编码策略运行。这比“没有设置功能”更危险，因为它制造了可控的假象。

**必须整改**

建立唯一 `TradingPolicy` 服务，所有创建计划、审批、自动执行、加仓、平仓和调度入口都必须读取同一版本化策略；拒绝时返回命中的策略版本与原因。无法接线前应下线页面控制项并明确标为未生效，不能继续显示确定性承诺。

### P0-3 默认测试入口可能连接并修改现有 PostgreSQL

**证据等级：A/B**

- `tests/test_scheduler_integration.py` 整文件标记 `real_pg`，fixture 强制 `PERSISTENCE_BACKEND=sql`。
- 测试说明要求读取 `.env.local` 的目标库，且调用 `run_pre_market_job`、盘中、盘后、过期和调度作业。
- `Makefile` 的 `test` 和 `.github/workflows/ci.yml` 的 pytest 命令都未排除 `real_pg`。
- 默认全量测试本轮出现 32 个连接失败；准备独立库后该文件 35 项通过，证明这些并非自动跳过的占位测试。

**影响**

开发者仅执行 README 推荐的 `make test` 就可能在本机现有库中生成候选、计划、授权、报告或改变状态。CI 干净环境则直接失败。

**必须整改**

1. 默认 `addopts = -m "not real_pg"`，`make test` 和普通 CI 只跑隔离测试。
2. real_pg 必须使用独立 job、临时 PostgreSQL service、随机数据库名和显式 `RUN_REAL_PG_TESTS=1`。
3. 会写库的 fixture 启动前校验数据库名包含 `test`/随机前缀，拒绝 `.env.local` 生产式连接。
4. 每项测试自建数据并事务回滚，不依赖 2026 年 8 月预存行情。

### P0-4 授权幂等已改善，但执行状态和账本仍不可信

**证据等级：A/C**

积极变化：Repository 已提供原子 `APPROVED -> EXECUTING` claim，双入口重复执行风险降低，自动执行 order id 也改为唯一。

仍存在四个阻断缺陷：

1. `ApprovalExecutionService.execute_approved()` 不检查是否产生有效成交/持仓，循环后无条件把授权标记为 `EXECUTED`。
2. 隔离实测 broker 无任何结果时：`positions = 0`，但 `approval_status = EXECUTED`。
3. `_auto_execute()` claim 成功后，撮合未成交或抛异常只返回 `None`/记录日志，授权可能永久停在 `EXECUTING`，没有回滚、失败终态或重试策略。
4. 自动路径在保存 `EXECUTED` 后才 `_record_fill()`；若成交记录失败，会得到“授权已执行、持仓已变、成交账本缺失”。人工路径也没有落完整 order request/execution/fill 账本。

**影响**

状态页可能显示已执行但没有成交，或显示执行中永不恢复；持仓、成交、订单和授权无法对账。后续报告、学习和绩效将继承错误数据。

**必须整改**

采用数据库事务内的订单状态机：`APPROVED -> EXECUTING -> PARTIALLY_FILLED/FILLED/FAILED/RETRYABLE`。授权只在订单达到可核对终态后完成；order、fills、position lots、cash ledger、fees 和 approval transition 使用同一 Unit of Work，并提供幂等键、超时恢复任务和对账命令。

### P0-5 生产秘密和安全配置不具备最低保障

**证据等级：A/C**

- `AppSettings(app_env="prod")` 仍接受开发签名密钥、默认弱口令和空 `internal_api_key`，没有 validator 或启动检查。
- Git 跟踪的导入、回填、备份脚本以及配置、调度和 compose 中仍能找到数据库凭据/连接串。
- 报告刻意不打印任何实际秘密值；是否已泄露不能靠改当前文件解决。

**影响**

源码、镜像、日志或 Git 历史的读取者可能伪造 Token 或访问数据库。生产环境配置错误也不会阻止服务启动。

**必须整改**

1. 立即轮换数据库、JWT、行情和第三方 API 凭据，并按泄露处理审计历史访问。
2. 从 Git 跟踪文件移除秘密，使用 secret manager/运行环境注入；必要时清理 Git 历史。
3. `app_env=prod` 时对默认/空密钥、弱口令、非 TLS 外部端点和调试开关强制启动失败。
4. 在 CI 增加 secret scanning，并对镜像层和构建日志做扫描。

## 六、P1 高风险问题

### P1-1 只有认证，没有业务 RBAC

`require_roles()` 基本只用于 `/auth/users`。VIEWER 实测可触发/复位熔断、切换全自动、全局平仓；workflow 在通过认证后会进入执行，只因本轮隔离 SQL 旁路返回 500。需要一份端点 x 角色权限矩阵，并为所有写操作建立 401/403/2xx 契约测试。

### P1-2 WebSocket 匿名且实时链缺少生产保护

`/market/ws/market` 不校验 Token；匿名连接实测收到 5 条 quotes。连接管理器串行向连接发送，无队列、背压、慢客户端隔离和心跳；生命周期任务每 5 秒执行同步 SQL，可能阻塞事件循环。应增加连接鉴权、订阅范围、每连接发送队列、超时断开、心跳和异步/线程池数据库访问。

### P1-3 `memory` 模式不是数据隔离边界

当前 `src` 中统计到 118 处 `get_session()` 和 10 处 `psycopg2.connect()`。大量 application/api 逻辑绕过 `PersistencePort`，设置 memory 不能保证不读 SQL。架构测试只是冻结部分已知违规，不能证明安全隔离。应把 DB session 收口到 Repository/Adapter，并让内存模式在网络层直接禁止 PostgreSQL 连接。

### P1-4 前端路由在认证服务网络错误时 fail-open

`ProtectedRoute.tsx:28-31` 明确在 `/auth/me` fetch 失败时 `setStatus('valid')`，对应单测也断言网络错误放行。虽然 API 自身仍应拒绝无效 Token，但前端会继续显示敏感页面壳、缓存数据和“在线”状态。建议网络错误显示不可验证状态和重试，不能把“后端不可达”解释为“身份有效”。

### P1-5 模拟成交费用没有进入资金与盈亏账

`SimulatedBroker` 计算 `OrderResult.fee`，但 `ExecutionService.apply_fill()` 只用成交量和成交价创建/减少持仓，没有消费 fee。于是券商输出的佣金、印花税、过户费不进入成本和 PnL，绩效会系统性偏高。

### P1-6 超持仓卖出和部分成交状态不完整

SELL 按 FIFO 消耗持仓，但卖出量大于持仓时剩余量被静默丢弃，没有 REJECTED/UNMATCHED 状态。部分成交虽能先记持仓，但剩余订单、后续 fill、最终订单状态和跨进程持久化不完整。

### P1-7 调度器只防单进程重入

大量 job 使用 APScheduler `max_instances=1`，只能约束当前进程。双实例、滚动部署、手工触发与定时触发之间没有数据库 advisory lock/租约。应为每个 `market + job + trade_date` 建立分布式锁与幂等运行记录。

### P1-8 实盘功能是占位而非可用能力

`LiveBroker.place_order()` 在 enabled 时抛 `NotImplementedError`。产品界面和 README 应明确“实盘未实现”，开关不应给用户已接通的印象。接入前必须完成订单状态回查、撤单、成交回报、资金/持仓对账和断线恢复。

### P1-9 仍有价格 100 的业务兜底

`workflow_service.py` 在市场价格缺失时仍可使用 `Decimal("100")` 作为 ref price；`trade.py` 默认 ref price 也是 100。缺价应拒绝生成资金动作并告警，不能用演示常量进入计划或执行。

### P1-10 Schema 漂移仍会积累部署风险

虽然 fresh migration 已可运行，`alembic check` 仍失败。类型、nullable 和唯一约束漂移会导致不同数据库实例表现不一致，也可能让 ORM 以为唯一性存在但数据库未约束。应生成明确迁移并把 `alembic check` 加入 CI。

### P1-11 移动端核心工作流不可用

CSS 在移动视口仍固定 `.ws-side width:216px` 和 `.ws-body margin-left:216px`。390px 宽度下主体约 166px，标签和内容横向溢出。若产品不支持移动端，应在需求和登录入口明确限制；若宣称支持，则必须提供抽屉导航、响应式表格和触控操作验收。

### P1-12 双轨审批让用户无法理解“批准”的含义

Trade Plan 的批准与 Approval Request 的批准仍是两个入口、两套状态。一个批准可能只改计划，另一个才触发执行。应合并为一个用户动作，或在 UI 中以“计划审核”和“下单授权”明确区分，并展示完整状态转换。

## 七、P2 工程与体验问题

1. **异常处理债**：`src` 有 132 处 `except Exception`，其中 API/application 80 处；部分把故障降级为空数据，运营无法区分“没有数据”和“系统失败”。
2. **静态门禁失效**：ruff 当前共 26 项失败；mypy 在声明依赖环境有 28 项第三方 stub 错误，提交信息与可复现环境不一致。
3. **覆盖率不足**：隔离覆盖率 53%，对交易状态机、失败恢复、并发、调度和跨市场规则不足。
4. **前端未进 CI**：44 个单测和生产构建虽通过，但 CI 不执行它们。
5. **前端包过大**：主包约 1.35 MB，未做路由级代码分割，弱网首屏成本高。
6. **审批确认信息不足**：后端列表缺 `price/name` 或前端未展示，弹窗只看到方向、代码、数量，没有价格、金额、账户、策略和风险摘要。
7. **数量单位可能错误**：A 股授权数量显示“手”，而后端成交数量语义需确认是股还是手；单位错误会放大 100 倍风险。
8. **文档漂移**：README 仍写“当前测试 37 passed”，同时把已实现功能列入待办，也把占位能力描述为已完成。
9. **compose 不含前端**：README 称“完整部署”，实际只包含 postgres、redis、migrate、api、scheduler，用户仍需另行部署 Web。
10. **行情链路同步阻塞**：同步 SQL 与网络请求混入异步/实时路径，需要超时、隔离和指标。

## 八、产品经理视角

### 8.1 产品定位

当前最诚实、最有竞争力的定位是：

> 面向内部量化团队的多市场研究、模拟决策、审批与复盘工作台。

它还不是“自动化实盘交易操作系统”。原因不是 LiveBroker 一项未完成，而是策略、风险、授权、成交、账务与治理之间的控制合同尚未闭合。

### 8.2 已形成的产品价值

- 四市场统一信息架构和 MarketContext 思路清晰，用户切换成本低。
- 从候选、计划、风控、授权到持仓、复盘、学习的对象链已经存在。
- 桌面端 32 个市场/功能组合和 41 个 A 股标签可达，产品覆盖面不是原型级。
- 模拟券商包含滑点、流动性分档、限价、部分成交和多市场费用模型，方向正确。
- 调度任务、迁移服务、治理和审计对象为后续生产化提供了骨架。

### 8.3 产品承诺与实际能力错位

| 产品承诺 | 用户理解 | 当前实际 |
|---|---|---|
| 手动模式 | 所有下单都需确认 | trade mode 未进入所有执行路径 |
| 日亏损熔断 | 达阈值自动阻断 | 页面参数无执行消费者 |
| 单笔止损 | 达阈值自动平仓 | 页面参数与实际 ExitPolicy 来源不同 |
| 动作权限 | AUTO/CONFIRM/BLOCKED 控制动作 | 目前主要用于展示 |
| 批准 | 一次批准后状态明确 | plan 与 approval 两次批准语义并存 |
| 已执行 | 已有可核对成交 | 无成交也可能标 EXECUTED |
| 四市场统一 | 同等深度与闭环 | UI 统一程度高于数据/策略/交易能力一致性 |
| 实盘开关 | 可接通实盘 | LiveBroker 仍是拒单/NotImplemented 占位 |

### 8.4 产品优先级建议

第一优先级不是继续增加页面，而是恢复“产品承诺可信度”：

1. 统一交易策略配置来源并让设置真正生效。
2. 合并审批旅程，展示订单/成交/持仓的可核对状态。
3. 删除或重做全局平仓，建立账户与市场作用域。
4. 明确标记模拟、占位和未实现能力。
5. 给每个关键数字增加口径、币种、数据时点和来源。

### 8.5 MVP 建议范围

建议先收敛为 **CN 单市场隔离模拟盘 MVP**：真实历史数据、可信回测、统一风控、一次审批、模拟成交、费用入账、持仓/PnL 对账、盘后复盘。该闭环通过后再逐市场复制，而不是让四市场同时携带相同的控制缺口。

## 九、技术总监视角

### 9.1 架构评价

优点：领域模型、MarketProfile、BrokerPort、PersistencePort、迁移和容器服务的方向合理；迁移链与鉴权修复说明系统具备被治理的可能。

主要问题：端口抽象未形成强边界，业务层仍大量直连基础设施；关键状态跨多个 Repository 操作，没有 Unit of Work；设置、权限、熔断、审批、执行各自形成局部状态，缺少一个强一致的交易命令处理器。

### 9.2 交易一致性目标架构

建议将所有资金动作收口到 `TradeCommandService`：

1. 解析当前用户、角色、账户、市场和策略策略版本。
2. 获取版本化 TradingPolicy，执行熔断、模式、仓位、日亏损和市场规则检查。
3. 创建不可变 order intent 和幂等键。
4. 在事务内 claim 授权、写 order、接收 fills、更新 lots/cash/fees。
5. 通过 outbox 发布复盘、学习、通知和审计事件。
6. 独立 reconciliation job 与 broker/数据库对账并恢复卡住状态。

### 9.3 安全基线

- API 默认认证，白名单公开 health/login；WebSocket 也必须鉴权。
- ADMIN、TRADER、REVIEWER、VIEWER 最小权限矩阵服务端强制执行。
- actor 从 Token 注入，禁止客户端自报。
- 生产启动配置 fail-fast，秘密仅由 secret manager 注入。
- 所有高危操作需要 request id、幂等键、理由、操作前后快照和不可变审计记录。

### 9.4 质量与发布工程

当前 CI 不是可信门禁：默认 pytest 会碰真实库、ruff 红、mypy 环境不可复现、前端完全缺席。应拆成：

1. `unit-isolated`：禁网、禁 PostgreSQL、快速执行。
2. `integration-postgres`：CI service 容器、随机库、迁移后运行。
3. `schema`：fresh upgrade、downgrade/upgrade 和 `alembic check`。
4. `frontend`：Vitest、TypeScript build、bundle budget。
5. `security`：secret scan、依赖扫描、匿名/角色 API 契约。
6. `docker-smoke`：构建并启动完整栈，验证 health、迁移版本和前端代理。

### 9.5 可运维性

补齐结构化日志、trace/request id、订单状态指标、卡在 EXECUTING 的数量、调度运行记录、行情时延、WebSocket 连接/丢弃、数据库连接池和 SLO。没有这些指标时，“页面显示在线”不能代表交易链健康。

## 十、最终用户视角

### 10.1 桌面体验

桌面 1440x900 下整体可用：四市场导航清晰、功能覆盖广、标签可切换且没有系统性页面崩溃。登录后来源恢复和美股决策流路由也符合预期。

影响信任的不是视觉，而是操作结果不够诚实：

- 设置保存成功不代表交易行为改变。
- “已执行”不一定有成交。
- 页面空数据可能是后端异常被吞。
- WebSocket 断开或后端不可达时，页面仍可能保留可用/在线外观。
- 审批确认缺价格、预估金额、账户和策略信息，无法做有效人工复核。

### 10.2 移动体验

390x844 下固定侧栏占 216px，主体只剩约 166px，标签和表格超出视口。当前不是“体验一般”，而是核心工作流不可完成。产品应二选一：明确只支持桌面，或完成移动抽屉导航、单列信息架构、表格卡片化和触控确认。

### 10.3 用户关键旅程

| 旅程 | 结果 | 用户风险 |
|---|---|---|
| 未登录进入工作区 | 正确跳登录 | 基础门禁可用 |
| 登录并回到来源页 | 通过 | 首次流程改善 |
| 切换四市场/功能组 | 32/32 可达 | 可达不等于数据同质 |
| 设置手动/全自动 | 能保存 | 用户以为生效，实际执行链未消费 |
| 审批一笔交易 | 有确认弹窗 | 缺价格、金额、账户和风险摘要 |
| 查看执行结果 | 有状态与持仓 | 无成交也可能显示 EXECUTED |
| 紧急平仓 | API 可全平 | 作用域过大、单价污染、权限过宽 |
| 后端网络异常 | UI 路由设计为放行 | 可能继续看到陈旧数据和错误在线感 |
| 移动端处理审批 | 页面能打开 | 布局挤压，实际不可用 |

### 10.4 用户最需要的改进

1. 每个高危动作明确“将影响哪个账户、市场、策略、标的和数量”。
2. 审批展示最新价、限价、预估金额、费用、仓位变化、规则命中和数据时点。
3. 状态区分“无数据、加载中、后端不可达、权限不足、执行失败、部分成交”。
4. 所有设置显示生效版本和最后应用时间；未接线功能不能显示为可用。
5. 提供订单/成交/持仓三方对账页和异常处理入口。

## 十一、整改路线图

### 阶段 0：立即止血（0-3 天）

1. 禁止公网和实盘接入；冻结新增交易功能。
2. 删除/封禁全局平仓接口，至少临时限制为 ADMIN 并增加 feature flag。
3. 默认排除 `real_pg`，CI/Makefile 禁止读取 `.env.local` 运行写库测试。
4. 轮换所有已进入源码/Git 的凭据；生产默认配置 fail-fast。
5. 高危接口建立临时 ADMIN/TRADER 角色门禁。
6. 对未生效设置加醒目标识或下线编辑能力。

### 阶段 1：恢复交易可信度（1-2 周）

1. 实现订单/授权状态机和 Unit of Work，补齐 FAILED/RETRYABLE/PARTIALLY_FILLED。
2. 订单、成交、费用、现金、持仓和授权同事务；增加 reconciliation。
3. 统一 TradingPolicy，让 trade mode、仓位、日亏损、止损、熔断权限全部生效。
4. 合并 plan/approval 用户旅程；actor 由 Token 注入。
5. fee 入账；超持仓卖出拒单；剩余订单持久化。
6. 修复 Exit Lab 空 exit rule 语义并建立变体必须产生可解释差异的测试。

### 阶段 2：恢复工程与数据边界（2-4 周）

1. 清理 SQL 旁路，让 memory 模式真正禁用数据库连接。
2. 清零 `alembic check` 漂移并加入 CI。
3. real_pg 使用临时库、独立 fixture、事务回滚。
4. 加 WebSocket 鉴权、背压、心跳、异步 DB 和指标。
5. CI 加前端测试/构建、Docker smoke、secret scan 和角色契约测试。
6. 清理 ruff；固定 mypy stub 依赖与版本。

### 阶段 3：形成可发布 MVP（1-2 月）

1. 先完成 CN 模拟盘闭环的资金/成交/PnL 对账。
2. 回测复用真实费用、滑点、部分成交和市场规则。
3. 完成移动端或正式声明仅支持桌面。
4. 建立完整可观测性、备份恢复演练和运行手册。
5. 真实券商接入必须走独立设计评审、沙箱和小额灰度，不复用“开关即上线”的模式。

## 十二、发布验收标准

只有同时满足以下条件，才可从 No-Go 调整为“内部模拟盘试点”：

- [ ] P0 为 0，所有高危接口完成账户/市场/资源作用域限制。
- [ ] VIEWER 对所有写操作均 403；角色矩阵自动化覆盖 100% 写 operation。
- [ ] 匿名写操作除明确白名单外 100% 返回 401；WebSocket 匿名连接失败。
- [ ] 生产默认密钥、弱密码、空 internal key 会导致启动失败。
- [ ] Git 当前树和历史处置完成秘密扫描，已泄露凭据全部轮换。
- [ ] 默认 `make test` 永不连接 PostgreSQL；real_pg 只连接随机临时库。
- [ ] unit、integration、schema、frontend、Docker smoke CI 全绿。
- [ ] fresh migration、downgrade/upgrade、`alembic check` 全绿。
- [ ] 同一授权并发 100 次只产生一个订单意图；失败可恢复，不会永久卡 `EXECUTING`。
- [ ] 无成交不得显示 `EXECUTED`；部分成交、拒单、超时、重试均有确定终态。
- [ ] approval、order、fill、position、cash、fee 可逐笔对账，总差异为 0。
- [ ] 所有设置项都有执行链契约测试，页面显示的值与实际策略版本一致。
- [ ] 全局/批量平仓逐标的使用可审计价格，二次确认且支持幂等重试。
- [ ] scheduler 双实例运行不会重复生成资金动作。
- [ ] 关键 API/页面明确区分空数据、后端错误和权限错误。
- [ ] 若声明移动端支持，390x844 与 430x932 下无横向页面溢出且可完成审批；否则产品明确标注桌面限定。

实盘发布还需额外满足：券商沙箱、订单回报、撤单、断线恢复、日终对账、限额、双人审批、应急停机、备份恢复、审计留存和小额灰度全部验收。

## 十三、结论

这轮修复使系统从“多数接口裸露、空库不可建、容器缺调度”的状态，前进到“认证基本覆盖、迁移可运行、容器后端链可构建、并发授权有初步防重”。这些是实质改善。

但交易系统的核心不是页面数量，而是控制是否真实生效、状态是否可恢复、账本是否可核对。当前三个最危险的错觉仍存在：

1. 用户以为设置已经控制风险，实际没有进入执行链。
2. 用户以为 `EXECUTED` 代表成交，实际可能没有任何成交或账本记录。
3. 开发者以为默认测试是安全的，实际可能连接并写入现有 PostgreSQL。

因此本轮最终意见保持 **No-Go**。下一轮评审应减少“新增功能数量”指标，改以 P0 清零、角色权限覆盖率、账本零差异、失败恢复、迁移一致性和隔离测试安全性作为唯一放行依据。
