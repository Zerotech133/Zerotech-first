### 5.2 等待预算 21 → 30 → 90 → **180 分钟，且判据换成「整批已落地」**（见第六节）

**第一次放宽（21→30）**按空载基线算：预演 27m55s，17:25 巡检只需再等 13 分钟，21 分钟只留 8 分钟余量。

**第二次放宽（30→90）是被实测推翻的**：10-18 03:29 用**生产解释器 py311** 在隔离根跑真篮子，同机另有会话的 22GB 大模型占住显存，`qwen3.5:9b` 被挤到 CPU（runner 进程 WS 7.64GB 而非显存），**首票 `latency_s=1101.2s`＝18.4 分钟/票，是空载 5.6 分钟/票的 3.3 倍**。按此推算 5 票 ≈ 92 分钟（17:10 → ~18:42），30 分钟预算会在跑完之前判 FAIL。

**第三次（90→180 + 判据换掉）**：同一轮 py311 预演跑完（4116s / 68.6 分钟）拿到完整分布，发现「首票 × 5」的推算方法本身错了——见第六节。**结论是别再猜时间，改成等「整批已落地」这个完成信号。**

放宽是安全的：正常路径首轮即 break（零成本）；等待期间每 90 秒打印「当日 N/5 行」，人看日志能区分「在推进」与「卡死」；任务 `IgnoreNew` + `PT72H` 不会被并发实例或超时打断。

> 这条判例值得单独记住：**预演时长是环境相关量，不是系统常量**。同一份代码在同一台机器上，只因别的进程占显存就能差 3.3 倍。用一次预演的数字定死等待上限，等于把「当天的机器状态」写成了判据。


### 5.3 断言上界与等待条件不同源（判例复犯）

`_needs_wait` 在「done 行数 **>=** BASKET_N」即返回 False，而断言写的是 `len(todays) **==** BASKET_N`。一旦账本多出重复行（`run_shadow` 双跑，run_id 不同不会被幂等吃掉），等待会正常结束、断言却判 FAIL，且 FAIL 文案与真正的「跑失败了」无法区分。

这是 10-17 判例「等待条件必须与最终断言同源」的**上界侧复犯**——上次只修了下界（「完全没有新行」→「部分落账」，见 09feafb4）。

修法：抽纯函数 `_basket_complete(todays)` = 行数 `>= BASKET_N` **且**不同标的数 `== BASKET_N`。既与等待同源，又比原来的 `==` 更严：旧实现下「4 个标的 + 1 条重复（共 5 行）」判 PASS，新实现判 FAIL（篮子没齐）。**门 3 仍是 7 项，未增删检查项**，只改既有检查的判真条件，保持与前几次 7/7 的可比性。

### 5.4 顺带修掉：push 分支的同类重定向缺陷（`fd20c19c`）

### 6.4 判据重构：从「等够时间」改成「等这批跑完」

`run_shadow` 对篮子 5 票串行处理、每票恰好写一行（`run_shadow.py:287` 循环、`:338` 落账；异常也在两次尝试后落 `failed` 行），因此：

```
当日已落地行数（done + failed） >= 5   <=>   这批跑完了
```

这是唯一可靠、且不随负载变化的完成信号。取值变化：

| 账本状态 | 旧 v2（`done < 5` 才等） | 现（`已落地 < 5` 才等） |
|---|---|---|
| 5 done | 立刻判 PASS | 立刻判 PASS |
| 4 done + 1 failed | **白等满上限**才判 FAIL | **立刻判 FAIL** |
| 全 failed（0 done） | **白等满上限** | **立刻判 FAIL** |
| 2 done（还在跑） | 继续等 | 继续等 |
| 1 failed + 4 未落地 | 继续等 | 继续等（failed 不推动提前结束） |
| 进程被杀，行永远到不了 5 | 等满上限 | 等满上限（仅此一态用到 180 分钟） |

**已知取舍**：若当天有票 failed、而人工在巡检**已退出之后**才补跑成功，巡检记的仍是 FAIL。这是有意为之——FAIL 是那一刻的真实结论，且 failed 本身已触发飞书 P0 告警；若补跑发生在巡检退出之前（17:25 起通常票还没跑完），`已落地 < 5` 会让它继续等，补跑成功的 done 行会被正常计入。

**为什么不做「N 分钟无新行即停滞」检测**：竞争态下单票要跑 38 分钟，期间账本一行都不落，任何停滞判据都会把「正在算」误杀成「已死」。这个系统没有可用的中途观测面（`last_run.log` 只在每票完成时写一行），所以只能给足上限 + 每轮打印进度让人自己判。

**附带**：FAIL 文案补上「当日 failed N 票」——只显示 `done=4（预期 5）` 会被误读成「还没跑完」，掩盖真实原因；删除已被 `_today_counts` 取代的 `_today_done`（同一事实留两份计数实现，迟早有一份先被改）。

### 6.5 顺手排除的三个隐患

1. **隔离开关未持久化**：`HKCU\Environment` 与 `HKLM\...\Environment` 均无 `SHADOW_*` / `REHEARSAL` 项。若被持久化，周一任务会被 `--rehearsal` 阀 exit 2，门 3 直接报废。当前环境变量无残留。
2. **run 分支调用形态**：`shadow_automation.ps1:25` 为 `run_shadow.py`（无 `--root` / `--rehearsal`），真仓路径不变。
3. **巡检任务 Settings 是较老一代 XML**：缺 `ExecutionTimeLimit` / `RunOnlyIfIdle` / `AllowHardTerminate`，且带 `StopOnIdleEnd=true`。`StopOnIdleEnd` 仅在 `RunOnlyIfIdle=true` 时生效（此处缺省 false）；且今天在**非空闲**状态下多次触发均 `Result=0`，**实证不被拦**。所需 180 分钟也远小于默认 72 小时上限。**未改动**——它改触发器前就是这样，非本轮引入。
