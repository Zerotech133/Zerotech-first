## 二、选批规则

候选：`jev_review_queue` 中 `status='pending'`（只读；legacy/resolved 绝不入批）。

```
batch_priority = machine_score（若该 id 在机器预审 JSONL 中）
               + decision_bonus(needs_evidence=30, reject=20, accept=0)
兜底（机器文件缺失/该 id 不在机器 200 档）：
batch_priority = fallback_score（intel_pre_review 同一打分口径：
                 impact high40/medium20/low5 + conf≤0.4 +15/<0.6 +8 + 近7天 +20 + 来源已知 +5 + 新来源 +10）
排序：batch_priority desc → queued_at desc → id asc（稳定、可复现）
取前 limit 条（默认/上限 50；请求 >50 自动封顶并标 limit_capped=true）
```

即：**机器判为 needs_evidence / reject 的优先**（因为它们最需要人看），同层内机器 score
已含 high impact/低 conf/近期/来源因素；机器缺失时退回 impact/conf/时效兜底，并在产物
与摘要中**明确降级**（见 §四）。

## 四、缺机器 JSONL 的降级（fail-visible，不静默）

| 情形 | 行为 |
|---|---|
| 机器 JSONL 文件不存在/不可读 | `machine.available=false`、`degraded=true`；全部记录 `machine_decision="unavailable"`、`reason_code="machine_jsonl_missing"`；markdown 顶部 ⚠️；shell 摘要打印降级原因；**仍生成批次**（按兜底排序） |
| 文件存在但该 id 不在机器 200 档 | 该条 `machine_available=false`、`machine_decision="unavailable"`、`machine_reason_code="not_in_machine_top"` |
| 文件有坏行 | 跳过并计数 `machine.bad_lines`；有有效记录则 `degraded=false` 但 `degrade_reason` 保留"有 N 行不可解析" |
| 文件存在但无有效记录 | 同"不存在"降级 |
| news.db 不存在 | 退出码 1（fail-visible，不生成半成品） |

## 五、用法

```powershell
# 默认 dry-run（只打印摘要，不落盘；不改库）
python tools/intel_review_batch.py --dry-run
python tools/intel_review_batch.py --json                    # 完整 JSON（含 records）
# 写批次（只写输出目录；默认 C:\Temp）
python tools/intel_review_batch.py --write
python tools/intel_review_batch.py --write --out-dir D:\tmp\review
# 指定机器预审文件 / 条数 / 回放时钟
python tools/intel_review_batch.py --machine C:\Temp\intel_pre_review_20261031.jsonl
python tools/intel_review_batch.py --limit 50
python tools/intel_review_batch.py --now 2026-10-31T13:25:00+08:00
```

- `--limit` 默认/上限 50（>50 封顶并在输出标 `limit_capped`）；<1 报错。
- `--machine` 默认 `C:\Temp\intel_pre_review_20261031.jsonl`（机器预审 200 建议）。
- `--out-dir`/`--out` 输出目录（默认 `C:\Temp`）；文件名固定
  `intel_review_batch_<YYYYMMDD>.md|jsonl`。
- 默认 `--dry-run`；`--write` 与之互斥；`--json` 输出 JSON 摘要+records。
- 只读：连接 `mode=ro` + `PRAGMA query_only=ON`；输出路径指向 news.db 会被拒绝。
- 退出码：0=成功（含降级）；1=参数/数据错误；2=写批次文件失败。

## 七、人工裁决与回填方式

1. 打开 `C:\Temp\intel_review_batch_<date>.md`，逐条读 JEV 摘要/原文摘录/机器建议；
   在三个选框里勾一个：`correct`（JEV 判定正确）/`wrong`（需改判）/`uncertain`（证据不足）。
2. 回填唯一写入口（`portal/api_jev_review.py`，仅 pending 可写；已 resolved 返回 409）：
   ```powershell
   curl -s -X POST http://127.0.0.1:8091/api/jev/review/resolve `
     -H "Content-Type: application/json" `
     -d '{"id":"<记录 id>","decision":"correct|wrong|uncertain","reviewer":"老田","note":"<备注>"}'
   ```
   - `reviewer` 必填（≤80 字符）、`note` ≤500 字符；成功即 `status='resolved'` + reviewed_at。
   - 每次只 resolve 一条；**不要**用批次文件批量伪造 resolve（本工具不提供、也不建议）。
3. `uncertain` 建议在 note 写清缺什么证据；需要从 legacy 捞回的条目走
   `POST /api/jev/review/reopen`（legacy→pending），再进入下一批。
4. 批次内未裁决的条目**仍是 pending**，下一轮批次会再次参与排序（可能重复出现，
   属预期：未决即仍待人工）。

## 九、残余风险与边界

- **R1 优先级是规则不是判断**：machine_score/bonus 只做"先看谁"的排序，不代表机器更懂新闻；
  高影响/低置信/近期之外的条目可能排在 50 之外（仍需后续批次）。
- **R2 机器缺失时排序退化**：降级到 impact/conf/时效兜底，可能与机器分档顺序不同；产物已标明。
- **R3 批次≠复核**：markdown/JSONL 未回填、未 resolve 前，pending 不变；不要把批次数当成果。
- **R4 产物含敏感新闻摘要**：`title` 与 `jev_raw` 是本地私有数据，落 `C:\Temp`，勿外发/勿入库房。
- **R5 50 条之外仍有 200 条 pending**：本单只交"第一批 50"；剩余由后续批次/机器预审消化。
- **R6 重复入选**：未 resolve 的条目会在下一批再次按优先级入选（预期行为，防漏看）。
- **未验证**：批量回填链路（自动 resolve）未实现（刻意不做）；人工实际裁决质量与耗时
  需首轮 50 条试跑后评估。
- 不做：不改 nginx/认证（另一单）、不动 API/DB schema、不重启服务、不合并。
