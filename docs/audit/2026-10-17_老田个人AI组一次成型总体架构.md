# 老田个人 AI 组一次成型总体架构

- 日期：2026-10-17
- 定位：老田个人 AI 组的统一底座，不是股票系统的扩展版
- 适用业务：股票投研、软件研发、商业路演与 PPT、自媒体生产、研究院、个人工作协同
- 总原则：先统一事实、任务、记忆、证据和权限，再扩展业务能力；不再为每个业务单独造一套 Agent 系统

## 一、最终定位

老田个人 AI 组是一套“个人 AI 操作系统”：

```text
老田的目标
  → 项目与计划
  → 数字军团组织
  → 任务与会议
  → Agent 执行
  → 产出与证据
  → 人工审批
  → 发布/模拟执行
  → 复盘与能力成长
```

股票只是六个业务域之一。所有业务都必须遵守同一条主链：

```text
Goal → Project → WorkItem → Run → Artifact → Review → Decision → Learning
```

## 二、总体控制边界（必须先冻结）

本系统采用“规则路由 / A0 仲裁 + 领域 Agent 执行 + PG 事实源 + 派生索引 + 事件审计”的控制模型，禁止让大模型承担路由、权限或状态机职责。

```text
老田：最终负责人和高风险审批人
A0 田丰：最高决策主体，负责计划、仲裁、汇报判读和决议
A0A / Legion：编排、派工、监督，不做业务最终决策
agent_platform/router.py：规则撮合与路由，不是 Supervisor，不是主控 Agent
领域 Agent：按岗位执行，产出带证据的候选结果
执行层：只接受已审批且通过风控的指令
```

现有 `router.py`、`engine/memory.py`、`checkpoints.py`、`tasks.py` 直接作为第一版底座：只做增强，不新建一套 Supervisor/Chief Agent。新增控制表、事件和投影使用独立命名空间，能力模块独立落盘；停止新增进程即可回滚。

### 1. 个人控制面：老田 + 田丰

权威对象：目标、预算、重大决策、风险边界、发布和执行审批。

- 老田：最终负责人、最终审批人、业务意图来源。
- 田丰 A0：总参谋长，负责拆解、协调、汇总、决议、下发和监督。
- 三方会议：老田、田丰、诸葛亮 AI1；用于复杂问题的控辩审，不替代任务系统。

### 2. 军团编排面：Legion

Legion 是唯一任务编排中枢，不允许 Paperclip、Hermes、门户各自维护一套任务真相。

保留并统一：

- `org.json`、team、HR、Prompt：身份与权限源；
- Legion API/UI：组织、工单、排程、复盘、会议和研究院入口；
- Worker：实际执行单元；
- Academy：训练、评测、阶段能力认证；
- Paperclip：未来可作为战略控制面适配器，不能直接成为第二任务主控。

### 3. 六大业务域

#### A. 投研与风险部

覆盖：图形、事件、资金、基本面、情绪、多空、控辩审、RiskGuard、Paper 模拟盘。

关键角色：T1、T2、N1、F1、D1、R1、R2、R3、STRAT1、BACK1、DATA1。

输出：`ResearchReport`、`Verdict`、`Decision`、`PaperOrderIntent`。

边界：影子只有建议权；真实交易不在当前基座内；必须经过人工审批和独立风控。

#### B. 软件研发部

覆盖：需求、架构、后端、前端、数据、测试、运维、发布。

采用控制塔—蜂群—监察：

- 控制塔：田丰/研发主管，只做目标、拆解和依赖仲裁；
- 蜂群：DEV/ARCH/QA 等 Worker 并行实施；
- 监察：独立审查方案、重复错误和 Done 前遗漏。

Codex 树体属于研发部战术编排能力，不取代 Legion 的任务账本。

#### C. 商业战略与路演部

覆盖：商业模式、市场规模、客户画像、竞争格局、财务假设、路演故事线、PPT 内容和演讲稿。

流程：

```text
商业目标 → 受众与场景 → 证据包 → 故事线 → PPT → 田丰审阅 → 用户确认 → 发布/汇报
```

PPT 必须区分：事实、假设、预测、待补证；禁止模型编造客户、订单、收入和政策数据。

#### D. 内容与自媒体部

覆盖：选题、研究、脚本、图文、短视频文案、标题、封面需求、平台适配、发布、评论复盘。

现有 `gzh/gzh_writer.py` 已具备可复用内容产线：

```text
素材 → LLM 选题 → Markdown / preview HTML → 飞书审阅
```

`gzh/drafts/index.json` 的 `draft / reviewed / published` 状态可作为内容项目投影，但最终发布状态必须回写统一 Task/Approval/Event。

统一流程：

```text
选题池 → 素材证据 → 初稿 → 事实审查 → 品牌审查 → 平台改写 → 人工确认 → 发布 → 数据复盘
```

映射关系：

```text
Project：栏目、账号和内容定位
Task：每日选题、撰文、审阅、发布
WorkItem：material_fetch / topic_generate / article_generate / publish_review
Artifact：Markdown、HTML、图片、视频和发布包
Evidence：新闻、公告、采访和原始素材引用
Approval：发布审阅和对外确认
```

`portal/creator.html` 只作为只读投影，不承担执行或发布控制。MKT1 只能读 gzh/reports/docs/knowledge_docs，写 gzh/docs/knowledge_docs，不能执行命令和交易；生成与发布必须物理分离，发布必须是独立审批动作。

#### E. 个人工作协同部

覆盖：日程、待办、邮件/消息摘要、会议准备、资料整理、提醒、个人决策支持。

默认只读；涉及外部发送、删除、付款、承诺、公开发布时必须 Ask first。

#### F. 研究院与能力工程部

覆盖：新方法论、Agent 评测、Prompt、路由、Skill、知识反哺、组织实验、商业化研究。

研究语言统一为：

```text
研究问题 → 对象 → 假设 → 证据口径 → 验证方法 → 结论等级 → 行动建议 → 风险边界
```

研究院不直接发布生产规则；知识必须经过候选、人工审查、评测、批准、版本化和可回滚。

## 三、共享能力层

### 1. 统一模型路由

`agent_coder.py` 保留为公共执行底座，但将模型路由按任务类型配置：

- 规划/仲裁：高推理档；
- 普通执行：中档模型；
- 监察/格式检查：低成本模型；
- 事实核验：规则和检索优先，模型辅助；
- 股票复杂研判：高档模型+事实包；
- 日常内容改写：中档模型。

### 2. 统一记忆入口

记忆不能由每个 Agent 自建一套。采用四层：

```text
L0 会话记忆：当前会议/当前任务
L1 项目记忆：项目决策、约束、版本和上下文
L2 个人长期记忆：老田偏好、长期原则、固定口径
L3 组织知识：已批准 Skill、方法论、标准、案例
```

规则：

- 原始对话不是知识；
- 候选知识不等于已批准知识；
- 任何长期写入必须带来源、时间、版本、审批状态；
- 记忆检索统一从 CowAgent/Khoj 入口进入；
- Qdrant 只保存可重建索引，PG/文件记录保存事实源。

### 3. 统一技能体系

Skill 是跨部门复用的标准动作，例如：

- LCS-1 看股；
- 路演 PPT 编制；
- 自媒体事实核验；
- Python 代码审查；
- 会议复盘；
- 数据源健康检查；
- 决策回放。

每个 Skill 必须具备：输入、输出、适用场景、禁用场景、验收器、样例、版本和回滚。

## 四、统一数据与证据层

### 统一对象

```text
Goal              目标
Project           项目
WorkItem          任务/工单
Run               一次执行
Evidence          证据
Artifact          产出
Review            审查
Decision          决策
Approval          审批
Meeting           会议
Memory            记忆
Skill             技能
Performance       绩效
```

### 统一主键

```text
trace_id          全链路业务主键
request_id        单次请求
correlation_id    跨服务关联
idempotency_key   幂等执行键
artifact_id       产出主键
decision_id       决策主键
```

所有业务都必须能回答：

```text
谁提出？为什么做？谁执行？依据是什么？产出在哪里？谁审过？谁批准？后续结果如何？
```

### 证据等级

```text
事实
佐证
证伪
存疑
未知
```

证据不足时只能输出：

```text
补证 / WATCH / HOLD / 需人工核验
```

不能为了“给出答案”强行输出 Go、BUY、SELL、发布或执行。

## 五、统一审批和权限模型

四类风险级别：

| 级别 | 示例 | 默认动作 |
|---|---|---|
| L0 | 内部草稿、格式整理、只读检索 | 自动执行 |
| L1 | 内部报告、代码修改、研究草稿 | 执行后审查 |
| L2 | 对外 PPT、自媒体发布、正式客户材料 | 用户确认 |
| L3 | 交易、付款、删除、权限变更、外部承诺 | 用户明确批准+审计 |

权限遵循：

```text
身份权限 ≠ 工具权限 ≠ 数据权限 ≠ 发布权限
```

所有 Agent 采用默认拒绝：

- 没有数据授权不能读；
- 没有写权限不能改；
- 没有发布权限不能发；
- 没有审批凭证不能执行高风险动作。

## 六、统一事件和任务账本

### 唯一任务账本

短期兼容现有 `tasks.json`，但其状态必须逐步迁移为统一任务存储；Legion 是唯一写入主控。

Hermes、Paperclip、Codex、门户均只能：

```text
创建请求 / 读取状态 / 回写事件
```

不能各自产生一套“任务完成”状态。

### 统一事件

```text
goal.created
project.created
workitem.created
workitem.claimed
run.started
artifact.created
review.requested
review.approved
review.rejected
decision.created
approval.granted
publication.sent
paper.order.planned
paper.order.filled
performance.updated
memory.proposed
memory.approved
```

当前 `portal.db events`、heartbeat、会议记录、Paper 事件应逐步汇入统一事件查询层；保留原始日志作为审计副本。


## 八、一次成型实施路线

### M0：地基冻结

交付：统一对象、ID、权限、状态机、事件规范、事实源清单。

验收：所有新业务都能映射到 Goal/Project/WorkItem/Artifact/Review/Decision。

### M1：控制面收敛

交付：Legion 唯一任务主控、HR 单一身份源、统一事件查询、三方会议与任务关联。

验收：同一任务只能有一个 owner、一个状态真源、一个幂等键。

### M2：共享能力层

交付：统一记忆入口、Skill 目录、证据仓、模型路由、成本统计。

验收：一个批准 Skill 可被投研、研发、内容和路演复用；候选知识不能直接进入生产记忆。

### M3：研发与内容生产线

交付：软件研发流水线、PPT 生产流水线、自媒体生产流水线；全部接入人工发布闸门。

验收：每份交付物都有来源、审查、版本、负责人和可回滚记录。

### M4：投研与模拟执行线

交付：StrategyAgent、控辩审、Regime 阵容、Paper 事件和绩效闭环。

验收：影子、结论、Paper、成交、绩效可由 `trace_id` 回放；禁止真实交易。

### M5：成长和监察线

交付：复盘蒸馏、Skill 候选、评测集、Agent 绩效、Token 预算分配、诸葛亮主动巡检。

验收：任何能力升级有对照评测、人工批准、版本和回滚。

### M6：战略控制面评估

仅在 M0-M5 稳定后评估 Paperclip：

- 若引入，只接管目标、预算、审批和公司级治理；
- Legion 继续负责本地业务任务执行，或明确迁移后关闭旧主控；
- 禁止长期双主控。

## 九、一次成型必须做出的关键决策

1. **Legion 是当前唯一任务主控。**
2. **HR/registry 是身份与权限唯一事实源。**
3. **Hermes 是执行与消息适配层，不是第二套组织系统。**
4. **Paperclip 是候选战略控制面，不立即接管。**
5. **CowAgent/Khoj 是统一记忆和知识入口。**
6. **所有业务共用同一对象模型和事件协议。**
7. **生成、审查、批准、发布/执行必须分离。**
8. **诸葛亮是反向审查和主动巡检，不绕过用户直接下命令。**
9. **股票、PPT、自媒体、代码都必须有证据和版本。**
10. **真实交易、真实外部发布、删除、付款和权限变更默认需要用户确认。**

## 十、明确不做

- 不为股票、研发、内容分别建立三套组织和任务系统；
- 不让 Paperclip、Legion、Hermes 同时成为任务主控；
- 不把所有历史聊天直接灌入长期记忆；
- 不让 Agent 自动发布未经确认的外部内容；
- 不让影子结论直接进入真实交易；
- 不在没有证据和审批的情况下自动升级 Prompt、Skill 或权限；
- 不以“模型回答成功”代替业务验收；
- 不把一次性项目经验未经评测就固化成通用规则。

## 十一、最终验收门槛

### 架构门

- 六个业务域都能使用同一套 Goal→Task→Artifact→Review→Decision 链；
- 只有一个任务主控和一个身份事实源；
- 所有跨系统动作具备统一 trace。

### 数据门

- 证据来源、时间、版本和血缘完整；
- 事实、推断、假设和未知可区分；
- 任何产出可回放到输入和执行记录。

### 治理门

- L2/L3 动作存在用户确认；
- 权限默认拒绝；
- 密钥不进入 Prompt、日志或产出；
- 可暂停、重试、取消、恢复和回滚。

### 质量门

- 代码有测试；
- PPT 有事实审查；
- 自媒体有事实/品牌/合规审查；
- 投研有多空与反方证伪；
- 研究院有阶段验收和人工批准。

### 运营门

- 每日有军团日报；
- 每个 Agent 有 heartbeat、任务、产出和复盘；
- 诸葛亮能发现延期、数据缺口、Prompt 缺陷、路由错误和执行偏差；
- 所有成本和模型调用可统计。

## 十二、统一对象模型与现有代码映射

所有业务对象继承统一 `ObjectEnvelope`，至少包含：

```text
object_id / object_type / schema_version
workspace_id / domain / owner_ref / acl
status / revision / created_at / updated_at
source_system / source_ref / provenance
trace_id / request_id / correlation_id / idempotency_key
tags / sensitivity / supersedes / metadata
```

### 核心对象

```text
Goal         老田要达成的结果
Project      有边界的长期或阶段性项目
Task         对外承诺、可审计的工作单
WorkItem     Task 的一次执行、重试或工具运行
Evidence     可验证事实或依据
Artifact     文件、报告、代码、PPT、视频等产物
Decision     判断或选择，不等于执行
Approval     对某个具体版本的授权
Meeting      会议、观点、分歧、纪要和行动项
Memory      带来源和时态的经验/知识
Skill        可复用、可评测、可回滚的能力
Performance  Agent、Skill、Strategy 或 Project 的绩效事实
```

### 现有实现映射

| 统一对象 | 现有实现 | 处理方式 |
|---|---|---|
| Task | `engine/tasks.py`、`.worktrees/tasks.json` | 收敛为一个 canonical Task；旧 JSON 做兼容适配器 |
| Project | `projects_registry.json`、academy topics | 统一 Project 投影，保留领域扩展字段 |
| Event | `portal.db.events`、flow、heartbeat、shadow/paper 日志 | 统一事件信封，原始账本保留为审计副本 |
| Meeting | 三方会议、paper pre_open/post_close 会议 | 统一 Meeting subtype，不改变交易会议语义 |
| Memory | `engine/memory.py` GNS 四级 namespace | 保留 append-only、RBAC 和 grants，不新建记忆主库 |
| Evidence | `agent_platform/contracts`、事实包 | 增加 hash、provenance、时效和可信等级 |
| Artifact | Worker outputs、PPT、代码、Paper 报表 | 统一 artifact_id、content_hash、revision 和来源 |
| Decision | Verdict、shadow decision、三方决议 | Decision 与 Approval 分离，批准后才可执行 |
| Performance | shadow J1/J2/J3、Paper fills、CI、内容反馈 | 统一 Performance 子类型，保留领域指标 |

### 硬性语义

```text
Task = 业务承诺
WorkItem = 一次执行
Evidence = 事实依据
Artifact = 产出文件/结果
Decision = 判断
Approval = 授权
Memory = 可复用经验
Performance = 结果表现
```

不能用“Task done”代替业务验收，不能用模型观点伪装 Evidence，不能用 Approval 代替 Decision。

### 幂等和并发规则

- 写命令必须使用 `idempotency_key`；实际唯一键为 `workspace_id + operation + idempotency_key`，并保存 `payload_hash`。同键同参数返回首次结果，同键不同参数拒绝。
- 现有 PaperEngine 的兼容事实是：`orders.idempotency_key` 尚未全局唯一，实际由 `orders.ref` 的条件唯一索引 `ux_orders_ref` 防重复；迁移时必须建立 `ref → canonical idempotency_key` 映射，不能误认为旧字段已经全局幂等。
- Shadow 同日同票只对 `date + symbol + status=done` 判重，失败允许重试；该语义必须通过统一 `IdempotencyRecord` 记录，不能粗暴改成所有失败都不可重试。
- Task 状态迁移采用 `expected_revision`，避免并发覆盖。
- WorkItem 重试产生新 attempt，不覆盖旧结果。
- Artifact 以 `content_hash` 去重。
- Event 使用稳定 `event_id`、`event_hash`、`causation_id` 和 sequence，支持重放。
- 所有审批绑定目标的 revision 和 content_hash，目标变更后原审批自动失效。

## 十三、现有代码锚点与防双主控门

- `agent_platform/router.py`：规则匹配、只撮合不决策；匹配不唯一时升级 A0。
- `agent_platform/registry/org.json`：A0=田丰，A0A 只调度不决策，职能部和项目部矩阵为组织基础。
- `agent_platform/onboard_agent.py`：Agent 入职唯一写入口，保持幂等和 fail-visible。
- `agent_platform/engine/memory.py`：四级 GNS、RBAC、append-only，作为统一记忆底座。
- `agent_platform/engine/tasks.py`：保留现有状态纪律，外面增加 canonical Task 信封。
- `tools/legion_tri_party_meeting.py`：保留双观点、分歧、用户确认和 `auto_dispatch=false`。
- `k_stock/paper/engine.py`：保留 Paper 的 T+1、撮合、幂等和风控语义，不泛化成普通任务。

防双主控铁律：

```text
全局路由只有 router.py
任务编排只有 Legion / 现有任务引擎
最高决策只有 A0 田丰与老田审批席
身份权限只有 org + HR
记忆只有 GNS / 统一检索入口
事实只有证据层
实际副作用只有执行网关
```

新增 Paperclip 时只能作为战略目标、预算、审批和审计适配层；若未来迁移任务主控，必须先完成全量双读校验，再关闭旧主控，禁止长期双写。

### 4. A0、A0A 和观察链


因此，任何新 Agent 都不能通过修改日报、heartbeat 或模型输出绕过 TaskStore、MemoryStore、Checkpointer 和 Approval。

## 十六、一次成型开发顺序

```text
P0：ObjectEnvelope + Event + IdempotencyRecord + ACL
P1：tasks / academy / portal.db / tri-party / paper / shadow 适配器
P2：门户全部改读统一投影，旧账本只保留为 source adapter
P3：统一路径、schema_version、revision 和迁移工具
P4：六大业务域按同一验收门逐个上线
```

第一批只做契约、状态、审计、重放和权限，不扩充 Agent 数量；第二批才做部门能力产品化；第三批才做 Paperclip 评估和跨业务商业化。

## 最终结论

“老田个人 AI 组”不应被建设成一个股票 Agent 集合，而应建设成一个个人 AI 操作系统：

```text
一个人
一个控制面
一个组织名册
一个任务账本
一个事件协议
一个记忆入口
一个证据体系
多个专业业务部门
多个可插拔 Agent
多个受控执行出口
```

先把这套基座冻结，再向股票、软件、PPT、自媒体和个人协同扩展，才能真正一次成型，避免未来再经历第二次系统重构。

## 十七、M0 地基冻结执行清单（本轮落地）

本节将架构原则转换为可执行的冻结门，作为后续开发的唯一入口。M0 完成前，禁止新增业务 Agent、第二任务系统或新的记忆/事件主库。

### 1. 已冻结的四项契约

| 契约 | 冻结内容 | 当前写入边界 |
|---|---|---|
| `ObjectEnvelope` | `object_id/object_type/schema_version/workspace_id/domain/owner_ref/acl/status/revision/source_system/source_ref/provenance/trace_id/request_id/correlation_id/idempotency_key/tags/sensitivity/metadata` | 业务对象先包络，领域字段放 `metadata` 或 subtype，不得重复造公共主键 |
| `EventEnvelope` | `event_id/schema_version/kind/environment/source/source_id/occurred_at/available_at/object_id/object_type/trace_id/request_id/correlation_id/causation_id/idempotency_key/sequence/payload/links/provenance/event_hash` | 生产者只追加事件；查询层可投影，不能反写生产者状态 |
| `IdempotencyRecord` | `workspace_id + operation + idempotency_key + payload_hash` 唯一；同键同参数复用结果，同键异参数拒绝 | Paper 旧 `orders.ref`、Shadow 同日同票规则通过 adapter 兼容，不直接假设旧字段全局唯一 |
| `ACL / Approval` | 身份、工具、数据、发布四类权限分离；Approval 绑定 `target_id + revision + content_hash` | 目标版本变化后旧审批自动失效；L2/L3 没有审批凭证不得执行 |

### 2. M0 事实源资产盘点表

以下对象先保留现有实现，统一通过 adapter 接入；本轮不做破坏式迁移：

| 资产 | 当前角色 | M0 处理 | 禁止事项 |
|---|---|---|---|
| `agent_platform/engine/tasks.py` / `task.py` | Task 状态与 RBAC canonical writer | 增加 Envelope、revision、事件包装；建立旧 JSON 兼容读适配 | 任何页面直接改 `tasks.json` |
| `.worktrees/tasks.json` | 历史/协作兼容账本 | 只读导入、差异报告、幂等回放 | 与 TaskStore 双写 |
| `agent_platform/registry/org.json` + HR | 身份、岗位、权限事实源 | 只允许 `onboard_agent.py` 写入并生成投影 | 直接改 bundle、Prompt 汇总文件 |
| `portal.db.events` | legacy 事件账本 | 保留原始记录；补 `event_id/object_ref/revision/event_hash/causation_id` adapter 字段 | 把现有少量 legacy 行误当完整事件主库 |
| flow / heartbeat / tri-party / Academy | 事件生产者或观察投影 | 统一 Envelope、source/source_id、trace；查询时聚合 | 各自维护全局完成状态 |
| shadow / Paper ledger | 影子与模拟执行事实 | 保留领域语义，接入统一事件和幂等记录 | 直连 live 或覆盖历史成交 |
| `projects_registry.json` / Academy topics | Project/研究课题领域账本 | 生成统一 Project 投影，保留领域扩展 | 再建一套全局项目主控 |
| `gzh/drafts/index.json` | 内容状态投影 | 通过 Content adapter 映射 Project/Task/Artifact/Approval | 以草稿索引替代发布审批真源 |
| Qdrant / Neo4j / Portal UI | 派生检索/展示索引 | 可重建、只读消费统一事实源 | 将索引写回事实源 |

### 3. M0 迁移顺序

```text
盘点字段与写入口
  → 只读 adapter
  → Envelope/事件旁写
  → 双读差异报告（禁止双写）
  → 迁移一个域并回放验证
  → 关闭旧读路径
```

迁移期间的硬约束：SQLite/文件仍是既有写真源，PG 仅作只读镜像；所有跨系统写命令必须带 `trace_id`、`request_id` 和幂等键；任何新 adapter 失败必须可见、可重试、不可静默吞错。

### 4. M0 完成定义

只有同时满足以下条件，才允许进入 M1：

- Authority Matrix 与 canonical writer 清单进入版本控制；
- TaskStore、组织 HR、MemoryStore、Checkpointer、Strategy Registry 的写入口可追踪；
- `.worktrees/tasks.json` 与 TaskStore 生成差异报告，且没有新增双写；
- legacy events、flow、heartbeat、会议、Academy、Shadow、Paper 均能映射 `EventEnvelope`；
- 统一幂等记录覆盖 Paper 旧 `ref` 和 Shadow 失败重试语义；
- 至少完成一次事件回放、断点恢复、并发认领、失败重试、死信和人工恢复验证；
- 现有 `smoke_test.py`、`test_tasks.py`、`test_contracts.py`、`onboard_agent.py --check` 通过；
- 架构门禁保持：无第二任务主控、无绕过 canonical writer 的写入、`live` 关闭。

M0 的目标不是“把所有业务一次写完”，而是先让任何未来业务都只能沿着同一套事实、任务、证据、审批和审计路径接入。
