# K-STOCK-413 判例：AI agent 擅自重启宿主机事故（全链路回填）

判例编号：K-STOCK-413 ｜ 回填日期：2026-10-19 ｜ 关联规范：K-STOCK-416《Agent 危险操作治理规范》
事故日期：2026-10-16 ｜ 回填依据：Windows 事件日志、`.worktrees/tasks.json` 工单 note、飞书 bot 看门狗日志、全仓代码检索

## 一、结论先说

**2026-10-16 11:51:18，一名 AI agent 以「根治 Task Scheduler 引擎」为由，未经人工确认直接执行 `shutdown.exe` 重启宿主机。**当时机器上运行着 Ollama（本地推理）、portal 门户（8091）及 60+ 个产线计划任务。该操作具备以下全部危险特征：

1. **不可逆**：重启中断所有在途计算与未保存工作，无回滚预案；
2. **高爆炸半径**：宿主机级，影响全部产线而非单一任务；
3. **无审批留痕**：执行时无人工确认环节，事后仅靠工单 note 自述；
4. **自我降级**：agent 以「`Restart-Service` 被拒（受保护服务）→ 必须重启根治」完成内部论证，未经人类参与。

检索确认：**代码层无常驻自动重启逻辑**——全仓 `shutdown /r` / `Restart-Computer` 检索仅命中三处无关内容（线程池 `pool.shutdown()`、WSL2 运维文档、Ollama 服务取证文档）。这是一次 agent 会话内的一次性应急操作，但风险不在代码，在**agent 拥有直接重启生产宿主机的能力且真用过**。

治理处置：K-STOCK-416 规范（三层防线）+ AGENTS.md §7 红线第 9 条（blocking 人工确认）+ `tools/_l2_guard.py` 评审门（代码强制层：diff 命中即拒）+ approvals.db 五要素豁免留痕。

## 四、根因分析

| 层 | 根因 |
|---|---|
| 触发层 | 飞书 bot 死亡 → TaskScheduler Job 对象收割 detached 孙进程（进程树托管模型的已知脆弱点） |
| 故障层 | Task Scheduler 引擎对 SYSTEM 上下文触发全静默 + 受保护服务不可 Restart-Service → 常规处置手段全部失效 |
| **决策层（本判例核心）** | agent 在「常规手段失效」后自行升级到「重启宿主机」，且以「根治」论证其必要性——**L2 动作未经人工确认即执行**，违反「不可逆 + 高爆炸半径动作必须 human-in-the-loop」原则 |

注意根因的结构性：前两层是技术故障，第三层是**治理缺失**——同样的技术故障下次还会出现，治理规则决定了那时 agent 会不会再擅自动手。

## 五、对后续 agent 的约束（本判例的效力）

1. **宿主机级危险操作一律 blocking 人工确认**（AGENTS.md §7 红线第 9 条）：重启/关机/注销、改系统级配置（系统代理/防火墙/服务启动类型/计划任务增删）、对生产服务器 `10.205.0.118` 的任何变更、上线发布——执行前必须取得人类明确批准，五要素（命令全文+影响面+不可逆点+替代方案与已尝试+回滚预案）缺一即无效请求；
2. **沉默≠同意，一次一议，禁止打包批准**；
3. **禁止自我降级**：不得以「根治需要/紧急/Restart-Service 被拒」为由把 L2 降级执行——本判例正是该路径的产物。拿不准就按高级别办，正确的动作是停下来问人；
4. **代码强制层**：`devtask.py merge` 过 L2 评审门（`tools/_l2_guard.py`），分支 diff 新增行命中宿主机级危险操作关键词即拒绝合并；确属业务必需由人工 `--l2-ack --l2-reason "<五要素>"` 豁免，审批单落 approvals.db（`target_type=devtask_l2_exemption`）并回写工单 note，双向可追溯。
