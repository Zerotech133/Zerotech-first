# 军团 IDE 架构研究（2026-10-30）

> 研究问题：这套 IDE 现在是什么架构？它的安全/状态/执行/前端边界在哪里？下一步应该往哪演化，而不是继续加按钮？

## 一、研究对象与证据

- 旧前端：`portal/ide.html`（约 2164 行）
- 原生前端：`Hermes/extensions/legion-ide/app.js`（约 1295 行）
- LDE 后端：`agent_platform/legion_ide/`（serve / rw_guard / writer / exec_runner / exec_sandbox）
- OH 引擎：`agent_platform/legion_command/openhands_engine.py`（约 626 行）、8796、8771
- 入口/认证：8734 nginx、auth_gateway、`/_auth_guard`
- 质量：IDE 聚焦 pytest、`test_legion_ide_http.py`、fast gate

## 二、当前架构事实

```text
浏览器
  ├─ /ide     旧单页（legacy）
  │    └─ 直接 fetch /openhands/*、localhost:8796
  └─ /hermes/ Hermes 原生扩展
       ├─ /openhands/ → 8796  (OH 执行/事件/会话)
       ├─ /lde/      → 8103  (LDE 施工台 API)
       └─ /extensions/app.js 静态扩展

nginx 8734
  ├─ auth_request /_auth_guard  (登录页/页面/data plane 入口)
  ├─ /hermes/   → 8787
  ├─ /lde/      → 8103
  ├─ /openhands/→ 8796
  └─ /api/      → 8091
```

**关键变化**：研究前 `/lde/` 与 `/openhands/` **没有 auth_request**：

```text
未登录 GET /lde/rw                          → 200
未登录 GET /lde/api/ide/session             → 返回 owner
未登录 GET /lde/api/ide/scope               → 17 个 worktree
未登录 GET /openhands/api/ide/openhands/... → 200
```

已补：

```text
/lde/      → auth_request
/openhands/→ auth_request
/agent_ide_bundle.json → auth_request
```

复测：

```text
未登录 /lde/rw → 302
未登录 /lde/api/ide/scope → 302
未登录 /openhands/... → 302
登录后三者 → 200
```

**这是本轮研究最重要的发现：页面认证 ≠ 数据面认证。**

## 三、五个结构性发现

### F1：认证边界已修，但仍是“本机信任”而非“用户身份”

- 登录后 cookie 是 Phase A auth session；
- LDE 自己再发 `ide_session`，owner 绑定到 LDE session；
- 两者是两套会话，没有把“登录用户”映射到 LDE owner；
- 直接连 127.0.0.1:8103/8796 的本机进程仍可绕过 nginx。

结论：当前是**单机单用户信任边界**，不是多用户/零信任。

### F2：LDE 会话/owner/undo 都在内存

- `rw_guard._SESSIONS` 内存字典；
- `serve._UNDO` 内存字典（10 分钟）；
- 8103 重启 → 所有浏览器 LDE session 失效，前端要重新 `/rw`；
- undo 重启即丢。

结论：安全修复有效，但**不具备进程重启后的连续性**。

### F3：执行隔离是“进程树隔离”，不是“权限隔离”

- OH 走 8771 Docker sandbox；
- LDE exec 走 Job Object：
  - KILL_ON_JOB_CLOSE
  - ActiveProcessLimit=32
  - 超时整树终止
- 但命令仍以当前 Windows 用户权限运行，文件系统可达工作区外。

结论：Job Object 能防子进程残留/资源失控，**不能防恶意命令**。

### F4：状态仍是三套

```text
浏览器 localStorage：旧页 tab/分裂/会话
8796 server JSON：OH sessions（已加跨进程文件锁）
8103 内存：LDE session + undo
```

没有统一 run_id / event log；LDE audit 与 OH event stream 是两条链。

结论：可以审计“做了什么”，但不能完整回放“一次 IDE 操作”。

### F5：前端仍是单体扩展

- `app.js` 1295 行，状态/请求/视图/事件全在一个文件；
- 无构建/类型检查/组件边界；
- 旧页 2164 行，功能仍有两套；
- 已有 4 条 LDE HTTP 测试，但没有浏览器测试。

结论：单人用足够，团队/长期维护成本会继续上升。

## 五、推荐目标架构

### 1. 控制面/数据面分离

```text
nginx / auth_gateway
  ├─ 页面：会话 cookie
  └─ /lde /openhands /agent_ide_bundle：统一 auth_request + 短期 API token
```

不要出现“页面要登录、API 不要”的缝。

### 2. LDE 会话持久化

- 把 `_SESSIONS` / `_UNDO` 落 SQLite（或加密文件）；
- owner 绑定 auth session `sub`，而非随机 `lde-xxxx`；
- 8103 重启后 session 可恢复/明确失效。

### 3. 执行服务容器化

- LDE exec 从 Job Object 升级为**每任务容器/低权限账户**；
- 挂载仅当前 worktree；
- Job Object 保留为资源兜底。

### 4. 统一 run/event 模型

```text
run_id: 一次用户任务
  event: start / context / tool_call / observation / approval / write / commit / stop
```

LDE audit 与 OH SSE 写入同一 event store，支持回放/取消/追责。

### 5. 单壳 + 模块化

- 退役旧 `/ide`（先迁 MCP/模型/语音/多 Tab）；
- 原生扩展拆 module：state / api / view / events；
- 加浏览器级 smoke（登录 → 打开 → OH → diff → undo）。

## 六、下一步研究/施工顺序

| 顺序 | 动作 | 验收 |
|---|---|---|
| 1 | LDE 会话/undo 落盘 | 重启 8103 后 owner/undo 可预期 |
| 2 | LDE owner 绑定 auth `sub` | 同一登录用户跨浏览器同 owner |
| 3 | exec 容器化威胁模型/POC | 命令只能访问挂载的 worktree |
| 4 | 统一 run_id/event store | 一次任务可完整回放 |
| 5 | 旧页能力迁移 | MCP/模型/语音/Tab 有归属 |
| 6 | 前端模块化 + browser smoke | app.js 拆分，登录链路可自动测 |

## 七、结论

**这套 IDE 已经是一个可用的单机工作台，但它的“实战边界”不是按钮数量，而是：**

```text
页面认证已补 → 数据面刚补
LDE owner 已会话绑定 → 还不是用户身份
Job Object 已进程隔离 → 还不是权限沙箱
undo 已有 → 还不是持久 checkpoint
```

下一步真正的价值是把这四条边界做深；继续加 UI 按钮不会提高可托付程度。
