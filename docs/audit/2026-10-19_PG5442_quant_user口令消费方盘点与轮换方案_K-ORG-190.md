## 2. 轮换五要素草案

### 2.1 ALTER ROLE 命令全文（占位口令，执行时生成新口令替换）

```sql
-- 在 5442 上执行；旧会话不受影响，新连接立即要求新口令
ALTER ROLE quant_user WITH PASSWORD '<NEW_PW>';
-- 验证（应失败）：
-- PGPASSWORD='<OLD_PW>' psql -h 127.0.0.1 -p 5442 -U quant_user -d quant_system -c 'SELECT 1'
-- 验证（应成功）：
-- PGPASSWORD='<NEW_PW>' psql -h 127.0.0.1 -p 5442 -U quant_user -d quant_system -c 'SELECT 1'
```

### 2.3 影响面

- **8097 trade_pool 状态机全链**（投研拿票/决策/建仓埋点/盯盘触发/平仓闭环）——当前实走硬编码 fallback，S1 未做前轮换即断。
- xmap 三件套 + 策略层三件 + 血缘两处 + 磁盘巡检 + 两迁移脚本：S3 落盘后下一次调度即恢复。
- watchdog/quant_watch.py：不直连 DB，随 8097 恢复而恢复。
- zhice@5446 域（chanlun/data_loader/zerobound-kg/jev-eval）**不受影响**（独立角色独立口令）。

### 2.4 不可逆点

- `ALTER ROLE ... PASSWORD` 本身可再次 ALTER 回滚，**非不可逆**；真正的不可逆风险是**轮换后旧口令从 pg_authid 消失**：若 S1-S3 任一步漏改且无备用入口，对应消费方将因 raise 而暴露断链（fail-fast，比静默 fallback 好）。执行窗口建议：盘后（16:30 后）低峰，避开 14:55 qd 快照与 16:00 daily runner。

### 2.5 替代方案

- A（推荐，本草案即此）：先代码去 fallback 走 env，再库口令轮换——断链窗口最小。
- B（最小动作版）：只改 .env.local + push_secrets.json + 库口令，**保留** trade_pool 硬编码兜底——轮换后 8097 反而因 fallback 失效而断，**不成立**，仅作反面教材。
- C（半替代）：pg_hba 改 scram 策略 + 独立 `quant_ro` 只读角色分流巡检/血缘类只读消费——后续加固项，不在本次范围。

### 2.6 回滚

- `ALTER ROLE quant_user WITH PASSWORD '<OLD_PW>'`（旧口令 = `qua****23`，执行人自持，不落文档）；
- git 层面 S1 为单文件小 diff，`git checkout -- portal/quant_mid/trade_pool.py` 即回滚（注意：仓库纪律禁 WS 工位自行 commit，回滚由老田执行）；
- .env.local 改前先备份一份为 `.env.local.bak-YYYYMMDD`（同盘、同权限）。

1. **先代码**：S1 去 fallback（评审+单测 test_trade_pool.py 回归）→ 8097 K-RESTART 换血（`C:\Temp\push_admin_restart.marker`，SYSTEM 通道，勿裸杀）→ 验证 8097 /health 与 trade_pool 端点（此阶段旧口令仍在，fallback 已删，靠 S2 预置 push_secrets.json 键续命）。
