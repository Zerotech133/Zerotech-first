## 二、缺陷定性

| 维度 | 应有语义 | 实际语义 |
|---|---|---|
| G2 未扫描 | 无法判定（UNPROVEN） | PASS |
| G3 未扫描 | 无法判定（UNPROVEN） | PASS |
| 实查数 0 | 无证据，隔离**未被证明** | PASS |
| 结论行 | 只在三查均有实证时才可称「成立」 | SKIPPED 也印「三查全绿：影子隔离成立」 |
| 退出码 | 0 仅当有实证 | SKIPPED 亦为 0 |

问题不在 G1（G1 扫的是本仓源码，恒有对象，实测有效）。**问题在 G2/G3 把「没查」与「查了没问题」合并成同一个 PASS**。

## 三、为什么危险

1. **W16 收口项 4 会被自证通过**。施工单 W16 验收项 4 原文要求「`check_shadow_isolation.py` 三查全绿」。用上述任一命令跑，脚本自己就给出「三查全绿」——**收口判据的关键一环是空的**，而审计者看到的是一行绿色结论。
2. **阴性无法区分空集**。M2 预研阶段影子件产物本就稀疏（当前 `adapters/` 下 0 个产物），所以「实查数 0」是**常态**而非常态异常。「没产物所以没违规」与「有产物且全合规」在输出上完全同形。
3. **缺阳性对照，脚本的咬合力未被证明**。没有任何证据表明：投入一条带 `risk_passed` 的恶意件时，G2 会真的报 FAIL。未经阳性对照的校验器，其 PASS 不具备信息量。

## 四、应补的三条判据（建议，供该件所有者）

1. **`--scan-dir` 改必填**：未指定 → 打印 `INCONCLUSIVE` 并 `exit 2`，禁止在未扫描的情况下输出任何 PASS 字样。
2. **实查数下限断言**：`影子件实查数 == 0` → `INCONCLUSIVE`（非 PASS）。确需在空集下运行时，必须显式 `--allow-empty`，且此时结论行改写为「无产物可查，隔离未证明」。
3. **内建阳性对照 `--self-test`**：脚本自行构造一条 payload 含 `risk_passed` 的样例 IntelItem 与一个白名单外路径，跑一遍 G2/G3，**必须报 FAIL** 才证明脚本有咬合力；自检不过时拒绝出具正式结论。

三态口径：`PASS`（有实证且干净）/ `FAIL`（有实证且违规）/ `INCONCLUSIVE`（无实证），**只有 PASS 与 FAIL 允许进收口判据，INCONCLUSIVE 一律视为未完成**。

## 五、与 W16 收口的关系

W16 验收项 4 的收口口径应改为：

> `check_shadow_isolation.py` 三查均有实证且全绿（G1 有源码对象、G2 实查影子件数 > 0、G3 实查产物数 > 0），且 `--self-test` 阳性对照报 FAIL 通过；任一项 SKIPPED 或实查数为 0，收口不成立。
