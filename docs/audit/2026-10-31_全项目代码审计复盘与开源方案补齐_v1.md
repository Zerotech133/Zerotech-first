## 3. 真实代码审计发现

> 级别：P0=可导致信任边界突破/任意执行；P1=可导致生产不一致/证据失真；P2=可维护性/卫生/性能

### P0-1 Codex 插件“受限 globals”不是安全边界（verified）

证据（安全验证，不执行危险命令）：

```text
agent_platform/adapters/codex_bridge.py 的 _exec_globals() 仅白名单 builtins，
但插件代码可执行：
  (1).__class__.__mro__[1].__subclasses__()
实测 reached=316（可继续按名字/属性取 os/subprocess 相关子类）
静态 DENY_CALLS 只拦 eval/exec/compile/open/getattr 等字面名，
不拦 __class__/__mro__/__subclasses__ 属性链；in-process register_from_source 直接 exec。
```

影响：如果 Codex 插件来源不完全可信，静态校验 + biltins 白名单会被绕过；`register_from_source` 在宿主机主进程执行，风险高于子进程 runner。
建议：
- **不要把 Python restricted exec 当安全边界**；
- 插件注册/试跑统一进 OS 级沙箱（Windows AppContainer/Job Object/Windows Sandbox；或 Linux Firecracker/E2B）；
- in-process exec 至少移除，改为独立低权限子进程；静态 deny 仅作纵深防御；
- 将 `__class__/__mro__/__subclasses__/__globals__/__code__` 等列入 AST 拒绝，但**不能替代 OS 隔离**。

### P0-2 `exec_sandbox` Job Object 分配失败 fail-open（verified by code）

证据：

```text
agent_platform/legion_ide/exec_sandbox.py run():
  assigned = AssignProcessToJobObject(...)
  ... 无论 assigned 真假，进程继续跑，返回 isolation="job-assign-failed"
  SetInformationJobObject 失败也被 except Exception: pass
```

影响：资源/进程树隔离失效时仍然执行命令，且只靠返回字段提示；上层若只看 returncode，会把“未隔离执行”当成功。
建议：assign/info 失败 → 立即终止进程并返回失败（fail-closed）；或拒绝启动；日志/指标记录；测试覆盖失败分支。

## 5. 外部/开源方案对标

### 5.1 Agent 隔离与运行时安全

- **Windows 原生**：Microsoft `Experimental_CreateProcessInSandbox`（Windows 11 experimental）支持 AppContainer 内核级隔离、文件系统/网络策略、Job Object UI/进程限制；明确说 app_container=false 时 fs/network/capability 字段不生效。链接：<https://learn.microsoft.com/en-us/windows/win32/secauthz/createprocessinsandbox>
- **Linux/云端**：Firecracker microVM（Rust、小攻击面、~125ms 启动、<5MiB 开销）适合短生命周期不可信代码；E2B 用它跑 AI 代码。链接：<https://e2b.dev/resources/firecracker-vs-qemu>、<https://docs.e2b.dev/network/internet-access>
- **风险清单**：OWASP Top 10 for LLM/GenAI（含 Agentic 风险）。链接：<https://genai.owasp.org/initiative/owasp-top-10-for-llm-and-genai/>
- **对本项目**：P0 不应再用“受限 globals + AST deny”当安全边界；Windows 单机可先 AppContainer/Job Object + 低权限账户，跨平台/高风险执行再上 Firecracker/E2B。**先做 P0-1/P0-2，不先买服务**。

### 5.2 工具调用策略与人工审批

- **OPA Agent Tool Calling**：harness=PEP，OPA=PDP；每次 tool call 送 `input.tool_calls`，deny 非空则不执行；支持 bundle 热更新和 decision logs。链接：<https://www.openpolicyagent.org/docs/agent-tool-calling>
- **OpenAI Agents guardrails/approvals**：官方提供 guardrails 与 human review/approval 模式（文档页当前 403，概念可引用）：<https://developers.openai.com/api/docs/guides/agents/guardrails-approvals>
- **对本项目**：现有 L2 静态正则 + 分散门禁适合“合并前”；缺“运行期每次工具调用”的统一策略/审计。建议 OPA 或最小 policy JSON + decision log，先覆盖 shell/write/网络/审批四类。

### 5.3 发布完整性与供应链

- **SLSA v1.2 Build Provenance**：定义 buildDefinition/resolvedDependencies/runDetails，用于验证 artifact 由谁/如何构建；L1 即要求 provenance。链接：<https://slsa.dev/spec/v1.2/build-provenance>
- **Sigstore/cosign**：可签 blob/attestation（sign-blob/attest-blob），签名可进透明日志；适合签 manifest+artifact。链接：<https://docs.sigstore.dev/cosign/signing/other_types/>、<https://docs.sigstore.dev/quickstart/quickstart-cosign/>
- **in-toto attestation**：statement/subject/predicate 标准，SLSA provenance 的承载格式。链接：<https://github.com/in-toto/attestation>
- **CycloneDX**：SBOM 标准，适合把依赖/组件清单纳入发布。链接：<https://cyclonedx.org/specification/overview/>
- **对本项目**：现有 sha/manifest/guard 是“完整性”，缺“来源/签名/SBOM”。P1 建议：`cosign sign-blob` 签 manifest，`cosign attest-blob` 附 SLSA-like provenance（commit、builder、命令），发布前 verify；artifact 只读。

### 5.4 数据时点与数据质量

- **Feast point-in-time joins**：特征按 event timestamp 取当时可见值，防未来数据泄漏。链接：<https://docs.feast.dev/getting-started/concepts/point-in-time-joins>
- **Great Expectations schema/数据质量**：schema、类型、列存在性、取值分布校验。链接：<https://docs.greatexpectations.io/docs/reference/learn/data_quality_use_cases/schema/>
- ** lakeFS/Delta Lake time travel**：数据版本/回滚/可复现快照。链接：<https://lakefs.io/blog/power-up-lakehouse-with-git-semantics-and-delta-lake/>
- **对本项目**：D4 已有 manifest/冲突/tie-break 工具，但缺统一数据契约与 PIT 查询层；建议先做 manifest schema + 行数/键/时间可见性断言（GE 风格），再考虑 Feast（重）。

### 5.5 Agent 可观测与评测

- **OpenTelemetry GenAI semantic conventions**：LLM/agent 调用的标准属性；链接：<https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/>
- **Langfuse**：开源 trace/evals/prompt 管理，基于 OTel，可自托管；链接：<https://langfuse.com/docs>
- **对本项目**：当前有 dev_events/A0 日志/审计报告，但缺“每次 LLM/tool 调用的 trace_id + 输入输出摘要 + 成本/延迟 + eval 分数”。建议先 OTel 兼容 JSONL（不引入服务），再接 Langfuse/Phoenix。

### 5.6 测试与静态分析

- **pytest-testmon**（测试影响分析）：只跑受影响测试；官方文档页当前 404，PyPI/GitHub 可查：<https://pypi.org/project/pytest-testmon/>
- **Bandit**：Python 安全 linter；<https://github.com/PyCQA/bandit>
- **Semgrep**：跨语言规则/CI 扫描；<https://docs.semgrep.dev/>
- **CycloneDX/SBOM** 同上。
- **对本项目**：目前 ruff/bandit/mypy/coverage/pip-audit 均未安装；fast gate 88 文件覆盖约 41%；建议先加 bandit+ruff（低误报配置）+ coverage 报告，不追求全量 CI 阻塞。
