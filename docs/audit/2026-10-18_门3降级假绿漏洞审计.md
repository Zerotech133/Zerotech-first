## 一、结论先说

**有假绿风险，严重度 P1（判据层结构性缺口，非偶发）。**
5 票全部降级（LLM 全挂 / parse 全失败 / 数据源全异常）时，只要每票仍落一行 `status="done"`，
门3 的 10 个运行项**全 PASS、EXIT=0**——实测复现（场景 A1/A2/A3 均 10/10 PASS）。
根因：判据体系里**没有一条「降级必须为 0」或「降级率 ≤ 阈值」的项**；唯一带 `degraded`
字样的判据（`monday_checkpoint.py:371`）方向是反的——它只校验「parse 失败的行有没有被
标记成 degraded」，把 `degraded=True` 当作**合格证据**而不是**异常信号**。
补充：「done」在写侧被硬编码（`run_shadow.py:246`），与「有效决策」不等价。

降级在生产端的表达（读码结论）：

- 字段落点：影子账本行 `data/shadow/shadow_ledger.jsonl` 的 **`degraded`（bool）** 与 **`parse_ok`（bool）**，
  schema 见 `run_shadow.py:244-255`。没有独立的 `fallback` 字段；`error` 只出现在 `status="failed"` 行。
- 语义：`degraded = (not parse_ok) or any(source_status != "normal")`（`run_shadow.py:243,252`）。
  `source_status` 是 interpreter 逐节点的 `normal/degraded` 字典（`engine/interpreter.py:182`）；
  LLM 异常在此被吞成文本 `"[降级] LLM 不可用…"` + `status="degraded"`（`engine/interpreter.py:221-223`，
  `engine/llm.py:95,102`）。
- **关键分叉**：`interp.run()` 整体不抛异常时写 `done` 行（哪怕 5 个节点全 degraded）；
  只有抛到 `run_shadow.main` 外层才写 `failed` 行（`run_shadow.py:423-425`）。
  即：**LLM 层失败 → done+degraded；取数层失败 → failed**。前者正好是判据看不见的那一类。

A1 原始输出片段（真实）：

```
[PASS] 最新交易日 2026-10-19 done 行数=5（预期 5） —— 不同标的 5 个；当日 failed 0 票；账本总行数 5
[PASS] 首跑行全带 schema_version=m5.v1 —— 5/5
[PASS] 首跑行全带 dk_* 六字段 —— 六字段键齐备
[PASS] degraded 联动（parse_ok=false 行 degraded 必 True） —— 刀1 扩义生效
结论: 10/10 PASS——观察点门全过
EXIT=0
```

N 证明探针非空转（判据会红）；S 暴露第二个缺口：**日期锚定**——判据用「账本里最新日期」而非
「今天」，只要历史某天有 5 行，后续某天完全没产出也能 PASS。周一暂时被 v0 哨兵
（`latest <= 2026-10-14` → 判"首跑未发生"）挡住；**10-20 起该哨兵失效，此缺口会独立生效**。

## 四、假绿成立条件 与 周一现场人工补充判读

成立条件（三条同时满足即可，均为"LLM 快速失败"路径的常态产物）：

1. 5 票各落一行 `status="done"`（LLM 连接被拒/报错时 interpreter 兜底，分钟级即写完，不会卡到超时）；
2. `dk_*` 六键齐（正常数据源即满足；即使 dk 挂也齐，见 A3）；
3. `parse_ok=False` 的行都正确标了 `degraded=True`（写侧代码保证，:252）。

不成立（会正常判红）的情形：同票两次尝试都抛到最外层→`failed` 行；或 Ollama 挂起式超时
（300s×重试）拖过 180 分钟等待上限→done 不足 5。

## 五、门3 之后的最小修补建议（本次不动代码，仅方案）

按「风险/改动量」排序，建议合并为一次改动，且**排在 10-19 观察之后再上**（门3 口径中途变更
会让此前 PASS 失去可比性，这是本仓既有判例）：

1. **新增第 8 项（核心）**：`check("当日无降级票", not any(r.get("degraded") for r in todays))`，
   或阈值化 `degraded_n == 0`（首跑期本就应该 0）。这是唯一能真正堵住假绿的项。
2. **把降级计数放进 detail**（不改判定）：门1 的 done 行数项 detail 追加 `degraded %d 票 / parse_fail %d 票`，
   让人一眼看见，而不是去翻 jsonl。
3. **把第 6 项改成双向**：既罚"parse 失败未标 degraded"，也罚"`degraded=True` 而 `recommendation` 为空"；
   更彻底的做法是把第 3 项改为「**有效决策行数**」= `done and parse_ok and recommendation in {BUY,HOLD,SELL}`。
4. **第 5 项改值校验**：`dk_*` 六键齐 ≠ 计算成功；应加 `r.get("dk_error") is None`。
5. **日期锚定**：`latest` 必须等于 `date.today()`（节假日用交易日历例外），否则判"当日未产出行"FAIL。
   否则 10-20 起，"今天什么都没跑"会被昨天的 5 行判成 PASS。
6. 以上第 1、3、5 条建议先在 `[observe]` 段挂一个周期（沿用 `_strategy_runs_observe` 的只增不改纪律），
   观察满一周再升为正式门。
