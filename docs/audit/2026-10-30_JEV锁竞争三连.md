- 日期：2026-10-30 20:06
- 结论：**连续四轮同一根因——k266_m3 持有 ollama_batch.lock，JEV 只好收工；不是动态 batch 问题。**

## 判断

- 动态 batch 已生效，不是“批量过大”；
- JEV 小时轮在 M3 持锁时先抢到过锁，随后 `tick` 发现锁被 M3 抢走，只判 8 条；
- 每小时重复“抢锁 → 丢锁 → 8 条”是纯浪费，且积压继续上涨（left 1068→1618→1897）；
- 继续调 batch 公式不会改善。

## 建议（按优先级）

1. **错峰**：M3 活跃时段 JEV 小时轮不抢锁，直接 skip（现在抢到再丢，浪费 30-350s）；
2. **优先级**：明确 M3 优先还是 JEV 优先；不要让两者每轮互相抢；
3. **独立资源**：若都要跑，给 JEV 单独 Ollama 实例/模型槽，而不是共享 `ollama_batch.lock`；
4. 夜跑（21:50）若仍被 M3 打断，应先确认 M3 是否应在夜间运行。

## 错峰方案（可执行）

### 方案 A（推荐，改动小）

`jev_backfill` 取批前先做一次**只读锁预检**：

```text
读 locks/ollama_batch.lock
holder 含 k266/m3 且 pid 存活
→ 打印 BACKFILL skip: m3_active，直接退出（不 acquire、不判 8 条）
```

效果：

- 不再每小时浪费 30-350s 抢锁；
- 积压会暂时上涨，但 M3 空闲后小时轮/夜跑可连续消化；
- 不改 M3、不改 Ollama 资源。

### 方案 B（夜间优先）

- 21:50 JevNight 启动前检查 M3 进程；
- 若 M3 活跃，先写 `C:\Temp\k266_m3.pause` 或确认 M3 让位；
- 夜跑结束后恢复 M3。

### 方案 C（长期）

- 给 JEV 独立 Ollama 实例或模型槽；
- 彻底移除共享 `ollama_batch.lock` 的互抢。

### 关键计算

```text
处理：159
起始待判：2825
结束待判：3137
净增：+312
推算新增：159 + 312 = 471 条 / 862s ≈ 32.8 条/分钟
JEV 吞吐：159 / 862s ≈ 11.1 条/分钟 ≈ 666 条/小时
```

结论：

```text
M3 已停、锁竞争已消失
但入站速度（≈33/min）> JEV 吞吐（≈11/min）
→ 夜跑不能清积压，积压会继续上涨
```

这不是锁的问题，是**吞吐 vs 入站**的问题。
