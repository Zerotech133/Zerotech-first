# 军团 IDE 实战准入评估（2026-10-30 18:20）

## 结论

**可以投入“单人、受控、真实开发”的实战；不能投入“多人 / 无人值守 / 生产发布”。**

通俗说：

```text
老田一个人用它改真实代码：可以，按下面的使用规则走
让多个人同时用 / 让 Agent 无人值守执行 / 当作生产发布通道：不可以
```

## 二、刚发现的 P0 运维问题

检查时 LDE 是：

```text
rw_enabled=False
/api/ide/scope → 403
```

原因：8103 被重启时没带 `-EnableWrite`。已用 launcher 恢复：

```text
stop pid=25692
start pid=10308 IDE_RW=on
```

问题：**LegionOps 没有 8103/rw 健康守卫**。  
这意味着任何人都可能把 IDE 重启成只读，而主路径没有任何告警。

## 三、准入矩阵

| 场景 | 判定 | 条件 |
|---|---|---|
| 单人内部真实开发 | 🟢 GO | worktree + 锁 + 预览/确认 + 人工审 diff |
| 真实项目小步提交 | 🟡 有条件 | 每步可回滚；不跑不可信命令 |
| 多人同时操作 | 🔴 NO-GO | owner 会话自报、无身份绑定 |
| 无人值守执行 | 🔴 NO-GO | LDE exec 是宿主权限；无审批队列 |
| 生产发布通道 | 🔴 NO-GO | 无回滚/checkpoint/发布审计 |
| 旧 `/ide` 继续写码 | 🔴 NO-GO | legacy，只作为只读/补充入口 |

## 四、可以实战的依据

1. **写路径有基本护栏**
   - 工单锁显式获取/释放；
   - preview → confirm 两阶段；
   - 单文件 diff/add/commit；
   - 路径限制在受控 worktree。

2. **执行有两条路**
   - OH：8796 → 8771 Docker sandbox，适合让 Agent 跑命令；
   - LDE exec：宿主 subprocess，只适合受控人工命令，不适合不可信输入。

3. **失败可恢复**
   - 写的是任务 worktree，不直接碰 master；
   - 最坏 git 恢复/丢弃 worktree；
   - LDE 有 audit 记录。

4. **测试基线**
   - IDE 聚焦 67 passed；
   - 新 LDE HTTP 测试覆盖 tree/lock/read/write/git/exec/越权。

## 五、实战使用规则（现在就必须遵守）

```text
1. 只从 8734 /hermes/ 进，不用旧 /ide 写码
2. 只选 doing/review 工单
3. 写前必须拿锁；改后 preview → confirm
4. 提交前看 diff；commit 只提交单文件
5. 命令执行优先走 OH sandbox；LDE exec 只跑 git/测试等白名单命令
6. 不把密钥、token、密码贴进 prompt
7. 一人一单；不要多人共用同一工单锁
```

## 六、上生产前必须补的

### P0

1. `LegionOps` 增加 8103 + `rw_enabled=True` 守卫，掉线/只读即告警；
2. LDE owner 与会话身份绑定，禁止客户端自报；
3. LDE exec 隔离（Job Object/低权限/容器）或明确“仅人工白名单”；
4. IDE 路由接入统一认证（当前本机边界，不是多用户认证）。

### P1

5. checkpoint/undo（写前快照，可回滚）；
6. 旧 `/ide` 独有能力迁移清单闭环；
7. 8787 直连 LDE；
8. IDE 端点测试进质量闸（现在专项测试不在 fast gate）。

## 七、建议的实战方式

先拿 **一个低风险真实任务** 试：

```text
工单：只改一个文件 + 跑一个白名单测试
路径：/hermes/ → 军团 IDE → LDE
流程：锁 → 读 → 改 → preview → confirm → diff → git commit
监控：8103 rw=True、8796 health、无孤儿进程
```

跑 2-3 个这类任务后再扩大，不要第一天就用于批量/无人值守。

## 八、判定

```text
单人受控实战：GO
多人/无人值守/生产：NO-GO
最大短板：执行隔离、身份绑定、8103 运维守卫
```
