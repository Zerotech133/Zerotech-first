## 3. 根因链（两层）

1. **直接根因**：lark-cli 凭证注入机制与 jev app 的 open_id 签发跨应用错配——同机多 app 共用 lark-cli 必踩（关联判例：K-STOCK-141 飞书同 app 多消费者黑洞；本例是它的姊妹形态：**凭证错配**而非**连接截流**）。
2. **放大根因**：修复写盘后未换血——15:32 修复版落盘到 16:01 换血之间 29 分钟，`start_jev_stack.ps1` 是纯「缺则拉」守护，旧进程（born 15:13）带旧码继续跑，99992361 持续复刷。

## 4. 核心判例（五条）

1. **修复写盘 ≠ 生效**：进程出生时间必须 > 修复文件 mtime；「缺则拉」型守护器无 mtime 重启逻辑，修码后必须杀旧换血。验证三件套=新 PID born > mtime + 日志新「网关启动」行 + 故障特征零复发。
2. **杀 S4U Session0 进程需 UAC**：`Start-Process cmd -Verb RunAs taskkill /F /PID <pid>`；降权 token 直接 Access denied。
3. **端口判活 > 进程枚举**：`Get-NetTCPConnection -LocalPort 9101..9104` 可靠；CIM/Win32_Process 对 S4U Session0 枚举不可靠（本日双实证：四件套全漏、CommandLine 全 null）。
4. **except pass 豁免边界（C2批2）**：只豁免「可预期且无害」分支——ALTER TABLE 的 OperationalError 仅 duplicate column 属预期，其余（locked 等）全是真故障，原 pass=迁移静默假成功。
5. **e2e 验证法**：`import jev_gate; jev_gate.push_feishu(alert, verdict)` 直打真实链路（main() 在 `__main__` 守卫内，import 安全）；死信文件 err 字段是故障演变史的唯一直接证据（本例两阶段演变全靠它还原）。

## 5. 处置模式（可复用）

- **换血四步**：UAC taskkill 旧 PID → 守护器自动重拉 → 核对 born > mtime → 打特征行验证（e2e 探针 + 日志关键行）。
- **死信补达**：final:true 不可自动重放（无生产读方），人工汇总后随 e2e 验证卡一次性补推；修复后死信零新增即闭环。
- **双路推送自洽配对**：OpenAPI 直连（apps[0] 凭证 + push_targets「个人」）为主，lark-cli 回退——凭证与 open_id 同 app 侧才自洽。
