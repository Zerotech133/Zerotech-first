# Hermes「二开」合理性评估（2026-10-30）

- 工单：`WO-LEGION-HERMES-FORK-AUDIT-20261030`
- 性质：只读评估；本轮不改 Hermes/IDE 代码
- 口径：按“二开 = 二次开发/定制”理解；若指“双开两个 Hermes 实例”，见 §八附注
- 关联：[IDE 再研究 v2](2026-10-30_IDE再研究_v2.md)

---

## 一、结论

**IDE 面板在 Hermes 上做“官方扩展”是合理的；把平台连接器和核心补丁直接二开进 Hermes，不合理。**

准确说：

```text
IDE ≠ Hermes。
Hermes 只是壳（UI shell）；
真正的 IDE 能力在 LDE 8103 + OpenHands 8796/8771。
```

| 层 | 现状 | 判定 |
|---|---|---|
| IDE 面板 UI | `Hermes/extensions/legion-ide`，走官方 `/extensions/` 注入面，不覆盖核心 static | 🟢 **合理，继续** |
| 平台连接器 | `api/legion.py`、`pulse.py`、`alerts.py` 等直接嵌进 Hermes 核心 | 🟡 **短期可接受，必须下沉** |
| 核心补丁 | `routes.py` 等直接改，且生产基 `hermes-webui-next` 无 git、无上游 diff | 🔴 **不合理，停止扩大** |
| 长期路线 | 把 Hermes 当“不可替换的 IDE 底座” | 🔴 **不建议** |

一句话：

> **Hermes 可以是可替换的门面，不能是不可回滚的底座。**

## 二、现场证据

### 2.1 生产基与双基

`start_hermes_bg.py` 指向：

```text
SERVER = ...\Hermes\hermes-webui-next\server.py
_CWD   = ...\Hermes\hermes-webui-next
```

- `hermes-webui-next` = 生产基（upstream master 快照 + 定制接线）；
- `hermes-webui` = 回滚资产；
- 两套并存，改错基就“白改”（文档已记录双基判例）。

### 2.2 版本库状态（关键）

```text
Hermes/hermes-webui-next/.git         不存在
主仓 git ls-files Hermes              只有 10 个文件
  - extensions/legion-ide/README.md
  - extensions/legion-ide/app.js
  - extensions/legion-ide/app.css
  - start_hermes_bg.py
  - start_hermes_next.py
  - cowbridge/...（5 个）
```

也就是说：

- IDE 扩展（1,302 行 JS + 303 行 CSS）**在版本库**；
- 生产 Hermes 核心（`routes.py` 33,873 行、`server.py` 等）**不在版本库**；
- 定制连接器（legion/pulse/alerts/brief/events/observe 等约 1,500 行）**不在版本库**；
- 核心补丁只有 `docs/dev/` 登记文档作“唯一版本留痕”。

### 2.3 上游事实

- 上游：`https://github.com/nesquena/hermes-webui`，MIT；
- 本地快照：2026-10-17；
- 上游 README 明确写明：
  - WebUI 仍与 Hermes Agent 内部实现耦合（imports/state layout）；
  - 稳定 Agent API 边界尚未完成；
  - 跨版本搭配“untested and unsupported”；
  - 全 agent-loop delegation 尚未发布。
- 即：**上游自己都不保证版本兼容，我们在其上做核心补丁，升级风险会被放大。**

### 2.4 扩展本身

`legion-ide/README.md` 明确：

```text
方式 A：作为 Hermes WebUI 扩展运行，不修改 Hermes 核心。
```

启动脚本注入：

```text
HERMES_WEBUI_EXTENSION_DIR=...\extensions\legion-ide
HERMES_WEBUI_EXTENSION_SCRIPT_URLS=/extensions/app.js
HERMES_WEBUI_EXTENSION_STYLESHEET_URLS=/extensions/app.css
```

这部分设计是对的：官方扩展面、可回滚、已入库。

## 三、核心二开的风险矩阵

| 风险 | 证据 | 影响 | 等级 |
|---|---|---|---|
| 升级不可合并 | 核心无 git、无上游 diff；上游快速迭代 | 上游升级=手工重放/冲突 | P0 |
| 不可复现 | 代码活磁盘；只有 docs 登记 | 换机/回滚/审计靠记忆 | P0 |
| 上游兼容性 | 上游 README 自认耦合、跨版本不支持 | import/route/state 漂移 | P0 |
| 双基漂移 | next 生产、webui 回滚 | 改错基、行为不一致 | P1 |
| 扩展硬编码 | `OH_BASE=127.0.0.1:8796`、`window.open(127.0.0.1:8734/ide)`、`LDE_BASE` 分支 | 远程/PWA/双开失效；CORS/认证旁路 | P1 |
| 认证资产暴露 | `/extensions/app.js` 200 未登录；`/agent_ide_bundle.json` 200；`/lde/` 未认证 | 信息/施工台边界被打穿 | P1（LDE 为 P0） |
| 连接器无测试 | 定制 api 模块不在主仓测试体系 | 路由/契约回归靠人肉 | P1 |
| 前端单体 | 扩展 1,302 行、Hermes app.js 1,194 行 | 维护成本持续上升 | P2 |

## 四、什么做对了

1. **IDE 面板没有直接改核心 static**，走官方 extension 注入面；
2. 扩展文件在版本库，有 README/实测记录；
3. Hermes 只做 UI 门面，LDE/OH 仍是独立服务；
4. 双基保留回滚资产，至少有一套旧代码可退。

这说明团队已经有“扩展优先”的意识，问题在**连接器/补丁层没有守住同一条边界**。

## 五、建议方案

### 方案 A（推荐）：扩展 + Sidecar，核心零补丁

```text
Hermes（只做壳）
  └─ legion-ide 扩展（官方 /extensions/）
        └─ 同源 /api/ide-proxy/*（nginx 或 Hermes 薄代理）
              ├─ LDE 8103
              ├─ OH 8796
              └─ 平台 8091/8093
```

- 连接器从 Hermes 核心移到**独立 sidecar**（可复用 8091/8793 现有边界，不新增常驻优先）；
- 扩展只调同源 API，不直连 8796，不硬编码 host；
- Hermes 升级不碰我们的代码；扩展 API 变化时只改扩展。

**代价**：一次迁移（约 1–2 天）；**收益**：Hermes 可随时升级/替换。

### 方案 B（次选）：Git 化薄 fork

如果短期不能把连接器移出核心：

1. `hermes-webui-next` 初始化 git，首个 commit = 上游快照（记录 upstream commit/tag）；
2. 定制补丁单独 commit，保留 `patches/`；
3. `hermes-webui` 回滚基也打 tag；
4. 每次升级：拉 upstream → 重放补丁 → 跑扩展 smoke；
5. 至少让“二开”可 diff、可回滚、可复现。

**这是最低限度的补救，不是长期架构。**

### 明确不做

- ❌ 不再往 `routes.py` 增加新连接器；
- ❌ 不把 Hermes 当唯一入口/唯一身份源；
- ❌ 不做 Hermes 的“全面二开”（编辑器/LSP/插件市场）；
- ❌ 不在无 git 状态继续改核心。

## 七、判定

```text
IDE 面板扩展化：合理，继续
连接器嵌核心：短期可接受，限期迁出
核心补丁无版本库：不合理，必须 git 化
把 Hermes 当 IDE 底座：不合理，应视为可替换门面
```

如果只记一句：

> **可以“在 Hermes 上开面板”，不要“把平台长进 Hermes 里”。**

## 八、附注：如果你说的是“双开两个 Hermes 实例”

当前：

```text
8787 生产（hermes-webui-next）
8788 原型（已 down）
```

- 两个实例共用同一 `webui-state`/session 时，会出现状态串写、guard 双拉、端口竞争；
- 若必须双开，必须**隔离 state dir / profile / port / 日志**，并明确主实例；
- 不建议长期双开；验证用 8788 临时起、验完即停。
