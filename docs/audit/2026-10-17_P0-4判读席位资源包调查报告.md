## 四、调查结论

1. **"glm-4.6 死绑定"判定不成立——资源包现状健康**。zhipu_key 为包年主 key：coding 端点 5.3/5.3-flash/4.5-flash 全通，anthropic 端点 4.6 实测可用。org.json 绑定的是"注册语义"而非"实际调用通道"，只要 zhipu_key 在位，glm-4.6 通道活着。
2. **问题本质 = 双 key 双通道错配**：
   - GLM_API_KEY（379b…）资源包已耗尽：anthropic 端点 429[1113]；coding 端点对 4.6/4.5 不报错但静默重路由为 5.3-flash（该 key 计划不含 4.6 档位）。
   - K-ORG-136 当时切 5.3 的正确解读：旧 key（flash 档）在 anthropic 端点 429 → 换 zhipu_key + coding 端点后 5.3/5.3-flash 全通，而非"glm-4.6 不可用"。
3. **静默重路由是潜在风险**：若某调用方 key 优先级配错（用了 379b…），请求 glm-4.6 会静默拿到 5.3-flash 输出，不报错难发现——类 K-STOCK-396"API 静默忽略参数"风险模式。
4. **claude_agents.json 的 30 处 glm-4.6 无需改**：同为注册语义，实际调用走 agent_coder anthropic 通道（zhipu_key 可用）。
