# zhice-OS V2 三视角系统功能评审测试报告

> 评审日期：2026-08-27（Asia/Shanghai）
> 评审范围：产品能力、核心交易闭环、四市场一致性、桌面与移动体验、API、权限、安全控制、数据隔离、架构质量、测试与部署
> 评审视角：产品经理、技术总监、最终用户
> 结论口径：基于实际代码、自动化测试、API 冒烟与浏览器操作，不把文档声明视为已实现证据

## 一、执行摘要

### 1.1 总体结论

zhice-OS V2 已经形成了较完整的交易操作系统产品骨架：四市场统一入口、候选池、计划、风控、授权、持仓、复盘、研究、治理、监控和调度均有真实代码与页面，不是简单原型。桌面端的信息架构清晰，核心页面覆盖较广，后端领域拆分也具备继续演进的基础。

但系统当前**不满足联网部署、多人使用或真实资金交易的发布条件**。主要阻断项不是页面缺失，而是安全控制、交易正确性、数据结构与运行控制同时存在生产级缺口：

1. 后端绝大多数读写接口未做用户认证与角色授权。
2. 存在无认证的“按同一价格全平所有市场全部持仓”接口。
3. 同一授权可被手动审批和盘中循环重复全额执行；固定订单/持仓 id 又会覆盖持仓并去重成交记录，造成真实撮合、持仓和成交账本互相矛盾。
4. 全新数据库的迁移链会重复创建同一张表；ORM 另有约 12 张表和至少 5 个关键列没有迁移，无法可靠从零部署。
5. 设置页的交易模式和风控参数没有进入执行链，动作权限矩阵也未实际控制对应动作。
6. `memory` 持久化模式不能隔离 SQL，测试或演示环境仍可能读取真实库。
7. 默认认证实现包含弱默认密码、固定签名密钥和 URL 查询参数传密码，且 Git 已跟踪脚本中存在数据库凭据。

因此发布建议是：

| 使用场景 | 结论 |
|---|---|
| 单机只读研究、内部演示 | 有条件可用；必须关闭写入口并明确数据口径 |
| 内部模拟盘、小范围试用 | 整改 P0 后再试点 |
| 局域网多人协作 | 当前不建议 |
| 公网部署 | 禁止 |
| 实盘交易 | 禁止；当前实盘适配器本身也未实现 |

### 2.2 自动化失败说明

失败用例为 `test_entry_query_excludes_dead_plan_but_keeps_orphan`。根因是测试同时使用本地 `date.today()`、UTC `datetime.now(UTC)` 和 UTC profile，在上海时区跨 UTC 日界线后，测试数据落在过滤下界之前。生产调用使用市场时区计算交易日，当前证据更接近**时区相关的脆弱/地域依赖测试**，而不是已证明的生产查询回归。

仍应修复：测试应固定时钟并统一 `today` 与 `created_at` 的时区来源，避免开发机失败而 CI 因运行时区不同通过。

### 2.3 未执行项

以下操作会改变现有交易数据，本次没有在真实 SQL 数据上执行：真实审批成交、批量平仓、策略晋升/降级、生成报告、运行盘前/盘后工作流、修改生产风险参数。相关结论来自隔离 TestClient 验证与代码审查。

### 2.5 风险分级

- **P0 阻断**：可能造成未授权操作、错误交易/账本、秘密泄露、无法部署或控制失效；发布前必须清零。
- **P1 高风险**：关键业务路径明显错误、并发/市场规则可绕过，或联网后存在高可用与隐私风险。

## 三、阻断级问题（P0）

### P0-1 后端认证授权基本未接入业务接口

**证据**

- 前端工作区仅通过 `localStorage` 是否存在 token 决定放行，未校验 token 有效性。
- 后端的 `get_current_user` / `require_roles` 仅在 `/auth/me` 和 `/auth/users` 使用。
- OpenAPI 中 48 个 POST/PUT/DELETE 写操作均无安全声明。
- 无 token 调用 `POST /brokers/live`、`POST /circuit-breaker/trigger`、`POST /circuit-breaker/reset` 均实测返回 200。
- 67 个无必填参数 GET 中 65 个无 token 返回 200，意味着账户、持仓、策略、风险、报告、系统状态等数据默认公开。

**影响**

任何能访问 API 的客户端都可绕过前端，读取交易数据、批准/拒绝授权、修改风险参数、触发或解除熔断、运行工作流、晋升策略，甚至触发持仓变化。客户端传入的 `actor="user"` 还能伪造审计主体。

**整改**

1. 在 `/api/v1` 路由组设置默认认证依赖，仅对 health、login 等明确白名单开放。
2. 建立 ADMIN / TRADER / REVIEWER / VIEWER 权限矩阵，写操作按最小权限授权。
3. 服务端从 token 注入 actor，禁止客户端自报审批人。
4. 增加 401/403 契约测试：每个写端点至少覆盖无 token、错角色、合法角色。

### P0-2 无认证的全局一键平仓接口可造成灾难性误操作

**位置**：`src/zhice_os_v2/api/routers/positions.py:372`

`POST /api/v1/positions/close` 没有账户、市场、标的或 position id 参数，会遍历 `db.list_open_positions()`，把**所有市场、所有策略、所有标的**按请求中的一个 `close_price` 全部关闭。代码注释也承认同一价格并不代表真实成交价。

**影响**

- 一次误调用即可污染全部持仓、盈亏、复盘和学习数据。
- 跨市场资产使用同一个价格，财务数据必然错误。
- 接口名称没有体现 `close-all`，危险性不可发现。

**整改**

立即删除生产路由或仅在显式 test/demo profile 编译启用。生产平仓必须要求 `account_id/market/position_id/qty`、幂等键、服务端行情校验、二次确认和不可篡改审计。批量平仓要先 dry-run 返回影响清单，再使用短期确认 token 执行。

### P0-3 风控设置与交易模式是“可保存但不生效”

**证据**

`trade_mode`、`max_single_position_pct`、`max_total_position_pct`、`max_daily_loss_pct`、`stop_loss_pct` 仅在 settings router 中保存和返回，执行代码没有读取点。用户把模式切到 `manual` 或降低日亏上限，并不会改变工作流行为。

动作权限矩阵的 `_effective_permission()` 也只用于状态展示；执行链仅在两个位置读取全局 `is_tripped()`，没有消费单项 `AUTO/CONFIRM/BLOCKED`。

**影响**

这是交易系统中最危险的一类问题：界面显示保护已开启，运行时却不执行，用户会基于错误安全感放大风险。

**整改**

建立唯一的 `ExecutionPolicyService`，任何候选生成、计划创建、建仓、加仓、平仓、止损和自动报告都必须在副作用前调用。设置修改后增加端到端验收，例如 `manual` 模式下自动建仓必须返回明确拒绝；`BLOCKED` 动作必须无法执行。

### P0-4 `memory` 模式不是数据隔离边界

**证据**

- 仓库中有 115 处直接 `get_session()`、10 处直接 `psycopg2.connect()`。
- 本次用 `PERSISTENCE_BACKEND=memory` 启动，工作区仍读取到本机 SQL 中数百条计划与持仓历史。
- `PipelineService`、positions、overview 等多条用户主链直接访问 SQL，绕开 `PersistencePort`。

**影响**

开发、测试和演示人员会误以为使用内存隔离，实际仍可能读取或修改生产数据。测试数据污染与生产事故风险高于普通架构债。

**整改**

1. 禁止 application/domain/api 直接导入 `get_session`，通过架构测试强制约束。
2. 把所有 SQL 查询收敛到 repository/query service，并由环境注入实现。
3. test profile 使用独立数据库 URL，启动时校验数据库名必须带 `_test`。
4. 写操作增加环境 guard，生产凭据不得出现在开发测试进程。

### P0-5 认证密钥、凭据传输与秘密管理不满足生产要求

**证据**

- token HMAC 密钥固定为源码中的 `zhice-os-v2-dev-secret`。
- 默认管理员密码为 `123456`。
- 登录将密码放在 URL query：`/auth/login?username=...&password=...`。
- `INTERNAL_API_KEY` 默认空；中间件只有配置非空时才生效。
- 用户仅存在进程内固定 admin，没有密码哈希、锁定、撤销、轮换或会话管理。
- `scripts/import_v1_production.py`、`scripts/backfill_fill_pnl.py`、`scripts/backfill_v1_replays.py`、`scripts/backfill_sell_reason.py` 包含数据库连接凭据，且均由 `git ls-files` 确认已被版本库跟踪。

**影响**

密码可能进入访问日志、代理日志和浏览器记录；任何拿到源码的人都能伪造 token；默认配置容易直接暴露管理员权限。已经提交到 Git 的秘密不能仅通过修改当前文件解决，因为旧值仍可能存在于历史提交、镜像、备份或开发者克隆中。

**整改**

立即轮换所有已暴露的数据库凭据，检查访问日志和异常连接；从源码删除硬编码值，改由 secret manager 或部署环境注入；在评估协作影响后清理 Git 历史并重新分发凭据。认证侧使用成熟实现，密码放 JSON body 并采用强哈希；签名密钥支持轮换；生产启动时对默认密码、空密钥、开发 secret 执行 fail-fast；增加登录限速、失败锁定、token 撤销和安全审计。

### P0-6 全新数据库无法执行完整迁移

**证据**

- `migrations/versions/0001_initial.py:165-174` 已创建 `v2_market_calendar`。
- `migrations/versions/0002_market_calendar.py:18-28` 再次创建同名表，且主键类型由 `BigInteger` 变为 `Integer`。
- 因此 fresh `alembic upgrade head` 会在 `0002` 遇到 DuplicateTable；历史开发库可运行不能证明新环境可复制。
- Docker API 镜像又未复制 migrations、未在启动流程执行 migration，健康检查也不会验证 schema 版本。

**影响**

新开发环境、灾备恢复、CI 临时数据库和正式发布均无法按标准路径初始化。依赖手工建表或历史库会让不同环境的 schema 继续分叉，回滚和故障恢复不可预测。

**整改**

不要修改已经在外部环境执行过的迁移历史来“掩盖”问题；先盘点各环境 Alembic revision 与真实 schema，再制定兼容迁移。为 fresh install 修复重复建表路径，为既有库提供可重复执行的校正 revision。CI 必须每次在空 PostgreSQL 上执行 `upgrade head`、schema diff、最小 CRUD 冒烟和 `downgrade/upgrade` 演练。

### P0-7 ORM 与迁移严重漂移，关键业务路径可能首触即崩

**证据**

- SQLAlchemy 元数据共 39 张模型表，迁移只覆盖约 27 张。
- 至少 12 张模型表无正式迁移，包括 `v2_app_state`、`v2_adj_factor`、`v2_earnings_forecast`、`v2_holder_trade`、`v2_top_list`、`v2_dividend`、`v2_market_environment`、`v2_promotion_decision`、`v2_gray_release`、`v2_backtest_run` 等；个别表靠运行时自建不能替代受控迁移。
- 至少 5 个模型列未进入迁移：`v2_strategy.description`、`v2_bar_daily.pre_close`、`v2_fill_record.realized_pnl`、`v2_fill_record.sell_reason`、`v2_learning_case.status`。
- 写入路径还会运行时创建唯一索引，说明 schema 所有权同时分散在 Alembic、repository 和 scheduler 中。

**影响**

即使绕过 P0-6，策略 CRUD、行情同步、平仓盈亏、学习闭环、环境判定、灰度发布和回测等功能也可能因 UndefinedTable/UndefinedColumn 在第一次使用时失败。现有测试大量使用内存库或已有历史库，无法拦截该问题。

**整改**

以生产模型为基准生成新的显式 migration，并逐表逐列人工复核默认值、非空约束、索引和数据回填顺序；删除运行时 DDL，把 schema 变更收口到 Alembic；CI 增加 `alembic check` 或等价 schema diff，并禁止模型变更在无迁移时合并。

### P0-8 同一授权可重复撮合，持仓与成交账本会失真

**证据**

- 授权状态只有 PENDING/APPROVED/REJECTED/EXPIRED/CANCELLED，没有 EXECUTING/EXECUTED/FILLED 终态；执行后仍可被查询为 APPROVED。
- 手动批准会立即调用执行服务，盘中入场循环又会重复扫描 APPROVED 授权；二者没有共享事务锁或消费标记。
- `_auto_execute()` 每次都使用固定 `order_id = "{request_id}-sim"`，`ExecutionService.apply_fill()` 又固定生成 `position_id = "pos-{order_id}"`。
- SQL repository 遇到同一 position id 时直接覆盖 `open_qty`，不累加、不生成新 lot；成交和意图记录也按固定 order id 去重。
- `MAX_ENTRIES_PER_PLAN = 2` 的计数依赖去重后的 order intent，重复执行未必产生第二条可计数记录，次数闸门无法可靠阻断。

**影响**

同一授权可能在真实撮合语义上被执行多次，但数据库只保留一次成交或最后一次持仓数量。资金占用、仓位、平均成本、成交审计、风险预算和复盘数据会相互矛盾；这是会直接算错仓位与资金的交易正确性故障。

**整改**

建立一次性授权消费状态机：APPROVED -> EXECUTING -> PARTIALLY_FILLED/FILLED/CANCELLED，并以数据库条件更新或行锁原子抢占执行权。每一次尝试使用独立 execution id/order id，业务幂等键对同一授权只允许一个活动执行；部分成交维护 remaining qty。持仓按不可变 lot 新增或在乐观锁下原子累加，成交记录不得用覆盖/静默去重替代一致性约束。补充双线程、双进程、重试和部分成交集成测试。

## 四、高优先级问题（P1）

### P1-1 登录成功后流程中断

浏览器实测：从大屏点击 A 股进入登录页，登录成功后仍停留在 `/login`，只显示“登录成功：admin / ADMIN”，没有返回来源页面，也没有进入默认工作台。

建议在 ProtectedRoute 保存 `location`，登录成功后 `replace(from || '/cn/overview')`；已登录用户访问 `/login` 应自动离开。

### P1-2 跨市场快捷导航强制跳回 A 股

浏览器实测：

- 美股工作台点击“查看决策流”后进入 `/cn/signals?tab=pipeline`。
- 点击美股代码 `WDAY` 后进入 `/cn/overview?tab=kline&symbol=WDAY`。

根因是 Dashboard 和 SymbolLink 使用 `/pipeline`、`/approvals`、`/kline` 等旧路由，而旧路由表统一重定向到 CN。所有工作区内跳转应使用当前 market route，公共组件从 MarketContext 获取市场。

### P1-3 桌面首页关键数字口径不一致且缺少时间维度

A 股工作台实测同屏显示：

- 最新候选 `14`，闭环候选 `516`；
- 当前持仓 `0`，闭环“持仓” `135`；
- 当前待授权 `0`，闭环待授权 `8`（在 memory/SQL 混用环境下尤为明显）。

Pipeline 的候选和持仓实际是“每个标的历史上曾出现过候选/持仓”的去重累计，页面却使用现在时“候选/持仓”。建议统一成“当前快照”或明确标为“历史覆盖标的”；每项都显示 `as_of`、过滤范围和口径说明。

### P1-4 移动端核心工作区不可用

390x844 实测：固定侧栏 216px，主内容只剩约 166px；document scroll width 为 631px；顶部四市场、页签、表格、标题和底栏均被截断或纵向挤压。

当前 media query 只覆盖大屏首页，没有工作区布局断点。建议小屏改为抽屉导航、底部关键导航或只读模式；表格提供固定首列和横向滚动；工具栏分行；至少覆盖 390、768、1024 三档视觉回归。

### P1-5 公开大屏在异常时显示 `NaN` 并静默吞错

接口未正确返回时，大屏实测总资产和四市场资产显示 `¥NaN`。HomeBigscreen 对多数请求 `.catch(() => {})`，用户只能看到破折号或 NaN，无法区分“真实为零”“暂无数据”“数据源故障”。

应对所有数值做 `Number.isFinite` 守卫；保留上次成功值和 as-of；显式展示 stale/error 状态；公共大屏若保留公开访问，只能使用脱敏聚合接口。

### P1-6 Docker 声称的一键部署不能得到完整可用系统

`docker-compose.yml` 只有 Postgres、Redis、API，没有前端；API 容器未复制 migrations，也没有执行 `alembic upgrade head`。即使手工执行，当前 migration 仍会触发 P0-6 的重复建表。SQL repository 不会创建全部表，只有少数表有按需建表逻辑。健康检查只检查 `/health`，数据库表缺失时仍可能显示健康。

建议提供 frontend 构建/静态托管、migration 独立 job、数据库 readiness、应用级依赖检查和最小种子流程。README 的 Docker 说明必须与实际部署形态一致。

### P1-7 实盘开关是孤立状态，实盘能力实际不可用

`POST /brokers/live` 只修改 `BrokerConfigService.live_enabled`，没有连接 `StrategySwitch` 或 `LiveBroker.enabled`；`LiveBroker.place_order()` 在 enabled 后仍抛 `NotImplementedError`。

产品应把它明确标记为“尚未接入”，隐藏生产开关，避免用户误以为已经具备真实下单能力。等真实 adapter、订单回报、撤单、对账、幂等和风控全部验收后再开放。

### P1-8 错误吞没过多，故障容易伪装为空数据

源码含 129 个 `except Exception`。多个市场、持仓、候选、overview 路由捕获异常后返回空列表、0 或 None。交易系统中“空仓/无候选”和“数据库故障/行情故障”必须严格区分。

建议统一错误码、trace id、结构化日志和可观测指标；只对已知可降级异常降级；写失败不得 fail-open；用户页面显示错误状态而不是空态。

### P1-9 静态汇率会影响跨市场权益，但大屏缺少醒目标识

跨市场折算使用 2026-01-01 静态汇率（USD 7.2、HKD 0.92、USDT 7.2），后端正确返回了 `fx_stale=true`，但大屏契约未声明 `fx_stale/fx_asof`，仅显示“CNY 归一”。

应接入带时间戳的真实汇率；在此之前，跨市场总资产必须展示“估算/静态汇率”和日期，不应作为真实净值或风控基数。

### P1-10 前端缺少自动化质量门

前端没有 unit/component/E2E 测试，没有 ESLint 和可访问性检查，CI 也只跑 Python。登录不跳转、跨市场跳 CN、移动端崩坏都属于低成本自动化可以拦截的问题。

建议至少补：Vitest + Testing Library、Playwright 核心链路、axe、路由矩阵、响应式截图、构建 chunk 阈值，并纳入 CI 阻塞。

### P1-11 部分平仓路径绕过 A 股 T+1 与可卖性检查

`run_intraday` 的常规止盈止损路径会检查 T+1、停牌和涨跌停可卖性，但 `run_spec_signals` 在收到 exit 信号后直接调用 `_close_position()`；该底层函数本身不检查市场规则。CN spec 任务每 5 分钟运行时，可能把当日开仓在当日按不可成交价格平掉，也可能在跌停封死或停牌时产生“成功止损”的虚假记录。

应把 T+1、交易时段、停牌、涨跌停、可用数量和账户状态收敛到唯一平仓 Command，任何调用方都不能绕过。补充 CN 当日开仓、次日可卖、跌停封死、停牌和节假日矩阵测试。

### P1-12 调度器、API 与手动审批之间缺少并发互斥

API 可手动触发 workflow，scheduler 同时运行盘前/盘中任务；启动 catch-up 与固定时点 job 采用 check-then-act 判定，没有跨进程锁。手动批准立即执行与盘中授权扫描也构成双执行入口；平仓读取 OPEN 后再更新 CLOSED，没有行锁或版本号，两个任务可同时关闭同一持仓。

建议按 `market + trade_date + job_type` 使用数据库 advisory lock/租约锁，并让交易 Command 使用行级锁或乐观版本。调度触发只创建幂等 job run，worker 原子领取；对双 worker、超时重试、进程崩溃恢复做并发测试。

### P1-13 部分成交、费用、超卖和风控参数没有形成完整核算链

- PARTIALLY_FILLED 只把本次 `filled_qty` 入仓，没有可靠维护剩余委托量，后续重试可能再次按原始全量下单。
- SELL 数量超过可用持仓时，FIFO 消耗完现有 lot 后将剩余量静默丢弃，没有拒绝或异常回执。
- `OrderResult.fee` 已计算佣金、税费等，但没有进入持仓成本、已实现盈亏和权益，模拟收益系统性偏高。
- 平仓状态、盈亏和成交记录跨多个提交步骤，任一步失败都可能留下 CLOSED 但 pnl/fill 不完整的状态。
- 风险预算与流动性规则的部分调用点没有传 stop price/turnover，相关规则实际恒不生效；无行情时还有 `ref_price=100` 的估值兜底。

应引入订单/成交/持仓/现金的双向可核对账本，把 fee、remaining qty、拒绝原因和版本号纳入模型；一个成交应用必须在同一事务内更新订单、lot、现金、费用与审计事件。风险规则参数缺失时应 fail-closed，不得用固定价格静默替代。

### P1-14 WebSocket 绕过 HTTP 鉴权且实时链路可被慢客户端阻塞

`/api/v1/market/ws/market` 没有 token 或 internal key 校验；FastAPI 的 HTTP middleware 不会拦截 WebSocket，因此即使 HTTP 配置了 key，行情推送仍可匿名连接。广播对客户端逐个串行 `await send_json`，没有订阅、心跳、发送超时或背压；一个慢连接会拖慢后续客户端。应用 lifespan 每 5 秒还在 asyncio 事件循环内执行同步 SQL 查询。

应在握手阶段认证并按用户/市场授权订阅；每连接使用有上限的发送队列、超时、心跳和慢消费者断开策略；同步 SQL 移到线程池或异步驱动；增加连接数、消息延迟、断线重连与洪泛测试。

## 五、中优先级问题（P2）

1. **README 严重过时**：仍写“当前测试 37 passed”、真实数据/实时推送/券商为后续待办，与现有 198 项测试、真实网关和 WebSocket 代码不一致。
2. **类型债高**：mypy 110 个错误涉及 optional、DTO、repository enum/id、market data 和 pipeline 类型，不应长期设为 CI `continue-on-error`。
3. **生产包体偏大**：单 JS chunk 1.35MB，首屏加载和低性能终端体验受影响；应按功能组 lazy load。
4. **认证只看 localStorage**：伪造任意字符串即可进入工作区，直到个别受保护 API 失败；应启动时调用 `/auth/me`。
5. **审批“通过”一键执行**：没有订单摘要二次确认；拒绝反而要求原因。至少应显示市场、账户、方向、数量、限价、预估金额、风控结果和过期时间。
6. **登录页视觉与产品壳脱节**：裸 h1/input/button，缺少加载态、返回入口、忘记密码/联系管理员路径和会话过期提示。
7. **系统状态过度乐观**：侧栏固定显示“在线、调度器运行中”，应由真实心跳和依赖检查驱动；数据库/行情错误不能仍显示在线。
8. **健康检查太浅**：API 存活不代表 DB schema、Redis、调度器、行情源和 WebSocket 可用。
9. **部分页面控件缺少可访问名称**：多个 input 依赖视觉上下文，没有 label；SymbolLink 用 span + role link，缺少键盘行为和 href。
10. **文案混合内部枚举**：用户页面直接出现 `replay` 等英文阶段值；应统一业务文案并保留技术值到详情/tooltip。
11. **部署端口文档不一致**：README/Makefile/Docker 使用 8002，部署文档使用 8102，前端默认代理为 localhost:8002。
12. **CI 未验证部署**：没有 migration from empty DB、Docker build、前后端联调和 scheduler 启动测试。
13. **会话异常路径可能泄漏**：多处 `session.close()` 未放在 `finally` 或上下文管理器中，数据库异常后可能持续占用连接。
14. **同日重跑可复活终态对象**：部分 upsert 没有状态守卫，可能把 CANCELLED/REJECTED 的计划或授权重新写回活动状态。
15. **ST 市场规则识别不可靠**：证券名称加载路径返回空映射时，A 股 ST 5% 涨跌停规则退化为普通 10%。
16. **运行时 DDL**：行情 upsert 每次执行 `CREATE UNIQUE INDEX IF NOT EXISTS`，既增加写路径开销，也使 schema 依赖业务代码是否曾运行。

## 六、产品经理视角

### 6.1 做得较好的部分

1. 信息架构从大量页面收敛为“市场 x 八功能组”，方向正确，降低了模块发现成本。
2. 交易闭环主线完整：候选、计划、风控、授权、持仓、复盘、学习和治理可以在一个产品中串联。
3. 四市场采用统一界面并保留市场差异，具备平台化价值。
4. 工作台能同时呈现账户 KPI、待办、闭环和持仓，符合交易人员扫描式使用习惯。
5. 复盘、日报、知识库、策略衰减和治理让产品不只停留在“下单工具”。

### 6.2 产品定义问题

- “真实交易能力”和“模拟/占位能力”边界不清。实盘开关存在但实盘适配器未实现。
- “系统设置”给出强控制感，但参数没有接入执行链。
- “已批准”被同时当成可重复扫描的执行条件，而不是一次性消费状态，产品状态机没有覆盖订单生命周期。
- 漏斗把历史累计和当前快照混在同一屏幕，指标没有 as-of 与统计周期。
- 公开大屏展示资产聚合，需要明确产品究竟面向私人单机还是组织指挥中心，并据此重新设计隐私边界。
- 当前功能面很宽，但策略创建、回测、AI 研究、模型注册等部分缺少从结果到生产使用的明确验收链路。

### 6.3 产品优先级建议

短期停止继续扩页面，先建立“可信控制面”和“可信账本”：权限、一次性授权、订单状态、数据口径、配置生效、审计、错误状态和生产部署。交易产品的核心不是功能数量，而是用户能确认“谁在什么时间基于哪份数据做了什么动作，是否只执行一次，控制是否真实生效，资金和仓位能否对账”。

## 七、技术总监视角

### 7.1 架构优点

- 模块化单体、domain/application/infrastructure/api 分层方向合理。
- MarketProfile、BrokerPort、PersistencePort 等抽象符合多市场扩展目标。
- 交易关键逻辑已有较多单元测试，Ruff 可作为基础质量门。
- 调度器已显式使用市场时区，并覆盖四市场多类任务。
- 近期修复针对跨币种、卖出方向、部分成交、市场状态等问题已有明显进展。

### 7.2 架构风险

- 分层边界未被执行：API/application 大量直接访问 session，PersistencePort 变成局部抽象。
- 控制面分裂：settings、broker config、strategy switches、circuit breaker 各有独立状态，没有统一决策入口。
- 授权、委托、成交、持仓缺少严谨状态机和事务边界，重复执行、部分成交与重试无法保持一致。
- ORM 模型与 Alembic schema 没有同一所有权，空库迁移失败且大量表列漂移。
- 内存状态、SQL 状态和多进程 scheduler 状态并存，跨 worker 一致性脆弱。
- 大量宽泛异常吞没破坏可观测性，也会掩盖数据不完整。
- 类型错误集中在 ORM/领域枚举/ID 契约，说明模块间契约仍未稳定。
- 部署没有把 schema migration、frontend 和 readiness 纳入一个可复现发布单元。

### 7.3 推荐目标架构

1. API 默认认证，Command 层执行 RBAC、幂等、审计和 policy check。
2. Query/Repository 统一承载 SQL；领域与应用层禁止 import ORM/session。
3. `ExecutionPolicyService` 成为所有副作用的唯一前置闸门。
4. 授权、订单、成交、lot、现金采用显式状态机；以原子状态迁移消费授权，以独立 execution id 记录每次尝试。
5. 将配置改为版本化、可审计、可回滚的数据库对象，发布事件通知 API 与 scheduler。
6. 交易写链使用单事务、outbox/event、幂等键和版本号；关键动作留下前后状态快照。
7. Alembic 成为 schema 唯一变更入口，以空数据库部署 E2E 和模型/schema diff 作为发布基线。

## 八、用户视角

### 8.1 桌面端体验

优点是导航清楚、信息密度适合专业用户、市场切换醒目、表格与业务标签较丰富。主要痛点是可信度：同屏数字不一致、登录后不前进、错误时 NaN/空白、跨市场操作跳回 A 股。对于交易用户，任何一个口径冲突都会使整屏数据失去参考价值。

### 8.2 决策与操作体验

- 审批列表应优先回答“为什么买、风险是什么、金额多大、何时失效”，当前主要展示标的/方向/数量。
- 自动执行和熔断需要在所有页面保持一致、醒目的全局状态，不应只是某个标签页的控件。
- 任何行情缺失、静态汇率、延迟数据都要显式标 stale，不能用开仓价或 0 伪装正常。
- 高风险操作需要预览、确认、结果回执和审计编号。
- 授权通过后必须显示唯一订单号、已成交/剩余数量、费用和最终状态；同一授权不得出现多份互相矛盾的持仓或成交回执。

### 8.3 移动端体验

当前不是“体验欠佳”，而是核心布局不可操作。若产品不计划支持移动交易，应明确做响应式只读看板；如果要支持操作，则需要重新设计导航和密度，不应简单压缩桌面布局。

## 十、发布验收标准

满足以下条件后，才建议进入内部模拟盘试点：

- 无 token 的所有业务读写接口均返回 401；错角色写操作返回 403。
- Git 当前版本和扫描范围内不存在硬编码秘密；已暴露凭据全部轮换，旧凭据验证为不可用。
- `manual` 模式、BLOCKED 动作和各项风险参数有可重复的端到端阻断测试。
- memory/test 环境对生产 DB 执行连接即启动失败，不能静默旁路。
- 新建空数据库可通过 migration 启动完整前后端并完成一次模拟闭环；ORM/schema diff 为零。
- 同一授权经手动、调度、重试和双 worker 并发触发时只产生一次有效执行；每次部分成交的 remaining qty、lot、fill、费用和现金可对账。
- 所有平仓入口都通过 T+1、停牌、涨跌停、可用数量和账户状态校验。
- 后端 pytest 全绿，无时间/时区漂移；关键交易包覆盖率达到 85% 以上。
- 前端核心 E2E 覆盖登录、四市场切换、候选到授权、持仓、复盘和会话过期。
- 390/768/1440 三档视口无主布局溢出；移动端若不支持交易，必须显式只读。
- 工作台所有 KPI 均有统一口径、统计周期、币种和 as-of。
- 任何数据源错误不得显示为 0、空仓或 NaN；必须显示故障/陈旧状态。
- 审批、执行、平仓、配置和治理变更均可追溯到真实用户、请求、前后状态与结果。
- WebSocket 未认证连接被拒绝；慢客户端、断线重连和消息洪泛不影响其他用户或 API 事件循环。

## 十一、最终判断

本系统的优势是“业务闭环已经长出来了”，当前最需要解决的是可信性而不是继续扩展功能。以产品演示标准看，它已经超过一般 MVP；以交易生产系统标准看，权限、一次性执行、账本一致性、控制生效、数据隔离和部署可复现性均未过最低线。

建议将下一版本目标定义为“可信模拟盘版本”，暂缓实盘与更多功能扩张。先让每一个数字可解释、每一个设置真实生效、每一个授权只消费一次、每一笔成交和仓位可对账、每一个环境彼此隔离，再进入真实资金相关阶段。当前结论为 **No-Go**：完成全部 P0 并通过上述验收前，不应开放自动模拟交易、多人联网部署或任何实盘能力。
