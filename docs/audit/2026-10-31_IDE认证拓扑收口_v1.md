## 一、背景与目标

现状两个问题：

1. **8734→/hermes/ 双登录**：nginx `/hermes/`、`/extensions/` 已有 `auth_request /_auth_guard`（门户 session 校验），但 8787 的 Hermes 自身仍以「密码认证」运行（`start_hermes_bg.py` Phase B2 从 `_vault\legion_ide\hermes_webui_password` 注入 `HERMES_WEBUI_PASSWORD`）。结果：过了门户认证后，Hermes 还要再输一次密码 → 第二次登录，且 PWA 入口体验断裂。
2. **8787 直连 A0 可执行**：Hermes 扩展 `a0-mainchat.js` 在 8787 直连时把主聊天切到 A0（`http://127.0.0.1:8796` 执行面）。直连页没有门户身份，却仍会去调 8796（被 403 或形成无认证旁路），语义与"零信任/同源"不一致。

目标：

- A. 用 Hermes **原生 trusted-header 认证**（`HERMES_WEBUI_TRUSTED_AUTH_HEADER`）取代第二道登录步骤；nginx 对 `/hermes/`、`/extensions/` 在 auth_request 通过后注入 `X-Portal-User`（单用户常量 `laotian`）；直连 8787 无该头 → Hermes 原生 302（页面）/401（API）。
- B. 直连 8787 的 A0 主聊天进入**只读模式**：不调 8796 执行，显示"直连只读/请走 8734"；8734 同源（`/openhands/` 反代）行为不变、仍可执行。
- C. 测试不依赖生产：nginx 静态断言 + JS `node --check` 与可执行断言。
- D. 落盘改动/验证/回滚/残余风险（本文档）。

## 三、认证拓扑（改动后）

### 3.1 nginx / 8787 链路

```
浏览器(8734) → nginx auth_request /_auth_guard → 8091 /api/auth/guard（门户 cookie）
   200 → 注入 X-Portal-User: laotian → 8787 Hermes
        Hermes: peer=127.0.0.1（loopback，默认信任）+ X-Portal-User 非空
        → ensure_trusted_auth_session 建 trusted 会话 → 直接进（无第二道密码）
   401 → @login_required → 302 /login?next=...（门户登录，仅一道）
```

### 3.2 直连 8787（无该头）

```
浏览器直连 http://127.0.0.1:8787/
   页面 → 302 /login（Hermes 原生；trusted 头缺失，不建会话）
   API  → 401（{"error":"Authentication required"}）
   /health → 200（PUBLIC_PATHS 公共探活，监控不受影响）
   密码登录 → 页在但密码=每次启动随机未知值 → 不可用（等价拒绝）
```

### 3.3 Hermes 原生能力依据（只读核对 api/auth.py，未改）

- 环境变量名：`HERMES_WEBUI_TRUSTED_AUTH_HEADER`（auth.py:105）；header 名合法性校验 auth.py:667-679；取值 auth.py:752-761。
- trusted 会话建立：auth.py:905-944；**只采信 loopback/白名单 peer**：auth.py:917-923 → `api/routes.py:_raw_peer_is_trusted_proxy`（routes.py:7199-7214），默认信任链 `127.0.0.0/8`、`::1/128`（routes.py:7145-7170），可用 `HERMES_WEBUI_TRUSTED_PROXY_CIDRS` 扩（本单不需要，见下）。
- 认证总开关：`is_auth_enabled = 密码 ∨ passkey ∨ OIDC ∨ trusted`（auth.py:570-577）；密码优先级 env > settings（auth.py:430-438）——这是「随机密码覆盖 settings 旧 hash」的依据。
- `/health` 在 PUBLIC_PATHS（auth.py:52-53），无需认证。

### 3.4 关键实测：容器→宿主 127.0.0.1 的 peer 是 loopback

nginx 跑在 Docker（`ai-portal`，nginx:alpine），经 `host.docker.internal` 连宿主 8787。为确认 Hermes trusted 头不会被 peer 校验拒绝，2026-10-31 08:2x 做了一次**只读诊断**：

- 方法：在宿主开一次性 loopback TcpListener（临时端口，秒级关闭）→ `docker exec ai-portal wget http://host.docker.internal:<port>/` → 读取宿主侧看到的 socket 对端。
- 结果：**peer = 127.0.0.1:64166**。
- 结论：Docker Desktop 的 host.docker.internal 转发在宿主侧以 loopback 出现，Hermes 默认的 loopback 信任即可满足；**无需**设置 `HERMES_WEBUI_TRUSTED_PROXY_CIDRS`（避免放宽信任面）。

## 六、残余风险（诚实边界）

- **R1 本机伪造头边界（最重要）**：Hermes 对 trusted 头的唯一校验是「socket peer 属于 loopback/白名单」+「头非空」。8787 只绑 `127.0.0.1`，因此**本机上任何进程**都可以 `curl -H "X-Portal-User: laotian" http://127.0.0.1:8787/` 获得 trusted 会话并访问 Hermes（含其会话/文件/终端等原生能力）。这是本机信任边界，不是远程可伪造（8787 不对外）；但"本机多用户/恶意进程"模型下等于免认证。缓解建议（后续单，需拍板）：① trusted 头值改为 nginx 与 launcher 共享的一次性随机 secret（两边同源注入，客户端猜不到；仍需防本机读取）；② 评估把 Hermes 原生高危能力收紧；③ 保留 loopback-only + 监控 8787 直连/异常登录（`/api/auth/status`、Hermes 访问日志）。本单不扩大攻击面（未开放 CIDR、未改绑定）。
- **R2 旧密码会话 cookie 仍在**：重启前已签发的 Hermes 密码会话（服务端 `.sessions.json`）在 TTL 到期前仍可能直连 8787 有效；本单未撤销（清 `.sessions.json` 属运行态变更，超出本单写作用域）。影响：短暂窗口内"旧登录者直连 8787 可进"，但 A0 执行已被本单只读模式挡住。
- **R3 密码入口形式上仍存在**：随机密码覆盖后 `/api/auth/status` 仍报 `password_auth_enabled=true`（Hermes 判"配置了密码"），登录页仍显示密码框，但无人知道随机值 → **等价不可登录**。若要连 UI 入口都消失，需改 auth.py 或清 `settings.json` 的 `password_hash`（均超出本单允许范围，需另行批准）。
- **R4 `/mission`、`/console` 未注入 trusted 头**：本单严格限定 `/hermes/`、`/extensions/`。部署后这两个旧诊断页经 8734 将 302 到 Hermes 登录页（原先可密码登录；现密码不可用 → 实际不可达）。如需保留，后续单补同样两行头即可。
- **R5 部署顺序**：先 Hermes 后 nginx 会出现 `/hermes/` 短暂 302 不可用（见 §4.2）；必须按"先 reload nginx → 再重启 8787"。
- **R6 扩展发布链**：生产加载的是 `_vault\...\legion-ide\current` release（junction），不是本仓工作树；合并后不执行 §4.2.2 的 build/promote/切换，则 a0-mainchat 只读改动**不生效**（不报错、静默旧版）。
- **R7 8787 `start_hermes_next.py`（8788 验证环境）未改**：仍无 trusted 头配置、扩展用工作树路径；非生产，不影响本单。
- **R8 头注入不是"会话吊销"机制**：用户退出门户后，Hermes 侧 trusted 会话是另一本账（Hermes 自行签发 cookie）；门户登出不等于 Hermes 登出。本单不改退出语义（后续可评估 `HERMES_WEBUI_TRUSTED_AUTH_LOGOUT_URL`）。
