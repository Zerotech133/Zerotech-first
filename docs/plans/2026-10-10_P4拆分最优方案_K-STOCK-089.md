# P4 拆分最优方案（K-STOCK-089，基于 077 施工图强化）
> STATUS: frozen（只读保留）



> 2026-10-10 深夜 · 回答老田「巨石文件最优解」· 前置：077 施工图（docs/plans/2026-10-10_P4拆分施工图.md）勘察正确，本方案不推翻、只强化

## 一、判定：拆法本身已经是最优，不需要换方案

portal_api.py 实测 **23,398 行 = 模块级函数约 4,960 行 + Handler 类 18,408 行（112 方法）**。候选方案对比：

| 方案 | 风险 | 判定 |
|---|---|---|
| ❌ 重写为 Flask/FastAPI 包结构 | 111 条路由行为全量重验，等于重写全站 | 不做 |
| ❌ 一次性拆完 | 单次 diff 万行，无法回退定位 | 不做 |
| ✅ **Mixin 渐进拆分（077 原案）** | 每批独立提交+三重门槛，可逐批回退 | **保持** |

理由：Mixin 多继承下 `self._json/_html/共享态` 全兼容、调用点零改动、路由分支（do_GET/do_POST）留基座不动——这是对 2.3 万行在产文件风险最低的搬法。

## 二、五项强化（077 图没有的）

### 强化 1：先建 api_common.py，把依赖斩成单向（新批 0，最优先）

实测依赖密度：`_read_json`/`pill_nav`/`log_exc` 各被引用 **~65 次**、`_news_db` 7 次、`_kline_data` 5 次。
Mixin 文件必须 import 这些 helper——若留在基座，`api_kg.py → import portal_api` 就是**循环 import**，这是 077 图未点破的最大暗雷。

分层定死：

```
api_common.py   ← _read_json/_env_market_key/pill_nav/_tabs_html/_back_link_html/log_exc/
                  _portal_token/_load_cainiao_env + ROOT/REPORTS_DIR 等常量（零依赖）
api_kg.py 等    ← from portal_api_common import *   （只向下依赖）
portal_api.py   ← import api_common + 各 Mixin，Handler(common.Base, kg.KgMixin, ...)（顶层装配）
```

规则：**common 不许 import 任何 api_\*；Mixin 之间互不 import**。违者说明归域错了，回炉。

### 强化 2：调批次顺序——先小域试批，再啃 kg 大块

077 把 kg 大块（7,200 行）排第 1。**反对此顺序**：第一批就该拿最小域验证整条流程（脚本+门槛+回退），错了代价最小。修订批次：

| 批 | 内容 | 规模 | 为什么 |
|---|---|---|---|
| 0 | api_common.py（helper 下沉） | ~300 行 | 斩循环依赖，后面所有批的地基 |
| 1 | api_data.py（data_sync/warehouse，12 个） | ~800 行 | **最小域试批**：验证脚本+门槛全流程 |
| 2 | api_bridge.py（6 个，自闭合） | ~700 行 | 第二验证批 |
| 3 | api_kg_pages.py（kg 大块 L14404~21626） | ~7,200 行 | 流程已验证，安全啃最大单体（体积砍 40%） |
| 4 | api_portfolio.py（council/debate/portfolio 19 个） | ~1,500 行 | |
| 5 | api_chanlun.py（9 个，注意 pool/anno 交互） | ~2,500 行 | |
| 6 | api_backtest.py + api_pulse.py + page_html | ~4,000 行 | |
| 7 | misc 尾批（逐个人工归域，禁机扫硬塞） | 剩余 | 基座最终只留：Handler 基座+路由分支+misc 骨架，目标 <3,000 行 |

**每批一个 Mixin、一次提交**；批 3 完成后即可宣布"巨石已死"（降到 ~15K），批 7 是收尾不阻塞其他事。

### 强化 3：三重门槛之外加第四道——AST 方法集断言

route_baseline 三件套（`--check` 零 diff / `--probe-all` ≥51/52 / settle+test_paper_engine）保持。新增机械校验，搬前搬后各跑一次对比：

```python
# tools/_mixin_integrity.py：AST 提取 Handler 方法名集合，diff 必须为零
before = {m.name for m in ast.parse(old_src) if isinstance(m, ast.ClassDef)}
after  = set()
for f in glob('portal/api_*.py'): after |= extract(f)
after |= extract(new portal_api.py Handler)
assert before == after   # 多一个少一个都拒收
```

这防住"搬丢一个方法但路由探针恰好没打到"的静默缺损。

### 强化 4：施工窗口独占令

今天并行线还在改 build_pick_verdicts、我们刚加 /algo——**拆分期 portal 域必须冻结其他改动**。规则：10-17 施工日起，K-STOCK/并行线任何 portal_api.py 改动一律挂账到拆分结束后；拆分分支上只允许"搬代码不改逻辑"的提交（commit 前缀 `P4-批N:`）。

### 强化 5：防再膨胀闸门（拆完立装）

拆分没意义如果文件再长回来。拆完后在仓库加 pre-commit 级检查（或晨检项）：

- `portal_api.py` 行数 **>5,000 拒收新增 handler**（新页面一律独立模块挂路由，/algo 模式已示范）；
- 任何新路由文件 >2,000 行须开新域 Mixin。

## 三、执行安排

- **谁执行**：077 原计划"10-17 automation 照此施工"——建议改为**脚本批量搬+每批人工过目**（纯 automation 万行级搬迁太冒险，一批错检探针未必抓得住）。
- **节奏**：批 0~2 一晚可完成（试批+验证流程）；批 3 单独一晚；批 4~7 每晚一批，**总计约 5~6 个工作晚**。
- **回退预案**：每批独立 commit，出问题 `git revert` 单批即可；批 3 前 tag 一次 `pre-p4-kg`。
- **不动项**：do_GET/do_POST 路由分支、_COCKPIT_CSS、端口/令牌逻辑、nginx 反代约定——全部留基座。

## 四、一句话总结

**不换拆法、不加速、不加戏：077 的 Mixin 渐进拆分已是巨石文件的最优解，本方案补的是它没点的三处暗雷——common 层斩循环依赖、先小批验证再啃 kg 大块、AST 方法集断言堵静默缺损——外加一条拆后防再膨胀闸门。约 5~6 晚还清这笔 2.3 万行的债。**
