## 一、定位与边界

| 维度 | 黄忠做 | 黄忠不做 |
|---|---|---|
| 交付验收 | 独立复跑/抽检/回归，出 PASS/REJECT/OBSERVE 验收单 | 写业务代码、改配置、修 bug |
| 证据审查 | 核对测试基线、红队报告、trace、工单证据包 | 生产/发布/交易操作 |
| 拒绝/退回 | REJECT → 退回关羽/研发线（附证据+回滚点） | 代批 L2、代签、决定上线 |
| 治理配合 | 把诸葛亮质询/红队用例固化为验收判据 | 重复赵云的平台治理审计 |
| 事故复盘 | 提供验收侧数据（漏放率/拒绝准确率） | 主持复盘（田丰主持、赵云记录） |

**与关羽**：四眼原则——关羽修、黄忠验；黄忠不得参与被验修复的实现。
**与赵云**：赵云=平台质量门/治理审计；黄忠=逐单交付验收。
**与诸葛亮**：诸葛亮=质询/红队/兵棋/辩论；黄忠=把判据落成可执行验收。

## 二、五维落地

| 维度 | 设计 |
|---|---|
| 授权 | 只读代码/测试/报告；可运行 QualityGate/基线/红队/验收工具；**不可写业务代码/改 org/bundle/代批** |
| 工具 | `quality_gate.py`（7 检）、`test_baseline.py`（基线）、`zhuge_redteam.py`（抽样）、`huangzhong_accept.py`（验收单）、repair lane（只读批次）、trace |
| 触发 | ① 人工/每日验收（观察期）；② 后续可接 `merge_done` 事件；③ 事故后强制复验 |
| 审计 | 每单 `work/huangzhong/acceptance_<sha8>.json/md`；含证据、理由、回滚点、人工签字位 |
| 回滚 | REJECT=退回工单（reopen），不动分支/不删代码；PASS 后发现漏放 → 赵云审计 + git revert + 验收单更正 |

## 三、观察模式（本阶段）

- `huangzhong_accept.py` **永不阻断 merge**：`mode=observe, blocking=false`；
- 每日/人工跑一次，采集一周：验收覆盖率、误拒绝率、漏放率、平均耗时；
- 误拒绝率 <5% 且漏放率可统计后，再讨论接入 merge 前置（需老田再批）；
- 首单验收对象：`K-QUANT-20261027-COMMANDHQ` 之后的 HEAD（黄忠入编批次本身不自我验收）。

## 四、KPI（数据来自验收单）

1. 验收覆盖率 = 有验收单的 merge 数 / 总 merge 数；
2. 漏放率 = PASS 后 7 天内事故数 / PASS 单数；
3. 拒绝准确率 = 复核确认有效的 REJECT / 总 REJECT；
4. 平均验收时长。

## 五、升级路径

观察模式（1 周）→ 接入 merge 前置（观察不阻断，1 周）→ 阻断模式（误杀<5%）→ 季度规则修订。
