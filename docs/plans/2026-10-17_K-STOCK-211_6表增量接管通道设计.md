## 背景

五单受控发布完成后，6 表（daily/adj_factor/daily_basic/margin_detail/index_daily/moneyflow）生产仓为静态全量（至 20261016，margin 至 20261015）。`tushare_sync.py` 夜更体系与 6 表零重叠（直写模式、无 staging/回执/锁，K-STOCK-211 受控发布体系即为替代它而生）。日常增量（新交易日）需一条自动化通道接管。

## 用户裁决（2026-10-17）

1. **通道形态 = 纯脚本全自动**：编排器 + Windows 计划任务每日 20:30 自跑，异常自动 held 次日重试（4dc69546 判例模式常态化），真无人值守。
2. **git 模式 = 自动提交 manifest**：发布成功后 `git add _manifest.json` + 内联身份提交（`laotian@local`，判例不改全局 config），单元明细见 `work/increment_guard_*.json` 可审可回溯。
3. 时点设计：每日 20:30 一任务全 6 表（tushare 盘后已齐 + 错开 KgDailySync 06:20 / TushareSync 23:30 配额）；margin_detail 源侧不齐自动 held 次日重试，无需单独 T+1 任务。

## 架构（三层，发布器协议零改动——增量只是新消费者）

```
Windows 计划任务 TushareIncrementGuard（每日 20:30）
  → increment_guard_run.cmd → increment_guard.py（编排器）
      1. capture   ：subprocess tail_fill_capture.py（缺口算法天然增量：
                     只拉 > 生产 max d_*.parquet 的开市日；脏行过滤/万行
                     翻页/幂等 skip 内建；与人工单共用 staging 协议）
      2. 质量门禁  ：新 receipt（capture 前后集合 diff）校验
                     row_count ≥ 表阈值 且 duplicate_keys == 0；
                     不合格自动移 held_tail_fill/<table>/（覆盖式留证）
      3. 发布      ：subprocess staging_materialize_full_history.py
                     --pattern "tail_fill/*"（幂等 skip + sha/行数双回读
                     + 发布锁与人工单互斥；增量只填空，绝不带
                     --allow-overwrite——覆盖类修复单永远走人工）
      4. manifest  ：仅 stats 全净（mismatch/missing/conflict_preserved=0
                     且 rc=0）时更新；rows 累加、file 指最新分片、note 追加
                     通道记录（滚动保留）；异常 → DEGRADED 留人工
      5. git       ：manifest 有 diff 才自动提交
      6. 报告      ：work/increment_guard_YYYYMMDDTHHMMSS.json
                     status ∈ OK / NO_GAP / HELD_ONLY / DEGRADED
```

行数阈值（近期完整日分位松下限，`MIN_ROWS` 可配）：
`daily 5000 / adj_factor 5000 / daily_basic 4400 / margin_detail 4000（完整 ~4455，一所 2001）/ index_daily 9000 / moneyflow 4500`

## 安全边界

- **无新开市日**（节假日）→ NO_GAP 直落报告，零发布零提交。
- **源侧滞后**（margin 两所 T+1）→ held，次日缺口重算自动重试，生产永不收残缺日。
- **capture 非零退出** → 已合格单元照发（缺口明日自愈），报告记 rc。
- **发布异常**（mismatch/missing/conflict）→ manifest/git 不动，DEGRADED 留人工。
- **与人工单互斥**：发布锁内建；held 目录协议与 4dc69546 类补发单共用。
- **registry 裁决不变**：`global_activation/production_write` 保持 false——本通道是"发布器通道（批准协议化+锁+quarantine）"的常态消费者，不经全局开关。
