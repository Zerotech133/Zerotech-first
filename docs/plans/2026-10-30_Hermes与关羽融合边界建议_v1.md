## 一、问题定义（先拆"融合"的三种含义）

| 解读 | 含义 | 是否可行 |
|---|---|---|
| A. **角色融合** | 让 Hermes 承担"关羽"的治理职责（门禁/审计/工单合并权） | ❌ 不建议 |
| B. **代码/仓库融合** | 把 `Hermes/` 并入自研主线、纳入门禁与指标 | ❌ 不建议（已有边界判例） |
| C. **能力级融合** | Hermes 作为门面/总控面，与军团/DSH 通过扩展面/HTTP/事件对接 | ✅ **建议**（分层推进） |

## 二、现状证据（为什么不应做 A/B）

1. **边界判例已定**（2026-10-28）：`Hermes/` 是**外部桥接/WebUI 子系统**（745 条 ruff 等），
   不参与自研健康度指标；修改需原 owner 同意；新代码禁止放进 `Hermes/`。
2. **K-ORG-112 三原则/双表面**：①**调度本体绝不进 Hermes**；②**写侧单源**（console 动作与飞书卡同源同落点，不产生第二本任务真相）；③门面可替换、执行面独立。
3. **今日二开评估结论**（军团线）：`Hermes 可以是可替换的门面，不能是不可回滚的底座`；
   - IDE 面板走官方 `/extensions/` 注入 → 合理继续；
   - 平台连接器直嵌 Hermes 核心 → 短期可接受、须下沉；
   - 核心补丁（`routes.py` 等）→ 不合理、停止扩大；
   - 生产基 `hermes-webui-next` **无 git**、双基并存（`hermes-webui` 为回滚资产）。
4. **已有能力级对接雏形**：`agent_platform/legion_command/hermes_orchestrator.py`
   已实现"Hermes 规划（/api/chat）→ OH 执行"的编排模式——这正是 C 类融合的正确形态，无需合并代码。
5. **角色维度**：关羽=治理席（确定性门禁、审计、证据链、只出报告/工单、L2 人签），
   把治理权放进 Hermes（UI/编排面）会引入**不可回滚的审计链断点**与"第二真相"风险，违反双表面原则。

## 三、建议：不动 A/B，做 C 的"三层融合"

### 第 1 层（推荐先做）：治理结果的**只读投影**到 Hermes 扩展面板

- 形态：在 `Hermes/extensions/` 下新增扩展（沿用 `legion-ide` 官方注入面，不覆盖核心 static）；
- 数据源（只读）：`agent_platform/data/reports/`（metadata_daily/dep_audit/ocr_gate_eval 等）、
  门禁摘要（fast 门/语法/导入/元数据/端口）、待批与回签清单（deliverables 文档索引）；
- 约束：**只读、不写、不产生任务真相**；断连时显式"红条"（fail-visible）；不改 Hermes 核心；
- 价值：老田在 Hermes 门面上一眼看到零界健康/治理积压，减少多入口切换。

### 第 2 层（已有雏形，继续收口）：**接口/事件转调**

- 保持 `hermes_orchestrator`（Hermes 规划 → OH 执行）为唯一编排通道；
- 事件回流通往 8091/8097 hub（R6 事件总线方向），**调度本体不进 Hermes**；
- 写侧单源：console 动作与飞书卡同源同落点（K-ORG-112 §3.2）。

### 第 3 层（明确不做）：**深度融合**

- Hermes 接管门禁/审计/任务真相、或把 `Hermes/` 并入主线门禁 → 违反边界判例 + K-ORG-112 红线 + 无 git 生产基不可回滚。

## 四、若推进第 1 层的最小落地单（L1，需老田/军团线确认）

| 项 | 内容 |
|---|---|
| 交付物 | `Hermes/extensions/legion-health/`（只读卡：门禁 5 项 + 数据日报 1 行 + 待批/回签计数） |
| 数据源 | 现有只读 JSON/MD（不新增写路径）；或复用 portal 已有 `/api/*` 只读接口 |
| 修改面 | 仅 `Hermes/extensions/`（官方注入面），**零核心补丁**；需 Hermes owner（军团线）同意 |
| 验收 | 只读展示与 CLI 结果一致；断连红条；不写任何状态；Hermes 回滚资产（`hermes-webui`）不受影响 |
| 风险 | 低（外部目录新增扩展，不入门禁指标）；回滚=删除扩展目录 |

## 五、需确认事项

1. 老田是否要"关羽治理面板"出现在 Hermes 门面（A 层第 1 层）？
2. 军团线（Hermes owner）是否同意在 `extensions/` 新增只读扩展（沿用 legion-ide 模式）？
3. 若要做，是否按"扩展只读 + 不写 + fail-visible"三约束立 L1 工单（我可起草五要素）。

## 六、一句话结论

> **Hermes 与关羽不"融合成一个系统"，而是"门面投影 + 接口转调"：Hermes 当可替换门面，关羽当确定性治理后端；不碰核心、不并代码、不接管真相。**
