## 一、背景与问题定义

2026-10-16 11:51:18，工单 K-STOCK-413（owner: Trae·Worker）执行中，agent 发现 Task Scheduler
引擎整机故障（SYSTEM 任务触发全静默，TraeDiag 实证；`Restart-Service` 被拒——受保护服务），
判定"只能重启根治"，直接调用 `shutdown.exe` 重启宿主机。当时机器上跑着：Ollama
（llama-server）、portal 8091/8080、约 60 个 schtasks 产线任务、Trae/VS 等可能带未保存工作的会话。

**问题不在"重启错了"——当时判断可能是对的——而在三个缺失：**

| 缺失 | 表现 | 后果 |
|---|---|---|
| 动作无门 | 宿主机级不可逆操作由 agent 单方面决定 | 人类对爆炸半径最大的动作零控制 |
| 动作无痕 | 调用点在 agent 会话，代码无落点 | 事后只能从 tasks.json note 考古还原 |
| 动作无级 | 宪法有"杀进程前辨认线上服务"红线，却没有"重启机器"条款 | 小动作有规，大动作放任 |

## 二、设计原则

1. **按动作分级，不按 agent 分级**。同一 agent 跑只读探针 vs 重启机器是两回事——门控挂在
   *动作*上，不挂在*身份*上。
2. **不可逆 + 高爆炸半径 = 永久人工确认**，不随 agent "用得顺了"降级。业界的原话：
   "Graduating those isn't maturity — it's how the expensive incidents happen."
3. **爆炸半径是风险单位**：能力强的 agent + 窄边界，比能力弱的 agent + 宽写权限更安全。
   零界实情 = 宿主机是生产机（量化产线 + 飞书触达 + 数据根都在本机），爆炸半径天然大。
4. **分级必须基础设施强制，不靠 agent 自觉**。零界落地四层：宪法红线 → 判例库 →
   评审门守卫（devtask.py）→ 事件层留痕（dev_events.jsonl）。
5. **防审批戏剧（approval theatre）**：审批必须带完整上下文，一次一议，禁止打包批准；
   批准率长期接近 100% = 门失效红旗，触发复查。
6. **out of the loop ≠ out of the log**：L0 自主动作也必须落事件层，可事后审计。

## 三、动作三级分类

| 级别 | 名称 | 判定条件 | 零界实景典型动作 | 控制模式 |
|---|---|---|---|---|
| **L0** | 自主 | 可逆；爆炸半径 ≤ 当前工作区 | 读文件/搜索/跑测试/写工作区与 worktree/git 本地提交/重启自己的开发服务/只读系统查询（Get-Process、netstat、事件日志查看） | 无门；事后审计（dev_events.jsonl 四事件） |
| **L1** | 升级 | 可逆但影响生产链路或跨会话共享状态 | 杀线上服务进程（portal 8091、Ollama、news_collector 等）/改常驻服务代码后杀旧换血/数据根结构性操作（循 §3 共享数据根互斥章）/删除文件（一律回收站）/git push/飞书生产推送/改工单状态机 | 先做后报：工单 note 记录动作+理由+结果，A0 日报可见 |
| **L2** | 人工确认 | **不可逆** 或 **爆炸半径 ≥ 宿主机/生产服务器** | **重启/关机/注销宿主机（shutdown / Restart-Computer / logoff）**/改系统级配置（系统代理、防火墙、服务启动类型、计划任务增删）/批量删除/对生产服务器 `10.205.0.118` 的任何变更/上线发布与对外发布/资金与交易通道操作/修改 AGENTS.md 与用户级铁律 | **blocking：取得人类明确批准后才可执行**；批准记录落工单 note（有 approvals.db 链路同步落库） |

**判定优先级：不可逆 > 爆炸半径 > 成本 > 是否受监管。命中 L2 任一条件即 L2。**

**禁止自我降级**：agent 不得以"紧急""根治需要""服务已计划内""Restart-Service 被拒所以只能重启"
为由把 L2 当 L1/L0 执行。K-STOCK-413 正是这条路径——当时正确的动作是**停下来问人**，
而不是继续往下走。拿不准级别时，按高级别办。

## 四、L2 审批协议（怎么问才算数）

### 4.1 agent 发起请求——五要素齐全，缺一即无效

| # | 要素 | 要求 |
|---|---|---|
| 1 | **命令全文** | 将逐字执行的命令/脚本路径；禁止"将要重启机器"式描述 |
| 2 | **影响面** | 哪些服务/进程/未保存工作会受损，附在线服务清单证据 |
| 3 | **不可逆点** | 明确什么做了回不来 |
| 4 | **替代方案与已尝试** | 为什么非做不可（如 K-STOCK-413 须附 Restart-Service 被拒证据） |
| 5 | **回滚/恢复预案** | 恢复路径、验证手段（哪个看门狗/哪条日志）、预计恢复时间 |

### 4.2 人类侧纪律

- 回复必须明确：**「批准」/「改 X 后批准」/「否决」**——**沉默 ≠ 同意**；
- **一次一议**，禁止"这批都批了"式打包批准；
- 批准记录（时间/命令全文/批准人）进工单 note；
- 对"改 X 后批准"类回复，agent 必须复述修改后的最终命令再执行。

## 六、复盘与登记

- 每次 L2 动作（无论批准与否）在工单 note 登记：时间/命令全文/批准人/结果/恢复验证；
- L1 动作进 A0 日报；
- 每月 monday_checkpoint 抽查审批记录；**批准率 >95% 且零否决** → 判定门失效，
  限期整改（降量/补上下文/换审批人）。
