## 1. AlertEvent v1 统一 Schema（13 字段）

| # | 字段 | 类型 | 必填 | 说明 | 示例（今日真实数据） |
|---|---|---|---|---|---|
| 1 | `alert_id` | string | ✅ | 全局唯一，`{source}-{yyyymmdd}-{序号或信号}` | `regime-20261016-risk_off` |
| 2 | `source` | enum：`regime_center` \| `board_issues` \| `engine_8001` | ✅ | 三源之一 | `regime_center` |
| 3 | `severity` | enum：`info` \| `warn` \| `critical` | ✅ | 三档，见 §2 默认映射 | `critical` |
| 4 | `scope` | enum：`market` \| `domain` \| `strategy` | ✅ | 市场级/工程级/策略级 | `market` |
| 5 | `title` | string(≤64) | ✅ | 一句话标题，上屏横幅直用 | `市场 regime=risk_off，禁止做多` |
| 6 | `body` | string(≤512) | ✅ | 明细正文，飞书卡片直用 | `策源快照 20261016 判定 risk_off，/api/regime 实测 200（10-19 07:09）` |
| 7 | `evidence` | object | ✅ | 可溯源证据，至少 1 个键；禁止无账本空口 | `{"regime":"risk_off","snapshot":"20261016","api":"/api/regime","checked_at":"2026-10-19T07:09+08:00"}` |
| 8 | `route` | enum：`banner_feishu` \| `board_red_morning` \| `engine_own` | ✅ | 路由目标，见 §2 | `banner_feishu` |
| 9 | `ack_required` | bool | ✅ | true=需人确认（待确认/自动决策回执）；false=留痕即可 | `false`（risk_off 属预授权，不等拍板） |
| 10 | `created_at` | ISO8601 | ✅ | 事件产生时间（非投递时间） | `2026-10-19T07:09:00+08:00` |
| 11 | `stale_after` | int(秒) | ✅ | 超过则消费端标黄「数据陈旧」（D5 口径） | `120`（大屏刷新周期同源） |
| 12 | `probe_ref` | string | ⬜ | 引用健康探针路径，缺源/离线时必填 | `8001 离线："/alerts/status"（60s 探针，提示 tools/alerts_shadow.py start）` |
| 13 | `dedup_key` | string | ✅ | 幂等键，同键不重复插台账/不重发 | `regime-riskoff-20261016` |

校验规则：`severity=critical` 时 `ack_required` 允许 false 但必须 `route` 有即时通道；`evidence` 为空对象即拒收（fail-visible，对齐四态原型「零写入 fail-visible」判例）。

## 2. 三源 → 路由映射表

| 源 | 层级 scope | 默认 severity | 路由 route | ack 语义 | 宁多勿漏→「待确认」判定条件 |
|---|---|---|---|---|---|
| ③ 策源 regime_center | market | risk_off/断链=`critical`；neutral 不产事件 | `banner_feishu`：大屏置顶横幅 + 飞书即时 | risk_off=**预授权**，`ack_required=false` 不等拍板，回执归「自动决策」 | 首次出现的风险信号、扩大覆盖面的新规则 → true，进待确认 |
| ② 板块 board_issues | domain | P0=`critical`；P1=`warn`；P2=`info` | `board_red_morning`：大屏板块内红标 + 晨会宣读，不打扰群 | 台账留痕即确认，`ack_required=false`；P0 需晨会宣读到 | P0 但来源非自动插单（人工登记未复核）→ true |
| ① 8001 engine_8001 | strategy | 告警=`warn`；熔断=`critical` | `engine_own`：8001 自有渠道（飞书订阅）分发；**大屏只显示引擎状态灯，预警本体不出 8001** | 8001 订阅人回执，大屏不承担 ack | —（8001 离线时只产一条状态灯事件，`severity=warn, probe_ref 必填`） |

今日判例对齐：issues 自动插 P0 已幂等（dedup_key，Demo `os_entry_v3_demo.html` 22/22 PASS）；RiskGuard R1-R4 账本 2322 拦截属②源 P1 级证据；8001 实测离线 → 状态灯灰、`probe_ref="/alerts/status"`，不假绿。

## 3. 四态映射与状态机（文字版）

四态对齐飞书通知指挥原型（W39-W41）：**自动决策 auto / 待确认 review / 不打扰 idle / 异常死信 blocked**。线上基线（10-19 05:2x 实测）：auto=3 / review=0 / blocked=84 / idle=67。

| 四态 | 进入条件（由 AlertEvent 判定） | 出口 |
|---|---|---|
| 自动决策 auto | `ack_required=false` 且 route 含即时通道且投递成功（evidence≥api_accepted） | 终态，留痕 |
| 待确认 review | `ack_required=true`；**宁多勿漏：判定不了的一律进此态** | 老田确认→转 auto 或搁置；超 deadline 旗标升级 |
| 不打扰 idle | 重复事件（dedup_key 命中）或闸门策略内抑制（channel=hub-gate 不冒充异常） | 终态，留痕 |
| 异常 blocked | 投递失败/身份不匹配→死信登记，补达不冒充原发送成功 | 补达成功→auto；人工介入→关闭 |

状态机转移（事件视角）：`产生 →(dedup 命中)→ idle`；`产生 →(ack_required=false 且投递成功)→ auto`；`产生 →(ack_required=true 或判定不了)→ review →(确认)→ auto`；`任意投递态 →(失败)→ blocked →(补达)→ auto/blocked 终态`。死信独立留痕（W41 判例：evidence 三级 api_accepted/receiver_verified/dead_letter）。

## 4. 实现落点建议

- **schema 定义文件**：`agent_platform/contracts/alerts.py`（新文件，落 contracts 与 `objects.py` 同族；agent_platform 已有 contracts 目录承载跨域对象，且三源里 8001/策源均非 portal 独有——portal 只是消费方，schema 放 portal 会造成消费方定义生产方契约的倒挂）。v1 先 dataclass/JSON Schema 双写，v2 直接升 alert bus 消息体。
- **生产方**：③策源 `regime_center`（/api/regime 快照引擎）；②工作台 issues 汇聚（自动插 P0 逻辑已在 Demo，幂等键=dedup_key）；①8001 状态探针（大屏侧 60s 探针 /alerts/status，只产状态灯事件）。
- **消费方**：os_entry 置顶横幅（只消费 `route=banner_feishu`）；通知指挥四态聚合（消费全量）；飞书 push_flow（消费即时通道，复用 send_msg_tracked 证据三级）。
- **对齐判例**：regime 预授权=risk_off 不等拍板（D2 已落地）；issues 自动插 P0 幂等（dedup_key）；大屏不保存第二本业务账，只消费不生产。

## 5. 验收标准与演进路径

验收（v1 纸面 schema）：
1. 三源各自能产出合法 AlertEvent（13 字段全、evidence 非空、dedup_key 稳定）；
2. 四态判定覆盖全部分支，无事件落入"四态皆非"；宁多勿漏歧义样本 100% 进 review；
3. 今日真实数据回放：risk_off 快照 20261016 → auto；2322 拦截 → board_red_morning 留痕；8001 离线 → 状态灯事件 probe_ref 必填；
4. 死信路径演练一次：投递失败 → blocked 登记 → 补达不冒充成功。

演进：**v1 纸面 schema（本档，供工位实现）→ v2 alert bus 落地**（portal 增统一收口 API，三源 POST AlertEvent，dedup/四态判定服务端化）**→ v3 死信补偿自动化**（blocked 定时补达 + receiver_verified 闭环 + 补达账独立审计）。
