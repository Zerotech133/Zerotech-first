## 一、独立性四原则（宪法条款）

1. **自持**：体系本体 = 一个目录树（registry/ + catalogs/ + dispatcher/），纯文件 + 纯 Python 标准库，零外部运行时依赖。不依赖菜鸟、不依赖 WorkBuddy、不依赖任何云服务——**拷走目录树即可在新机复活**（junction 判例配套）。
2. **契约通信**：agent 之间只通过两种东西协作——8093 工单（任务）+ jsonl 文件（事实/记忆）。不绑定任何厂商协议，任何 LLM/任何进程只要能读写这两样就是军团成员。
3. **单一权威**：数据在哪、接口在哪、谁会什么——各只有**一个**权威目录。目录之外的信息一律视为未登记（黑户告警）。
4. **人设可换、体系不换**：底层模型（qwen/GLM/Claude/未来任何模型）只是员工换届，目录/路由/账本/体检四件套永续。

## 二、核心问题与解法：AI 增长 × 有效管理

AI 从 29 → 100+ 的过程中，混乱来自三处：**任务找不到人（谁会做）、人找不到资源（数据/接口在哪）、账对不上号（谁干的）**。解法 = 三册一台：

```
┌──────────────────────────────────────────────────┐
│  任务台 dispatcher（唯一入口）                      │
│  收任务 → 拆解 → 查三册 → 生成执行计划 → 派单 → 追踪  │
└──────────┬──────────────┬──────────────┬─────────┘
           ▼              ▼              ▼
   📔 数据册          📕 接口册          📗 能力册
   data_catalog      service_catalog    org_registry v2
   (什么数据/在哪/    (什么服务/端口/    (哪个agent/
    怎么读/新鲜度)     怎么调/配方)       会什么/找谁)
           └──────────────┴──────────────┘
                          ▼
                  账本三件套（工单/观察/记忆）+ 体检黑户告警
```

**一个任务的完整旅程**（以今天真实的 600337 刻画为例）：
1. 任务进台：「刻画 600337」
2. 路由器查数据册 → K线=parquet[ashare/600337_SH]、席位=Neo4j[bolt:7687]、新闻=news.db、概念=KG
3. 路由器查能力册 → 五虎（辩方向）+ xsec_profile 工具（三线标准件）
4. 生成执行计划：xsec_profile(600337) → 五虎辩论 → D1 裁决 → 风控组
5. 派单（8093 工单，caller=dispatcher 归因）→ 追踪 → 账本留痕

**全程无需任何 agent "知道"数据在哪——它只需要会查册。新 AI 入职第一天即可干活，这就是规模化的解。**

## 三、三册 schema（v1 定稿）

### 数据册 `catalogs/data_catalog.yaml`

```yaml
- id: ashare_kline                    # 唯一标识
  kind: parquet                        # parquet|mysql|neo4j|sqlite|jsonl|api
  uri: quant_backtest/data/ashare/{code}_{mkt}.parquet   # 相对主仓根
  what: A股日K全量（OHLCV+涨跌幅，后复权）
  freshness: 每日 17:00（ts_daily 入库后）
  access: 产线311 + pandas.read_parquet
  owner: DATA1
  grants: [invest, trading, quality]   # 哪些部门可读
- id: kg_seats
  kind: neo4j
  uri: bolt://127.0.0.1:7687 （凭据 .env.local KG_*）
  what: 龙虎榜席位/游资/机构持仓/缠论形态（147万节点）
  query_recipe: "MATCH (seat:Seat)-[t:TRADED_ON]->(:Security {symbol:{code}})"
  ...
```

### 接口册 `catalogs/service_catalog.yaml`

```yaml
- id: queue_link_api
  endpoint: 127.0.0.1:8300
  what: OSINT 链接队列（入队/认领/流转）
  recipe: POST /tasks {url, source}   # 调用配方=照抄即用
  owner: ops_runtime
- id: lark_push
  endpoint: lark-cli（本地 exe）
  what: 飞书推送（卡片/文本）
  recipe: send_feishu.py <file>      # 产线封装
  ...
```

### 能力册（org_registry v2 增补）

入职简历的 `skills` 升级为**机器可匹配**的结构：

```yaml
capabilities:
  can_do: [xsec_profile, 六维评分解读, 席位分析]     # 能力标签（路由器匹配键）
  needs_data: [ashare_kline, kg_seats, news_db]     # 引用数据册 id
  needs_service: [lark_push]                         # 引用接口册 id
  produces: decision_json | report_md | trades       # 产出契约
```

**路由算法 v1（简单可解释，不搞 AI 黑盒）**：任务标签 ∩ can_do 得候选 → 按 needs_* 资源可用性过滤 → 按职级/负载排序 → 人审确认（E1 需 A0 附署）。匹配不唯一时升级田小皮仲裁——**路由器只做撮合，不做决策**。

## 四、dispatcher 任务台（8093 泛化，不新增进程）

复用 K-ORG-116 的 devtask 泛化：`devtask dispatch --plan <执行计划.json>`。执行计划 = 三册匹配产物（谁+什么数据+什么接口+什么顺序），人审后派发。**不新起服务、不加端口**——判例：调度本体在骨干。
