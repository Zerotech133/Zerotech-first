> 2026-10-28 · DSH-Lead 调研 · 范围：现有会议系统审计 + 社区/互联网模式研究 + 落地结合方案
> 结论先行：**现有会议能力已够用但被割裂、且没有任何五席指挥入口**；建议做「**一个入口、两种会场、三段闭环**」——会前异步议程（原议会厅）→ 会中五席作战室（现有 warroom 升级）→ 会后决议/派单/验收/归档闭环。

### 1.4 关键缺口（为什么"两套系统没结合"）

1. **没有五席入口**：作战室参会列表里 **没有 ZHAOYUN / GUANYU / HUANGZHONG**；R2 虽显示"赵云"但那是风控席，与治理席 ZHAOYUN 不是同一个体 → 五席实际无法整桌开会。
2. **会前会中割裂**：议会厅有议程/材料/留言，但无实时多智能体研讨；作战室能实时研讨，但没有议程、材料、预读、角色权限。
3. **纪要不结构化**：schema v1 只有 participants/minutes/orders；**没有决议、异议、责任人、截止时间、证据引用**；`source_verification=unverified`。
4. **订单不闭环**：`/api/dispatch` 只提交标题/类型，**没有 task_id 回链、没有验收挂接、没有会议→任务→验收→归档的追踪**。
5. **无会议纪律**：无发言顺序/时间盒/证据强制/跑偏检测；自由点选 3–6 席导致"谁在场谁说话"。
6. **无进化**：会议不产记忆、不产评测用例、不进 Phoenix trace、不做周复盘。

## 二、结合方案：一个入口，两种会场，三段闭环

### 2.1 总览

```
┌──────────────── 指挥部会议入口（/hq-meeting，8796 内）────────────────┐
│ 会前(异步)            会中(同步)                 会后(闭环)            │
│ 议会厅式议程     →    五席作战室(固定桌)      →   决议/派单/验收/归档    │
│ 议题/材料/预读       发言顺序+时间盒+证据         decisions→tasks→accept │
│ 参会确认/留言        诸葛亮质询轮/老田终裁        trace/记忆/判例/周复盘  │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 三种会议类型（先做 3 个模板）

| 类型 | 时长 | 主持 | 固定议程 | 产出 |
|---|---|---|---|---|
| **晨会（站会）** | 15min | 田丰 | ①昨日决议跟进 ②今日三优先 ③阻塞与风险 ④黄忠验收闸口 ⑤老田一句话 | 决议+今日派单 |
| **作战会** | 30–45min | 田丰 | ①诸葛亮"败因卡" ②各席证据陈述 ③黄忠验收判据 ④决议草案 ⑤老田终裁 | 决议+订单+任务 |
| **验收/复盘会** | 20–30min | 黄忠 | ①基线/红队证据 ②PASS/REJECT ③拒绝理由与回滚点 ④赵云归档判例 ⑤改进项 | 验收单+判例 |

### 2.3 五席角色协议（A 组 + 老田）

| 席位 | 会议职责 | 发言权 | 决定权 | 强制证据 | 时间盒 |
|---|---|---|---|---|---|
| **田丰 A0** | 主持/议程/决议草案/**派单** | 开场、收口、点名 | 草案与优先级（L1） | 任务账本/排期 | 3min |
| **诸葛亮 AI1** | **质询/反方/败因卡**、会前研判 | 质询轮（可打断一次） | 无（只有否决建议权） | 红队/推演/引用 | 5min |
| **关羽 GUANYU** | 执行/修复状态、阻塞项、工时 | 证据陈述 | 无（工程建议） | 工单/commit/tests | 4min |
| **黄忠 HUANGZHONG** | **验收判据/通过否/拒绝理由** | 验收轮 | **REJECT 权**（观察期不阻断 merge） | 基线/红队/验收单 | 4min |
| **赵云 ZHAOYUN** | 记录/决议追踪/治理合规/记忆归档 | 记录与提醒 | 合规否决（治理） | 审计/trace/审批留痕 | 2min |
| **老田** | 列席/终裁/签批 | 终裁 | **最终决定（L2 必须人工）** | — | 3min |

**决策规则**：每席对决议草案表态 `支持/反对/保留`；反对与保留**必须写入纪要**（异议记录）；田丰收口；老田终裁。**L2 事项（宿主机/发布/计划任务/凭据）不得在会议内"投票通过"，必须走五要素审批**。

### 2.4 三段闭环的技术落点（复用现有，最小改造）

| 段 | 复用 | 新增（最小） |
|---|---|---|
| **会前** | 议会厅 `council_ops.py` 的议题/留言/材料/上传（或收编进 8796） | 议程 JSON：议题/时长/材料链接/参会确认/预读 |
| **会中** | `meeting.html` + `/api/chat`（每席模型）+ 现有分组与实时消息 | 五席预设 `command_hq` + 固定桌 + 模板按钮 + 发言顺序/时间盒 + 证据引用字段 |
| **会后** | `/api/meeting/minutes` 存档 + `/api/dispatch` 派单 + `inbox_gateway` | schema v2（decisions/orders/acceptance/trace）+ task_id 回写 + 黄忠验收挂接 + 次日晨会跟进 |

## 三、社区与互联网研究对照

| 来源 | 关键模式 | 对本方案的映射 |
|---|---|---|
| [Anthropic · Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 区分 **workflow** 与 **agent**；orchestrator-workers；evaluator-optimizer；"先简单、按需加复杂度" | 会议用**固定工作流**（模板/顺序/时间盒），不要做成全自治圆桌；五席=workers，黄忠=**evaluator**，田丰=orchestrator |
| [Microsoft · Magentic orchestration](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)（Magentic-One） | 经理维护 **task ledger + progress ledger**；动态选下一个发言者；**stall detection 自动重规划**；**human-in-the-loop plan review** | 田丰=manager；议程=task ledger；会议进度/跑偏=progress ledger；跑偏告警=stall detection；**老田批准议程**=plan review |
| [Du et al. · Multiagent Debate (arXiv 2305.14325)](https://arxiv.org/abs/2305.14325) | 多实例"提出-反驳-收敛"多轮辩论，提升事实性与推理 | 诸葛亮**质询轮** + 异议记录；但设"最多 1 轮反驳"控制时延/成本 |
| [CrewAI · Hierarchical Process](https://docs.crewai.com/en/learn/hierarchical-process) | manager agent 分配任务、校验产出 | 田丰=manager、五席=specialists；禁止经理"代写" specialist 意见 |
| [AutoGen · Selector Group Chat](https://microsoft.github.io/autogen/0.4.8/reference/python/autogen_agentchat.teams.html) | speaker selection + termination condition | 发言选择器：固定顺序为主 + 主持人动态点名；终止条件=议程走完/时间盒到/决议形成 |
| [n8n · Meeting decisions/tasks extraction](https://n8n.io/workflows/15896-extract-meeting-decisions-and-tasks-with-outlook-gpt-4o-sharepoint-and-to-do/) | 会议纪要 → 结构化 **Strategic_Decisions + Action_Items** → 写任务系统（含期限/负责人） | 会后自动抽取决议/任务，写 `decisions` + `orders`（我们已有 `inbox_gateway`，复用即可） |
| [LangGraph Supervisor](https://pypi.org/project/langgraph-supervisor/) | supervisor 协调多 agent/团队，分层可嵌套 | 指挥部=顶层 supervisor 层；日常研发军团=下层团队，会议不越级派单 |

**研究结论**：
1. 业界成熟做法不是"一屋子 agent 自由聊"，而是 **经理+台账+固定流程+人工关键审批**；
2. 会议价值在**会前材料、会中异议、会后任务闭环**，不在"多聊几轮"；
3. 我们的差距主要在**模板/结构化决议/任务回链/验收挂接**，而这些都能在现有 8796 上增量实现，不必新建平台。

## 四、落地路线图

### P0（本周，不新建服务，纯增量）
1. `meeting.html` 增加「**指挥部会议**」预设：五席固定上桌 + 3 个模板（晨会/作战会/验收会）+ 议程条 + 决议面板；
2. `serve.py` 增加 `/api/hq/meeting/*`（create/agenda/decision/close），纪要落 `agent_platform/data/meetings/hq/`（schema v2）；
3. 复用 `/api/dispatch`：订单派发后把 `task_id` 写回纪要；
4. 用一次**真实晨会**跑通：五席各 1 条有证据发言 → 1 条决议 → 1 张任务单 → 次日跟进。

### P1（2 周）
5. 会前异步：议会厅**收编**进 8796（`/api/hq/agenda` + 材料上传），8798 转只读归档或下线；
6. 黄忠验收会：会议材料自动带 `test_baseline` + `huangzhong_accept` 证据；REJECT 记录进判例；
7. Phoenix trace：meeting_id 作 span；`source_verification` 从 unverified → server；
8. dev_events 回流：merge/guard_fail 自动进下次晨会议程。

### P2（4–6 周，进化）
9. progress ledger/跑偏检测（超时、议程未走完、发言无证据、重复议题）；
10. 会议回放与决议回看（会后 7 天自动核对决议完成率）；
11. 记忆/评测飞轮：决议→判例、事故复盘→红队用例；
12. 会议成本与时延看板。

## 六、风险与红线

1. **会议表演化**：无证据发言=禁止进入决议；speaker 发言须带 `evidence` 字段；
2. **审批绕过**：L2（宿主机/发布/任务/凭据）**不得**会议投票通过，必须五要素+老田签批；
3. **角色越权**：黄忠只验不改；诸葛亮只质询不裁决；关羽只执行不自验；
4. **成本失控**：逐席实时模型调用有并发闸；会议模板限制席位数与轮次；
5. **数据割裂**：P0 就定 schema v2，否则又会造第三套纪要格式。
