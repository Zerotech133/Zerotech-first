## 三、偏差链路（逐层闭环）

1. **写入口径（主因，ACAD1 owner）**：`pool_date` 字段被当作「该市场候选池日」使用；一次 ACAD1 同步（目标 30）实际写入 30 行，但 CN 写 11-03、HK 写 10-30、US 写 10-29、CRYPTO 写 10-31。日志 selected=30/synced=30 与库内 latest-per-market 30 完全对上。
2. **读口径（次因/放大，API owner）**：`/api/acad1/pool` 的 PG 读取为单日读取——`portal/api_acad1_pool.py` L65 `_PG_SQL` + L188/L192 `WHERE pool_date = (SELECT max(pool_date) FROM ...)`。因 11-03 只有 CN，故返回 12；`pool_id=ACAD1-POOL-PG-20261103`、`pool_date=2026-11-03` 均为单日口径。**这不是过滤 bug，而是读口径与写入口径不一致。**
3. **历史 11/02 的 30→12（外部更新，非丢失）**：
   - 11/02 曾以**单一 pool_date=11-02** 写 30：日志 L1105/L1106（旧格式 `{"pool_date":"2026-11-02","selected":30}`、`pool_date=2026-11-02 synced=30`）；另 task-27 交接实测（2026-11-03 07:40 CST）PG 11/02=30（CN12/HK10/US6/CRYPTO2）；ADR-018（11-02）记 PG 101 行/最新 10-31 30 只；IFS v1 标准（11-03）记 PG 30 只 vs JSON 36。
   - 11/03 起日志改为 per-market `pool_dates` 口径（L1168/L1272），11/02 的 CN 行被 upsert（保留旧 selected_at 的 11 行 + 新增 1 行 chanlun id=1024，selected_at=11-03T02:41:00Z），非 CN 的 18 行从 11/02 消失；当前 11/02 仅 CN12。全表从 ADR 记录的 101 行降到 73 行，说明有外部清理/重写。
   - 旧版脚本实现**无法从 git 复原**（zhice 仓仅 `f8bfac9` 一次批量入库，scripts mtime 11/03 14:26），故对「11/02 具体是哪一条 DELETE 清掉统一日 18 行」**不下猜测结论**；需 ACAD1 用 `C:\Temp\zhice_daily_task.log` 历史与任务历史复现确认（列为待办）。
4. **已排除**：① review 过滤——review 是池级 1 行（topic 明确「ACAD1日复核30」、verdict 观察），不做 per-code 过滤；② 另一张表/未投影 30 版本——探针全部 `v2_*` 含 pool_date 表，无 11-03 30 行版本；③ 分批发布事务中断——最新 run rc=0、19 步全 success、sync 在 20:51:29 一次完成，selected=30；问题不在丢了 18 行，而在 18 行的 `pool_date` 不是 11-03。

4. API 字段语义风险：`pool_id/pool_date/data_date/published_at` 目前全部是单日口径；即使临时按 market-latest 聚合，也需明确 `pool_date` 取哪个日期，否则 id 语义不稳定。
