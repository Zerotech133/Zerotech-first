# 多 Agent 协作开发：方案选型与落地施工图（K-STOCK-104）
> STATUS: done（完工归档；据 INDEX_计划全集索引 2026-10-12 口径；2026-10-31 W2 校核）



> 2026-10-11 · 老田问：平台能否管理多个 Agent ID（谁在干什么/多项目进展），
> 还是在软件开发项目上直接实现多 Agent 协作编码？哪个方案最好？
> 方法：全网/开源社区实调研（2026-10 现状）× 自有家底盘点

## 一、调研结论（2026-10 开源社区现状）

**框架类（自己搭编排）**：
| 框架 | 星数 | 判断 |
|---|---|---|
| CrewAI | 52k | 上手最快，但流程控制/状态持久化天花板低 |
| LangGraph | 24k+ | 生产级状态图+checkpoint，学习曲线陡 |
| MetaGPT | 46k+ | 专做「软件公司模拟」，出了软件场景几乎没用 |
| AutoGen | 40k+ | **维护模式**（微软转向 Agent Framework），新项目不选 |
| OpenHands | 55k+ | 完整 AI 工程师产品，Docker 沙箱 DevOps 重 |

**执行器类（终端 agent）**：Claude Code（子代理/agent teams 内建）、Codex、Aider；**Claude Squad**（8.5k 星，tmux+git worktree 并行编排+diff 审查）——**硬依赖 tmux，无 Windows 原生**。

**业界共识四条**（多份 2026 报告一致）：
1. 最稳协作模式=**一个 orchestrator 分派 + 窄 worker 各管一件 + 独立上下文 + 独立评审门**；
2. 多 Agent 成本 3-10 倍，**不要为多而多**，先 1 编排+2 worker 起步；
3. 隔离靠 **git worktree**（每 agent 独立分支工作树）是事实标准；
4. 2026 竞争点=工程化（可靠性/可恢复/审计），不是模型。

## 二、关键判断：我们不需要引框架

**家底盘点**——agent_platform 已有等价物：
| 业界框架提供 | 我们已有 |
|---|---|
| 角色注册（CrewAI Agent） | org.json 五部门+岗位 |
| 任务分派/状态（LangGraph state） | **tasks 七态工单**（已影子验证） |
| checkpoint 恢复（LangGraph） | checkpoints.db + replay |
| 审计（LangSmith） | events 统一 trace 表 + A0 日报 |
| orchestrator | A0 总管（K-STOCK-102 已定案） |

引 CrewAI/LangGraph=把已有的东西用别人的抽象重写一遍，成本>收益。**真正缺的只有两件**：①执行隔离（worktree）②「谁在干什么」的可视看板。

## 三、拍板推荐：方案丙「组织层自有 + worktree 隔离 + 终端 agent 执行」

```
菜鸟/A0（orchestrator，已有）
   │ 建任务单（tasks 七态）
   ▼
开发部看板（新增，/dev 域）──────── 谁·干什么·分支·进度 一屏尽览
   │ 每单派一个 worker
   ▼
git worktree 隔离（Windows 原生支持，弃 tmux 类工具）
   worktree/.task-T017/ → 分支 task/T017-xxx
   │ 执行器=WorkBuddy Agent 会话 / Claude Code（任选，可混配）
   ▼
评审门（已有！）：_mixin_integrity + check_ports + unify_nav + 自有测试
   │ 过门
   ▼
合并回 master → 任务单 done → A0 日报汇总
```

**为什么不选其它**：Claude Squad（tmux 硬依赖，Windows 无缘）；OpenHands（Docker 沙箱 DevOps 重，单人站养不起）；框架类（见第二节）。

## 四、落地施工图（三步，批 0 后启动）

1. **worktree 助手**（tools/devtask.py，0.5 天）：`new T017`（建 worktree+分支+登记任务单）/`list`（各任务分支 ahead/behind+最近提交）/`merge T017`（过评审门后合并+清 worktree）——Windows 原生 git 全覆盖；
2. **开发部看板**（/dev 域新页，1 天）：数据源=tasks db + `git worktree list` + 分支 tip——每行：工单号·负责人 Agent·分支·状态灯·最近提交时间；复用 nav.js/短屏化（103 准入三件套）；
3. **首战试点**（批 0 后还债道挑 3 单）：P4 批 1（data_sync）+ TushareSync 补任务 + 死角页 canvas v1 退役——1 编排（菜鸟）+2-3 worker，验证全链后再扩编。

**纪律**（照业界共识）：worker 窄职责一单一事；评审门不过不合并；任务单先行（无单不写码）；每 worker 独立上下文不共享会话。

## 五、执行器选型备注

- **WorkBuddy Agent**：已在本机、有任务清单/子代理体系，默认首选；
- **Claude Code**：理解力强、子代理内建，适合啃硬骨头（P4 批 3 巨石手术可点将）；
- 二者可混配：同一 worktree 谁顺手谁上，看板只认工单不认执行器。
