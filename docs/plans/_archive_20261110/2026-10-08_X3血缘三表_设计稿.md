## 0. 一句话方案

临界 PG 建 `lineage` schema 三张表：`job_run`（作业运行）、`lineage_edge`（输入→输出表级血缘边）、`schema_version`（表结构版本）；埋点以一个 ~80 行的 `linreg.py` 助手模块实现，在 `start_kg_sync.ps1` 所辖各入图脚本的 main/build 函数入口出口各插 2-3 行；不引 OpenLineage。

## 1. 范围界定：血缘 ≠ 证据链

| | kg_trace（已有） | X3 lineage（本稿） |
|---|---|---|
| 回答 | "这个结论的证据链/传导树是什么"（个股×事件×语义） | "这张表是谁算出来的 / 这张表挂了影响谁"（管道拓扑） |
| 载体 | Neo4j 图（Event→DRIVE→MarketEvent…） | PG 关系表（job/表/边） |
| 粒度 | 个股×日期×假设 | 作业运行 × 逻辑表 |

两者互补不重叠。图上的边有 source 属性（kg_schema.py:161 EDGE_PROPS），但那是"数据来源标签"，不是可递归的管道拓扑——X3 补的就是这个。

**逻辑表命名约定**（lineage_edge 里的表名统一用 URN 式字符串，让 parquet/Neo4j/PG/文件四种存储同构登记）：

| 前缀 | 例 | 实证出处 |
|---|---|---|
| `parquet:` | `parquet:tdx/ts_top_inst`、`parquet:youzi_registry` | kg_build_cl1.py:44-45,103（data/tdx/ts_top_inst、youzi_registry.parquet） |
| `jsonl:` | `jsonl:chanlun_pool` | kg_build_cl1.py:44 |
| `neo4j:` | `neo4j:TRADED_ON`、`neo4j:Security`、`neo4j:MarketEvent` | kg_schema.py REL_/LBL_ 常量 |
| `pg:` | `pg:v2_bar_daily` | data_loader.py:2（zhice-db v2_bar_daily） |
| `file:` | `file:kg_communities.json`、`file:catalog` | 聚合快照落盘件 |

Neo4j 的标签/关系类型视为"逻辑表"——TRADED_ON 就是一张按日重建的表，这样图边也能进同一张 lineage_edge。

## 2. PG 三表 DDL（schema: lineage）

> 落在临界 PG（127.0.0.1:5442）。PG 语法，已自检（text[]、GIN、部分索引均合法，事务内 BEGIN…ROLLBACK 全量通过；容器实测 `POSTGRES_USER=quant_user`、`POSTGRES_DB=quant_system`）。

```sql
-- ============================================================
-- X3 管道级血缘三表（临界 PG newquantsystem_v2 / schema lineage）
-- ============================================================
CREATE SCHEMA IF NOT EXISTS lineage;

-- ── ① 作业运行记录 ──────────────────────────────────────────
CREATE TABLE IF NOT EXISTS lineage.job_run (
    id              bigserial PRIMARY KEY,
    job             text        NOT NULL,   -- 'kg_daily_sync' | 'tdx_sync' | 'tushare_sync'
                                            -- | 'xmap_sync'（X2 §4 也登记进来）
    step            text        NOT NULL,   -- 'cl1_sync' | 'seat_winrate' …
                                            --   与 start_kg_sync.ps1 的 step.name 一一对应
    started_at      timestamptz NOT NULL,
    ended_at        timestamptz NULL,       -- NULL = 运行中/被杀
    status          text        NOT NULL DEFAULT 'running',
                    -- 'running' | 'ok' | 'fail' | 'skipped' | 'partial'
    rows_written    bigint      NULL,       -- 入图节点+边总数（脚本自报，可空）
    git_sha         text        NULL,       -- quant_backtest 目录 git rev-parse --short HEAD
    host            text        NOT NULL DEFAULT (inet_server_addr())::text,
    detail          jsonb       NULL        -- 每步自由备注（如跳过原因、watermark）
);
CREATE INDEX IF NOT EXISTS idx_jobrun_job
    ON lineage.job_run (job, step, started_at DESC);

-- ── ② 血缘边：输入 → 输出（表级，字段级可选）────────────────
CREATE TABLE IF NOT EXISTS lineage.lineage_edge (
    id              bigserial PRIMARY KEY,
    job_run_id      bigint      NOT NULL REFERENCES lineage.job_run(id) ON DELETE CASCADE,
    output_table    text        NOT NULL,   -- URN，见 §1 命名约定
    input_table     text        NOT NULL,
    output_cols     text[]      NULL,       -- 字段级可选：本次写入了哪些列/属性
    input_cols      text[]      NULL,       -- 本次读了哪些列
    transform       text        NULL,       -- 'regex_match' | 'dtw' | 'llm_judge' | 'agg' …
    created_at      timestamptz NOT NULL DEFAULT now()
);
-- 下游影响面查询：按输出表找边
CREATE INDEX IF NOT EXISTS idx_lineage_out
    ON lineage.lineage_edge (output_table, job_run_id DESC);
-- 上游溯源查询：按输入表找边
CREATE INDEX IF NOT EXISTS idx_lineage_in
    ON lineage.lineage_edge (input_table, job_run_id DESC);
-- 字段级查询（可选字段用）
CREATE INDEX IF NOT EXISTS idx_lineage_outcols
    ON lineage.lineage_edge USING gin (output_cols);
CREATE INDEX IF NOT EXISTS idx_lineage_incols
    ON lineage.lineage_edge USING gin (input_cols);

-- ── ③ 表结构版本 ────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS lineage.schema_version (
    id              bigserial PRIMARY KEY,
    table_name      text        NOT NULL,   -- 同 §1 URN
    version         int         NOT NULL,
    ddl_hash        text        NOT NULL,   -- 列清单+类型的 sha1，变了才出新版本
    columns         jsonb       NOT NULL,   -- [{name,type,comment}…]
    detected_at     timestamptz NOT NULL DEFAULT now(),
    detected_by     text        NOT NULL DEFAULT 'linreg'
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_schema_ver
    ON lineage.schema_version (table_name, version);
```

要点：
- `job_run.step` 与 start_kg_sync.ps1:35-54 的 `$step.name` **逐字对齐**（cl1_sync/m2_drive_sync/bclass_sync…），血缘可直接与 `C:\Temp\kg_sync_task.log` 的 exit 码互查。
- `lineage_edge.job_run_id ON DELETE CASCADE`：删旧运行记录时边随之清理，表不膨胀。
- 边是"每次运行都追加"的事实流；查"当前管道拓扑"用最新一次 ok 运行的边即可（§4 示例）。

## 4. 示例查询（验收口径）

```sql
-- Q1 这张表的下游影响面：ts_top_inst 挂了影响谁？（递归两层）
WITH RECURSIVE down AS (
    SELECT DISTINCT output_table FROM lineage.lineage_edge
    WHERE input_table = 'parquet:tdx/ts_top_inst'
  UNION
    SELECT e.output_table FROM lineage.lineage_edge e
    JOIN down d ON e.input_table = d.output_table
)
SELECT * FROM down;   -- → neo4j:TRADED_ON → seat_winrate 的 win_rate → kg_features/sector_flow

-- Q2 这个数是谁算出来的：neo4j:SIMILAR_K 上游溯源
SELECT j.job, j.step, j.started_at, j.status, e.input_table, e.transform
FROM lineage.lineage_edge e
JOIN lineage.job_run j ON j.id = e.job_run_id
WHERE e.output_table = 'neo4j:SIMILAR_K'
ORDER BY j.started_at DESC LIMIT 3;
-- → kg_daily_sync / sim_k / 输入 parquet:tdx/ts_daily / transform=dtw

-- Q3 昨晚链路哪步断了（对齐 kg_sync_task.log）
SELECT step, status, ended_at - started_at AS dur, detail
FROM lineage.job_run
WHERE job = 'kg_daily_sync' AND started_at::date = current_date - 1
ORDER BY started_at;

-- Q4 当前管道拓扑（最新一次全 ok 的运行链）
SELECT DISTINCT ON (e.output_table, e.input_table)
       e.output_table, e.input_table, j.step
FROM lineage.lineage_edge e
JOIN lineage.job_run j ON j.id = e.job_run_id AND j.status = 'ok'
WHERE j.started_at > now() - interval '7 days'
ORDER BY e.output_table, e.input_table, j.started_at DESC;
```

## 5. 写入开销评估

- 规模：KgDailySync 20 步 + 2 个前置同步 + xmap_sync ≈ **23 job_run/日**；每步 1-6 条 edge ≈ **60-100 行 lineage_edge/日**，schema_version 仅在列变更时出新增（月级几行）。
- 单步成本：3-5 次单行 INSERT + 1 次 UPDATE，psycopg2 本机往返 <5ms/条，对比各步动辄数分钟的入图/DTW 计算，占比 <0.01%——**可忽略**。
- 增长：约 4 万行/年，含索引年增 <20MB，无需分区；保留策略建议 400 天（`DELETE FROM lineage.job_run WHERE started_at < now()-interval '400 days'`，CASCADE 自动清边），施工时挂进 KgDailySync 第 19 步 graph_check 前。
- 可靠性：linreg best-effort 不阻断（§3.1）；登记表自身损坏不影响任何产线数据。

## 6. 不引入 OpenLineage 的理由声明

1. **规模错配**：OpenLineage 的价值在多团队、多运行时（Spark/Airflow/Flink/Kafka 流式）环境下的事件标准化与 Marquez/数据目录生态。本管线是单机、20 个 Python 脚本、每日一跑的批处理链，引入它需要常驻 Marquez 服务 + HTTP 事件上报 + 客户端 SDK，为一个 4 万行/年的需求建一整套基础设施。
2. **模型错配**：OpenLineage 的 RunEvent/Facet 模型面向"作业动态上报 + 消费者订阅"；本需求的消费方就是人（勘查缺口 #1 的两个问句），三张静态表 + 递归 SQL 已 100% 覆盖，§4 四个验收查询全部原生 PG 可答。
3. **运维纪律**：本工作站铁律是"轻件、可自检、失败不阻断"（kg_client 懒加载、notice_llm 跳过降级同款）。linreg.py 80 行、零外部依赖、best-effort——OpenLineage SDK 多一个 pip 依赖链和一个网络故障面。
4. **留了后路**：URN 命名（§1）与 job/step 二级命名与 OpenLineage 的 job namespace/name 概念同构，未来若真要接，写一个 50 行的 exporter 把三表翻译成 RunEvent 即可，今天不预付这笔复杂度。
