# 部门内多项目/子项目承载设计 —— 工作区 × 项目线 × 身份 三维键位
> STATUS: declared



- **编号**：K-ORG-057（设计稿，待老田拍板后实施）
- **时间**：2026-10-14 07:12
- **起因**：老田问——研发部一个部门内会出现多个开发项目、多个子项目，怎么承载、怎么不混乱
- **现状**：IDE 工作区 = 部门（动态，来自 bundle.departments）；工单账本 devtask 有 owner **无 project** 字段；会话/轨迹已带 k_id（K-STOCK/K-ORG/K-PUSH… 前缀即天然项目线判别器）

## 一、核心决策：项目线是工作区内的二级维度，不另开工作区

- 工作区 = 部门：**稳定维度**，按部门数增长（当前 12，扩到 8 个项目部量级）
- 项目线 = 子项目：**易变维度**，随立项/结项增减（N 个），只作为工单/会话/记忆的**标签过滤**，不产生新工作区
- 若把项目做成工作区：8 部门 × N 项目的工作区矩阵必然爆炸，且部门上下文（共享文件树、共同人设、部内协作）被割裂——这是"混乱"的根源，设计上直接排除

**三维键位**：`ws（部门）× project（项目线）× me（身份）`——任一会话、工单、提交都能三键定位，三问必答：哪个部门、哪条项目线、谁干的。

## 二、项目线的天然判别器：k_id 前缀

K 编号按模块加前缀的机制（K-STOCK / K-ORG / K-PUSH / K-BK / K-GIT / K-N1）**就是项目线**：
- 一条项目线注册时绑定一个 k 前缀（如"量化双刀"→K-STOCK）
- 会话、工单、提交、审计、SEC2 走查全部按 k_id 归线，**零额外标注成本**
- SEC2 走形检查自动对照该线的研发方案（--plan 已按线组织）

## 三、数据模型

新增 `agent_platform/registry/projects.json`：

```json
{"projects": [
  {"project_id": "quant", "dept": "dev", "name": "量化双刀",
   "k_prefix": "K-STOCK", "members": ["DEV1", "DEV5"], "status": "active"},
  {"project_id": "watchbot", "dept": "dev", "name": "盯盘机器人",
   "k_prefix": "K-PUSH", "members": ["DEV2"], "status": "active"}
]}
```

- devtask 工单 schema +`project` 字段（缺省=部门 id）；dispatch 派单带上
- 组织图（org.html）部门卡加「+ 子项目」表单 → 落 projects.json → 重烘 bundle → IDE 自动出现（与部门注册同构，零改码）

## 四、IDE 呈现（portal/ide.html，一期最小改）

- 工作区内顶栏（部门按钮行下方）加**项目线 chips**：`全部 | 量化双刀 | 盯盘机器人 | …`（来自 bundle.projects，按当前工作区过滤 dept）
- 点芯片 = 过滤：会话列表（按 k_id 前缀）、工单看板（project+owner 双过滤）、记忆面板
- **文件树不切项目**：同一 monorepo 一棵树（仓库本来就是一个）
- 持久化键：`ide-proj@<ws>`，与既有键位规划同款

## 五、防混乱判据（写进验收）

1. 三问必答：任意产物可答 ws/project/me 三键（审计脚本可机检）
2. 项目线生命周期：立项=组织图注册；结项=status=archived（chips 置灰不删，历史可溯）
3. 跨线工单必须显式声明 project（dispatch 不带 = 拒收，产线校验）
4. 晨会三件套按项目线分组输出工单状态

## 六、实施分期（拍板后）

- **一期（半天）**：projects.json 注册表 + 种子数据（量化双刀/盯盘/门户三线）+ devtask project 字段 + dispatch 带线 + IDE 项目线 chips（会话/工单过滤）
- **二期（半天）**：org.html「+子项目」表单 + 记忆面板过滤 + 结项置灰 + 晨会三件套按线分组
- **验收**：8 部门任一部门挂 ≥3 项目线演示不混乱；三问必答机检脚本过
