## 1. 问题定位（失真三处）

| 位置 | 现状 | 失真机理 |
|---|---|---|
| `chat_auto` (L332) | 降级链逐级 try/except，只 return str | 实际生成通道信息在降级瞬间丢弃 |
| `run()` (L348 trace_log) | `"via %s" % backend()` | backend()=请求档；降级后轨迹仍记请求档 |
| `commit_work` (L489) | `msg = "... via %s" % channel`（调用方传参） | channel=调用方认知的请求档 |

## 2. 方案比选

| 方案 | 形态 | 评估 |
|---|---|---|
| A. 模块级 `_LAST_META` + `last_channel()` | 零签名改动 | ✅ 最小；⚠️ 并发下不可靠（产线单进程单线程，可接受但治标） |
| **B. ChatResult 结构化（推荐）** | 内部 `_chat_auto_impl()→ChatResult`，公开 `chat_auto()` 变薄壳 return `.content` | ✅ 零调用方破坏 + 元数据完整可取；ChatResult 可带 attempts/latency 观测面 |
| C. 直接改 chat_auto 返回类型 | 破坏性 | ❌ 所有调用方（run/qa1_review/驱动脚本）连锁改，风险大 |

**拍板：方案 B。** 公开签名与返回类型完全不变，新增并行入口 `chat_auto_meta()`。

## 4. 接线点（三处失真全治）

1. **`run()`**：改调 `chat_auto_meta()`；trace_log generate 行与返回 `detail` 尾部追加实际通道（如 `via anthropic(requested=gpt6)`）；attempt 降级 print 保持。
2. **`commit_work`**：`channel` 参数语义升级——`None` 或 `"auto"` → 取同进程最近一次 `ChatResult.channel`（`_LAST_META` 兜底，方案 A 机制复用）；显式传值仍可覆盖（旧驱动脚本零破坏）。
3. **`qa1_review.py`**：复核通道标签取 `backend()` 的地方不动（QA1 是显式定档调用，无降级歧义）——不改，留观察。
