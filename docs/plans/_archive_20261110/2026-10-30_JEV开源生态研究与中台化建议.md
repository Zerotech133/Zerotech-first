# JEV 开源生态研究与中台化建议（2026-10-30）
> STATUS: done（研究结论已交付；K-ORG-20261030-JEVMIDPLAT done）



> 工单：K-ORG-20261030-JEVMIDPLAT ｜ 方法：开源社区/论文检索（FinGPT、FinBen/PIXIU、TradingAgents、OpenBB、结构化金融信息抽取论文、中文 FinBERT、数据中台方法论）+ 项目内契约/消费者盘点。
> 结论先行：**JEV 值得走"判定能力中台（Judgment-as-a-Service）"路线，但应是轻中台：以 API/MCP/事件流/数据集四种形态输出，核心资产是"事件 schema + 校准可信层 + 评测治理"，而不是组织级重中台。**

## 一、研究问题

1. JEV 这类"新闻 → 结构化判定"能力，开源社区已经做到什么程度？我们能借鉴什么、不必重造什么？
2. JEV 对平台还能提供什么价值（当前只服务告警门/简报/角色日报/校准）？
3. 是否应把 JEV 从"一个板块/一组脚本"升级为"中台"？形态、边界、路线怎么定？

## 二、开源生态扫描（与 JEV 直接相关的 8 类资产）

| 方向 | 代表项目/论文 | 关键做法 | 对 JEV 的启示 | 是否复用 |
|---|---|---|---|---|
| 金融 LLM 数据管道 | **FinGPT**（[repo](https://github.com/AI4Finance-Foundation/FinGPT) / [arXiv](https://arxiv.org/abs/2306.06031)） | 数据驱动：自动数据清洗管道 + LoRA 低成本微调；强调"数据质量 > 模型规模" | JEV 的护城河不是 9B 模型，而是 10 万条已判数据 + 后验账本；应把"数据管道/评测"当一等公民 | 借鉴理念；模型不必替换 |
| 金融评测基准 | **FinBen / PIXIU**（[arXiv](https://arxiv.org/abs/2402.12659)） | 36 数据集 / 24 任务 / 7 维度（信息抽取、文本分析、QA、生成、风控、预测、决策） | JEV 需要自己的"JEV-Eval"：分类/校准/稳定性/延迟四类指标 + 固定测试集 + CI 门 | 借鉴任务框架 |
| 结构化抽取（最重要） | **Beyond Sentiment: Structured Information Extraction from Financial News**（[arXiv 2607.28496](https://arxiv.org/abs/2607.28496)） | 用 LLM 抽 6 个语义维度（事件类型/影响对象/时间跨度/语义置信度等）；41,618 新闻-股票对实证：结构化特征与情绪特征**正交**（系统性分歧 53.5%），组合 F1 0.600 > 单 FinBERT 0.576；非情绪维度独立贡献 ΔF1 +0.019 | **直接验证 JEV 路线**：多维判定优于单一情绪；JEV 已有 event_type/scope/impact/conf，但缺 **temporal_horizon（时间跨度）** 与 **probabilities 分布**，应补齐 | 直接采用结论 |
| 新闻-价格对齐数据集 | **FNSPID**（[arXiv](https://arxiv.org/abs/2402.06698)） | 1,570 万条新闻 + 2,970 万价格序列（1999-2023，4,775 美股），可复现更新 | JEV 的 posterior 账本（19,052 条）本质是"中文新闻-价格对齐数据"，可产品化为数据集资产 | 借鉴结构 |
| 多智能体框架 | **TradingAgents**（[arXiv](https://arxiv.org/abs/2412.20138) / [repo](https://github.com/TauricResearch/TradingAgents)） | 分析师角色分工（基本面/情绪/技术）+ 多空辩论 + 风控；情绪分析是独立 agent 角色 | JEV 不需要自建多智能体；它本身就是"情绪/事件判定 agent"，应被上层多智能体**当作工具/服务消费** | 不做；作为消费方 |
| 平台化数据/服务范式 | **OpenBB Platform**（[providers 文档](https://docs.openbb.co/odp/python/extensions/providers) / [MCP server 扩展](https://github.com/OpenBB-finance/OpenBB/tree/develop/openbb_platform/extensions/mcp_server)） | provider 插件化（一个数据源=一个包/命名空间）+ 统一 Router + REST + MCP；"不托管数据，只做连接器" | 中台的正确边界：**统一契约 + 多 provider + API/MCP 出口**；JEV 应把自己的"判定"当一个 provider 暴露给上层 agent | 借鉴架构 |
| 中文金融情绪 baseline | 中文 FinBERT（[valuesimplex FinBERT1/2](https://huggingface.co/valuesimplex-ai-lab/FinBERT1-base)）、社区 FinBERT-on-tushare、[FinClaw a-share-nlp-sentiment skill](https://github.com/aifinlab/finclaw/blob/main/skills/a-share-nlp-sentiment/SKILL.md) | 中文金融语料预训练情绪分类；A股新闻情绪 skill 化 | JEV 评测应加 **FinBERT baseline 对照**（比"全判 bull"更强的 baseline），避免高估自身 edge | 引入评测对标 |
| Agent 工具交付形态 | [finagent-mcp](https://pypi.org/project/finagent-mcp/) 等 MCP 金融工具 | 把行情/情绪/分析能力封装成 MCP tools 供 agent 调用 | JEV 已有 MCP 服务（8 tools），应继续把 calibration/event_stream/feedback 也工具化 | 扩展既有 MCP |

**一句话**：开源社区验证了"结构化多维判定 > 单一情绪"，也给出了"provider + Router + API/MCP + 评测"的平台化范式；JEV 不需要重造模型/多智能体，需要补的是**评测治理、契约版本化、服务出口形态**。

## 三、JEV 对平台还有什么价值

当前 JEV 已在服务 5 类消费方：告警门（9101）、复核门（9102）、QD bridge（9103）、角色日报（07:10）、健康卡/校准看板；并已与 yz-substrate 签字段契约、每日导出 posterior jsonl。

潜在增量价值（按价值/成本排序）：
1. **风险前置**：负面事件（立案/退市/违约/爆雷）实时推送到告警门与组合风控 → 已有雏形（bear 标签），可扩成"风险事件流"。
2. **量化因子**：JEV 每日事件聚合（多空家数、事件类型分布、置信度加权）→ 送 quant 作为情绪因子/事件因子（与量价因子正交）。
3. **简报/研究**：Hermes/角色日报的"今日事件-影响"段落；可追溯到 news_id 的证据链。
4. **数据资产**：19k 条 posterior（新闻-价格对齐）+ 10 万条判定 → 可对外/对内作为"中文财经事件标注集"。
5. **评测基线**：JEV 的方向判定可成为平台内其他 agent 的"情绪参考工具"（MCP tool），避免每个 agent 各自调模型。
6. **治理样板**：账本/后验/门控/回放/回滚这一套，是平台里少有的"可审计 AI 判定"样板，可复制到其他判定点。

## 四、是不是该做成中台？——判断与边界

### 4.1 中台的本质
数据中台 = 把"多源数据"变"标准服务"，核心是**治理 + 复用 + 服务化**（[方法论参考](https://wap.seeyon.com/article/Zcng6TG0.html)）：统一口径、API/服务输出、质量与血缘、复用率 KPI。判断标准不是"技术堆多大"，而是"是否有多个场景反复消费、口径是否必须一致"。

### 4.2 JEV 已具备的中台特征（所以不是从零建）
| 中台要素 | JEV 现状 |
|---|---|
| 统一 schema | JEV JSON（bias/conf/scope/event_type/impact/companies/reason）+ yz-substrate 判定点契约 |
| 服务出口 | REST `/api/jev/query`、MCP `jev-news`、批量 posterior jsonl、告警门/复核门/QD 三个常驻服务 |
| 口径治理 | 校准门控（edge/Wilson/20 交易日）、健康卡、审计账本、回放 |
| 质量与血缘 | news_id ↔ run_id/posterior 账本、prompt_version/model 记录 |
| 多消费方 | 简报/角色日报/告警/量化研究/健康卡 |
| 运维 | 夜跑/小时轮/日报/备份/告警 |

**缺的是"中台级治理硬指标"**：SLA、版本弃用策略、复用率/消费方台账、评测门（CI）、限流/缓存。

### 4.3 判断：适合"轻中台"，不适合"重中台"
- ✅ 适合：平台内多 agent/多线消费同一判定；口径必须一致（校准可信层是核心资产）；已有契约与账本，边际成本低。
- ❌ 不适合：组织级重中台（多租户/权限体系/独立团队编制）——当前是个人 OS + 多 agent，没有多租户与独立中台团队需求；过度建设会变成"为建而建"（方法论文章明确的反面案例）。
- 结论形态：**判定中台 = 稳定契约 + 校准可信层 + 四种输出形态（REST/MCP/事件流/数据集）+ 评测治理**；底层仍是现有 news.db + JEV 账本，不引入新的大数据平台。

## 五、目标架构（轻中台）

```
L0 采集/规范化   news.db → 事件规范化（title/source/time/event_type/公司映射）
L1 判定层        云端强模型 + 本地 9B + safe 预筛 + 未来 temporal/probabilities 维度
L2 校准/审计层   jev_audit.db / posterior jsonl / latest.json / 门控 / 回放 / prompt_version
L3 服务层        REST（query/calibration/event_stream） + MCP tools + 批量导出 + 推送订阅
L4 治理层        契约版本化 / SLA / 评测门（JEV-Eval）/ 回滚 / 复用率台账
L5 消费方       Hermes 简报、角色日报、告警门、量化因子、健康卡、其他 agent（MCP）
```

关键设计原则（对齐 OpenBB 的 provider 范式）：
- **一种能力一个 provider 包**：JEV 判定、JEV 校准、JEV 事件流各自独立出口，互不耦合；
- **契约先行**：任何字段/口径变更先改契约文档（已有 yz-substrate 契约先例），带 schema_version + 弃用窗口；
- **服务不托管原始数据**：原始新闻仍在 news.db，中台只保证"判定与校准结果"的一致口径；
- **评测是门禁**：没有 JEV-Eval 通过，不允许改 prompt/模型/预筛（当前靠人工审计，太贵）。

## 六、差距与可落地改进（按优先级）

| 优先级 | 改进 | 现状 | 动作 | 预估 |
|---|---|---|---|---|
| P0 | 补 `temporal_horizon`（时间跨度）与 `probabilities` 分布 | 缺（契约文档已标 `probabilities` ❌） | 判定 prompt + JSON schema 加两字段；契约 v2；向后兼容 | 1-2 天 |
| P0 | 统一 JEV-Eval（评测门） | jev_bench（预筛 A/B）+ OOS 问题集 v3 + 校准账本，分散 | 整合成 `jev_eval.py`：分类/校准/稳定性/延迟四类指标 + 固定集 + CI 门（可先用代理标注） | 2-3 天 |
| P0 | 契约版本化 + 弃用策略 | schema_version 有，弃用策略无 | docs 契约加 schema 版本表 + 弃用窗口；服务响应带 schema_version | 0.5 天 |
| P1 | 增量事件流输出 | 只有全量查询 | REST `updated_since`/cursor + 可选推送（Hermes/告警） | 2 天 |
| P1 | MCP 工具面扩展 | 8 tools（query/pending/calibration） | 加 `event_stream`/`feedback`/`batch_export`；统一 -32602 校验 | 1 天 |
| P1 | 低置信 review 闭环 | 复核门有 triples，未闭环到评测集 | reviewed 样本回灌 JEV-Eval 测试集（人工/半自动标注） | 2 天 |
| P1 | SLA + 限流/缓存 | 无显式 SLA | API 加 P95 目标、429 限流、校准结果缓存（已有 latest.json 缓存雏形） | 1 天 |
| P2 | 复用率/消费方台账 | 无 | 健康卡加"JEV 消费方调用统计"（简报/告警/量化各调用次数） | 1 天 |
| P2 | FinBERT baseline 对照 | 无 | JEV-Eval 加中文 FinBERT baseline，防"全判 bull"过弱基线 | 1 天 |

## 七、路线图（建议 3 阶段，2-6 周）

- **阶段 1（本周-下周）治理先行，不扩架构**：契约 v2（temporal/probabilities）、JEV-Eval 雏形、schema 版本表、finbert baseline 对照。目标：改动有门禁、口径可追溯。
- **阶段 2（2-3 周）服务化出口**：增量事件流 API、MCP 扩展、低置信闭环、SLA/限流。目标：至少 2 个新消费方（量化因子/Hermes 事件段）接入。
- **阶段 3（3-6 周）复用率与资产化**：消费方调用台账、posterior 数据集产品化（对内/对外 JSONL 契约）、门控转绿后方向信号下游化（需老田批准）。

**成功 KPI**：①门控 gate_pass=True 且连续 20 交易日；②JEV 消费方 ≥6（当前 5）；③JEV-Eval 进入 CI 且改 prompt/模型先过评测；④口径变更零破坏（弃用窗口内双向兼容）；⑤P95 查询延迟 <300ms。

## 八、不做什么 / 风险

- **不重建模型/多智能体**：开源已证明数据与评测 > 模型堆叠；TradingAgents 类框架可作为上游消费方，而非替代 JEV。
- **不做多租户/权限重中台**：个人 OS + 多 agent 场景不成立，投入产出比差。
- **不为中台而中台**：先有 2 个以上真实复用场景再扩服务；否则把现有 API/MCP 维护好即可。
- **评测缺位是最大风险**：没有固定评测集与 baseline，服务化只会把"不可信判定"放大到更多消费方。
