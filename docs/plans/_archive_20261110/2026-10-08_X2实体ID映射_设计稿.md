## 0. 一句话方案

在临界 PG 建 `xmap` 独立 schema（三张表：`entity_map` 主映射 + `unmatched_queue` 兜底队列 + `map_audit` 审计），真相源唯一在 PG；Neo4j 图内**不建映射节点**，用 Security 节点属性 `cnm_code` 挂接（每日增量同步）；菜鸟侧零改动（远端生产无写权，拉取式增量）。

## 1. 三类实体的两边现状（实证）

### 1.1 股票代码

| 侧 | 字段 | 格式 | 证据 |
|---|---|---|---|
| 菜鸟 | `stock_basic.stock_code`（UNIQUE） | 6 位裸码，如 `600519` | all_ddl.sql `uk_stock_code`【✅实证】 |
| 菜鸟 | `stock_basic.market` | `SH`/`SZ`/`BJ`（业务表注释一致，如 stock_trade_strategy_pool.market） | all_ddl.sql【✅实证】 |
| 菜鸟 | `stock_basic.ts_code`（可空） | tushare 风格 `600519.SH`，**菜鸟自己已存了一份** | all_ddl.sql【✅实证】 |
| 临界 | Neo4j `Security.ts_code`（唯一约束） | `600519.SH` | kg_schema.py:83-84【✅实证】 |
| 临界 | 证券主档 | stock_basic parquet（kg_schema.py:78 SOURCE_SEED）+ PG 行情明细 | kg_schema.py 头注【✅实证】 |

**关键红利**：菜鸟 stock_basic 同时有 `stock_code`+`market`+`ts_code` 三重冗余——首次全量映射几乎可以纯确定性完成（约 2.1 万行，AUTO_INCREMENT=21431【✅实证】），零猜测。

业务表中散落的 `stock_code`（stock_trade_strategy_pool / stock_trade_strategy_instruction / stock_trade_member_real_order / ai_team_task 等约 25 张表）一律通过本映射表换算，不改菜鸟任何一行。

### 1.2 策略

| 侧 | 键 | 形态 | 证据 |
|---|---|---|---|
| 菜鸟 | `stock_trade_strategy.id` bigint（租户内） | 三模式策略（AGENT/MODEL/HYBRID，strategy_mode 列【✅实证】）+ `stock_trade_selection_model` / `stock_trade_model` 两个模型表 | all_ddl.sql |
| 临界 | `portal/strategies.json` 的 `id`（string） | `chanlun`/`ninedim`/`weak`/`linkage`/`cross`… 产线级策略注册表 | portal/strategies.json:15-80【✅实证】 |

**性质差异【⚠️关键判断】**：两边"策略"不是同一层的东西——菜鸟是**用户实例策略**（每人每租户可建任意多个），临界是**产线策略资产**（全局唯一、人工注册）。因此：
- 股票映射目标是"全量自动"；策略映射目标是"**少量精选挂接**"：只把菜鸟里与临界产线语义对应的少数策略（以及值得观察的高质量社区策略 stock_community_strategy）挂到图上，其余不映射也不入队。
- 映射方向菜鸟→临界为主；菜鸟 `stock_community_strategy.source_strategy_id`（跨租户复制链【✅实证】）也要挂接，用于观察"哪个源头策略在社区传播"。

### 1.3 用户

| 侧 | 键 | 证据 |
|---|---|---|
| 菜鸟管理端 | `system_users.id`（+ mobile） | all_ddl.sql |
| 菜鸟会员端 | `member_user.id`（+ mobile）；yudao 双 user_type（admin/member）惯例如 system_oauth2_access_token.user_type【✅实证】 | all_ddl.sql |
| 菜鸟跨系统锚 | **mobile 已被菜鸟自己当作跨系统唯一标识**（stock_community_strategy.source_mobile、stock_community_strategy_interaction.user_mobile、system_client_info.mobile）【✅实证】 | all_ddl.sql |
| 临界 | 登录态尚不存在，由 X1（登录整合预置说明）定义 | docs/plans/2026-10-08_X1登录整合_预置说明.md |

**决策**：临界**不新建用户表**。菜鸟 userId 即权威登录态（X1 已定调复用菜鸟 userId）；xmap 用户映射解决的是两个问题：
1. 菜鸟内部归并：同一自然人的 `system_users` 账号与 `member_user` 账号（按 mobile 归并，同 mobile 即同人【✅实证有据：菜鸟跨系统锚就是 mobile】）。
2. 为未来临界原生登录态预留 dst 槽位（dst_system='lingjie', dst_id 先空，status='pending'）。

## 2. PG 映射表 DDL（schema: xmap）

> 落在临界 PG（127.0.0.1:5442），独立 schema 不污染 public。PG 语法。
> 【✅实证·自检】本稿 DDL 已于 2026-10-08 在容器 newquantsystem_v2-postgres-1 事务内（BEGIN…ROLLBACK）全量通过语法验证；容器实测 `POSTGRES_USER=quant_user`、`POSTGRES_DB=quant_system`——施工连接串用此二者，勿写库名 newquantsystem_v2（那是 compose 项目名）。

```sql
-- ============================================================
-- X2 实体 ID 映射表（临界 PG newquantsystem_v2 / schema xmap）
-- ============================================================
CREATE SCHEMA IF NOT EXISTS xmap;

-- ── ① 主映射表 ──────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS xmap.entity_map (
    id              bigserial PRIMARY KEY,
    entity_type     text        NOT NULL,   -- 'stock' | 'strategy' | 'user'
    src_system      text        NOT NULL DEFAULT 'rookie',
    src_ns          text        NOT NULL DEFAULT '',
        -- stock: ''；strategy/user: 菜鸟 tenant_id 或 user_type(admin/member)
    src_id          text        NOT NULL,   -- 菜鸟侧原始键（stock_code / 表主键）
    dst_system      text        NOT NULL DEFAULT 'lingjie',
    dst_ns          text        NOT NULL DEFAULT '',
    dst_id          text        NOT NULL,   -- 临界键（ts_code / strategies.json id / 预留）
    match_method    text        NOT NULL,   -- 'rule' | 'ts_code_confirm' | 'mobile'
    --   | 'name_fuzzy' | 'manual'
    confidence      numeric(4,3) NOT NULL DEFAULT 1.000,  -- 0~1
    status          text        NOT NULL DEFAULT 'matched',
        -- 'matched' | 'pending'(待人工复核) | 'unmatched' | 'disabled'
    src_payload     jsonb       NULL,       -- 菜鸟侧快照（名称/市场/时间等，审计用）
    reviewed_by     text        NULL,
    reviewed_at     timestamptz NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now()
);

-- 正向查询：菜鸟键 → 临界键（主路径）
CREATE UNIQUE INDEX IF NOT EXISTS uq_xmap_fwd
    ON xmap.entity_map (entity_type, src_system, src_ns, src_id);

-- 反向查询：临界键 → 菜鸟键（图上点回菜鸟业务表、反查下游影响）
CREATE UNIQUE INDEX IF NOT EXISTS uq_xmap_rev
    ON xmap.entity_map (entity_type, dst_system, dst_ns, dst_id)
    WHERE status = 'matched';

-- 覆盖 status 过滤的快速扫描（队列页/看板）
CREATE INDEX IF NOT EXISTS idx_xmap_status
    ON xmap.entity_map (entity_type, status);

-- ── ② 对不齐兜底队列 ────────────────────────────────────────
CREATE TABLE IF NOT EXISTS xmap.unmatched_queue (
    id              bigserial PRIMARY KEY,
    entity_type     text        NOT NULL,
    src_system      text        NOT NULL DEFAULT 'rookie',
    src_ns          text        NOT NULL DEFAULT '',
    src_id          text        NOT NULL,
    src_payload     jsonb       NULL,
    reason          text        NOT NULL,
        -- 'no_ts_code' | 'ts_code_mismatch' | 'dst_not_found'
        -- | 'ambiguous' | 'new_entity'
    attempt_count   int         NOT NULL DEFAULT 0,
    status          text        NOT NULL DEFAULT 'open',
        -- 'open' | 'resolved' | 'ignored'
    resolved_map_id bigint      REFERENCES xmap.entity_map(id),
    detected_at     timestamptz NOT NULL DEFAULT now(),
    resolved_at     timestamptz NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_xmap_unq
    ON xmap.unmatched_queue (entity_type, src_system, src_ns, src_id)
    WHERE status = 'open';   -- 同一实体只排一次队

-- ── ③ 审计（谁改了映射，只追加不改）─────────────────────────
CREATE TABLE IF NOT EXISTS xmap.map_audit (
    id              bigserial PRIMARY KEY,
    map_id          bigint      NOT NULL REFERENCES xmap.entity_map(id),
    action          text        NOT NULL,   -- 'insert' | 'update' | 'disable'
    old_row         jsonb       NULL,
    new_row         jsonb       NULL,
    actor           text        NOT NULL DEFAULT 'system',
    acted_at        timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_xmap_audit_map
    ON xmap.map_audit (map_id, acted_at DESC);
```

**语法自检**：部分唯一索引 `WHERE status='matched'`、`WHERE status='open'` 为 PG 合法语法；jsonb/bigserial/timestamptz 均为 PG 内建；外键引用同 schema 表无需前缀。

**设计取舍**：
- 不用枚举类型，`entity_type/status` 全用 text + CHECK 留给施工期（初期口径可能微调，text 改动零成本）。
- `src_payload` 存菜鸟侧行快照——菜鸟是远端生产，映射表必须能独立回答"当时是按什么对上的"，减少回查生产库。
- 反向索引带 `WHERE status='matched'`，pending 行不参与反查，避免半成品映射污染查询。

## 3. 首次全量对齐方案（确定性优先 + 复核队列）

### 3.1 股票（全自动，预计 99%+ 直接过）

```
输入：菜鸟 stock_basic 全量（stock_code, market, ts_code, stock_name, list_status）
基准：临界证券全集 S = Neo4j Security.ts_code ∪ PG stock_basic parquet ts_code

步骤：
 ① 若菜鸟 ts_code 非空 且 ∈ S      → matched, method='ts_code_confirm', conf=1.000
 ② 若菜鸟 ts_code 为空              → 规则推导（§3.2 映射规则表）得 ts_code
                                     ∈ S → matched, method='rule', conf=0.990
 ③ 推导结果 ∉ S（含菜鸟 ts_code 与推导不一致、S 中找不到）→ 入 unmatched_queue
                                     reason='ts_code_mismatch'/'dst_not_found'
 ④ 菜鸟有、临界 S 无（新股未同步等）→ 入队列 reason='dst_not_found'，
                                     同时提示临界侧跑 stock_basic 增量
```

### 3.2 代码格式映射规则表（rule 引擎唯一依据）

| 菜鸟 market | 菜鸟代码特征 | 临界 ts_code 后缀 | 备注 |
|---|---|---|---|
| `SH` | 全部 | `.SH` | 含 60/68/11(转债)/5(基金) |
| `SZ` | 全部 | `.SZ` | 含 00/30/12(转债)/1(基金) |
| `BJ` | 全部 | `.BJ` | 北交所 43/83/87/92 |
| `NULL`/其他 | 6 开头 | `.SH` | 兜底推导 |
| `NULL`/其他 | 0/3 开头 | `.SZ` | 兜底推导 |
| `NULL`/其他 | 4/8/92 开头 | `.BJ` | 兜底推导 |
| `NULL`/其他 | 其他 | —— | 直接入 unmatched_queue |

规则表只覆盖 A 股+ETF+转债（两边现状均如此【✅实证】）；港美股/期货不在本期范围，进队列人工裁决。

### 3.3 策略（半自动，少量精选）

- 候选生成：临界 strategies.json 每条 sid，用 `stock_trade_strategy.strategy_name` 做相似度提案（PG `pg_trgm` 的 `similarity()`，阈值 0.35 提案、不自动通过）。
- 全部提案进 `pending`，人工在复核页点选确认（method='manual' 或 'name_fuzzy'，conf 按人工操作记 1.0）。
- 菜鸟社区策略（stock_community_strategy）按 `source_strategy_id` 回溯到源策略后继承映射；无源可溯的进 pending。
- 预计量级：几十条，人工成本一次性的。

### 3.4 用户（mobile 归并）

```
① 菜鸟内部归并：system_users.mobile ∪ member_user.mobile 同号 →
   同一 canonical 自然人（canonical_id = 归并组内最早的 member_user.id，
   组内每个账号各存一行映射，dst_id = canonical 键）
② 临界侧：dst_system='lingjie', dst_id=NULL 不可行（dst_id NOT NULL）→
   约定 dst_id 存 canonical 键（即菜鸟 member_user.id），
   status='pending' 表示"临界原生登录态未上线，挂接未完成"；
   X1 上线后批量 UPDATE 一次 status='matched'
③ 无 mobile 的账号（system_users.mobile 可空）→ unmatched_queue
   reason='ambiguous'（不能拿 username 猜人）
```

## 4. 增量维护方案（谁变更谁上报 → 落地为"临界拉取 + watermark"）

**定调**：菜鸟是远端生产库，我们无权植入变更钩子/Binlog 监听；且菜鸟三张核心表都有可靠的 `update_time`（stock_basic 有 ON UPDATE CURRENT_TIMESTAMP【✅实证】，stock_trade_strategy 同【✅实证】）。因此"谁变更谁上报"在物理上落地为**临界侧每日拉取式增量**：

| 实体 | 拉取源 | 增量谓词 | 频率 | 动作 |
|---|---|---|---|---|
| stock | 菜鸟 stock_basic | `update_time > :wm` | 每日 1 次（KgDailySync 前置，06:00 槽位） | 走 §3.1 同一规则函数；新增→插入或入队；改名/退市→更新 src_payload，status 不删（退市标 `disabled`，历史映射保留——回测/血缘要查历史） |
| strategy | stock_trade_strategy / stock_community_strategy | `update_time > :wm` | 每日 1 次 | 新策略默认**不入队**（§1.2 精选原则），仅当命中"已映射策略的副本/学习链"时自动扩展；其余静默 |
| user | system_users / member_user | `update_time > :wm` | 每日 1 次 | mobile 归并重跑该 user 的组；手机号变更→旧映射 `disabled` + 新映射插入 + audit |

- watermark 存 `xmap.map_audit` 外的轻量处：复用 entity_map 无处放 → 建议 4 行 `infra` 式小表 `xmap.sync_watermark(entity_type text pk, wm timestamptz)`（施工期建，DDL 附于实施稿）。
- 全程只读菜鸟（SELECT），连接串单独配置，只授 SELECT 权限。
- 每次增量运行本身登记进 X3 的 job_run（job='xmap_sync'），血缘闭环。

## 5. 对不齐的兜底

1. **查询侧兜底函数**（施工时以 SQL 函数或 Python helper 呈现）：
   `resolve(entity_type, src_id) -> dst_id | NULL`——查 matched 未中 → 规则表推导（仅 stock）→ 仍失败则 `INSERT INTO unmatched_queue ... ON CONFLICT DO NOTHING` 并返回 NULL。调用方拿到 NULL 时用规则推导的临时码继续跑，**不阻塞主流程**（如 KgDailySync 挂菜鸟事件时，个别未对齐标的照常入图，只是 CrossRef 属性缺失）。
2. **复核队列消费**：unmatched_queue open 项按 reason 分流——`dst_not_found` 多为临界数据滞后（重跑临界同步即消）；`ts_code_mismatch`/`ambiguous` 需人工；`ignored` 留痕不删。
3. **防漂移**：matched 行每月抽样 100 条反向校验（菜鸟 stock_basic.ts_code ↔ 临界 S 再比对一次），不一致自动转 pending + audit。

## 6. 与 Neo4j 的挂接方式（建议：属性为主，CrossRef 边不做）

**建议：映射表不落图。图上只在 Security 节点加一个属性 `cnm_code`（菜鸟 6 位裸码），每日增量 `SET`。**

理由：
1. **基数事实**：股票映射是近似严格 1:1 且可规则推导的双射，"边"承载的是*关系存在性*信息，1:1 双射用属性零信息损失；为 2.1 万条等价关系建 2.1 万条 CrossRef 边，让 420 万边的图平添 5% 噪声边，所有遍历（如 SIMILAR_K 邻居扩展）都要白白跳过它们。
2. **单一真相源**：映射真相源在 PG xmap（需要事务、部分唯一索引、审计），图里只是投影缓存——与 kg_communities.json"快照可为真相源，图不是"同一哲学。
3. **查询形态**：未来"菜鸟事件挂图"（勘查报告缺口 #3）的入口都是"拿菜鸟 stock_code 找 Security"，一条 `MATCH (s:Security {cnm_code: $code})` 即可，无需穿越边；属性查询走 `CREATE INDEX sec_cnm IF NOT EXISTS FOR (n:Security) ON (n.cnm_code)`。
4. **保留升级路径**：若未来出现真·多对一（例如菜鸟终端自定义代码、或跨市场实体挂接），再引入 `Security -[:CROSS_REF {system:'rookie', src_id:...}]-> Security` 这类边——今天不为假想需求建边。

同步实现：X2 每日增量末尾（§4 stock 步骤后），把当日 matched 变更行 `UNWIND + MATCH (s:Security {ts_code: row.dst_id}) SET s.cnm_code = row.src_id`（复用 kg_client.py:77 `KgClient.upsert_nodes` 同款批量范式，但此处走 MATCH+SET 避免 MERGE 误建节点）。
