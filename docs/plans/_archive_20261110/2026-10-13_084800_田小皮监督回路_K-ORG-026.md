## 二、最优方案：田小皮监督回路（三层）

**田小皮 = 平行空间的老田**：以 org_baseline.json 计划基线为「应然」，只读巡检三源「实然」，diff 产出四色判读与建议动作。

```
┌─ 应然：org_baseline.json（计划基线，批A-E + 阈值）
│
├─ 实然三源（全只读）：
│   1. .worktrees/tasks.json      工单状态（39 done/4 doing/19 review）
│   2. portal/data/dev_events.jsonl 开发事件流（今日 86 条）
│   3. memory jsonl 黑板           各岗 decision/observation
│
├─ 判读器：tools/chief_patrol.py（E1 已落地）
│   · 组织脉搏（活性/积压/超时单）
│   · 计划符合度（五批逐项 ✅⬜🧊 销账）
│   · 风险四色：🟢正常/🔵超前/🟡滞后/🔴阻塞 + 建议动作
│   · 判读落 data/shadow/chief_patrol_*.md + chief observation 黑板
│
└─ 行动层（只派单不代跑）：
    晨巡 automation（E2）→ 有风险即派单（K-ORG-025 链）/简报
    17:35 日报并入判读（E3，随批 B 10-15 解禁）
```

**关键设计决策**：
1. **监督与执行分离**：田小皮只读+判读+派单，merge/执行权留各岗与团队线门禁——避免「监工下场干活」的权限混乱（CrewAI hierarchical 的 manager 也只 reroute 不执行）。
2. **基线即配置**：改研发计划=改 org_baseline.json+重跑巡检，零代码；判读器永远对照最新计划。
3. **阈值护栏**：doing 48h 无流转=滞后、review≥20=警戒、≥30=P0 冻结新派发——机器可判，不靠感觉。
4. **冻结面识别**：批 B 的哨文件冻结纪律写进基线（blocked_until_1015），巡检器显式标 🧊 防止代理误动。
