# 数字军团统一收编方案（K-ORG-116 建议稿）
> STATUS: frozen（只读保留）



> 2026-10-16 · 触发：老田拍板「所有智能体归入数字军团统一管理调配，方便未来对接与数据统一」
> 上游判例：K-ORG-112（Hermes 总控与双表面边界）· K-ORG-087（军团改进 T1-T6）· K-ORG-094/095/109（8093 骨干/军团连接器/caller 归因）
> 性质：**总体解决方案**——回答「怎么把 29 编制 + 6 运行体 + 未来新增（OSINT worker 等）收进一个军团」

---

## 〇、设计公理（从判例提炼，本方案一切取舍以此裁决）

1. **编制统一 ≠ 运行时合并**（K-ORG-112 §3.1）：Jev 四件套/Hermes/cowbridge 代码一行不动、进程原地跑——统一发生在「编制、身份、账本、调度入口、数据」五个抽象层。谁把运行体逻辑搬进门面，评审门直接拒收。
2. **Jev 只拥有判断，不拥有系统**：收编后依然成立——Jev 判断 → 军团执行，边界不变。
3. **调度本体在骨干不在门面**：定时=计划任务，事件=PG NOTIFY，指挥=8093；Hermes/飞书只是表面。
4. **同源同落点**（K-ORG-112 §3.2）：全军团一套账本、一套工单、一套记忆 ID 空间，禁止第二套状态。
5. **fail-visible + caller 归因**（§4 配方）：任何新接入体照抄 legion.py 配方，账本必见 `caller=`。

## 一、现状盘点（收编对象清单）

| 类别 | 成员 | 当前登记 | 缺口 |
|---|---|---|---|
| 编制岗（29） | A0/A0A + 8 职能部 22 岗 + 3 项目部 | ✅ org.json + claude_agents.json + 岗卡 | 无（已是军团） |
| 运行体（6） | Jev 四件套、cowbridge 记忆桥、Hermes WebUI | ❌ 各自为政，org.json 无名分 | 编制/身份/账本三无 |
| 宿主环境（2） | WorkBuddy（本会话）、菜鸟 ai_team（投研五虎运行环境） | 部分（五虎经 ai_team_role 配置） | 归因口径不一 |
| 未来增量 | OSINT worker（采集/抽取/质检）、Khoj 检索、OpenClaw 网关 | 未出生 | 必须出生即军团籍 |

**核心病根**：军团有「编制表」没「全量名册」——运行体干了活，账本上却没有军团身份，数据无法 join，未来每个新成员都要发明一次接入方式。

## 二、目标架构：五层一册

```
┌─ L4 表面层：Hermes 8787（PC）+ 飞书（移动）+ 8080 门户大屏 ── 只转调只读态
├─ L3 调度层：8093 OrgRegistry（devtask 工单/状态）+ 8095 定时 + PG NOTIFY 事件
├─ L2 骨干层：message_hub（K-STOCK 阶段2）+ observe 账本（llm_tool_audit.jsonl）
├─ L1 执行层：29 编制岗 + Jev 四件套 + cowbridge + Hermes + OSINT workers（原样跑）
└─ L0 编制层（★本方案核心）：org_registry v2 —— 全军团唯一名册
```

**一个名册（org_registry v2）**：在 org.json 基础上扩 schema，每个成员一条记录：

```json
{
  "agent_id": "JEV_GATE",
  "kind": "runtime",            // staff=编制岗 | runtime=常驻运行体 | external=外部宿主
  "dept": "ops_runtime",        // 新设「运行体部」
  "name": "Jev 告警降噪网关",
  "endpoint": "127.0.0.1:9103", // 存活探针（kind=runtime 必填）
  "supervisor": "JevStack",     // 守护任务/看门狗名
  "memory_ns": "jev",           // 记忆/账本命名空间
  "tools_allowed": {"read":["v2_alert"], "write":["gate_ignored"], "danger":"deny"},
  "inited": "2026-10-16"
}
```

三条铁律写进 schema 校验：① runtime 必须有 endpoint+supervisor（可探活可归责）；② 全册 agent_id 唯一（数据 join 的主键）；③ tools_allowed 四维矩阵与编制岗同构（权限模型统一）。

## 三、数据统一：一主键三账本

**主键 = agent_id**。三本账全用它 join：

| 账本 | 内容 | 现状 → 目标 |
|---|---|---|
| 工单账（tasks.json / devtask） | 谁在干什么 | 已有 → 运行体也开单（如 JEV_GATE 的复核任务可追） |
| 观察账（llm_tool_audit.jsonl） | 谁调了什么工具 | 已有 caller 归因 → 运行体全部补 caller=<agent_id> |
| 记忆账（agent__X__{decision,knowledge}.jsonl） | 谁积累了什么 | 军团 29 岗已有 → 运行体建同名 ns（如 agent__JEV_GATE__） |

统一后一条 SQL/查询即可回答：「过去 7 天，军团每个成员干了什么、判断了什么、学到了什么」——这就是你要的「数据统一」的实体。

## 四、调度统一：devtask 泛化

8093 的 devtask 目前只认编制岗。泛化为军团统一调度入口：

1. **staff**：现状不变（devtask new → worktree/branch → 产码）。
2. **runtime**：新增 `devtask dispatch --agent JEV_GATE --op recheck --payload {...}`——转调运行体已有 HTTP/CLI 入口（照抄 legion.py 配方：HTTP 转调、fail-visible、caller 注入），**不给运行体加新逻辑**，只加「被军团调得动」的壳。
3. **出生即入籍**：OSINT worker 开发规约（进 osint_video/README）：新建运行体第一件事=注册 org_registry v2 条目，否则 PR 不合（挂 org_supervision 体检门）。

## 五、体检与治理（挂 K-ORG-087 体系）

`org_supervision.py` 新增 `check_registry_v2()`：
- ① 全册 agent_id 唯一、schema 合法；
- ② runtime 条目探针：endpoint 存活率（死=红，同 N1 巡检口径）；
- ③ 账本覆盖率：近 7 天 observe 账本中出现但名册无籍的 caller=「黑户告警」（防再出现孤岛）；
- ④ 记忆 ns 对齐：有 memory_ns 的成员，对应 jsonl 存在。

田小皮（A0）每日判读清单加一行：「黑户/失联运行体」——参谋长统一点名。

## 七、风险与边界

| 风险 | 对策 |
|---|---|
| 收编变「合并」（有人想把 Jev 塞进 Hermes 进程） | 公理 1 写进评审门；连接器一律 legion.py 配方 |
| 名册双源（org.json 与 v2 并存漂移） | v2 是 org.json 的超集演进，**同文件升级**不留第二份；org_baseline.json 保留作回滚锚 |
| 运行体探针拖慢体检 | 探针并发+超时 3s，死=红不阻塞其余 |
| 冻结链破坏 | 全部改动走新工单（本档 → K-ORG-116 立项），D-Day 冻结 tag 不触碰 |

## 八、拍板项（需老田圈阅）

1. 「运行体部」命名与编制（建议 dept=ops_runtime，部长挂 A0A 兼任——只调度不决策，合其宪章）；
