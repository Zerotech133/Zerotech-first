# 按角色统一：数据 / 能力 / 页面动线方案 v1（2026-11-04）

> 目的：把“按业务域平铺的 6 大菜单”收敛为 **“角色是主语，数据/能力/页面是谓语”** 的统一工作台动线；**不新增页面、不新增第二入口、不新做平台**，全部映射到 8734 现有页面。
> 依据：`org.json`（17 部门/77 席/5 HQ）、Q2 证据矩阵（6 军团 auto 6/6、owner 0/6）、`portal/nginx.conf` 现网路由、`nav.js` 现菜单、2026-11-04 数据打通评估。
> 结论：**先做“角色—数据—能力—页面”四张对齐表 + 一个角色导航器；页面复用现有路由，动线固定为“看数→处理→交证据”三步。**

## 一、统一原则（五条硬约束）

1. **单一入口**：只有 `http://127.0.0.1:8734`；8787/8103 是子工具，不作为第二入口。
2. **单一真源**：每类数据只认一个 API/账本；页面不直读 DB、不复制口径（`/api/dw/*`、`/api/hq/*`、`/api/acad1/pool`、`/api/d1/*`、`/api/strategies`、`/api/intel/*`）。
3. **角色唯一工作台**：每个角色只配置 **1 个 landing 页 + 1 条三步动线**；其余页面为下钻，不另设入口。
4. **能力即权限**：角色能力=可看的 API/可做的动作（查看/签收/审批/执行/合并/签字）；L2 动作仍走五要素，不因页面动线而放开。
5. **收口期不新增页面**：所有动线复用现有页面；新增页面/组合须 11-16 后按 ADGS 立项，先有 DOR/DOD。

## 三、页面动线统一模型

### 3.1 三层结构（所有角色同一骨架）
```text
L0 统一入口：8734（登录态）
L1 角色工作台（landing）：一屏看“我的 KPI / 待办 / 告警 / 证据缺口”
L2 业务处理页：该角色唯一主业务页（任务/队列/审批/验收）
L3 证据与下钻：报告/回执/审计/血缘/矩阵（只读，带 data_date+owner）
```
### 3.2 统一三步动线（强制）
```text
看数（L1 工作台） → 处理（L2 唯一动作页） → 交证据（L3 回执/签字/矩阵） → 返回 L1
```
- 每个角色**最多 3 次点击**到达动作页；禁止从首页直接平铺全部业务域。
- 所有页面必须有“返回我的工作台”+面包屑；当前 `nav.js` 的“← 返回”保留。
- 跨角色协作只走“任务/工单”链接（ARCH1 派单、A0 审批），不允许直接跳到他人写域页面。

### 3.3 首页（`/`）角色卡（替代 6 大域平铺）
```text
┌ 零界 · 今日 ──────────────────────────────┐
│ 我的角色：[A0 田丰 ▼]  （首次登录可按账号绑定）│
│ [我的工作台]  [待办 3]  [告警 1]  [证据缺口 2] │
│ 快捷三步：看数 → 处理 → 交证据               │
├ 角色工作台（仅显示相关 3–5 个）───────────────┤
│ A0: /hq  ·  ARCH1: /devops  ·  INTEL0: /intel │
│ DATA1: /dataops · ACAD1: /academy/shuijing    │
│ D1: /d1/ · STRAT1: /strategies · 黄忠: 验收    │
└────────────────────────────────────────────┘
```
> 不新增页面：首页 `/` 已是 `home_v3` 入口，只加“角色卡 + 3 个快捷入口”；角色映射配置化。

## 四、数据对齐规则（每角色 4 个字段）

每个角色在配置中只声明 4 项，其他页面不得复制口径：
```yaml
role_id: INTEL0
primary_data: news.db / jev_review_queue / dec_audit / intel 源健康
api_contract: /api/news/intel, /api/jev/*, /api/intel/*
freshness_sla: 采集 T+0；队列 pending ≤3 天；hit 空 ≤30%
evidence: 受理回执/源健康报告/复核台账（owner 签字）
```
- **一张指标一个 API**：页面显示的数字必须来自 `api_contract`；禁止页面自己算第二份。
- **T+0/T+1 明示**：页面必须显示 `data_date` 与来源；stale 数据打黄标（如 TDX 三表 11-01）。
- **写权限**：角色只写自己的域（`write_scope`）；跨域只能发任务/审批，不得直接写对方账本。
- **数据字典**：`dataset_id / api_path / owner / freshness / pii` 五字段入 `role_workspaces.json`，作为唯一映射。

## 五、能力对齐规则（角色=能力包）

| 能力类 | 含义 | 谁有 |
|---|---|---|
| 查看/下钻 | 读该角色数据域 | 全部角色（仅自己域） |
| 受理/签收 | 签收上游报告出 ACK | INTEL0、DATA1、D1 等受理席 |
| 创建/派单 | 建任务/工单 | A0、ARCH1、各主官 |
| 审批/裁决 | 批准 L2/例外/风险 | A0 + 双签（ARCH1/治理） |
| 执行/合并 | 改代码/合并 | ARCH1 及研发 worker（门禁内） |
| 验收/签字 | Q2/交付签认 | HUANGZHONG + 各 owner（不代签） |
| 发布/通知 | 对外推送/客户消息 | LUSU1/邓芝（白名单+人工确认） |

- 能力缺口已登记：军情司 **6/8 席无 role_profile/tools**；全公司 profile 仅 5/69；Hermes MCP **11/13**；页面能力不得先于 profile 上线。
- 每个角色能力包必须含：可用 API 清单、可执行动作、禁止动作、L2 触发条件、审计字段。

## 七、验收指标

1. **动线**：每个角色从 8734 首页 ≤3 击到达自己主业务页；≤5 击完成“看数→处理→交证据”一次闭环。
2. **数据**：每个角色显示的数字均有唯一 API 与 `data_date`；stale/缺口可见（黄标/红标）。
3. **能力**：角色只能执行能力包内动作；越权在 API 层 403，不靠页面隐藏。
4. **无重复入口**：同一业务域只在一个角色工作台为主入口；其他角色仅下钻。
5. **证据**：每次处理有回执/审计记录（owner+时间+data_date+命令/rc）。

## 八、风险与边界

- **不新增页面/第二入口**；现有 6 大域菜单保留为“全部功能”二级入口，角色卡只是首页快捷层，不替代导航。
- **不改路由**：P0 只改首页卡片与 nav 数据；如必须新增路由，先 `portal_route_inventory.py --write-baseline` 同提交，避免 route 门 FAIL。
- **不代签**：角色卡只显示待签/缺口，不在首页直接签；签认仍进 Q2/审批页并留痕。
- **并发**：`role_workspaces.json` 为新文件，单一 owner（Lead/ARCH1）；`nav.js` 由 `api_common.py` 导出，避免手改。
- **收口优先**：P1 遇数据未打通板块，先补数据不补页面；页面动线不掩盖 49 未注册数据集、intel 4.5 天队列、D1 decisions=0 等硬缺口。
