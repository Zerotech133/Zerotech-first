## 0. 结论速览

| 设计点 | 方案 |
|---|---|
| 核心原则 | **执行拓扑与组织架构正交**：DSL 管「一个任务内部怎么跑」（K-STOCK-003 已解决），组织层管「长期分工、汇报、权限」（本报告） |
| 组织模型 | org 树：老田（人类决策）→ A0 总管 → 部门（研发/策略/交易/市场[规划]）→ Agent 成员；**部门主管可选**（小部门 A 主直管省 token） |
| 汇报机制 | 三通道：**日报**（定时汇总）/ **事件**（P0/P1/P2 严重度分级实时上报）/ **问询**（老田问 A 主，A 主带授权查部门） |
| 跨部门协作 | 显式任务单（ticket）+ share 白名单，禁止 Agent 私下跨部门读写 |
| 记忆演进 | namespace 四级不变，`team` 语义泛化为 `dept`；A0 获跨部门 team 级读权限（agent 级仅异常时经授权+审计） |
| 验收标准 | 与 K-STOCK-003 一致：新增部门/Agent = 注册表加配置，零代码改动 |

## 1. 需求锚定（老田原话）

> 「我希望这套开源架构下面能实现组织架构。比如说一个 A 主来负责和我汇报。他下面有很多部门，有负责研发的，负责量化的。研发的就负责去做拉代码、优化代码、训练我们的模型。那么做策略的就负责是复盘，那么做交易的就是做交易的。当然未来还有 Agent 可能是基于现目前的所有的结构在做视频、做宣发。我需要的是一套有组织架构的 Agent 的多元架构的平台。」

拆解为四个工程需求：

1. **N-1 汇报链**：唯一入口 A 主向老田汇报，老田不直接面对 N 个 Agent（降噪）。
2. **N-2 部门分工**：研发（代码/训练模型）、策略（复盘）、交易（执行），职责边界清晰。
3. **N-3 可扩展**：未来加部门（视频、宣发）像加团队一样加配置。
4. **N-4 平台化**：同一套框架承载所有业务线（选股只是策略部下的一个团队）。

## 2. 核心设计决策：两个正交维度

```
维度一：执行拓扑（intra-job）   —— K-STOCK-003 DSL 已解决
   一个任务内部：T1⇄T2 辩论 → 屏障 → D1 决策 → checkpoint
   生命周期 = 单次任务，跑完即散

维度二：组织架构（inter-org）   —— 本报告新增
   长期存在：部门分工 / 汇报链 / 记忆权限 / 跨部门协作
   生命周期 = 永续，像公司编制
```

**为什么正交重要**：选股拓扑里的 T1/T2/N1/F1/D1 是「策略部内部的一次选股流程」，不是五个长期员工；而研发部 DEV1 是长期员工（持续拉代码优化）。两者生命周期、权限模型、考核方式完全不同——混在一个模型里必然混乱。DSL 解释器不感知组织，组织层不感知执行细节，中间只通过**记忆**（产出沉淀）和**任务单**（工作交接）交互。

## 3. 组织架构模型

```
老田（人类，最高决策，唯一汇报对象）
 └── A0 总管 Agent（汇报入口 / 任务仲裁 / 记忆治理者）
      ├── 研发部 dev
      │    ├── DEV1 代码工程师（拉代码 / 优化代码 / code review）
      │    └── DEV2 模型训练师（训练 / 评估 / 版本登记 domain）
      ├── 策略部 strategy
      │    ├── ST1  复盘分析师（读交易 feedback → 提改进任务单）
      │    └── team:alpha  ← K-STOCK 选股线整体挂载（T1/T2/N1/F1/D1 执行拓扑）
      ├── 交易部 trading
      │    └── TR1  交易执行员（执行策略产出 → 成交/滑点写 feedback）
      └── 市场部 marketing（规划中，结构预留）
           ├── MKT1 视频制作（预留）
           └── MKT2 宣发文案（预留）
```

**部门主管设计为可选**：`lead: null` 时 A 主直管（当前规模下省一层 LLM 调用与 token）；部门 Agent 数 >3 或跨团队协调变复杂时再设主管，架构上零改动（注册表 `lead` 字段填上即生效）。

**A0 三项职能**：
1. **汇报聚合**：三通道汇总（§4）；
2. **任务仲裁**：跨部门任务单的拆解与派发（§5）；
3. **记忆治理**：domain 级标准的写入者之一（与老田共同），部门间记忆冲突的仲裁人。

---

## 4. 汇报机制：三通道

| 通道 | 触发 | 链路 | 严重度规则（对齐老田 P0/P1/P2 习惯） |
|---|---|---|---|
| **日报** | 定时（18:00） | 各部门 17:30 从 `decision/feedback` 记忆自动提炼日报 → A0 汇总（含 K 线图/净值等可选附件）→ 飞书/微信推老田 | 无需分级，固定格式：{部门, 今日产出, 异常, 明日计划} |
| **事件** | 实时 | 部门 Agent 产生异常/里程碑 → 事件总线（Redis pub/sub）→ A0 判级 → 推送 | **P0 立即推**（如交易 RiskGuard critical、CI 红灯堵住发布）；P1 小时内；P2 攒入日报不单独打扰 |
| **问询** | 老田随时 | 老田 → A0 → A0 带读权限查各部门 team 级记忆，必要时向部门派一次性子任务 → 汇总答复 | 无 |

**降噪原则**：老田只面对 A0 一个入口；P2 级信息永远进日报不进实时推送——避免多 Agent 平台常见的「告警轰炸」。

## 5. 跨部门协作协议：任务单（ticket）

Agent 间**禁止**直接读写对方部门记忆（白名单除外），一切协作走显式任务单：

```
任务单生命周期：发起 → A0 仲裁派发 → 接收方认领 → 执行 → 结果回填 → 发起方验收 → 关闭
存储：org/tickets（PG 表），状态机：open/assigned/doing/done/rejected
```

**业务闭环实例（用现有业务串起来）**：

```
TR1 交易执行 → 成交/滑点写 agent/TR1/feedback
  → ST1 复盘（读 trading 部门共享 feedback）发现因子失效
    → 提任务单 T-xxx「重训动量因子」→ A0 派发
      → DEV1 拉代码优化 / DEV2 重训模型 → 新版本登记 domain（版本化）
        → ST1 验证 → 交易部次日自动用新版本 → 闭环
```

**A0 在协作中的角色**：只做仲裁与派发，不越俎代庖执行——避免总管成为瓶颈；P0 异常时 A0 有权直接暂停部门任务（熔断权）。

## 6. 记忆权限演进（K-STOCK-003 §5.2 的泛化）

| 变更 | K-STOCK-003 | K-ORG-001 |
|---|---|---|
| 二级语义 | `team`（临时团队） | `dept`（常设部门）+ `team`（部门内项目组，如 alpha）→ **五级**：`domain/dept/team/agent/type`，team 可缺省 |
| A0 读权限 | — | 全部门 `team` 级可读（汇报需要）；`agent` 级**默认不可读**，仅 P0 异常调查时经老田授权读，授权留审计 |
| A0 写权限 | — | `org/daily`（日报）、`org/tickets`（任务单）、domain 级标准（与老田共同治理） |
| 部门间 | `share/*` 白名单 | 不变；默认关闭，开通须任务单理由登记 |

**防扩容混乱的锚点不变**：所有权限只存在于注册表 `memory_grants` 字段，运行时校验 + apply 时重叠写权限报错——组织变大不改变管控机制。

## 7. 注册表扩展（org 段）

```yaml
# registry/org.yaml
org: laotian_ai
report_to: human                      # 老田
chief:
  agent_id: A0
  role_profile: chief_of_staff        # 人设存角色配置表（对齐菜鸟 ai_chat_role 模式）
  llm_binding: glm-4.7                # 总管用强模型，部门员工按需配
departments:
  - dept: dev
    lead: null                        # 可选，null = A0 直管
    charter: 拉代码/优化代码/训练模型
    agents: [DEV1, DEV2]
  - dept: strategy
    agents: [ST1]
    sub_teams: [alpha]                # K-STOCK 执行拓扑整体挂载
  - dept: trading
    agents: [TR1]
  - dept: marketing
    status: planned                   # 结构预留，不实例化
reporting:
  daily_push: "18:00"                # 日报通道
  event_bus: redis://6379/org_events # 事件通道
  severity: {P0: immediate, P1: 1h, P2: daily}
```

执行拓扑注册表（K-STOCK-003 §5.1）原样保留，新增 `dept` 归属字段即可——**两个注册表，一个 apply 命令，同一套校验**。

## 8. 平台化路线（多元架构）

| 阶段 | 内容 | 前置 |
|---|---|---|
| P1 | A0 + 三部门（dev/strategy/trading）最小组织 + 日报通道；alpha 团队挂入策略部 | K-STOCK S1 PoC 完成后 |
| P2 | 事件通道 + 任务单闭环（TR1→ST1→DEV 闭环实跑一次） | P1 稳定跑 1 周 |
| P3 | 市场部实例化（视频/宣发 Agent）；问询通道交互化 | 有真实宣发需求时 |
| P4 | Hermes 个人助理线挂载为平行 org（org 隔离、domain 可选择性共享）——对齐「集成超级助理」愿景 | Hermes WebUI 成熟后 |

**平台定位**：这套 org 框架不绑定选股业务——它就是「老田的 AI 公司」的编制表，任何新业务线（量化之外的视频、宣发、个人助理）都是加部门，不是改平台。

## 9. 风险登记

| 编号 | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| R1 | A0 成为单点瓶颈（所有汇报/仲裁挤一个入口） | P1 | A0 只做聚合与路由不做执行；事件通道允许 P0 直推老田（A0 挂了也能收到）；A0 本身可降级为规则路由 |
| R2 | token 成本随组织膨胀 | P2 | 部门主管默认不设；日报靠记忆提炼不靠重跑上下文；部门员工用 qwen3.5:9b，A0 用 qwen3.5:35b 或云端强模型（2026-10-08 本地实测在库） |
| R3 | 汇报失真（部门报喜不报忧） | P2 | 日报数据源固定为 `decision/feedback` 记忆（客观记录），A0 可抽查原始事件对账 |
| R4 | 任务单死循环（A 派 B、B 派 A） | P2 | 任务单有向：发起方/接收方不可互逆重复；A0 检测循环即熔断并上报 |
| R5 | 与 K-STOCK S1 PoC 的时序耦合 | P1 | 本设计不阻塞 PoC——P1 阶段才需要 org 层，S1 先跑纯执行拓扑 |

## 11. AIGC 松耦合扩展评估（K-ORG-002 追加，回应老田「未来不停增加 AIGC」）

### 11.1 平台已具备的能力（骨架不动，直接挂）

| 平台机制 | 对 AIGC Agent 的适配 |
|---|---|
| Agent 注册制 | 加 MKT1（视频）/MKT2（文案）= 注册表加一段 YAML，§6 扩容演练已验证零代码 |
| namespace 记忆分配 | `agent/MKT1/artifact`、`dept/marketing/*` 照用，规则与业务无关 |
| 任务单协作 | 「策略部周报 → 市场部做宣发视频」= 现成跨部门任务单流 |
| 汇报三通道 / 人设配置化 | 与部门类型无关；文案风格、脚本作者人设存角色配置表 |
| llm_binding 路由 | 已支持任意 provider（本地 ollama/xxx、云端 cloud/xxx、专用图像/视频模型各挂各的） |

### 11.2 三个补件（AIGC 特有，各 ~50-100 行，P3 市场部实例化前落地）

1. **异步工具契约**：视频渲染是分钟~小时级长任务，不能像查 K 线一样同步等待 → 工具层加异步模式：提交任务 → 拿 task_id → 回调/轮询 → 产出落盘 → 记忆存**引用 + 文本摘要**。
2. **GPU 资源配额**：DEV2 训练、选股推理、MKT 渲染抢同一块 GPU → 注册表加 `resource_quota` 字段（如 `{gpu_mem: 8GB, priority: low}`），执行器按配额排队。
3. **artifact 产出契约**：产出从「结构化 JSON」扩展到「媒体文件」→ 统一约定：**本体落文件系统/OSS，元数据 + 文本摘要入 Qdrant**（payload 加 `artifact_path/mime/duration` 字段），向量库永不存媒体本体。

### 11.3 新模态接入四步验收（松耦合的检验标准）

```
① 注册表加 agent（一段 YAML）
② 工具注册（异步工具走 11.2-1 契约）
③ 记忆权限自动生效（namespace 规则通用，零配置）
④ 产出声明（JSON 决策 or artifact 模式）
—— 全程平台代码零改动即为合格
```
