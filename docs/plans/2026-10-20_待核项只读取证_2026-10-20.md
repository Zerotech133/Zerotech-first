### 2.3 不可判定时的处置建议

**"外部请求到飞书事件回调，走哪个端口 / 经不经过 nginx / 有没有鉴权"——要分成两条完全不同的链路，不能一句话答：**

| 链路 | 入口 | 端口 | 经 nginx？ | 鉴权 | 证据强度 |
|---|---|---|---|---|---|

### 6.2 取证中发现的、与既有文档记载不一致之处

1. **访问日志不能证明 key 状态（新发现的取证陷阱）**。`Handler.log_message`（`portal_api.py:646-659`）对所有 Handler 实例无条件写 `C:\Temp\portal_api_access.log`，而 4 个测试文件用真实 `HTTPServer(("127.0.0.1",0), portal_api.Handler)` 起服务。日志里 `list` 的 `401×64` 与 `200×110` 是**生产与测试混写**，16:01/16:15/16:16 那几批 401 极可能来自测试用例。**任何据此外推"生产 key 已开"的结论都不成立。**
2. **环境注入通道不止启动脚本**。检查清单 N1 的"当前掌握"只写了"仓库与启动脚本内无配置引用"，漏掉了 `api_common._load_cainiao_env()`（`:656-669`）——它会以 `setdefault` 把 `C:\Temp\cainiao_oauth2.env` 的**任意** KEY 注入 `os.environ`。当前该文件只有 3 个 `CAINIAO_*` 键（实证），所以本轮结论不变；但这条通道是"运维手工开闸"的现成后门，且**必须重启才生效**。文档应补记。
3. **8097 的宿主不是 SYSTEM**。`ops/launch_push_admin.py:21,46-50` 的注释写"8097 宿主是 SYSTEM 计划任务，用户终端无权 taskkill"。实测 `AI工作站推送中台守护8097` 的 Principal = `t` / `S4U` / `Limited`（非 SYSTEM）。"无权终止"的现象可能来自 S4U 令牌 + Session 0，而非 SYSTEM；注释的因果解释已过期。同理 `portal/start_portal_api.ps1:1` 自称"SYSTEM-safe path"，实际也是 `t`/S4U。
4. **8787 不是 `start_hermes_next.py` 拉起的**。派工单写"8787（邓芝 WebUI）… 检查 `C:/aios/Hermes/start_hermes_next.py`"，但该脚本**硬编码 `HERMES_WEBUI_PORT="8788"`**（`:62`），而 8787 与 8788 **同时在监听**（PID 15232 / 22472）。8787 属 `start_hermes_bg.py` 家族（`HermesWebUI-Guard`，该脚本 `:5` 明写 8787）。派工单把两个进程混成了一个。
5. **nginx 里没有 `/feishu` 映射，也没有 catch-all 反代**。`portal/nginx.conf` 全文 97 条 `location`、只有 `listen 80`、`feishu|inbound|bot` 0 命中，且 `root /usr/share/nginx/html` 静态根无 `location /` 兜底。因此 `POST /feishu/event`（卡片回调）**按本仓配置不进 8091**。若飞书后台真配了回调地址，那背后还有一条本仓不可见的通道——这条要在门禁 C（生产部署）里补上，否则线上卡片按钮点了没反应会被误判成"订阅功能坏了"。
6. **"落盘≠生效"再添一例实证**。15:28:56/57 日志里 `/api/subscription/status`、`/api/subscription/list` 均返 **404**，而磁盘 15:03 的代码里这两条路由已存在（`:4003`/`:4027`）——因为当时在役的是 06:45 的旧进程。同时 `portal_api_task.log` 显示 15:25~15:55 连续 7 次 `skip: 8091 already serving`，最后一次 16:00:17 才真正 `starting`。**只看"任务跑了/退出码 0"会得到完全错误的结论。**
7. **N4 的 89 有口径歧义**。89 是条目数，`/org` 在 `quant` 与 `ops` 各挂一次，唯一路由 88。检查清单/就绪自查若一处写"89 入口"、另一处写"88 页面"，会再次制造假冲突。
