## 1. "一件成果"的六条硬条件（任一不满足 = 空壳）

| # | 条件 | 证据形态（可检查） | 空壳反例 |
|---|---|---|---|
| 1 | **真实输入** | 老田原话/文件/需求记录（item.created.source_text） | 系统自造一个示例需求 |
| 2 | **可检查产物** | 文件/文档/报告/代码版本 + sha256 + 版本链 | 只有页面截图、没有产物 |
| 3 | **本人反馈** | 老田 verdict 或反馈原文（user actor） | AI 自己写"用户已确认" |
| 4 | **下一版本或明确不改** | v2 产物 + supersedes + 修订理由；或"接受，不改"的明确回执 | 一版到底、无修订记录 |
| 5 | **证据与来源** | citations（来源面/类型/置信度/指纹）+ 各面必备证据 | 引用空、或推断当事实 |
| 6 | **授权边界** | 对应动作的 grant/签准记录；越界=BLOCKED | 无授权就执行/外发 |

**另加一条时间条件**：每件成果老田的参与时间 **≤30 分钟**（提需求/确认/试用/反馈），
且必须记录**真实开始、结束、所做动作**（时间戳来自页面/账本，不靠估计）；超时视为体验不达标，
计入成果缺陷，不得用"约 20 分钟"填合格。否则说明产品在要求用户做工程，不是"释放能力"。

## 2. 四件成果定义（首件候选可由老田替换，模板不变）
> 「v2 要求」= 必须有 v2，或本人明确给出「接受不改」回执（二者必有其一）；后者同样记录在事件账本。


### 2.1 产品与研发（software）

| 项 | 定义 |
|---|---|
| **首件候选** | 把一句真实需求做成**可在隔离环境打开的单页原型**。建议首件：把 `09_产品基线` 的"目标—事项—成果"做成一个可点击的三级关系小页（产品自用 + 可给朋友看） |
| **真实输入** | 老田一句话需求（记录原话）→ 澄清 2–4 问 → 需求 v1（目标/边界/成功标准） |
| **团队动作** | 推荐卡（三角色来源可辨）→ 本人收窄授权（隔离 4 动作）→ 工单认领 → 隔离生成 → 浏览器测试 → 本人试用 |
| **交付物** | 需求 v1；推荐卡 c1；授权 GRT；工单 WO；产物 a1（index.html + SHA256SUMS）；测试回执；本人 verdict；**a2（按反馈修订）** |
| **验收** | 老田打开、接受或指出"这里改"；a2 体现该修改；测试回执可复现；无生产/外发 |
| **证据** | 事件账本（v1 判据器 G0–G7）+ 产物指纹 + 测试输出 |
| **禁止** | 发布到现网、改共享仓、接真实数据 |
| **v2 要求** | 至少 1 条本人反馈 → a2；旧版本保留、supersedes 串链 |

### 2.2 商业与融资（business_plan）

| 项 | 定义 |
|---|---|
| **首件候选** | 围绕零界自己写 **BP v1**：目标用户、问题、产品（四工作面/三级关系）、商业假设、竞争、里程碑；随后依新证据修订 **BP v2** |
| **真实输入** | 老田对事业目标的原话 + 现有战略材料（ROADMAP、基线、审计） |
| **团队动作** | 主张逐条标注证据等级（primary/secondary/assumption）→ 假设台账 → BP v1 → **等待 G3 的老田审核反馈（X1）** → 修订理由 → BP v2（diff） |
| **交付物** | BP v1（md/pdf 草稿）+ 假设台账 + citations + **BP v2 + 修订说明** |
| **验收** | 老田能指出 ≥1 处要改；v2 体现改动；假设状态有更新（≥1 条 hypothesis→validated/falsified 或新增证据）；**未对外发送** |
| **证据** | 每条数字/结论有来源或明确标"假设/待验证"；引用符合三值规则 |
| **禁止** | 编造客户访谈、市场规模数据；对外发送/融资承诺 |
| **v2 要求** | v2 至少新增 1 条新证据（**首版允许且仅允许"老田审核反馈"**）+ 修改 ≥1 个假设状态；审核反馈只能使**表达/理解类**假设 `falsified` 或保持 `hypothesis`，**不得**让市场/付费类假设升 `validated`（那需要 primary/secondary 证据，等 C/D 阶段） |

> 诚实提醒：首版没有真实客户访谈时，BP 里所有市场判断必须标 `assumption/secondary`，
> 不得写"已验证"。这是"能不能用"的分水岭，也是第 2 期（真实客户）的输入。

### 2.3 内容与增长（content）

| 项 | 定义 |
|---|---|
| **首件候选** | 从产品基线/研发进展提炼 1 个选题（建议：《一个人怎么用 AI 团队把想法做成事业？》），出**草稿 v1 + 审核意见 + 发布计划**；不发布 |
| **真实输入** | 老田对目标读者的判断 + 产品基线（09）作为素材 + 已有 gzh/自媒体资产 |
| **团队动作** | 选题依据（为什么现在写、给谁看）→ 大纲 → 草稿 v1 → 审核（事实/引用/风险）→ 老田审 → 草稿 v2 → 发布计划（时间/渠道/授权待签） |
| **交付物** | 选题卡；草稿 v1；审核记录；**草稿 v2**；发布计划（未执行） |
| **验收** | 老田给出"可发/要改/不发"；v2 体现意见；发布动作 **BLOCKED**（未授权） |
| **证据** | 文中事实/数字的 citations；引用自己的产品结论要标来源 |
| **禁止** | 自动发布、代发、批量投放；未经授权导出 |
| **v2 要求** | 至少 1 轮老田审核意见 → v2；保留 v1 与审核记录 |

### 2.4 量化与投资研究（research）

| 项 | 定义 |
|---|---|
| **首件候选** | 对一条真实量化想法（数据只用现有本地只读数据）做：数据来源 manifest → 回测/模拟 → 风险结论；**不产生任何真实交易指令** |
| **真实输入** | 老田一句研究问题（例：某信号/因子在样本窗口内的表现与风险） |
| **团队动作** | 数据快照与 as_of → 方法说明 → 回测/模拟运行 → 风险分层结论（数据/方法/执行风险）→ 老田看图/报告 → 修订 v2（窗口/参数/口径） |
| **交付物** | 研究报告 v1；数据 manifest（来源/指纹/as_of）；结果文件；风险结论；**v2 + 修订理由** |
| **验收** | 数据可回溯；结论与数据一致（不夸大）；风险分层清楚；无真实交易/资金动作 |
| **证据** | 数据指纹 + 运行命令 + 输出文件；引用外部数据/结论须带来源 |
| **禁止** | 真实交易、资金操作、改生产数据根、把模拟说成"实盘验证" |
| **v2 要求** | 至少 1 条本人/反证驱动的修订（参数/窗口/结论），旧结果保留 |

## 3. 跨面关联（必须证明"同一支团队、同一本账"）

B 阶段至少 2 条，字段与判据见 `04b` X1/X2。

### 3.1 链 A：本人审核反馈 → BP 修订（hypothesis 链，v3.1 修正）

```text
内容面：草稿 v1 完成 → 老田审核并给出真实意见（例："客户最在意成本结构"这句话说过了）
        → citation：source_surface=content, source_kind=conversation,
          confidence=hypothesis, source_ref=CNT-草稿v1, source_sha256=…
   → BP 面：引用该审核反馈更新"客户画像/表达"假设（状态仍 hypothesis，新增 evidence_ref）
   → BP v2 修订理由写明：为什么改、依据哪条反馈、置信度仍为假设
判定：v2 diff 可指向该 citation；假设未被升级为 validated；
      表述只能是"产品表达或客户理解需调整"，不得写成"市场需求已验证"。
```

> **首版没有"读者反馈"**：未获外发授权、内容尚未发布，任何"读者/客户反馈"都是编造（判 FAIL）。
> 真实读者反馈只能在取得发布授权、实际发布并收到后，进入下一版（C/D 阶段）。
> 依赖：**BP v2 的跨面验收必须等 G3 的真实审核反馈出现**，G2 先产 BP v1，不得抢跑。

### 3.2 链 B：研究结论 → 第二产品事项（fact 链，不倒填）

```text
研究面（G4）：回测结论（citation: source_kind=data, confidence=fact, 附样本窗口/局限）
   → 在同一 Goal 下**新建事项 G4X**（why_now 引用该研究 outcome，attempt_no 从账本读取）
   → 由 G1 的软件能力产出 G4X 的隔离小页（第二个 item，不合并、不倒填）
判定：G4X 的 why_now 引用字段指向研究 outcome；页面显示来源与局限；
      不把"样本内"说成"实盘有效"。
```

> **不得回填**：两日窗口内 G1 的软件首件用老田的真实需求原话做 `why_now`，
> 与 G4 研究结果无关；G4 完成后另建 G4X，时间顺序与引用来源都真实。
> 这同时给出第二条跨面关联，且不增加两日窗口对量化面的依赖。

> 可选链 C：BP 的假设 → 研究面验证 → 回到 BP 更新假设状态（hypothesis→validated/falsified）。
> 三条链共用同一 citation 规则：**推断不得升级、同源不得升级、冲突不选边**。

## 4. B 阶段出口判据（硬）

| # | 判据 | 通过条件 | 工具/证据 |
|---|---|---|---|
| B-1 | 四件成果齐全 | 四类 outcome 各 ≥1 件，类型与 `item.outcome_kind` 一致 | `os_goal_check` G8 |
| B-2 | 每件有 v1→v2 | 每件至少 1 轮本人反馈 + v2（或明确"接受不改"回执） | 事件账本 verdict + supersedes |
| B-3 | 跨面关联 ≥2 | X1（仅本人审核反馈）+ X2（仅 G4X 链）各 1 条，引用字段齐全、无升级违规 | citation 校验 |
| B-4 | 目标锚定 | 每件都挂在同一 Goal 下；attempt_no/why_now 可读 | `os_goal_check` G-1 |
| B-5 | 边界未破 | 无生产发布/外发/真实交易/真实账本写入；越界尝试被拒并留痕 | 负例 + 拒绝日志 |
| B-6 | 本人逐件验收 | 老田对每件各一句"接受/返工"；自动 PASS 不算 | verdict（user actor） |

**任一不过 → B 不通过**，只能报"已建 N/4 面 + 缺口清单"。

## 6. 空壳识别清单（评审时逐条问）

1. 这件成果的**输入原话**在哪？是用户说的还是系统编的？
2. 产物**版本与指纹**在哪？能下载/打开/复现吗？
3. 用户的**反馈原话**在哪？是谁的 actor？
4. **v2 改了什么、为什么改**？旧版本还在吗？
5. 每条引用有**来源面/类型/置信度/指纹**吗？有没有推断被当事实？
6. 动作有**授权记录**吗？越界的尝试被拒了吗？
7. 这件事是否**只用了 30 分钟**以内的用户时间？
