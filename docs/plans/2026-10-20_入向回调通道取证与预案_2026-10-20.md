## 三、B1 阻塞项确认或推翻（对照 N-D 结论）

**结论：确认，且比 N-D/B1 原表述更严重、但机理不同。**

检查清单 B1 原文（`docs/plans/2026-10-20_商业化上线检查清单_v0.md:253`）：
> 卡片回调无对外通道：`POST /feishu/event` 在 `portal_api.py:2673` 存在，但 nginx 97 条 location 中 `feishu|inbound|bot` 零命中、只有 `listen 80`、无 catch-all 反代。若飞书后台配了回调，背后有一条本仓不可见的通道；上线后「点按钮没反应」会被误判成订阅功能故障。

本工位三处增补/修正：

1. **「不可见通道」假设被削弱**：8080（nginx）与 80（IIS）实测均 404，宿主上不存在任何能到达 8091 `/feishu/event` 的对外通道。若飞书后台真配了 Webhook，它当前必然握手失败（飞书侧应有配置告警），而不是「背后有条看不见的通道在偷偷工作」。
2. **真正的阻塞在 WS 链上**：买点订阅卡按钮 `{"act":"subscribe_buypoint"}`（`quant_backtest/subscribe_action.py:106-110`）的唯一执行链是 8091 HTTP 回调（`api_misc.py:703-733` → `subscribe_action.subscribe_from_card`）。而 card.action.trigger 若走 WS 长连接到达 bot，`feishu_bot_ws.py:823-829` 会转 `card_actions.dispatch("subscribe_buypoint")`，其结局是（`portal/card_actions.py:313-316`，实证）：
   ```python
   # 已注册但尚未迁入统一分发（老链自行处理）
   log_event(action_id, who=who, result="dispatch: 老链动作，无统一 handler")
   return True, "已注册（%s），由老链处理" % info["handler"]
   ```
   且注册表自注（`card_actions.py:70-72`，实证）：`"subscribe_buypoint": ("订阅买点", "量化订阅", "card", "8091 HTTP 老链")`。**即：无论飞书后台配长连接（WS 收到但无 handler）还是 Webhook（HTTP 不可达），订阅买点按钮「点了没反应」在当前代码+配置下是必然结果**，与是否打通 nginx 无关。这与 B1 原文「误判成订阅功能故障」的担忧方向一致，但根因是**双链都断在各自末端**，不只是 nginx 缺映射。
3. **「listen 80」的表述陷阱**（详见第六节不一致项 1）：`nginx.conf:11` 的 `listen 80` 是容器内端口，宿主侧是 8080；宿主 80 是 IIS。排查时打 `http://<内网IP>/feishu/event` 会得到 IIS 的 404，误以为「试过了，不通，问题在别处」。

## 五、客户面身份入口风险

### 5.1 现状（实证）

`portal/static/my_subscription.html` 的 open_id 获取路径：

```javascript
// my_subscription.html:337-339
// URL 参数优先：页面带 ?open_id= 时直接进入查询态
const qOid=new URLSearchParams(location.search).get('open_id');
if(qOid){$('oid').value=qOid;}
```

且查询后回写地址栏（:325-332 `setOid` → `history.replaceState` 把 `?open_id=ou_xxx` 固化进 URL），每 60 秒轮询 `/api/subscription/status?open_id=...`（:307, :341）。页面文案自认（:89-90）：「直接用带 `?open_id=` 参数的链接打开本页……飞书内打开将自动带上你的身份（M3 接 OAuth，本期可用 ?open_id= 查询）」。

**访问日志明文落盘 open_id（实证）**：`portal_api.py:657-659` 的 `log_message` 原样写 `fmt % args`，BaseHTTPRequestHandler 的 requestline 含完整 query：

```
$ grep -an "open_id=" /c/Temp/portal_api_access.log | head -3 | cut -c1-200
68959:2026-10-20 15:28:56 127.0.0.1 "GET /api/subscription/status?open_id=probe HTTP/1.1" 404 -
```

（该行是探测值 `probe`，但机制已证：**任何真实 `?open_id=ou_xxx` 访问都会把明文 open_id 写进 `C:\Temp\portal_api_access.log`**，日志混写生产与测试、无脱敏。）

### 5.2 风险评估

- **链接转发＝身份泄露**：客户把 `/my-subscription?open_id=ou_xxx` 链接转给他人（或经剪贴板/截图/群聊外泄），收到者可直接查看该 open_id 的订阅档位、有效期、当日额度余量，且无任何时效/绑定校验。缓解面：响应字段已最小化、open_id 仅回掩码（`my_subscription.html:72,114`，实证），且 open_id 是应用级标识、不可跨应用冒用——所以泄露的是「查看权」，不是「支付权」。
- **风险定级**：
  - **M3 前＝中低**：页面只读、字段最小化、无变更按钮，泄露后果限于「看别人的档位与额度」。
  - **M3 后＝高**：订阅闸切 enforce（`inbound_gateway.py:664-666` 注释明写 M3 后切 enforce 需另批）、收银台变更按钮上线后，若 actor 口径仍是「页面传入 open_id」，则拿到链接＝拿到身份＝可代点订阅/退订按钮。OAuth 设计稿 §三也把按钮回写 actor 定为 open_id（`docs/plans/2026-10-20_订阅OAuth免登录设计_v0.md`）。
- **缓和方案**（引用不重写）：`docs/plans/2026-10-20_订阅OAuth免登录设计_v0.md`（H-C 工位）已给全链：飞书自建应用网页免登授权码模式 → 服务端 code 换 token 取 open_id → 中台自签 HttpOnly Cookie 会话；open_id 与订阅账本 owner、订阅闸主体同口径直通，不建第二账。补充两点本工位增量观察：
  1. 设计稿写「按钮回写走 W43 唯一入口」——W43 是 bot 进程内函数、无监听端口（二.3），**页面回写要落进它还缺一条 HTTP→进程内函数的桥，该桥当前不存在**，设计稿此句是意图不是现状；
  2. 免登落地前，至少应把 `?open_id=` 从访问日志里摘掉（portal_api 侧对 status 端点做 query 脱敏），否则设计稿 §五的安全边界守住了浏览器面、守不住日志面。
- **建议时序**：M3 收银台上线**之前**必须完成 OAuth 免登施工（设计稿自带「M3 前置预研」定位），`?open_id=` 仅作 M3 前过渡；若 OAuth 工期风险大，退而求其次先上短期 ticket（inbound_gateway 已有 `new_ticket()` 机制可参照口径）替换 URL 明文 open_id。分界线就画在 M3：**M3 后保留 `?open_id=` 直查＝不可接受**。

### 取证中发现的、与既有文档记载不一致之处（逐条）

1. **「listen 80」是容器内端口，不是宿主端口**。检查清单 B1 与 N-D 引用 `nginx.conf` "只有 listen 80" 会误导排查打到宿主 80 端口——实测宿主 80 是 **IIS 10.0**（curl `server: Microsoft-IIS/10.0`），本仓 nginx 在宿主侧映射为 8080（`portal/start_portal_nginx.ps1:10` `$Port = "8080:80"`，实证）。两份文档均未记录宿主映射关系。
2. **B1 的根因描述不完整**。原文把问题归为「无对外通道 + 若配了回调则背后有不可见通道」；实测证明宿主上不存在任何可达通道（8080/80 均 404），且真正的功能缺口在 WS 链：`subscribe_buypoint` 注册表项自注「8091 HTTP 老链」、dispatch 对其返回「老链动作，无统一 handler」（`card_actions.py:70-72, 313-316`）——即**打通 nginx 只救活 HTTP 链，按钮在 WS 链上仍是死的**。任何「加了 location 就修好了」的推断都不成立，handler 迁移是独立工程项。
3. **N1「两把 key 推断为关闭」获得新的独立行为级旁证**。N-D 只能从配置四链间接推断；本工位空探测未签名请求得 200（若 key 已配应 403），行为级证明运行中 8091 未配 Encrypt Key。
4. **OAuth 免登设计稿 §三「按钮回写走 W43 唯一入口」与现状有落差**。W43 无监听端口（N-D 5.2 关键纠正，本工位复核一致），页面回写所需的 HTTP→函数桥不存在，设计稿未标注这是待建桥。
5. **客户面身份的日志泄露面两份文档均未记**。`my_subscription.html` 与检查清单都只讨论了 URL 转发风险；本工位实证 `portal_api_access.log` 原样落盘 `?open_id=` 明文（68959 行样例），泄露面比「链接转发」多一条持久化通道。
6. **`my_subscription.html:90` 页面自述「M3 接 OAuth」**与 OAuth 设计稿「M3 前置预研、未实施」口径一致，但设计稿 v0 起草于同一日，页面文案已把未来时态写成承诺——上线检查清单若引用页面文案会得出「OAuth 已在排期=已解决」的误读，应改为引用设计稿状态（v0 待议定/待批准）。
