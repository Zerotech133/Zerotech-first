## 0.1 v1.1 最优方案决策（2026-11-10，覆盖下文冲突项）

**结论：方向对，但原计划四处不够优；按本节执行，不再另开决策会。**

### 决策 1：schema 只冻结“只读投影 v0.1”，不冻结完整 §4

M1 是只读投影，不是领域数据库。今天只冻结 `workline_view v0.1` 的 10 个字段：

```text
id, message_type, sender.identity, target.display, state,
template.id, intent.title, intent.summary, intent.buttons[], trace_id
```

- 其余字段（source/sla/owner/evidence/priority）允许 `extra`，M1 不落库、不校验全部字段；
- 页面与 API 用同一投影；模板/目标数据来自现有账本；
- 等 M3 真正产生写操作时，再升级为 `workline v1.0` 领域模型并做迁移；
- **不要因为“schema 没全定”卡住 M1**。

### 决策 2：SLA 不用“消息类型单维”，改用“优先级 × 类型”

类型只决定交互（消息/确认/交付）；时限由优先级决定，且可配置，不写死在页面。

| 优先级 | 确认类 ack / 升级 | 双向交付回执 / 升级 | 消息类失败告警 |
|---|---|---|---|
| P0（资金/客户/交易） | 15m / 30m | 5m / 15m | 5m |
| P1（日常运营） | 2h / 4h | 10m / 30m | 15m |
| P2（资讯/低风险） | 8h / 次工作日 | 30m / 2h | 1h |

- 页面只展示“要求 + 截止时间 + 超时后果”，不在前端算 SLA；
- M0 只确认这张默认表，后续放配置/策略表；
- 原 §5 的单一时限作废，以上表为准。

### 决策 3：`/feishu/messages` 独立页面，复用 F17 壳层，不塞进 F17 mock SPA

## 1. 目标与非目标

### 1.1 目标

让运维/值班人员在一个页面上回答五个问题：

1. 这条消息**谁发给谁**？
2. 它是**消息类 / 确认类 / 双向交付类**中的哪一种？
3. 发出去**长什么样**，按钮是否正常？
4. **能不能发**，如果不能，卡在哪一步？
5. 卡住后**谁来做、怎么做、做完怎么确认**？

### 1.2 非目标（本计划不做）

- 不在本工作台里直接调用飞书 OpenAPI；
- 不替代 8097 的发送/重试/死信逻辑；
- 不新建第二套决策台账；
- 不重写飞书卡片渲染引擎（M1 复用现有模板/卡片构建器）；
- 不一次性改 `/m` 的 17 条生产路由；
- 不做小程序（H5 已足够；未来只做 web-view 壳）；
- 不在 M1 开放任何写操作或测试发送。

## 2. 用户与场景

| 角色 | 场景 | 需要看到 | 可做的动作（M1） |
|---|---|---|---|
| 老田 / 产品 owner | “今天有哪些消息要发/要确认” | 工作线条、风险、待确认 | 查看、预览、发起预检 |

| 审批人 | “这条确认类该不该通过” | 卡片预览、影响范围、证据 | 查看（审批仍在决策台账） |

典型场景：

- 盘前晨报：消息类，发核心订阅组；预览卡片 → 预检 → 允许发送（M3 后）。
- 客户域订阅扩容：确认类，目标变更；预览按钮 → 预检 → 审批人确认 → 决策台账。
- 涨停复盘包：双向交付类；预览证据/按钮 → 预检发现机器人不在群 → 反向溯源 → 通知值班 → 修复后重发。
- 二买周度交付：双向交付类；查看回执 42/42，确认交付。

## 4. 工作线条模型（草案，M0 定稿）

### 4.1 对象

```yaml
workline:
  id: WL-YYYYMMDD-NNN
  source:                 # 从哪里来
    type: schedule|event|manual|incident
    ref: string           # 任务/事件/调度 id
    occurred_at: iso8601
  message_type: message|confirm|delivery
  sender:
    identity: notify|command|qa|exec|service
    bot_id: string
    display: string
  target:
    type: chat|user|customer_domain|subscription
    ref: string
    display: string
    member_count: int
  template:
    id: string
    version: string
    card_schema: string
  intent:
    title: string
    summary: string
    fields: [{label, value}]
    buttons: [{label, action, style, requires_signature}]
    deep_link: string
  state: draft|preview_ready|preflight_passed|preflight_blocked|
         approval_pending|approved|rejected|sending|sent|delivered|failed|closed
  owner: string           # 谁处理这条线条
  sla:
    receipt_required: bool
    ack_deadline: iso8601|null
    escalate_to: string|null
  trace_id: string
  created_at / updated_at: iso8601
```

### 4.2 预检结果

每个检查项固定返回：

```yaml
code: identity_in_target|target_in_allowlist|template_schema|button_manifest|
      callback_health|signature|quiet_window|quota|receipt_sla|evidence_present
status: pass|warn|block
detail: 一句人话
fix_hint: 一句人话（运维照做）
owner: OPS1|PM1|ARCH1|...
evidence_ref: 可选
```

### 4.3 反向链路

固定七段，失败必须定位到其中一段：

```text
1 数据源 → 2 消息意图 → 3 卡片生成 → 4 发送前检查
→ 5 审批/闸门 → 6 8097 发出 → 7 回执/点击
```

反向视图从第 7 段往第 1 段查；红色节点是阻断点，展示：

- 一句人话的“卡在哪”；
- 失败是谁的责任；
- 修复 3 步（不出现 schema/SLA/trace 等术语，技术细节折叠）；
- 通知值班 / 转工单（M1 只预览，M3 才写）。

## 5. 消息类型与回执 SLA（草案，M0 定稿）

| 类型 | 用途 | 允许按钮 | 回执 | 超时/升级（草案） |
|---|---|---|---|---|
| 消息类 | 简报、预警、通知 | 查看全文/深链 | 不要求确认；有 message_id | 失败 5 分钟告警；不升级 |
| 确认类 | 审批、目标变更、二次确认 | 拒绝/通过 | 必须有人确认；进决策台账 | 2 小时未确认提醒；4 小时升级到 owner |
| 双向交付类 | 文件/证据包/任务交付 | 查看证据/确认交付/补发 | 必须有点击/交付回执 | 10 分钟无回执告警；失败进死信；值班处理 |

**以上时限只是建议值，M0 由老田拍板；未拍板前 M1 只展示“回执要求”，不写死 SLA 数字。**

## 6. 技术方案

### 6.1 路由与页面

- 页面：`/feishu/messages`（F17 壳层内；不新建第二套登录）。
- 静态页：`portal/feishu_messages.html` + `portal/static/feishu_messages/{app.js,styles.css}`。
- API 前缀：`/api/feishu/messages/`（8091 BFF）。
- 鉴权：nginx `auth_request /_auth_guard`；页面 401 → 登录；API 401 → JSON。
- 入口：F17 左侧导航“消息工作台”；不在 `/m` 加新 tab（M4 再接 H5 深链）。

### 6.2 后端

新增 `portal/api_feishu_messages.py`（只读聚合），`portal_api.py` 只加 early branch（不扩 handler 大文件）：

```text
GET  /api/feishu/messages/worklines?status=&type=
GET  /api/feishu/messages/worklines/{id}
POST /api/feishu/messages/preview
POST /api/feishu/messages/preflight
GET  /api/feishu/messages/incidents/{id}
```

M1 没有 `/send`、`/test-send`、`/notify` 写接口。
M2 才加 `/test-send`（测试群，显式 flag）；M3 才加真实发送/通知工单。

### 6.3 数据映射

| 视图 | 数据源 | 说明 |
|---|---|---|
| 工作线条列表 | `push_flow.jsonl` + `schedule.json` + `dead_letters.jsonl` | 按 trace/source 去重；deny 不算失败 |
| 发送预览 | 现有卡片模板/`feishu_push` 构建器 | 复用真实卡片渲染，不另写模板 |
| 预检结果 | 本地目标/身份/schema/回调配置 + 8097 健康 | M1 只读，不发送 |
| 审批状态 | `notification_decisions.sqlite3` | 只读；不写决策台账 |
| 回执/死信 | `push_flow` / `dead_letters` | 原始死信 vs 补达行分开 |
| 目标/订阅 | `subscriptions.json` / `receivers.json` / `targets` | 只读，ID 脱敏 |
| 模板清单 | 现有 card builder + 模板注册表 | M0 盘点，M1 版本化 |

### 6.4 安全与开关

- 只读默认：页面无写按钮，API 无写方法。
- 开关（环境/配置，默认关闭）：
  - `FEISHU_MSG_PREVIEW_ONLY=1`
  - `FEISHU_MSG_SEND_GATE=closed`
  - `FEISHU_MSG_TEST_SEND=off`
- 任何开关不为默认值，页面显示“安全配置异常”并拒绝渲染（原型已实现）。
- 真实发送只允许由 8097 + 决策闸执行；本工作台最多调用 8097 的“测试发送”接口（M2）。
- 数据脱敏：不返回完整 open_id/chat_id/消息正文；目标只显示前缀；技术 trace 折叠。
- 不新增公网端口；不重启 8091/8097；不碰其他会话 WIP。

### 6.5 可观测性

- 每条 workline 一个 `trace_id`，从 source → intent → preview → preflight → send → receipt 贯穿。
- 指标：workline 数、预检通过率、阻断原因 TopN、失败到修复时长、死信未补达、回执率。
- 告警：M1 只读不告警；M2 测试发送告警；M3 真实发送告警（通知值班/转工单）。
- 日志：结构化 JSONL，禁止把完整 ID/正文写入日志。
