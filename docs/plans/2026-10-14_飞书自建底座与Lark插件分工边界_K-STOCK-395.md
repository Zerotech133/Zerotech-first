## 2. 划界总原则

**不按 API 域划界，按「谁在场 + 是否计量」划界**：

1. **生产无人值守**（计划任务、watchdog、outbox、配额、活性监督）→ 只走 A/B/D。
2. **Agent 会话内人在场交互**（查询、读写个人资源、新能力探索、代办）→ 只走 C。
3. **新飞书能力需求**：先用 C（lark-openapi-explorer 探路 + skills 试跑）；确需无人值守后，才评审收编入 A/B（feishu_client 只改不扩精神，K-STOCK-394 重申）。

## 4. 五条红线（违者评审门拒收）

1. **C 禁止生产推送**：插件通道发的消息不进 push_flow 计量（商业化套餐失真）也不受 push_liveness 监督（漏发无人知）。临时通知可用，但产出须注明「会话通道·未计量」。
2. **C 禁止常驻**：event consume 必须 `--max-events N` / `--timeout D` 有界（lark-event 子进程契约）；常驻监听=B 判例（watchdog+stderr ready-marker+outbox）。**card.action.trigger 会话内调试 consume 与 9104 常驻共享 bus daemon，禁止起第二个同名 key consume——调试看 9104 日志，不抢订阅。**
3. **B 线 lark-cli 运行实体 = 仓库 `bin/lark-cli.exe`**（K-STOCK-396 已解耦落地）：新代码定位 lark-cli 必须走统一解析序（bin/ 优先），禁止绕过 bin/ 直连插件目录路径；bin/ 副本刷新须带工单号并复跑守卫测试；缺失时晨检 [4.6] 报警，从插件目录拷回即恢复（解析链自动回退插件扫描，产线不断链）。
4. **身份不混用**：自建代码禁止以 user 身份调 lark-cli（B 全部 USER_ACCESS_TOKEN="" 判例）；C 的 user token 由 lark-cli 自管，自建代码禁止读取。user 身份能碰个人日历/云盘/邮箱，泄漏面大于 bot。
5. **写生产资源（家人群/正式文档/生产 Base 表）**：C 通道必须经用户显式确认（lark-shared 安全规则退出码 10 门禁本身即此语义）；A/B 走既有 outbox/白名单/操作留痕链，禁止新增裸写。
