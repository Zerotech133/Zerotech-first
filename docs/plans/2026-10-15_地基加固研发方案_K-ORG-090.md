## 一、G1 记忆回注（P0，半天）

**改什么**：`_persona()` 加第 7 通道——岗卡 `memory.decision.recent` 最近 3 条摘要注入 system prompt，让岗位「记得自己做过什么判断」。

**实现**：
- BUNDLE 岗卡 memory.recent 结构已实测（ts/event/desc）；取 `desc` 非空的最近 3 条，格式 `## 本岗近期判断（memory 回注·K-ORG-090）\n- [MM-DD] desc`；
- desc 超 60 字截断（防膨胀）；字段缺失/为空静默跳过（fail-open，复用 T1 模式）；
- **预算**：3 条 ≤150 tokens，超了只取 2 条再超取 1 条。

**验收**：QA1/DEV1 persona 含「近期判断」段且 ≤150 tokens；29 岗批量冒烟无异常；memory 为空岗（新岗）不注入不报错。

**回退**：_persona() 删一段拼接即可。

## 二、G2 通道自动降级（P0，1 天）

**改什么**：产码调用失败自动级联 anthropic→cloud→ollama，通道健康计数落盘，判读卡可见。

**实现**：
- 新增 `chat_auto(agent_id, task)`：按 `["anthropic", "cloud", "ollama"]` 顺序尝试（GPT-6/Claude CLI 因密钥/CLI 依赖不进默认链，env `CODER_CHAIN` 可覆盖）；捕获网络异常/空回/超时三类失败即降下一通道；
- 每次尝试落 `portal/data/llm_health.jsonl`（ts/agent/通道/结果/耗时）；
- `org_supervision` 新增 `check_llm_health()`：读 24h 健康 jsonl，某通道连续失败 ≥3 次且已降级=黄灯提示，全链失败=红灯；
- devtask/e2e 产码入口改调 chat_auto（行为面：产码产物不变，仅容错增强）。

**验收**：mock anthropic 抛异常→cloud 接管出活；健康 jsonl 有降级痕迹；判读卡出现「通道健康」段。

**回退**：入口改回原 chat 函数（单点）。

## 三、G3 usage 持久台账（P1，半天）

**改什么**：五通道统一记账，花销从黑盒变账本。

**实现**：
- 统一封装 `_log_usage(agent_id, channel, task_label, in_tok, out_tok, elapsed)`，落 `portal/data/llm_usage.jsonl`（ts/agent/channel/label/in_tok/out_tok/elapsed）；
- 接线点：chat_openai/chat_anthropic/chat_cloud 已解析 usage 字段的直接接；chat(Ollama) 与 chat_claude 无 usage 就记字符数（in_tok/out_tok 置 0、chars 字段兜底）；
- 参照 Hermes metering 的 begin/record/end 形状但我们落盘（它是内存的，重启即失）；
- `org_supervision` 判读卡加一行「昨日 LLM 用量：N 次调用 / in X tok / out Y tok（按通道分列）」；
- 智谱积分折算：anthropic 通道按 K-ORG-038 判例（单工单 ≈4~5 积分）在判读卡注释，不自动算钱。

**验收**：三通道各实跑一次，jsonl 三行齐全；判读卡出现用量行。

**回退**：_log_usage 内部直接 return（一行）。

## 四、G4 devtask 工单 checkpoint（P1，随二轮 T3 同批）

**改什么**：复用 engine/checkpoints.py（LangGraph 式节点快照），给工单链加四节点快照：开单→产码→质检→merge。

**实现**：
- Checkpointer schema 的 `stock` 是 quant 专用字段，加 `task_id` 维度（新表或改 schema——**改 schema 需迁移**，倾向新表 `task_checkpoints`）；
- devtask 每完成一节点 save_node（state=产物路径+状态+sha），崩溃重启时 `get_run_states` 判断从哪续跑；
- 8093 探活判例复用：续跑前 HTTP 确认服务在位。

**验收**：人为 kill 产码中途进程→重启续跑不重头；checkpoint 表有四节点记录。

**回退**：开关 env `DEVTASK_CHECKPOINT=0` 关闭。

## 五、G5 Hermes 军团连接器（P1 门面，1 天，G1/G2 后开工）

**改什么**：Hermes 加一个「军团连接器」——老田在任意表面（浏览器/终端）一句话，Hermes 调底座开工单，判读卡回飞书。

**实现**：
- 对接点拍板：**8093 新增 `POST /api/task/create`（校验+调 devtask 开单逻辑+返回工单号）与 `GET /api/task/status?task=`（读 devtask 状态）**——8093 是 SYSTEM 驻留且已有审计链，比直连 portal 稳；新增端点走 preview/register 同款校验+审计模式；
- Hermes 侧：hermes-webui 加 `api/legion.py`（~100 行）：POST /api/legion/task → 转调 8093 → 返回工单号；WebUI 前端加「军团」命令入口；
- 权限：8093 新端点仅绑 127.0.0.1（Hermes 同机调用），不暴露外网；
- 回执链：复用现有判读卡推送（工单状态变化→飞书），Hermes 侧不做重复通知。

**验收**：Hermes WebUI 发「让 DEV 线修 X」→ 8093 审计留痕 + 工单号返回 + devtask 看板可见；8093 重启后连接器自愈（幂等探测复用 K271 模式）。

**回退**：8093 端点独立文件独立路由，摘除即回退；Hermes 侧 legion.py 单文件删除。

## 七、全局验收判据（地基闭环定义）

- ✅ 记忆能想起来：QA1 问「你上次的判断是什么」能答（memory 回注探针）
- ✅ 通道挂了有人接：mock 主通道故障，产码 30 秒内降级出活
- ✅ 花销有账：判读卡每日一行用量汇总
- ✅ 崩了能续跑：产码中途 kill，续跑不重头（G4 后）
- ✅ 门面指挥通：Hermes 一句话→工单号→飞书回执（G5 后）

## 八、边界与风险

1. **冻结面不动**：G1/G2/G3 均为注入与容错增强，产码产物格式零变化；072 金样本与 e2e 正验链路回归比对。
2. **8093 改动克制**：G5 只加两个只读+一个受校验写端点，沿用现有 preview/register 校验模式与审计链，不动既有路由。
3. **token 预算总闸**：G1 ≤150t + T1 铁律 268t ≈ 420t/岗，逼近 QA1 挂账观察②红线（~1.3K 人设 + 420t ≈ 1.7K），判读卡加「persona 体积」体检项盯防。
4. **Hermes 不引入新运行时依赖**：连接器纯 stdlib（urllib），hermes-webui 现有依赖不增。
5. **序纪律**：G5 必须在 G1/G2 之后——门面接的是闭环底座，否则「指挥进去是哑炮」。
