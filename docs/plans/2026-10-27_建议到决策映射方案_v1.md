# 建议 → 决策映射方案 v1（2026-10-27）
> STATUS: done（已落地：WO-LEGION-SUGMAP-20261027 done）



- 工单：`WO-LEGION-SUGMAP-20261027`
- 目标：让 OS 建议卡能带 `decision_id`，下钻链接被 access-log 归集后精确回填到决策记录。
- 原则：**只做精确 join，不按领域猜、不自动建决策、不伪造映射**。

## 1. 为什么不能自动映射

| 方案 | 问题 |
|---|---|
| 按 domain 映射（研发/情报/通知） | 一个领域可能对应多条决策，会把采纳算错 |
| 每条建议自动建一条决策 | 建议每天变化，决策账本会被噪声灌满 |
| 前端随机/顺序绑定 | 采纳信号失真，复盘无意义 |

## 2. 选定方案：决策侧声明 `suggestion_ids`

决策记录（P1-4）新增字段：

```json
{
  "id": "DR-20261027-03",
  "suggestion_ids": ["task:t1", "notify:n1"]
}
```

含义：这条决策**覆盖/对应**这些建议（建议 ID 来自 `/api/zhuge/brief` 的
`suggestions[].id`，形如 `task:...`、`notify:...`、`alert:...`、`pushflow:...`）。

### 写入方式

```powershell
python tools/zhuge_decision_record.py create ... --suggestion-ids "task:t1,notify:n1"
python tools/zhuge_decision_record.py update DR-20261027-03 --suggestion-ids "alert:a1"
```

- create/update 均支持；append-only 合并去重；
- 一个建议 v1 只对应一条决策（出现冲突视为配置错误，需人工消歧）。

## 3. 读取/透传链路

```text
api_zhuge_brief.build_brief()
  └─ _decision_suggestion_map(): 读 work/p1/decisions/decisions.jsonl
       └─ suggestion_ids → decision_id（只读、无映射不写）
  └─ 命中的 suggestion 附 decision_id
       └─ os_entry_v9_prod.html briefCard → linkFor 拼 ?decision_id=
            └─ nginx access log（referer 含 os-entry）
                 └─ harvest_adoption.parse_entries 解析 query
                      └─ zhuge_c3_decisions 按 decision_id 精确回填
```

## 4. 边界与注意

- `decision_id` 只用于**采纳统计/复盘**，不触发执行；
- 不改变旧行为：无 `suggestion_ids` 的决策、无映射的建议，页面照旧跳领域路径；
- 建议 ID 若跨日复用，映射可能跨日生效——v1 只建议映射**稳定 ID**，或决策
  `review_at` 到期后人工清理 `suggestion_ids`；
- 建议对象只在 brief 响应中增加可选字段，页面在字段存在时才拼参数；
- `ZHUGE_DECISION_REPO` 可指向临时仓库（测试用）。
