# 黄忠事故台账口径 v1（incidents.jsonl）

> 工单：WO-HZ-INCIDENTS-20261031（P6）· 作者：黄忠（HUANGZHONG，交付验收总长）· 载体：DSH 会话
> 日期：2026-10-31 · 状态：v1 口径（工具 `tools/huangzhong_incidents.py` 同批落地）
> 定位：为认证 v2 第④条「漏放 = 0」提供**可审计、append-only** 的事故台账；本文件只定口径，不代替复核判定。

## 一、为什么需要台账

认证 v2 第④条口径（判例：`docs/plans/2026-10-30_黄忠认证标准v2与验收工具证据口径拍板_v1.md:85-88`）：

> 对每张 PASS 单检查其生效后 7 天窗口；窗口内发生与该 commit 相关的事故（含 git revert、事故单、生产异常、回滚记录）即计漏放；满 7 天窗口的 PASS 单中漏放数必须 = 0。

现状（2026-10-30 预检 `work/huangzhong/incidents_scan_20261030.md`）：台账文件缺失，④ 只能按「无已知事故 + 人工核对 docs/audit/ 与 STATUS 事故段」处理，结论依赖人工、不可复算。本台账把「事故 ↔ commit ↔ 时间窗」落成机器可读的追加式证据，让 ④ 的判定有稳定输入。

**分工边界**：本工具只负责**记录与自检**；④ 的判定权仍在只读复核侧（`tools/huangzhong_review.py` 的 `item4_leakage`、`tools/huangzhong_go_no_go.py` 的 `load_incidents`），避免「既写台账又判自己」的单点。

## 二、文件与路径优先级

- 唯一台账文件：`<work-dir>/incidents.jsonl`（JSONL：一行一条 JSON object）。
- 路径优先级：`--work-dir` 参数 > 环境变量 `HUANGZHONG_WORK_DIR` > 默认 `<repo>/work/huangzhong/`。
  - 默认路径即「正规台账」：`work/huangzhong/incidents.jsonl`；
  - 测试/迁移/演练演示一律用 `--work-dir` 或 env 指到临时目录，**不要**写正规台账。
- 工具只写这一个文件；父目录缺失时自动创建目录，不生成锁文件/索引/备份等其它文件。
- 编码：UTF-8；一行一条；追加写在文件末尾（`open(..., "a")`）。

## 三、字段口径（每行 6 个字段）

| 字段 | 必填 | 校验口径 | 说明 |
|---|---|---|---|
| `ts` | 是 | 可解析时间（ISO8601 含 `Z`/偏移、`YYYY-MM-DD HH:MM:SS`、`YYYY-MM-DD`、epoch 秒）；无时区按本机时区（Asia/Shanghai）解释；写入时归一化为带偏移的秒级 ISO | **事故发生时间**（不是入账时间），决定落在哪张 PASS 单的 7 天窗口 |
| `commit` | 是（可为空串） | 空串=未绑定事故；非空须为 **7–40 位 hex**（大小写均可，写入归一化小写） | 相关提交。复核侧按 **8 位前缀**匹配 PASS 单 sha（`_match_sha`）；短 SHA 与全 SHA 同等可用 |
| `kind` | 是 | 非空字符串；建议词表 `incident`（生产事故）/`revert`（回滚）/`outage`（服务中断）/`data`（数据事故）/`drill`（演练，正规台账禁写）/`other` | 分类统计用；未知 kind 不拒收，计入 `stats.by_kind` 便于人工归类 |
| `desc` | 是 | 非空字符串（一句话描述，写清「什么坏了/影响了谁」） | 人读摘要，不替代原始证据 |
| `source` | 否 | 字符串，默认 `manual` | 来源指针：`docs/audit/xxx.md`、回执路径、事件 ID 等，保证可回溯 |
| `added_at` | 工具自动写 | 可解析时间；手工补录可缺省，缺省时 verify 不判坏 | 入账时间（审计用；与 `ts` 分离，防止「事后补录」被误当发生时点） |

## 四、写入纪律（append-only + fail-visible）

1. **只追加，不删不改**：工具没有 delete/update 子命令；发现记错 → 追加一条 `kind=other` 的更正记录并在 `desc` 写明「更正 line=N」，原行保留（审计链完整）。手工编辑台账属例外，需在回执注明并重跑 `verify`。
2. **同 `ts + commit + kind` 去重**：已存在则 `action=skipped / reason=duplicate`，不重复追加（防重复入账把 ④ 统计注水）。
3. **写前校验**：ts 不可解析、commit 非法、kind/desc 为空 → `ok=false` 且 exit 2，**不落盘**（不产生半条脏记录）。
4. **缺失 ≠ 报错**：文件不存在按空台账处理（`exists=false, ok=true`），不造数据、不自动建空文件（避免「假台账」）。
5. **不可读必须报错**：文件存在但读不了（权限/同名目录占位等）→ `ok=false`、`error=ledger_unreadable`、exit 2；**绝不静默当空**（否则 ④ 会把「读不到」误判成「没事故」）。
6. **坏行容错但不销毁**：解析失败的行只计入 `bad_lines`，文件不做任何改写；`verify` 逐条报 issue，`list/stats` 照常工作并在输出中显示 `bad_lines`。
7. **演练不写正规台账**：见第六节。

## 五、CLI 口径（`tools/huangzhong_incidents.py`）

```powershell
cd C:\项目\老田的AI助手
$py = "C:\项目\py312\python.exe"
# 入账（只在确有事故/回滚时用；本单开发期不写正规台账）
& $py -X utf8 tools\huangzhong_incidents.py add --ts 2026-10-30T10:00:00+08:00 `
  --commit abcdef1234567890 --kind incident --desc "服务短暂不可用" `
  --source docs/audit/2026-10-30_JEV锁竞争三连.md
# 列表（倒序，新→旧；limit 默认 20；since 过滤）
& $py -X utf8 tools\huangzhong_incidents.py list --limit 5 --since 2026-10-01 --json
# 校验（必填字段/ts/commit；输出 ok/bad_lines/issues）
& $py -X utf8 tools\huangzhong_incidents.py verify --json
# 统计（总数/按 kind/按 commit 去重/最近 30 天）
& $py -X utf8 tools\huangzhong_incidents.py stats --json
```

退出码：`0` 正常（含 empty/skipped）；`1` verify 不通过（存在 issues 或坏行）；`2` 参数/环境/写前校验错误（含 `ledger_unreadable`、演练写正规台账被拒）。
所有子命令支持 `--json`（可写在子命令前或后），JSON 里恒有 `ok` 字段；`list` 的 `total` 是全部有效行数、`matched` 是 `since` 过滤后的行数。

统计约定：
- `commit_unique` = 非空 commit 的 **8 位前缀**去重数（与复核侧 `_match_sha` 的 8 位匹配口径一致）；
- `unattributed` = `commit` 为空的事故数（复核侧会单列告警，需人工核对归属）；
- `recent_30d` = `ts` 在最近 30 天内的条数（滚动窗口，非自然月）；
- `bad_ts` = `ts` 不可解析的行数（这类行无法参与窗口判定）。
- `stats`/`list`/`verify` 均**不**修改文件（只读）。

## 六、与④（漏放 = 0）的关系

1. **输入角色**：台账是 ④ 的**可选输入**，不是唯一证据；原始证据仍在 `docs/audit/`、`deliverables/` 回执、`STATUS.md` 事故段。台账提供「时间 + commit」索引，减少满窗核对时的人工翻找。
2. **复核侧怎么读**（只读消费，不改口径）：
   - `tools/huangzhong_review.py` → `item4_leakage`：读 `work/huangzhong/incidents.jsonl`；逐张 PASS 单取 `generated_at + 7 天` 窗口，`gen <= incident.ts <= gen+7d` 且 commit **8 位前缀**匹配 → 计 1 起漏放；**未绑定 commit** 的事故不直接计漏放，但列入 `unattributed_incidents` 告警要求人工归属；满窗 0 单时 ④ 记 `tracking`，不强行判 ✓。
   - `tools/huangzhong_go_no_go.py` → `load_incidents`：文件缺失即返回「缺失 → 视为无已知事故（需人工确认）」并计入决策包 warnings；坏行计数进 warnings。
   - 台账里多出来的 `source/added_at` 字段复核侧忽略，不影响判定。
3. **判定权**：④ 是否 =0 由复核/Go-No-Go 侧给结论；本工具不写「④ 通过/不通过」，避免自证。
4. **当前状态（2026-10-31）**：`work/huangzhong/incidents.jsonl` 仍缺失 → 工具输出 `empty ok`；11-04 满窗复核（`docs/plans/2026-10-31_黄忠11-04复核一键流程_v1.md` §1.3）时如仍缺失，按 runbook 以 `docs/audit/` + `STATUS.md` 人工核对并在回执注明「无已知事故」。

## 七、演练与真实事故的区分（硬纪律）

演练（受控拒收/故障注入/历史失败证据构造）**不计入事故台账**，三条区分通道：

1. **正统演练台账独立存放**：`work/huangzhong/drills/drill_ledger_<日期>.json`（既有实证：`work/huangzhong/drills/drill_ledger_20261030.json`，schema=`huangzhong_drill_ledger/v1`，记录 `drill=true`、`kind=REJECT/OBSERVE`、见证人字段）。演练的「结果」是验收单/见证，不是事故。
2. **工具级硬拒**：`add --kind drill`（或 `desc` 以「演练」/“【演练】”开头）写**正规台账**路径时被拒：`ok=false, error=drill_not_allowed_in_production_ledger`，提示改用 `--work-dir` 临时目录。这样即使误操作也不会污染 ④ 统计。
3. **允许的演示方式**：确需演示 add/list/verify/stats 全链路时，`--work-dir C:\Temp\<临时目录>` 指到临时目录，台账只存在临时目录、随用随删（删除走回收站），回执注明「演练/演示，未写正规台账」。

为什么必须分开：把演练当真实事故写进台账 → ④ 漏放统计被打假（误判不合格）；反过来把真实事故写成演练 → 漏放被掩盖（更严重）。宁可 ④ 记 `tracking` 等人工确认，也不混写。

## 九、已知边界与后续

- 不自动从 `portal/data/dev_events.jsonl` 捞事故：事件层当前没有事故类 kind（预检已确认），且「什么算事故」需人工判读；自动抓取会引入误报，后续如做需单独立单并先定白名单。
- 不做清理/归档：append-only；如未来台账过长，另行立项做只读归档（不删原文件）。
- 手工补录（直接 edit 文件）后必须跑 `verify`；`added_at` 与 `ts` 分离是审计要求，不因补录而改。
- 复核侧读取失败会退化为「缺失→无已知事故 + 告警」，不会崩溃；台账不可读时请先修权限，不要用空文件顶替。
