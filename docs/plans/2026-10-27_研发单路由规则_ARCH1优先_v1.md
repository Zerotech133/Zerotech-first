# 研发单路由规则：新研发需求优先 ARCH1/组长（v1）
> STATUS: unspecified（owner: TBD；2026-11-07 前补状态或标 superseded）



> 日期：2026-10-27 ｜ 批准：A0 田丰（流程 L1，老田会话确认） ｜ 执行：研发部 ARCH1 曹操 ｜ 依据：A0 2026-10-27 派单治理意见
> 性质：**流程规则（L1）**，不新增代码门禁、不改 devtask 权限模型；生效即按此路由与留痕。

## 一、规则（一句话）

**新研发需求优先派研发部主官 ARCH1（或按拆组派组长 G1 DEV1 / G2 DEV5），不再直接落 DSH/治理席。**
DSH/治理席只在三类例外下接单（见 §三），其余一律退回/转派研发部。

## 二、判定表（派单前先判）

| 需求类型 | 首选 owner | 说明 |
|---|---|---|
| 代码/功能/修 bug/工具/平台改造/数据管道实现 | **ARCH1**（由 ARCH1 按组拆给 G1 DEV1 / G2 DEV5 或具体 DEV） | 研发交付本位；ARCH1 已有 `dispatch/accept/escalate/reassign` 指挥权 |
| 后端/平台类 | ARCH1 → **G1 DEV1**（DEV6/DEV7/DEV2/OPS1） | 组长承接，ARCH1 终审 |
| 前端/业务/策略/回测/文档类 | ARCH1 → **G2 DEV5**（DEV8/DEV3/DEV4/DOC1） | 组长承接，ARCH1 终审 |
| 跨部门治理（审计/体检/事故复盘/流程/判例） | DSH/治理席 | 治理本位，不动研发归属 |
| A0/老田显式指派给 DSH/治理席 | 按指派 | 指派须在工单 desc 写明 A0/老田指令原文 |
| 研发部请求支援（架构/疑难攻关） | ARCH1 主责，DSH 可支援 | 支援不夺主责 |

## 三、例外（只有三类）

1. **A0/老田显式指派**：工单 desc 必须带指令来源与原文（如“老田 2026-10-27 指令：…”）；
2. **跨部门治理任务**：审计、体检、事故复盘、流程/判例、文档索引治理等（非研发交付）；
3. **研发部请求支援**：ARCH1 明确请求且写明支援范围；主责仍在 ARCH1，DSH 只做支援/复核。

例外之外的“研发单”落到 DSH/治理席时：**不自己开工**，退回 A0 或转 ARCH1（转派留 note）。

## 四、操作与留痕

- 建单：`python tools/devtask.py new <TID> "<目标/验收>" --project <quant|portal|watchbot>`；owner 按 §二填 ARCH1/组长；
- ARCH1 拆组派单：可用既有 `command_authority`（dispatch/accept/escalate/reassign）；拆组后在工单 note 写明组别与验收；
- 留痕：`task_start` 事件 + `.worktrees/tasks.json` owner 字段；A0 日报按 owner 统计；
- 例外单：desc 必须带“例外类型 + 指令来源”，否则视为违规路由，转回研发部。

## 五、生效与回滚

- 生效：2026-10-27 起（本文入库即生效）；
- 配套：AGENTS.md §4 增加一条硬规则引用（不重写宪法）；
- 回滚：`git revert <merge-commit>`（文档与 AGENTS 一条同批回滚）；无需数据/服务回滚。

## 六、边界

- 本规则只改**派单路由**，不改变各席位能力/工具授权、不改变评审门、不改变 L2 审批；
- 不追溯已建单；在途单按原 owner 完成，新单按本规则；
- 与既有“一单一事、单据先行、独立 worktree、评审门”纪律并行。
