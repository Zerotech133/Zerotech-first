## 三、统一研发思路（已达成共识的六条铁律，后续所有工位照此执行）

1. **双闸门单向**：出向唯一走 8097（计量/静默/blocked/分域闸），入向唯一走 W43（意图识别/订阅校验/反推 OS）。任何生产者不得直连飞书 API（osint 收口为范本）。
2. **不建第二账**：通知计量在 8097、权益在订阅账本、业务事实在各自平台；飞书中台只做归属、路由、闸门与投影，不持业务事实。
3. **证据四级**：rc=0 ≠ API 接受 ≠ 可读 ≠ 已读；对外承诺一律用 receiver_verified 口径。
4. **域隔离**：本人/运维/客户三域，模板白名单+频控+额度按域配置；critical 豁免静默仅限本人域（待最终确认）。
5. **页面=只读投影+受控回写**：页面不直接改业务账，人的判断经页面提交后仍走 W43 入向闸进 OS（受控回写），保证"人→OS"也有唯一入口与审计。
6. **closed on failure**：降级路径显式、显式标注缺源，不造数、不假绿。

## 四、v3 新增设计：管理型平台的页面体系

### 4.1 关键架构决策：页面放哪（建议，待批）

**结论建议：不建第二套前端。portal 既有 nginx 鉴权 + 只读投影页体系为承载，飞书做壳与入口。**

```
飞书侧（看到的点）                    OS 侧（承载）
┌────────────────────┐            ┌─────────────────────────┐
│ 消息卡片（按kind差异化模板）│──deep-link─►│ portal 页面（nginx 鉴权）    │
│ 自建应用「网页应用」壳      │◄─OAuth打通──│ /notify-command 本人指挥面  │
│ 卡片按钮=页面动作入口      │            │ /ops-board 运维对账面      │
└────────────────────┘            │ /my-subscription 客户面    │
                                   │ /sub-admin 商务运营面      │
                                   └─────────────────────────┘
```

- **消息卡片按 kind 差异化**：同一 8097 出口，不同信息类型用不同卡片模板（预警卡片带"查看个股页"按钮、死信卡片带"分诊"按钮、日报卡片带"订阅管理"按钮）——这就是"推不同的信息，看到的点不一样"的第一层。
- **页面按域路由**：登录身份属于哪个域，就投影哪个管理面——第二层。
- **飞书网页应用壳**：自建应用开启"网页应用"能力挂 portal 域名，飞书 OAuth 换身份后免二次登录；卡片按钮 deep-link 直达对应页面锚点。
- **受控回写**：页面上的操作按钮（重放/分诊/订阅变更/盯票设置）不直接改账，统一作为 W43 入向请求进 OS，带操作人身份，全审计。

### 4.2 四张管理面（分批上线）

| 页面 | 域 | 内容 | 依据 |
|---|---|---|---|
| 本人指挥面（已有，增强） | 本人 | 四态分组通知、重放/分诊/对账、待确认事项 | notify_command.html 已上线，补 DD-5 决策账入口 |
| 运维对账面 | 运维 | 死信/blocked 滚窗/服务健康/回执率（receiver_verified） | N6 state 段已有数据，纯投影 |
| 客户订阅面 | 客户 | 我的订阅状态/有效期、我的盯票与预警词管理、账单与续费 | 依赖 M2 订阅账本 |

### 4.3 快速投入生产的最短路径

**先让"管理型平台"以最小形态跑起来**：卡片模板差异化（纯 8097 发送侧改动）+ 运维对账面（纯投影、数据已有）可以在 M1/M2 之前先行上线，立即产生管理价值；客户订阅面/商务面随订阅账本（M2）交付。
