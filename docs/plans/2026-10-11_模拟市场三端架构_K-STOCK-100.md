## §1 三端角色定义与现状映射

| 端 | 角色 | 现状 | 缺口 |
|---|---|---|---|
| **端1 策略源 Agent**（strategist） | 决定「今天喂各账本什么信号、喂多少」——按各源近期战绩+市场状态动态路由 | **静态路由**：automation 写死 `--source qd/qpzm/ai_team`， hires 雇佣表只定账本不定源 | 战绩驱动的动态路由器；源健康度（连续拦截/信号重叠/陈旧率）未量化 |
| **端2 持仓交易员**（trainees） | 各风格 Agent 执行持仓（快枪手/稳如泰山/追风者/青萍US台/main） | **已成骨架**：trainee.py 例程 + hires 雇佣 + scoreboard 成绩单 + conf_floor/止损档案 | 上岗验收（acceptance_check 周一跑首次）；毕业判据已留位 |
| **端3 评判 Agent**（judge） | 统一评审模拟过程的问题：信号质量/执行偏差/风控行为/账本纪律，产出结构化评审+叙述分析 | **空白**（acceptance_check 是一次性验收器，非日常评审） | 日常评审器 + 评审数据模型 |
| **蒸馏沉淀**（distill corpus） | episode=(上下文，信号，决策，结果，评语) 语料，供日后蒸馏小模型 | **原料齐全**（orders 全字段含 conf/reason/strategy/ref + events + equity_marks） | 语料化导出器与 episode schema |

## §2 数据流（目标态）

```
[端1 strategist] 源健康度打分 → 今日路由表（源×账本×权重）
        ↓ poc_*.json（同构信号协议）
[端2 trainees] exec → pending → settle → 持仓/止损/mark
        ↓ 全程留痕（orders.ref / events / marks）
[端3 judge] 日评审：规则检查项（确定性）+ LLM 叙述分析（增强）
        ↓ judge_reviews/YYYYMMDD.json + episode 评分
[蒸馏沉淀] distill_corpus.jsonl：上下文+信号+决策+结果+评语
        ↓ 积累 N 千 episode
[蒸馏] 小模型 SFT（远期）：让 7-9b 模型学会「给定上下文做出 scoreboard 高分行为」
```

## §3 分期落地

| 期 | 内容 | 交付物 | 状态 |
|---|---|---|---|
| **M1 评审骨架** | judge.py 日常评审器：7 项规则检查（确定性，不依赖 LLM）+ 可选 `--llm` 叙述分析（Ollama qwen3.5:9b，think:False，失败降级） | `k_stock/paper/judge.py`；评审落 `k_stock/data/judge_reviews/YYYYMMDD.json` | 本期 ✅ |
| **M2 蒸馏导出** | distill_export.py：orders×marks×judge 拼 episode → `data/distill_corpus.jsonl`（outcome 字段留 T+N 回填） | 导出器 + episode schema | 本期 ✅ |
| **M3 动态路由** | strategist.py：源健康度（陈旧拦截率/信号重叠度/近期胜率）→ 路由表；先影子模式（只输出建议不改 automation） | 路由建议投影进 /paper | 排期 10-17 后 |
| **M4 蒸馏训练** | 语料量达标（≥3k 有效 episode）后 SFT；对齐 A6/Ollama 基建 | 远期 | 积累中 |
| **页面展示** | /paper 加「评判」tab：最近评审+问题清单 | portal_status.judge_status | 随 M3 |

## §4 episode schema（蒸馏语料最小单元）

```json
{
  "episode_id": "20261012-main-600519.SH-BUY-17",
  "ts": "2026-10-12T07:14:23", "account": "main", "strategy": "ai_team",
  "context": {"asof": "2026-10-11T23:35", "run": "poc_qpzm_...",
              "equity": 1000000.0, "pos_pct": 0.0, "regime": null},
  "signal": {"side": "BUY", "conf": 0.55, "qty": 100, "plan_date": "20261012",
             "reason": "D1 BUY conf=0.55 → 目标仓位 11.0%"},
  "exec": {"status": "filled", "fill_price": 1250.0, "fee": 6.25,
           "guard_flags": ["replan_cancelled=2", "stale_rejected=1"]},
  "outcome": {"ret_5d": null, "ret_20d": null, "mfe": null, "mae": null},
  "judge": {"score": 82, "flags": ["CONF_BELOW_FLOOR"], "narrative": null}
}
```

原则：**outcome 永不回填 falsy 值**——没到 T+N 就是 null，蒸馏时按可训练性过滤；
**guard_flags 记录执行链干预**（守卫拦截/撤销），这是端3最重要的评审素材——
「Agent 想做什么」与「系统让它做了什么」的差值就是问题所在。

## §5 与既有体系的关系

- **不新增库表**：judge 走 paper.db 只读 + 自产 JSON 落 data/judge_reviews/；
  episode 导出读 orders/marks 现有字段，零迁移
- **不双跑**：judge 由 automation 07:05 例程尾追加（或手动 `python judge.py --date`），不进 settle/exec 链
- **诚实声明**：M1 规则评审是确定性的（可复算）；LLM 叙述仅增强可读性，不进评分
