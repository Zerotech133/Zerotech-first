## 〇、老田模型复述（确认理解）

1. 老田 ↔ **田小皮**（参谋长）商量开会 → 形成一个个**研发方案**；
2. 研发方案**分别下发**各研发部门——前端/后端/UI/代码审计/压力测试**并发分工**；
3. 各部门工作汇总**直接传导回田小皮**；
4. 田小皮安排一名**助理**；另设（未来）一名**三十年网络安全工程师**（兼技术全栈、渗透/反渗透、压力测试）；
5. 该工程师**对照研发方案**检查下属 Agent 产出：做得完善否？有没有**走形**？
6. 走形/不完善 → **直接推信息到田小皮** → 田小皮向 AI Agent **下发修改命令**；
7. 开发中遇**确定因素** → 田小皮**对照研发计划直接同意**（审批通道）。

## 二、Gap 与新岗设计

### G1 · A0 助理：`A0A`（chief_assistant · E1 档）
- 职责：研发方案下发分发、各部门汇总**归集与初筛**（按部门/工单聚类、标红异常项）、田小皮命令**下发跟踪**（哪条命令、发给谁、闭环没闭环）、晨会材料预备。
- 边界：**只调度不决策**——判断类事项一律上浮田小皮。

### G2 · 网络安全工程师：`SEC2`（security_lead · **E3 三十年档**）
- 人设要点：30 年网络安全 + 技术全栈；渗透测试/反渗透/加固；压力测试与性能瓶颈定位；**代码走形检查**（对照研发方案读实现，判断「做偏了没有/做全了没有」）。
- 与 SEC1 分工：SEC1=内部合规红线（凭据/权限/危险操作），SEC2=**研发质量对抗线**（渗透、压测、走形审查）—— SEC2 审查报告直推田小皮。
- 走形检查产出格式（制度化）：`对照方案条目 → 实现证据 → 判定(完善/走形/缺失) → 建议命令`，走形项自动开任务单并 @田小皮。

### G3 · 走形检查闭环（工作流，非岗位）
```
研发方案(PM1/田小皮产出·文档化) 
  → A0A 分发各部门(并发) 
  → 部门产出(工单承载) 
  → A0A 汇总归集 
  → SEC2 对照方案走形检查 
  → [完善] 归档结案 / [走形] 推田小皮 
  → 田小皮下发修改命令(A0A 跟踪) → 部门返工 → SEC2 复查 → 闭环
```

### G4 · 确定因素直批通道
- 「开发中需确认的因素」当前散在工单 review 状态与任务单评论。
- 制度化：任务单加 `approval_request` 事件类型——Agent 遇确定因素 → 写明「方案依据条目 + 请批事项」→ 田小皮晨巡/即时判读对照研发计划 → agree/reject 直接回单（不升级老田，除非超权限）。
- 老田保留：超预算/跨部门/对外承诺三类仍需老田终审。
