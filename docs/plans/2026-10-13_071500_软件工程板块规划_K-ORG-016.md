## 1. 需求锚定（老田原话拆解）

「多 IDE 在不同板块进行软件研发：写策略、改 bug、做回测、做前端 UI，也可以写其他应用。」

拆为五个工程需求：

- **S-1 分域**：策略/回测/前端/通用开发各有专属岗位与流水线，不混岗。
- **S-2 并行**：多 IDE 同时开工互不踩脚（已有 worktree 机制实证 63 单）。
- **S-3 闸门**：每类产出有对应质量门——策略过回测、UI 过版面宪法、代码过三守卫。
- **S-4 仲裁**：A0 统一拆单派发，老田只面对一个入口。
- **S-5 通用性**：平台不绑定量化——「写其他应用」= 加一张工单，不是改平台（K-ORG-001 §8 原则）。

## 5. 四条流水线（每条带闸门）

1. **策略研发线**：老田/A0 立项 → DEV3 写策略（strategies.json 注册制）→ DEV4 回测（判据前置：如缠论联立先例「假阳率降 ≥30% 且净收益不降」，不过就终止留档）→ 影子账观察 → alpha 团队挂载。**判例纪律：论证不过就地降级（快枪手先例）。**
2. **Bug 修复线**：健康巡检/告警/用户反馈 → A0 判级 → DEV1 领单 → 三守卫 → merge → 飞书回执。review 积压 18 单本周清一次。
3. **前端 UI 线**：老田拍板 Demo 先行（判例：门面迭代全走「Demo→拍板→怼代码」）→ DEV5 实施 → 版面宪法+tokens 单源+CR 字节检查 → 8080 实测 → merge。
4. **应用开发线**：任何新应用（Hermes 插件/工具脚本/对外小产品）→ devtask 开单 → 岗位认领 → 端口注册 → 事件回流。**平台零改动，加单即扩。**

## 6. 多 IDE 并行机制（现状已通，补三条规则）

- 已有：一单一线程 worktree 隔离；merge 三守卫；事件回流；board 看板（docs/dev/devboard.html）。
- **新增规则 1（派单路由）**：A0 按域路由到岗位，IDE 只是执行器——同一岗位可由不同 IDE 领不同单（DEV5·CodexWeb 与 DEV5·Trae 并行两张前端单）。
- **新增规则 2（长任务分配）**：回测/训练类长跑单优先派给可长驻的 IDE（Codex 系）；交互式 UI 单派给响应快的（Trae/CodeBuddy）。具体分工表待老田拍板。
- **新增规则 3（编号纪律）**：工单 TID 用 K-<域>-<号>（K-DEV/K-STOCK/K-ORG）；worker 提交前 `git log --oneline -5` 查邻号（撞号 7+ 次判例）。
