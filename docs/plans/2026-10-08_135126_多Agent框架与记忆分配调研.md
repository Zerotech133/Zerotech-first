## 1. 需求锚定（老田原话）

> 「我们把多 AI 做成一个框架式的，未来可以随时增加 AI。那么多 AI 的记忆库、向量库，它的分配也是一个框架式的，避免以后它的混乱，方便于 AI 和 AI 之间的多区（协作/区隔）。你去开源社区找一找同样的项目，看看有没有可借鉴的方案。」

拆解为三个工程需求：

1. **N-A 框架化多 Agent**：拓扑、角色、流程全部配置化，新增一个 AI Agent 不改解释器代码。
2. **N-B 记忆/向量库框架化分配**：隔离规则（谁读谁的、谁写谁的）在架构层一次定死，杜绝 Agent 间记忆混写。
3. **N-C Agent 间协作与区隔并存**：辩论对手要能互读，无关 Agent 要互相隔离。

## 2. 编排框架对比（开源社区调研，2026-10）

| 框架 | 编排模型 | 拓扑定义方式 | 动态增减 Agent | 生产背书 | 对本项目的适配度 |
|---|---|---|---|---|---|
| **LangGraph** | 图/状态机 | Python 代码定义图+边 | 加节点需改图代码 | Klarna/Uber/LinkedIn 生产使用；checkpointing、node 级可观测性 | 中：能力强但主范式是代码定义拓扑，与 N-A「配置驱动」有张力 |
| **CrewAI** | 角色驱动 | 角色列表+任务委派 | 配置化较好，但团队结构偏固定 | 中型项目快速原型 | 低：token 效率低，辩论链表达弱 |
| **AutoGen** | 对话驱动 | 群聊参与者 | — | **已进维护模式**（微软官宣 MAF 1.0 接班，AG2 为社区分叉） | 排除：不再演进 |
| **MS Agent Framework 1.0** | actor 模型 | 代码 | — | 微软新接班人 | 低：生态太新，风险高 |
| **Google ADK** | agent 树 | 代码/配置混合 | 中 | A2A/MCP 原生，4 语言 | 低：绑定 Google 生态 |
| **菜鸟 ai_team_role DSL**（自有资产） | **数据驱动树** | **数据库行=节点** | **增删一行配置即扩容** | AUTO_INCREMENT=3114、7095 次真实执行 | **高：原生满足 N-A** |

**关键洞察**：菜鸟的 ai_team_role 表本质上就是一个「配置即拓扑」的 DSL——`node_key`+`parent_node_keys` 定义树形拓扑，`is_parallel`+`wait_all_complete` 定义并行屏障，`debate_partner_key`+`max_debate_rounds` 定义辩论链。这与 LangGraph 的图模型同构，但拓扑存于数据而非代码。**用户要的「框架式、随时增加 AI」，菜鸟已经给出了经过大规模实跑验证的答案形状**，我们要做的是用 Python 重实现其解释器（蓝图 v2 已定），并补上 LangGraph 的两个精华思想：

- **checkpointing**：每个节点执行完把状态快照落 PG，崩溃后可从任意节点恢复（菜鸟缺这个，掉电即全废）。
- **node 级可观测性**：每个 Agent 的输入/输出/token 消耗/耗时落 trace 表，辩论过程可回放。

## 3. 记忆框架对比（开源社区调研，2026-10）

| 框架 | 隔离模型 | 后端支持 | 核心思想 | 对本项目的适配度 |
|---|---|---|---|---|
| **Mem0** | User/Session/Agent 三级分区 | **Qdrant/Chroma/Neo4j/pgvector** | 多层级记忆+自动提炼 | 中：分级思想可借鉴；但其隔离轴是「用户/会话/Agent」，面向 C 端个人助理，本项目是 **B 端多团队协作**，隔离轴应为「团队/角色/记忆类型」 |
| **Zep + Graphiti** | bi-temporal 知识图谱 | Neo4j | 时态双轴+边失效（观点被新数据推翻时标记失效而非删除） | 思想高价值：**复盘时「当时的判断」不能被覆盖**，本报告 §5.2 采纳其失效语义 |
| **Letta/MemGPT** | OS 式分页 Core/Recall/Archival | 自带服务 | 把记忆当内存分页管理 | 低：agent-as-server 部署模型过重 |
| **Cognee** | 图+向量 hybrid | 多后端 | cognify 管道（数据→知识图谱→可查询） | 低：转换管道重，PoC 阶段不需要 |
| **LangMem** | LangGraph 原生 BaseStore | 任意 | 与 LangGraph 状态绑定 | 备选：仅在升级方案 B 时启用 |
| **OpenMemory** | local-first | 本地 | MCP 标准记忆接口 | 低：接口标准合适但实现单薄 |

**关键洞察**：没有一个现成框架的隔离模型直接匹配「多团队选股 Agent」场景——这是**定制点也是护城河**。本项目的记忆分配必须自己定义规范（§5.2），但分级思想（Mem0）、失效语义（Zep）、分区存储（共同点）全部可借鉴。

## 4. 菜鸟 ai_team_role DSL 再定位（源码级事实）

来源：`菜鸟\thunder_model\all_ddl.sql`（`ai_team_role` 表，AUTO_INCREMENT=3114）

```sql
CREATE TABLE `ai_team_role`  (
  `node_key`            varchar(255)  COMMENT '节点id',
  `parent_node_keys`    varchar(1000) COMMENT '节点父级ID',
  `level`               int           COMMENT '层级（1-第一级，2-第二级...）',
  `analysis_type`       varchar(32)   COMMENT 'market_technical/news_event/fundamental/investment_advice/final_decision',
  `is_parallel`         bit(1)        COMMENT '是否并行执行（同一层级的多个角色）',
  `wait_all_complete`   bit(1)        COMMENT '是否等待所有同级分析完成才流转到下级',
  `input_config`        varchar(1000) COMMENT '输入配置',
  `output_config`       varchar(1000) COMMENT '输出配置',
  `debate_partner_key`  varchar(64)   COMMENT '辩论对手节点key（两个互为辩论对手的节点填对方的nodeKey）',
  `max_debate_rounds`   int           COMMENT '最大辩论轮次（默认2轮）',
  `is_debate_node`      tinyint(1)    COMMENT '是否为辩论节点',
  `x` int, `y` int                   COMMENT '画布坐标（可视化编排）',
  ...
) COMMENT = '分析师团队角色配置表';
```

配套调度表 `ai_team_task`：`analysis_frequency`（once/daily/weekly/monthly）+ `analysis_time` + `next_execute_time`——**任务级定时调度也是配置化的**。

**定性**：菜鸟缺的不是框架思想，是三样东西——
1. 算法本体（选股服务/评分服务/TradingAgents 三个 Python 服务源码缺失，Java 壳只是 HTTP 客户端）；
2. 记忆层（所有 Agent 共用会话上下文，无隔离规范——这正是「混乱」的根源，老田要求避免的东西）；
3. checkpointing（掉电即废）。

**新框架 = 菜鸟的拓扑 DSL + 补齐这三样。**

## 5. 推荐方案：配置即拓扑 + 四级记忆命名空间

### 5.1 Agent 注册表（框架化的核心，YAML+PG 双存）

YAML 走 Git 版本化（评审/回滚），PG 表作运行时源（解释器读取），格式对齐菜鸟 DDL 字段以便未来双向同步：

```yaml
# registry/team_alpha.yaml
team: alpha
description: 激进多头团队
agents:
  - agent_id: T1
    role_profile: aggressive_bull      # 人设存配置（对齐菜鸟 ai_chat_role 1036 角色模式）
    analysis_type: market_technical
    node_key: t1_market
    parent_node_keys: []               # 根节点
    is_parallel: true
    wait_all_complete: true            # 与同级形成屏障
    debate_partner_key: t2_market      # 与 T2 互为辩论对手
    is_debate_node: true
    max_debate_rounds: 2
    llm_binding: ollama/qwen3.5:9b     # 2026-10-08 实测本地库（35b/9b/4b 三档，无 qwen2.5）
    tools: [tdx_kline, news_feed]
    memory_grants:                     # 记忆权限（§5.2 RBAC 的载体）
      read:  ["domain/*", "team/alpha/*", "agent/T1/*"]
      write: ["agent/T1/*", "team/alpha/observation"]
```

**新增一个 Agent = 注册表加一段 YAML + `registry apply` 同步 PG，解释器零改动。** 拓扑合法性（无环、辩论对手互指、屏障闭合）由解释器启动时校验，不合法拒绝执行。

### 5.2 记忆分配：四级命名空间 + RBAC

**命名空间格式**：`{domain}/{team}/{agent}/{type}`

| 层级 | 内容示例 | 读权限 | 写权限 | 冲突仲裁 |
|---|---|---|---|---|
| `domain/*` | 六维评分标准、风控规则、全局市场状态 | 所有 Agent | 仅治理者（D1/人工），带版本号 | 版本化+人工审核，**只进不改**（Zep 失效语义：旧版标记 superseded 不删除） |
| `team/{team}/*` | 辩论上下文、团队中间结论 | 本团队 Agent | 本团队 Agent | 同 key 并发写按 `confidence DESC, ts DESC` 取胜者，败者落审计表 |
| `agent/{id}/*` | 该 Agent 历史判断、复盘、角色画像 | 仅本 Agent | 仅本 Agent | 无需仲裁 |
| `share/*` | 跨团队白名单共享区 | 白名单 Agent | 白名单 Agent | 显式声明，默认关闭 |

**记忆类型**（第四级）固定四种：`observation`（市场观察）/ `decision`（决策记录）/ `feedback`（后验复盘）/ `profile`（角色画像）。复盘纪律：feedback 只 append 不 update——**「当时的判断」永远保留原始版本**（采纳 Zep 时态思想）。

**防混写三道闸**（N-B 的落地）：
1. 解释器在 Agent 读写记忆时校验 `memory_grants`，越权直接拒绝并告警；
2. 所有写入强制携带 payload 头 `{agent_id, team, ts, symbol, round, confidence}`，源头可溯；
3. 命名空间漂移检测：每次 `registry apply` 时扫描全量 grants，发现重叠写权限即报错。

### 5.3 向量库分配：Qdrant collection 规范

```
collection 命名：stock_{team}_{agent}_{type}
示例：stock_alpha_t1_observation / stock_global_domain_standard
维度：bge-m3 = 1024（2026-10-08 本地实测，多语模型；固定单模型，换模型则建新 collection 并迁移）
payload 统一 schema：{agent_id, team, ts, symbol, round, confidence, text_ref}
```

- **每 Agent 每 类型一个 collection**：物理隔离最彻底，Agent 间零串扰；团队级共享用 `stock_{team}_shared_{type}`。
- Redis(6379) 只做 Working Memory（单次任务内会话态，TTL 自动过期），不承担长期记忆——**冷热分离**：RAM 会话态 / Qdrant 语义检索 / PG 审计与 checkpoint。

### 5.4 编排解释器（Python 轻量自研）

规模控制在 ~500 行内（菜鸟 TeamTaskServiceImpl 851 行 Java 是功能上限参照）：

```
执行循环 = 读注册表 → 校验拓扑 → 按 level 分层 → 层内 is_parallel 并行 fan-out
        → wait_all_complete 屏障 → 辩论节点对循环（max_debate_rounds 上限 +
          余弦相似度>0.8 提前收敛，对齐菜鸟 bull/bear 链）→ 节点结果 checkpoint 落 PG
        → 流转下级 → 最终决策节点出五档推荐
```

- **checkpointing**（借鉴 LangGraph）：`checkpoint(node_key, run_id, state_json, ts)` 落 PG，崩溃恢复从最后完成节点续跑；
- **降级三态**（对齐菜鸟 degraded）：正常 / 降级（LLM 超时走规则兜底）/ 失败；
- **trace**：每节点落 `{run_id, node_key, input_ref, output_ref, tokens, latency}`，辩论全程可回放。
