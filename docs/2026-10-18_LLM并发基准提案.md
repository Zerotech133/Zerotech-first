## 二、关键发现

1. **并发=2 有真实收益 1.53×**：纯 decode 速率（eval tok/s）几乎不变，收益来自 llama.cpp continuous batching 重叠 prompt-eval/decode 气泡——CPU-only 机器上这是白捡的吞吐。
2. **并发=4 饱和无益**：吞吐与 2 持平（1.50×），单条延迟反而从 5.75s 恶化到 11.08s——CPU 算力已打满，多开的槽只摊薄不增产。**不建议设 4。**
3. **★重大事实修正：本机 Ollama 是 100% CPU 推理**（`ollama ps`：PROCESSOR=100% CPU，7.8GB；`nvidia-smi` 不存在=无 NVIDIA GPU）。此前「45-57s/条」与「1.4s/条」之争的物理底座就是 CPU decode ~12.7 tok/s。无 GPU 是硬约束，GPU offload 在本机不可行。

## 三、提案（留拍板，不自行执行）

**建议设 `OLLAMA_NUM_PARALLEL=2` 并重启 Ollama 服务**：

- 预期收益：追平轮吞吐 ~1.5×。16.5k pending 墙钟口径 1×≈31h → 2×≈20h（真实混合长度按比例保守外推）。
- 内存代价：并发槽 ×2 → KV cache 翻倍（每槽 num_ctx=2048 很小，权重 7.8GB 不变，RAM 充裕，低风险）。
- 执行窗口：须在自动化轮间隙重启（重启杀当前请求队列；今晚 18:00 爬虫环不用 LLM，19:00 日报环用——**推荐明天 13:30 sprint 首跑前执行**，或拍板即时执行）。

操作步骤：
1. 设系统环境变量 `OLLAMA_NUM_PARALLEL=2`；
2. 重启 Ollama 服务（冷加载 ~13s，无痛）；
3. 验证：重跑 `python quant_backtest/tools/llm_bench_conc.py`（28 调用）确认 1.5× 复现，`ollama ps` 复核。

## 四、更大杠杆的如实陈述

无 GPU 前提下，2× 并发只是把 CPU 榨到 1.5×。数量级级的提速只有两条路（均超出本提案范围）：
- 换更小量化模型（如 4bit 更激进量化 / 3-4B 级模型，先跑 agreement 验收）；
- 上加速硬件（本机无 NVIDIA GPU；国产算力/NPU 路线属另案）。
