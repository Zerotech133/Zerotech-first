# 需求单：涨停池分钟覆盖（提交采集工位）

| 项 | 内容 |
|---|---|
| 提出 | JEV 线（J-03 交叉卡），2026-11-13 |
| 状态 | 待接收 |
| 优先级 | 高（J-03 时间维的唯一阻塞点） |
| 关联 | `portal/jev_cross.py`、`tools/jev_mins_fetch.py`、`docs/2026-11-13_JEV研发计划_v1.md`（J-03） |

## 一句话

每个交易日收盘后，把**当日涨停/触板池**的分钟线补齐到本地，241 根、完整交易日、
可幂等重跑；JEV 只读，不做采集。

## 现象与量化（2026-11-13 实测，非估计）

本地 `quant_backtest/data/tushare/stk_mins/` 有 34,298 个月文件，2026-11 的有
1,100 只票（全市场 5,500+，约 20%）。对**涨停/触板池**逐票核对「该日是否有分钟行」：

| 交易日 | 涨停/触板池 | 有当日分钟 | 有月文件但缺当日 | 无月文件 |
|---|---|---|---|---|
| 11-06 | 52 | **39（75.0%）** | 1（1.9%） | 12（23.1%） |
| 11-10 | 118 | 4（3.4%） | 31（26.3%） | 83（70.3%） |
| 11-11 | 112 | 8（7.1%） | 24（21.4%） | 80（71.4%） |

三层含义完全不同，处置也不同：

1. **无月文件（≈70%）**：从来没过采。这批是涨停小票，不在 1,100 只里。
2. **有月文件但缺当日（≈21–26%）**：采过这只票、但没跟上这一天。月文件停在
   更早的日期上，「存量不同步」是这一类。
3. **有当日（11-06 的 75%）**：证明**采集能力本身存在**。11-06 能到 75%，
   11-10/11-11 掉到 3%–7% —— 差别不是能力，是**没有每日必采**。

结论：这不是「小票采不到」，是「没有按日闭环」。所以本单要的是一个**日更任务**，
不是新数据源。

### 远端兜底为什么救不了（已实测，不必重试）

`portal/jev_graph.py` 的分钟链路是「本地 → `ts_stk_mins` → `ts_rt_min`」。当日盘后实测：

- `ts_stk_mins`：对当日涨停小票**无存量**，`jev_mins_fetch --day 20261110 --limit 100`
  只成功 1 只；
- `ts_rt_min`：只有 237 根、**缺 15:00 收盘那根**，采集工具刻意拒写（`partial_skip`
  97 只）——这个拒写是对的，写进去会把残缺日固化成「已补齐」。

所以远端只能当补救，不能当常规来源。

## 需要什么（产物规格）

| 项 | 要求 |
|---|---|
| 路径 | `quant_backtest/data/tushare/stk_mins/{code.replace('.','_')}_{YYYYMM}.parquet` |
| 粒度 | 1 分钟。**每只票每个交易日恰好 241 根**（09:30–11:30、13:00–15:00，含收盘那根） |
| 字段 | `ts_code, trade_time, open, close, high, low, vol, amount`（与现有文件同 schema，不改） |
| 时间 | `trade_time` 为 `YYYY-MM-DD HH:MM:SS` 字符串，与现有文件一致 |
| 写入 | **追加式幂等**：同一天重跑不得产生重复行，不得改动其他日期的行 |
| 覆盖范围 | 当日 `is_limit_up` 或 `touch_only` 的全部票（11-10/11-11 实测 112–118 只/日） |

### 硬约束（不是建议）

1. **不完整不落盘**。不足 241 根或首根不是 09:25/09:30/09:31 的，整票当日不写，
   并记一条 `partial_skip` 理由。宁可缺，不可假完整——缺了 JEV 标 `unavailable`，
   假完整会让「13:35 首次异动」这种伪结论直接进卡面。
2. **不覆盖已有的完整日**。已有 241 根的日期跳过，不重写（避免把好数据换成坏数据）。
3. **原子替换**：先写临时文件再 `os.replace`，中途失败不留半截 parquet。
4. **价格口径必须与日线一致**。`daily/d_YYYYMMDD.parquet` 的 `close` 与分钟 `close`
   对同一只票、同一交易日必须相等（涨停判定用它算涨停价）。若日线是复权价而分钟
   是原始价，请在交付说明里明确写出，我们需要跟着改判定口径——**这一条请回执确认**。
5. **不改渲染层**。不碰 `portal/`，不改 `jev_cross.py` / `jev_graph.py`。采集与渲染
   物理隔离，JEV 侧只做读取方。

## 时效

| 时点 | 要求 |
|---|---|
| 收盘后（15:00） | 当日数据源才完整；此前采到的必然缺尾盘，不要落盘 |
| T+1 08:30 前 | 当日卡完成。此前 JEV 把时间维标 `unavailable`，不影响主维（资金+席位） |
| 补历史 | 11-03 ~ 11-12 优先（近 8 个交易日），更早不急 |

盘中不需要分钟：盘中链路用的是快照/逐笔，分钟在本项目里是**盘后复核**用的。

## 验收口径

连续 5 个交易日，同时满足：

1. 涨停/触板池**当日覆盖率 ≥ 95%**（分母 = `jev_cross.candidate_codes(day)`）；
2. 已覆盖票中，**241 根占比 = 100%**（允许整票缺失，不允许半截落盘）；
3. 随机抽 5 只，分钟最后一根 `close` 与日线 `close` 相等（复权口径见硬约束 4）；
4. 同一日重跑一次，文件行数与内容不变（幂等）。

验收由 JEV 侧跑，命令：

```
python tmp/stat_mins_gap.py            # 三层缺口（临时脚本，不入库）
python portal/jev_cross.py --day <YYYYMMDD> --all --limit 100   # 看 time 维转 ok 的比例
```

## 明确不要求

- 不做反爬攻关、不为一个参数反复试；
- 不追求全市场 5,500 只全覆盖，只要**事件池**（涨停/触板）；
- 不追求历史全量回填，先近 8 个交易日；
- 不做复权、不做因子、不做任何分析——交付物就是 parquet。

## 交付回执需要写清的四件事

1. 数据源与接口（哪个表/哪个文件），以及当日可得的最早时点；
2. 11-10 / 11-11 两个交易日的实测覆盖率（用上面同一口径，报 4/118、8/112 这种
   绝对值，不要只报百分比）；
3. 硬约束 4（复权口径）的确认结论；
4. 若做不到 241 根，说明卡在哪一步（接口只给 237 根 / 只给分时不给分钟 / 无权限）。

## 对 JEV 侧的影响

- 时间维从 `unavailable` 转 `ok`，卡面附表才有内容；
- **验收口径不变**：J-03 的主维仍是资金 + 席位，时间维是附表、不参与
  `acceptance.verdict`。本单不是为了让交叉卡「看起来更完整」，是为了让附表有东西可看。
- 若覆盖率长期上不去，J-01（媒体滞后时钟）的最小样本闸（n<200 判不可建）不受影响，
  因为那条线的瓶颈是**时间戳分辨率**，不是分钟数据。
