# 涨停事件交叉卡 v1 · 实测报告（J-03 交付）

**编制**：A 组 / OSINT1 · 2026-11-13
**代码**：`portal/jev_cross.py`（只读、零联网、不调 LLM）+ 门禁 `portal/tests/test_jev_cross.py`（18 passed）
**结论先说**：**卡做出来了，但计划定的 DoD 没达到。** 差在时间维——不是代码没写，是分钟数据在票池上不存在。

---

## 一、这是什么

一个涨停事件 → 一张四维卡。**卡上不写结论**，只写哪一维有数据、精度到哪、原始值多少。

| 维 | 取数 | 精度 | 五态语义 |
|---|---|---|---|
| `time` | `stk_mins` parquet | 分钟 | `ok` / `partial`（残缺不可采信）/ `unavailable` |
| `flow` | `_jev_snap/flow_*.json` | 收盘终值 | `ok` / `none`（无该票）/ `unavailable` |
| `seat` | `data/hm_detail/*.jsonl` | **T+1** | `ok` / `none`（未上榜）/ **`pending`**（当日未到） |
| `narrative` | `_jev_snap/disc_*.json` | 日期级 | `ok` / `none`（确认无公告） |

**五态必须分开**，这是本模块的核心设计决定：

- `pending`（按规则还没到）≠ `unavailable`（取不到）≠ `none`（确认没有）。
  三个词混成一个"缺失"，第二天就不知道该等、该补、还是可以下判断。
- `partial` 单独设一档：拿了数据但不可采信时，**把值置空而不是照用**。

## 三、DoD 判定（对照研发计划 §三 J-03 / §五）

| 计划 DoD | 实测 | 判定 |
|---|---|---|
| ≥3 维**有值**率 ≥ 70% | 11-10：**4%**；11-11：**18%** | **未达成** |
| 每维标来源与时点精度 | 四维全部带 `precision` + `source` | 达成 |
| 无数据维显式 `unavailable` 不省略 | 100% 显式 | 达成 |

**不达标的唯一瓶颈是时间维**（11-11 的 50 张里 46 张时间维取不到）。

### 3.1 归因：分钟数据的"三重残缺"

补数实测（`tools/jev_mins_fetch.py --day 20261110 --limit 100`，188 秒）：

```
取数完成 98 只，{'merged': 1, 'already': 2, 'empty': 0, 'fail': 0,
                'partial_skip': 97, 'via_xtcloud': 1}
```

1. **本地 `stk_mins` 只覆盖中证800** —— 涨停股多是小票，天然不在内（11-10 覆盖 4/100）。
2. **远端 `ts_stk_mins` 对这批票没有存量** —— 98 只里只有 1 只有完整数据（判例 #26 坑 4「存量不同步」的又一次实证）。
3. **`ts_rt_min` 只有 237 根、缺 15:00 收盘那根** —— 采集工具**刻意拒绝写盘**（写进去会把残缺日固化成"已补齐"，
   之后永远补不上第 241 根，尾盘封板会永久判错）。97 只 `partial_skip` 就是这个决定的产物。

所以：**不是没采，是数据不存在。** 与第五辑「分钟级信息传导时钟不可建」是同一个结论的第二个侧面。

## 四、处置选项（需你裁定，我不擅自改口径）

> 纪律：**不许为了让 DoD 变绿而改验收标准**（判例 #38 的 p-hacking 禁令）。

| 选项 | 做法 | 代价 | 我的看法 |
|---|---|---|---|
| **A. 接受两维卡** | 主卡只认 `flow + seat`，时间/叙事降为附表；DoD 改成"两维有值 ≥95%" | 放弃时间维（异动时刻/封板时刻） | 最稳，但丢掉了卡最独特的一维 |
| **B. 补分钟数据** | 让采集工位解决小票分钟覆盖（tushare 完整源 / 盘中落盘） | 依赖外部，非我这条线 | 治本，但要等 |
| **C. 改验收口径为"已知率"** | 四维保留，DoD 改成"已知 ≥3 维 ≥95%"（现 100%） | 口径变松，容易自我安慰 | **不建议单独用**，必须与 A/B 之一并用 |

**我的建议**：**先按 C 记录台账，同时走 B 提需求，暂不宣布 DoD 达成。**
理由：卡的真实价值就在"知道哪一维不知道"——把 `none`（确认无公告）和 `unavailable`（取不到分钟）
合起来算"完整度"，等于把判例 #38 的错误换个地方重犯。

## 五、已知缺陷

| # | 缺陷 | 影响 | 当前处置 |
|---|---|---|---|
| 1 | 席位维 T+1 才全 | 当日卡 `pending` | 卡面显式标注，次日重算 |
| 2 | 时间维本地覆盖 4% | 异动/封板时刻大面积不可得 | 标 `unavailable` / `partial` |
| 3 | `ts_rt_min` 237 根 | 尾盘封板可能漏判 | 一律 `partial` + note，不报 `ok` |
| 4 | 批量走远端分钟会拖死 | 100 只跑 3 分钟 0 产出 | 批量默认只读本地，单票才走远端 |
| 5 | 披露快照按日采 | 无快照日 `narrative` 全 `unavailable` | note 写补法 |
| 6 | 涨停档位对 ST 靠名称 | 无名称时按涨幅反推 | 卡面 warning 留痕 |
