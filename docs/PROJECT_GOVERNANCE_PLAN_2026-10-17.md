# 并行开发期项目治理方案

> 状态：[CURRENT] + [PLAN]
> 日期：2026-10-17
> 适用范围：`C:/项目/老田的AI助手` 多 Agent、多服务、多数据根、多计划任务并行开发
> 决策主题：治理应先于开发，还是边开发边治理？

## 1. 结论先行

**不建议全项目停止开发后再治理，也不建议无门槛边开发边治理。采用“分层冻结 + 双轨并行 + 闸门治理”方案。**

具体结论：

1. **停止新增大功能 3–5 个工作日**，只处理会污染所有后续工作的基础治理项：事实源、路径、数据根、端口、任务、主干基线、发布/回滚和任务账本。
2. **不停止低风险、隔离型开发**：允许在独立 worktree/任务单中继续做单模块测试、文档补齐、只读页面、非生产实验和已批准的缺陷修复。
3. **生产面、共享数据面、主干、跨域契约面临时冻结**：未经治理门批准，不得新增跨域写入、改共享 schema、改端口、改计划任务、改生产启动器、改统一导航或直接写主干。
4. 基础治理达到“可继续开发”的最低门槛后，进入**治理随开发（Governance-as-a-Feature）**：每个工单同时交付代码、测试、事实记录、回滚方案和文档更新。
5. 对量化交易执行核心采用更严格的阶段门：先冻结新增真实执行能力，完成 G0–G6 基线/设计/实现/影子/人工小流量/发布/复盘，再恢复放量。

一句话：**先短暂停止扩张，先把地基和交通规则钉住；随后边开发边治理，但治理必须成为每个变更的交付物，而不是事后补文档。**

## 2. 为什么不能选择两个极端

### 2.1 全面停止后治理：优点与代价

优点：

- 可以集中清理路径、端口、数据根、旧服务和文档冲突；
- 治理期间不会继续制造新债；
- 适合主干已不可恢复、生产风险高、多人频繁互相覆盖的阶段。

代价：

- 当前项目仍有量化、门户、Agent Platform、Hermes 等持续运行需求；全部停开发会阻塞已明确的业务闭环；
- 并行 Agent 和已有任务不会自然消失，容易转为“无记录的私下修改”；
- 治理完成前无法验证规则是否适应真实开发，可能出现纸面治理；
- 3–5 天后一次性恢复开发，容易再次冲垮刚建立的规则。

**适用条件**：出现数据损坏、生产写面失控、主干无法回滚、共享资源持续互撞、权限或密钥泄露时，才升级到全停。

### 2.2 无条件边开发边治理：优点与代价

优点：

- 不阻塞业务和用户反馈；
- 治理规则在真实变更中验证；
- 可以按风险分层，先解决最痛的问题。

代价：

- 如果没有冻结区和闸门，治理会永远排在“下一项功能”后面；
- 路径漂移、重复服务、旧文档矛盾会继续扩散；
- 并行会话共享工作区时，审计结果可能被后续修改覆盖；
- 共享数据库、计划任务、端口和 nginx 的变更具有跨域影响，不能用普通模块开发流程处理。

**结论**：项目当前不适合无条件边开发边治理，必须先做一个短窗口的“扩张冻结”。

## 3. 当前项目的治理判断

### 特别原则：量化执行核心单独冻结

虽然不建议全项目停摆，但“会算错钱、会产生不可追责外部动作”的核心执行域必须单独提高等级：

- 交易执行、持仓一致性、授权幂等、跨进程并发、权限与迁移相关变更，先进入限定范围冻结；
- 只允许修复、测试、影子回放和证据补齐，不允许新增真实执行能力；
- 恢复顺序必须经过：基线（G0）→ 设计评审（G1）→ 实现验收（G2）→ 影子运行（G3）→ 人工小流量（G4）→ 发布（G5）→ 复盘（G6）；
- 任何阶段缺少可回滚证据、并发证明、授权边界或持仓一致性证据，保持 blocked，不得以“测试通过”替代。

这意味着本方案不是“一刀切停开发”，而是对不同风险域采用不同速度：业务展示和离线研究可以继续，金融执行核心必须先治理再放量。

### 已有基础（可复用）

- 已有项目总索引、架构复盘、运行态矩阵；
- 已有 `AGENTS.md`、worktree、工单、审计、幂等、审批和证据机制；
- 门户导航已有单一源：`DOMAIN_NAV_GROUPS → export_nav.py → nav.js`；
- Agent Platform 已有 M0/M1/M2 验收、事件回放和审批凭据；
- 已形成“只读先行、fail-visible、证据留痕、受控重启”的工程判例；
- 77 个门户导航路径已完成回归，`/org` 新版和 `/approvals` 入口已收口。

### 当前主要风险

1. **路径漂移**：`C:/项目`、`C:/aios` junction、历史 `E:/老田的AI助手` 并存；源码仍有旧绝对路径。
2. **共享资源冲突**：quant data、Neo4j、Ollama、nginx、8091 和计划任务会被多个会话共同使用。
3. **双副本误用**：Hermes 旧 `hermes-webui` 与当前 `hermes-webui-next` 并存；状态目录切换可能造成会话断裂。
4. **文档真相混杂**：plans、audit、deliverables、运行日志和当前实现混在一起。
5. **功能扩张快于收口**：portal/API 巨石拆分后，api_kg/api_backtest 等新巨石和新域接线仍可能继续增长。
6. **运行态不可从注册表推导**：任务“已注册”、端口“有进程”、测试“通过”都不能单独证明产线健康。

## 4. 治理分区：什么可以继续，什么必须冻结

| 分区 | 典型内容 | 当前策略 | 必要门禁 |
|---|---|---|---|
| G0 生产安全区 | 生产数据、Neo4j 写面、计划任务、密钥、外部推送 | 冻结新增变更 | 人工批准 + 备份/回滚 + 运行态验证 |
| G1 共享基础设施 | nginx、8091、8093、8791、Ollama、端口、启动器 | 冻结扩张，仅允许修复 | 变更单 + 互斥登记 + smoke + 回滚 |
| G2 跨域契约区 | API schema、事件契约、审批/幂等、数据根、导航源 | 冻结破坏性变更 | 契约测试 + 兼容策略 + 迁移记录 |
| G3 业务域开发区 | 单域页面、算法、分析器、Agent prompt、测试 | 可继续开发 | 独立 worktree + 工单 + 测试 |
| G4 文档与只读区 | 文档、只读报表、审计器、静态页面 | 可继续开发 | 事实源引用 + 状态标签 |
| G5 实验区 | Mock、离线回放、沙盒模型、原型 | 可继续开发 | 明确 `experimental/shadow`，禁止写生产 |

### 任何情况下都要升级审批的变更

- 删除或移动个人/共享目录文件；
- 改数据根、Neo4j schema、数据库表结构或共享 Parquet；
- 改 `nginx.conf`、端口、反代、计划任务、守护脚本；
- 变更统一事件契约、幂等键、审批状态机；
- 让 shadow/mock/live 语义切换；
- 改 token、密钥、外部推送、真实交易或发布开关；
- 同时触碰两个以上业务域或两个以上共享服务。

## 5. 三阶段落地方案

### 阶段 0：治理启动（半天）

目标：建立控制面，不碰业务功能。

交付：

- 冻结新增跨域功能；
- 所有在途工作登记到唯一工单账本，补 owner、范围、风险、状态和回滚点；
- 读取并登记 `C:/Temp/kg_sync_task.log`，确认共享数据面无冲突写入；
- 标记主干基线、生产版本、当前端口、当前数据根和当前守护任务；
- 每个并行会话声明“我改什么、不改什么、占用哪些资源”。

停止条件：无法列出当前在途变更、无法确定生产入口、无法确定数据根时，不进入下一阶段。

### 阶段 1：基础治理冻结（3–5 个工作日）

只治理会污染全局的项目。

#### P0-A 单一事实源

- 路径：代码、数据、Hermes state、worktree、日志统一记录；
- 端口：形成当前矩阵，明确用户入口与内部端口；
- 任务：任务名 → 启动器 → 解释器 → 产物 → 告警链五段映射；
- 服务：每个常驻服务只有一个生产启动器和一个守护来源；
- 文档：当前、审计、计划、历史四类分开。

#### P0-B 共享资源互斥

建立资源锁/登记表：

```text
resource: neo4j / quant_backtest/data / portal-nginx / portal-8091 /
          org-8093 / ollama / KG sync / scheduled-task
owner:    当前会话或工单
window:   开始时间-结束时间
mode:     read-only / write / restart
rollback: 回滚方式
```

规则：默认只读；写共享资源必须登记；重启必须使用受控入口；窗口结束必须写结果。

#### P0-C 可回滚发布

每个共享基础设施变更必须有：

1. 修改前快照或 diff；
2. 最小 smoke；
3. 回滚命令/文件；
4. 运行态验证；
5. 变更记录。

### 阶段 2：治理随开发（长期）

每个工单不再只有“代码完成”，而是五件套：

```text
代码/配置 + 测试 + 运行证据 + 文档更新 + 回滚说明
```

#### 工单最小字段

- ticket / owner / domain / risk_level；
- allowed_paths / forbidden_paths；
- input_source / output_artifact；
- shared_resources；
- acceptance_tests；
- rollout_mode：shadow / canary / production；
- rollback；
- evidence_path；
- docs_updated。

#### 合并门

- 单域低风险：测试通过 + 文件范围未越界；
- 共享基础设施：测试 + smoke + 审计 + 人工批准；
- 跨域契约：兼容性测试 + 迁移方案 + 双读/双写或回滚方案；
- 生产写面：必须人工批准，禁止 Agent 自行外发。

## 6. 并行开发协议

### 开工前

1. 先领工单，再建 worktree；
2. 读取当前索引、对应域规则和最近审计；
3. 宣布文件范围、排除范围、共享资源和预期产物；
4. 对共享资源执行登记；
5. 明确“本轮不顺手清理、不扩范围”。

### 施工中

- 同一文件禁止两个会话同时修改；
- 不直接改主干，不从旧 worktree 复制未知版本；
- 不把注释/文档当作实现证据；
- 不在 live 数据根做实验；
- 长跑命令输出落盘，进度看进程和产物 mtime；
- 发现与本任务无关的缺陷只登记，不顺手修。

### 收口时

- 运行最小测试和受影响域测试；
- 记录实际文件、端口、产物和状态；
- 更新当前文档或标记无文档影响；
- 由独立审查者检查范围、证据和回滚；
- 合并后重跑共享入口 smoke。

## 7. 治理指标

每周只看 8 个指标：

1. 在途工单中有 owner 的比例：目标 100%；
2. 越界修改数：目标 0；
3. 未登记共享资源写入：目标 0；
4. 变更带测试比例：目标 ≥95%；
5. 变更带回滚说明比例：目标 100%；
6. 运行态与文档不一致项：持续下降；
7. 旧路径/重复启动器新增数：目标 0；
8. 失败后可复现/可回滚比例：目标 100%。

不要以“文档数量”“提交数量”“通过测试数量”作为治理成功的唯一指标。

## 8. 何时真正全停开发

出现以下任一情况，切换为全停新增开发，仅保留事故修复和恢复工作：

- 生产数据发生不可逆损坏或来源无法证明；
- 共享 Neo4j/数据库写入无法识别责任人；
- 主干无法确定、无法回滚或多个副本同时对外服务；
- 密钥、Token、源码暴露到不受控范围；
- 计划任务/守护互相杀进程，导致核心服务持续抖动；
- 同一问题连续两轮治理后仍被并行开发重新引入；
- 关键事实源互相矛盾，且无法在 1 个工作日内确定真源。

全停期间只做：证据保全、备份、回滚、根因分析、事实源恢复和治理门修复。

## 10. 最终拍板建议

当前项目不需要“停摆式治理”，需要：

> **短期扩张冻结 + 分层治理 + 低风险开发不停 + 共享基础设施强闸门 + 每个工单内建治理交付物。**

建议立即执行的顺序：

1. 现在起暂停新增跨域大功能 3–5 个工作日；
2. 继续允许单域、只读、测试、文档和离线实验；
3. 先收口路径/数据根/端口/任务/启动器/主干基线；
4. 建立共享资源登记和变更窗口；
5. 之后恢复业务开发，但每项开发必须带测试、证据、文档和回滚；
6. 每周一次治理评审，每个里程碑一次事实源复核。

这比“全部停止后一次性整理”更适合当前项目：项目已足够复杂，治理必须进入生产节奏，而不能成为下一轮开发之前的一次性大扫除。
