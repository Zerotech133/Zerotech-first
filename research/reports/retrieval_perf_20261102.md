# 检索并发性能优化（P95 27s → 目标 ≤5s，2026-11-02）

## 结论

**达到目标：10 并发 retrieval P95 从 27.3s 降至 0.61s（≈44.8x），串行 P50 2.38s→0.06s；0 5xx、0 超时**

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 串行 retrieval P50 | 2.383s | **0.062s** |
| 串行 retrieval P95 | 2.531s | **0.087s** |
| 10 并发（200 次）P95 | **27.312s**（wave40 基线） | **0.61s** |
| 10 并发 200 次耗时 | 396.25s | **3.157s** |
| 5xx / 超时 | 0 / 1 | **0 / 0** |

- 目标：10 并发 retrieval P95 ≤5s → **已达成**（实测 0.61s，余量 4.39s）

## 诊断：慢点拆解

进程内计时（首次加载 vs 缓存命中）：

| 阶段 | 首次 | 缓存命中 |
|---|---|---|
| load_units（516 units） | 0.031s | 0.016s |
| load_corpus（4926 chunks） | **1.250s** | **0.000s** |

→ 主瓶颈 = **每次 retrieval 请求重复解析 rag_index_corpus.json（1.25s）** + 重复读取 knowledge_units；缓存命中后单请求耗时降至 ~0.06s（tokenize/fusion 可忽略）。

## 优化点

1. `tools/kb_corpus/kb_read_api.py`：`load_units` / `load_corpus` 增加**进程级缓存 + mtime_ns/size 签名失效**（数据文件变化自动重载，行为不变）；新增 `warm_cache()` 预热与 `cache_stats()` 统计。
2. `portal/api_kb_qa.py`：模块导入时 `warm_kb_cache()` 预热（经 `qa.kb_api()` 预热检索实际使用的模块实例；失败降级不影响请求）。
3. K-RESTART 重启加载新码：旧 PID 37524 → 新 PID 42248（flag 00:21:47、smoke OK 00:22:04、启动 00:22:05）。

## 前后对比（真实 HTTP）

| 用例 | 优化前 | 优化后 |
|---|---|---|
| 串行 10 次 | P50 2.383s / P95 2.531s / 0 错误 | **P50 0.062s / P95 0.087s / 0 错误** |
| 并发 10×20=200 | 200 成功 199、1 超时、429×0、P50 18.20s / P95 27.31s / P99 29.69s、耗时 396s | **200×49 成功、429×151（限流预期）、0 5xx、P95(all) 0.58s / 成功 P95 0.61s / P99 0.63s、耗时 3.16s** |

> 说明：优化后检索变快，200 并发在 3.2s 内超过 retrieval 60/分限流 → 151 次 429（限流预期行为，非故障）；成功请求 P95 0.61s。

## 剩余瓶颈与调参

- retrieval 60/分限流：检索变快后并发 200 次在 3.2s 内触发 151 次 429 —— 灰度放量前需调高限流（如 120–300/分）或按 IP/租户分桶
- 首次请求冷启动仍会加载缓存（预热已在 code 中，下一次重启后启动即预热）
- 搜索 CPU 成本 ~60ms/请求（tokenize/fusion），当前可忽略
- 单进程限流计数：多实例部署需一致性方案

- 性能优化基准仅供上线评审参考，不构成投资建议。
